# Empirical studies of AI-generated code quality and security
> Code T11 · slug ai-code-quality-studies · verified 2026-09-23 · counts: verified 9 / corrected 6 / downgraded 4 / dropped 0

## Summary

Sources were read in September 2026 and every cited URL was re-opened for this check. Versions used: Veracode GenAI Code Security Report 2025 (blog) and its Spring 2026 update (24 Mar 2026), GitClear 2025 ("4x Growth in Code Clones") and 2026 ("The Maintainability Gap", Jan 2026), DORA 2024 report (PDF v2024.3) and the DORA insight "Balancing AI tensions" (10 Mar 2026, drawing on the 2025 research), GitGuardian State of Secrets Sprawl 2025 and 2026, OWASP Top 10 for LLM Apps 2025 (LLM09), OpenSSF "Security-Focused Guide for AI Code Assistant Instructions" (2025-08-01), CodeRabbit "State of AI vs Human Code Generation" (17 Dec 2025), Sonar "Coding Personalities" (Aug 2025) plus the GPT-5 update (27 Aug 2025), OX "Army of Juniors" (23 Oct 2025), and several 2026 MSR/arXiv studies of agentic pull requests.

Peer-reviewed anchors (venues confirmed): Pearce et al. (IEEE S&P 2022), Perry et al. (CCS 2023), Asare et al. (Empirical Software Engineering 2023), Liu et al. (TOSEM 2024), Fu et al. (TOSEM 2025), Spracklen et al. (USENIX Security 2025, Distinguished Paper), EffiBench (NeurIPS 2024), BaxBench (ICML 2025, spotlight poster, confirmed via OpenReview), the Cursor difference-in-differences study (MSR 2026), the deprecated-API study (ICSE 2025), the PR message-code inconsistency study (MSR 2026 Mining Challenge track), and the test-oracle study (accepted at IEEE AITest 2026 per its arXiv page).

**Ranked list of defect categories reported as over-represented in AI-written code.** The ranking is the researcher's synthesis (effect size x evidence strength x harm). It is not a ranking any single source produced. Give these extra review weight, in this order:

1. **Output encoding and injection** (XSS, log injection, command and code injection). Veracode Spring 2026: XSS pass rate 15%, log injection 13%, but SQL injection 82%. Veracode says the overall pass rate is "stubbornly stuck at approximately 55% – virtually identical to where they stood two years ago". Fu et al.: CWE-94 is 9.87% and CWE-79 is 9.55% of weaknesses. Pearce et al.: about 40% of 1,689 programs were vulnerable.
2. **Dependencies that do not exist or are vulnerable.** Spracklen: 19.7% of 2.23M package references (from 576,000 code samples) did not exist, with 205,474 unique fake names. 2026 frontier models: 4.62-6.10%, with 127 names that all five models invent and 53 of them still registrable. Endor Labs: 34% of dependency versions hallucinated and 49% with known vulnerabilities.
3. **Duplication and failure to reuse existing code (contested).** GitClear reports copy/paste rising from 8.3% to 12.3% (2021-2024), duplicated lines up 81% (40.3 to 73.0 per million changed lines), refactoring moves falling from 21% (2022) to 3.8% (2026 YTD), and cross-file calls down 35%. The data is correlational. The peer-reviewed Cursor difference-in-differences study found no significant duplication effect.
4. **Complexity and sheer volume of code.** After Cursor adoption, static-analysis warnings rose 30.3% and complexity rose 41.6% (MSR '26 v3, 806 repositories), and the study calls both "substantial and persistent". The result depends on the estimator: the Callaway and Sant'Anna estimator gives negative but statistically insignificant estimates for both. A 100% rise in complexity is followed by a 64.5% drop in later velocity. In one small preprint, total lines of code correlate with architecture smells at rho = 0.94.
5. **Error handling, in both directions.** Broad exception catching is the most frequent AI-introduced smell (8.5%). GitClear reports "error-masking" up 47% but gives no definition. CodeRabbit found about 2x more error-handling gaps. Error-handling constructs are the least-tested code in agent PRs (miss rates of 86.0% in Java and 81.0% in Python).
6. **Excessive I/O and inefficient algorithms.** CodeRabbit (vendor) found about 8x more excessive-I/O findings, in a category that is rare in absolute terms. EffiBench: GPT-4 solutions take 3.12x the execution time of reference solutions on average.
7. **Hard-coded secrets.** Repositories using Copilot leak secrets 40% more often (6.4% vs 4.61%). Commits co-authored by Claude Code leak at about 2x the baseline. 24,008 secrets were found in MCP config files.
8. **Authorization and design-level flaws.** Apiiro (via CSA): privilege-escalation paths up 322% and design flaws up 153%. The Georgia Tech Vibe Security Radar confirmed 74 AI-linked vulnerabilities (14 critical, 25 high), with types *including* command injection, auth bypass and SSRF. BaxBench: exploits worked on about half of the functionally correct backends.
9. **Path traversal:** the top security rule hit in AI-authored commits in the wild (1.8% of all issues).
10. **Weak randomness and weak cryptography.** CWE-330 is the #1 weakness in Copilot code found in GitHub projects (18.15%). Veracode's weak-algorithm tasks fail 14% of the time (86% pass).
11. **Dead code, unused code and undefined references.** Unused variables or parameters are 5.8% of issues, unused arguments 5.0%, and undefined references 4.9%.
12. **Deprecated APIs.** 25-38% of completions use deprecated APIs, rising to 70-90% when the surrounding code is already outdated (2024-era models).
13. **Tests with weak or no oracles.** 80.2% of test patches written by agents have weak or no oracle signals. That agents delete or disable failing tests is reported only by practitioners (Kent Beck, HN); no study has measured it.
14. **Concurrency, ordering, resource and control-flow mistakes:** about 2x more often (vendor-only evidence).
15. **Readability, naming and formatting:** 3x, about 2x and 2.66x more often (vendor-only). This is cheap to fix with formatters.
16. **PR descriptions that claim things the code does not do.** 45.4% of high-inconsistency agent PRs claim changes that were never made (but only 1.7% of PRs are high-inconsistency).

**Categories that are not over-represented.** In CodeRabbit's data, spelling mistakes and testability issues are worse in human code. OX claims AI code has no more vulnerabilities *per line*. Asare et al. (EMSE) found Copilot reproduces the original human vulnerability less often (33%) than it would need to be "as bad as humans". GitHub's own RCT found Copilot-assisted code passed all unit tests more often and scored slightly higher on readability. None of these three measures the same thing as the others, so they do not add up to "AI code is no worse".

**Weaknesses in the evidence.** Most numbers come from vendors who sell detection tools. Attributing a given line to AI is unreliable, because it relies on co-author trailers and bot metadata that users can strip. A hardening pass run by an AI can itself make security worse: one preprint measured a 37.6% rise in critical vulnerabilities after 5 rounds of unguided "improvements". So every fix should be tied to a tool finding, re-checked after the change, and shipped in small batches.

## Findings

### T11-F02 — Presume every untrusted-data-to-sink path vulnerable; check XSS and log injection first, and check SQL identifiers separately
- **Grade:** A · **Verdict:** CORRECTED. (audit correction: the 80-task count is on the cited Veracode page after all, "80 coding tasks" in 4 languages; the 70-72% pass rate belongs to "the GPT-5 series with extended reasoning", not to OpenAI reasoning models in general.) An earlier pass removed "Veracode's 80 tasks" from the counterpoint as unconfirmable; the citation audit re-fetched the page and found "80 coding tasks spanning common development scenarios" in "4 programming languages: Java, JavaScript, C#, and Python", aimed at the four CWE classes (as ai-code-smells-practitioners T12-F18 states), so the count is restored. Also noted: Veracode measures XSS as CWE-80, and the pass-rate ordering (XSS and log injection worse than SQLi) comes from a vendor only. The peer-reviewed sources support the general injection prevalence, not that ordering.
- **Rule:** Every place where untrusted data reaches HTML, logs, shell, eval or a query is presumed vulnerable until shown otherwise. Check XSS (CWE-79/80) and log injection (CWE-117) first, because Veracode's models fail these far more often than SQL injection. Check SQL identifiers (ORDER BY, column and table names) separately, because parameterized queries do not cover them.
- **Rationale:** Veracode Spring 2026 (150+ models): pass rates of 15% for XSS and 13% for log injection, against 82% for SQL injection and 86% for insecure crypto. The overall pass rate is about 55%, "virtually identical to where they stood two years ago", and "model size has only a very small effect". In real GitHub projects, Fu et al. (TOSEM 2025) found CWE-94 code injection (9.87%), CWE-79 XSS (9.55%) and CWE-78 OS command injection (6.21%) among the top weaknesses. Pearce et al. found about 40% of 1,689 Copilot programs vulnerable. Sonar found injection and path traversal in every model tested.
- **Evidence:**
  - [Spring 2026 GenAI Code Security Update](https://www.veracode.com/blog/spring-2026-genai-code-security/) — Veracode, 2026 (24 Mar) — industry report — "security pass rates remain stubbornly stuck at approximately 55% – virtually identical to where they stood two years ago"; CWE-89 82%, CWE-327 86%, CWE-80 15%, CWE-117 13%; Java 29%, Python 62%; "80 coding tasks" in "4 programming languages: Java, JavaScript, C#, and Python"; "The GPT-5 series with extended reasoning achieved security pass rates between 70-72%" (the page says only in general terms that "OpenAI's reasoning models posted the largest step-ups") — confirmed; task count and GPT-5 scope restored by the citation audit.
  - [Insights from 2025 GenAI Code Security Report](https://www.veracode.com/blog/genai-code-security-report/) — Veracode, 2025 — industry report — "45% of code samples failed security tests"; XSS failed "in 86% of relevant code samples"; "Security performance remained flat, regardless of model size or training sophistication"; 100+ LLMs — confirmed. The task count is not stated on the blog.
  - [Security Weaknesses of Copilot-Generated Code in GitHub Projects](https://arxiv.org/html/2310.02059v3) — Fu, Liang, Tahir, Li, Shahin, Yu, Chen, 2025 — peer-reviewed (TOSEM, DOI 10.1145/3716848, confirmed via Crossref) — 733 snippets; 29.5% of Python and 24.2% of JS snippets affected; 628 weaknesses across 43 CWEs; CWE-94 62 (9.87%), CWE-79 60 (9.55%), CWE-78 39 (6.21%); CodeQL plus Bandit and ESLint — confirmed.
  - [Asleep at the Keyboard?](https://arxiv.org/abs/2108.09293) — Pearce, Ahmad, Tan, Dolan-Gavitt, Karri, 2022 — peer-reviewed (IEEE S&P) — "89 different scenarios ... 1,689 programs. Of these, we found approximately 40% to be vulnerable" — confirmed.
  - [The Coding Personalities of Leading LLMs](https://www.sonarsource.com/the-coding-personalities-of-leading-llms/) — Sonar, 2025 — industry report — "Injection flaws, path-traversal, and insecure cryptography are prevalent across all models"; 4,442 tasks per model — confirmed.
  - [Log Injection (js/log-injection)](https://codeql.github.com/codeql-query-help/javascript/js-log-injection/) — GitHub CodeQL — official docs — CWE-117: "If unsanitized user input is written to a log entry, a malicious user may be able to forge new log entries"; remove line breaks, or HTML-encode for HTML-viewed logs — confirmed.
- **Detect:** CodeQL security queries (js/xss, js/log-injection and the Python and Java equivalents), Semgrep security rulesets, and Bandit for Python. Grep sinks: `rg -n "dangerouslySetInnerHTML|innerHTML *=|v-html|mark_safe|\|safe|eval\(|new Function\(|child_process|shell=True|os\.system"`. For logs: `rg -n "(log|logger)\.(info|warn|error|debug)\(.*(req\.|request\.|params|body)"`. For SQL, find string building (f-strings, template literals, +) inside `execute(`/`query(` calls, then check every ORDER BY, table name or column name built from input against an allow-list.
- **Tools:** CodeQL, Semgrep, Bandit, ripgrep
- **Applies to:** Web backends and frontends, CLIs that shell out, and any code that logs request data. Java had the worst pass rate (29%).
- **When not to apply / counterpoints:** Benchmarks (Veracode's 80 curated tasks, Pearce's scenarios) prompt for code that is prone to these flaws. Real-repo rates are lower: Fu found 24-30% of snippets affected. Log injection is mostly harmless when logs go to a structured JSON sink that escapes newlines. Framework auto-escaping (React JSX, Jinja2 autoescape) already neutralizes most XSS unless it is explicitly bypassed. The ORDER BY check comes from practitioner experience (see Practitioner voice), not from a study.
- **Fix risk:** medium

### T11-F03 — Verify every dependency exists, is the intended project, and is not a fresh look-alike; pin non-vulnerable versions
- **Grade:** A · **Verdict:** CORRECTED. (1) "2.23M samples" was wrong: Spracklen generated **576,000 code samples**, which produced 2.23 million package references, of which 440,445 (19.7%) were hallucinated. (2) "About 45% came back on every run": the ;login: summary says ~45%, but the paper body says "43% of hallucinated packages were repeated in all 10 queries", so the range is now 43-45%. (3) Endor's sample is described more precisely. (4) Distinguished Paper status was confirmed on the USENIX page.
- **Rule:** Check that every declared and imported third-party package exists in the intended registry, is the intended project, and is not a newly registered look-alike. Pin versions that exist and have no known vulnerabilities. If a working build resolves a package name that the team cannot account for, treat it as a possible slopsquat, not as proof the package is legitimate.
- **Rationale:** Spracklen et al. (USENIX Security 2025, Distinguished Paper) tested 16 models, 576,000 code samples and 2.23M package references. 19.7% of the references pointed to packages that do not exist, giving 205,474 unique fake names. Commercial models were at ≥5.2% and open-source models at 21.7%. 43-45% of hallucinated names recur on every repeat of the same prompt, which makes them predictable attack targets. A 2026 independent replication on five frontier models found 4.62-6.10%, but 127 names were invented identically by all five models and 53 were still registrable. Endor Labs (2025) reports 34% of AI-suggested dependency versions hallucinated and 49% of versions imported by agents carrying known vulnerabilities. An empty placeholder under a hallucinated name ("huggingface-cli") got over 30,000 downloads in three months.
- **Evidence:**
  - [We Have a Package for You! (;login: summary)](https://www.usenix.org/publications/loginonline/we-have-package-you-comprehensive-analysis-package-hallucinations-code) — Spracklen, Wijewickrama, Sakib, Maiti, Viswanath, Jadliwala, 2025 — peer-reviewed summary — "averaging 19.6%"; commercial ~5% vs open-source ~21%; 205,474 unique non-existent packages; ~45% consistently regenerated — confirmed.
  - [USENIX Security '25 paper page](https://www.usenix.org/conference/usenixsecurity25/presentation/spracklen) and [arXiv:2406.10279](https://arxiv.org/html/2406.10279) — same authors, 2025 — peer-reviewed — "576,000 code samples"; "at least 5.2% for commercial models and 21.7% for open-source models"; "2.23 million packages ... of which 440,445 (19.7%) were determined to be hallucinations"; "43% of hallucinated packages were repeated in all 10 queries"; Distinguished Paper Award — confirmed.
  - [The Range Shrinks, the Threat Remains (arXiv:2605.17062)](https://arxiv.org/abs/2605.17062) — Aleksandr Churilov (independent researcher), 2026 — preprint — Claude Sonnet 4.6, Claude Haiku 4.5, GPT-5.4-mini, Gemini 2.5 Pro, DeepSeek V3.2; 4.62% (Haiku 4.5) to 6.10% (GPT-5.4-mini); 127 shared names (109 PyPI, 18 npm), 53 registrable — confirmed.
  - [State of Dependency Management 2025](https://www.endorlabs.com/lp/state-of-dependency-management-2025) — Endor Labs, 2025 — industry report — "1 in 5 dependency versions recommended by AI coding assistants are safe to use"; "49% of dependency versions imported by AI coding agents have known vulnerabilities"; "34% of dependency versions are hallucinated"; the sample combines 10,663 MCP-server repos with tests of AI recommendations across PyPI, npm, Maven and NuGet — confirmed.
  - [Security-Focused Guide for AI Code Assistant Instructions](https://best.openssf.org/Security-Focused-Guide-for-AI-Code-Assistant-Instructions) — OpenSSF Best Practices and AI/ML WGs, 2025-08-01 — standard/guide — "Do not add dependencies that may be malicious or hallucinated."; "Avoid adding obscure dependencies if a standard library or well-known package can do the same job."; "Run or simulate tools like CodeQL, Bandit, Semgrep, or OWASP Dependency-Check." — confirmed.
  - [LLM09:2025 Misinformation](https://genai.owasp.org/llmrisk/llm092025-misinformation/) — OWASP GenAI Security Project, 2025 — standard — "The model suggests insecure or non-existent code libraries, which can introduce vulnerabilities when integrated into software systems." — confirmed.
  - [Slopsquatting](https://en.wikipedia.org/wiki/Slopsquatting) — Wikipedia, 2026 — other — huggingface-cli placeholder got "over 30,000 downloads" in three months; "As of July 2026, there has not yet been a reported case where slopsquatting has been used as a cyberattack" — confirmed.
- **Detect:** List the direct dependencies from the manifests (package.json, requirements*.txt, pyproject.toml, go.mod, pom.xml), plus imports that have no manifest entry. npm: `npm view <pkg> time repository.url versions`. PyPI: `GET https://pypi.org/pypi/<pkg>/json` (a non-200 response means it is not on PyPI). Flag packages created recently, with few releases, no source repository, or a name one edit away from a popular package. Then run SCA (`npm audit`, OWASP Dependency-Check, or the ecosystem's equivalent).
- **Tools:** npm view, PyPI JSON API, OWASP Dependency-Check, npm audit, SCA tools (e.g. Socket)
- **Applies to:** All ecosystems that use public registries (npm, PyPI, Maven, NuGet). Most critical where agents can run install commands.
- **When not to apply / counterpoints:** Rates fell sharply for 2026 frontier models. Whether slopsquatting has been exploited in the wild is disputed: Wikipedia (July 2026) reports no confirmed attack, while the CSA research note (Apr 2026) describes a confirmed malicious "unused-imports" package that ran credential-stealing post-install scripts. Endor's agent-import figure is partly drawn from MCP-server repositories. Private or scoped packages legitimately return 404 on public registries.
- **Fix risk:** low

### T11-F05 — Treat surplus volume and complexity as the main maintainability defect; prefer deleting and simplifying
- **Grade:** B (was A) · **Verdict:** DOWNGRADED, with corrections. The core claim rests on one peer-reviewed quasi-experiment about one tool (Cursor, OSS GitHub repos), plus vendor benchmarks and small preprints. The sub-items (speculative abstractions, redundant defensive checks) are not measured by any cited source. Corrections: (1) The cited URL (v2 HTML) carries the earlier title "Does AI-Assisted Coding Deliver? A Difference-in-Differences Study of Cursor's Impact on Software Projects". The published MSR '26 title is "Speed at the Cost of Quality..." (v3, 26 Jan 2026), and the canonical link is now the abs page. Authors: Hao He, Courtney Miller, Shyam Agarwal, Christian Kästner, Bogdan Vasilescu (CMU). (2) "The most verbose model wrote 370,816 LOC" was wrong: in Sonar's later GPT-5 update, GPT-5-minimal wrote 490,010 LOC. The first-round comparison was Claude Sonnet 4 against OpenCoder-8B. (3) The rho = 0.94 comes from a MetaGPT experiment with 5 scenarios x 4 stages, analysed with PyExamine. (audit correction: the numbers now come from the published v3 rather than v2: 806 repositories, warnings +30.3%, complexity +41.6%; v3's Callaway and Sant'Anna estimator gives negative, insignificant estimates, and heavy adopters may show modest duplication increases.)
  - The citation audit found that the earlier figures (807 repos, +29.7% warnings, +40.7% complexity) were v2's. v3 says "static analysis warnings increase significantly by 30.3%, and code complexity increases by 41.6%" (Table 2: +30.26% ±6.66%, +41.64% ±7.62%) over "806 repositories". The 1,380 controls, the +281.3% month-1 lines, the 64.5%/50.3% velocity figures and the insignificant duplication effect are the same in v2 and v3.
  - v3 adds two caveats. The Callaway and Sant'Anna estimator "yields negative but statistically insignificant estimates" for warnings and complexity (−10.49%, −3.80%), while the Borusyak and TWFE estimators find significant increases. And "heavy Cursor adopters may exhibit modest increases" in duplication.
- **Rule:** Treat surplus volume and complexity as the main maintainability defect in AI-written code. Look for functions above the project's cognitive-complexity threshold, speculative abstractions and options, redundant defensive checks on values the type system already guarantees, and handling for edge cases that cannot occur. Prefer deleting and simplifying over adding structure.
- **Rationale:** A difference-in-differences study (806 Cursor-adopting repos vs 1,380 matched controls, MSR 2026, v3) found a "large, but transient" velocity gain (+281.3% lines added in month 1) and a "substantial and persistent increase" in static-analysis warnings (+30.3%) and code complexity (+41.6%). The increase is estimator-sensitive: Borusyak and TWFE find it significant, Callaway and Sant'Anna do not. Its panel-GMM analysis estimates that a 100% increase in complexity or warnings "causes a 64.5% and 50.3% decrease in development velocity". In Sonar's benchmark, Claude Sonnet 4 wrote 370,816 LOC against 120,288 for OpenCoder-8B on the same tasks, with cognitive complexity of 47,649 vs 13,965. GPT-5-minimal wrote 490,010 LOC with 3.90 issues per correct solution. In a small preprint, total LOC correlated with architecture smells at rho = 0.94, and requirement specificity had no effect (p > 0.8).
- **Evidence:**
  - [Speed at the Cost of Quality (arXiv:2511.04427, MSR '26)](https://arxiv.org/abs/2511.04427) — He, Miller, Agarwal, Kästner, Vasilescu (CMU), 2026 — peer-reviewed (MSR '26, Rio de Janeiro) — v3: 806 treated / 1,380 controls; warnings +30.3%, complexity +41.6% (Table 2: +30.26% ±6.66%, +41.64% ±7.62%; v2 had 807, +29.7%, +40.7%); Callaway and Sant'Anna estimates −10.49% and −3.80%, "negative but statistically insignificant"; "a 100% increase in code complexity and static analysis warnings causes a 64.5% and 50.3% decrease in development velocity"; measured with "a local SonarQube Community server"; "no significant effect" on duplicate line density, though "heavy Cursor adopters may exhibit modest increases" — confirmed (v2 HTML read, v3 abs page read; v3 figures and caveats added by the citation audit).
  - [Diving into the 3 traits that define your LLM's coding personality](https://www.sonarsource.com/blog/llm-coding-personality-traits/) — Sonar, 2025 (28 Aug) — industry report — Claude Sonnet 4 "370,816 lines of code" vs OpenCoder-8B "120,288"; cognitive complexity 47,649 vs 13,965 — confirmed.
  - [The Coding Personalities of Leading LLMs - GPT-5 Update](https://www.sonarsource.com/blog/the-coding-personalities-of-leading-llms-gpt-5-update/) — Sonar, 2025 (27 Aug) — industry report — "490,010 lines of code, over 30% more than the top-performing Claude Sonnet 4"; "3.90 issues for every correct solution"; "code smell density of 25.28 per KLOC" — confirmed.
  - [AI-Generated Smells (arXiv:2605.02741)](https://arxiv.org/html/2605.02741v1) — Yue Cai Zhu, Nikolaos Tsantalis, Peter C. Rigby (Concordia), 2026 — preprint — "Total Lines of Code (TLoC) exhibited a near-perfect positive correlation with architectural smells (ρ=0.94, p<0.001)"; specificity "had no statistical impact on any smell category (p>0.8)"; PyExamine — confirmed.
  - [Beyond Functional Correctness (arXiv:2604.06373)](https://arxiv.org/html/2604.06373v1) — Kashif, Li, Liang, Tahir, Feng, Li, Shahin, 2026 — preprint — 10 Cursor projects, 1,305 CodeScene issues: Complex Methods 377 (27.9%), Large Methods 171 (12.6%), Complex Conditionals 112 (8.2%) — confirmed. There is no human baseline.
- **Detect:** SonarQube (cognitive complexity per function, issues per KLOC) or CodeScene hotspots. Rank functions by complexity x change frequency. Manual checks: (a) null or undefined checks on values that are non-nullable by type or were validated upstream; (b) config options, flags or abstract base classes with exactly one caller or implementation; (c) branches for states the domain cannot produce. Compare LOC per feature with similar modules.
- **Tools:** SonarQube, CodeScene, git log (churn)
- **Applies to:** All languages; strongest for agent-generated multi-file projects.
- **When not to apply / counterpoints:** Some complexity is essential (parsers, protocol state machines). Defensive checks at trust boundaries (external input, deserialization, FFI) must stay even if they look redundant. The Sonar figures come from Java benchmark tasks, not real repositories. The DiD study covers Cursor only, in OSS projects, with data from Jan 2024 to Aug 2025, and its warnings and complexity increases are not significant under the Callaway and Sant'Anna estimator.
- **Fix risk:** medium

### T11-F17 — When an AI agent hardens code, tie every change to a tool finding, re-scan after each change, cap iterations, and escalate security diffs
- **Grade:** B · **Verdict:** VERIFIED
- **Rule:** When an AI agent does the hardening, tie every change to a concrete tool finding (rule id plus location). After each change, re-run the same scanners and the tests, and reject any change that adds findings. Cap automatic fix iterations per finding. Send security-sensitive diffs to a human. Never accept the agent's own claim that something is "secure" or "fixed".
- **Rationale:** A controlled experiment (400 samples, 40 rounds, four prompting strategies) found a "37.6% increase in critical vulnerabilities after just five iterations". Grounding the prompt helps: Copilot Chat fixed 19.3% of security issues with plain /fix, and 55.5% with an enhanced prompt that included the warning (Fu, TOSEM). ChatGPT given static-analysis feedback improved code quality by more than 20%, but only partially (Liu, TOSEM 2024). Perry et al. (CCS 2023) found participants with an AI assistant wrote significantly less secure code and were more likely to believe it was secure. METR found experienced developers 19% slower while they estimated a 20% speed-up.
- **Evidence:**
  - [Security Degradation in Iterative AI Code Generation (arXiv:2506.11022)](https://arxiv.org/abs/2506.11022) — Shukla, Joshi, Syed, 2025 — preprint — "400 code samples across 40 rounds of 'improvements' using four distinct prompting strategies"; "37.6% increase in critical vulnerabilities after just five iterations" — confirmed.
  - [Security Weaknesses of Copilot-Generated Code in GitHub Projects](https://arxiv.org/html/2310.02059v3) — Fu et al., 2025 — peer-reviewed (TOSEM) — "/fix command can fix 19.3% of security issues", "enhanced prompt raises the rate to 55.5%" — confirmed.
  - [Do Users Write More Insecure Code with AI Assistants?](https://arxiv.org/abs/2211.03622) — Perry, Srivastava, Kumar, Boneh, 2023 — peer-reviewed (CCS '23, pp. 2785-2799) — codex-davinci-002 users "wrote significantly less secure code"; "more likely to believe they wrote secure code"; those who "trusted the AI less ... provided code with fewer security vulnerabilities" — confirmed (abstract).
  - [Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity](https://arxiv.org/abs/2507.09089) — METR, 2025 — preprint (RCT) — 16 developers, 246 tasks; forecast -24%, post-hoc estimate -20%, actual +19% completion time — confirmed.
  - [Refining ChatGPT-Generated Code](https://arxiv.org/abs/2307.12596) — Liu, Le-Cong, Widyasari, Tantithamthavorn, Li, Le, Lo, 2024 — peer-reviewed (TOSEM, DOI 10.1145/3643674, confirmed via Crossref) — "ChatGPT can partially address these challenges, improving code quality by more than 20%" — confirmed.
- **Detect:** Process check. Keep a findings ledger (tool, rule id, file:line, before and after count). After each fix, run the tests and scanners again and diff the finding sets (`semgrep --json`, `codeql database analyze ... --format=sarif-latest`, linter JSON output). Any new high or critical finding reverts the change. Stopping after 2-3 failed attempts on one finding is a heuristic, not a sourced threshold.
- **Tools:** Semgrep, CodeQL, SonarQube, project test suite, SARIF diff
- **Applies to:** Any AI-driven refactoring or hardening pass, including this skill.
- **When not to apply / counterpoints:** The 37.6% figure comes from one unrefereed preprint with synthetic samples. METR studied early-2025 tools with 16 developers, and the authors warn against generalizing. Perry used codex-davinci-002, now obsolete. Veracode Spring 2026 shows the GPT-5 series with extended reasoning at 70-72% pass, so newer models may degrade less.
- **Fix risk:** low

### T11-F09 — Inventory entry points and verify authn, object-level authz, validation and SSRF restrictions on each
- **Grade:** B · **Verdict:** CORRECTED. (1) Georgia Tech lists command injection, auth bypass and SSRF as types *included* among the 74 cases, not as the "main" types. ### T11-F06 — Audit error handling in both directions: remove masking, add missing guards, and test error paths first
- **Grade:** B · **Verdict:** VERIFIED

- **Tools:** Pylint, ESLint, ripgrep, coverage.py / istanbul (nyc/c8)

- **When not to apply / counterpoints:** Top-level boundary handlers are legitimate: a request handler, worker supervisor or main loop that logs, reports and converts errors into a response. So is best-effort telemetry. The GitClear metric has no public definition. One HN user (ryandrake) makes the opposite complaint ("Null checks everywhere"), which is why the check runs in both directions. "Debt Behind" counts lint hits in Python/JS/TS only.

### T11-F14 — Check that tests actually test something: oracles, skips, deletions, and error-path coverage
- **Grade:** B · **Verdict:** CORRECTED. (1) arXiv:2606.18168 is now listed as accepted at the 8th IEEE International Conference on AI Testing (AITest 2026), so it is peer-reviewed at a conference rather than an unrefereed preprint. (2) Authors were added for 2607.18057 and 2601.21194. - **Detect:** `git log --shortstat` per hardening commit. Flag commits that touch more than one defect category, or diffs too large to review in one sitting. Each commit message names the finding ids it resolves.
- **Tools:** git
- **Applies to:** Any hardening or refactoring pass.
- **When not to apply / counterpoints:** The DORA figures are survey-based models, not causal estimates. The batch-size mechanism is DORA's hypothesis, not a measurement, and the 2024 and 2025/26 throughput findings point in opposite directions. Faros is a vendor. Some refactorings (codebase-wide renames) are atomic and cannot be split.
- **Fix risk:** low

### T11-F19 — Judge severity by category and evidence, not by AI authorship; handle formatting drift with autofix
- **Grade:** B · **Verdict:** VERIFIED
- **Rule:** Judge severity by defect category and evidence, not by whether AI wrote the code. Do not flag code as defective only because AI wrote it. Handle formatting and naming drift with the project's formatter and linter autofix, not with manual rewrites.
- **Rationale:** The evidence is not one-sided. In CodeRabbit's own data, human PRs had more spelling errors (18.92 vs 10.77) and more testability issues (23.65 vs 17.85), and "none of the noted vulnerabilities were unique to AI-generated code". Asare et al. (EMSE 2023) found Copilot replicated the original vulnerable code about 33% of the time and the fixed code 25% of the time, and concluded it is not as bad as humans. GitHub's RCT (202 developers) found Copilot-assisted code 53.2% more likely to pass all 10 unit tests, with readability +3.62%. OX says AI code has no more vulnerabilities per line. Agentic refactorings give "small but statistically significant improvements in structural metrics".
- **Evidence:**
  - [AI-assisted coding creates more problems - report](https://www.infoworld.com/article/4109129/ai-assisted-coding-creates-more-problems-report.html) — InfoWorld, 2025 (19 Dec) — trade press — "Spelling errors were almost twice as common in human-authored code (18.92 vs. 10.77)"; "Testability issues also appeared more frequently in human code (23.65 vs. 17.85)"; "While none of the noted vulnerabilities were unique to AI-generated code, they appeared significantly more often" — confirmed.
  - [Is GitHub's Copilot as Bad as Humans at Introducing Vulnerabilities in Code?](https://arxiv.org/abs/2204.04741) — Asare, Nagappan, Asokan, 2023 — peer-reviewed (Empirical Software Engineering, DOI 10.1007/s10664-023-10380-1) — "Copilot replicates the original vulnerable code about 33% of the time while replicating the fixed code at a 25% rate"; C/C++ — confirmed.
  - [Does GitHub Copilot improve code quality?](https://github.blog/news-insights/research/does-github-copilot-improve-code-quality-heres-what-the-data-says/) — GitHub, 2024 (18 Nov) — vendor study — 202 developers; "53.2% greater likelihood of passing all 10 unit tests"; readability +3.62%, maintainability +2.47% — confirmed.
  - [Agentic Refactoring (arXiv:2511.04824)](https://arxiv.org/abs/2511.04824) — arXiv, 2025 — preprint — 15,451 refactorings in Java projects; "small but statistically significant improvements in structural metrics"; Change Variable Type 11.8%, Rename Parameter 10.4%, Rename Variable 8.5% — confirmed.
- **Detect:** Process check. Each reported finding must name a tool rule id or a concrete failing scenario. Reject findings whose only justification is "looks AI-generated". Run the formatter (prettier, black/ruff format, gofmt, rustfmt) and lint autofix as a separate commit before the semantic review.
- **Tools:** prettier, black / ruff format, gofmt, rustfmt, ESLint --fix
- **Applies to:** All reviews of mixed human and AI codebases.
- **When not to apply / counterpoints:** GitHub's study is a vendor evaluating its own product on one task (API endpoints). Asare used 2022 Copilot on C/C++ vulnerabilities. OX gives no per-line method publicly. None of these erase the category-level over-representation in other findings. They argue for calibrating by category, not for skipping review.
- **Fix risk:** low

### T11-F07 — Look for I/O in loops, N+1 queries, repeated reads, and worse-than-needed complexity on hot paths; profile first
- **Grade:** C for the I/O-in-loops part (vendor-only); B for the algorithmic-efficiency part (EffiBench) · **Verdict:** DOWNGRADED. The headline "8x excessive I/O" comes from one vendor study of 470 PRs, in a category CodeRabbit itself calls rare. EffiBench is peer-reviewed but measures LeetCode-style algorithmic efficiency, not application I/O. Nothing independent supports the I/O ratio.
- **Rule:** Look for I/O and network or database calls inside loops, N+1 query patterns, repeated reads of the same file or resource, and algorithms of a higher complexity class than needed on hot paths. Profile before changing anything.
- **Rationale:** CodeRabbit: "Excessive I/O operations were ~8x more common in AI-authored PRs". EffiBench (NeurIPS 2024, 1,000 LeetCode problems, 42 models): GPT-4 code took on average 3.12x the execution time of canonical human solutions, and up to 13.89x the time and 43.92x the memory in the worst cases.
- **Evidence:**
  - [Our new report: AI code creates 1.7x more problems](https://dev.to/coderabbitai/our-new-report-ai-code-creates-17x-more-problems-7lh) — CodeRabbit, 2025 — vendor blog — "Excessive I/O operations were ~8x more common in AI-authored PRs"; performance regressions are rare overall but disproportionately AI-driven — confirmed.
  - [EffiBench](https://arxiv.org/abs/2402.02037) — Dong Huang, Yuhao Qing, Weiyi Shang, Heming Cui, Jie M. Zhang, 2024 — peer-reviewed (NeurIPS 2024, confirmed via Crossref) — "GPT-4 generated code has an average 3.12 times execution time that of the human-written canonical solutions"; worst cases 13.89x time, 43.92x memory — confirmed.
  - [no-await-in-loop](https://eslint.org/docs/latest/rules/no-await-in-loop) — ESLint — official docs — "each successive operation will not start until the previous one has completed"; disable for dependent iterations, rate limiting, bounded resources, retries — confirmed.
- **Detect:** ESLint no-await-in-loop. Calls inside loop bodies: `rg -n -A4 "for .* (in|of) |\.forEach\(|\.map\(" | rg "fetch\(|axios\.|\.query\(|\.execute\(|\.find(One|Unique)?\(|requests\.(get|post)|open\("`. Also ORM relation access inside loops, and nested loops over the same collection (O(n^2) lookups a map or set would replace). Confirm with a profiler or query log first.
- **Tools:** ESLint, ripgrep, ORM query logging, language profiler
- **Applies to:** Backends, data pipelines, CLI tools processing collections.
- **When not to apply / counterpoints:** The 8x ratio applies to a category that is rare in absolute terms. EffiBench uses algorithm puzzles, not application code. Sequential awaits are correct for dependent iterations, rate-limited APIs or bounded resources.
- **Fix risk:** medium

### T11-F01 — Weight review effort by the defect categories reported as over-represented in AI code; plan a dedicated post-completion pass
- **Grade:** C (was B) · **Verdict:** DOWNGRADED, with a correction. The per-category ratios that drive the weighting all come from one vendor study (CodeRabbit, 470 PRs). Its public page does not say how issues were detected: "Our full methodology is shared at the end of the report", which is gated. So the researcher's counterpoint that "issues were counted by an AI reviewer" is unconfirmed and has been removed. The survival claim (22.7% of issues still at HEAD) is better supported (B-level, large preprint).
- **Rule:** Weight review effort by the categories that measurements show are over-represented in AI-written code: excessive I/O (~8x), readability (3x), formatting (2.66x), security (up to 2.74x), error handling (~2x), concurrency (~2x), naming (~2x), logic (+75%). Do not expect AI-introduced issues to disappear through normal maintenance. Plan a dedicated pass once the project works.
- **Rationale:** The only direct AI-vs-human comparison of real PRs found 10.83 vs 6.45 issues per PR, with very different ratios per category. A 2026 study of 302,579 AI-authored commits in 6,299 repos tracked 484,366 issues and found "22.7% of tracked AI-introduced issues still survive at HEAD", including issues introduced more than nine months earlier. A separate 2026 study found that humans made 83.21% of maintenance commits on AI-generated files.
- **Evidence:**
  - [State of AI vs Human Code Generation Report](https://www.coderabbit.ai/blog/state-of-ai-vs-human-code-generation-report) — CodeRabbit, 2025 (17 Dec) — vendor report — 470 PRs (320 AI-co-authored, 150 human-only); 10.83 vs 6.45 issues per PR; logic +75%, readability 3x, error handling ~2x, security up to 2.74x, concurrency ~2x, formatting 2.66x, naming ~2x, excessive I/O ~8x; "we cannot guarantee all the PRs we labelled as human authored were actually authored only by humans" — confirmed.
  - [Debt Behind the AI Boom (arXiv:2603.28592v2)](https://arxiv.org/html/2603.28592v2) — Yue Liu, Ratnadira Widyasari, Yanjie Zhao, Ivana Clairine Irsan, Junkai Chen, David Lo, 2026 — preprint — 302,579 commits, 6,299 repos; 484,366 issues (89.3% smells, 6.0% correctness, 4.7% security); 22.7% survive at HEAD; commits introducing at least one issue range from 17.4% (Copilot) to 29.1% (Gemini) — confirmed.
  - [To What Extent Does Agent-generated Code Require Maintenance? (arXiv:2605.06464)](https://arxiv.org/html/2605.06464v1) — Sawada, Shirai, Kashiwa, Yamaguchi, Iwata, Iida, 2026 — preprint — "83.21% of commits (1,284) were made by human developers"; feature additions 21.78% vs bug fixes 11.73% on AI files — confirmed.
  - [Our new report: AI code creates 1.7x more problems](https://dev.to/coderabbitai/our-new-report-ai-code-creates-17x-more-problems-7lh) — CodeRabbit, 2025 — vendor blog — checklist "Are error paths covered? Are concurrency primitives correct? Are configuration values validated? Are passwords handled via the approved helper?" — confirmed.
- **Detect:** Run the category checks in this order: (1) injection and output encoding, (2) dependency existence and SCA, (3) duplication, (4) complexity, (5) error handling, (6) I/O in loops, (7) secrets, (8) authz on entry points, then the rest. The order is the researcher's synthesis. Record findings per category. To estimate AI provenance: `git log --format='%an %ae %(trailers:key=Co-authored-by)'` and bot actors (e.g. copilot-swe-agent[bot]). This is the same metadata the 2026 studies rely on, and it misses AI code whose markers were removed.
- **Tools:** CodeQL, Semgrep, SonarQube, ESLint, Pylint, jscpd, gitleaks, git log
- **Applies to:** Any finished codebase with substantial AI-assisted or agent-authored code.
- **When not to apply / counterpoints:** CodeRabbit is a vendor, the sample is small, labels were inferred from co-author signals, and the detection method is not stated publicly. An HN commenter (skeeter2020) asks whether AI PRs simply come from less experienced authors. "Debt Behind" is a preprint covering only Python/JS/TS. Ratios describe PR populations, not individual files.
- **Fix risk:** low

### T11-F04 — Find and merge semantic duplicates, choosing the correct variant rather than the first found
- **Grade:** C (was B) · **Verdict:** DOWNGRADED, with corrections. The evidence that duplication is *over-represented because of AI* is contested. GitClear (vendor) is correlational and does not attribute lines to AI. The only causal peer-reviewed study (Cursor DiD, MSR '26) found "no significant effect" on duplicate line density. The CodeScene preprint has no human baseline. Corrections: the GitClear 2025 page ties 8.3% to 12.3% to "the same period" as the 2021-2024 refactoring decline, not 2020-2024. In GitClear 2026, copy/paste and refactoring moves are compared from 2022 to 2026 YTD, and cross-file calls from 2023 (343 to 223 per thousand changed lines).
- **Rule:** Look for semantically duplicated code: copy-pasted blocks and helpers written again when the codebase already has one. Merge each group into one tested implementation, choosing the version that is actually correct. Do not simply keep the first one found.
- **Rationale:** GitClear 2025 (211M changed lines): copy/pasted lines rose from 8.3% to 12.3%, refactoring-associated (moved) lines fell from 25% in 2021 to under 10% in 2024, and copy/paste exceeded moved code "for first time in history". GitClear 2026 (623M changes): duplicated lines +81% (40.3 to 73.0 per million), within-commit copy/paste 9.4% (2022) to 15.7% (H1 2026), moved code 21% (2022) to 3.8%, function connectivity -35% since 2023. In 10 Cursor-generated projects, code duplication was the most frequent CodeScene issue (383, 28.4%). OX reports "Bugs Déjà-Vu" in 70-80% and "Avoidance of Refactors" in 80-90% of 300+ repos. Practitioners describe "Reimplementing the same helper functions five times" and "4 broken date parsing functions and 1 working one".
- **Evidence:**
  - [AI Copilot Code Quality: 2025 Data Suggests 4x Growth in Code Clones](https://www.gitclear.com/ai_assistant_code_quality_2025_research) — GitClear, 2025 — vendor report — "lines classified as 'copy/pasted' (cloned) rose from 8.3% to 12.3% in the same period"; refactoring "sunk from 25% of changed lines in 2021, to less than 10% in 2024" — confirmed.
  - [The Maintainability Gap](https://www.gitclear.com/the_ai_code_quality_maintainability_gap) — GitClear, 2026 (Jan) — vendor report — figures as above — confirmed. The method for attributing AI use is not detailed on the public page.
  - [Beyond Functional Correctness (arXiv:2604.06373)](https://arxiv.org/html/2604.06373v1) — Kashif, Li, Liang, Tahir, Feng, Li, Shahin, 2026 — preprint — 10 projects, avg 16,965 LoC, 91% functional correctness; Code Duplication 383 (28.4%), mapped to DRY — confirmed.
  - [OX Research: "Army of Juniors"](https://www.ox.security/blog/ox-research-ai-code-not-inherently-less-secure-but-army-of-juniors-effect-undermines-software-security/) — OX Security, 2025 — vendor report — Bugs Déjà-Vu 70-80%; Avoidance of Refactors 80-90%; Vanilla Style 40-50% — confirmed.
  - [jscpd](https://github.com/kucherenko/jscpd) — kucherenko — official docs — "Duplicate code detector for 220+ languages"; `npx jscpd .`; `--threshold`; active, not archived — confirmed.
- **Detect:** `npx jscpd --threshold <pct> --reporters console,html <src>` or SonarQube duplicated_lines_density. Also search for groups of same-purpose helpers by name stem, e.g. `rg -n "(def|function|const) +(parse|format|validate|normalize)[A-Za-z]*Date"`, and list utility modules per directory. Compare each group's behaviour on a small table of inputs before merging.
- **Tools:** jscpd, SonarQube, PMD CPD, CodeScene, ripgrep
- **Applies to:** All languages; most visible in codebases built over many independent agent sessions.
- **When not to apply / counterpoints:** The MSR '26 Cursor DiD study found "no significant effect" on duplication. GitClear is correlational, and HN commenters (ctoth, lostmsu) question the causal link. GitClear sells the measurement tool. Duplication in tests, in generated code, or across deliberately separate services or bounded contexts is often acceptable (rule of three). Duplication is still worth fixing on its own merits; what is weak is only the claim that it is AI-specific.
- **Fix risk:** medium

### T11-F15 — Review concurrency, ordering, resource lifetime and control flow
- **Grade:** C · **Verdict:** VERIFIED
- **Rule:** Review concurrency, operation ordering, resource lifetime and control flow. Check that every opened file, socket, connection or lock is released on all paths. Check that shared mutable state touched by concurrent handlers is synchronized, and that async results are awaited or explicitly detached.
- **Rationale:** CodeRabbit found about 2x more "incorrect ordering, faulty dependency flow, or misuse of concurrency primitives" in AI PRs. Sonar reports resource-management issues as 15.07% and threading issues as 9.81% of Claude Sonnet 4's bugs. Control-flow mistakes were 48.15% of GPT-4o's bugs and about 24% of GPT-5-minimal's.
- **Evidence:**
  - [Our new report: AI code creates 1.7x more problems](https://dev.to/coderabbitai/our-new-report-ai-code-creates-17x-more-problems-7lh) — CodeRabbit, 2025 — vendor blog — quote confirmed.
  - [Diving into the 3 traits...](https://www.sonarsource.com/blog/llm-coding-personality-traits/) — Sonar, 2025 — vendor report — GPT-4o control flow 48.15%; Claude Sonnet 4 resource management 15.07%, threading 9.81% — confirmed.
  - [GPT-5 Update](https://www.sonarsource.com/blog/the-coding-personalities-of-leading-llms-gpt-5-update/) — Sonar, 2025 — vendor report — control-flow mistakes ~24% of GPT-5-minimal's functional bugs — confirmed.
- **Detect:** SonarQube bug rules (resource leaks, thread safety). Grep for resources opened outside with/using/try-with-resources: `rg -n "open\(|createReadStream|new FileInputStream|connect\(|acquire\("`, and confirm each is closed in finally or a context manager. Find unawaited promises (typescript-eslint's floating-promise checks where configured). Look for module-level mutable state modified in request handlers.
- **Tools:** SonarQube, typescript-eslint, ripgrep, race detectors (e.g. `go test -race`)
- **Applies to:** Servers, async and multi-threaded code, anything holding OS resources.
- **When not to apply / counterpoints:** Both sources are vendors. Sonar's percentages describe bug mix within Java benchmark tasks with no human baseline. The CodeRabbit ratio rests on 470 PRs. No independent peer-reviewed confirmation was found.
- **Fix risk:** high

### T11-F16 — Verify every comment/doc claim about code properties; delete false claims and narration
- **Grade:** C · **Verdict:** VERIFIED
- **Rule:** Verify every comment, docstring, README statement and changelog claim that asserts a property of the code ("validated", "sanitized", "thread-safe", "idempotent", "retries", "cached"). Correct or delete false claims. Remove comments that only restate the next line, and keep comments that explain why.
- **Rationale:** OX saw "Comments Everywhere" in 90-100% of 300+ repos. Sonar measured comment density of 16.4% for Claude 3.7 Sonnet against 4.4% for GPT-4o. An MSR '26 study of 23,247 agent PRs found 406 (1.7%) with high message-code inconsistency, of which 45.4% were "descriptions claim unimplemented changes". Those PRs had acceptance of 28.3% vs 80.0% and took 55.8 vs 16.0 hours to merge. A practitioner reported AI-generated docstrings "frequently out of date if not just wrong".
- **Evidence:**
  - [Analyzing Message-Code Inconsistency in AI Coding Agent-Authored Pull Requests](https://arxiv.org/abs/2601.04886) — Jingzhi Gong, Giovanni Pinna, Yixin Bian, Jie M. Zhang, 2026 — peer-reviewed (MSR '26 Mining Challenge track) — figures as above; 974 PRs manually annotated — confirmed.
  - [OX Research: "Army of Juniors"](https://www.ox.security/blog/ox-research-ai-code-not-inherently-less-secure-but-army-of-juniors-effect-undermines-software-security/) — OX Security, 2025 — vendor report — Comments Everywhere (90-100%) — confirmed.
  - [Diving into the 3 traits...](https://www.sonarsource.com/blog/llm-coding-personality-traits/) — Sonar, 2025 — vendor report — Claude 3.7 Sonnet 16.4% vs GPT-4o 4.4% comment density — confirmed.
- **Detect:** Grep comments and docstrings for property claims: `rg -n -i "(#|//|\*|\"\"\").*(sanitiz|validat|thread.?safe|idempotent|retr(y|ies)|atomic|cached|secure|O\(1\))"`. Check each against the code and its tests. Compare README and API docs with the actual routes, flags and config keys. Use SonarQube comment_lines_density to find narration-heavy files.
- **Tools:** ripgrep, SonarQube, manual review
- **Applies to:** All codebases; most relevant where agents wrote docs together with the code.
- **When not to apply / counterpoints:** The MCI study covers PR descriptions, not inline comments, and high inconsistency affects only 1.7% of PRs. The OX percentages have no public methodology. Heavy commenting is sometimes wanted (teaching repos, regulated code). Deleting comments that carry rationale destroys knowledge.
- **Fix risk:** low

## Contradictions and open questions

**Contradictions (all re-checked)**
- **Security relative to humans.** Veracode and CodeRabbit report more vulnerabilities in AI code (45% of tasks fail; security issues up to 2.74x). Asare et al. (EMSE) conclude Copilot is not as bad as humans (33% vulnerable vs 25% fixed replications). OX says there are no more vulnerabilities per line. Jeff Williams says it is "roughly the same". The gap is partly benchmark prompts vs real repos, and per-task vs per-line measurement.
- **Logic bugs.** CodeRabbit finds logic and correctness issues +75% in AI PRs. Apiiro (via CSO and CSA) reports trivial syntax errors -76% and logic bugs -60%, while privilege-escalation and design flaws rose. The primary Apiiro page was unreachable (403).
- **Duplication.** GitClear reports "4x more code cloning" (2025 headline) and duplicated lines +81% (2026). The researcher's "8x duplicated blocks" figure could not be confirmed on GitClear's public pages. The peer-reviewed MSR '26 Cursor DiD study found "no significant effect" on duplication, while confirming the rise in complexity and warnings.
- **Churn.** GitClear's 2024 report projected that code churn would "double in 2024 compared to its 2021, pre-AI baseline" (confirmed). The researcher's claim that 2025 data shows only 5.5% to 7.9% could not be confirmed on the public 2025 landing page, so it is unverified.
- **DORA throughput.** 2024: AI adoption linked to lower throughput (-1.5% per +25% adoption). DORA's 2026 insight on the 2025 data links it to higher throughput. Instability was worse in both.
- **Package hallucination.** 19.7% on 2024-era models (Spracklen) vs 4.62-6.10% on the 2026 frontier cohort. Yet 127 names are shared by all five models. On exploitation in the wild, CSA describes a confirmed malicious "unused-imports" package, while Wikipedia (July 2026) says no attack has been reported.
- **Tests.** 80.2% of agent test patches have weak or no oracles, and OX reports fake coverage in 40-50% of repos. Yet 2601.21194 finds "no meaningful differences" in test smells between agent and human PRs, and agent PRs have nearly double the test-to-source ratio.
- **Readability.** GitHub's RCT finds Copilot code 3.62% more readable, while CodeRabbit finds readability issues 3x higher. The researcher also cited "a study of GPT-4o refactoring" where readability fell, but gave no source, so that point is unverified and excluded.
- **Model generations.** Sonar: Claude Sonnet 4 is "93% more likely to produce BLOCKER vulnerabilities" than its predecessor. Veracode: security is flat regardless of model size, but the GPT-5 series with extended reasoning reaches 70-72%.
- **Productivity.** METR RCT: experienced developers 19% slower. GitClear 2026: heavy AI users 25% faster than their past selves. Cursor DiD: +281% lines in month 1, then the gain fades as complexity accumulates.

**Open questions**
- **Attribution.** GitClear does no per-line detection, CodeRabbit infers labels from co-author signals, and Georgia Tech and "Debt Behind" depend on trailers and bot metadata that users can strip. CSA notes Claude Code's high CVE count partly reflects its commit signatures. How much of each ratio is due to AI rather than to who adopts AI?
- **Model drift.** Most numbers come from 2023-mid-2025 models. Package hallucination has improved in 2026, while XSS and log injection have not. Which categories still deserve extra weight for late-2026 agents?
- **GitClear's "error-masking constructs" (+47%)** has no public definition.
- **Vendor bias.** CodeRabbit, Sonar, Veracode, OX, Apiiro, GitGuardian, Endor, Faros and GitClear all sell detection or governance tools. Independent peer-reviewed support exists for security (Pearce, Fu, Perry, BaxBench), package hallucination (Spracklen plus a 2026 independent replication), complexity (Cursor DiD), deprecated APIs (ICSE'25) and weak test oracles (AITest 2026).
