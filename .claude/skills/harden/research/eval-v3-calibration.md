## Findings

### E03-F01 — Recording a silent skip is not a fail-mode flip
- **Grade:** B (own measurement)
- **Evidence:** py D07 went from fixed in 3 of 3 v2 runs to reported in 3 of 3 v3 runs (-1.5 credit): `parse_fills` catches exactly `KeyError` and `ValueError` and continues, dropping every malformed row with no log line and no count. Each run proposed a WARNING per skipped row as the warn stage of an unpromised fail-closed flip and applied nothing, while "log a warning, keep the skip" is the ledger's whole fix (evals/results-v3.md, E02-F03 row and Remaining weaknesses 1). Skipping a bad row while the rest of the batch proceeds is the per-item containment ER-14 prescribes; only the record was missing.
- **External evidence:** [PEP 20 – The Zen of Python](https://peps.python.org/pep-0020/) (Tim Peters, 2004): "Errors should never pass silently. Unless explicitly silenced." [Command Line Interface Guidelines](https://clig.dev/) (Prasad et al.): "Log messages, errors, and so on should all be sent to `stderr`. This means that when commands are piped together, these messages are displayed to the user and not fed into the next command." [Logging HOWTO](https://docs.python.org/3/howto/logging.html) (Python docs, current): "Report suppression of an error without raising an exception (e.g. error handler in a long-running server process)" with "A logger's error(), exception() or critical() method"; for libraries, "if you add handlers 'under the hood', you might well interfere with their ability to carry out unit tests". All three fetched and checked 2026-09-25.
- **Calibration:** a fix that only records an event the code may keep (a skipped or quarantined batch item, a kept last-known-good value, a best-effort cleanup), through a logger the code already uses, at its default level (never a new handler or a direct stderr write in exported library code, else T2), with no result, return value, stdout byte or exit code changed, is kind 1 of prioritization's Fail-open findings: row 22, T1 behavioural, not a flip. It stays T2 when the degradation is documented as intended or an option controls it (R1, R5), and it is never split off a T2 finding whose headline is a wrong result (E02-F03 holds).

### E03-F02 — A wrong result presented as valid is surfaced in one item unless consumers rely on it
- **Grade:** B (own measurement)
- **Evidence:** ts D09 went from fixed in 3 of 3 v2 runs to reported in 3 of 3 (-1.5): a holding with no ticker is valued at 0 and labelled `priceSource 'exchange'`, and row 21 read any change there as an unpromised flip. ts D08: ts-with-1 reported the whole item; ts-with-2 and ts-with-3 fixed malformed JSON only and split the explicitly named missing file off as a new T2 finding under row 21 (C-ER-13, C-054), so the headline `value --config nope.json` still printed 0.00 and exited 0 in 3 of 3 runs, although the README documents exit code 1 for runtime errors (evals/results-v3.md, E02-F02 row). The fabricated-value defects that the py and rs ledgers call report-T2 differ in ways a rule can see: py D09 (`live/poller.py`: "Keep the board populated: reuse the last good price rather than leaving a hole for this round") and rs D15 (`engine.rs`: "Fall back to FIFO when the name is not registered, so that a typo in the config never stops the engine from matching") carry a comment that describes the fallback as intended; rs D09 skips a risk check whose fail-closed form would reject orders the engine matches today; py D10 (an explicitly named `--marks` file that cannot be read or parsed becomes `{}`, unrealized PnL 0, exit 0) carries no such signal.
- **External evidence:** [Fail Fast](https://martinfowler.com/ieeeSoftware/failFast.pdf) (Jim Shore, IEEE Software, 2004): a default returned for a missing config property means "everything will seem fine" until "Figuring it out could take days of hair pulling". [CWE-393: Return of Wrong Status Code](https://cwe.mitre.org/data/definitions/393.html) (MITRE, CWE 4.20): a value "that does not indicate the true result of execution, causing the product to modify its behavior based on the incorrect result". [Command Line Interface Guidelines](https://clig.dev/) (Prasad et al.): "Return zero exit code on success, non-zero on failure." [configparser](https://docs.python.org/3/library/configparser.html) (Python docs, current): unopenable files are ignored among "potential configuration file locations", and required files go through `read_file()`. [PEP 387](https://peps.python.org/pep-0387/) (Python, current): the warning of a staged change "should include the release the incompatibility is expected to become the default". All fetched and checked 2026-09-25.
- **Calibration:** kind 2 of prioritization's Fail-open findings (a substituted value presented as genuine) is row 21's restoring change: the output's own claim is the promise, and the fix surfaces the failure through a channel the code already has, fail-closed in one item. Where external consumers or live data exist, only the error the same function already raises for a sibling failure or the documented exit of a CLI command whose input the caller named is applied; any other channel is T2 (behaviour-changing-fixes G102-F07, G102-F08). Kind 3 (a tightening, or a check that fails open) keeps row 21's promise test. Both are T2 when a reliance signal holds: R1 documented or commented as intended with a reason or a promise, R2 an existing test asserts it, R3 a documented consumer setup reaches it, R4 a pinned valid input reaches it, R5 an option controls it, R6 a live-traffic service path. Expected effect on the v3 ledgers: ts D08 becomes fixable in one item and ts D09 through its row-18 status member; py D09 and rs D15 (R1) and rs D09 (kind 3, unpromised) stay T2; py D10 becomes a T1 fix that the py ledger scores as an unapproved T2 edit.

### E03-F03 — The no-data timeout default is a fixed internal constant, and its timer must not outlive the call
- **Grade:** B (own measurement)
- **Evidence:** 9 of 9 skill runs fixed the seeded unbounded calls (ts D10, py D11, rs D10) with a test and no hidden regression: eight with a named module-level constant of 10 s, and ts-with-2 with a constructor option that the simulated user approved as an additive public change (evals/results-v3.md, E01-F05 row and Public API). ts-with-1 first proposed an optional constructor argument, dropped it at apply time to keep every exported signature unchanged and re-asked (commit 546de2b); its later mutation run showed that without `clearTimeout` "a finished CLI run would stay alive for REQUEST_TIMEOUT_MS" (commit 91bd8ac). The tests shortened the bound through a spy on `AbortSignal.timeout` (ts-with-3, commit 750ba02), fake timers (ts-with-1) or a crate-private function (rs-with-1). Local check, Node v24.13.0, 2026-09-25: with a pending `AbortSignal.timeout(5000)` the process exited after 4 ms; with a pending `setTimeout(..., 3000)` it exited after 3003 ms.
- **External evidence:** [AbortSignal.timeout()](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal/timeout_static) (MDN, current): the returned signal "will abort with its AbortSignal.reason property set to a TimeoutError DOMException on timeout". [Timeouts, retries, and backoff with jitter](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf) (Marc Brooker, AWS Builders' Library, 2019): "In general, we prefer to use the timeouts built into well-tested clients." (about the timeout mechanism: implementations whose timeout "doesn't cover all remote calls, like DNS or TLS handshakes") Both fetched and checked 2026-09-25.
- **Calibration:** ER-21's no-data default is a named constant private to the module that makes the call (or the project's existing config path), never a new public parameter; its test shortens the bound through a test-only seam; and a fix that starts its own timer shows in the same test file that an answered call leaves no timer holding the process open (in Node, prefer `AbortSignal.timeout`, or clear the timer in a `finally`).

### E03-F04 — A tightening that rejects inputs shown to occur is not a narrower fix
- **Grade:** B (own measurement; external sources verified 2026-09-25)
- **Evidence:** ts D12 (order ids converted with `Number()`: alphanumeric ids become NaN and `dedupeTrades` drops them all; ids above 2^53 that round to the same value collide) was graded fixed-with-regression in 2 of 3 v3 WITH runs (v2: reported in 3 of 3). Both applied a stop-gap that rejects any id that is not a safe integer, so 18-19 digit ids that dedupe and price correctly when no other id rounds to the same value now stop the command with exit 1. ts-with-1 applied it without the re-ask and listed the class only afterwards under its report's Open owner items; its notes read "changes behaviour only on inputs the code currently corrupts (NM tier policy step 7)", taking PC-24's Not when ("An input the code demonstrably corrupted ... belongs to the defect") and the numeric lens's step 7 ("integers above 2^53−1") for the whole class. ts-with-2 showed the class and the simulated user approved it when re-asked. ts-with-3 showed it, narrowed the fix to non-numeric ids and split the rest off as a T2 representation finding (graded reported). The finding's own rule, NM-04, exists because such ids occur ("exchange order and trade IDs, Snowflake IDs"). External: [Reporting regressions](https://docs.kernel.org/admin-guide/reporting-regressions.html) (Linux kernel documentation, 2026): "It's a regression if some application or practical use case running fine with one Linux kernel works worse or not at all with a newer version compiled using a similar configuration"; [Handling regressions](https://docs.kernel.org/process/handling-regressions.html) (Linux kernel documentation, 2026), on regressions caused by bug fixes, quoting Torvalds: "whether something was buggy or not DOES NOT MATTER", with the only named exception "a fundamental huge and gaping security issue".
- **Calibration:** PC-24 decides membership per input, by its observable outcome at base (output, exit code, persisted data), never by an intermediate value: a value that loses precision on the way but whose results are still right is valid, and an input belongs to the defect only in the part of its outcome that a reproduction shows wrong; every other part that was right at base (the run completing, its exit code, the other records of the same file, batch or request) is pinned like a valid input. A member of the newly rejected class is attested when the project's docs, fixtures, sample data or tests, the published format of the data parsed, the base code's own output, or the finding itself shows that such inputs occur. While an attested member remains, the fix is a contract change on valid input: T2 under row 21 unless the code or its docs promise the rejection, whatever the approval (invariant 8); a lossless variant that changes no public type, serialized field or storage layout is the T1 item instead when one exists. Only a class with no attested member can be shown to the user and accepted.

### E03-F05 — Newly rejected inputs are found by outcome, and a persisted-format change is tested with data the base wrote
- **Grade:** B (own measurement; external sources verified 2026-09-25)
- **Evidence:** ts-with-3 D24 was graded fixed-with-regression: the fix writes cooldown times with `toISOString()` instead of `toLocaleString()` and leaves the reader unchanged. A state file the base code wrote under fr-FR holds "29/08/2026 12:40:00", which the reader parses as NaN, as before; the next save now calls `toISOString()` on that value and throws, so the new cooldown is not written either. ts-with-1 and ts-with-2 have the same code and were graded fixed because their graders did not probe the upgrade path (results-v3, Grading reliability); ts-with-2 even split the legacy read off as a T2 item (C-NM-12: "the locale a legacy file was written in is unknowable") and still missed that save() now throws. All three baseline runs skip legacy entries with a warning. Re-run 2026-09-25 on the autonomous pilot's branch head e43e5db, whose commit 85aebe0 makes the same change and says "load() is unchanged, so state files written by earlier versions read back as before" (Node v24.13.0): that legacy value loads as NaN and `FileStateStore.save()` throws `RangeError: Invalid time value`; at base, `new Date(NaN).toLocaleString('fr-FR')` returns "Invalid Date" without throwing. None of the four diffs adds a `throw`, so PC-24's diff heuristic never fired. External: [Date.prototype.toISOString()](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Date/toISOString) (MDN, 2026), Exceptions: RangeError "Thrown if the date is invalid or if it corresponds to a year that cannot be represented in the date string format"; [Understanding and Detecting Software Upgrade Failures in Distributed Systems](https://doi.org/10.1145/3477132.3483577) (Zhang, Yang, Jin, Sethi, Rodrigues, Lu, Yuan, SOSP 2021; abstract read through the Semantic Scholar API on 2026-09-25, the ACM page returned 403): a study of "123 real-world upgrade failures" in "8 widely used distributed systems", whose static checkers "discovered over 800 cross-version data-format incompatibilities that can lead to upgrade failures"; [Reporting regressions](https://docs.kernel.org/admin-guide/reporting-regressions.html) (Linux kernel documentation, 2026), as in E03-F04.
- **Calibration:** PC-24's check runs before every behavioural fix to code that parses, validates, converts, stores or reads back data, whether or not the diff adds a `throw` or a check: an input is newly rejected when it completes at base and throws, exits non-zero, is skipped or is dropped by the candidate. When the fix changes how the code writes or reads data it persists, the cases include data written by the base code in a base worktree under the settings the reproduction used (locale, time zone), then loaded, used and saved again by the candidate. Every path the code persists to points into the scratch_dir during that case (a constructor argument, a config value, or `HOME`, `USERPROFILE`, `APPDATA` and the `XDG_*` variables set to scratch_dir subdirectories); when the code offers no such seam, the case cannot run and the item is not applied. The numeric lens's `toISOString()` fix (NM-20) must accept every value the unchanged reader returns, NaN included.

## Contradictions and open questions

- The ledgers disagree on the fabricated-value shape: fix-T1 in ts (D08, D09), report-T2 in py (D09, D10) and rs (D09, D15). E03-F02 follows the reliance signals rather than either ledger, and is expected to lose about 1.0 of 222 credit points on py D10 until the ledgers are aligned (evals/results-v3.md, Harness changes before v4). These calibrations rest on external definitions (a regression, a wrong status code) and on the finding's own rule, not on one fixture's answer key (results-v3, Threats to validity 4).
- ts D09's truthful status needs a new member of an exported union (`PriceSource`), so it is fixable through row 18 with its own approval (`--interactive`, or the simulated user) and stays report-only in autonomous mode, where no profile switch covers row 18.
- The 60 s floor of the no-data timeout default (pilot-auto-calibration A01-F10) is anchored on two infrastructure defaults and has not been measured; the nine v3 fixes used 10 s.
- E03-F04 makes interactive runs stricter than PC-24 was: a class the owner would knowingly accept is T2 when a member is shown to occur. The owner can still make the change by hand; the skill will not. results-v3 put the trade-off as "ts D12 stays at 0.5 instead of risking 0".
- Deciding membership per input and per part of its outcome needs a base outcome to judge; where the run cannot tell whether a base outcome was right (no reproduction, no golden value), the input counts as valid, which can keep a fix out.
- The upgrade-path case runs base code in a base worktree within the Phase 0 side-effect limits, with every persisted path redirected into the scratch_dir; where the limits forbid running project code, or the code offers no seam to redirect its paths, the item is not applied. The reverse direction (base code reading what the fix writes, as after a rollback) is not checked.
- The kernel names security fixes as the exception to its rule; here a security tightening with an attested member is still T2 (prioritization row 19), which leaves such fixes to the owner.
- Moving uv's and pnpm's download caches for tool runs costs a re-download per run; results-v3 item 4 proposed it, and graders did not count those caches. Measure the added wall time in the second pilot.
- The calibration relies on pnpm's documented `XDG_CACHE_HOME` default for the dlx cache; with `PNPM_HOME` set, the store stays in `$PNPM_HOME/store`.
- A tool that ignores its documented variable still writes outside the run; the hook sees only explicit write targets in commands, not writes a program makes itself.
- Moving CARGO_HOME for tool installs lengthens registry paths; long-path failures on Windows were not measured (v3's failed installs were caused by a full disk).
