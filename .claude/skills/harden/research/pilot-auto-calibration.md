### A01-F07 — The glob list uses the .gitignore pattern format, ignores letter case, and is void while a pattern matches nothing
- **Grade:** B (official documentation, and the skill's existing glob dialect)
- **Evidence:** [gitignore](https://git-scm.com/docs/gitignore) (Git project, accessed 2026-09-25): "An asterisk "*" matches anything except a slash."; "If there is a separator at the beginning or middle (or both) of the pattern, then the pattern is relative to the directory level of the particular .gitignore file itself. Otherwise the pattern may also match at any level below the .gitignore level."; "A slash followed by two consecutive asterisks then a slash matches zero or more directories."; "Other consecutive asterisks are considered regular asterisks"; "If there is a separator at the end of the pattern then the pattern will only match directories"; "An optional prefix "!" which negates the pattern"; "A backslash ("\") can be used to escape any character."; "It is not possible to re-include a file if a parent directory of that file is excluded. Git doesn't list excluded directories for performance reasons, so any patterns on contained files have no effect, no matter where they are defined." [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) (GitHub Docs, accessed 2026-09-25): "A CODEOWNERS file uses a pattern that follows most of the same rules used in gitignore files."; "Using ! to negate a pattern doesn't work"; "Order is important; the last matching pattern takes the most precedence."; "The `docs/*` pattern will match files like `docs/getting-started.md` but not further nested files like `docs/build-app/troubleshooting.md`."; "CODEOWNERS paths are case sensitive, because GitHub uses a case sensitive file system."; "If any line in your CODEOWNERS file contains invalid syntax, that line will be skipped." [git-config](https://git-scm.com/docs/git-config) (Git project, accessed 2026-09-25), core.ignoreCase: "Internal variable which enables various workarounds to enable Git to work better on filesystems that are not case sensitive, like APFS, HFS+, FAT, NTFS, etc." [fnmatch](https://docs.python.org/3/library/fnmatch.html) (Python Software Foundation, accessed 2026-09-25): "Note that the filename separator ('/' on Unix) is not special to this module."; "Both parameters are case-normalized using os.path.normcase()."; "For a literal match, wrap the meta-characters in brackets. For example, '[?]' matches the character '?'." [pathlib](https://docs.python.org/3/library/pathlib.html) (Python Software Foundation, accessed 2026-09-25), PurePath.match: "the recursive wildcard “**” isn’t supported (it acts like non-recursive “*”), and if a relative pattern is provided, then matching is done from the right"; full_match is "Added in version 3.13", and its "case-sensitivity follows platform defaults". The skill's scripts already share one `*_globs` dialect of this kind (scripts/_common.py, used by rank.py and ledger.py).
- **Calibration:** patterns follow _common.py's dialect, a subset of the .gitignore format: `*`, `?` and `[...]` stay inside one path segment, `**` is a whole segment, a pattern without `/` (other than a trailing one) matches a name at any depth, a trailing `/` matches a directory and never a file, `[[]` matches a literal `[`, and a negated class `[!...]` may also match `/` (a wider reading, which only withholds more). A pattern that matches a directory covers everything below it, as a .gitignore pattern does, so `src/*` covers the whole of `src/` (CODEOWNERS reads it as one level; the wider reading only withholds more). Refused, so that the profile is invalid rather than silently read another way: `!` negation (an allow-list has nothing to negate, and an order-dependent list is harder to audit), a backslash (git paths use `/` on every platform, and .gitignore reads `\` as an escape), a leading `/`, a drive letter, a `.` or `..` segment, `**` inside a segment, an unclosed `[` and a class holding `/`. Matching ignores letter case on every platform: a case-sensitive match suits GitHub's server, but runs execute on NTFS and APFS too, and in a list whose "yes" only withholds, a case slip must fall on "yes". Python's fnmatch (separator not special, platform case) and PurePath.match (right-anchored; `**` not recursive; full_match needs Python 3.13, the scripts support 3.9) are not used. With `--repo`, each pattern is matched against the files of the base commit: a pattern that matches none voids the whole list and the run judges again, because an authoritative list that names what the tree does not hold was mistyped or written for another tree, and every file it misses would otherwise read "not a money path". A pattern that matches only when case is ignored, or matches every file, is a warning. Where CODEOWNERS skips an invalid line, an invalid pattern here makes the profile invalid.

### A01-F08 — Code that signs, sends orders or transactions, or handles keys stays a money path whatever the list says
- **Grade:** B (built on verified findings and official documentation)
- **Evidence:** a path list protects only what it names: [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) (GitHub Docs, accessed 2026-09-25), on a path left without owners: "Without an owner, changes to `apps/github` can be made with the approval of any user who has write access to the repository."; [Code Owners](https://docs.gitlab.com/user/project/codeowners/) (GitLab Docs, accessed 2026-09-25): "Use approval rules to define areas of expertise that don't correspond to specific file paths in your repository." Scope lists miss the code that matters: web3-audit-practice G207-F24 (Cetus, 2025: "the integer-mate library was not included in the scope of our audit"). Keys are where the losses are: web3-audit-practice G207-F17 (Chainalysis: "Private key compromises accounted for the largest share of stolen crypto in 2024, at 43.8%"). The run's own controls do not reach the merged change: `forbidden_commands`, `live_side_effects: "none"` and offline gates keep the run's commands away from live endpoints (PF-03; hardening-induced-regressions G205-F16), but a changed signing or order-sending path meets the venue or chain only after the owner merges it, which is why U01-F03 withholds such behavioural items unless an offline check executes them. Own measurement: the pilot's verifier V3 marked H-007 (an API key sent as a header, `binance.ts:8`, `:36`, `:43`) as a key path, while the same file's price parsing (H-036, `binance.ts:56`) touches no key code: the floor belongs to the code a change touches, not to a file.
- **Calibration:** whatever `money_paths_globs` says, an item stays on a money path when the code its change touches creates, submits, amends or cancels orders, payments, transfers or withdrawals, signs anything, broadcasts transactions, or reads, derives, stores, logs or sends private keys, seed phrases, API keys or secrets. The verifier ends its note with `money-path: floor <kind> at <file:line>` (detection step 11). The orchestrator judges the floor where that line is missing, and at Phase 7 it scans every staged change with a keyword list whose every hit it must answer in the finding's notes (protocol-change step 9); the scan only prompts the judgement, and doubt keeps the floor. The floor only ever adds a money path, so a wrong floor judgement withholds a fix and never applies one. It stays a judgement with file:line evidence rather than a script: a path list cannot see what code does, and a keyword scan cannot tell a signing call from a comment about one, while its false "no" is the costly direction.

### A01-F09 — A defect's own log line is not a warn stage; a wrong result presented as valid is surfaced in one item
- **Grade:** B (own measurement, n = 1; external sources fetched and checked 2026-09-25)
- **Evidence:** D08 (H-001, `src/config/load.ts:34-37`): a missing, unreadable or malformed config returned `DEFAULT_CONFIG` (0 holdings, 0 rules) with a `log.warn`, and the command exited 0. The run found the promise (the sibling `validateConfig` throws `ConfigError`; the README documents "Exit codes: `0` success, `1` runtime error"), saw external consumers in PF-14 (published CLI, cron), chose the staged path, then read the defect's own `log.warn` as the warn stage already in place: "only the enforce stage remains, which no auto_apply switch covers". It stayed report-only with `auto_apply.behavioural=true`, and its headline reproduction was unchanged at HEAD. D09 (H-019, `src/portfolio/valuation.ts:35`): a holding with no ticker was valued at price 0 with `priceSource "exchange"`; row 21 made it T2 as "a fail-open -> fail-closed change ... that nothing promises", although the fix the run itself proposed (a distinct `priceSource`) rejects no input.
- **External evidence:**
  - [PEP 387 – Backwards Compatibility Policy](https://peps.python.org/pep-0387/) (Python, current): a staged incompatible change starts with "Add a warning", and "The warning message should include the release the incompatibility is expected to become the default and a link to an issue that users can post feedback to", and the change waits until the warning has appeared in at least two minor Python versions (or one in an older major version). The same PEP lists "the return value, side effects, and raised exceptions of a function" as covered and adds: "This does not preclude changes from reasonable bug fixes."
  - [Pod Security Admission](https://kubernetes.io/docs/concepts/security/pod-security-admission/) (Kubernetes, current): "warn: Policy violations will trigger a user-facing warning, but are otherwise allowed"; "enforce: Policy violations will cause the pod to be rejected". Warning and enforcement are separate modes the operator chooses.
  - behaviour-changing-fixes G102-F08 (verified in the skill's dossier): PEP 479 turned a StopIteration that silently ended a generator into a RuntimeError over three releases, and Node turned unhandled rejections from a deprecation warning into a throw by default in v15: platforms stage the surfacing of silently swallowed failures where consumers exist.
  - [Fail Fast](https://martinfowler.com/ieeeSoftware/failFast.pdf) (Jim Shore, IEEE Software, 2004): for a config reader that returns a default when a property is missing, "everything will seem fine. But when customers start using the software, they'll encounter mysterious slowdowns. Figuring it out could take days of hair pulling"; a fail-fast system "fails immediately and visibly".
  - [CWE-393: Return of Wrong Status Code](https://cwe.mitre.org/data/definitions/393.html) (MITRE, CWE 4.20): "A function or operation returns an incorrect return value or status code that does not indicate the true result of execution, causing the product to modify its behavior based on the incorrect result."
  - [Command Line Interface Guidelines](https://clig.dev/) (Prasad et al.): "Return zero exit code on success, non-zero on failure"; "Exit codes are how scripts determine whether a program succeeded or failed, so you should report this correctly."
  - [configparser](https://docs.python.org/3/library/configparser.html) (Python docs, current): "If a file named in filenames cannot be opened, that file will be ignored. This is designed so that you can specify an iterable of potential configuration file locations"; "An application which requires initial values to be loaded from a file should load the required file or files using read_file()". Local check (Python 3.13.2, 2026-09-25): `read()` on a file without a section header raises `MissingSectionHeaderError`, so only absent optional files are skipped.
  - [Semantic Versioning 2.0.0](https://semver.org/) (Tom Preston-Werner): "Use your best judgment. If you have a huge audience that will be drastically impacted by changing the behavior back to what the public API intended, then it may be best to perform a major version release, even though the fix could strictly be considered a patch release."
  - [PEP 20 – The Zen of Python](https://peps.python.org/pep-0020/) (Tim Peters, 2004): "Errors should never pass silently. Unless explicitly silenced." "In the face of ambiguity, refuse the temptation to guess."
- **Calibration:** a warn stage is a warning a fix adds that names the change to come (PEP 387); a log line the defect already emits is never one, and no mode applies an enforce stage, because enforcement follows the warning by at least one release the owner ships. A fail-open finding is tiered per consequence by what its headline shows wrong (prioritization, Fail-open findings): kind 1 records a silent event with every result unchanged (T1, not a flip); kind 2 surfaces a wrong result presented as valid through a channel the code already has, the output's own claim being the promise (CWE-393, ER-15, OP-12), and is applied fail-closed in one item (T1); kind 3, a tightening, stays T1 only when promised and PC-24 leaves no newly rejected valid class. Kinds 2 and 3 are T2 when a reliance signal holds (R1 to R6); PF-14's external consumers alone are not one, and the change goes on the behaviour-change list (SemVer). An implicit optional input that is absent keeps its fallback (configparser). Where external consumers or live data exist, kind 2 uses only the error the same function already raises for a sibling failure or the documented exit of a CLI command whose input the caller named; any other channel is T2 with the staged path proposed. R1 needs text that gives the fallback a reason or a promise; a log message, the defect's own warning included, is not R1.

### A01-F10 — A missing timeout gets a fixed internal default, never a public option
- **Grade:** B (own measurement, n = 1; external sources fetched and checked 2026-09-25)
- **Evidence:** D10 (H-015, `src/http/client.ts:36-40`): `fetch` without a `signal` backs every exchange and webhook call. The run's tiering note reads "Row 14: without latency data the fix is a configurable, documented default, i.e. a new FetchHttpClient option = additive public API change (row 18), which no auto_apply switch covers in autonomous mode. Not applied." ER-21 already allowed "a named module-level constant", but row 14 said "a configurable default" and was read first. `FetchHttpClient` is exported from `src/index.ts`, and the run had restored its own first attempt at H-014 because a private field changed the exported `.d.ts`, so any option or field on that class would have failed the API comparison as well; a module constant changes no declaration.
- **External evidence:**
  - [Timeouts, retries, and backoff with jitter](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf) (Marc Brooker, AWS Builders' Library, 2019): "Typically, the most difficult problem is choosing a timeout value to set. Setting a timeout too high reduces its usefulness, because resources are still consumed while the client waits for the timeout. Setting the timeout too low has two risks: Increased traffic on the backend and increased latency because too many requests are retried. Increased small backend latency leading to a complete outage, because all requests start being retried."; for clients with substantial network latency "we factor in reasonable worst-case network latency"; "In general, we prefer to use the timeouts built into well-tested clients." (said of the timeout mechanism, next to implementations whose timeout "doesn't cover all remote calls, like DNS or TLS handshakes", not of default values); "A timeout or failure doesn't necessarily mean that side effects haven't happened."
  - [Addressing Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/) (Mike Ulrich, Google SRE book, 2016): "Setting either no deadline or an extremely high deadline may cause short-term problems that have long since passed to continue to consume server resources until the server restarts."; "Short deadlines can cause some more expensive requests to fail consistently."; "Balancing these constraints to pick a good deadline can be something of an art."
  - [undici Client](https://raw.githubusercontent.com/nodejs/undici/main/docs/docs/api/Client.md) (Node.js undici, current): `connectTimeout` "The timeout, in milliseconds, for establishing a socket connection ... Default: `10e3`"; `headersTimeout` "Default: `300e3`"; `bodyTimeout` "Monitors the time between consecutive body chunks ... Default: `300e3`".
  - [ngx_http_proxy_module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html) (nginx, current): "Default: proxy_read_timeout 60s"; "The timeout is set only between two successive read operations, not for the transmission of the whole response. If the proxied server does not transmit anything within this time, the connection is closed."
  - [Edit attributes for your Application Load Balancer](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html) (AWS, current): "By default, Elastic Load Balancing sets the idle timeout value for your load balancer to 60 seconds."
  - [Requests: Timeouts](https://requests.readthedocs.io/en/latest/user/advanced/#timeouts) (Python requests, current): "By default, requests do not time out unless a timeout value is set explicitly. Without a timeout, your code may hang for minutes or more."; connect timeouts "slightly larger than a multiple of 3, which is the default TCP packet retransmission window"; the read timeout is the wait between bytes, and "In 99.9% of cases, this is the time before the server sends the first byte".
  - [HTTPX: Timeouts](https://www.python-httpx.org/advanced/timeouts/) (Encode, current): "HTTPX is careful to enforce timeouts everywhere by default. The default behavior is to raise a TimeoutException after 5 seconds of network inactivity."
  - [noctx](https://github.com/sonatard/noctx) (sonatard, current): "`noctx` finds function calls without context.Context." A call with a context that carries no deadline is still unbounded, so a noctx hit is a lead, not proof of a missing timeout.
- **Calibration:** without latency data, a missing timeout gets a fixed internal default: a named constant in the module that makes the call, or the project's existing config path, never a new parameter, option or field of an exported signature, so row 18 never applies. The default errs long: at least 60 s per request and response, or about 10 s to connect and at least 60 s between reads where the client has per-phase settings; at least ten times any latency the repository documents; never above the caller's own deadline. A per-query or per-statement database timeout without latency data for that query stays T2, and so does a timeout on a call with side effects that a retry wrapper would resubmit without an idempotency key. The constant is private to its module and the test seam adds no export; a finite library default (undici's 300 s behind Node's `fetch`) is recorded as the old bound; a caller that already carries a deadline passes its remaining budget down instead.
