# User policy: autonomous mode
> Code U01 · slug user-policy-autonomy · decided 2026-09-24 and extended 2026-09-25 by the skill's owner · source: the owner's instructions in the build sessions, plus the verified dossiers and the external documentation each finding cites

## Summary

The owner runs /harden unattended (for example overnight) and does not want a run to stop while waiting for a
confirmation. Their acceptance criterion: once all fixes are applied, an independent agent tests the project end to
end and nothing is broken. This dossier records that decision and the verified evidence the autonomous design relies
on. It changes who approves T1 categories (a pre-written run profile instead of a live answer). On 2026-09-25 the
owner widened the scope (U01-F06, U01-F11 to U01-F13): every finding a test can demonstrate is fixed on the branch,
money paths and the items the tier table leaves to the owner included, each in its own gated commit. Where two
behaviours are valid, the run takes the conservative option, and every such commit is listed for review before merge
with its `git revert` command. What only a live system could prove (keys, signing, order or transaction submission,
deploys), secrets, CI and gate configs, history, and the removal or change of an existing test line stay
report-only; an existing test file only gains checked additions (U01-F07). Nothing is merged.

On 2026-09-25 the owner also extended the policy: typing `/harden` must be enough, so without an owner profile the
run writes its own (U01-F05). A self-setup profile approves every kind the owner chose, money paths included, but no
dependency change that brings in a new version (U01-F08). It gates only commands that a classification clears
without running them (U01-F09), with credential and live-switch variables removed, and a probe that drops only
gates that cannot run (U01-F10).

## Findings

### U01-F01 — Autonomous runs never wait for the user
- **Grade:** policy (owner decision, 2026-09-24)
- **Evidence:** owner, 2026-09-24: "je veux que le skill soit autonome, du coup si ca coupe en pleine nuit en attendant ma confirmation c'est problématique. tant qu'a la fin de tout les fix, un agent teste le projet end to end et que rien n'est cassé c'est bon."
- **Calibration:** in autonomous mode (the default), every question the workflow would ask is answered from the run profile the owner writes before the run; an unanswered question takes its conservative default and is logged; approvals of T1 categories come from the profile's auto-apply settings. `--interactive` restores live approvals; `--report-only` never edits.

### U01-F02 — The end-to-end verifier replaces the human approval as the final gate
- **Grade:** B (built on the cited verified findings)
- **Evidence:** passing tests are a weak oracle (29.6% of plausible SWE-bench patches behave differently from the reference; refactoring-safety T09-F14, hardening-induced-regressions G205-F14); every commit must build and pass on its own so `git bisect` can land on any commit (refactoring-safety T09-F08); a fresh-clone replay exposes hidden local state (docs-accuracy G106-F01); differential runs of base and candidate on the same inputs detect behaviour drift (cleanup-practice-forums T30-F11, T30-F13); report-first approval tiers (skill-design T31-F11) are the evidence-backed default this policy overrides, which is why the replacement gate must be stronger than the per-commit gates.
- **Calibration:** after the last fix, a fresh-context verifier clones the hardened branch, installs from the lockfile, runs every gate and every end-to-end check from the profile, and compares the base's golden outputs (Phase 1) with the branch's. A failure is bisected to the first bad commit, which is reverted with `git revert`; the loop repeats until green or until its cap, after which the run reverts the whole range it applied and reports.

### U01-F03 — What cannot be proven offline is not applied unattended
- **Grade:** B (built on the cited verified findings; narrowed by the owner on 2026-09-25, U01-F06)
- **Evidence:** live side effects of project code (orders, signing, transactions) cannot be exercised safely by the run (PF-03; hardening-induced-regressions G205-F16); secrets are the human's (PC-21); existing test lines are read-only (invariant 2; llm-refactoring T10-F06; U01-F07); owner, 2026-09-25 (U01-F06): "Ce qui ne peut pas être prouvé hors ligne (signature, déploiement, réseau live) reste en rapport."
- **Calibration:** in autonomous mode, whatever the profile says, these are never applied; they are reported with a proposed first step: a change on a live-effect path (U01-F12); a secret and its rotation; a CI workflow, gate-config or history change; a package no manifest lists, or a new suppression; a test deletion, or a removal or modification of an existing test line (U01-F07 admits checked additions only); a T2 item while `auto_apply.owner_judgement` is false or while the Owner-judgement lane keeps it report-only (U01-F06). Commands the profile lists as forbidden (for example a script that signs transactions) are refused mechanically by the PreToolUse hook. Until 2026-09-25 this finding also withheld every T2 item and every behavioural money-path item that no check the pass did not write executes offline. U01-F06 moved the first kind to the Owner-judgement lane and the second to the differential alternative of PC-14 condition (d).

### U01-F04 — The profile is the owner's consent, written before the run
- **Grade:** policy (owner decision, 2026-09-24)
- **Evidence:** the owner's standing preference is to be asked before major decisions (global CLAUDE.md), and an autonomous run cannot ask; the profile moves those decisions to before the run.
- **Calibration:** `.harden/profile.json` (validated by a script) records the gates, the end-to-end checks, network scope, live-side-effect status, forbidden commands, situation, auto-apply switches and an optional budget or deadline. With no profile, an autonomous run behaves as `--report-only` for anything that would execute project code, and says so. Superseded in part by U01-F05 (2026-09-25): with no owner profile, self-setup writes one, and the report-only fallback applies when it cannot write a valid profile or clears no gate.

### U01-F06 — Full scope: every finding a test can demonstrate is fixed on the branch, money paths included
- **Grade:** policy (owner decision, 2026-09-25)
- **Evidence:** asked "Jusqu'où le skill corrige-t-il seul sur la branche ?", the owner chose "Tout, argent compris (Recommandé)", described as: "Tout problème qu'un test peut démontrer est corrigé, y compris les changements de comportement et le code de swap/liquidité. Chaque correction a son commit et son test, les vérifications passent après chaque commit, et le test de bout en bout final annule ce qui casse. Ce qui ne peut pas être prouvé hors ligne (signature, déploiement, réseau live) reste en rapport." The same day's goal is U01-F05's quote, and the owner's decision on existing tests is U01-F07's. Standing decision (U01-F01): "tant qu'a la fin de tout les fix, un agent teste le projet end to end et que rien n'est cassé c'est bon." Measured: the first autonomous pilot applied 7 of 37 verified findings (evals/pilot-auto-2026-09-25.md); the second applied 13 of 49 and left 32 at T2, report-only (pilot-auto-calibration A01-F28).
- **Calibration:** the run profile's `auto_apply` takes a switch `owner_judgement`. When it is true, an autonomous run decides each T2 item, and each T1 item that needs its own explicit approval (an additive public API change, a whole-repository format run), with the Owner-judgement lane of prioritization.md's Autonomous mode. The run applies an item on the branch when a new test that fails at its parent and passes at its commit demonstrates the fix. A structural change needs its own proof instead: AST identity, a compiler proof, a PC-15 differential, or, for a documentation fix, a check against an executed source. Every other item is reported with the lane's reason. An applied T2 item keeps tier T2 as the mark of its origin, takes the class of its change, and carries a `review` object (findings schema) that lists it under the report's Applied, review before merge. On a money path, PC-14 condition (d) accepts an alternative to a check the pass did not write: a PC-15 differential over PC-24's characterization cases plus the PF-18 net check. The profile self-setup infers (U01-F05) and the profile template set `structural`, `behavioural`, `dependencies`, `money_paths` and `owner_judgement` true, and `dependency_versions` false (U01-F08). `owner_judgement: false` keeps T2 items, row 18 and PC-11 report-only. The live-effect exclusion (U01-F12), the review object and the scaled revert cap (U01-F13), and the consequence-ordered queue with its deadline reserve (pilot-auto-calibration A01-F34) apply in every autonomous run. `--interactive` and `--report-only` are unchanged (T2 stays report-only with `--interactive`). Nothing is merged, pushed or deployed (U01-F03, U01-F13).

### U01-F07 — Existing tests only gain checked additions
- **Grade:** policy (owner decision, 2026-09-25); the checks that bound it rest on the external sources below, fetched and checked 2026-09-25
- **Evidence:**
  - Owner, 2026-09-25, asked "Les tests existants du projet : le skill peut-il les renforcer ?", chose "Ajouts seulement (Recommandé)": "Le skill peut ajouter des assertions à un test existant trop faible (ex. un test qui ne peut jamais échouer). Retirer, affaiblir ou modifier une assertion reste bloqué mécaniquement." The same day's goal is U01-F05's quote, and the standing criterion U01-F01's.
  - Own measurement: the first autonomous pilot's D22 (`tests/engine.test.ts:37`, `expect(result).toBeTruthy()` on an object that always exists) was graded partial-fix: a new pinning file covered the contract and invariant 2 kept the hollow assertion (evals/pilot-auto-2026-09-25.md; the grader: "Invariant 2 makes D22 a partial fix by design"). The second pilot did the same for the same test (a new `tests/engine-dispatch.test.ts`, the hollow test left as it was).
  - [ImpossibleBench: Measuring LLMs' Propensity of Exploiting Test Cases](https://arxiv.org/abs/2510.20270) (Zhong, Raghunathan, Carlini; arXiv preprint 2510.20270v1, 23 Oct 2025; abstract and HTML version read 2026-09-25): "Modify Test Cases: The model directly modifies tests despite being explicitly instructed not to."; "Claude models and Qwen3-Coder, however, cheat primarily (>79%) through modifying test cases."; "Read-only access provides a middle ground: it restores legitimate performance while preventing test modification attempts. This approach is particularly effective against models like Opus-4.1, whose primary cheating strategy involves modifying test cases, but it does not eliminate other cheating methods"; its example B.1 (Claude Sonnet 3.7) replaces `assert clf.empty is not clf2.empty` with `assert clf.empty is clf2.empty`: "the agent directly inverted the test assertion". The documented modification removes an existing line, which an additions-only rule refuses.
  - [Assertions Are Strongly Correlated with Test Suite Effectiveness](https://people.ece.ubc.ca/amesbah/resources/papers/fse15.pdf) (Zhang, Mesbah, ESEC/FSE 2015): "We find that the number of assertions in a test suite strongly correlates with its effectiveness" (test-quality T13-F07). An added assertion must itself be seen to fail (test-quality T13-F15), with the operators coupled to real faults (pilot-auto-calibration A01-F22).
  - Ways an added line weakens existing ones: [Jest: Setup and Teardown](https://jestjs.io/docs/setup-teardown) (OpenJS): "Jest executes all describe handlers in a test file before it executes any of the actual tests."; [Jest: Globals](https://jestjs.io/docs/api) (OpenJS), `test.failing`: "If failing test will throw any errors then it will pass."; [Jest Object](https://jestjs.io/docs/jest-object) (OpenJS), `jest.retryTimes`: "Runs failed tests n-times until they pass or until the max number of retries is exhausted."; [Vitest: Test API](https://vitest.dev/api/test) (Vitest): `fails` "Whether the test is expected to fail. If it does, the test will pass, otherwise it will fail." and `retry` "The number of times to retry the test if it fails."; [Compound statements](https://docs.python.org/3/reference/compound_stmts.html) (Python Software Foundation): "A function definition is an executable statement. Its execution binds the function name in the current local namespace to a function object" and "Default parameter values are evaluated from left to right when the function definition is executed.", so a later `def` with an existing test's name replaces that test.
  - Snapshots: [Jest: Snapshot Testing](https://jestjs.io/docs/snapshot-testing) (OpenJS): "The first time this test is run, Jest creates a snapshot file"; [Jest CLI](https://jestjs.io/docs/cli) (OpenJS), `--ci`: "Instead of the regular behavior of storing a new snapshot automatically, it will fail the test"; [Vitest: Snapshot](https://vitest.dev/guide/snapshot) (Vitest): "The first time this test is run, Vitest creates a snapshot file" and "By default, Vitest does not write snapshots in CI (process.env.CI is truthy)". An added snapshot matcher writes a snapshot entry outside CI, so it is a snapshot update.
  - The tools the hook reproduces: [Claude Code tools reference](https://code.claude.com/docs/en/tools-reference) (Anthropic, 2026): "The Edit tool performs exact string replacement."; "`old_string` must appear exactly once."; the Write row: "Creates or overwrites files."; "NotebookEdit modifies a Jupyter notebook one cell at a time, targeting cells by their `cell_id`."; [Hooks reference](https://code.claude.com/docs/en/hooks) (Anthropic, 2026): "A timed-out `command`, `http`, or `mcp_tool` hook doesn't block the tool call." and "Any other exit code doesn't block on its own for most hook events."; hook_guard.py also exits 0 on an internal exception, so the checks refuse an existing-test edit on any error or after an 8-second budget. The Edit fields (`file_path`, `old_string`, `new_string`, `replace_all`) and the Write fields (`file_path`, `content`) are the tools' input schema as Claude Code sends it to hooks (hook_guard.py's tests), not a documentation quote.
  - Line accounting: [git-diff](https://git-scm.com/docs/git-diff) (Git project): `--diff-algorithm` minimal "Spend extra time to make sure the smallest possible diff is produced."; `--numstat` "shows number of added and deleted lines in decimal notation ... For binary files, outputs two - instead of saying 0 0." Local check (git 2.51.1.windows.1, 2026-09-25): with core.autocrlf false, `--numstat` counted one deleted line when lines were appended after a final line without a newline, and every line when LF endings became CRLF; with core.autocrlf true the CRLF working tree showed no change; myers, minimal, patience and histogram gave the same counts on these cases.
  - [Writing Tests](https://getfoundry.sh/forge/tests/writing-tests) (Foundry): "`setUp()` runs before each test"; "Forge runs tests with call isolation enabled by default."
- **Calibration:** In every mode an existing test source file may gain lines, never lose, change, reorder or re-encode one; `scripts/strengthen.py` decides, and protocol-change PC-06 states the rule. Only JavaScript, TypeScript, Python, Rust, Go and Solidity files that held a test definition at base, outside snapshot, fixture, mock and support files, may gain lines. Each block of added lines is balanced and sits at the tail of a test body, or adds complete test cases at the tail of a describe block, test class, test contract or the module, or adds named imports to the header. No added line may skip, focus, mark as failing, retry, reconfigure, hook, mock, exit or return early, catch, snapshot, read the environment or a key, reach the network, a live chain or a process, assign or mutate a name the block did not declare, or redeclare a hoisted, item or module-level name the file already uses. The PreToolUse hook applies the rule to Edit, Write and MultiEdit against the file's HEAD version and refuses NotebookEdit and shell writes. diff_guard.py applies it to the working tree and to every commit (a revert removes only what its target added, and adds nothing its target did not remove) and compares line endings through git. Every failure of the checks (an exception, the hook's 8-second budget, an unreadable file) refuses the change. A pure strengthening is its own `test(...): strengthen` commit that comes before the first behavioural commit and fails under a seeded fault its base version survives. A behavioural fix's demonstrating test in an existing file is a new test case, which fails at the fix's parent and raises the executed-test count. `strengthen.py replay` runs the test gates with every strengthened file back at its base version and every test file the run added set aside, per behavioural item that strengthens and at Phase 8, where a confirmed red replay reverts the first commit it fails at (at most 5, then PC-26's range revert). Pure strengthening is T1 structural (`auto_apply.structural` in autonomous mode).

  - [npm debug and chalk packages compromised](https://www.aikido.dev/blog/npm-debug-and-chalk-packages-compromised) (Charlie Eriksen, Aikido, 2025-09-08, updated 2026-03-17): 18 packages with about 2 billion downloads a week; the compromised versions include "debug 4.4.2, chalk 5.6.1, ansi-styles 6.2.2, strip-ansi 7.1.1, supports-color 10.2.1" (each one patch release above a clean one: own reading of the listed versions).   - [Widespread Supply Chain Compromise Impacting npm Ecosystem](https://www.cisa.gov/news-events/alerts/2025/09/23/widespread-supply-chain-compromise-impacting-npm-ecosystem) (CISA, 2025-09-23): "the malicious cyber actor deployed malware that scanned the environment for sensitive credentials."; it "targeted GitHub Personal Access Tokens (PATs) and application programming interface (API) keys for cloud services"; the malware "Exfiltrated the harvested credentials to an endpoint controlled by the actor."; it spread by "publishing compromised versions to the registry"; CISA recommends: "Pin npm package dependency versions to known safe releases produced prior to Sept. 16, 2025." - **Calibration:** A self-setup profile sets `auto_apply` `structural`, `behavioural`, `dependencies`, `money_paths` and `owner_judgement` to true, with provenance "owner decision 2026-09-25 (U01-F06)". Every exclusion of U01-F03 and invariant 8 still holds. A switch, `auto_apply.dependency_versions` (default false, never set by self-setup), is needed on top of `dependencies` by a dependency change that adds or changes a resolved version in a lockfile (DP-08, DP-09, DP-10, SE-21), because such a change's safety cannot be shown offline, whatever its semver level. With `dependencies` alone, an item is applied only when its staged lockfile diff adds no line that sets a version, resolution, integrity or checksum; otherwise its files are restored and it is reported. Under `network: registry-only`, which self-setup writes, a change that fetches a version the lockfile does not hold is already outside the network scope (protocol-preflight step 4); the switch also covers offline re-resolutions such as a dedupe (DP-08). An owner profile that sets `dependencies` true without `dependency_versions` no longer approves version-moving items: this is stricter than before 2026-09-25. Even with `dependency_versions` true, a version the base lockfile does not hold stays report-only while a secret file (`.env*`, a keystore) sits in the repository or a directory above it, checked by file name only (U01-F12).

## Contradictions and open questions

- skill-design T31-F11 (report first, apply in approved tiers) is the evidence-backed default for interactive use; this policy trades the live approval for a profile (the owner's, or one self-setup infers, U01-F05) plus a stronger final gate. The profile-driven trade was measured by two autonomous pilots on one fixture; self-setup is unmeasured, and its classification (U01-F09) is a heuristic that cannot see third-party code, tool-internal downloads (Hardhat's compiler, browsers) or a secret held under an innocuous variable name.
- Decision 2 keeps in the report what cannot be proven offline. Whether a demonstrating test the pass writes counts as that proof on a money path is settled by U01-F14: with PC-24's pinned outputs it does.
- The full scope (U01-F06, U01-F11 to U01-F13) is unmeasured: no autonomous pilot has run with `auto_apply.owner_judgement` true. Pilot 2's findings project about 27 of 49 applied instead of 13 (pilot-auto-calibration A01-F28), an upper bound. Hidden-test failures, trap hits and reverts under the lane are unknown.
- The conservative-option ladder (U01-F11) is a synthesis of the kernel's no-regressions rule, PEP 387's warn stage and Python's logging guidance. A record-only line does not correct a wrong result, so the headline of such an item stays under Open owner items.
- With `--interactive`, T2 items stay report-only, although an autonomous run may apply them: the owner who is present can apply less than the owner's own profile. This is not changed here.
- Phase 8's per-commit re-run (PC-23) costs one gate run per commit. `gates.py --reuse-if-tree` skips commits whose exact tree already passed every gate in its item run (pilot-auto-calibration A01-F40); the verifier's fresh clones still run in full.
- Narrowing the system-contract criterion (U01-F12 (5)) lets contract logic that calls the HTS precompile be tested against a local stub, whose fidelity to the live system contract is unmeasured; every such commit carries the review kind `contract-source`.
- U01-F07's checks are this skill's synthesis over text, not a parser, and are unmeasured: an added call with side effects on shared state, or an alias, passes them, and the replay of the base test set, with added test files set aside, is what catches a masked regression, once at Phase 8 plus a commit-by-commit rerun only when it is red. JSX text and unusual syntax can make the scanner refuse a valid addition; the item then pins its contract in a new file. Foundry state cheatcodes (prank, deal, warp, roll) are allowed at a test body's tail on the strength of "setUp() runs before each test" and call isolation; per-test isolation of state is assumed, not measured. The replay adds one test-gate run per strengthening behavioural item and one at Phase 8, not yet measured on a monorepo. Setting added test files aside assumes no production file imports a file under the test globs.
