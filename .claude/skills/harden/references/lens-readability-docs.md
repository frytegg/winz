# Lens: Readability and Docs

> Purpose: find names, comments, parameter lists and documentation that mislead a reader or have drifted from the code, and classify each as a verified fix or a report-only item. Never edit by score or taste.
> Read when: the readability-docs lens is in scope, or the pass renames, moves or deletes anything that comments, docs or agent context files mention.

## Contents
- Procedure
- Rules: RD-01–05 naming; RD-06–09 expressions, literals and units; RD-10–11 parameter lists; RD-12–19 comments and TODO markers; RD-20–22 formatter commits and renames; RD-23–39 documentation accuracy
- False-positive exclusions
- Evidence limits

A command with no output file is a gap for your limits, never a clean result. If you are the unseeded pass, you receive no tool output: judge from the files alone and say so.

   - Go: golangci-lint varnamelen, revive, godox, durationcheck; `go vet` (tests analyzer); Example tests.
   - Java: Error Prone ArgumentSelectionDefectChecker; Checkstyle MagicNumber; javadoc doclint.
   - C/C++: the ast-grep atom patterns (RD-06); clang-format in check mode.

4. **Manual checks** the tools do not make: misleading names against the LAPD checklist (RD-03); synonym clusters (RD-05); guarded operands before any extraction (RD-07); every comment of every function the pass changed (RD-14), and stale references elsewhere (RD-15); workaround provenance from git (RD-17); TODO triage with age (RD-19); the rename census before any rename (RD-22).

## Rules

### RD-01 — Justify every readability edit by a named rule, never by a score
- **Rule:** Map every readability hunk to a rule id (an RD rule or a linter rule id); drop hunks without one. Use Maintainability Index, cyclomatic or cognitive complexity and model-based readability scores only as regression tripwires, never as the goal or as evidence of improvement. Keep AI-written readability diffs small and reviewable.
- **Detect:** Process check: every candidate names its rule id. Tripwire: `radon cc -s -a` / `radon mi` (Python) or lizard (CCN, NLOC, parameter count) before and after; flag a function whose complexity or LOC rose without a stated benefit.
- **Not when:** An MI drop can come from helpful docstrings or explaining variables: treat it as a prompt to review, not an automatic reject. Scores are weak proxies. Scalabrino et al. (63 developers, TSE 2019) found none of 121 metrics captured understandability. Horikawa et al. (403 agent readability commits, MSR 2026) saw MI fall in 56.1% and cyclomatic complexity rise in 42.7%.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Automatically Assessing Code Understandability](https://doi.org/10.1109/tse.2019.2901468) (Scalabrino et al., TSE 2019); [Do AI Agents Really Improve Code Readability?](https://arxiv.org/abs/2603.13723) (Horikawa et al., MSR 2026); [From Human to Machine Refactoring](https://arxiv.org/abs/2601.13139) (Midolo, Tramontana, Di Penta, 2026); [Learning a Metric for Code Readability](https://doi.org/10.1109/tse.2009.70) (Buse, Weimer, TSE 2010) · dossier: readability T17-F14

### RD-02 — Full-word names for identifiers wider than a tiny scope
- **Rule:** Flag single letters and ad-hoc abbreviations in parameters, fields, module-level variables and exported functions, including abbreviations made by deleting letters (`cntusr`). Make descriptiveness proportional to the name's scope of visibility. Propose renames only through RD-22.
- **Detect:** ESLint id-length (frozen; min 2, exceptions such as i, j, k, x, y, _), golangci-lint varnamelen, ruff E741 (`l`, `O`, `I`). Manual pass: parameters, fields and exported or module-level names of 2 or fewer characters, or with a non-dictionary abbreviation (`cnt`, `mgr`, `usrLst`). Propose a rename only when the scope is wider than about 10 lines or the name crosses a function boundary.
- **Not when:** Established abbreviations (id, url, ctx, err, db, io; Google: "an abbreviation is probably OK if it's listed in Wikipedia"), loop indices, short lambda parameters, and math that mirrors a cited formula. Public names are a breaking rename: T2. Words versus abbreviations is mixed: Lawrie et al. (over 100 programmers, ICPC 2006) often found no difference.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [Shorter identifier names take longer to comprehend](https://doi.org/10.1109/SANER.2017.7884623) (Hofmeister, Siegmund, Holt, SANER 2017); [Descriptive compound identifier names improve source code comprehension](https://doi.org/10.1145/3196321.3196332) (Schankin et al., ICPC 2018); [What's in a Name? A Study of Identifiers](https://doi.org/10.1109/ICPC.2006.51) (Lawrie et al., ICPC 2006); [Effects of Variable Names on Comprehension](https://doi.org/10.1109/icpc.2017.27) (Avidan, Feitelson, ICPC 2017); [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html) (Google); [Linux kernel coding style](https://www.kernel.org/doc/html/latest/process/coding-style.html) (kernel community); [golangci-lint linters](https://golangci-lint.run/docs/linters/) (golangci) · dossier: readability T17-F01

### RD-03 — Treat misleading names as defects before any cosmetic rename
- **Rule:** Flag names whose implied type, cardinality, side effects or return contract contradict the code, and fix them before any cosmetic rename: `is`/`has` returning a non-boolean; `get`/`find` that mutates or returns nothing; `set` that returns; a singular name holding a collection, or the reverse; Rust `as_`/`to_`/`into_` contradicting C-CONV.
- **Detect:** The LAPD catalogue IDs (A1–A4, B3/B4, B6, B7, D1/D2, E1) as a manual checklist. ast-grep for predicate names: TS `function $N($$$): $T { $$$ }` filtered on `^(is|has|can|should)[A-Z]`; Python `def (is|has|can|should)_` plus the return annotation. `rg -n 'def get_|function get[A-Z]|fn get_'`, then inspect. Check cardinality against the type annotations.
- **Not when:** The studies are small and lab-based (Avidan n=9; Fakhoury et al. fNIRS). "Misleading" is partly subjective: two developers pick the same name with a median probability of 6.9% (334 subjects, TSE 2020). Public renames are breaking: T2. The LAPD tool is an unmaintained 2013 Eclipse prototype, so use only its catalogue.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [The Effect of Poor Source Code Lexicon and Readability on Developers' Cognitive Load](https://doi.org/10.1145/3196321.3196347) (Fakhoury et al., ICPC 2018); [Exploring the Influence of Identifier Names on Code Quality](https://doi.org/10.1109/csmr.2010.27) (Butler et al., CSMR 2010); [LAPD linguistic antipattern catalogue](https://www.veneraarnaoudova.com/linguistic-anti-pattern-detector-lapd/las/) (Arnaoudova); [Rust API Guidelines: Naming](https://rust-lang.github.io/api-guidelines/naming.html) (Rust project) · dossier: readability T17-F02

### RD-04 — Naming case: project linter, touched code only, never mass-convert
- **Rule:** Leave naming-case enforcement to the language linter, applied to new or touched code only. Never mass-convert an established codebase between camelCase and snake_case. Map wire-format names (JSON keys, DB columns) with serializer aliases; never rename them.
- **Detect:** ruff N801–N818 and E741; ESLint camelcase (frozen); rustc naming lints plus a manual acronym check (`rg -n 'struct [A-Z]*[A-Z]{3,}'`; C-CASE prefers `Uuid` to `UUID`); golangci-lint revive. Scope every check to changed files.
- **Not when:** The project documents its own convention: follow it. The style studies disagree, with small, training-driven effects. Binkley et al. (135 programmers and non-programmers, 2009) found camelCase more accurate. Sharif and Maletic (2010) found no accuracy difference and faster underscore recognition. PEP 8: "do not break backwards compatibility just to comply with this PEP!"
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [Rust API Guidelines: Naming](https://rust-lang.github.io/api-guidelines/naming.html) (Rust project); [PEP 8](https://peps.python.org/pep-0008/) (PSF); [To camelcase or under_score](https://doi.org/10.1109/ICPC.2009.5090039) (Binkley et al., ICPC 2009); [An Eye Tracking Study on camelCase and under_score](https://doi.org/10.1109/icpc.2010.41) (Sharif, Maletic, ICPC 2010); [Ruff rules](https://docs.astral.sh/ruff/rules/) (Astral) · dossier: readability T17-F17

### RD-05 — One term per concept: report synonym drift, do not unify it
- **Rule:** Report true synonym drift within one module or bounded context (get/fetch/retrieve/load; remove/delete/destroy), and near-identical names in one scope (data/data2/dataList, e/ex). The owner chooses the term.
- **Detect:** Extract identifiers with universal-ctags or tree-sitter, split them into words, and count synonym clusters per module. Near-duplicates: `rg -n --pcre2 '\b([a-zA-Z_]+?)([0-9]+|List|Arr|Obj|Data|Info|Tmp)\b'`, compared against sibling names. Align with the README or glossary vocabulary.
- **Not when:** Different words can signal real differences (load from disk versus fetch over the network). Cross-module public renames are breaking. No experiment shows that synonym drift slows readers, and merely asking for longer names does not give better names (Alpern et al., 2024 preprint).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** C
- **Source:** [How Developers Choose Names](https://arxiv.org/abs/2103.07487) (Feitelson et al., TSE 2020); [Reproducing, Extending, and Analyzing Naming Experiments](https://arxiv.org/abs/2402.10022) (Alpern et al., 2024); [Identifier Name Similarities](https://arxiv.org/abs/2507.18081) (Wong et al., ESEM 2025); [Learning Natural Coding Conventions](https://arxiv.org/abs/1402.4182) (Allamanis et al., FSE 2014) · dossier: readability T17-F18

### RD-06 — Rewrite atoms of confusion as a comprehension fix
- **Rule:** Rewrite the patterns shown in the lab to cause misreadings: assignment used as a value; `++`/`--` inside larger expressions; nested or chained conditional operators; unparenthesised mixed precedence; implicit type conversion; the comma operator; omitted braces on multi-line bodies; octal 0-prefix and mixed literal encodings. Record this as a comprehension fix, not a defect fix, and verify every precedence or conversion rewrite with tests.
- **Detect:** ESLint no-cond-assign, no-nested-ternary, no-sequences, no-implicit-coercion, no-octal, no-plusplus (`allowForLoopAfterthoughts`), curly `multi-line`, eqeqeq `smart`, and @stylistic/no-mixed-operators (core no-mixed-operators deprecated since ESLint v8.53.0). C/C++: ast-grep such as `if ($A = $B) $$$`. Any language: `rg -n '\?[^:]*\?'` for chained ternaries.
- **Not when:** Idiomatic atoms: JS `x == null` (eqeqeq `smart` exists for it) and `i++` in a for header. Java field studies found no link to review confusion (Bogachenkova et al., ICSME 2022) or to defect fixing (Shi et al., ESEM 2024; 76,610 PRs, six projects). The bug-fix association is reported for C/C++, second-hand, so weight the rule higher there.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [Understanding misunderstandings in source code](https://doi.org/10.1145/3106237.3106264) (Gopstein et al., ESEC/FSE 2017); [Atoms of Confusion in Java](https://arxiv.org/abs/2103.05424) (Langhout, Aniche, ICPC 2021); [Evaluating Atoms of Confusion in the Context of Code Reviews](https://doi.org/10.1109/icsme55016.2022.00048) (Bogachenkova et al., ICSME 2022); [Reevaluating the Defect Proneness of Atoms of Confusion](https://doi.org/10.1145/3674805.3686677) (Shi et al., ESEM 2024); [ESLint rules reference](https://eslint.org/docs/latest/rules/) (ESLint v10.11.0) · dossier: readability T17-F16

### RD-07 — Explaining variables only for hard expressions, and never eager
- **Rule:** Introduce a well-named explaining variable or predicate function only for a genuinely hard expression (long or mixed `&&`/`||`, dense arithmetic), and never with a meaningless name. Never turn a guarded or short-circuit operand into an eagerly evaluated variable.
- **Detect:** ruff PLR0916 (preview, default 5); ESLint no-nested-ternary and @stylistic/no-mixed-operators. Manual: 4 or more boolean operands, or mixed `&&`/`||` without parentheses. Before extracting, look for guarded operands (`x != null && x.y`, `i < len && a[i]`, `cheap() || expensive()`): those need a predicate function or a lazy local.
- **Not when:** The effect is small. It appeared only on the hardest of 6 mathematical functions (Cates et al., 113 subjects, ICPC 2021), and meaningless intermediate names slightly lowered understanding. Eager evaluation of a costly operand is not free.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [Does Code Structure Affect Comprehension? On Using and Naming Intermediate Variables](https://arxiv.org/abs/2103.11008) (Cates, Yunik, Feitelson, ICPC 2021); [Ruff PLR0916](https://docs.astral.sh/ruff/rules/too-many-boolean-expressions/) (Astral) · dossier: readability T17-F15

### RD-08 — Do not over-extract; report shallow one-caller helpers
- **Rule:** Never split cohesive logic into tiny functions whose names stand in for comments. Extract only a meaningful, reusable abstraction whose interface is simpler than its body. Report chains of shallow one-caller helpers as "consider inlining".
- **Detect:** lizard or an IDE/LSP call hierarchy: private functions with exactly one caller and 3 or fewer statements that are not a reusable concept, and chains of 3 or more such helpers.
- **Not when:** Small functions help testing and reuse, and both sides of the evidence are expert opinion and anecdote. Inlining is risky when a helper is overridden, mocked or referenced dynamically.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** C
- **Source:** [A Philosophy of Software Design vs Clean Code](https://github.com/johnousterhout/aposd-vs-clean-code/blob/main/README.md) (Ousterhout, Martin, 2024–25); [The Myth of Self-Documenting Code](https://buttondown.com/hillelwayne/archive/the-myth-of-self-documenting-code/) (Wayne, 2021); [HN johnfn](https://news.ycombinator.com/item?id=41928634) (2024) · dossier: readability T17-F21

### RD-09 — Name domain literals; carry units in types or names
- **Rule:** Name the numeric and string literals that encode a domain rule, threshold or protocol value, or that repeat with the same meaning. Give a value with a unit (time, size, money, angle, rate) a unit type (Duration, timedelta, std::chrono, a money type) or, failing that, a unit in its name (timeoutMs). Never pass a bare literal to an API whose unit varies by language: Python `time.sleep(300)` is 5 minutes, Java `Thread.sleep(300)` is 0.3 s.
- **Detect:** ruff PLR2004; ESLint no-magic-numbers (`ignore: [-1,0,1,2]`, `ignoreArrayIndexes`, `ignoreDefaultValues`, `enforceConst`); Checkstyle MagicNumber; golangci-lint durationcheck. Bare literals: `rg -n 'sleep\(\s*\d|setTimeout\([^,]+,\s*\d|time\.Sleep\(\s*\d|Duration\(\s*\d'`. Unit-less names: `rg -n -i --pcre2 '\b(timeout|delay|interval|ttl|duration|max_?age|retry_?after|backoff|period|size|limit|price|amount|angle)\b\s*[:=]\s*-?\d'`.
- **Not when:** Obvious literals, formula constants beside a citation, test expectations, data tables and generated code. A unit suffix on a name already typed as a Duration is redundant. Renaming config keys, env vars, CLI flags or API fields is breaking: T2. There are no controlled studies for either half, and over-application yields `SECONDS_PER_MINUTE = 60` noise.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** C
- **Source:** [ESLint no-magic-numbers](https://eslint.org/docs/latest/rules/no-magic-numbers) (ESLint); [Ruff PLR2004](https://docs.astral.sh/ruff/rules/magic-value-comparison/) (Astral); [Checkstyle MagicNumber](https://checkstyle.org/checks/coding/magicnumber.html) (Checkstyle 14.1.0, 2026); [Please put units in names](https://ruuda.nl/2022/please-put-units-in-names) (van Asseldonk, 2022); [HN: Please put units in names](https://news.ycombinator.com/item?id=30749134) (2022); [golangci-lint linters](https://golangci-lint.run/docs/linters/) (golangci) · dossier: readability T17-F11, T17-F03

### RD-10 — Adjacent same-typed parameters: review call sites for swapped arguments
- **Rule:** Flag functions with two or more adjacent same-typed parameters (width/height, from/to, lat/lon, userId/orgId), public and hot APIs first, and review their call sites: a call whose arguments would match the parameter names better if permuted is a swapped-argument defect candidate, reported as a probable defect whose fix is behavioural, never as a readability edit. Use more than 5 parameters only as a priority signal for this swap review, because the chance of an argument selection defect "increases markedly" above five (Rice et al.). The parameter-count finding, its threshold (7 or more) and "report, do not reshape" belong to CX-30 in the complexity-design lens: file parameter objects, named arguments or wrapper types there, and never reshape a signature under this rule.
- **Detect:** Java: Error Prone ArgumentSelectionDefectChecker. Adjacent same-typed parameters: `rg -n --pcre2 '\((\s*\w+\s*:\s*(number|string|int|str|float|i64|u32|bool)\s*,){2,}'`, then review the call sites for swaps. Priority order for the review: functions above 5 parameters in the lizard PARAM column, ruff PLR0913 and PLR0917 (both default 5; PLR0917 stable since ruff 0.16.0) or ESLint max-params with max 5 (the default of 3 is noisy on finished code).
- **Not when:** Overrides must match the parent (ruff exempts `@typing.override`). FFI, math and conventional orders such as (x, y). Name-based swap detection has false positives: DeepBugs reported 102 mistakes in 150,000 JavaScript files at a 68% true-positive rate. The ">5" evidence is one Java study at Google (Rice et al., OOPSLA 2017; 200M lines internal plus 10M external). The tool defaults (ESLint 3, ruff 5) state no evidence.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [Detecting argument selection defects](https://doi.org/10.1145/3133928) (Rice et al., OOPSLA 2017); [Error Prone ArgumentSelectionDefectChecker](https://errorprone.info/bugpattern/ArgumentSelectionDefectChecker) (Google); [DeepBugs](https://doi.org/10.1145/3276517) (Pradel, Sen, OOPSLA 2018); [Ruff PLR0913](https://docs.astral.sh/ruff/rules/too-many-arguments/) (Astral); [Ruff PLR0917](https://docs.astral.sh/ruff/rules/too-many-positional-arguments/) (Astral); [ESLint max-params](https://eslint.org/docs/latest/rules/max-params) (ESLint) · dossier: readability T17-F05

### RD-11 — Replace behaviour-switching boolean parameters
- **Rule:** Replace a boolean parameter that switches a function between different behaviours with separate functions, an enum or union, or a required keyword or named argument. At minimum, no call site passes a bare positional `true`/`false`. When the logic is tangled, keep one private flagged implementation behind the public functions.
- **Detect:** ruff FBT001/FBT002/FBT003; clippy fn_params_excessive_bools and struct_excessive_bools (pedantic, so enable them explicitly); `ast-grep --lang ts -p '$F($$$A, true, $$$B)'` (and the `false` variant), then check whether the callee branches on it. Structs with 3 or more mutually exclusive bools are enum candidates.
- **Not when:** Booleans passed straight from data (Fowler's check-box case), setters, dunder operators and overrides. Languages that label arguments at the call site (keyword-only Python, Kotlin, Swift). Do not pre-model enums for states that may never appear. Public signatures: T2.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** C
- **Source:** [FlagArgument](https://martinfowler.com/bliki/FlagArgument.html) (Fowler, 2011); [Ruff FBT001](https://docs.astral.sh/ruff/rules/boolean-type-hint-positional-argument/) (Astral); [clippy excessive_bools](https://raw.githubusercontent.com/rust-lang/rust-clippy/master/clippy_lints/src/excessive_bools.rs) (rust-clippy); [HN: Booleans Are a Trap](https://news.ycombinator.com/item?id=42099897) (2024) · dossier: readability T17-F04

### RD-12 — Never delete or blindly edit executable and directive comments
- **Rule:** Before deleting or editing any comment, check whether a tool executes or parses it, and preserve or update it if so. This covers Python doctests, Rust doc examples, Go `//go:build`/`//go:generate`/`//go:embed`, lint and type suppressions (`eslint-disable`, `noqa`, `type: ignore`, `@ts-expect-error`, `nolint`, `#[allow]`), JSDoc types under checkJs, coverage pragmas, and licence and SPDX headers.
- **Detect:** Exclude from comment edits: doctests `rg -n --pcre2 '^\s*(>>>|\.\.\.)\s'`; Go directives `rg -n '//go:(build|generate|embed|linkname)|// \+build'`; suppressions, pragmas and licences `rg -n 'eslint-disable|@ts-(ignore|expect-error|nocheck)|#\s*(noqa|type:\s*ignore|pragma)|//\s*nolint|istanbul ignore|c8 ignore|pragma: no cover|SPDX-License-Identifier|@license'`; fenced code in Rust `///` comments; JSDoc `@type`/`@param {..}` under checkJs. After any comment edit, the gates must include `cargo test --doc`, `pytest --doctest-modules`, `go vet` and `go build` for all tagged platforms, plus the linters.
- **Not when:** Stale suppressions should go, but only through the linters' own unused-directive checks (ESLint `--report-unused-disable-directives`, mypy `warn_unused_ignores`), never through blind cleanup.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [doctest](https://docs.python.org/3/library/doctest.html) (PSF, Python 3.14.7); [Rustdoc: Documentation tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html) (Rust project); [go command: Build constraints](https://pkg.go.dev/cmd/go#hdr-Build_constraints) (Go project); [ESLint CLI](https://eslint.org/docs/latest/use/command-line-interface) (ESLint); [mypy config](https://mypy.readthedocs.io/en/stable/config_file.html) (mypy) · dossier: readability T17-F22

### RD-13 — Delete or rewrite comments that only restate the code
- **Rule:** Flag comments that only narrate what the next line obviously does, and docstrings that only repeat the name and parameters. Propose deleting them, or rewriting them to give intent, rationale, constraints, invariants, units or non-obvious consequences. For a restating comment on a complex line, first ask whether the code should be clearer or the comment should state the reason instead.
- **Detect:** eslint-plugin-jsdoc informative-docs (not in the recommended config). A token-overlap check: drop stop words, split the camel/snake identifiers of the documented signature or next statement, and flag comments they almost fully cover. `rg -n -i '(//|#|/\*)\s*(increment|decrement|sets?|gets?|returns?|loop (over|through)|calls?|initiali[sz]e)\b'`, then manual review.
- **Not when:** "What" comments on regular expressions, bit manipulation and dense math (Google: "regular expressions and complex algorithms often benefit greatly from comments"). Teaching code and API reference docs. A documented project convention (the Linux kernel wants comments to say what, not how). Pure restatement is real but not dominant: in 21,140 Python files, the header comments that existed usually added information beyond the signature (Oxenhorn et al., 2024 preprint).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [PEP 8](https://peps.python.org/pep-0008/) (PSF); [Google Engineering Practices: What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html) (Google); [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html) (Google); [Linux kernel coding style](https://www.kernel.org/doc/html/latest/process/coding-style.html) (kernel community); [Best practices for writing code comments](https://stackoverflow.blog/2021/12/23/best-practices-for-writing-code-comments/) (Spertus, 2021); [The Paradox of Function Header Comments](https://arxiv.org/abs/2401.07704) (Oxenhorn et al., 2024); [eslint-plugin-jsdoc informative-docs](https://github.com/gajus/eslint-plugin-jsdoc/blob/main/docs/rules/informative-docs.md) (gajus) · dossier: readability T17-F06

### RD-14 — Reconcile every comment of every function the pass changes
- **Rule:** For every function whose body the pass modified, re-read its whole docstring and all its comments, not only the diff hunks. Flag any comment that mentions a token the diff deleted, or that describes the old control flow, return values or raised errors. Update it in the same commit as the code, once the new behaviour is pinned by a test.
- **Detect:** Removed identifiers: `git diff -U0 BASE..HEAD | grep -E '^-[^-]' | grep -oE '[A-Za-z_][A-Za-z0-9_]{2,}' | sort -u`. Collect the comment lines of the changed hunks from `git diff -U10 BASE..HEAD`, and flag lines containing a removed token (`grep -wFf`). Then re-read each modified function in full. This needs the pass's diff, so run it only after the apply phase.
- **Not when:** The token-overlap heuristic reached 74.1% precision (F1 68.0) only on a deliberately balanced benchmark (Panthaplackel et al., AAAI 2021), so expect lower precision in the field. It misses semantic drift where the same names now mean something else. Comments on code the pass did not change belong to RD-15.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Deep Just-In-Time Inconsistency Detection Between Comments and Source Code](https://arxiv.org/abs/2010.01625) (Panthaplackel et al., AAAI 2021); [A Large-Scale Empirical Study on Code-Comment Inconsistencies](https://doi.org/10.1109/ICPC.2019.00019) (Wen et al., ICPC 2019); [PEP 8](https://peps.python.org/pep-0008/) (PSF); [ETF](https://arxiv.org/html/2410.14748v4) (Maharaj et al., ACL 2025); [HN u801e](https://news.ycombinator.com/item?id=29674080) (2021) · dossier: readability T17-F08; docs-accuracy G106-F11

### RD-15 — Report stale comment references and code-comment disagreements; never fix either side silently
- **Rule:** Scan all comments for references to identifiers, parameters or files that no longer exist, and for comments that contradict the code. When comment and code disagree, establish which side is wrong from the tests, `git log -L` and the linked issue; never edit one side to match the other without that. The code is the wrong side when all of these hold: the comment is the declaration's doc comment, or the project's docs, and states what the code does for its callers rather than how; `git log -L` shows no commit that changed that behaviour after the comment was written, so the comment is not stale; no existing test, snapshot, golden output, help text or other doc states the current behaviour; every in-repo caller of the declaration, read and cited at file:line, is consistent with the comment's statement and none relies on the current behaviour; and a new test asserting the comment's statement fails at base. Then fixing the code restores a promise (prioritization row 21, PC-14): the comment is the promise, cited by file:line in the `Behaviour change:` line, and the item is T1 behavioural, filed under the rule that names the code defect (PZ-24 step 1) or under this rule when none does. Its demonstrating test, its `Behaviour change:` line and its report entry are what make it not silent. Report everything else as a possible bug, T2: a stale reference, a disagreement whose wrong side is not established, and a comment that is itself the wrong side, which is corrected only with the owner. In autonomous mode with `auto_apply.owner_judgement` true, the Owner-judgement lane decides these T2 items (prioritization.md, Autonomous mode). A stale reference to an identifier that `git log -S` shows was renamed or removed, and a comment that a test, the docs or the history establishes as the wrong side, are corrected as comment-only structural changes proven AST-identical and listed under Applied, review before merge. A disagreement whose wrong side is not established stays report-only (lane 1(i)), because no test shows which side the owner meant (user-policy-autonomy U01-F06).
- **Detect:** ReCite-style scan: extract `name()` tokens and backticked identifiers from comments, and resolve each against universal-ctags or an LSP `workspace/symbol` query. `git log -L :func:file` shows whether a comment predates the last logic change; for a disagreement, run `git log -L <start>,<end>:<file>` over the comment's and the contradicting code's lines, and `git grep -n` the stated behaviour in tests, snapshots, docs and help text. Also rustdoc broken_intra_doc_links.
- **Not when:** Detectors are imprecise. ReCite (ASE 2026) found 869 stale references in Linux v6.18-rc1, but only 42.5% of its repairs were directly applicable. The 1.5x bug-introduction figure for inconsistent changes comes from one preprint using a GPT-3.5 detector (Radmanesh et al., 2024). A disagreement alone does not say which side is wrong: iComment found 33 bugs and 27 bad comments among 60 inconsistencies in Linux, Mozilla, Wine and Apache, 19 of them confirmed by developers (SOSP 2007). In the autonomous pilot, this rule's T2 left a table sorted by its formatted strings although its doc comment, written in the same commit, says "largest position first"; the v3 runs fixed the same item under TS-33 in 3 of 3 (pilot-auto-calibration A01-F14).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [We Must Have Missed This Comment (ReCite)](https://arxiv.org/abs/2608.03734) (Sun et al., ASE 2026); [Investigating the Impact of Code Comment Inconsistency on Bug Introducing](https://arxiv.org/abs/2409.10781) (Radmanesh et al., 2024); [PEP 8](https://peps.python.org/pep-0008/) (PSF); [rustdoc lints](https://doc.rust-lang.org/rustdoc/lints.html) (Rust project); [/* iComment: Bugs or Bad Comments? */](https://www.sigops.org/s/conferences/sosp/2007/papers/sosp054-tan.pdf) (Tan, Yuan, Krishna, Zhou, SOSP 2007); [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html) (Google: "Almost every function declaration should have comments immediately preceding it that describe what the function does and how to use it"; "Declaration comments describe use of the function (when it is non-obvious); comments at the definition of a function describe operation") · dossier: readability T17-F08; pilot-auto-calibration A01-F14; user-policy-autonomy U01-F06

### RD-16 — Public contracts: report missing interface comments; write none that is unverified
- **Rule:** Report every exported function, class or module that has no interface comment and whose contract its signature and types do not fully express (preconditions, formats, units, ordering, ownership, side effects, errors, concurrency, cost). Never strip comments on "self-documenting code" grounds. Write no new behaviour description; cite the verifying code location or test in the report for the owner.
- **Detect:** ruff D100–D107; Rust `missing_docs` (allowed by default, so enable it for the run); golangci-lint revive exported checks. Manual: ask Ousterhout's questions of each public symbol (expected formats, ordering, duplicates).
- **Not when:** Trivial getters and private helpers. Mandated docs invite template noise, and LLM-written docs can assert false behaviour (RD-34).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [A Philosophy of Software Design vs Clean Code](https://github.com/johnousterhout/aposd-vs-clean-code) (Ousterhout, Martin, 2024–25); [The Paradox of Function Header Comments](https://arxiv.org/abs/2401.07704) (Oxenhorn et al., 2024); [The Myth of Self-Documenting Code](https://buttondown.com/hillelwayne/archive/the-myth-of-self-documenting-code/) (Wayne, 2021); [Go Proverbs](https://go-proverbs.github.io/) (Pike, 2015) · dossier: readability T17-F07; docs-accuracy G106-F10, G106-F21

### RD-17 — Workarounds and unidiomatic code carry a "why" with provenance
- **Rule:** Flag workarounds, deliberately unidiomatic code, sleeps and retries, copied code, suppressions and bug-fix guards that lack a short "why" comment linking the upstream issue, ticket, spec or source. Propose the comment only when a commit message, issue or upstream link states the reason. Never invent a rationale; report the rest for the owner.
- **Detect:** `rg -n --pcre2 '(sleep\(|setTimeout\(|time\.Sleep\(|retry|navigator\.userAgent|sys\.platform|process\.platform|runtime\.GOOS|#\s*noqa|eslint-disable|@ts-ignore|@ts-expect-error|#\s*type:\s*ignore|#\[allow\(|@SuppressWarnings|//\s*nolint)'`, then check for an explanatory comment within about 3 lines. Also check version guards and broad exception handlers. Provenance: `git log -S` and `git blame`.
- **Not when:** There is no quantitative evidence. A wrong "why" is worse than none (PEP 8), and links to private trackers rot.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** C
- **Source:** [Best practices for writing code comments](https://stackoverflow.blog/2021/12/23/best-practices-for-writing-code-comments/) (Spertus, 2021); [HN hinkley](https://news.ycombinator.com/item?id=41941026) (2024); [HN laserlight](https://news.ycombinator.com/item?id=29672365) (2021); [Google Engineering Practices](https://google.github.io/eng-practices/review/reviewer/looking-for.html) (Google) · dossier: readability T17-F20

### RD-18 — Delete commented-out code, keeping explained alternatives
- **Rule:** Propose deleting commented-out code blocks, since version control keeps them. Keep a disabled alternative whose comment says why it is kept and when to restore it, and keep examples inside documentation.
- **Detect:** ruff ERA001. Other languages: `rg -n --pcre2 '^\s*(//|#)\s*([a-zA-Z_][\w.]*\s*\(.*\)\s*;?|(if|for|while|return|const|let|var|def|fn)\b.*[{:;]\s*)$'`, then review by hand. Run `git log -S'<snippet>'` before proposing a deletion.

- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** C

### RD-19 — Triage TODO, FIXME and HACK markers; never blanket-delete
- **Rule:** Inventory the TODO, FIXME, HACK, XXX, KLUDGE, WORKAROUND and "temporary" markers, and the AI-debt phrases. Label each one: resolved (condition verified gone), actionable, limitation note, or escalate (FIXME/HACK on a security or correctness path). Report the inventory with each marker's age. Never impose a link or author policy the project lacks: the TODO-policy dispute is unresolved, so report and do not auto-fix.
- **Detect:** `rg -n -i '\b(TODO|FIXME|HACK|XXX|KLUDGE|WORKAROUND)\b|temporary (fix|hack|workaround)'`, plus copilot, chatgpt, claude, gemini, "generated by", "not sure why" and "untested". ruff TD003 and FIX001–FIX004; ESLint no-warning-comments (frozen); golangci-lint godox. Age: `git blame --porcelain`.
- **Not when:** Do not enable ruff TD002 (author required) where the project follows Google Python style, which says to avoid TODOs that name a person or team. ESLint no-warning-comments on a large legacy base "might get hundreds of warnings". SATD is a maintainability signal, not a defect predictor: SATD changes induced fewer future defects (Wehaibi et al., SANER 2016).

### RD-20 — Run only the formatter the project already enforces, in check mode
- **Rule:** Detect the project's configured formatter for each language and run it in check mode. If the project already enforces it (CI or pre-commit) and the check fails, formatting the files the pass touches is T0, in its own `style:` commit made before that item's other changes (PC-11, RD-21). A whole-repository format run is T1 and needs its own explicit approval (PC-11); without it, report the remaining drift. If no formatter is configured, report adoption as an owner decision; never add one.

### RD-21 — Mechanical changes in their own commits, listed in .git-blame-ignore-revs
- **Rule:** Keep formatting, mass renames, codemods and import sorting in their own commits, never mixed with behaviour changes. Propose adding those SHAs to `.git-blame-ignore-revs` at the repository root. Print the `git config blame.ignoreRevsFile .git-blame-ignore-revs` line in the report instead of setting per-developer config.
- **Detect:** Per commit, `git show --stat` and `git diff -w --ignore-blank-lines <sha>^ <sha>`: a format commit has no non-whitespace hunk left, and a logic commit has no large whitespace-only hunk. Check that the ignore file exists and lists the mechanical SHAs, and read `git config --get blame.ignoreRevsFile`.
- **Not when:** The ignore file applies from Git 2.23 on. GitHub and GitLab 17.10+ honour it in blame views by default; other hosts need per-developer config. Squash-merge collapses the separate commits unless the mechanical change lands as its own PR. Rewriting history instead forces every clone to be redone (HN skrause, 2022).

### RD-22 — Rename behaviour-safely and repo-wide
- **Rule:** Drive every rename through a semantic LSP or IDE rename, never text replace. First search the whole repository, non-code files included, for the old name as a string in its snake, camel and kebab variants. Never rename an exported, public, serialized or reflected name: that is T2, and a deprecation alias is the owner's call. Confirm the touched code is covered by tests before trusting a green run; if it is not, add a characterization test or skip the rename.
- **Detect:** `rg -n -w '<oldName>' --hidden -g '!.git' -g '!node_modules'` across all file types. Export status: `__all__`, `index.ts`, `pub`, capitalised Go names. Serialization: serde rename, `@JsonProperty`, pydantic alias, ORM columns, GraphQL/OpenAPI. Dynamic access: getattr, Reflect, Class.forName, `obj["name"]`, DI containers. Coverage of the touched functions. Then type-check, tests and build. Docs references to the old name go through RD-24.
- **Not when:** LSP renames of locals are very low risk, and demanding coverage for them is overkill.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B

### RD-23 — Classify every documentation finding as safe-fix (T1) or report-only (T2) before acting
- **Rule:** For each docs finding, record the evidence, whether the pass caused it, whether a test or executed command confirms the corrected text, and its class. Safe-fix is T1, one `docs:` commit per class: broken relative links and anchors to moved files; references to names the pass renamed; commands and version pins that ran in the fresh-clone sandbox; blocks regenerated from real output; docstring parameter names that mechanically mismatch the signature; missing .env.example keys with empty values; CHANGELOG `[Unreleased]` entries. Everything else is T2. When a doc is known to be wrong but the right content is unknown, propose a visible "may be outdated" note rather than a deletion.
- **Detect:** Manual classification of each finding using the four fields above.
- **Not when:** Over-conservative reporting creates noise that owners ignore. The class boundaries are judgement calls, not measured optima.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B

### RD-24 — Every code-formatted identifier, path, flag, config key and env var in the docs exists at HEAD
- **Rule:** Check every code-formatted identifier, path, CLI flag, config key and env var in the README, docs/ and wiki pages against the source at HEAD. Check every symbol or path the pass renamed or deleted against all the docs. Fix only references the pass itself renamed, using the verified new name; report every other stale reference.

- **Not when:** CHANGELOG files, release notes and migration guides, whose references are historically correct. A flag removed from the source but still relevant to users, or a name whose functionality remains in the program logic. ### RD-25 — Execute every example that claims to run
- **Rule:** Run the project's examples as tests: Python doctests (modules and Markdown), Rust doc tests, Go `Example*` functions with `// Output:`, TypeScript examples in Markdown, and CLI transcripts. Every escape hatch needs a reason: Rust `ignore` blocks, Go examples with no Output comment (these only compile), doctest `+SKIP`. Adding a runner is T1. Fixing an example is T1 only when its corrected output was verified against the intended behaviour; otherwise report.

- **Not when:** Output-comparing doctests break on minor dependency changes (HN, a SageMath packager). Network examples need `no_run` or compile-only; pytest's NUMBER option relaxes float matching. Updating the expected output to match the code can enshrine a bug.

### RD-26 — Execute every shipped notebook top to bottom in a fresh kernel
- **Rule:** Execute every notebook shipped as documentation, a tutorial or a result, top to bottom in a fresh kernel, from the fresh-clone environment. Each of these is a finding: any error; any dependence on out-of-order runs (null or non-increasing `execution_count`); any import missing from the declared dependencies. Fix only missing imports, paths and pins verified by re-running; report changed numeric results.
- **Detect:** Inside the fresh clone in `<scratch_dir>` (RD-31), on the tracked notebooks only (`grep '\.ipynb$'` over the repository's `.harden/tools/inscope.txt`, read by absolute path since the clone has no `.harden/`; the relative paths are the same in the clone): `pytest --nbmake --nbmake-timeout=600 <those notebooks>` or `jupyter nbconvert --to notebook --execute <notebook>`. Per notebook, `jq -c '[.cells[]|select(.cell_type=="code")|.execution_count]'`. Compare the imports with the declared dependencies.
- **Not when:** Long-running, GPU or proprietary-data notebooks tagged `skip-execution`, with the README saying so. Stochastic results need seeds before comparison. nbmake activity has slowed (1.5.5, December 2024).

### RD-27 — Build the generated reference docs with warnings as errors
- **Rule:** Build the project's generated API or reference docs with warnings as errors and cross-reference checks on; any non-zero exit is a finding. Fix a broken reference only when its target was renamed and the new target resolves. Report references whose target was removed.
- **Detect:** `sphinx-build -W -n` (from Sphinx 8.1 it runs the whole build before exiting 1); `mkdocs build --strict` with `validation.links.not_found` and `validation.links.anchors` set to `warn` (anchor validation is new in MkDocs 1.6); `typedoc --treatWarningsAsErrors` (invalidLink and notExported on by default); `RUSTDOCFLAGS='-D warnings' cargo doc --no-deps` (rustdoc lints other than missing_docs never run under rustc); `javadoc -Xdoclint:all -Werror`.
- **Not when:** Nitpicky mode floods the build with unresolvable third-party references: use `nitpick_ignore` or intersphinx rather than switching it off. ### RD-28 — Gate on local links and anchors; only report external links
- **Rule:** Check the links in Markdown and HTML docs and in doc comments. A broken local link or anchor is a finding. ### RD-33 — Commands, flags, versions and tags in the docs resolve against one source of truth
- **Rule:** Cross-check every command in the README, CONTRIBUTING and agent files against the task runner (package.json scripts, Makefile or justfile targets, pyproject scripts, Cargo aliases), against the commands CI runs, and against each other. Check that the lockfile matches the documented package manager, and that the README's CLI usage matches the real `--help` of each subcommand. Report "which variant is intended" questions and docs that diverge from the published artefact.

## False-positive exclusions

- Generated and vendored code, for every rule.
- Established abbreviations (id, url, ctx, err, db, io, anything "listed in Wikipedia"), loop indices, short lambda parameters, and names mirroring a cited formula (RD-02).
- Wire-format, serialized and reflected names: never rename them; map them with aliases (RD-04, RD-22).
- Idiomatic atoms: JS `x == null`, and `i++` in a for header (RD-06).
- Obvious literals (-1, 0, 1, 2), formula constants beside a citation, test expectations and data tables (RD-09).
- Booleans passed straight from data, setters, dunder operators and overrides; FFI, math and conventional (x, y) parameter orders (RD-10, RD-11).
- "What" comments on regular expressions, bit manipulation and dense math; teaching code; API reference docs (RD-13).
- Comments a tool executes or parses: doctests, Rust doc examples, `//go:` directives, suppressions, coverage pragmas, SPDX and licence headers, JSDoc types under checkJs (RD-12).
- ERA001 or grep hits on prose and pseudo-code; examples inside documentation; a disabled alternative that says why it is kept (RD-18).
- CHANGELOG files, release notes and migration guides that mention removed elements; flags removed from the source but still relevant to users; common words caught by backtick extraction (RD-24, RD-39).
- External-link 429/403, Cloudflare and login-wall failures, and anchors created by JavaScript (RD-28).
- Deliberate command differences (a stricter CI variant, several supported package managers), a README documenting a subset of flags, external tools' flags, and width-dependent help output (RD-33).
- Dynamic env-key access and framework- or platform-injected variables (RD-35). Official HTTPS `curl | sh` installers (rustup, uv, nvm) and legitimate private mirrors, once the domain is verified (RD-30).
- The user's private `~/.claude` files (RD-32), and notebooks tagged `skip-execution` for GPU, long runs or proprietary data (RD-26).

## Evidence limits

- **Naming** evidence comes from lab snippets without IDE support. Hofmeister et al. (72 professional C# developers, SANER 2017): words gave 19% faster comprehension than letters and abbreviations. Schankin et al. (88 Java developers, ICPC 2018): semantic defects found about 14% faster, for experienced developers only. Lawrie et al. (over 100 programmers, 2006) often found no difference, and Avidan and Feitelson had n=9.
- **Atoms of confusion:** 2.7–56x more mistakes for 7 of 14 atoms in the lab (132 students, Java, ICPC 2021), and 15 of 19 candidate atoms confirmed with 73 participants (ESEC/FSE 2017). The Java field studies are null, and the C/C++ bug-fix association is second-hand.
- **Readability metrics:** none of 121 metrics captured understandability (Scalabrino et al., 63 developers, 444 evaluations). Buse and Weimer's model (120 annotators) predicts readability judgments, not comprehension.
- **Parameters:** the ">5" figure rests on one Java study at Google (OOPSLA 2017), so RD-10 uses it only to order swap review; the count threshold is CX-30's. The tool defaults (ESLint 3, ruff 5) state no evidence.
- **Comments:** no controlled experiment measures the cost of redundant comments. The 1.5x inconsistency-bug link is one 2024 preprint with an LLM detector. Wen et al. (1.3 billion AST changes, 1,500 systems) was read as an abstract only.
- **TODO removal rates conflict:** Potdar and Shihab (4 projects, 2014) found 26.3–63.5% removed. Maldonado et al. (5 projects, 2017) found the majority removed, with median lifetimes of 18–172 days. Zampetti et al. (MSR 2018) found 20–50% of removals accidental. No study compares inline TODOs with tracker tickets.
- **No empirical studies** exist for magic numbers, units in names, commented-out code or workaround comments.
- **Formatters:** the only trial is n=20 (ICSOFT 2023), where unindented code took 179% more time. There is no data on retrofitting formatters or repo-wide renames onto long histories.
- **Renames:** only 22% of refactored methods and fields were tested by existing regression tests (Rachatasumrit and Kim, 3 Java projects, ICSM 2012).
- **Docs drift:** Tan et al. (top-1000 GitHub projects, EMSE 2024) found an outdated code-element reference in 28.9% at analysis time and 82.3% at some point, outdated for 4.7 years on average. Treude and Baltes (2026 preprint, 356 repos, 612 agent files) flagged stale references in 23.0% of repositories. No study measures whether stale context files lower agent success.
- **Fresh-checkout failure** depends on the population. More than 38% of 7,200+ Java builds failed (PLATEAU 2016). Of 2,500 Java projects on JDK 6–23, 30–44% built per JDK from Java 8 on, and about 32% failed on every JDK (EMSE 2026). 75.6% of Python gists need non-trivial configuration (ICSME 2018). Of 863,878 notebook runs, 24.11% ran without errors and 4.03% reproduced their results (MSR 2019).
- **LLM doc hallucination** was measured on 2024–25 models: only 61.10% of entities existed in DocAgent's GPT-4o-mini chat baseline (ACL 2025), and ETF found 31.63% (130 of 411) of summaries hallucinated (ACL 2025).
- **Research prototypes, not maintained products:** DOCER (2023), LAPD (2013), ReCite and the just-in-time comment detectors.
