# Lens: Frontend

> Find the defects a finished React, Next.js, Vue or Svelte frontend still carries: unguarded Server Functions and route handlers, secrets crossing into client bundles, vulnerable RSC versions, effect, key and memoisation bugs, compiler drift and accessibility gaps. Keep every behaviour-changing fix narrow and test-covered.
> Read when: JSX/TSX, `.vue` or `.svelte` files, or a `react`, `next`, `vite`, `vue` or `svelte` dependency, are in scope.

## Contents
- Procedure
- Rules: server/client boundary (FE-01 to FE-05); hooks and effects (FE-06 to FE-12); identity, memoisation and compiler (FE-13 to FE-17); accessibility (FE-18 to FE-22); bundle (FE-23)
- False-positive exclusions
- Evidence limits

## Procedure

You are a fresh-context, read-only lens subagent (detection step 8). You detect and triage; the orchestrator runs the tools, verifies, ranks and applies. Your tools are Read, Grep and Glob: never edit or write a file and never run a command. The orchestrator never runs a fix mode (`eslint --fix`, `knip --fix`, `pnpm audit --fix`), installs packages or changes project config.

1. **Load context.** Read `.harden/inventory.json` (frameworks, manifests, lockfiles, configured linters), `.harden/config.json` (scope, exclude globs), `.harden/rank.json`, the raw detector outputs in `.harden/tools/` (none in an unseeded pass, DT-21), and the TypeScript language file. Exact commands, pinned versions and ephemeral invocation live in the language file; this lens names tools, rule ids and grep patterns. The project's own ESLint config runs first. Nothing here overrides it.
2. **Classify the frontend and record versions.** Note the framework and version (`react`, `next`, `vite`, `vue`, `svelte`), the rendering mode (client SPA, SSR/SSG, App Router with Server Functions), whether React Compiler is on (FE-15 Detect) and whether Strict Mode is on (FE-09). Several rules are version-gated. If there are no JSX/TSX, `.vue` or `.svelte` files and no framework dependency, return "lens not applicable" with the evidence.
3. **Server/client boundary first.** It carries the highest consequence. Where Server Functions, route handlers or a bundler that inlines env vars exist:
   - inventory entry points and walk FE-01's four checks for each exported function;
   - run the FE-02, FE-03 and FE-05 greps through the Grep tool;
   - read the FE-04 version-check output (`pnpm ls`, `pnpm why`; `pnpm audit --prod` only with `"network": "allowed"`, see FE-04) and the gitleaks `dir` output on build output, both detector commands. gitleaks runs only if the baseline gates already produced the build; otherwise record "bundle scan not run".
4. **Detector commands (run by the orchestrator in detection step 4; read their outputs from `.harden/tools/`): static lint in report mode.** The orchestrator uses ephemeral overrides so the project's config file is never edited and writes JSON to `.harden/tools/`. Summarise per rule and file each diagnostic under the FE rule that owns it.
   - React: eslint-plugin-react-hooks v7 `recommended` with compiler rules overridden to `warn` (FE-06); eslint-plugin-react `no-array-index-key`, `jsx-key`, `no-unstable-nested-components`; eslint-plugin-jsx-a11y `flatConfigs.recommended`; optionally eslint-plugin-react-you-might-not-need-an-effect, all rules at warn.
   - Vue: eslint-plugin-vue `flat/essential`, which includes `vue/no-use-v-if-with-v-for`.
   - Svelte: no linter was verified; use the FE-08 and FE-10 greps.
5. **Manual sweeps no lint covers.** Run the ripgrep patterns in FE-07 to FE-14 through the Grep tool, read the ast-grep outputs (detector commands) from `.harden/tools/`, and read every hit: effects without cleanup, ref guards, setState in effects, keys, mutation during render, hydration-sensitive render code. Classify each hit as its rule directs.
6. **Runtime checks, run by the orchestrator only where the gates can already start the app and Playwright is present; read their output from `.harden/tools/`.** axe through `@axe-core/playwright` with tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa` on the main routes and states (FE-18, FE-21), and the browser console for hydration errors after a production build (FE-12). Profiler evidence (FE-15, FE-17) needs a human with React DevTools, so emit those candidates as `needs_review`.
7. **Return candidates plus files_read as your final message**; the orchestrator merges them into `.harden/candidates.json`. files_read lists every file you read with its line ranges (DT-02). One candidate per location, in the findings schema (`assets/findings.schema.json`):
   - `lens: "frontend"`; `rule_ref` = FE-NN, or `project:eslint/<rule>` for a project-configured rule;
   - `file` repo-relative and `line` at `base_sha`; `class`, `tier` and `fix_risk` copied from the rule block; `verified: false`; `status: "candidate"`;
   - `confidence`: `tool_high_precision` for axe `violations`; `reproduction` for an observed runtime error (hydration error, duplicate requests); `needs_review` for lint and grep hits; `inference` for reading alone;
   - `evidence[]`: `tool` (command, rule id, output path), `source` (file:line trace, e.g. the effect body and the resource it acquires), `doc` (the advisory or doc a version or config finding matches);
   - `cwe: "CWE-502"` only for FE-04 findings on CVE-2025-55182; otherwise leave `cwe` null;
   - never write a secret value into any field; cite file:line and the scanner rule id.
8. **Record coverage gaps for Limits** in the same final message. List tools and runtime checks with no output and why (no browser, no build output, no profiler), plus the framework versions. Report a clean axe run as "no automatically detectable issues". Do not rank, verify or fix.

## Rules

### FE-01 — Every Server Function and route handler authenticates, authorises and validates on its own
- **Rule:** For every exported Server Function (`'use server'`), route handler (`route.ts`, API routes) and framework action or loader, confirm inside the function: an auth or session call before any data access, schema validation of the arguments, an ownership check on every ID argument (IDOR), and a return value cut to the fields the UI needs. Report each function whose only gate is middleware, `proxy.ts` or a page-level check, naming the missing checks. Never invent the authorisation policy.
- **Detect:** Entry points: `rg -n "['\"]use server['\"]" -g '*.{ts,tsx,js,jsx}'` and `rg -l -g '**/route.{ts,js}' 'export (async )?function (GET|POST|PUT|PATCH|DELETE)'`. Walk the four checks in order for each exported async function, then check whether auth exists only in `middleware.*` or `proxy.*` (`middleware` was renamed `proxy` in Next v16.0.0). Exported Server Actions are reachable by direct POST even when no UI imports them; a page-level check does not cover actions defined in that page; a matcher change or a moved Server Function silently removes proxy coverage. CVE-2025-29927 (CVSS 9.1) bypassed middleware-only authorisation on self-hosted `next start` and `output: 'standalone'`: confirm `next` is at or above 12.3.5, 13.5.9, 14.2.25 or 15.2.3 in its line.
- **Not when:** Machine callers (webhooks, cron jobs, wallet-signed messages) need their own signature or shared-secret verification; session auth breaks them. Next's mitigations (encrypted action IDs, dead-code elimination of unused actions, Origin checks) reduce exposure but do not replace per-function checks. React Router/Remix actions and loaders follow the same principle, but their framework docs were not verified.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** ['use server' security considerations](https://react.dev/reference/rsc/use-server) (React, 2025); [How to think about data security in Next.js](https://nextjs.org/docs/app/guides/data-security) (Vercel, 2026); [proxy.js file convention](https://nextjs.org/docs/app/api-reference/file-conventions/proxy) (Vercel, 2026, v16.3.6); [CVE-2025-29927](https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=CVE-2025-29927) (NIST NVD, 2025); [Postmortem on Next.js middleware bypass](https://vercel.com/blog/postmortem-on-next-js-middleware-bypass) (Vercel, 2025) · dossier: frontend-react-hygiene G110-F15

### FE-02 — Guard every server-only module with `import 'server-only'`
- **Rule:** Add `import 'server-only'` as the first import of a module that reads non-public env vars, holds DB or SDK clients or contains privileged logic, when no client module imports it. Keep the change only if the production build passes. A build error means a client imports the module: revert, and report it under FE-03 (splitting the module is a refactor).
- **Detect:** `rg --pcre2 -l 'process\.env\.(?!NEXT_PUBLIC_|NODE_ENV)\w+' app src lib | xargs rg --files-without-match "['\"]server-only['\"]"`. In Next.js, unprefixed env vars read in client code are replaced with an empty string, so the misuse fails silently; `server-only` turns an accidental client import into a build-time error.
- **Not when:** Pure client SPAs with no server code. The rule applies to the Next.js App Router and other RSC frameworks (React Router RSC, Waku); Vite SSR code shared with the client is covered only by analogy, so report there instead of editing. The taint APIs (`experimental_taintObjectReference`, `experimental_taintUniqueValue`) are an extra layer, not a substitute.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [Server and Client Components: preventing environment poisoning](https://nextjs.org/docs/app/getting-started/server-and-client-components) (Vercel, 2026, v16.3.6); [How to think about data security in Next.js](https://nextjs.org/docs/app/guides/data-security) (Vercel, 2026) · dossier: frontend-react-hygiene G110-F14

### FE-03 — Only a server-only data access layer touches secrets and the database; clients receive minimal DTOs
- **Rule:** Report modules outside a server-only data access layer (DAL) that import database packages or read `process.env`, `'use client'` components whose props are typed as raw DB or ORM records (`user: User`), and Server Functions that return whole records. Moving access into a DAL that authorises and returns minimal DTOs is a module restructuring for the owner.
- **Detect:** `rg -l "^['\"]use client['\"]" app src | xargs rg -n 'from [\x27\x22](@/)?(lib|server|db|data)/'` lists client files importing server-side modules. By hand, apply Next's audit checklist to `'use client'` files: "Are the Component props expecting private data? Are the type signatures overly broad?" Passing a whole DB row to a client component exposes every field.
- **Not when:** Props typed as a narrow DTO; DB access in server-only files already behind the DAL. Taint APIs do not replace filtering in the DAL.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [How to think about data security in Next.js](https://nextjs.org/docs/app/guides/data-security) (Vercel, 2026, docs v16.3.5) · dossier: frontend-react-hygiene G110-F14, G110-F15

### FE-04 — Check RSC and Next.js versions against the Dec 2025 to Jan 2026 advisories
- **Rule:** In any app using React Server Components or Server Functions, compare the installed `next` and `react-server-dom-*` versions with the React advisories. Upgrade to a patched version within the same release line and gate it with the E2E suite, because a framework bump can change behaviour. For `react-server-dom-*`, the React advisory (updated 26 Jan 2026) calls 19.0.4, 19.1.5 and 19.2.4 "safe". Report any fix that needs a major-line change.
- **Detect:** `pnpm ls next react react-dom --depth 0`; `pnpm why react-server-dom-webpack react-server-dom-turbopack react-server-dom-parcel`. Next bundles its own copy, so compare `next` with the advisory tables: the patched lines as of the React advisory updated 2026-01-26 (tables read 2026-09-23) were 14.2.35 (for 13.3.x to 14.x), 15.0.8, 15.1.12, 15.2.9, 15.3.9, 15.4.11, 15.5.10, 16.0.11, 16.1.5; re-read the live React and Vercel advisory tables before relying on them, because a stale table can call a vulnerable version patched. Also `pnpm audit --prod --audit-level high`, which sends the dependency list to the registry: the orchestrator runs it only when `.harden/config.json` has `"network": "allowed"` (skill-design T31-F15), otherwise it is a Limits entry. CVE-2025-55182 (pre-auth RCE via unsafe deserialisation, CVSS 10.0, CWE-502, CISA KEV 2025-12-05) was exploitable in a default create-next-app production build. Wiz found vulnerable versions in 39% of cloud environments (Dec 2025). Follow-ups: CVE-2025-55184 and CVE-2025-67779 (DoS), CVE-2025-55183 (source exposure), CVE-2026-23864 (DoS, Jan 2026).
- **Not when:** Pure client SPAs are not affected. Pages-Router-only Next apps may not use the vulnerable paths; check the vendor advisory instead of assuming. Patched versions for CVE-2026-23864 per Next minor line were not collected; read the live React and Vercel tables.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** A
- **Source:** [Critical security vulnerability in React Server Components](https://react.dev/blog/2025/12/03/critical-security-vulnerability-in-react-server-components) (React, 2025); [Denial of service and source code exposure in RSC](https://react.dev/blog/2025/12/11/denial-of-service-and-source-code-exposure-in-react-server-components) (React, 2025, updated 2026); [CVE-2025-55182](https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=CVE-2025-55182) (NIST NVD, 2025); [React2Shell](https://www.wiz.io/blog/critical-vulnerability-in-react-cve-2025-55182) (Wiz, 2025); [pnpm audit](https://pnpm.io/cli/audit) (pnpm, 2026) · dossier: frontend-react-hygiene G110-F16; skill-design T31-F15

### FE-05 — No secret behind a client-exposed prefix, in a built bundle, or hard-coded in server source
- **Rule:** Report every secret named with a client-exposed prefix (`NEXT_PUBLIC_`, `VITE_`, `REACT_APP_` or a custom Vite `envPrefix`), every secret found in built client assets, and every secret hard-coded in Server Function source. A secret that shipped in a bundle is rotated by a human and then served through a server route or Server Function; moving the variable does not undo the leak.
- **Detect:** Names: `rg -n -e '(NEXT_PUBLIC|VITE|REACT_APP)_[A-Z0-9_]*(SECRET|PRIVATE|PASSWORD|PASS|TOKEN|KEY|MNEMONIC|SEED)' -g '!node_modules' .`. Config: `rg -n 'envPrefix|define:' vite.config.*`. Build output: gitleaks `dir` on `.next/static` or `dist`. Server source: `rg -l "['\"]use server['\"]" | xargs rg -n '(sk_live|-----BEGIN|password\s*[:=]\s*[\x27\x22])'`. dApps: `rg -n -g '!node_modules' '0x[a-fA-F0-9]{64}'`, then confirm by hand that each hit is a key. Next inlines `NEXT_PUBLIC_` values at build time ("frozen"), but not dynamic lookups such as `process.env[varName]`. Vite bundles `VITE_*` and throws on `envPrefix: ''`. React says CVE-2025-55183 can expose secrets hard-coded in source, not runtime `process.env` values.
- **Not when:** Keys that are public by design: the Supabase anon key (safe only with RLS on), Stripe publishable keys, domain-restricted RPC or analytics keys, WalletConnect project IDs. Flag them for a scope and restriction review, not as leaks. Escape's scan (5,600+ AI-built apps, Oct 2025) reported 400+ exposed secrets without saying where they were found; its Lovable bundle finding was anonymous Supabase JWTs, exploitable only with RLS missing. The same report says Supabase service keys were "often trivially retrievable from frontend bundles"; a `service_role` key in a bundle is a leak, not a public-by-design key.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [How to use environment variables in Next.js](https://nextjs.org/docs/app/guides/environment-variables) (Vercel, 2026); [Env variables and modes](https://vite.dev/guide/env-and-mode) (Vite, v8.3.0); [Shared options: envPrefix](https://vite.dev/config/shared-options) (Vite, 2026); [Denial of service and source code exposure in RSC](https://react.dev/blog/2025/12/11/denial-of-service-and-source-code-exposure-in-react-server-components) (React, 2025); [Vibe-coding methodology](https://escape.tech/blog/methodology-how-we-discovered-vulnerabilities-apps-built-with-vibe-coding/) (Escape, 2025); [gitleaks](https://github.com/gitleaks/gitleaks) (gitleaks, v8.30.1, 2026) · dossier: frontend-react-hygiene G110-F13, G110-F16

### FE-06 — Run eslint-plugin-react-hooks v7 `recommended` in report mode; never `--fix`
- **Rule:** Lint every React codebase with eslint-plugin-react-hooks 7.x `recommended` (flat: `reactHooks.configs.flat.recommended`), with `rules-of-hooks` as error and the compiler rules overridden to `warn` for the first run. Do not enable `recommended-latest`. Never run `eslint --fix` with these rules; triage each diagnostic by hand under the FE rule that owns it. Recommend adoption with compiler rules at warn and a burn-down, not the preset as-is in CI.
- **Detect:** `pnpm ls eslint-plugin-react-hooks`: versions below 6.1 lack the compiler rules. `recommended` holds `rules-of-hooks` (error), `exhaustive-deps` (warn) and 14 compiler rules at their built-in severity: config, error-boundaries, gating, globals, immutability, incompatible-library, preserve-manual-memoization, purity, refs, set-state-in-effect, set-state-in-render, static-components, unsupported-syntax, use-memo. Some, such as set-state-in-effect, map to `error`. Existing suppressions: `rg -n "eslint-disable.*react-hooks/" -g '*.{ts,tsx,js,jsx}'`. The compiler diagnostics surface even when the app does not use React Compiler.
- **Not when:** The compiler rules are young and their precision and recall are unmeasured. On the react/react tracker (2026-09-23), 23 issues mention set-state-in-effect, and 180 carry both the Compiler and Bug labels (91 open). A project that already configures the plugin wins: use its config.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [eslint-plugin-react-hooks](https://react.dev/reference/eslint-plugin-react-hooks) (React, 2025-2026); [CHANGELOG](https://github.com/facebook/react/blob/main/packages/eslint-plugin-react-hooks/CHANGELOG.md) (Meta/React, 2026); [plugin index.ts](https://github.com/react/react/blob/main/packages/eslint-plugin-react-hooks/src/index.ts) (React, 2026); [CompilerError.ts](https://github.com/react/react/blob/main/compiler/packages/babel-plugin-react-compiler/src/CompilerError.ts) (React, 2026); [npm registry](https://registry.npmjs.org/eslint-plugin-react-hooks) (npm, 7.1.1 of 2026-04-17); [Rules of React](https://react.dev/reference/rules) (React, 2025) · dossier: frontend-react-hygiene G110-F01

### FE-07 — Resolve exhaustive-deps warnings by restructuring, never by blind dependency-adding or suppression
- **Rule:** Fix each `react-hooks/exhaustive-deps` warning with the restructuring that fits: move objects and functions used only by the effect inside it; depend on primitives, not objects; hoist constants out of the component; read non-reactive values through `useEffectEvent` (React 19.2+); or stabilise values with `useCallback`/`useMemo`. Apply a fix only where a test covers the component and exercises the effect; otherwise report it. Treat every `eslint-disable … react-hooks/exhaustive-deps` as a likely stale-closure bug.
- **Detect:** `react-hooks/exhaustive-deps` at error for the run. `rg -n "eslint-disable(-next-line|-line)?\s+react-hooks/exhaustive-deps" -g '*.{ts,tsx,js,jsx}'`. `rg -n enableDangerousAutofixThisMayCauseInfiniteLoops`: the legacy autofix is off by default and its source calls it "Dangerous". By hand: an object, array or function literal from the component body in a dependency array re-runs the effect on every render. Configure `additionalHooks` or `additionalEffectHooks` so custom effect hooks are checked. Cloudflare's 12 Sept 2025 dashboard and API outage (17:57 to 19:12 UTC) started with such an object in a `useEffect` dependency array, compounded by a concurrent Tenant Service deploy and too little capacity.
- **Not when:** react.dev sanctions a ref guard for an effect that must truly run once, such as an analytics call. `useEffectEvent` needs React 19.2+ and must not be called in arbitrary closures (enforced since plugin 6.1.0). The rule's demand for the whole `props` object is disputed (#16265, open since 2019).
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** high · **Grade:** A
- **Source:** [Removing Effect dependencies](https://react.dev/learn/removing-effect-dependencies) (React, 2025); [exhaustive-deps lint](https://react.dev/reference/eslint-plugin-react-hooks/lints/exhaustive-deps) (React, 2025); [ExhaustiveDeps.ts](https://github.com/react/react/blob/main/packages/eslint-plugin-react-hooks/src/rules/ExhaustiveDeps.ts) (React, 2026); [Cloudflare Sept 12 outage deep dive](https://blog.cloudflare.com/deep-dive-into-cloudflares-sept-12-dashboard-and-api-outage/) (Cloudflare, 2025) · dossier: frontend-react-hygiene G110-F02

### FE-08 — Every resource-acquiring effect returns a cleanup; async fetches drop stale responses
- **Rule:** Give every effect that acquires a resource a cleanup that releases it: `removeEventListener`, unsubscribe or close for subscriptions and sockets, `clearInterval`/`clearTimeout`, `cancelAnimationFrame`, disconnect. Guard async fetches with an `ignore` flag or an `AbortController` so stale responses are dropped. Svelte 5 `$effect` blocks that acquire resources return a teardown with the same semantics. The test: a user cannot tell one setup from setup, cleanup, setup.
- **Detect:** ast-grep over `*.tsx`/`*.jsx`: `useEffect(() => { $$$ }, $DEPS)` bodies containing `addEventListener`, `setInterval`, `setTimeout`, `requestAnimationFrame`, `.subscribe(`, `new WebSocket`, `new EventSource` or `fetch(` with no `return`. Quick grep: `rg -n -g '*.{tsx,jsx}' -A12 'useEffect\(' | rg 'addEventListener|setInterval|requestAnimationFrame|subscribe\(|new WebSocket|watchContractEvent|\.on\('` (the last two catch viem/wagmi and ethers listeners). At runtime, keep `<StrictMode>` on in development, navigate away and back, and watch for duplicate listeners or requests; MemLab finds leaks. LeakPair's four fix patterns (subscriptions, event listeners, timers, animation frames) fixed 102 of 124 confirmed React memory-leak bugs (82%; ASE 2023).
- **Not when:** An `ignore` flag or an abort protects state only; the server still processes the request. Aborting rejects `fetch` with an `AbortError`, which existing catch blocks may show to the user unless they filter it. Replacing hand-written effect fetching with a data library is an architecture change: report it. LeakPair's numbers describe fixed, confirmed bugs, not how often leaks occur.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** B
- **Source:** [LeakPair](https://arxiv.org/abs/2308.08144) (Shahoor, Khamit, Yi, Kim, ASE 2023); [Synchronizing with Effects](https://react.dev/learn/synchronizing-with-effects) (React, 2025); [You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect) (React, 2025); [$effect](https://svelte.dev/docs/svelte/$effect) (Svelte, 2026) · dossier: frontend-react-hygiene G110-F03, G110-F23

### FE-09 — Keep Strict Mode on; fix cleanup instead of ref-guarding resource effects
- **Rule:** Report `reactStrictMode: false` in `next.config.*` and a `<StrictMode>` removed from a Vite or React Router entry. Replace a `useRef` guard whose purpose is to stop a resource-acquiring effect (connection, subscription, socket, listener) from running twice with the missing cleanup (FE-08). Leave ref guards around fire-and-forget run-once actions such as an analytics call: react.dev documents that pattern.
- **Detect:** `rg -n "reactStrictMode:\s*false" next.config.*`; `rg -n "StrictMode" src/main.* src/index.*`; ref guards: `rg -n -g '*.{tsx,jsx}' -A8 'useRef\((false|true|null)\)' | rg 'current\)\s*return|if \(!?\w+Ref\.current\)'`, then read whether the guarded effect acquires a resource and lacks cleanup. Strict Mode re-renders, re-runs effects and re-runs ref callbacks an extra time, in development only. The Next App Router has it on by default since 13.5.1; the Pages Router needs the flag.
- **Not when:** Third-party SDKs that cannot be initialised twice (older wallet, map or analytics SDKs): a documented module-level singleton, or initialisation outside React, is legitimate. Double invocation applies only inside the `<StrictMode>` subtree.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [StrictMode](https://react.dev/reference/react/StrictMode) (React, 2025); [Synchronizing with Effects](https://react.dev/learn/synchronizing-with-effects) (React, 2025); [exhaustive-deps lint](https://react.dev/reference/eslint-plugin-react-hooks/lints/exhaustive-deps) (React, 2025); [reactStrictMode](https://nextjs.org/docs/app/api-reference/config/next-config-js/reactStrictMode) (Vercel, v16.3.6) · dossier: frontend-react-hygiene G110-F04

### FE-10 — Flag effects that only derive state or relay events; rewrite only covered pure derivations
- **Rule:** Classify every effect that sets state: pure derivation (compute during render; `useMemo` if expensive), event logic (move into the handler), external synchronisation (keep), hydration flag or ref measurement (keep). Rewrite only derivations and event logic that have no other side effect and are covered by tests; report the rest. Never apply `react-hooks/set-state-in-effect` mechanically. In Svelte 5 the equivalent is `$derived` in place of an assignment inside `$effect`.
- **Detect:** `react-hooks/set-state-in-effect`; optionally eslint-plugin-react-you-might-not-need-an-effect (`no-derived-state`, `no-chain-state-updates`, `no-event-handler`, `no-adjust-state-on-prop-change` and others). Grep: `rg -n -g '*.{tsx,jsx}' -A4 'useEffect\(\(\) => \{' | rg '^\S+-\s+set[A-Z]\w*\('`. Svelte: `rg -n -g '*.svelte' -A3 '\$effect\(' | rg '^\S+-\s+\w+\s*=\s*'`.
- **Not when:** React documents the hydration two-pass pattern (`useState(false)` plus `useEffect(() => setIsClient(true), [])`) for intentional server/client differences, and the rule flags it; ref measurements in `useLayoutEffect` are a documented exception. Known false positives (#34905, #34045) and false negatives (#37177, #35029, #35390) exist. A rewrite changes render counts, removes intermediate states and reorders effects; a `key` reset remounts the subtree. Banning `useEffect` outright (Factory, 2026) is a team policy, not a hardening rule. Moving Svelte `$effect` to `$derived` changes timing.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** high · **Grade:** A

### FE-11 — Flag render-purity and immutability violations; fix only small local cases
- **Rule:** Report mutation of props, state, hook arguments or return values, and of values after they are passed to JSX; side effects during render (fetching, subscribing, writing module globals); `ref.current` read or written during render; unconditional setState during render. ### FE-12 — In SSR/SSG apps, flag render-path code whose output differs between server and client
- **Rule:** Report render-path uses of `typeof window`, `window.matchMedia`, `localStorage`, `Date.now()`, `new Date()`, `Math.random()`, locale-dependent formatting and invalid HTML nesting. Treat mismatches as bugs: at best a slowdown, at worst event handlers attached to the wrong elements; React 19 regenerates the tree on the client.

- **Not when:** Pure client-rendered Vite SPAs. Moving the read into an effect or `useSyncExternalStore` adds a render and can flash; that is the documented two-pass pattern, which FE-10 keeps. `suppressHydrationWarning` works one level deep only.

### FE-13 — Stable, data-derived list keys; treat any key change as a behaviour change
- **Rule:** Report index keys on lists that can be inserted into, removed from, reordered, filtered, paginated or streamed, and keys generated during render (`Math.random()`, `crypto.randomUUID()`, `nanoid()`). Replace one with a stable id from the data (`item.id`) only after approval, as its own behaviour change: a new key remounts the component, resetting its state, focus and input and re-running its effects. In Vue, give `v-for` a stable `:key` when items hold component or DOM state, and never put `v-if` on the same element as `v-for`.
- **Detect:** eslint-plugin-react `react/no-array-index-key` and `react/jsx-key`. `rg -n -g '*.{tsx,jsx}' -e 'key=\{\s*(i|idx|index)\s*\}' -e 'key=\{\s*(Math\.random|crypto\.randomUUID|nanoid|uuid\w*)\('`. For each hit, check whether the source array is ever sorted, filtered, spliced, paginated or streamed (live trade or price feeds). Vue: eslint-plugin-vue `flat/essential` (`vue/no-use-v-if-with-v-for`) and `rg -n --pcre2 -g '*.vue' 'v-for="[^"]*"(?![^>]*:key)'`.
- **Not when:** Index keys on static, id-less lists that are never reordered or filtered (Pokorny, 2015). Vue allows omitting keys for simple content or deliberately for performance. Keys used on purpose to reset state (`<Chat key={contact.id}/>`) must stay. If the data has no stable id, adding one at fetch time is a data-layer change: report it.

- **Source:** [Rendering lists](https://react.dev/learn/rendering-lists) (React, 2025); [Preserving and resetting state](https://react.dev/learn/preserving-and-resetting-state) (React, 2025); [Index as a key is an anti-pattern](https://robinpokorny.com/blog/index-as-a-key-is-an-anti-pattern/) (Pokorny, 2015); [react/no-array-index-key](https://github.com/jsx-eslint/eslint-plugin-react/blob/master/docs/rules/no-array-index-key.md) (jsx-eslint, 2025); [List rendering](https://vuejs.org/guide/essentials/list.html) (Vue, 2026); [vue/no-use-v-if-with-v-for](https://eslint.vuejs.org/rules/no-use-v-if-with-v-for.html) (eslint-plugin-vue, 2026) · dossier: frontend-react-hygiene G110-F06, G110-F23

### FE-14 — Flag components defined inside components; hoist only after checking reset-dependent behaviour
- **Rule:** Report components, including inline factories, that are defined in another component's body and rendered as `<X/>`. ### FE-17 — Report superfluous re-render anti-patterns with profiler evidence; never auto-apply the fixes
- **Rule:** Report the five anti-patterns only with profiler evidence of user-visible cost: controlled inputs that re-render large parents; state that does not affect the UI; prop-less children re-rendered by their parent; children receiving new object or array props on every render; children receiving new function props on every render. - **Not when:** Most extra renders of cheap components have no user-visible impact, and the compiler may remove some. The study used relatively small open-source apps, and its prevalence figures come from a static analysis the authors call "potentially unsound".

### FE-23 — Report bundle-hygiene issues; propose a size budget at the current size
- **Rule:** Report, never refactor: `'use client'` placed high in the tree (layouts, whole pages), barrel re-exports that pull in heavy libraries, and unused exports or dependencies (knip findings belong to the dead-code lens; never run `knip --fix` unattended). ## False-positive exclusions

- Keys that are public by design: Supabase anon key with RLS on, Stripe publishable keys, domain-restricted RPC or analytics keys, WalletConnect project IDs. Route them to a scope and restriction review, not a leak report (FE-05). A Supabase service key is never one of them.
- Route handlers for machine callers (webhooks, cron, wallet-signed messages) verified by signature or shared secret instead of a session (FE-01).
- Ref guards around fire-and-forget run-once actions such as analytics (FE-07, FE-09).
- Third-party SDKs that cannot be initialised twice, behind a documented module-level singleton (FE-09).
- setState in effects for hydration flags, ref measurements in `useLayoutEffect`, and genuine external synchronisation (FE-10).
- Known lint false positives: #34905 and #34045 (set-state-in-effect), #34954 and #34955 (refs, immutability). Check the tracker before reporting a matching pattern (FE-06, FE-10, FE-11).
- Interior-mutability libraries (MobX, TanStack Table, react-hook-form `watch`) flagged by purity or immutability rules (FE-11).
- Hydration-sensitive reads inside effects or handlers, anywhere in pure client-rendered SPAs, and `suppressHydrationWarning` on a single text or attribute node (FE-12).
- Index keys on static, id-less lists that are never reordered or filtered; Vue lists of simple content; keys used deliberately to reset state (FE-13).
- Render helpers called as functions rather than rendered as components (FE-14).
- Extra renders of cheap components with no user-visible impact (FE-17).
- A "div with onClick" that wraps a focusable child (FE-19), and complex widgets that need ARIA (FE-20).
- None of these closes a finding on its own: a zero-diagnostic lint run, a clean axe run, or a passing build.

## Evidence limits

- Most rules rest on official React, Next.js, Vite, Vue and Svelte docs and on plugin source. The empirical sources are narrow: the ICSE 2026 re-render study (relatively small open-source apps, analysis the authors call "potentially unsound"), LeakPair (fixed, confirmed leaks; no prevalence) and one multi-cause Cloudflare incident.
- No peer-reviewed study measures how often hooks misuse (missing dependencies, stale closures, missing cleanup beyond leaks) occurs in production React apps.
- The v7 compiler lint rules have no independent precision or recall figures; tracker counts are not rates.
- Rust React Compiler ports claim parity by self-report only, and the two sources date the Oxc release differently (4 Aug versus 18 Aug 2026).
- Versions were checked on 2026-09-23: react 19.3.0, next 16.3.6, eslint-plugin-react-hooks 7.1.1, babel-plugin-react-compiler 1.0.0, axe-core 4.13.0, Vite docs 8.3.0. - React Router/Remix authorisation guidance was not retrieved. Vue and Svelte are covered briefly, with no bug studies; Svelte keyed each blocks were not checked.
- Accessibility figures are detection counts: WebAIM (WAVE, one million home pages, Feb 2026 data), Deque (vendor), Fischer et al. (Swedish public-sector pages), GDS (one test page, 2017). None measures usability; keyboard and screen-reader testing stays manual.
