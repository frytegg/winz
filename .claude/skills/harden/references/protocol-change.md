# Change Application Protocol

> Phase 7 of a /harden run: apply approved changes one kind per commit, so that every commit is green, bisectable and revertible, and behaviour changes only where an approved finding says so.
> Read at: Phase 7 (apply), before the first edit, again at Phase 8 for step 13, and again after any compaction or context reset.

## Contents
- Steps: preconditions and queue (1-4); per item (5-11); per batch (12); final verification (13)
- Rules: commits and gates (PC-01, PC-02); engines, census and moves (PC-03 to PC-05); tests and anti-gaming (PC-06 to PC-08); autofix trust (PC-09 to PC-11); scope and retries (PC-12, PC-13); behaviour changes and parity (PC-14, PC-15); guards and risk lanes (PC-16, PC-17); deletions, history and secrets (PC-18 to PC-21); mutation and final check (PC-22, PC-23); valid inputs a fix used to accept and multi-consequence findings (PC-24, PC-25); end-to-end verification with bisect and revert (PC-26)
- Evidence limits

Tiers: T0 auto-apply after a green baseline (still gated, one rule id per commit); T1 apply only after its category is accepted in `.harden/approvals.md`, by the `auto_apply` switches of `.harden/profile.json` in autonomous mode (the default, rows marked `auto (profile)`) or by the user's live answer with `--interactive` (step 3; user-policy-autonomy U01-F01, U01-F04); T2 report only, except what the Owner-judgement lane of an autonomous run applies under `auto_apply.owner_judgement` (prioritization.md, Autonomous mode; user-policy-autonomy U01-F06). Process rules that constrain how the skill works carry `T2 · report-only`: a violation is reverted and reported, never "fixed" in the target code.

Autonomous mode never waits for the user (U01-F01). Wherever a step or rule below says to ask, show or put something back to the user, an autonomous run takes the answer from `.harden/profile.json`; when the profile gives none, it takes the conservative default that step names (nothing applied, nothing deleted, the item reported), logs `default: <question> -> <choice> (<rule id>)` in `.harden/progress.md` and continues. Only `--interactive` asks.

## Steps

Use `python` on Windows and `python3` elsewhere. Run state lives in `.harden/`, not in the transcript.

1. Reload state: re-read `.harden/progress.md`, `.harden/approvals.md` and this file; in autonomous mode also `.harden/profile.json`.
2. Check preconditions; if any fails, stop editing and continue in report-only mode:
   - `.harden/active` exists with `"mode"` set to `auto` (autonomous, the default) or `interactive` (`--interactive`; `apply` is its older name), and `.harden/gates/baseline.json` shows every gate green;
   - in autonomous mode, `python "${CLAUDE_SKILL_DIR}/scripts/validate_profile.py" .harden/profile.json` exits 0 and the profile's `live_side_effects` is `none`: without a valid profile an autonomous run executes no project code and applies nothing, and the report says so (U01-F04);
   - `git status --porcelain` prints nothing and `git rev-parse --abbrev-ref HEAD` prints the branch recorded in `.harden/active` (never main or master);
   - `python "${CLAUDE_SKILL_DIR}/scripts/validate_findings.py" .harden/findings.json` exits 0. Fix `.harden/findings.json` or `.harden/approvals.md` and re-run it until it does. Only an error that no edit of those two files can clear makes the run report-only.

   Then, before the first item, confirm that the gates in `.harden/config.json` include the project's documented or CI lint command when `.harden/inventory.json` lists one. If not: with `--interactive`, ask the user to add it and re-record the baseline, and a declined lint gate is a Limits line, not a stop; in autonomous mode, add it without asking and re-record the baseline, because a gate can only refuse commits, so adding it is the conservative default (a lint command red at base runs as the PF-11 ratchet), and log the decision in `.harden/progress.md` (PC-02; U01-F01).
3. Build the queue from `.harden/findings.json`: T0 items with status `verified`, plus T1 items with status `approved` whose category is accepted in `.harden/approvals.md`. Who accepts a category depends on the mode in `.harden/active`:
   - Autonomous (`auto`): the profile accepts it and nobody is asked (U01-F01, U01-F04). Before the first item, write the rows with `python "${CLAUDE_SKILL_DIR}/scripts/findings.py" approvals` from `.harden/decisions.json` and the `auto_apply` switches of `.harden/profile.json`, one row per item under its finding id: `| <id> | accepted | 1 | auto (profile): auto_apply.<switch>=true | <UTC time> |` (`auto (profile): T0` for a T0 item, which stays `verified`), or decision `report-only` with `auto (profile): auto_apply.<switch>=false, not applied`; it refuses a live-effect item and never widens an approval (pilot-auto-calibration A01-F60). The switch is `structural` for a structural category, `behavioural` for a behavioural one and `dependencies` for a dependency, manifest or lockfile item, plus `dependency_versions` for one that adds or changes a resolved version (prioritization, Lockfile version check; DP-08, DP-09, DP-10, SE-21; user-policy-autonomy U01-F08). Which items are on a money, order, key, signing or transaction path follows the Money paths paragraph of prioritization.md's Autonomous mode (pilot-auto-calibration A01-F06 to A01-F08): the profile's `money_paths_globs` through `python "${CLAUDE_SKILL_DIR}/scripts/validate_profile.py" .harden/profile.json --repo . --base <base_sha> --classify <files>` when it sets them, the lens and verifier judgement when it does not or the script prints `judgement`, and in every case the floor of code that signs, sends orders or transactions, or handles keys. An item on a money, order, key, signing or transaction path also needs `auto_apply.money_paths=true` and gets its own row under its finding id, unless its change is proven AST-identical to its parent (comments and whitespace only), which cannot change behaviour and needs only its own switch (pilot-auto-calibration A01-F01). Set the accepted items to `approved`. While `auto_apply.owner_judgement` is not true, T2 items stay out, each with a `report-only` row reading `auto (profile): T2`. While it is true, the Owner-judgement lane of prioritization.md's Autonomous mode decides each T2 item, a whole-repository format run (PC-11) and an additive public API change (prioritization row 18, TS-42) (user-policy-autonomy U01-F06, U01-F11). It writes one of two rows. An item it accepts gets `| <id> | accepted | 1 | auto (profile): owner judgement, T2 by <rule id>, auto_apply.owner_judgement=true, auto_apply.<switch>=true | <UTC time> |` (`T1 by <rule id>` for the format run and the API change; `auto_apply.money_paths=true` added on a money path), and becomes `approved` with the class of its planned change and its `review` object (kinds holding `owner-judgement`, the option chosen). An item it keeps out gets `| <id> | report-only | 1 | auto (profile): T2 by <rule id>, not applied: owner-judgement lane 1(<letter>) | <UTC time> |`. These T0, T1 or T2 items also stay out whatever the switches say, each with its own row (decision `report-only`, quote `auto (profile): <reason>`) and status `reported` (U01-F03, U01-F12): an item on a live-effect path (prioritization.md, Money paths); a behavioural item that fails PC-14's offline-verification conditions; a dead-code item whose deletion needs a DC-15 test deletion, and any removal or modification of an existing test line (PC-06's checked additions are not one); a package no manifest lists yet (PC-12); items no switch covers, which take the conservative default: a new suppression line (PC-08), PC-21's placeholder deletion, a newly rejected input class PC-24 cannot narrow to empty, and, while `auto_apply.owner_judgement` is not true, a whole-repository format run (PC-11) and an additive public API change (prioritization row 18, TS-42). What shows only while an item is applied (PC-14 condition (b), PC-24's class) takes it out then: restore its files (step 9's restore command), commit nothing, and write its row.
   - Interactive (`interactive`, `--interactive`): the rows hold the user's live answers (SKILL.md Phase 6).

   A T2 item enters the queue only through the Owner-judgement lane, and only in the form the lane chose (its conservative option, U01-F11). The staged path proposed for one (a warning that names the change to come, then enforcement) never enters it: it stays the item's `Proposed first step:` line (PC-14; eval-v2-calibration E02-F03). Order: category batches in the Phase 4 order of their highest-ranked item (prioritization step 9, the RP-06 key: blocking first, then severity, confidence rung, location and dimension), and items within a batch in the same order, so that an Apply window the run budget cuts has already landed the most important fixes (PZ-01; pilot-auto-calibration A01-F34). The T0 autofix commits of one rule id stay together (PC-09, PC-10), and at equal rank T0 comes before T1, T1 before owner-judgement items, and structural items before behavioural ones (PC-14). Three placements override that order: a preparatory refactor goes, as a structural item, right before the behavioural fix that needs it (PC-01); each PC-24 or PF-19 characterization `test:` commit goes right before the fix it guards, and each pure strengthening of an existing test (PC-06) before the first behavioural commit; a whole-repository format run (PC-11) goes last, so that reverting it never conflicts with a later commit. A batch is a run of consecutive queue items of one `.harden/approvals.md` category; the PF-18 net check, the PF-19 characterization tests and step 12's SAST delta run per batch. Before each item, run `python "${CLAUDE_SKILL_DIR}/scripts/budget.py" check --phase apply`. Exit 0: go on. Exit 1: the Apply window is spent (the final check keeps its reserve): start no new item, go to step 13 and set the remaining items to `deferred`. Exit 2 means no plan exists yet: run `budget.py plan` first and check again; it is never a stop. When the queue is empty, run `python "${CLAUDE_SKILL_DIR}/scripts/budget.py" check --phase cycle`. Exit 0 (candidates left, a verdict in the last cycle, the verify spend cap not reached, time before both reserves) opens the next verify/apply cycle for the candidates verification left `deferred` unverified: detection steps 11 to 13 with `budget.py verify-plan --cycle <n>`, then prioritization steps 7 to 9 and this step for the findings that cycle verified or promoted. Phase 5 only validates `.harden/findings.json`; SKILL.md Phase 8 brings the report up to date with every cycle's findings. A cycle never re-applies or re-decides an item already `applied`, `partial`, `blocked`, `reverted` or `reported`, except a finding its reproduction raised (detection step 12). Exit 1 goes to step 13 (pilot-auto-calibration A01-F50). An approved item you re-tier or narrow at apply time (to T2, or to a variant such as warn-first) is never dropped silently. With `--interactive`, put it back to the user with the rule id and the reason, and record the answer in `.harden/approvals.md` before moving on. In autonomous mode, ask nothing: the tier table (prioritization PZ-24) decides the item again with the facts the run holds, such as the PF-14 consumer inventory, and the outcome is its own row under its finding id (U01-F01; PC-14). It is applied only when it is still T0 or T1, the `auto_apply` switches cover it as re-decided (`money_paths` too on a money, order, key, signing or transaction path; a T0 item needs no switch) and none of the exclusions above applies (U01-F03): row `| <id> | accepted | 1 | auto (profile): re-tiered to <tier> by <rule id>, auto_apply.<switch>=true | <UTC time> |`, with `T0` in place of the switch for a T0 item. Otherwise it is not applied: restore its files (step 9's restore command), commit nothing, set its status to `reported`, write `| <id> | report-only | 1 | auto (profile): re-tiered to <tier> by <rule id>, not applied | <UTC time> |`, and report it with the rule id and the reason; a warn-first step or safer default for it stays its `Proposed first step:` line (eval-v2-calibration E02-F03). `<tier>` is the new tier, with its class for T1 and the variant when narrowed (for example `T2` or `T1 behavioural`); the `auto (profile)` prefix keeps the row out of the reporting RP-20 ratio.
4. For each item, append its scope line to `.harden/progress.md`: `id | class | tier | files | symbols | rule id or refactoring | target metric` (PC-12). A finding that names several consequences gets one line per consequence (`<id>.1`, `<id>.2`, ...), each with its own class and tier, decided by applying PC-14's restoring-promise test to that consequence alone (PC-25). When the finding's evidence records a headline reproduction (a `repro` item: command plus observed output), the target metric of its behavioural line is that exact reproduction turning green (PC-14).
5. Non-mechanical item: check the safety net on the lines to be changed (PC-22). Run mutation only after the Phase 0 side-effect check (protocol-preflight) has confirmed an offline env policy for the test run (in autonomous mode, the profile's `live_side_effects: none`); without one, record "safety net unmeasured" and set the item to T2. If mutants survive there, first add a characterization or killing test as its own `test:` commit (steps 8-11), or set the item to T2. Record each survivor's disposition in `.harden/tools/mutation-triage.md`, never as an in-code or config skip. Before a behavioural fix to code that parses, validates, converts, stores or reads back data, the characterization tests include previously accepted valid inputs of the defect's class and, when the fix changes a persisted format, data written by the base code (PC-24). Before every behavioural fix they also pin the current outputs of each exported function or method the fix's diff edits, bin and CLI entry modules included, and of the exported functions of the same module that call an edited function that is not exported, with representative inputs that include the call with every optional argument omitted and the bare command; when the diff edits code outside every exported function (a top-level statement, a class field, an object-literal member) or a file `contract_check.py` cannot parse (JSX, Solidity), a characterization test imports that module. A characterization that reaches a function through another entry point (a registry, a CLI main) declares it on a header comment line `pins: <file> <function>`, or `pins: <file> *` for a whole module (PC-24; pilot-auto-calibration A01-F29, A01-F47). An owner-judgement behavioural item gets the same cases whatever code it touches, taken from fixtures, samples, tests and docs, never from `.env` files or another secret store (PC-21; U01-F06).
6. Rename, move, signature change or deletion: save the census (PC-04):
   `rg -n -w -F '<old>' --hidden -g '!node_modules' -g '!.git' > .harden/tools/census-<id>-before.txt`
   Without ripgrep, `git grep -n -w -F --untracked '<old>' > .harden/tools/census-<id>-before.txt` searches the same tracked and untracked, non-ignored files (the second autonomous pilot had no `rg`).
7. If the project enforces a formatter, commit formatting of touched files as its own T0 `style:` commit before the item's other changes (PC-11): format only the files the item will touch, then gate and commit that change alone (steps 9-10). This also covers drift that a formatting gate red at base reported in those files (PF-11). Formatting the rest of the repository is never part of an item: it is a separate T1 item that needs its own explicit approval (PC-11). Then apply exactly one operation through an engine or the tool's own fixer (PC-03, PC-09), and re-run the formatter on the touched files so only the new lines change. For a lint rule, run its per-rule selector until `git diff --quiet` shows no new edits, at most 3 passes.
8. Check the edit before staging:
   - re-run the census into `census-<id>-after.txt`, diff the two lists, justify or fix every surviving hit (PC-04);
   - review moved blocks: `git diff --color-moved=zebra --color-moved-ws=allow-indentation-change` (PC-05);
   - run the guard-removal and test-gaming scans (PC-16, PC-07);
   - when a lint gate is configured, run its command and fix the hits the edit introduced, never by suppression (PC-02, PC-08); a hit already present at base is a new candidate, not an edit (PC-12);
   - when Phase 2 ran a duplicate-code detector for the item's language, re-run it with the same pinned version, flags and threshold (lens-duplication) over the scope Phase 2 scanned, save the output as `.harden/tools/<detector>.<id>-a<n>.*`, compare it with the baseline output and keep the new groups that have an instance in a file the item changes (DU-16; eval-v2-calibration E02-F07): fix a new clone the edit introduced in production code before staging, turn a group formed only because a DU-04 fix brought existing copies closer into a new DU-03 candidate (PC-12) rather than an in-item merge, and record a clone group confined to test files the item adds as a nit candidate (DU-14), never a reason to restore or revert (PC-02);
   - `python "${CLAUDE_SKILL_DIR}/scripts/diff_guard.py" --base <base_sha> --quick` exits 0 (PC-06, PC-08).
9. Stage only the item's files and confirm nothing is left unstaged. Write the planned commit message (step 10) to `.harden/tools/msg-<id>-a<n>.txt`; step 10 commits that file with `git commit -F`. Run the contract check (PC-24; pilot-auto-calibration A01-F29, A01-F47). For a behavioural item: `python "${CLAUDE_SKILL_DIR}/scripts/contract_check.py" pins --staged --message-file .harden/tools/msg-<id>-a<n>.txt --out .harden/tools/contract-pins-<id>-a<n>.json`. Fix a `claim` problem in the message file and run the check again. An `unpinned` problem restores the item's files: commit the missing characterization test first as its own `test:` commit (steps 8-11; a new test file, or cases added to an existing one), then retry the item once; that retry is not one of invariant 9's gate attempts, and a unit still unpinned after it leaves the item unapplied and reported (`not applied: unpinned <file> <unit>`). Exit 2 from the script: correct the call once; a second exit 2 is a Limits line (`contract check not run: <message>`), never a restore. In autonomous mode, scan the staged change for the money-path floor (prioritization.md, Autonomous mode): `git diff --cached -U3 | grep -nEi -e '\bsign(ed|er|ers|ature|atures|ing|transaction|message|typeddata|tx)?\b' -e 'private[_ -]?key|secret|mnemonic|seed[_ -]?phrase|api[_ -]?key|keystore' -e 'withdraw|transfer|payment|payout|broadcast|send_?(raw_?)?transaction' -e '(create|place|submit|amend|cancel|new)[_ ]?orders?\b' > .harden/tools/floor-<id>-a<n>.txt` (grep exits 1 when nothing matches), and answer every hit in the finding's `notes` with `money-path: floor <kind> at <file:line>` or `money-path: not floor at <file:line>: <why>`; a hit left unanswered counts as the floor. The scan only prompts that judgement: a changed line it misses still meets the floor when its code does. Answer the same hits for the live-effect path too (prioritization.md, Money paths; U01-F12), with `live-effect: <kind> at <file:line>` or `live-effect: none at <file:line>: <why>`. A hit left unanswered counts as live-effect, and a live-effect item is restored and reported. Before the first run of any file the pass writes or extends that is not production code (a new or extended test, fixture or helper), wherever it runs (PC-14's parent worktree, a PC-24 or PF-19 characterization run, a PF-18 net check, a gate), scan it for reach beyond the machine. Scan the whole of a new file, and only the added lines of an extended one: `{ grep -nHEi -e '(https?|wss?)://' <new files>; for f in <extended files>; do git diff -U0 HEAD -- "$f" | grep -nEi '^\+.*(https?|wss?)://'; done; } | grep -viE '://(127\.0\.0\.1|localhost|\[::1\])([:/]|$)' > .harden/tools/test-reach-<id>-a<n>.txt`, then the same two sources with the patterns `process\.env|os\.environ|getenv|dotenv|\.env\b`, `private[_ -]?key|mnemonic|seed[_ -]?phrase|api[_ -]?key|secret|keystore` and `--network|hre\.network|hre\.config|config\.networks|defaultNetwork|forking|JsonRpcProvider|WebSocketProvider|getDefaultProvider|createPublicClient|createWalletClient|getSigners|testnet|mainnet|previewnet|hashio|mirrornode`, appended with `>>` (grep exits 1 when nothing matches). Answer every hit in the finding's `notes` with `test-reach: local at <file:line>: <why>`: a loopback stub, the in-process chain, Hardhat's `hardhat` network only when the Hardhat config sets `defaultNetwork` to `hardhat` or leaves it unset and `networks.hardhat.forking` is absent or disabled (read in the config file, never in `.env`), or a variable the test sets itself. A hit that cannot be answered so restores the item and reports it (PC-14 condition (c); U01-F12). A file with an unanswered hit is not run. When the profile sets `money_paths_globs`, also run `python "${CLAUDE_SKILL_DIR}/scripts/validate_profile.py" .harden/profile.json --repo . --base <base_sha> --classify --staged`. A `money-path` line for a file other than a new test file the pass wrote, or a staged line that meets the floor, makes an item decided off a money path a money-path item, which step 3 decides again before any gate runs (restore its files when it is not applied). Then run `python "${CLAUDE_SKILL_DIR}/scripts/gates.py" --label <id>-a<n> --min-count-from baseline`, whose gate set includes the project's lint command (PC-02). A formatting or lint gate that was red at base runs instead as the PF-11 ratchet: `python "${CLAUDE_SKILL_DIR}/scripts/gates.py" --config .harden/ratchet.json --label <id>-a<n>-ratchet --ratchet-from probe` (eval-v1-calibration E01-F02). For a ratchet gate a non-zero exit code is not a failure by itself: the gate passes when its violation count (its `count_regex`, such as ESLint's `(\d+) problems? \(`) is at most the count recorded for it in the probe, and fails when the count rises or cannot be read; `.harden/gates/<id>-a<n>-ratchet.json` records `ratchet: {reference, current, passed}`. The main gate run fails when the test gate's executed-test count (`count_regex`) drops below the baseline's; gates.py lowers that reference by the test cases recorded with `run_state.py allow-test-deletion --cases` (PC-02, PC-06). When the staged change adds lines to an existing test file and changes a production file (a behavioural item's demonstrating test case, PC-06, PC-14), also run `python "${CLAUDE_SKILL_DIR}/scripts/strengthen.py" replay --base <base_sha> --label <id>-a<n>-oldlines` in the Bash tool with `timeout: 600000` (or `run_in_background` when the baseline test gate took more than 8 minutes). It runs the configured test gates with every existing test file at its base version and every test file the run added set aside, then restores them. Exit 1 counts as a red gate. After exit 2, or when the call was interrupted, run `strengthen.py restore`; when the exit-2 message names the configuration (no test gate, unknown gate, untracked test files), move the demonstrating test case into a new test file instead of retrying. On red: `git restore --source=HEAD --staged --worktree -- <files>`, delete only files this step created, then retry or block (PC-13).
10. Commit (PC-01):
    - structural: `refactor(<scope>): <refactoring> NFC (<id>)`, `style(lint): apply <tool>@<version> <RULE> (<n> edits) NFC` or, for the formatting commit of step 7, `style(format): <formatter>@<version> on files of <id> NFC`, and for an approved whole-repository run `style(format): <formatter>@<version> on the whole repository NFC (<id>)`;
    - behavioural: `fix(<scope>): <summary> (<id>)`, body line `Behaviour change: <inputs affected, old -> new>` naming, where they apply, the promise a restoring fix restores (for a fail-open finding, its kind and the claim or channel, prioritization Fail-open findings) and the newly rejected valid class of the fix, or `newly rejected: none (<test files>)` naming, inside those parentheses, the characterization test files committed before the fix that pin every exported function it edits (PC-14, PC-24; pilot-auto-calibration A01-F29, A01-F47), demonstrating test in the same commit (PC-14);
    - a change to a public API, a serialized field, a CLI output, an error string or an exit code (prioritization, Owner-judgement lane step 4): when it breaks a consumer, `!` before the colon (`fix(<scope>)!: <summary> (<id>)`) and a `BREAKING CHANGE: <what breaks and what a consumer must change>` footer; when it only adds, a body line `Public API: <what is added>`. An owner-judgement item also carries `Review: <rule id>; option <direct|lossless-variant|record-only|documented-default>; alternatives: <the behaviours left to the owner>` (Conventional Commits 1.0.0; user-policy-autonomy U01-F11, U01-F13);
    - every body carries `cmd: <exact command>`; no AI attribution trailers.
11. Set the finding's status to `applied` with the commit sha and, when the change is behavioural, comes from the Owner-judgement lane, sits on a money path, changes a public contract or a contract source, or is a whole-repository format run, its `review` object (findings schema; validate_findings.py rejects its absence), and its `live-effect: none` entry in `notes` (or `blocked`, with the reason), recorded with `python "${CLAUDE_SKILL_DIR}/scripts/findings.py" mark <id> --status applied --commit <sha> --test <test id> --test-detail "<red at the parent, green at the fix>"`, which refuses a write `validate_findings.py` would reject and never writes the live-effect judgement for you (pilot-auto-calibration A01-F60); a finding with several consequence lines changes status only once each line is applied, blocked or split into its own finding (PC-25). A finding with at least one applied line whose headline reproduction, re-run on the branch head, still reproduces is not `applied`: set it to `partial`, with the reproduction's current output in its notes, and it heads the report's "Open owner items" section (PC-14, PC-25). Re-run `validate_findings.py` and update `.harden/progress.md`.
12. After each category batch, re-run the baseline SAST tools into `.harden/tools/<tool>.<batch>.sarif` and run `python "${CLAUDE_SKILL_DIR}/scripts/sarif_delta.py" .harden/tools/<tool>.baseline.sarif .harden/tools/<tool>.<batch>.sarif`. A new result reverts the batch's commits with `git revert --no-edit <sha>` (PC-16, PC-20). A duplicate-code clone group confined to test files the pass added is a nit candidate, not a result that reverts (step 8, PC-02).
13. Final verification, in every mode that committed anything, run by the orchestrator itself in this order (PC-23, PC-26, PC-22, PC-16):
    - every commit on its own: `for c in $(git rev-list --reverse <base_sha>..HEAD); do git checkout "$c" && python "${CLAUDE_SKILL_DIR}/scripts/gates.py" --label "commit-$c" --reuse-if-tree "$c" || echo "red $c"; done; git checkout <branch>`; a red commit is reverted with `git revert --no-edit <sha>` and its finding set to `reverted` (PC-23); a commit whose exact tree already passed every gate in its item run is recorded as reused, not re-run (`reused_from` in `.harden/gates/commit-<sha>.json`; pilot-auto-calibration A01-F40);
    - when `python "${CLAUDE_SKILL_DIR}/scripts/strengthen.py" list --base <base_sha>` lists a file (an existing test file that gained lines, or a test file the run added), the old-lines replay at HEAD, in the Bash tool with `timeout: 600000` (or `run_in_background` when the baseline test gate took more than 8 minutes): `python "${CLAUDE_SKILL_DIR}/scripts/strengthen.py" replay --base <base_sha> --label final-oldlines` exits 0, so every existing test, as written at base and with the test files the run added set aside, still passes (PC-06). On exit 1, run it once more with `--label final-oldlines-confirm`; green there is flaky: a Limits line, nothing reverted (PC-26). Locate a confirmed red oldest first: `for c in $(git rev-list --reverse <base_sha>..HEAD); do git checkout --quiet "$c" || break; python "${CLAUDE_SKILL_DIR}/scripts/strengthen.py" replay --base <base_sha> --label "commit-$c-oldlines"; rc=$?; python "${CLAUDE_SKILL_DIR}/scripts/strengthen.py" restore; [ "$rc" -eq 0 ] || { echo "replay exit $rc at $c"; break; }; done; git checkout --quiet <branch>`. ## Rules

### PC-01 — One kind of change per commit, structure before behaviour
- **Rule:** Give each commit one class and one kind of change: a formatter run on the next item's touched files (or, as its own approved T1 item, on the whole repository, PC-11), one autofix rule id (one rule id per commit, never a family), one named refactoring, one deletion group, one dependency, one config change, one test-only addition, or one behavioural fix. Never fold a bug found mid-refactor into the refactor; record it as a new candidate. Put structural commits before the behavioural commit that needs them, do not modify moved code in the commit that moves it, and never squash the pass into one commit.
- **Detect:** `git show --stat <sha>` touches one category; `git log --shortstat <base_sha>..HEAD` flags commits mixing lockfiles, config, tests, migrations and src; a `refactor:` or `style:` commit is misclassified when `git diff <sha>^ <sha> -- '*test*' '*spec*' | grep -E '^-[^-]'` prints anything (except the approved test-case deletions of a `refactor(dead-code):` commit, PC-06) or it changes literals, exit codes or error-path conditions; if the commit's description needs an "and", split it.
- **Not when:** A cross-module rename that only compiles as one commit stays one commit. Separation is well supported for bisect and revert but weakly for review: in the one controlled experiment (di Biase et al., PeerJ CS 2019, 28 developers) decomposed and tangled changes gave 17 vs 20 defects found (p=0.6) and only false positives fell. Squash-merge workflows collapse the commits, so keep the branch.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [LLVM Developer Policy](https://llvm.org/docs/DeveloperPolicy.html) (LLVM, current); [Submitting patches](https://www.kernel.org/doc/html/latest/process/submitting-patches.html) (Linux kernel, current); [Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html) (Google, current); [Augmented Coding: Beyond the Vibes](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes) (Kent Beck, 2025); [Decomposed vs tangled review experiment](https://peerj.com/articles/cs-193/) (di Biase et al., 2019) · dossier: behaviour-changing-fixes G102-F01; cleanup-practice-forums T30-F01; finished-project-scope G101-F10; refactoring-safety T09-F07; skill-design T31-F09; llm-refactoring T10-F12; hardening-induced-regressions G205-F10, G205-F12, G205-F21; eval-v1-calibration E01-F02

### PC-02 — A commit exists only after its gates are green
- **Rule:** Run the configured gates (build, type-check, lint, tests, cheapest and loudest first) on the staged change and commit only on green, so that `git bisect` can land on any commit. The per-item gate set includes the project's documented or CI lint command, so a fix is linted before it is committed, not reverted after (grade C, E01-F12). In the same way, each item's diff passes the duplicate-code check of step 8 before its commit, not at batch end (grade C, E02-F07): a new clone the edit introduced in production code is fixed before staging (a group formed only because a DU-04 fix brought existing copies closer becomes a new DU-03 candidate, DU-16), while a clone group confined to test files the item adds, which legitimately repeat setup code (DU-14), is reported as a nit and never restored or reverted. That check runs with the gates but outside `.harden/config.json`, so the recorded gate set and its baseline stay unchanged (PF-07). If `.harden/config.json` lacks the lint command, ask the user before the first item with `--interactive` and, once approved, re-record the baseline: gates.py refuses a count comparison across different gate sets. In autonomous mode, add it without asking (a gate can only refuse commits) and re-record the baseline (step 2; user-policy-autonomy U01-F01). A lint command red at base is handled as protocol-preflight's baseline rule says (PF-11). On red, restore the step's files to the last green commit and take a smaller step instead of debugging forward. The executed test count must be at least the baseline count, less the test cases recorded with `run_state.py allow-test-deletion --cases` (PC-06).
- **Detect:** `python "${CLAUDE_SKILL_DIR}/scripts/gates.py" --label <id>-a<n> --min-count-from baseline` exits 0 and `.harden/gates/<id>-a<n>.json` holds commands, exit codes and counts; restore with `git restore --source=HEAD --staged --worktree -- <files>`. The count that decides is the test gate's `count_regex` in gates.py, which counts tests executed. Listing commands are cross-checks only (test-quality T13-F01): `pytest --collect-only -q | tail -1`, `vitest list`, `jest --listTests` (file count), `go test -list . ./...` (top-level tests only), `cargo test -- --list`; a test case deleted inside an existing file is invisible to the jest and go listings. When `.harden/inventory.json` lists a lint command taken from the README or CI, every `.harden/gates/<id>-a<n>.json` records a gate running it. When Phase 2 ran a duplicate-code detector, every committed attempt has its `.harden/tools/<detector>.<id>-a<n>.*` output, and no commit or revert in `git log <base_sha>..HEAD` exists only to remove a clone confined to new test files.
- **Not when:** A full suite after every micro-step is costly: use affected tests per micro-step (`jest --findRelatedTests`, pytest-testmon) and the full configured gates before each commit. No controlled study gives an optimal step size. A tool's "safe" label never skips the gate (PC-09). The per-item lint gate rests on one run pair in eval v1: one Python fix took 5 commits, two of them attempts reverted for new lint hits (UP017, then an EncodingWarning), and the paired run had one revert for the same fix. The per-item duplicate check rests on eval v2 (n = 3 per cell): six revert/redo pairs across three runs, after the duplicate-code detector found clones in newly added tests only at batch end.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Submitting patches](https://docs.kernel.org/process/submitting-patches.html) (Linux kernel, current); [git-bisect](https://git-scm.com/docs/git-bisect) (Git project, current); [Refactoring book page](https://martinfowler.com/books/refactoring.html) (Martin Fowler, 2018); [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices) (Anthropic, 2026); [cargo_fix module docs](https://github.com/rust-lang/cargo/blob/master/src/ops/cargo_fix/mod.rs) (Rust project, 2026) · dossier: refactoring-safety T09-F08, T09-F06; llm-refactoring T10-F02, T10-F01; autofix-trust G105-F02, G105-F03; test-quality T13-F01; duplication T08-F09; eval-v1-calibration E01-F12; eval-v2-calibration E02-F07; user-policy-autonomy U01-F01

### PC-03 — The model chooses, an engine applies
- **Rule:** Perform every rename, move, extract and inline with a semantics-aware engine (LSP or IDE refactoring, the engine's library API or CLI, a tool fixer) and record tool, version, command and returned edit list in the commit body. Hand-write a structural edit only where no engine supports that operation in that language, and then apply PC-04 and PC-05 in full. Use pattern rewriters (sed, ast-grep, jscodeshift, LibCST codemods, rust-analyzer SSR) for API-migration patterns only, never to rename or move a symbol a semantic engine can handle. The language reference file lists the engines and their gaps.
- **Detect:** Several Edit or `sed` calls replacing the same identifier across two or more files with no engine call in the transcript; a supposed move with low similarity in `git diff -M` (re-typed). Before relying on a bridge, list what it offers: MCP `tools/list`, or LSP `initialize` capabilities (`renameProvider`, `codeActionProvider.codeActionKinds`, `workspace.fileOperations.willRename`); Claude Code's LSP tool offers diagnostics and navigation only. On Windows Git Bash pass repo-relative or `cygpath -m -l` long paths, prefix `MSYS_NO_PATHCONV=1` when an argument starts with `/`, and check `git ls-files --eol | rg 'w/mixed'` after engine edits.
- **Not when:** Engines ship bugs, so the gates stay mandatory: 518 historical engine bugs in Eclipse, IntelliJ IDEA and NetBeans, 66 of them behaviour changes, Extract 28.76%, Inline 16.99%, Move 15.44% (Wang et al., 2024 preprint). Change-signature has no engine in TS, Rust or C++, and Solidity has no extract or move. LSP renames miss strings, reflection and `getattr` (PC-04). The engine-versus-LLM evidence is Java/IntelliJ only: RefactoringMirror replayed 32 of 35 refactorings from 22 unsafe LLM solutions and avoided all their bugs (Liu et al., ASE journal 2025).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [Potential of LLMs in Automated Software Refactoring](https://arxiv.org/abs/2411.04444) (Liu et al., 2025); [How is Google using AI for internal code migrations?](https://arxiv.org/html/2501.06972) (Google, 2025); [An Empirical Study of Refactoring Engine Bugs](https://arxiv.org/abs/2409.14610) (Wang et al., 2024); [gopls: Code transformation features](https://go.dev/gopls/features/transformation) (Go team, 2026); [Claude Code tools reference](https://code.claude.com/docs/en/tools-reference) (Anthropic, 2026); [Git for Windows release notes](https://github.com/git-for-windows/build-extra/blob/main/ReleaseNotes.md) (Git for Windows, 2026) · dossier: llm-refactoring T10-F03; agent-refactoring-engines G105-F01, G105-F02, G105-F07, G105-F10, G105-F12, G105-F13, G105-F17; refactoring-safety T09-F09; cleanup-practice-forums T30-F03; behaviour-changing-fixes G102-F03; autofix-trust G105-F20

### PC-04 — Census the old name before and after every rename, move, signature change or deletion
- **Rule:** Save a textual census of the old name across code and non-code files (config, templates, SQL, docs, `.env.example`) before the edit; after the engine runs, re-run it and justify or hand-fix every surviving hit in the commit body. For an LSP rename, wait until indexing ends and abort unless every file returned by `textDocument/references` is in the WorkspaceEdit; an exported symbol whose rename touches one file is a failure. After a move, search the old module path in strings and config too.
- **Detect:** `rg -n -w -F '<old>' --hidden -g '!node_modules' -g '!.git'` into `census-<id>-before.txt` and `-after.txt`, then diff; reflective sweeps: Python `rg -n 'getattr[(]|setattr[(]|hasattr[(]|__getattr__|import_module[(]|mock[.]patch[(]|globals[(][)]'`, Go `rg -n 'reflect[.]|MethodByName|json:'`, Rust `rg -n 'macro_rules!|serde[(]rename'`, Solidity `rg -n 'abi[.]encodeWithSignature|keccak256[(]|[.]selector'`; after a move `rg -n -F 'old/module/path'` and `rg -n -F 'old.module.path'` over tsconfig `paths`, package.json `exports`, jest `moduleNameMapper`, pyproject entry points and `mock.patch` strings.
- **Not when:** Auto-renaming strings (rope `docs=True`, ts-morph `renameInStrings`) also hits unrelated literals, so the census is a review list, not an automatic fix. Review the list, not the count: in the researcher's runs a drop from 5 to 4 hits hid a broken `getattr`. In statically typed code without reflection the residual risk is small. Renaming an exported or public symbol is a public API change (T2).
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [gopls: Rename](https://go.dev/gopls/features/transformation) (Go team, 2026); [rope rename.py docstring](https://github.com/python-rope/rope/blob/master/rope/refactor/rename.py) (python-rope, 2026); [ts-morph: Renaming](https://ts-morph.com/manipulation/renaming) (ts-morph, 2026); [clangd Features](https://clangd.llvm.org/features) (LLVM, 2026); [Refactoring engine bugs](https://arxiv.org/html/2409.14610v1) (Wang et al., 2024) · dossier: agent-refactoring-engines G105-F05, G105-F11, G105-F16, G105-F18; refactoring-safety T09-F09; llm-refactoring T10-F17

### PC-05 — Verify moved and extracted code mechanically
- **Rule:** Review every move, extract or split with a block-mode moved-code diff: a line inside a moved region that is not marked moved is a real edit to justify or split out. Check that no comments, docstrings or licence headers were lost, and keep formatting noise out of the semantic commit.
- **Detect:** `git diff --color-moved=zebra --color-moved-ws=allow-indentation-change <sha>^ <sha> -- <files>`; `git diff -M100% --name-status` for whole-file renames; comment-line counts per touched file on both trees (`cloc --by-file`); `git diff --stat` against `git diff -w --stat` (a large gap is format noise).
- **Not when:** Extraction legitimately changes parameters, returns and imports. Moves under 20 alphanumeric characters show as plain adds and deletes, and `--color-moved=plain` cannot show permutations. Stale comments on changed code may be updated. The evidence is thin: one blog, one HN report (Codex re-typed HTML from memory and 32 of 40 links broke, 2025) and one peer-reviewed Extract Method that swapped two statements (Bavota et al., SCAM 2012, Java).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** C
- **Source:** [git-diff](https://git-scm.com/docs/git-diff) (Git project, 2026); [Two things LLM coding agents are still bad at](https://kix.dev/two-things-llm-coding-agents-are-still-bad-at/) (Kix, 2025); [HN: Codex rewrote HTML from memory](https://news.ycombinator.com/item?id=45523537) (rossant, 2025); [When does a Refactoring Induce Bugs?](https://people.lu.usi.ch/bavotg/papers/scam2012.pdf) (Bavota et al., 2012); [Refactoring Programs Using LLMs with Few-Shot Examples](https://arxiv.org/abs/2311.11690) (Shirafuji et al., 2023) · dossier: refactoring-safety T09-F10; agent-refactoring-engines G105-F14, G105-F16; llm-refactoring T10-F15; cleanup-practice-forums T30-F01

### PC-06 — Existing test lines are read-only; an existing test file only gains checked additions
- **Rule:** Never remove, change, reorder, skip, focus or loosen a line of an existing test file, never edit an existing snapshot, golden file, fixture, mock module, test helper or test configuration, and never run snapshot-update commands; the one removal is the approved dead-code deletion below. New test files are allowed: characterization tests in their own `test:` commits, demonstrating tests in behavioural commits. In every mode an existing test source file may gain lines (user-policy-autonomy U01-F07), and `scripts/strengthen.py` decides which: the file held a test definition at base, is JavaScript, TypeScript, Python, Rust, Go or Solidity, and is not a snapshot, fixture, mock or support file; every line it had at base and at HEAD survives, in order, with its line ending; each block of added lines is balanced and sits at the tail of a test body, or adds complete test cases at the tail of a describe block, test class, test contract or the module, or adds named imports to the import header; and no added line skips, focuses, marks as failing, retries or reconfigures a test, adds a hook, test double, fake timer, chain-state helper, environment, process, network, live-chain or key access, exits or returns early, catches an error, calls a snapshot matcher, assigns or mutates a name the block did not declare, redeclares a hoisted, item or module-level name the file already uses, or runs code from a string. Pure strengthening, such as a hollow test (TQ-07), is its own `test(<scope>): strengthen <test> (<finding id>)` commit that changes no other file and comes before the first behavioural commit (step 3's order), so the code it runs against still behaves as at base: the strengthened file passes at the commit and fails under at least one seeded fault or mutant of the code it covers (PF-19; pilot-auto-calibration A01-F22's operators) under which its parent version passes, each run a row of `.harden/tools/strengthen-<id>.md` (fault or parent commit, file:line, command, exit code of the strengthened and of the parent version). A behavioural fix's demonstrating test in an existing file is a new test case at the tail of a describe block, test class, test contract or the module, so the executed-test count rises (PC-14 (b)); it fails at the fix's parent and passes at the fix (PC-14), and `python "${CLAUDE_SKILL_DIR}/scripts/strengthen.py" replay --base <base_sha> --label <id>-a<n>-oldlines` shows every existing test, as written at base and with the test files the run added set aside, still passing with the fix (step 9). A line the run added and committed is an existing line from then on: when a later fix contradicts it, run `git revert --no-edit` on its commit first (a revert may remove only what its commit added) and set that commit's finding to `reverted`. When a test seems to need any other change or looks wrong, stop the item, set it `blocked` and write the case into `.harden/progress.md` for the owner. An approved deletion (paths recorded with `run_state.py allow-test-deletion <path> --cases <n> --reason <finding id>`) happens only in the `refactor(dead-code):` commit that deletes the production symbols those test cases reference, and only with `--interactive`: an autonomous run approves no test deletion, so a dead-code item that needs one is reported, never applied (user-policy-autonomy U01-F03). Other lines in those files stay byte-identical (only import lines that refer solely to deleted symbols may also go), and diff_guard checks that the change is deletion-only (DC-15, TE-2, TE-3). Every apply prompt says: write general solutions, never hard-code or special-case test inputs, never work around a test, report tests that look incorrect. That clause is never the only control.
- **Detect:** While `.harden/active` exists, `hook_guard.py` refuses an Edit, Write or MultiEdit of an existing test file unless `strengthen.py` accepts the resulting file (reason_code `edit-test`, the problem after `[test-edit: …]`), every NotebookEdit of one, and every shell write, copy, move or deletion of one; `diff_guard.py --base <base_sha>` (with `--quick` per item, at Stop, and in full at Phase 8) reports `test_modified` with a `reason` for the working tree against base and for each commit of base..HEAD against its parent (a revert commit may remove only lines its reverted commit added, and add none it did not remove), `test_deleted` (`reason` `renamed` when the content reappears under another path) and new skip markers, lists accepted additions under `info.strengthened_tests`, and reports `replay_pending` while a replay has not restored its files; any snapshot or golden diff reverts the step; grep scripts and transcripts for `-u`, `--updateSnapshot`, `--snapshot-update`, `insta accept`, `INSTA_UPDATE`; `git diff <sha>^ <sha> -- <test globs> | grep -E '^-[^-]'` prints nothing outside a DC-15 commit or a `git revert` of a commit of this run, except the last line of a file that had no final newline, which reappears with one; executed test count at or above the baseline less the recorded `--cases` (`gates.py --min-count-from baseline`, PC-02); at Phase 8 `strengthen.py replay --base <base_sha> --label final-oldlines` exits 0 (step 13); every `test(...): strengthen` commit has its rows in `.harden/tools/strengthen-<id>.md`.
- **Not when:** An engine rename that must update test imports, or implementation-coupled tests (mocks of internals, private-method tests) that break legitimately, still go to the user first; an autonomous run sets such an item `blocked` and reports it. The additions checks read text, not a syntax tree: a call with side effects on shared state, an alias of a shared object or a line the scanner misreads can pass them, which is why the replay runs every existing test at its base version with the test files the run added set aside (new test files are not content-checked, and a shared-process runner such as Mocha or pytest lets one register hooks for all tests), and a refusal can be a false positive, after which the item pins its contract in a new test file. Test files in languages other than the six stay fully read-only. The allowance is the owner's policy (U01-F07) and its checks are this skill's synthesis, unmeasured when written. Read-only tests do not stop special-casing or operator overloading (PC-07). The rates come from deliberately impossible tasks: on Conflicting-SWEbench GPT-5 cheated 54% and Claude Opus 4.1 50%, Claude models mostly by editing tests (ImpossibleBench, 2025 preprint), and its documented example inverts an existing assertion, which removes a line; an anti-hack prompt cut Claude Opus 4 from 47% to 5% but left Sonnet 3.7 at 78-80% (Claude 4 system card). ### PC-21 — Secrets are reported, never handled
- **Rule:** When a secret appears in the working tree or in history, edit, move and commit nothing about it, and never print or log its value. Report file, line, secret type and first commit with the value redacted, as a T2 finding for the user to rotate. Rewriting history to remove it is the user's decision; rotation is usually better, because a rewrite breaks existing clones and signatures. One exception (grade C, eval-v2-calibration E02-F04): a literal that is verifiably a placeholder may be deleted in the same commit that removes its last use, as part of an approved T1 item (such as the removal of a placeholder credential fallback, SE-17), never under a T2 item (invariant 8). Verifiably means both: the value carries a test-shaped marker (`test`, `fixture`, `example`, `dummy`, `changeme`, `xxx`, `not_a_real`), and a secret scanner run in its verified mode, which needs the user's go-ahead because it logs in to the provider with the value (SE-17), does not match it. The item's approval shows the file:line, the marker and the scanner result, never the value, so that a human confirms the call (SE-17: a verifying scanner prioritises, it never dismisses on its own). An autonomous run has no such human, so the exception never applies there: the literal stays reported (user-policy-autonomy U01-F01, U01-F03). That commit removes the literal's lines and changes nothing else about the value; history stays as it is. Anything that could be a live credential (no marker, a verified or unknown scanner status, no verified-mode run, or no confirmation from the user) stays under this rule: never touched, reported, rotated by the human.
- **Detect:** No commit in `<base_sha>..HEAD` touches a file:line listed by a secret finding, except a placeholder deletion: that commit belongs to an approved T1 item, the finding's notes record the marker and the verified-mode result without the value, `.harden/approvals.md` holds the user's confirmation, the commit only removes lines that hold the literal (none re-added or moved), and a PC-04 census of the constant's name, or of the marker when the literal is inline, finds no remaining use; production credentials in the environment and in `.env*` files are checked by name only, without logging values; the report shows no secret value.
- **Not when:** Secret scanners produce false positives: verify before reporting. Google's release guidance is written for Google-owned projects. The placeholder exception is the skill's own policy (eval v2, 9 runs, n = 3 per cell): the runs handled one seeded placeholder credential in four different ways, because this rule blocked the T1 fallback removal whenever the literal had to go. A marker is a naming convention, not proof: two eval-v2 baseline runs measured that the exchange accepted the placeholder (HTTP 200), and verified-only triage misses services the scanner cannot verify (46% of critical secrets, GitGuardian 2026, vendor), hence the human's confirmation. A wrong call touches a live secret's line, though it never prints the value, and deleting the line never replaces rotation (SE-18).

### PC-24 — Pin the valid inputs a behavioural fix used to accept, and never reject one shown to occur
- **Rule:** Before every behavioural fix, characterization cases committed first pin the current outputs of each exported function or method the fix's diff edits (bin and CLI entry modules included), of the exported functions of the same module that call an edited function that is not exported, and, for an edit outside every exported function or in a file the script cannot parse, of the module through a test that imports it, with representative inputs that include the call with every optional argument omitted and the bare command; `contract_check.py pins` computes that set from the staged change, not from the finding's line, and checks the commit's `newly rejected: none (<test files>)` claim against it (pilot-auto-calibration A01-F29, A01-F47). Include values at and past any boundary the fix introduces; the other formats found in the project's fixtures, sample data, tests and docs; and, when the fix changes how the code writes or reads data it persists (a state or cache file, a config it rewrites, stored rows, an export it reads back), data written by the base code in a base worktree in the run's scratch_dir, under each locale, time zone or setting the defect's reproduction used, then loaded, used and saved again by the candidate; every path the code persists to points into the scratch_dir (a constructor argument, a config value, or `HOME`, `USERPROFILE`, `APPDATA` and the `XDG_*` variables set to scratch_dir subdirectories), never at the owner's real files, and when the code offers no such seam the case cannot run and the item is not applied. A member is attested when the project's docs, fixtures, sample data or tests, the published format of the data the code parses, the base code's own output, or the finding itself (its rule or its reproduction) shows that such inputs occur. Each clone installs with the lockfile-enforcing command (`npm ci`, `pnpm install --frozen-lockfile`, `uv sync --locked`, `cargo build --locked`), so that hidden local state cannot make it pass (G106-F01), then runs the config's gates, the ratchet gates and every gate and `e2e` check of the profile. A clone of the base runs the same checks first, as the reference: a count may not fall below the base's, and a `compare: true` check must give the same normalised output at base and head, because a green suite is a weak oracle and existing behaviour is hard to specify (G205-F14, T09-F14, T30-F11); the Phase 1 golden captures (PF-16) belong in the profile as such checks. A check red at the base, or red at the head and green on one re-run (flaky), cannot be judged: it is recorded `unjudged`, nothing is reverted for it, and the verifier exits 3 (inconclusive); name it under Limits. A confirmed red check is bisected in the clone with `git bisect run` to the first bad commit, which holds only because every commit was green on its own (T09-F08, step 13); the probe skips (exit 125) a commit it cannot build for environmental reasons. The verifier reverts that commit in the repository with `git revert --no-edit <sha>` (each candidate, newest first, when skipped commits leave several), never with a reset or rebase (PC-20), and starts again from a new clone. At `--max-reverts` (default 5) with a check still red, or when the first bad commit is itself a revert or a merge, or bisect names none, it reverts the whole applied range, newest first, so that the tree ends equal to the base's, and exits 1 (`range-reverted`). A revert that conflicts is aborted with `git revert --abort` and the verifier exits 1 (`revert-conflict`): then first revert, newest first, each commit after the bad one that touches a path the bad commit touches, then the bad commit itself, each with `git revert --no-edit`, because later changes to the same files are what make a rollback conflict (U01-F13). When one of these conflicts, `git revert --abort` and revert the range yourself the same way, one `git revert --no-edit <sha>` per commit of `git rev-list --first-parent <base_sha>..HEAD`, newest first (each applies to the tree its commit produced, so none conflicts), check `git diff --quiet <base_sha> HEAD`, and run the verifier again. Read `.harden/verify.json` yourself (PC-23): confirm that each `revert_sha` it lists is in `git log`, set every finding whose commits were all reverted to `reverted` (one that keeps a commit is `partial`, RP-16) with the failing check and the revert sha in `notes`, and never re-apply a reverted item in the same run. Any later revert (SAST delta, ratchet, diff guard) re-runs the verifier, so that its record describes the HEAD handed over. With no `e2e` check in the profile, or with `--interactive` and no profile, the verdict adds "gates only", and the report names the missing end-to-end checks under Limits. With `--e2e-coverage` it then runs each profile `e2e` check once more in the last green clone with Node's built-in V8 coverage written to a run directory (`NODE_V8_COVERAGE`), never judging, bisecting or reverting on that run; `e2e_reach.py` states per changed production file whether a check executed its changed code, only loaded or imported it, or neither (pilot-auto-calibration A01-F21).
- **Detect:** `.harden/verify.json` exists and its `head_at_end` equals `git rev-parse HEAD`; its `final_status` is `green` (exit 0) or `inconclusive` (exit 3, every unjudged check named under Limits), or it is `range-reverted` with `tree_equals_base` true and `git diff --quiet <base_sha> HEAD` exiting 0, and the report's Summary gives that verdict; each entry of its `reverts` (`sha`, `subject`, `check`, `reason`, `revert_sha`, `kind`) has its `revert_sha` in `git log --oneline <base_sha>..HEAD` and a row in the report's "Reverted by end-to-end verification" section, and each reverted `sha` that is not itself an earlier revert is the `commit` of a finding with status `reverted` or `partial` whose `notes` name the check; every path in its `clones` lies under the run's scratch_dir (`run_state.py status`); no `git reset`, `git rebase`, `commit --amend` or force-push appears among the run's commands; a `revert-conflict` status is followed by the range revert and a later verifier run.
- **Not when:** Bisect names the first commit at which a check fails: a failure caused by two commits together is pinned on the later one, and a flaky check that fails twice in a row is bisected and can blame an innocent commit. A wrong revert loses a fix but adds no defect, and the cap bounds the loop. A check already red at the base proves nothing about the branch, so it is reported, never used to revert. Green end-to-end checks prove only what they exercise: of the SWE-bench Verified patches that pass the tests, 29.6% behave differently from the reference (Wang, Pradel, Liu, 2026). Code with side effects cannot simply be run twice (T30-F11), which is why live money, order, key, signing and transaction paths stay report-only in autonomous mode (U01-F03), and a fresh clone on one OS cannot check another OS's steps (G106-F01). Replacing the live approval with this gate is the owner's policy and has not been measured: an autonomous pilot on an evaluation fixture must precede use on a deadline project (user-policy-autonomy, open questions).

## Evidence limits
- Most refactoring-safety numbers come from Java (some JS/TS) and 2023-2025 models; no replication exists for current frontier agents on TS, Python or Rust.
- Engine failure rates per operation are unmeasured outside Java IDEs; the engine observations behind PC-03 and PC-04 are 2-5-file fixtures run once on one Windows machine.
- The retry cap (2-3), the 3 fixed-point passes, the 20-file deletion prompt, the 100-line fix ceiling and the 3 final repeats are heuristics or borrowed policies, not measured optima.
- The per-survivor mutation gate and the four-way survivor disposition (grade D), and the 100% touched-line coverage condition and tier boundaries for T0 autofixes (grade C), are policy; no study validates them. Recording mutation dispositions in a triage log instead of in-code skips departs from the mutation dossier.
- Separating commits is supported for bisect and revert, weakly for review effectiveness (one experiment, 28 developers).
- Reward-hacking rates come from deliberately impossible tasks; everyday rates are lower (METR: o3 reward-hacked in 0.7% of HCAST runs). Read-only tests do not stop special-casing.
- Hooks can fail silently (#69970), hook_guard.py fails open on its own internal errors, and native Windows has no Claude Code sandbox; `diff_guard.py` at each commit is the backstop, not a proven boundary.
- Refactoring-type risk is SZZ-based and Java-only; the claim that type or signature changes are high-risk was contradicted by its own source and is not used.
- Mutation tooling differs by platform: mutmut needs WSL on Windows, and StrykerJS verdicts depend on the runner version.
- No study compares a one-shot end-of-project pass with continuous refactoring.
- The eval-v1 calibrations (PC-02's per-item lint gate, PC-14's restoring-versus-breaking split, warn-first staging and re-ask, PC-24, PC-25) rest on the skill's own paired evaluation: 3 fixtures, 12 runs, n = 2 per cell, one grader per run; indicative, not significant, and to be re-measured with at least 3 runs per cell.
