# Lens: Complexity and design

> Purpose: find complexity and design problems that raise the cost of change, use metrics only as review triggers with stated provenance, and rank smells by the evidence that they cause harm.
> Read when: the complexity-design lens is in scope for a slice of source code in any language (functions, classes, modules, abstractions).

## Contents
- Procedure
- Rules: metrics and thresholds (CX-01 to CX-09)
- Rules: function-level changes (CX-10 to CX-16)
- Rules: design and abstraction (CX-17 to CX-22)
- Rules: smells ranked by evidence of harm (CX-23 to CX-32)
- False-positive exclusions
- Evidence limits

## Procedure

You are a fresh-context, read-only lens subagent with Read, Grep and Glob only (detection step 8): you edit nothing and run nothing, and you emit candidates only. The orchestrator runs every command this file names (metric tools, linters, `git log`, `git blame`), never in fix mode, and saves the raw output under `.harden/tools/`; you read those files. If you are the unseeded pass, you receive no tool output: judge from the source alone and say so in your limits.

1. Load context: `.harden/inventory.json` (languages, configured linters), `.harden/config.json` (`scope`, `exclude_globs`), `.harden/rank.json` (location class, churn, history verdict) and the raw outputs in `.harden/tools/`. Work only on the slice you were given.
2. Build the threshold-policy header before judging anything: project configuration first, then skill defaults, each with tool, version, variant, source and provenance (CX-02 to CX-04).
3. Read the per-function metric outputs for each language family: orchestrator-run commands whose raw output (JSON, SARIF or CSV) is saved under `.harden/tools/`. A tool listed here with no output file is a coverage gap for your limits, never a clean result. Exact commands, pins and ephemeral runners live in the language file; the tools and rule ids are:
   - Any language: lizard (NLOC, CCN, PARAM per function; `-m` only as a side-by-side view).
   - Offline fallback, for a language with neither lizard nor a native linter output: `.harden/tools/complexity.json` from `complexity.py` (a heuristic: nloc, ccn_estimate, max_nesting and params per function, plus the functions above CX-04's triggers or CX-10's nesting; pilot-auto-calibration A01-F18). Label its numbers `complexity.py (heuristic)` in the policy block, never compare them with another tool's (CX-02), and still read each function before its scores (CX-07).
   - TypeScript/JavaScript: ESLint `complexity`, `max-depth`, `max-lines-per-function`, `max-params`, `no-useless-constructor` (typescript-eslint variant for TS), `no-cond-assign`, `no-param-reassign`; eslint-plugin-sonarjs `cognitive-complexity`.
   - Python: Ruff C901, PLR0912, PLR0913, PLR0915, PLR0917, PLR1702 and PLR0916 (both preview); Pylint W0246, R0904; Radon `cc` only as a named second opinion.
   - Rust: Clippy `too_many_lines`, `excessive_nesting`, `too_many_arguments`, `fn_params_excessive_bools`; lizard CCN. Not Clippy `cognitive_complexity`.
   - Go: golangci-lint `gocyclo`, `gocognit`, `cyclop`, `nestif`, `funlen`.
   - C/C++: clang-tidy `readability-function-cognitive-complexity`, `readability-function-size`; lizard.
   - Java/C#: PMD CyclomaticComplexity, CognitiveComplexity, NcssCount, GodClass, ExcessiveParameterList, AvoidDeeplyNestedIfStmts, UselessOverridingMethod, SingularField; Checkstyle CyclomaticComplexity; SonarJava S3776, S138, S134, S2301 where SonarQube is configured; CA1502.
   - Module structure: dependency-cruiser, import-linter, ArchUnit; code-maat co-change when history is sufficient.
4. Join one row per function: NLOC, CCN, cognitive score, nesting, parameters, branch coverage if a report exists, churn and location class. Keep languages apart.
5. Drop the false-positive exclusions below, then read every remaining function before looking at its scores and write the one-sentence note of CX-07.
6. Run the manual design checks on the slice: extraction depth and single-caller helpers (CX-12, CX-13), pass-throughs (CX-17), flag-accreting shared functions (CX-18), speculative generality (CX-19), the public surface (CX-20), class cohesion (CX-22) and context-dependent smells (CX-28, CX-32).
7. Rank by distinct smell families and change activity (CX-23, CX-24), and count the flat-dispatch and intent-marker exemptions.
8. Return, as your final message, the candidates as JSON in the findings schema (`assets/findings.schema.json`) plus `files_read` (every file you read, with its line ranges); the orchestrator merges them into `.harden/candidates.json`. Per candidate: `lens: "complexity-design"`; `rule_ref` = CX-NN or `project:<tool>/<rule>`; `file` and `line` (and `end_line`) at `base_sha`; `tier`, `class` and `fix_risk` copied from the rule block (CX-20 overrides them for exported code); `evidence` items of kind `tool` (command, tool version, metric values) and `git` (churn, co-change); `confidence: "needs_review"` for metric-triggered candidates and `"inference"` for design judgements; `verified: false`; `status: "candidate"`; `location_class` from rank.json; every cited tool in `tool_versions`. Return the policy header and the exemption counts with the candidates.

## Rules

### CX-01 — Read size next to every complexity number
- **Rule:** Report logical size (NLOC or SLOC) beside every cyclomatic (CC) or cognitive score, per function, and treat size as the first-order signal and a likely confounder. Call a long, low-CC function a size finding and a short, high-CC function dense decision logic. Never divide a metric by LOC to control for size, and never present a size reduction as a complexity improvement.
- **Detect:** `lizard --csv` (NLOC, CCN, PARAM per function) or the native tool; sort by NLOC and by CCN; list "both high" first and keep "high CC, small size" as its own bucket (terse code, a reliability risk per NASA SATC as quoted by Microsoft).
- **Not when:** File- or class-level aggregates serve overviews only, because aggregation and log transforms inflate the CC-size link (R² 0.87-0.97 for SourceForge files, log-log, vs 0.40 for 17.6M Java methods and 0.44 for 6.3M C functions). Generated code, data tables and flat configuration builders inflate LOC without adding load.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Relationship between CC and SLOC (JSEP preprint)](https://aserebre.win.tue.nl/Landman2015-ccsloc-jsep2015-preprint.pdf) (Landman et al., 2016); [Revisiting the Debate (EMSE preprint)](https://www.cs.ubc.ca/~rtholmes/papers/emse_2022_chowdhury_preprint.pdf) (Chowdhury et al., 2022: 730K Java methods; dividing by LOC fails to neutralise size); [Code metrics: cyclomatic complexity](https://learn.microsoft.com/en-us/visualstudio/code-quality/code-metrics-cyclomatic-complexity) (Microsoft, 2024) · dossier: complexity-metrics T03-F01; metric-thresholds G208-F11

### CX-02 — Record tool, version and variant with every number
- **Rule:** Measure each language with one named tool and variant, and record `<tool> --version` and the effective configuration with every number. Compare before and after only with the same tool, version and settings, never across tools or languages, and never pool languages into one ranking. Never switch a variant or a tool to make findings disappear.
- **Detect:** Know the counting differences: Ruff C901 counts statements only (no `and`/`or`, comprehensions or conditional expressions); Radon adds boolean operators, comprehensions, `with` and `assert`; gocyclo counts `if`, `for`, `case`, `&&`, `||`; ESLint counts logical assignment since v7.18.0 (Jan 2021), `?.` and default values since v9.0.0 (Apr 2024), and offers `variant: "modified"` since v9.12.0 (Oct 2024); Sonar-spec cognitive ignores null-coalescing and `?.`; clang-tidy implements Sonar spec v1.2 (2017), not v1.7 (2023). Record variant options: ESLint `variant`, lizard `-m`, Checkstyle `switchBlockAsSingleDecisionPoint`, clang-tidy `IgnoreMacros`, PMD `cycloOptions`.
- **Not when:** When two tools disagree, report the project's native linter number and note the other. Differences are small for ordinary code and concentrate around switch/match, default parameters, `?.` and macros (dropping `&&`/`||` changed CC for 1.3M of 17.6M Java methods).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Ruff C901 source](https://raw.githubusercontent.com/astral-sh/ruff/main/crates/ruff_linter/src/rules/mccabe/rules/function_is_too_complex.rs) (Astral, 2026); [Radon: introduction to code metrics](https://radon.readthedocs.io/en/latest/intro.html) (Radon, 2026); [ESLint v9.0.0 released](https://eslint.org/blog/2024/04/eslint-v9.0.0-released/) (ESLint, 2024); [ESLint complexity](https://eslint.org/docs/latest/rules/complexity) (ESLint, 2026); [clang-tidy function-cognitive-complexity](https://clang.llvm.org/extra/clang-tidy/checks/readability/function-cognitive-complexity.html) (LLVM); [Landman et al. §2.1](https://aserebre.win.tue.nl/Landman2015-ccsloc-jsep2015-preprint.pdf) (2016) · dossier: metric-thresholds G208-F09, G208-F13; complexity-metrics T03-F12

### CX-03 — Label every threshold with its provenance
- **Rule:** Never cite a shipped tool default as evidence that code is too complex. Open the lens output with a threshold-policy block giving, per metric, tool, version, variant, value, source (project config path, skill default or vendor default) and provenance class (standard-backed convention, vendor convention, benchmark percentile with corpus and version, or fault-calibrated on this repository). State that exceedances are review candidates, not defects.
- **Detect:** `eslint --print-config`, `ruff check --show-settings`; search configs for `complexity|max-complexity|max-args|max-params|max-lines-per-function|too-many-.*-threshold|cognitive-complexity-threshold|min-complexity|funlen|CA1502`; label values equal to the tool default "vendor default (convention)".
- **Not when:** Defaults are reproducible and help consistency: label them, do not discard them; the block may be a table but is never omitted. Provenance examples: ESLint's CC default 20 was chosen in 2015 partly from ESLint's own worst functions (maximum 36, six above 20); golangci-lint ships gocyclo/gocognit 30 while recommending 10-20; the Sonar white paper states no threshold; shipped CC defaults span 10 to 30.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [ESLint issue #4808 comments](https://api.github.com/repos/eslint/eslint/issues/4808/comments) (ESLint, 2015); [golangci-lint linter settings](https://golangci-lint.run/docs/linters/configuration/) (golangci-lint, 2026); [Clippy cognitive_complexity.rs](https://raw.githubusercontent.com/rust-lang/rust-clippy/master/clippy_lints/src/cognitive_complexity.rs) (Clippy, 2026: left in `restriction` so it is not used as a measurement tool); [NIST SP 500-235](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication500-235.pdf) (Watson & McCabe, 1996) · dossier: metric-thresholds G208-F02, G208-F18

### CX-04 — Project configuration enforces; skill triggers only advise
- **Rule:** Report exceedances of the project's own configured limits as findings. Where the project sets none, or a laxer one, apply these advisory per-function triggers and label them: classic CC > 10 (priority above 25), Sonar-spec cognitive > 15 (only where a Sonar-spec implementation exists), logical SLOC > 60, 7 or more declared parameters; each hit ends in a behaviour-preserving refactor proposal or a one-line written justification. List inline suppressions as recorded exceptions and flag one only when the function also has high churn or bug history.
- **Detect:** `lizard --csv` filtered on CCN > 10, NLOC > 60, PARAM ≥ 7, or, when neither lizard nor a native linter ran, the `candidates` of `complexity.py`'s JSON (same triggers plus nesting above 3); native linters in warn mode; config files (`eslint.config.*`, `ruff.toml`, `pyproject.toml`, `.pylintrc`, `clippy.toml`, `.golangci.y*ml`, `sonar-project.properties`, `CodeMetricsConfig.txt`, PMD and Checkstyle XML); suppressions (`noqa: C901|PLR09`, `eslint-disable … complexity`, `allow(clippy::too_many_arguments|too_many_lines|cognitive_complexity)`, `nolint: gocyclo|gocognit|cyclop|funlen`, `#pragma warning disable CA1502`).
- **Not when:** Generated, vendored and third-party code; report test code separately. Go: each `if err != nil` adds 1 to gocyclo and to cognitive complexity, so record the err-check count beside CC (downgrading runs of flat err checks is a policy choice, grade D). The combination is an unvalidated synthesis: CC 10 is NIST's recommended limit (limits up to 15 "used successfully"), 25 is SIG's top band and the CA1502 default, cognitive 15 is the uncalibrated Sonar/PMD default, 60 lines is SIG's top band and Holzmann's safety-critical C guideline, 7 parameters is SIG's top band.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [NIST SP 500-235](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication500-235.pdf) (NIST, 1996); [SIG Guidance for Producers v18.1](https://www.softwareimprovementgroup.com/wp-content/uploads/SIG-TUViT-Evaluation-Criteria-Trusted-Product-Maintainability.pdf) (SIG, 2026); [CA1502](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1502) (Microsoft, 2026); [The Power of 10](https://web.eecs.umich.edu/~imarkov/10rules.pdf) (Holzmann, 2006); [Automatic metric thresholds derivation](https://api.openalex.org/works/doi:10.1109/WETSoM.2015.14) (Arcelli Fontana et al., 2015); [lizard README](https://github.com/terryyin/lizard) (Yin, 2026); [A Complexity Measure](https://api.openalex.org/works/doi:10.1109/TSE.1976.233837) (McCabe, 1976) · dossier: metric-thresholds G208-F01, G208-F14, G208-F13; complexity-metrics T03-F03; pilot-auto-calibration A01-F18

### CX-05 — A threshold is not a cliff
- **Rule:** Rank continuously and write "above the review trigger"; never write "unmaintainable", "violates" or "must be below N" for a skill-default exceedance. At file and class level, never propose moving code into smaller files or classes only to lower a metric.
- **Detect:** Check the wording of every candidate; flag any proposal that moves code between files or classes without removing logic as low value.
- **Not when:** At method level smaller Java methods were less change-prone (Chowdhury et al., MSR 2022), so method-level splits stay possible under CX-11 and CX-12. Shatnawi (2010, Eclipse only) did find threshold effects for CK metrics.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** B
- **Source:** [Thresholds for size and complexity metrics (QRS 2016)](https://posl.ait.kyushu-u.ac.jp/~kamei/publications/Yamashita_QRS2016.pdf) (Yamashita et al., 2016: very-high-risk Java files more often defective but with uniformly lower defect density; 3 OSS and 4 industrial projects, file level); [The optimal class size](https://api.openalex.org/works/doi:10.1109/TSE.2002.1000452) (El Emam et al., 2002: no threshold effect of class size); [Functional form of the size-defect relationship](https://api.openalex.org/works/doi:10.1109/TSE.2008.90) (Koru et al., 2009: logarithmic, class level); [Acceptable risk levels of OO metrics](https://api.openalex.org/works/doi:10.1109/TSE.2010.9) (Shatnawi, 2010) · dossier: metric-thresholds G208-F03

### CX-06 — Exempt flat dispatch; never alter the metric
- **Rule:** Before raising a CC trigger, check whether the function is a single flat dispatch: a switch, match, if-elif chain or lookup whose arms are one call, return or assignment with no nested branching. If so, exempt it from the CC trigger, re-judge it on cognitive complexity and record the exemption; never exempt a dispatch whose arms branch, and never change the gate metric or variant yourself.
- **Detect:** Heuristic (the researchers' own, unvalidated): CC above the trigger with cognitive ≤ 5 or ≤ CC/3, or switch-as-one CC (ESLint `variant: "modified"`, `lizard -m`) ≤ 10, as a side-by-side view only. Confirm with ast-grep `switch ($X) { $$$ }` or `match $X { $$$ }` that no arm contains `if`, `for`, `while` or `match`. Find repeated dispatch on one discriminant, e.g. `rg -n "switch \(\w+\.(type|kind)\)"`.
- **Not when:** The same switch repeated across the codebase, or arms with their own logic, lose the exemption. The exemption covers "too complex" claims only: a flat dispatch still needs one test per branch. A switch-as-one variant the project config already declares stays and is recorded in the policy block. Replacing a switch with a map or polymorphism can lose exhaustiveness checks (TS `never`, Rust `match`), change default or fallthrough behaviour and cost speed (CX-16).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [NIST SP 500-235 §2.5](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication500-235.pdf) (NIST, 1996: exempt single multiway decisions unless the branches are complex; a divide-by-branches "modified" measure took a module from 90 to 10); [Linux kernel coding style](https://www.kernel.org/doc/html/latest/process/coding-style.html) (Linux kernel); [CA1502](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1502) (Microsoft, 2026); [Cognitive Complexity white paper v1.7](https://www.sonarsource.com/docs/CognitiveComplexity.pdf) (SonarSource, 2023: a whole switch is +1); [rust-clippy #3793](https://github.com/rust-lang/rust-clippy/issues/3793) (Clippy maintainers, 2019) · dossier: complexity-metrics T03-F04; metric-thresholds G208-F10, G208-F09

### CX-07 — Scores select candidates; reading decides
- **Rule:** Use CC as a test-effort number (structured testing needs exactly CC tests) and cognitive complexity or nesting only to choose what to read. Read each flagged function before looking at its scores and write one sentence on what makes it hard (nesting, interleaved concerns, hidden state, boolean soup) or "reads fine", which becomes a recorded exemption. Never present a metric as a validated measure of understandability or as proof that a change made code easier to read.
- **Detect:** ESLint `complexity` with eslint-plugin-sonarjs `cognitive-complexity` (default 15); Ruff C901 or `radon cc`; PMD CognitiveComplexity; clang-tidy `readability-function-cognitive-complexity`; gocognit; Rust: lizard CCN with Clippy `excessive_nesting` and `too_many_lines`, not Clippy `cognitive_complexity`. In TS/JS report CC and cognitive together before calling null-safe code complex, because ESLint counts `?.` and defaults while Sonar-spec cognitive ignores them.
- **Not when:** Candidate selection at scale still needs the metrics. Showing a metric value produced a large anchoring effect on comprehensibility ratings, but not on time or correctness, in a randomized double-blind experiment, which is why reading comes first.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Empirical validation of Cognitive Complexity (ESEM 2020)](https://arxiv.org/abs/2007.12520v1) (Muñoz Barón et al.: about 24,000 evaluations of 427 snippets; r = 0.54 with comprehension time, I² = 85%; -0.29 with ratings; no reliable link with correctness); [The Mind Is a Powerful Place (ICSE 2021)](https://arxiv.org/abs/2012.09590) (Wyrich et al.); [Early career developers' perceptions](https://arxiv.org/abs/2303.07722v2) (Esposito et al., IEEE Access 2025: "modest predictors"); [Checkstyle CyclomaticComplexity](https://checkstyle.org/checks/metrics/cyclomaticcomplexity.html) (Checkstyle, 2026); [NIST SP 500-235](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication500-235.pdf) (NIST, 1996) · dossier: complexity-metrics T03-F02, T03-F14; metric-thresholds G208-F11, G208-F13

### CX-08 — Do not act on the Maintainability Index
- **Rule:** Never use MI to select, justify or report a refactoring; report its components (size, CC or cognitive, nesting) per function, using maximums or high percentiles rather than averages. Leave existing MI dashboards in place and do not act on them.
- **Detect:** `rg -n -i "radon mi|maintainability.?index|maintidx|CA1505|wily"` in code and CI; treat any MI gate as advisory.
- **Not when:** Counter-evidence: in 730K Java methods MI was the best and most consistent predictor of change-proneness beyond size (Chowdhury et al., EMSE 2022), so a single-tool MI trend line may carry signal. The rule rests on MI not saying what to fix: its coefficients were fitted to late-1980s HP C and Pascal systems of 1,000-10,000 lines, and Visual Studio's cut-offs were chosen "to keep the noise level low".
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [Think twice before using the Maintainability Index](https://avandeursen.com/2014/08/29/think-twice-before-using-the-maintainability-index/) (van Deursen, 2014); [Maintainability index range and meaning](https://learn.microsoft.com/en-us/visualstudio/code-quality/code-metrics-maintainability-index-range-and-meaning) (Microsoft, 2025); [Questioning software maintenance metrics](https://www.mn.uio.no/ifi/personer/vit/dagsj/sjoberg.anda.mockus.esem.2012.pdf) (Sjøberg et al., 2012: MI ranked 4 equivalent systems opposite to measured effort); [Revisiting the Debate](https://www.cs.ubc.ca/~rtholmes/papers/emse_2022_chowdhury_preprint.pdf) (Chowdhury et al., 2022) · dossier: complexity-metrics T03-F10

### CX-09 — Reject changes whose only effect is a lower score
- **Rule:** Reject any proposed complexity change whose only effect is a smaller number: part1/part2 splits, dispatch tables that just move branches, new suppressions, raised thresholds or switched variants. Accept a fix only when re-reading the diff shows less to hold in mind (nesting depth, variables live across branches, branch count), not because the linter went quiet.
- **Detect:** In proposed diffs: new suppressions (`eslint-disable… complexity|max-depth|max-lines-per-function|max-params|sonarjs/cognitive-complexity`, `noqa: C901|PLR09\d\d|PLR1702`, `allow(clippy::cognitive_complexity|too_many_lines|too_many_arguments|excessive_nesting)`, `NOLINT(readability-function-…)`, `NOSONAR`, `rubocop:disable Metrics/`, `nolint:(gocyclo|gocognit|cyclop|funlen|nestif)`); raised thresholds or variant changes in lint configs; new names matching `(part|step)\d|helper\d|Rest\b|_impl\d`.
- **Not when:** A suppression with a one-line justification is legitimate for flat switches (CX-06), generated code, parsers and state machines.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [NIST SP 500-235 §2.5](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication500-235.pdf) (NIST, 1996: a module went from 90 to a "modified" 10 through a do-nothing switch); [ESLint issue #19360](https://github.com/eslint/eslint/issues/19360) (ESLint maintainers, 2025: a rewrite lowers CC "despite looking more convoluted"); [RuboCop issue #15363](https://github.com/rubocop/rubocop/issues/15363) (Batsov, 2026: across the 233 configs shipped by the top 500 Ruby repos, metric cops lead every suppression list); [HN 45640380](https://news.ycombinator.com/item?id=45640380) (2025: threshold "fixes" by naive copy pasting) · dossier: complexity-metrics T03-F11; code-smells-evidence T27-F21, practitioner voice

### CX-10 — Flatten nesting deeper than 3 before splitting
- **Rule:** Flag blocks nested more than 3 levels inside a function (4 at most). Propose flattening first (guard clauses, early return or `continue`, inverted conditions, an extracted loop body) and only then consider splitting the function.
- **Detect:** ESLint `max-depth` (default 4; set 3); Ruff PLR1702 (preview, needs `--preview`; `max-nested-blocks` default 5) or Pylint R1702; Clippy `excessive_nesting` with `excessive-nesting-threshold = 4` (the default 0 disables it); PMD AvoidDeeplyNestedIfStmts (3); SonarJava S134 (3); clang-tidy `readability-function-size` `NestingThreshold`; golangci-lint `nestif` scores nested ifs and is not a depth.
- **Not when:** A project standard that requires a single exit point; nesting that mirrors the data (a 2D grid). Traps: early returns can skip cleanup, logging, unlock or commit; guard clauses reorder side effects; `!(a > b)` is not `a <= b` with NaN or null; moving a loop body changes `break`/`continue`. The limit is convention with partial support: RuboCop 1.91 schedules BlockNesting for default-off in 2.0, and `Style/GuardClause` is disabled in 32.2% of the sampled Ruby configs.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [Linux kernel coding style](https://www.kernel.org/doc/html/latest/process/coding-style.html) (Linux kernel: "more than 3 levels of indentation"); [PMD Java design rules](https://pmd.github.io/pmd/pmd_rules_java_design.html) (PMD, 2026); [ESLint max-depth](https://eslint.org/docs/latest/rules/max-depth) (ESLint, 2026); [Replace nested conditional with guard clauses](https://refactoring.com/catalog/replaceNestedConditionalWithGuardClauses.html) (Fowler); [RuboCop issue #15363](https://github.com/rubocop/rubocop/issues/15363) (Batsov, 2026); [Revisiting the Debate](https://www.cs.ubc.ca/~rtholmes/papers/emse_2022_chowdhury_preprint.pdf) (Chowdhury et al., 2022: nesting depth predicts change-proneness better for small methods) · dossier: complexity-metrics T03-F05; code-smells-evidence T27-F13

### CX-11 — Length is a reason to look, not to split
- **Rule:** Review functions above the project's limit, or above 60 logical lines where none is set (the 60-line trigger is a grade C convention, metric-thresholds G208-F16, downgraded, as in CX-04; tool triggers cluster at 40-60). Propose a split only when length comes with nesting above 3, CC above 10 or mixed levels of abstraction; leave long flat sequences and single simple switches whole, with section comments at most. Quote the 24-SLOC figure only as the 70% code-volume quantile of 785,606 methods in 49 Java OSS projects, never as a limit for other languages.
- **Detect:** `lizard -L 60 -w` or the lizard CSV sorted by NLOC; ESLint `max-lines-per-function` with `skipBlankLines`/`skipComments` true (both default false); Ruff PLR0915; Clippy `too_many_lines`; golangci-lint `funlen`; PMD NcssCount; clang-tidy `readability-function-size` `LineThreshold`; then check CX-01 and CX-10 before proposing.
- **Not when:** Scope of the 24-SLOC study: small-vs-medium effects on change-proneness were mostly medium or large (for #revisions, medium in 55.1% of projects, large in 34.69%), but on bug-proneness negligible (38.78%) or small (57.14%); decomposed method groups did better in 84 of 115 comparisons (73%) across five indicators, all with negligible or small effects. A controlled decomposition experiment was inconclusive. Extraction traps: closure capture, `this` binding, early return and `break`/`continue`, exception types, stack traces, defer/finally/RAII scope.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [Maintainable method size in Java (MSR 2022)](https://www.cs.ubc.ca/~rtholmes/papers/msr_2022_chowdhury.pdf) (Chowdhury, Uddin, Holmes, 2022); [same paper on arXiv](https://arxiv.org/pdf/2205.01842) (2022); [Google C++ style: write short functions](https://google.github.io/styleguide/cppguide.html) (Google: about 40 lines, no hard limit); [Linux kernel coding style](https://www.kernel.org/doc/html/latest/process/coding-style.html) (Linux kernel); [Comprehensibility of functional decomposition (ICPC 2024)](https://juholeinonen.com/assets/pdf/tempero2024comprehensibility.pdf) (Tempero et al., 2024) · dossier: complexity-metrics T03-F06, T03-F07; metric-thresholds G208-F16, G208-F04

### CX-12 — Extract only deep functions
- **Rule:** Before proposing an extraction, apply the two-sided test: a reader of the parent must not need the child's body, and a reader of the child must not need the parent's state. Extract only blocks with a nameable intent ("what", not "how"), keep branching in the parent and move non-branching work into leaves. Stop when the new function's interface (parameters, flags, returned tuple) is as complex as the code it hides.
- **Detect:** For each proposed extraction check that every new function has a "what" name, takes no more than about 4 parameters threaded only from the caller, needs none of the caller's locals or ordering assumptions, and that parent plus children did not gain total cognitive complexity.
- **Not when:** Martin prefers to err towards decomposition and the kernel style recommends helper functions for complex code; no controlled experiment compares tiny and deep decompositions. Developers asked to decompose the same code extracted 3 to 10 functions covering 37-95% of it, so there is no single correct split.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** C
- **Source:** [APOSD vs Clean Code](https://github.com/johnousterhout/aposd-vs-clean-code/blob/main/README.md) (Ousterhout & Martin, 2024-2025: both agree over-decomposition exists); [Philosophy of Software Design notes](https://sive.rs/book/PoSD) (Sivers on Ousterhout); [FunctionLength](https://martinfowler.com/bliki/FunctionLength.html) (Fowler, 2016); [TIGER_STYLE](https://raw.githubusercontent.com/tigerbeetle/tigerbeetle/main/docs/TIGER_STYLE.md) (TigerBeetle, 2026); [How developers extract functions](https://arxiv.org/abs/2209.01098) (Braver & Feitelson, 2022 preprint) · dossier: design-simplicity T05-F03; code-smells-evidence T27-F13; metric-thresholds G208-F16; complexity-metrics T03-F07

### CX-13 — Inline shallow single-caller helpers and entangled methods
- **Rule:** Propose inlining a non-exported function when it has one caller and its body is no clearer than its name, or when understanding it requires reading its caller (entangled). Where methods pass data through a member field that one sets and another reads, merge them or turn the field into explicit parameters and return values, preferring pure functions.
- **Detect:** Occurrences via `rg -w -o '<name>' src | wc -l` (2 means definition plus one call; `rg -c` counts per file) or find-references; flag one call site with 3 or fewer statements, chains of 3 or more one-line wrapper hops, helpers with 4 or more parameters that were all the caller's locals, boolean flag parameters, names like `doStep2`, `handleRest`, `processPart` (heuristics unvalidated). Hidden state: PMD SingularField; fields written in one method and read only by the next; `if (!this.initialized)` guards and "must call X first" comments.
- **Not when:** Named helpers kept as test seams; builders, parsers, state machines and iterators that keep state by design; exported surface (CX-20). Traps: overrides, mocks or spies that target the helper, recursion, reflection, serialization and framework hooks that call by name; stack frames and log context names change.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** C
- **Source:** [APOSD vs Clean Code](https://github.com/johnousterhout/aposd-vs-clean-code/blob/main/README.md) (Ousterhout & Martin, 2024-2025: entangled methods; Martin "struggled with the names and structure" of his own example); [It's probably time to stop recommending Clean Code](https://qntm.org/clean) (qntm, 2020: fields used as hidden parameters); [Inline Function](https://refactoring.com/catalog/inlineFunction.html) (Fowler); [John Carmack on inlined code](http://number-none.com/blow/john_carmack_on_inlined_code.html) (Carmack, 2007 with 2014 preface); [PMD Java design rules](https://pmd.github.io/pmd/pmd_rules_java_design.html) (PMD, 2026) · dossier: complexity-metrics T03-F07; design-simplicity T05-F04

### CX-14 — Check each score-lowering rewrite for its semantic trap
- **Rule:** Treat flattening, if-chain to switch or lookup, named boolean sub-conditions and `??`/`?.` as rewrites that lower the cognitive score by construction but are not shown to lower comprehension effort for a given function. Propose one only after checking its trap.
- **Detect:** clang-tidy `readability-function-cognitive-complexity` (DescribeBasicIncrements on by default) and eslint-plugin-sonarjs list each increment; Ruff PLR0916 (preview) or Pylint R0916; Checkstyle BooleanExpressionComplexity; ast-grep `if ($X === $A) { $$$ } else if ($X === $B) { $$$ }` for chains on one value.
- **Not when:** Traps: `a || b` to `a ?? b` changes results for `0`, `''`, `false`, `NaN`; `?.` turns a crash into a silent `undefined`; hoisting `x != null && x.f()` into a variable loses short-circuiting; an if-chain turned switch changes comparison semantics and risks fallthrough; a JS `switch` has no exhaustiveness check where a TS discriminated union with `never` does; a lookup table can hide control flow from type checkers. Python has neither `??` nor `?.`.
- **Tier:** T1 · **Class:** structural · **Fix risk:** high · **Grade:** C
- **Source:** [Cognitive Complexity white paper v1.7](https://www.sonarsource.com/docs/CognitiveComplexity.pdf) (SonarSource, 2023); [Replace nested conditional with guard clauses](https://refactoring.com/catalog/replaceNestedConditionalWithGuardClauses.html) (Fowler); [The Grug Brained Developer](https://grugbrain.dev/) (Gross); [Ruff PLR0916](https://docs.astral.sh/ruff/rules/too-many-boolean-expressions/) (Astral, 2026) · dossier: complexity-metrics T03-F15

### CX-15 — No branch coverage, no complexity refactor
- **Rule:** Before proposing a refactor of a complex function, check its branch coverage. If coverage is missing, label the candidate "needs characterization tests before refactor", or leave the function unchanged and report it. One exception: for Extract Function on a large deterministic function, a byte-identical differential over inputs generated through the public API (protocol-change PC-15) stands in for branch coverage, one extraction per commit (PC-17; eval-v2-calibration E02-F06).
- **Detect:** Per-function branch coverage (Vitest v8/istanbul, `pytest --cov --cov-branch`, JaCoCo, cargo llvm-cov; `go test -coverprofile` is statement-only) joined with lizard CCN; rank by CRAP = CCN² × (1 − cov)³ + CCN (no CRAP cut-off is sourced).
- **Not when:** Coverage does not prove behaviour is preserved when assertions are weak; characterization tests can freeze existing bugs, so record suspicious behaviour instead of fixing it. On hot paths add a benchmark gate (CX-16).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [NIST SP 500-235 §2](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication500-235.pdf) (NIST, 1996); [This code is C.R.A.P.](https://www.artima.com/weblogs/viewpost.jsp?thread=210575) (Savoia, 2007); [Field study of refactoring challenges (FSE 2012)](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/kim-fse-2012.pdf) (Kim et al.: 77% of 328 Microsoft engineers see regression risk); [Refactoring and regression testing (ICSM 2012)](https://doi.org/10.1109/icsm.2012.6405293) (Rachatasumrit & Kim: 22% of refactored methods and fields covered, 3 Java projects); [CA1502](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1502) (Microsoft, 2026) · dossier: complexity-metrics T03-F13; metric-thresholds G208-F19; code-smells-evidence T27-F18; eval-v2-calibration E02-F06

### CX-16 — Keep the less abstract version in measured hot paths
- **Rule:** In code that a profile or benchmark shows is hot, do not propose replacing switch or table dispatch with polymorphism, splitting a single-pass early-exit loop into several passes, or adding per-element indirection unless before-and-after measurements show the change is neutral. Performance is not a reason to keep complexity in cold code.
- **Detect:** Existing profiler output or benchmark files (perf, py-spy, `node --cpu-prof`, JFR); in proposals touching hot functions, flag early-exit loops turned into passes, switch or table dispatch turned into virtual dispatch, per-item allocations or closures; require hyperfine, JMH, pytest-benchmark or vitest bench runs. The "above about 5% of CPU" hot cut-off is unsourced.
- **Not when:** Muratori's numbers come from one author's C++ toy microbenchmark; in the Ousterhout-Martin exchange a still-decomposed version became faster once measured (440 ms vs 561 ms for a million primes), so the lesson is "measure", not "decomposition is slow". IO-bound handlers are rarely affected.
- **Tier:** T1 · **Class:** structural · **Fix risk:** high · **Grade:** C
- **Source:** ["Clean" Code, Horrible Performance](https://www.computerenhance.com/p/clean-code-horrible-performance) (Muratori, 2023: switch about 1.5x faster than virtual dispatch, table about 10x); [APOSD vs Clean Code](https://github.com/johnousterhout/aposd-vs-clean-code) (2025: splitting an early-exit loop gave a 3-4x slowdown); [Clean Code Q&A](https://github.com/cmuratori/misc/blob/main/cleancodeqa.md) (Muratori & Martin, 2023) · dossier: design-simplicity T05-F13; metric-thresholds G208-F19; complexity-metrics T03-F04

### CX-17 — Inline pass-through methods and variables in internal code
- **Rule:** Treat as a pass-through a function that only forwards near-identical arguments to one callee and adds no validation, translation, policy, error mapping, logging, auth, transaction, retry or higher-level name; in non-exported code, propose inlining it into its callers. Propose removing pass-through variables (parameters threaded unchanged through functions that never use them) by giving the value to the component that uses it.
- **Detect:** ESLint `no-useless-constructor` (typescript-eslint variant for TS), Pylint W0246 `useless-parent-delegation`, PMD UselessOverridingMethod; ast-grep `function $F($$$P) { return $G($$$A); }`, `$M($$$P) { return this.$D.$G($$$A); }`, Python `def $F($$$P):\n    return $G($$$A)`; confirm by hand that the arguments are essentially the parameters and that no decorator or annotation adds behaviour.
- **Not when:** Dispatchers; deliberate adapters, facades at process or IO boundaries, compatibility shims and framework-required wrappers; exported surface (CX-20). A context object introduced for pass-through variables can become a hidden global dependency. Hide Delegate and PMD LawOfDemeter pull towards delegation, so this rule stays at function level; class-level Middle Man is CX-29.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Philosophy of Software Design notes](https://sive.rs/book/PoSD) (Sivers on Ousterhout); [Modular design, CS 190](https://web.stanford.edu/~ouster/cgi-bin/cs190-spring16/lecture.php?topic=modularDesign) (Ousterhout, 2016); [Refactoring ch.3: Lazy Element](https://www.informit.com/articles/article.aspx?p=2952392&seqNum=14) (Fowler & Beck, 2018); [useless-parent-delegation](https://pylint.readthedocs.io/en/stable/user_guide/messages/warning/useless-parent-delegation.html) (Pylint 4.0.9); [no-useless-constructor](https://eslint.org/docs/latest/rules/no-useless-constructor) (ESLint) · dossier: design-simplicity T05-F01

### CX-18 — Unwind wrong abstractions that accreted flags
- **Rule:** When a shared function has accumulated flag or mode parameters and each caller passes fixed literals that select a disjoint subset of its branches, propose inlining it back into each caller, constant-folding the flags so only that caller's branches remain, and re-extracting only what is truly common. Do not introduce a new shared abstraction during hardening for fewer than about three real, stable uses or without a clear one-sentence name (both rules of thumb, not validated).
- **Detect:** SonarJava S2301; literal flags grouped by callee (`rg -n '\((.*,\s*)?(true|false|null)\s*[,)]'`); bodies that are mostly `if (flag) … else …`; `git log -L :funcName:path` showing repeated "add option for X" commits; parameters every caller passes with the same value.
- **Not when:** Flags that encode real variants of one concept (Prechelt et al. found a Decorator version easier to extend but more error-prone to configure than a flag version); Carmack consolidates work "perhaps with flags" to reduce state bugs; duplicated copies can drift and break together. Inlining raises LOC and can trigger duplication detectors.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** C
- **Source:** [The Wrong Abstraction](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction) (Metz, 2016); [AHA Programming](https://kentcdodds.com/blog/aha-programming) (Dodds, 2020); [Eliminate YAGNI smells](https://testing.googleblog.com/2017/08/code-health-eliminate-yagni-smells.html) (Eaddy, Google, 2017); [Rule of Three](https://understandlegacycode.com/blog/refactoring-rule-of-three/) (Carlo); [Design patterns vs simpler solutions](https://page.mi.fu-berlin.de/prechelt/Biblio/patmain_tse2001.pdf) (Prechelt et al., TSE 2001); [HN 48620623](https://news.ycombinator.com/item?id=48620623) (2026: a duplicated query broke in hundreds of places) · dossier: design-simplicity T05-F05, T05-F06; code-smells-evidence T27-F07

### CX-19 — Remove speculative generality only where nothing depends on it
- **Rule:** In non-exported code, propose removing interfaces or abstract bases with exactly one implementation and no process, IO, plugin or test-double role; hooks and plugin points nothing uses; parameters always passed the same value; and members that could be private. In Go, define interfaces on the consumer side and only once a real use exists. Report code used only by tests instead of removing it, because removal means deleting tests.
- **Detect:** Implementer counts (`rg -c 'implements X\b|extends X\b|: X\b'`, find-implementations); abstract classes with fewer than 3 children (Palomba candidate rule); symbols referenced only from test paths; the same literal at every call site; IDE "can be private"; empty template methods and no-op callbacks never overridden.
- **Not when:** DI containers, mocking frameworks, reflection, plugin loaders and serialization that name the type (runtime wiring the compiler does not see); exported surface (CX-20). Evidence is mixed: Prechelt et al. (29 professional engineers, nine maintenance tasks) found mostly positive effects from pattern flexibility, one despite superfluous Decorator flexibility (stated in the authors' preprint abstract), and advise the pattern "unless there is a clear reason to prefer the simpler solution"; top-voted SE answers favour interfaces for mocks and at subsystem boundaries; its removal carried a high change-proneness benefit (limited for faults) in Palomba et al. 2018, while Speculative Generality "reduced faults only in Eclipse" in one of three systems (Hall et al. 2014).
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [Eliminate YAGNI smells](https://testing.googleblog.com/2017/08/code-health-eliminate-yagni-smells.html) (Eaddy, Google, 2017); [Go Code Review Comments: interfaces](https://go.dev/wiki/CodeReviewComments) (Go Authors); [Go style best practices](https://google.github.io/styleguide/go/best-practices) (Google); [Yagni](https://martinfowler.com/bliki/Yagni.html) (Fowler, 2015); [Design patterns vs simpler solutions](https://page.mi.fu-berlin.de/prechelt/Biblio/patmain_tse2001.pdf) (Prechelt et al., TSE 2001, author preprint); [Diffuseness and impact of code smells](https://fpalomba.github.io/pdf/Journals/J9.pdf) (Palomba et al., EMSE 2018); [Some code smells have a significant but small effect on faults](https://eprints.lancs.ac.uk/id/eprint/127419/1/Tosem_code_smells.pdf) (Hall et al., TOSEM 2014) · dossier: design-simplicity T05-F07; code-smells-evidence T27-F05, T27-F11; complexity-metrics T03-F04

### CX-20 — Never restructure a published boundary
- **Rule:** Restrict inlining, interface removal, signature changes and module moves to non-exported, internal code. At published boundaries (library or SDK exports, HTTP/RPC/GraphQL APIs, CLI flags, config keys, DB schemas, event payloads), report the design finding with a deprecation path and propose no edit.
- **Detect:** List the surface first: `package.json` `exports`/`main` and barrel files; Python `__all__`; capitalised identifiers in non-internal Go packages; public types in published Java/C# artefacts; OpenAPI and proto files, CLI `--help`, config schemas, migrations.
- **Not when:** In a single deployable with no outside consumers "exported" often is not "public": ask the owner (`--interactive`; in autonomous mode list the question under Needs your decision, reporting RP-07), since the compiler and tests can prove there is no other consumer. Excess caution preserves speculative abstractions (CX-19). Hyrum's Law is an observation, not a study.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** B
- **Source:** [Hyrum's Law](https://www.hyrumslaw.com/) (Wright); [Go style best practices: interface ownership](https://google.github.io/styleguide/go/best-practices) (Google); [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) (Go Authors) · dossier: design-simplicity T05-F16; metric-thresholds G208-F15

### CX-21 — Report dependency and co-change anti-patterns; do not restructure
- **Rule:** Report module-level anti-patterns in this order: Unstable Interface and Crossing first, then modularity violations (files that change together with no structural dependency), then dependency cycles. Propose each fix case by case with its risks; never restructure modules during hardening.
- **Detect:** dependency-cruiser `circular` rule (JS/TS); import-linter contracts via `lint-imports` (Python); ArchUnit `slices()…beFreeOfCycles()` (JVM); Go forbids import cycles, so use package co-change; code-maat `-a coupling` on a git2 log (`--min-coupling 30` is a tool default, not validated); flag coupled pairs with no import edge, high fan-in files in the top change decile, files with both high fan-in and fan-out; shared literals (keys, column names, formats) in two or more modules show leaked design decisions.
- **Not when:** The evidence is correlational and from Java/C# only; no study shows that breaking these structures reduces defects, and no criterion separates harmful from harmless cycles. Breaking an import cycle in JS/TS, Python or Ruby can change module initialisation order (an engineering caution the dossier marks unsourced). Co-change needs history, so it is weak on young repositories.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [Architecture anti-patterns](https://www.cs.drexel.edu/~yc349/papers/2019/tse2019.pdf) (Mo et al., IEEE TSE 2021: 19 projects; anti-pattern files more bug- and change-prone, up to about 120x bug-fix frequency in Cassandra; Package Cycle has smaller impact); [Circular dependencies and change-proneness](https://hal.science/hal-01203525v1) (Oyetoyan et al., SANER 2015); [On the criteria for decomposing systems into modules](https://www.win.tue.nl/~wstomv/edu/2ip30/references/criteria_for_modularization.pdf) (Parnas, 1972); [dependency-cruiser rules reference](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md) (sverweij, 2026); [Code Maat](https://github.com/adamtornhill/code-maat) (Tornhill) · dossier: design-simplicity T05-F10, T05-F08

### CX-22 — Split large classes on cohesion or co-change, never on size
- **Rule:** Report a large class or module as a split candidate only when it shows low cohesion (disconnected method-field clusters), methods that mostly use another class's data, or separate co-change clusters inside the file; never on line or method count alone. Leave the split itself to the owner.
- **Detect:** PMD GodClass (WMC ≥ 47, ATFD > 5, TCC < 1/3, a combination rather than raw size); elsewhere map each method to the fields it reads and writes and look for disconnected clusters; confirm with in-file co-change (commits touching method group A rarely touch group B). PMD TooManyMethods, NcssCount and Pylint R0904 are triage only.
- **Not when:** Evidence on size conflicts: smelly classes were riskier across 30 projects (Palomba et al.), God/Brain classes were less change- and defect-prone per line once normalised by size in 3 systems (Olbrich et al.), and file-level redistribution may be counterproductive (Yamashita et al.). Splitting changes object identity, construction, serialization and DI wiring. Ousterhout's 200-2000 lines per class is a teaching heuristic.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [Are all code smells harmful?](https://doi.org/10.1109/icsm.2010.5609564) (Olbrich et al., ICSM 2010); [PMD GodClassRule](https://github.com/pmd/pmd/blob/main/pmd-java/src/main/java/net/sourceforge/pmd/lang/java/rule/design/GodClassRule.java) (PMD, 2026); [Modular design, CS 190](https://web.stanford.edu/~ouster/cgi-bin/cs190-spring16/lecture.php?topic=modularDesign) (Ousterhout, 2016); [Thresholds for size and complexity metrics](https://posl.ait.kyushu-u.ac.jp/~kamei/publications/Yamashita_QRS2016.pdf) (Yamashita et al., 2016) · dossier: design-simplicity T05-F17; metric-thresholds G208-F03; code-smells-evidence T27-F03

### CX-23 — Rank by distinct co-located smell families
- **Rule:** Count distinct smell families (size, complexity, coupling/encapsulation, duplication, hierarchy) per class or file, not raw violation counts, and shortlist those with at least two; count smells in tightly coupled classes as co-located. Report single-smell classes as information unless they are hotspots (CX-24).
- **Detect:** Run at least two detectors with JSON or SARIF output (PMD, SonarQube export, ESLint JSON, Ruff or Pylint, jscpd), map rule ids to families, count families per file, and use the import or call graph to find coupled smelly pairs.
- **Not when:** Co-occurrence correlates with size (no smell effect after adjusting for size and changes, Sjøberg et al. 2013); the count depends on which detectors ran; classes with several smell types are a minority (3-9% in Tufano et al.), so expect a short list.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Diffuseness and impact of code smells](https://fpalomba.github.io/pdf/Journals/J9.pdf) (Palomba et al., EMSE 2018: 395 releases of 30 Java OSS projects; median changes 12, 22, 32, 54 for 0-3 smells, large effects except 1 vs 2 smells (medium); median faults 3 to 12 with smaller effects, 1 vs 2 small and 2 vs 3 medium; the change link held under size control, OR 4.46 vs 1.7 for size); [Spaghetti Code and Blob on comprehension](https://arxiv.org/abs/2009.02438) (Politowski et al., 2020: 133 participants; two occurrences hurt, one did not); [Inter-smell relations](https://doi.org/10.1109/icse.2013.6606614) (Yamashita & Moonen, ICSE 2013) · dossier: code-smells-evidence T27-F01

### CX-24 — Weight by change activity and respect the fence
- **Rule:** Prioritise smelly or complex code that keeps changing (hotspots, co-change clusters) and leave smelly-but-stable working code alone unless planned work touches it. Before removing or reshaping code whose purpose is unclear, find out why it exists.
- **Detect:** Churn and fix counts from `.harden/rank.json` when history is sufficient; relative churn (added plus deleted lines from `git log --numstat` over current LOC); intersect with CX-23; for unclear code `git log -S'<symbol>' --oneline`, `git blame -w -C`, linked issues, and which tests fail when it is removed.
- **Not when:** A fresh or squashed history has little churn and past churn may reflect the initial build: rank by metrics and take the modules the owner will extend from prioritization step 3. The CodeScene hotspot figures (1.2% of code, 12.5% of effort, 45% of fixed bugs) are a single vendor example.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Quantifying the effect of code smells on maintenance effort](https://doi.org/10.1109/TSE.2012.89) (Sjøberg et al., TSE 2013: 6 developers, 4 equivalent Java systems; size and changes explained almost all effort, the 12 smells did not); [Relative code churn](https://doi.org/10.1145/1062455.1062514) (Nagappan & Ball, ICSE 2005: 89% accuracy, Windows Server 2003); [Coupling and cohesion](https://newsletter.kentbeck.com/p/coupling-and-cohesion) (Beck, 2024); [Mining metrics to predict component failures](https://www.st.cs.uni-saarland.de/publications/files/nagappan-icse-2006.pdf) (Nagappan et al., 2006); [CodeScene hotspots](https://codescene.io/docs/guides/technical/hotspots.html) (CodeScene, vendor) · dossier: code-smells-evidence T27-F02; design-simplicity T05-F11; complexity-metrics T03-F09

### CX-25 — Size and complexity smells come first
- **Rule:** Among smells, put Long Method, Complex Method or Class, God/Brain Class and Spaghetti Code first, and propose reducing them in hotspots with small behaviour-preserving method-level steps (CX-10 to CX-13). Route class splits through CX-22.
- **Detect:** PMD GodClass, CognitiveComplexity (15), CyclomaticComplexity (method 10, class 80), NcssCount (60); SonarJava S3776 (15), S138 (75 lines), S134 (nesting 3); ESLint, Pylint and Ruff per CX-04; Palomba's Spaghetti Code pre-filter: a class with at least two long methods interacting through calls or shared fields.
- **Not when:** Parsers, state machines, interpreter loops and generated code are legitimately long (Palomba's worst Long Method release was Apache Derby's SQL parser package). Removal carried a high change-proneness benefit but only a limited fault benefit (CX-26).
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [Diffuseness and impact of code smells](https://fpalomba.github.io/pdf/Journals/J9.pdf) (Palomba et al., EMSE 2018: Long Method in 84% of 395 releases, 28 per KLOC; God Class median 46 vs 12 changes); [Antipatterns and change- and fault-proneness](https://link.springer.com/article/10.1007/s10664-011-9171-y) (Khomh et al., EMSE 2012: 54 releases of 4 systems; size alone does not explain the odds); [Do they really smell bad?](https://fpalomba.github.io/pdf/Conferencs/C3.pdf) (Palomba et al., ICSME 2014: developers rate these most severe) · dossier: code-smells-evidence T27-F03

### CX-26 — Never justify a refactor by expected defect reduction
- **Rule:** Present complexity and smell refactorings as lowering change cost, never as reducing defects. Where a smelly or complex class has a bug-fix history, recommend adding or strengthening tests there before touching it.
- **Detect:** Intersect the smell shortlist with bug-fix commits (`git log -i -E --grep='fix|bug|defect' --name-only`, or rank.json fix counts) and read branch coverage for those files.
- **Not when:** Higher fault odds for smelly classes remain an association (Khomh et al. 2012; Palomba RQ2); in JavaScript, smell-free files had 65% lower fault hazard, also an association. SZZ and commit-message fault data are noisy.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Diffuseness and impact of code smells](https://fpalomba.github.io/pdf/Journals/J9.pdf) (Palomba et al., 2018: no substantial fault difference in the same classes with and without the smell, "a co-occurring phenomenon"); [Some code smells have a significant but small effect on faults](https://doi.org/10.1145/2629648) (Hall et al., TOSEM 2014: under 10%, sometimes negative); [Some SonarQube issues have a significant but small effect](https://arxiv.org/abs/1908.11590) (Lenarduzzi et al., JSS 2020: 33 Apache projects, no fault difference between clean and dirty classes) · dossier: code-smells-evidence T27-F04

### CX-27 — Do not rank by analyser severity labels
- **Rule:** Never rank or propose fixes by an analyser's severity or "bug" label. Keep a smell candidate only when two detectors agree or a written justification names the concrete change the smell makes harder.
- **Detect:** Pair detectors (PMD with SonarQube, Ruff with Pylint, DesigniteJava with PMD); ignore severity fields and use the CX-23 and CX-24 ordering.
- **Not when:** The fault studies rely on noisy SZZ, and "bug" rules may prevent faults that never reached a tracker.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Are SonarQube rules inducing bugs?](https://arxiv.org/abs/1907.00376) (Lenarduzzi et al., SANER 2020: 21 projects, 202 rules; 3 of 57 "bug" rules fault-prone, AUC 50.94%, severity unrelated to fault-proneness); [Automatic detection of bad smells](http://www.jot.fm/issues/issue_2012_08/article5.pdf) (Arcelli Fontana et al., 2012: 4 tools on 1 system disagree except for God Class); [Systematic review on the code smell effect](https://doi.org/10.1016/j.jss.2018.07.035) (Santos et al., 2018: low human agreement) · dossier: code-smells-evidence T27-F16

### CX-28 — Feature Envy and hierarchy smells need measured evidence; never restructure a hierarchy
- **Rule:** Report Feature Envy only when access counts show a method uses another type's data and behaviour more than its own, and propose a move only for methods in hotspots, with a one-line justification naming the change the smell makes harder. Report Refused Bequest and deep or broken hierarchies with their override counts and refusals. Never restructure a hierarchy during hardening (pull up, push down, extract or collapse a superclass): the report may name the restructuring for the owner, with the tests it needs first. Fat interfaces, message chains, language-model verdicts and inheritance depth are CX-32.
- **Detect:** Feature Envy: JDeodorant, or `other.x`/`other.m()` vs `this`/`self` access counts (more than half to one other type, little of the method's own state used; Palomba candidate rule: more calls to another class than to its own). Refused Bequest: overriding more than half the inherited methods, `UnsupportedOperationException|raise NotImplementedError`, empty overrides. Deep or broken hierarchies: DesigniteJava Rebellious, Broken and Deep Hierarchy.
- **Not when:** Strategy, Visitor, mappers and orchestrators envy other classes by design; framework-mandated base classes and test doubles refuse behaviour by design. Moving a method changes dispatch, visibility and serialization hooks. Evidence on Refused Bequest conflicts: it was associated with decreased effort (Sjøberg et al. 2013) but with more changes while present (median 43 vs 26, Palomba et al. 2018). Language-model detection of both smells is weak (Souza et al. 2026 preprint: Feature Envy F1 0.11-0.71 by model against 0.62-0.63 for static tools; Refused Bequest F1 below 0.40 for all four models).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** B
- **Source:** [Diffuseness and impact of code smells](https://fpalomba.github.io/pdf/Journals/J9.pdf) (Palomba et al., 2018: Feature Envy fault-proneness x8 while present); [Code smells and effort](https://ir.cwi.nl/pub/25393/Soh-SANER16_Smells-Effort.pdf) (Soh et al., SANER 2016: Feature Envy affects searching, editing, navigating and reading effort); [When does a refactoring induce bugs?](https://doi.org/10.1109/scam.2012.20) (Bavota et al., SCAM 2012: hierarchy refactorings "tend to induce faults very frequently", 3 Java systems); [Quantifying the effect of code smells on maintenance effort](https://doi.org/10.1109/TSE.2012.89) (Sjøberg et al., TSE 2013); [Beyond strict rules: LLMs for code smell detection](https://arxiv.org/abs/2601.09873) (Souza et al., 2026 preprint: 76-developer ground truth, 30 Java projects) · dossier: code-smells-evidence T27-F08, T27-F11

### CX-29 — Low-evidence smells are report-only
- **Rule:** Report, never bulk-fix, Class Data Should Be Private, Middle Man (including adjacent layers that expose the same operations with the same signatures; this layer-folding clause is grade C, design-simplicity T05-F02, downgraded), Lazy Class, Switch Statements and Data Clumps; long parameter lists follow CX-30. Treat Inappropriate Intimacy and Speculative Generality as contested and judge them case by case in hotspots (CX-19).
- **Detect:** Middle Man: classes delegating more than half their methods (Palomba candidate rule, Fowler and Beck's "half the methods are delegating"); compare X-Service and X-Repository signatures for identical operations with no mapping, validation or transaction logic. Lazy Class: LOC below the project's first quartile. Class Data Should Be Private: public mutable fields.
- **Not when:** A thin layer can carry cross-cutting behaviour through annotations or decorators (transactions, auth, caching, metrics); ports-and-adapters teams keep thin ports on purpose; public mutable fields can matter for thread safety or security; Data Clumps affected editing effort in one study (Soh et al. 2016).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [Do they really smell bad?](https://fpalomba.github.io/pdf/Conferencs/C3.pdf) (Palomba et al., ICSME 2014: CDSBP, Middle Man, Long Parameter List, Lazy Class not perceived as problems); [Diffuseness and impact of code smells](https://fpalomba.github.io/pdf/Journals/J9.pdf) (Palomba et al., 2018: limited removal effect; removing Middle Man or Lazy Class is expected to increase change-proneness); [Some code smells have a small effect on faults](https://eprints.lancs.ac.uk/id/eprint/127419/1/Tosem_code_smells.pdf) (Hall et al., 2014: Switch Statements no fault effect in 3 systems); [Refactoring ch.3: Middle Man](https://www.informit.com/articles/article.aspx?p=2952392&seqNum=18) (Fowler & Beck, 2018) · dossier: code-smells-evidence T27-F05; design-simplicity T05-F02

### CX-30 — Parameter lists: report, do not reshape
- **Rule:** Trigger a parameter finding at 7 or more declared parameters (excluding `self`, `cls`, `this` and receivers; a destructured options object or dataclass counts as 1), and report the 5-6 band only when two or more adjacent parameters share a type or boolean flags select behaviour. Report the proposed options object, split-on-flag or grouping type; never change an exported signature as hardening.
- **Detect:** lizard PARAM; Ruff PLR0913/PLR0917 (stable); ESLint `max-params` 6 (fires at 7); Clippy `too-many-arguments-threshold = 6` (the default 7 is the maximum allowed, so it fires at 8) and `fn_params_excessive_bools` (pedantic); PMD ExcessiveParameterList; ast-grep for adjacent identical type annotations; positional literals via `rg -n "\w+\([^)]*,\s*(true|false)\s*[,)]"`.
- **Not when:** Framework-mandated signatures (callbacks, handlers, ORM hooks), data and DI constructors, external API bindings and math functions (x, y, z). Keyword or named arguments carry far less order risk. Raise the priority in JS/TS (1,484 surveyed developers rated long parameter lists serious, Saboury et al. 2017); Java developers did not perceive them as a problem and removal had a limited effect (Palomba 2014, 2018). An options object changes default semantics (explicit `undefined` vs a missing key) and lets a callee mutate the caller's object.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** C
- **Source:** [SIG Guidance for Producers v18.1](https://www.softwareimprovementgroup.com/wp-content/uploads/SIG-TUViT-Evaluation-Criteria-Trusted-Product-Maintainability.pdf) (SIG, 2026: same-typed parameters "can be accidentally supplied in the wrong order"; at most 0.9% of code in units with 7 or more parameters); [Clippy conf.rs](https://raw.githubusercontent.com/rust-lang/rust-clippy/master/clippy_config/src/conf.rs) (Clippy, 2026); [ESLint max-params](https://eslint.org/docs/latest/rules/max-params) (ESLint, 2026: default 3); [PMD ExcessiveParameterList](https://pmd.github.io/pmd/pmd_rules_java_design.html) (PMD, 2026: default 10); [Sandi Metz' rules for developers](https://thoughtbot.com/blog/sandi-metz-rules-for-developers) (thoughtbot, 2013: four) · dossier: metric-thresholds G208-F15; complexity-metrics T03-F08; code-smells-evidence T27-F05, T27-F17

### CX-31 — JavaScript/TypeScript: re-assignment smells first
- **Rule:** In JavaScript and TypeScript, rank variable re-assignment and assignment inside conditionals above other smells, then nested callbacks and long parameter lists. Cite the ESLint rule as the detection method instead of restating it.
- **Detect:** ESLint `no-cond-assign` (`"always"`; the default is `"except-parens"`), `no-param-reassign` (not in recommended), `prefer-const`, `max-nested-callbacks` (default 10; 3-4 is a judgement call, not from the study), `max-params`; review `let` variables assigned in several branches.
- **Not when:** The evidence is five callback-era Node.js projects and shows association only. Converting callbacks to async/await changes error propagation and timing, so it is behavioural and outside this rule.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Code smells in JavaScript projects](https://doi.org/10.1109/saner.2017.7884630) (Saboury et al., SANER 2017: 537 releases of 5 Node.js projects; smell-free files 65% lower fault hazard; re-assignment and assignment-in-conditional had the highest hazard; 1,484 developers surveyed); [ESLint rules source](https://github.com/eslint/eslint/tree/main/lib/rules) (ESLint, 2026) · dossier: code-smells-evidence T27-F17

### CX-32 — Fat interfaces, message chains and inheritance depth: measured evidence only, never a model verdict
- **Rule:** Report ISP violations (fat interfaces) and long Message Chains only with concrete evidence: caller usage clusters, chains across different domain types, co-change from git. For every context-dependent smell (Feature Envy, Refused Bequest, Shotgun Surgery, ISP violation) a language-model verdict alone is not evidence: drop a candidate that carries no metric value, caller or callee count or co-change. Report single-subclass bases and inheritance used only for code reuse as collapse or delegation candidates for the owner (no restructuring during hardening, CX-28; internal single-implementation interfaces and abstract bases with no other role follow CX-19), and never add inheritance depth.
- **Detect:** ISP: start from types with many public methods (Pylint R0904, PMD TooManyMethods), list the methods each caller uses, and flag 2 or more caller clusters with little overlap. Message Chains: PMD LawOfDemeter (its docs warn of many false positives) or `rg -n '(\.[A-Za-z_]\w*\([^()]*\)){4,}'` (Palomba's candidate rule: chains longer than three), then drop fluent, builder, stream and ORM chains. Hierarchy: direct-subclass count per base (1 makes a Collapse Hierarchy candidate), protected fields written by subclasses, PMD UselessOverridingMethod; DIT above 3 for triage only. Shotgun Surgery: file-pair co-occurrence in `git log --format=%H --name-only`.
- **Not when:** Facades are broad by design, and splitting a public interface is a breaking change (CX-20). Hide Delegate adds forwarding methods that can create Middle Man (CX-29); DTOs and config trees are naturally navigated. Collapsing a hierarchy can break overrides, super calls, instanceof checks, serialisation discriminators and ORM inheritance mappings; framework-mandated hierarchies cannot be flattened. The evidence is thin: the ISP link comes from one dataset (6 developers, 4 systems); removing Message Chains had only a Limited fault effect (Palomba et al. 2018); the model-verdict clause rests on two preprints with model-specific results; on depth, a 3-level program was easier to maintain than a 0-level one (Daly et al. 1996, as reported by Prechelt et al.), and depth as such predicts little and the number of relevant methods more (Prechelt et al., JSS 2003).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** C
- **Source:** [Assessing the capability of code smells to explain maintenance problems](https://link.springer.com/article/10.1007/s10664-013-9250-3) (Yamashita, EMSE 2014: ISP violation had the strongest link to maintenance problems); [Code smells and effort](https://ir.cwi.nl/pub/25393/Soh-SANER16_Smells-Effort.pdf) (Soh et al., SANER 2016); [Diffuseness and impact of code smells](https://fpalomba.github.io/pdf/Journals/J9.pdf) (Palomba et al., 2018: Message Chain in 13% of releases); [Some code smells have a significant but small effect on faults](https://doi.org/10.1145/2629648) (Hall et al., TOSEM 2014: Message Chains increased faults in two of three systems); [Beyond strict rules: LLMs for code smell detection](https://arxiv.org/abs/2601.09873) (Souza et al., 2026 preprint); [Investigating the smells of LLM generated code](https://arxiv.org/abs/2510.03029) (Paul, Zhu, Bayley, 2025 preprint); [Refactoring ch.3: Insider Trading](https://www.informit.com/articles/article.aspx?p=2952392&seqNum=19) (Fowler & Beck, 2018); [Eliminate YAGNI smells](https://testing.googleblog.com/2017/08/code-health-eliminate-yagni-smells.html) (Eaddy, Google, 2017); [Inheritance depth as a cost factor](http://page.mi.fu-berlin.de/prechelt/Biblio/inherit_jss2003.pdf) (Prechelt et al., JSS 2003) · dossier: code-smells-evidence T27-F09, T27-F10, T27-F20; design-simplicity T05-F14

## False-positive exclusions

- Code with intent markers (`do not (attempt to )?simplify`, `intentional`, `keep in sync`, `space shuttle`) or a justified suppression: record it as an accepted exception, as Kubernetes' pv_controller asks (dossier: code-smells-evidence T27-F14).
- Generated code (`@generated`, `do not edit`, `auto-generated`), vendored and third-party directories (T27-F14; metric-thresholds G208-F01).
- Code whose complexity mirrors the domain: parsers, protocol handlers, state machines, interpreter loops, kernel-style dispatch (T27-F14, T27-F03).
- Single flat dispatches under CX-06, and long flat sequential functions, which get section comments instead of splits (complexity-metrics T03-F04; design-simplicity T05-F03).
- Parameter counts forced by frameworks (callbacks, handlers, ORM hooks), DI constructors, external API bindings and math or geometry functions (G208-F15, T03-F08).
- Dispatchers, adapters, IO-boundary facades, compatibility shims and wrappers that add behaviour through annotations or decorators (T05-F01, T05-F02).
- Builders, parsers, state machines and iterators that keep state between calls (T05-F04).
- Fluent APIs, builders, streams, query builders, optional chaining over plain data, DTO and config trees (Message Chains, T27-F10).
- Strategy, Visitor, mappers and orchestrators (Feature Envy); framework base classes and test doubles (Refused Bequest) (T27-F08, T27-F11).
- Test code: report its metrics separately; test smells belong to the tests lens (G208-F01, T27-F19).
- Go functions whose excess CC is only flat `if err != nil` checks: downgrade to low-priority review, do not exclude (a policy choice, grade D; G208-F13).

## Evidence limits

- Almost all smell-harm evidence comes from Java open source of the 2000s-2010s; apart from clone studies (C#, Cobol), the only non-Java smell study covers five Node.js projects. Applying these tiers to TypeScript, Python, Go or Rust is extrapolation (code-smells-evidence).
- No randomised or causal study shows that removing a smell or lowering a metric reduces defects; the demonstrated benefit is lower change-proneness in the same class (T27-F04).
- No complexity, length or parameter threshold has been validated: the cognitive-complexity meta-analysis had almost no snippets above 15, and SIG recalibrates its bands every year (v17.0 to v18.1), so always name the version (T03-F03, G208-F18).
- Method-length evidence is one large Java study; the only controlled decomposition experiment was inconclusive; no experiment compares many tiny methods with fewer deep ones, and no validated automated measure of module depth exists, so CX-12, CX-13 and CX-17 rely on reading (T03-F06, T05 open questions).
- Complexity scores do not see algorithmic complexity: accidentally quadratic loops and regex catastrophic backtracking (the 27-minute Cloudflare outage of 2 July 2019) belong to the performance and security lenses (T03-F16, T03-F17).
- AI-heavy repositories: one vendor study (Sonar, 4,442 Java tasks per model, 2025) found mean CC of about 1.7-2.3 per function, complexity smells at 2.7-8.4% of smells and dead, unused or redundant code at 14.8-42.7%; keep absolute triggers and give dead-code and design review at least equal budget (G208-F17).
- Language-model smell detection is weak for context-dependent smells and varies by model (preprints); this lens's design judgements stay candidates until the verification stage confirms them (T27-F20).
- Several supporting studies are vendor-authored (CodeScene) or were read only as abstracts; Lavazza et al. (JSS 2023) on cognitive complexity could not be read; APOSD, Tidy First? and Refactoring were checked through notes and publisher excerpts (all four dossiers).
