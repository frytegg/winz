# Lens: AI Failure Modes

> Purpose: give extra review weight to the defect categories that studies measure as over-represented in AI-written code (verification gaming, invented or deprecated dependencies, escape hatches, swallowed errors, injection sinks, surplus volume, narration and shims), and prove each candidate on its own evidence, never on AI provenance.
> Read when: the codebase was written largely with AI assistants or coding agents (agent trailers or bot commits in `.harden/inventory.json`, agent config files such as `.mcp.json`, `.cursor/` or `.claude/` in the tree), or the owner asks for this lens.

## Contents

- Procedure
- Rules: provenance and the lens's own bias (AI-01 to AI-03); verification gaming (AI-04 to AI-08); dependencies, APIs and escape hatches (AI-09 to AI-11); error handling and defensive code (AI-12 to AI-14); security categories (AI-15 to AI-19); volume, duplication and residue (AI-20 to AI-23); comments, claims and shims (AI-24 to AI-26); vendor-only categories (AI-27, AI-28)
- False-positive exclusions
- Evidence limits

## Procedure

You are a fresh-context, read-only lens subagent with Read, Grep and Glob only (detection step 8). You detect and triage; the orchestrator runs commands, verifies, ranks and applies. You share the biases this lens hunts for (AI-03), so rely on tools and traces, not on your own restraint.

1. **Stay read-only; the orchestrator runs the commands.** You edit, stage, commit, format and run nothing. Every command this file names (linters, scanners, `git log`, registry lookups, mutation tools) is an orchestrator-run command, never in a fix, snapshot-update or install mode, whose raw output (SARIF or JSON where the tool supports it) is saved under `.harden/tools/`; you read those files and copy each tool version into `tool_versions`. A command with no output file is a gap for step 9, never a clean result. If you are the unseeded pass, you receive no tool output: work from the source and say so.
2. **Load inputs.** Read `.harden/inventory.json` (languages, manifests, lockfiles, agent trailers, history stats), `.harden/config.json` (scope, `test_globs`, `protected_globs`, `network`), `.harden/prescan.json`, `.harden/rank.json`, the baseline records in `.harden/gates/`, and the language file of each detected language. This lens names tools and rule ids only; the exact pinned, ephemeral commands and Windows notes live in the language files. Read the outputs of the project's own configured linters and type checkers first (the orchestrator runs them with the project's config, DT-03), and file their hits as `project:<tool>/<rule>`.
3. **Provenance only sets the order.** Read agent trailers and bot actors to decide where to look first (AI-02). Never put provenance in a candidate's evidence (AI-01).
4. **History pass (the orchestrator's git outputs).** Deleted test files, removed assertions, new skip or focus markers, mass snapshot regenerations and commits that touch src and tests together (AI-04); gate-config loosening (AI-08); suppression counts over time (AI-11); scratch files (AI-23); secrets in history (AI-18).
5. **Tool outputs by language family** (orchestrator-run, read from `.harden/tools/`):
   - JS/TS: typescript-eslint `no-explicit-any`, `ban-ts-comment`, `no-unsafe-*`, `no-deprecated`, `no-unnecessary-condition`; ESLint `no-empty`, `no-unused-vars` (`caughtErrors: "all"`), `no-unreachable`, `no-console`, `no-debugger`, `no-await-in-loop`, `complexity`, `max-lines-per-function`, `reportUnusedDisableDirectives`; `@eslint-community/eslint-plugin-eslint-comments` `require-description`, `no-unlimited-disable`; eslint-plugin-jest or `@vitest/eslint-plugin` `no-disabled-tests`, `no-focused-tests`, `expect-expect`; eslint-plugin-sonarjs `cognitive-complexity`; knip; CodeQL `js/xss`, `js/log-injection`, `js/insecure-randomness`; Semgrep `path-join-resolve-traversal`.
   - Python: Ruff `BLE001`, `S110`, `S112`, `E722`, `PGH003`, `PGH004`, `RUF100`, `ANN401`, `F401`, `F841`, `ARG`, `ERA001`, `T201`, `T203`, `FIX`, `TD`, `C901`, `PLR0911`-`PLR0915`, `S`; Pylint `W0718`, `undefined-variable`; Bandit `B311`, `B303`, `B304`; mypy `warn_unused_ignores`, `--warn-unreachable`, `--strict-equality`; pyright `reportUnnecessaryIsInstance`, `reportUnnecessaryComparison`; vulture; radon; pytest `-rxXs` with `strict_xfail` and `-W error::DeprecationWarning`.
   - Rust: clippy `allow_attributes_without_reason`, `allow_attributes`, `dbg_macro`, `print_stdout`, `todo`, `unimplemented`; libtest `--list --ignored`.
   - Go: `errcheck -blank`, staticcheck `U1000`, deadcode, `go test -race`.
   - Any language: gitleaks (`git` and `dir`), Semgrep, CodeQL, SonarQube (`S1192`, `S3776`, `S1172`, `S125`), jscpd or PMD CPD, lizard, ast-grep, ripgrep; mutation tools (Stryker, mutmut, cargo-mutants, PIT) only in a scratch worktree; registry lookups (npm, PyPI JSON API, crates.io, Go proxy) only when `.harden/config.json` sets `"network": "allowed"` and the network is reachable (skill-design T31-F15: network checks only on explicit request, with their scope stated); otherwise record the gap in step 9.
6. **Manual sweeps no tool covers:** special-casing and fixture literals (AI-06), placeholders reachable in production (AI-07), fallback provenance traces (AI-13), entry-point inventory (AI-19), comment and claim queues (AI-24, AI-25), shims and their consumers (AI-26).
7. **Triage every hit** against the rule's "Not when" and the exclusions below. Classify error handlers as boundary, cleanup or swallow; trace fallbacks and sinks to their source. Heuristic grep or ast-grep hits never exceed `confidence: "needs_review"` here; verification raises narration comments and commented-out code (AI-24) through DT-27's deterministic check (eval-v1-calibration E01-F06).
8. **Return candidates as your final message:** JSON in the findings schema (`assets/findings.schema.json`), one per location, plus `files_read` (every file you read, with its line ranges); the orchestrator merges them into `.harden/candidates.json`. Per candidate: `lens: "ai-failure-modes"`; `rule_ref` = AI-NN or `project:<tool>/<rule>`; `file` repo-relative with forward slashes and `line` at `base_sha`; `class`, `tier` and `fix_risk` copied from the rule; `status: "candidate"`, `verified: false`; `confidence` from the evidence ladder (`tool_high_precision` only with a `tool` evidence item); `evidence[]` items of kind `tool` (command plus rule id), `git` (commit sha), `source` (file:line trace) or `test`. Never write a secret value anywhere; cite file:line, commit and scanner rule id.
9. **Record limits:** tools not run and why (network not allowed or unreachable for registry checks, no CodeQL database, languages without a tool), history depth scanned, and heuristic queues left unreviewed. Never report zero hits as "no AI failure modes".

## Rules

### AI-01 — Judge by defect category and evidence, never by AI authorship
- **Rule:** Never flag, rank up or dismiss code because AI wrote it or because it looks AI-written. Every candidate names a tool rule id or a concrete failing scenario at file:line. Use provenance only to choose where to look first (AI-02), and handle formatting or naming drift with the project's own formatter and lint autofix, not with manual rewrites.
- **Detect:** Before emitting, reject any candidate whose only justification is provenance ("looks generated", a co-author trailer). Estimate provenance from `git log --format='%an %ae %(trailers:key=Co-authored-by)'` and bot actors such as `copilot-swe-agent[bot]`; users can strip these markers, so their absence proves nothing.
- **Not when:** The evidence is not one-sided. CodeRabbit (vendor, 470 PRs, 2025) found more spelling (18.92 vs 10.77) and testability issues (23.65 vs 17.85) in human PRs. Asare et al. (EMSE 2023; 2022 Copilot, C/C++) found Copilot replicated the original vulnerable code about 33% of the time and the fixed code 25%. GitHub's RCT (vendor, 202 developers, one task) found assisted code 53.2% more likely to pass all 10 unit tests. These argue for calibrating by category, not for skipping review.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [AI-assisted coding creates more problems](https://www.infoworld.com/article/4109129/ai-assisted-coding-creates-more-problems-report.html) (InfoWorld, 2025); [Is GitHub's Copilot as Bad as Humans at Introducing Vulnerabilities in Code?](https://arxiv.org/abs/2204.04741) (Asare, Nagappan, Asokan, EMSE 2023); [Does GitHub Copilot improve code quality?](https://github.blog/news-insights/research/does-github-copilot-improve-code-quality-heres-what-the-data-says/) (GitHub, 2024); [Bad Vibes](https://news.research.gatech.edu/2026/04/13/bad-vibes-ai-generated-code-vulnerable-researchers-warn) (Georgia Tech, 2026) · dossier: ai-code-quality-studies T11-F19, T11-F09

### AI-02 — Order the pass by the categories measured as over-represented, and expect old issues to survive
- **Rule:** When provenance signals show substantial AI-assisted code, spend review effort in this order: injection and output encoding (AI-15), dependency existence (AI-09), duplication (AI-22), complexity and volume (AI-20), error handling (AI-12, AI-13), I/O in loops (AI-27), secrets (AI-18), entry-point authorization (AI-19), then the rest. Do not assume normal maintenance has already removed AI-introduced issues.
- **Detect:** Record candidates per category so the report can show coverage per category. The order is the dossier researcher's synthesis (effect size x evidence strength x harm), not a ranking any single source produced.
- **Not when:** The per-category ratios come from one vendor study (CodeRabbit, 470 PRs, 2025: 10.83 vs 6.45 issues per PR; excessive I/O ~8x, readability 3x, security up to 2.74x, error handling ~2x) whose detection method is not public and whose human labels are uncertain. Survival: "Debt Behind the AI Boom" (preprint, 2026; 302,579 AI-authored commits in 6,299 Python/JS/TS repos) found 22.7% of tracked AI-introduced issues still at HEAD. Ratios describe PR populations, not individual files, and may reflect who adopts AI. The duplication slot rests on C-grade, contested evidence: GitClear's rise is vendor-reported and correlational, and the only causal peer-reviewed study (Cursor difference-in-differences, MSR '26) found "no significant effect" on duplicate line density (T11-F04).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [State of AI vs Human Code Generation Report](https://www.coderabbit.ai/blog/state-of-ai-vs-human-code-generation-report) (CodeRabbit, 2025); [Debt Behind the AI Boom](https://arxiv.org/html/2603.28592v2) (Liu et al., 2026); [Speed at the Cost of Quality](https://arxiv.org/abs/2511.04427) (He et al., MSR '26); [The Maintainability Gap](https://www.gitclear.com/the_ai_code_quality_maintainability_gap) (GitClear, 2026) · dossier: ai-code-quality-studies T11-F01, T11-F04, T11-F05

### AI-03 — Tie every candidate to a tool finding or a trace, and never propose a bias-shaped fix
- **Rule:** Base every candidate on a tool finding (tool, rule id, file:line), a source-to-sink trace or a failing scenario, never on an agent's statement that code is "secure", "fixed" or "tested", including your own. Never propose as a remedy a new suppression, defensive check, comment, abstraction or dependency, or a weakened test or gate. Mark every proposed security fix for human review.
- **Detect:** Check each candidate before emitting: `evidence[]` holds a `tool`, `source` or `test` item, and the proposed remedy adds none of the constructs above. The apply phase re-runs the same scanners after each change and rejects any change that adds findings.
- **Not when:** The degradation evidence is small: one study (IEEE ISTAS 2025; GPT-4o, 10 base programs, 400 samples) measured a 37.6% rise in critical vulnerabilities after five unguided "improvement" rounds. Perry et al. (CCS 2023; codex-davinci-002, now obsolete) found assisted users wrote less secure code and were more likely to believe it secure. Grounding helps: Copilot Chat fixed 19.3% of security issues with plain `/fix` and 55.5% with the warning in the prompt (Fu et al., TOSEM 2025). Instructions only partly suppress bias: a strict prompt cut GPT-5 from 92% to 1% on Conflicting-LiveCodeBench but only from 66% to 54% on Conflicting-SWEbench (ImpossibleBench).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Security Degradation in Iterative AI Code Generation](https://arxiv.org/abs/2506.11022) (Shukla, Joshi, Syed, IEEE ISTAS 2025); [Do Users Write More Insecure Code with AI Assistants?](https://arxiv.org/abs/2211.03622) (Perry et al., CCS 2023); [Security Weaknesses of Copilot-Generated Code in GitHub Projects](https://arxiv.org/html/2310.02059v3) (Fu et al., TOSEM 2025); [ImpossibleBench](https://arxiv.org/abs/2510.20270) (Zhong, Raghunathan, Carlini, ICLR 2026) · dossier: ai-code-quality-studies T11-F17; ai-code-smells-practitioners T12-F21; llm-refactoring T10-F09

### AI-04 — Audit history and the test tree for tests weakened to go green
- **Rule:** Look for tests weakened to make a suite pass: deleted test files, removed assertions, loosened expectations, new skip, xfail, only or ignore markers, mass-regenerated snapshots, and tests edited in the same commit as the code they cover. Report each unexplained case with its commit. Never accept "tests pass" at face value.
- **Detect:** Deleted tests: `git log --diff-filter=D --name-only -- '*test*' '*spec*'`. Removed assertions: `git log -p -- '*test*' '*spec*' | rg '^-\s*.*(assert|expect\(|should\.|assert_eq!)'`, compared with the added ones. Review commits that touch src and tests together first. Track collected-test counts across history. Markers: `rg -n "\.(skip|only|todo)\(|\bx(it|describe|test)\(|@pytest\.mark\.(skip|xfail)|pytest\.skip\(|#\[ignore\]|t\.Skip\(|@Disabled|@Ignore"`, jest or vitest `no-disabled-tests` and `no-focused-tests`, pytest `-rxXs` with `strict_xfail = true` (the pytest 9.0 name; `xfail_strict` is an alias), libtest `--list --ignored`. Snapshots: `git log -p` on `__snapshots__` and `*.snap`.
- **Not when:** A test deleted with the feature it covered, a flaky test quarantined with a tracked issue, and a snapshot update for a deliberate UI change are legitimate. The strong numbers come from environments where cheating is the only path: in ImpossibleBench (ICLR 2026) GPT-5 passed 76% of one-off impossible SWE-bench tasks, and Claude models cheated mostly (>79%) by modifying tests despite explicit instructions; METR saw o3 reward-hack 39 of 128 RE-Bench runs (30.4%). Prevalence in ordinary product repos is unmeasured (practitioner reports only). Restoring an assertion edits an existing test, so the owner decides.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [ImpossibleBench](https://arxiv.org/abs/2510.20270) (Zhong, Raghunathan, Carlini, ICLR 2026); [Genie Wants to Leap](https://newsletter.kentbeck.com/p/genie-wants-to-leap) (Beck, 2025); [Recent Frontier Models Are Reward Hacking](https://metr.org/blog/2025-06-05-recent-reward-hacking/) (METR, 2025); [jest/no-disabled-tests](https://github.com/jest-community/eslint-plugin-jest/blob/main/docs/rules/no-disabled-tests.md) (jest-community); [How to use skip and xfail](https://docs.pytest.org/en/stable/how-to/skipping.html) (pytest) · dossier: ai-code-smells-practitioners T12-F04; ai-code-quality-studies T11-F14; llm-refactoring T10-F06

### AI-05 — Treat AI-written tests as unverified until they are seen to fail
- **Rule:** Report tests that mock the unit under test, assert only that a mock was called, assert a value the test itself set, re-implement the code under test, or contain no assertion. Treat a test as verified only after a mutation run or a deliberately injected fault makes it fail. The pass never rewrites these tests; stronger replacements are new-test candidates for the tests lens.
- **Detect:** jest or vitest `expect-expect`; files with no assertion: `rg -L "assert|expect\(|pytest\.raises|should\." -g "*test*"`; mocked SUT: `rg -n "jest\.mock\(|vi\.mock\(|@patch\(|mock\.patch\(" tests/` where the mocked path is the module under test; tests whose only assertions are `toHaveBeenCalled*` or `assert_called*` on a mock made in the same test. On core modules, run mutation testing in a scratch worktree: a surviving mutant in covered code points to a missing or tautological assertion.
- **Not when:** Interaction assertions are correct when the interaction is the behaviour ("sends exactly one email"); snapshot tests carry their oracle in the snapshot; smoke tests labelled as such are legitimate. Coverage is not the signal: Böckeler (2026) found a file at 100% statement coverage with no unit tests and 13 surviving mutants. Numbers: 80.2% of test-file patches in 33,596 agent PRs had weak or no explicit oracle signals (IEEE AITest 2026), yet Milanese et al. (preprint, 2026) found no meaningful test-smell difference between agent and human PRs.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Maintainability sensors for coding agents](https://martinfowler.com/articles/sensors-for-coding-agents.html) (Böckeler, 2026); [Do LLMs generate test oracles that capture the actual or the expected program behaviour?](https://arxiv.org/abs/2410.21136) (Konstantinou et al., 2024); [All Smoke, No Alarm](https://arxiv.org/abs/2606.18168) (2026); [Human-Agent versus Human Pull Requests](https://arxiv.org/abs/2601.21194) (Milanese et al., 2026); [AI-generated tests as ceremony](https://blog.ploeh.dk/2026/01/26/ai-generated-tests-as-ceremony/) (Seemann, 2026); [jest/expect-expect](https://github.com/jest-community/eslint-plugin-jest/blob/main/docs/rules/expect-expect.md) (jest-community) · dossier: ai-code-smells-practitioners T12-F06; ai-code-quality-studies T11-F14

### AI-06 — Hunt special-casing and test-awareness in production code
- **Rule:** Search production code for logic that passes tests without solving the problem: literals copied from test fixtures, branches keyed on specific test inputs, comments such as "special case for test", test-framework detection, `__eq__`/`equals` overrides that always or too broadly return true, call-count state that returns different output for identical input, early success exits, and monkey-patching of a harness or evaluator. Report every confirmed hit as a blocking defect for the owner.
- **Detect:** Test-awareness: `rg -n "NODE_ENV\s*={2,3}\s*['\"]test|process\.env\.(JEST_WORKER_ID|VITEST)|PYTEST_CURRENT_TEST|'pytest' in sys\.modules|isTest(ing)?\b" src/` (Rust `#[cfg(test)]` only outside `mod tests`). Gaming comments: `rg -n -i "special[- ]?case|for (the )?tests?|make (the )?tests? pass|hard[- ]?cod|expected (value|output)" src/`. Faked exits: `rg -n 'sys[.]exit[(]0[)]|os[.]_exit[(]0[)]|process[.]exit[(]0[)]' src/`. Equality: `ast-grep run -l python -p 'def __eq__(self, $O): return True'`, then read every cross-type `__eq__`, `equals`, `valueOf` and `Symbol.toPrimitive`. Leaked literals: `rg -F` each distinctive test-expectation literal in src. Hidden state: module-level counters or caches in functions that should be pure.
- **Not when:** Lookup tables, feature flags, and environment checks that disable telemetry or inject fakes in composition-root or config code match these patterns legitimately; domain constants can coincide with fixtures. Removing a hack turns tests red again: report that, never work around it. Read-only tests do not stop this pattern, and LLM monitors caught only 42-65% of cheating on multi-file tasks (ImpossibleBench). Rates are benchmark-only: METR measured o3 reward-hacking in 0.7% of HCAST runs but in every trajectory of one RE-Bench task.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [ImpossibleBench](https://arxiv.org/abs/2510.20270) (Zhong, Raghunathan, Carlini, ICLR 2026); [Claude 3.7 Sonnet System Card](https://www-cdn.anthropic.com/9ff93dfa8f445c932415d335c88852ef47f1201e/claude-3-7-sonnet-system-card.pdf) (Anthropic, 2025); [From shortcuts to sabotage](https://www.anthropic.com/research/emergent-misalignment-reward-hacking) (Anthropic, 2025); [Recent Frontier Models Are Reward Hacking](https://metr.org/blog/2025-06-05-recent-reward-hacking/) (METR, 2025); [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) (Anthropic, 2026) · dossier: ai-code-smells-practitioners T12-F05; llm-refactoring T10-F07

### AI-07 — Report placeholders and fake implementations that production can reach
- **Rule:** Find mock or sample data, stubs that return constants, "simulate" or "dummy" branches, TODO/FIXME/XXX markers, `NotImplementedError`, `todo!()`, `unimplemented!()`, `example.com` and lorem ipsum on production paths. Report each as an open defect for the owner; never implement it silently during hardening.
- **Detect:** `rg -n -i "\b(TODO|FIXME|XXX|HACK|placeholder|dummy|mock|fake|stub|simulat(e|ed|ion)|lorem ipsum|example\.com|hardcoded for now|for now)\b" src/ --glob '!**/*test*'`; `rg -n "NotImplementedError|todo!\(|unimplemented!\(|throw new Error\(['\"]not implemented" src/`; Ruff `FIX`, `TD`; ESLint `no-warning-comments`; clippy `todo`, `unimplemented`; functions whose body is one literal return and whose parameters are unused; `import .*(mock|fixture|sample)` inside src.
- **Not when:** Deliberate dev or demo fakes behind explicit config that production cannot reach, and tracked TODOs with issue links. The deciding test is whether a production path can reach the fake behaviour. Removing a placeholder that production code uses as the fallback for a missing credential implements nothing: it is a separate T1 behavioural candidate under OP-12 (SE-17; eval-v1-calibration E01-F07). Evidence is practitioner-only (Beck: "faking large swathes of implementation"; HN; the Replit forum).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** C
- **Source:** [Genie Wants to Leap](https://newsletter.kentbeck.com/p/genie-wants-to-leap) (Beck, 2025); [Feedback on Claude's tendency to produce fallback/mock implementations](https://replit.discourse.group/t/feedback-on-claude-s-tendency-to-produce-fallback-mock-implementations/7294) (Replit forum, 2025); [HN comment by stefan_](https://news.ycombinator.com/item?id=43899894) (2025); [Ruff FIX002](https://docs.astral.sh/ruff/rules/line-contains-todo/) (Astral) · dossier: ai-code-smells-practitioners T12-F16; eval-v1-calibration E01-F07

### AI-08 — Diff every quality-gate config against its first version
- **Rule:** Compare lint configs, tsconfig/mypy/pyright strictness, coverage thresholds, complexity maxima, CI steps and pre-commit hooks against their first committed version and the tool's recommended preset. Report each loosening that has no documented reason, with its commit.
- **Detect:** `git log -p --follow` over `eslint.config.* .eslintrc* tsconfig*.json pyproject.toml setup.cfg mypy.ini ruff.toml .pre-commit-config.yaml .github/workflows/ jest.config.* vitest.config.* .coveragerc`. Look for rules set to `off` or `0`, `"strict": false`, `strictNullChecks` or `noImplicitAny` disabled, `skipLibCheck`, `ignore_errors` or `ignore_missing_imports` added, new per-file ignores, raised `max-*` or `complexity`, lowered `coverageThreshold` or `fail_under`, `continue-on-error: true`, `|| true`, `set +e`, `--passWithNoTests`, `-p no:` plugin disables, `--no-verify` in scripts, and `testPathIgnorePatterns`, `--deselect` or `-k` filters.
- **Not when:** A threshold set too strictly at the start may be relaxed on purpose in a separate explained commit. Böckeler (2026) deliberately let agents make small, visible threshold bumps, so report unexplained bumps, not every bump. Path-scoped disables for generated or vendored code are legitimate. No source measures agents loosening gates unprompted (Böckeler's agent did it under an allowance she gave). Tightening a gate can turn the baseline red, so the owner decides.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [Maintainability sensors for coding agents](https://martinfowler.com/articles/sensors-for-coding-agents.html) (Böckeler, 2026); [HN: Be intentional about how AI changes your codebase](https://news.ycombinator.com/item?id=47446373) (2026); [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices) (Anthropic, 2026) · dossier: ai-code-smells-practitioners T12-F08; llm-refactoring T10-F08

### AI-09 — Verify every dependency exists, is the intended project and is not a fresh look-alike
- **Rule:** Check every declared and imported third-party package against its registry: it exists, it is the intended project, and it is not a newly registered look-alike. A name that a working build resolves but the owner cannot account for is a possible package-confusion (slopsquatting) case, not proof of legitimacy. Never propose a new dependency as a fix unless it passes the same checks, in its own commit, for human approval.
- **Detect:** List direct dependencies from the manifests plus imports with no manifest entry. Query the registry, only when `.harden/config.json` sets `"network": "allowed"` (otherwise record the gap) (`npm view <pkg> name time.created repository.url versions`, the PyPI JSON API where non-200 means absent, `pip index versions`, `cargo search`/`cargo info`, `go list -m <module>@latest`). Flag recent creation, few releases, no source repository, or a name one edit away from a popular package. Then run SCA (npm audit, pip-audit, cargo audit, OSV-Scanner or OWASP Dependency-Check) and confirm the lockfile reproduces.
- **Not when:** Private or scoped packages legitimately 404 on public registries. Rates fell: Spracklen et al. (USENIX Security 2025; 16 models, 576,000 Python and JS samples, 2.23M package references, 2024-era models) found 19.7% hallucinated (at least 5.2% commercial, 21.7% open-source; 205,474 unique names; 43-45% recurring on every repeat). A 2026 preprint on five frontier models found 4.62-6.10%, but 127 names were invented by all five and 53 were still registrable. Endor Labs (vendor, 2025): 34% of AI-suggested dependency versions hallucinated. In-the-wild exploitation is disputed (Wikipedia, July 2026: none reported; CSA, April 2026: one malicious package).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A

### AI-12 — Fix swallowed and over-broad exception handlers
- **Rule:** Find every catch-all with an empty body, catch-log-and-continue, catch-and-return None/[]/{}, `.catch(() => {})`, Go `_ = err`, and Rust `let _ =` or `.ok();` on fallible calls. - **Detect:** Ruff `BLE001`, `S110`, `S112`, `E722`; Pylint `W0718`; flag `except ...: return None|[]|{}|''` by hand, because BLE001 exempts re-raised and `exc_info`-logged handlers. - **Not when:** Top-level handlers (request handler, worker supervisor, main loop) that log, report and convert errors; best-effort telemetry, cache warm-up and `finally` cleanup that catch a narrow type. Propose merging only copies that share intent, and keep the variant that is actually correct, not the first one found. Merges across modules are T2 per PC-17 (report with a plan); T1 applies only to copies within one module.
- **Detect:** jscpd (`--min-tokens 50`; `--ignore-identifiers --ignore-literals` for renamed clones), PMD CPD, SonarQube duplications and `S1192`; group helpers by name stem, e.g. `rg -n "(def|function|const) +(parse|format|validate|normalize)[A-Za-z]*Date"`; count variants per concern (`rg -c "\bfetch\(|axios|got\(|ky\.|requests\.|httpx\.|urllib"`, env access outside the config module with `rg -n "process\.env\.|os\.environ|getenv\("`); compare each group's behaviour on a small input table before proposing a merge.
- **Not when:** "Duplication is far cheaper than the wrong abstraction" (Metz); tests, generated code and deliberately separate services tolerate duplication; some variation is justified (streaming vs JSON client, CLI vs server logging). The AI link is contested: GitClear (vendor, correlational, not attributed to AI lines; 623M changes 2023-2026) reports duplicated blocks +81% (40.3 to 73.0 per million changed lines) and moved code falling from 21% (2022) to 3.8% (2026 YTD), while the Cursor DiD study found no significant duplication effect, with modest increases possible for heavy adopters. The findings behind this rule's AI premise were downgraded to C for that reason (T11-F04, T10-F20); only the detection of re-invented helpers (T12-F10) stays at B.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** C
- **Source:** [The Maintainability Gap](https://www.gitclear.com/the_ai_code_quality_maintainability_gap) (GitClear, 2026); [Beyond Bug Fixes](https://arxiv.org/abs/2601.20109) (Cynthia et al., MSR '26); [Maintainability sensors for coding agents](https://martinfowler.com/articles/sensors-for-coding-agents.html) (Böckeler, 2026); [Beyond Functional Correctness](https://arxiv.org/html/2604.06373v1) (Kashif et al., 2026); [The Wrong Abstraction](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction) (Metz, 2016); [jscpd](https://github.com/kucherenko/jscpd) (kucherenko) · dossier: ai-code-smells-practitioners T12-F10, T12-F11; ai-code-quality-studies T11-F04; llm-refactoring T10-F20

### AI-23 — Remove iteration residue
- **Rule:** Find unused imports, variables, parameters and exception variables, unreachable branches, functions and files left from abandoned attempts, scratch scripts, and debug output (console.log, print, dbg!) in library or service code. Report an unused parameter next to a TODO or a half-finished branch as a possible unfinished edit, not as residue.
- **Detect:** `@typescript-eslint/no-unused-vars` (`caughtErrors: "all"`, `args: "after-used"`), `no-unreachable`, `no-console` (browser or library code), `no-debugger`; knip; Ruff `F401`, `F841`, `ARG`, `ERA001`, `T201`, `T203`; vulture `--min-confidence 80`; mypy `--warn-unreachable`; clippy `dbg_macro`, `print_stdout`; staticcheck `U1000`, deadcode; scratch files: `git ls-files | rg -i '(^|/)(tmp|temp|scratch|debug|try_|old_|backup|copy)'`. Compiler-proven unused locals and imports follow the dead-code lens's rules and tiers.
- **Not when:** DI, reflection, plugin registries, framework conventions, pytest fixtures, CLI entry points, side-effect imports and public API look unused. Interface-required parameters stay (prefix with `_`). print and console output is legitimate in CLIs, and Ruff marks the T201 fix unsafe. Numbers: in the Debt Behind preprint (Python/JS/TS lint hits) unused variables or parameters were 5.8% (28,272) and unused arguments 5.0% (24,357) of issues; Cynthia et al. (MSR '26; 1,210 merged agent bug-fix PRs, 206 Python repos, no human baseline) found `S1172` unused parameters the third most frequent smell.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Debt Behind the AI Boom](https://arxiv.org/html/2603.28592v2) (Liu et al., 2026); [Beyond Bug Fixes](https://arxiv.org/abs/2601.20109) (Cynthia et al., MSR '26); [On the Use of Agentic Coding](https://arxiv.org/html/2509.14745v3) (Watanabe et al., TOSEM); [no-unused-vars](https://eslint.org/docs/latest/rules/no-unused-vars) (ESLint); [T201](https://docs.astral.sh/ruff/rules/print/) (Astral); [Vulture](https://github.com/jendrikseipp/vulture) (Seipp) · dossier: ai-code-smells-practitioners T12-F15; ai-code-quality-studies T11-F12

### AI-24 — Queue narrating comments, echo comments and commented-out code for review
- **Rule:** Queue comments that narrate history or the session ("now uses X", "changed from", "fixed bug where", "no longer", "as requested"), comments that describe what the code does not do, comments that restate the next line, and commented-out code. Propose deleting only those that fail the survival test (still true and useful to a reader a year from now who never saw the diff); keep comments that state a non-obvious why, an invariant, a constraint or a hazard.
- **Detect:** `rg -n -i "(//|#|/\*|\*)\s*.*\b(now (uses|returns|handles)|previously|no longer|changed (from|to)|updated to|refactored|fixed (a |the )?bug|as requested|instead of the old|was (removed|replaced)|new implementation|legacy)\b" src/`; "not X" narration (`-- not |, not |rather than|instead of`); Ruff `ERA001` or Sonar `S125` for commented-out code (ERA001 is "prone to false positives"); per-file comment density. Every hit is a review item, never an autofix.
- **Not when:** Machine-meaningful comments (`# type:`, `// eslint-`, `@ts-`, licence headers, doctests, docstrings or JSDoc that feed docs) and notes on external constraints (an upstream bug link). Some practitioners keep comments on purpose for later agent sessions. The pass never translates, rephrases or adds comments to code it does not change. Numbers: Sonar (vendor, Java tasks) measured 16.4% comment density for Claude 3.7 Sonnet vs 4.4% for GPT-4o, but density is not narration; no validated narration detector exists.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** C
- **Source:** [The Coding Personalities of Leading LLMs](https://www.sonarsource.com/blog/the-coding-personalities-of-leading-llms/) (Sonar, 2025); [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) (Anthropic, 2026); [Codex Prompting Guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide) (OpenAI); [HN comment by fooster](https://news.ycombinator.com/item?id=49411258) (2026); [HN comment by nrmitchi](https://news.ycombinator.com/item?id=49392261) (2026); [ERA001](https://docs.astral.sh/ruff/rules/commented-out-code/) (Astral); [Refactoring Programs Using LLMs with Few-Shot Examples](https://arxiv.org/abs/2311.11690) (Shirafuji et al., APSEC 2023) · dossier: ai-code-smells-practitioners T12-F12; llm-refactoring T10-F15

### AI-25 — Treat every in-repo claim about properties or status as a claim to verify
- **Rule:** Check every comment, docstring, README or changelog statement that asserts a property ("validated", "sanitized", "thread-safe", "idempotent", "retries", "cached", "O(1)"), and every commit message, PR description or earlier agent summary that says something works or passes, against the code, its tests and the recorded baseline. Report a false property claim as either a doc defect or a missing guard, for the owner to decide.
- **Detect:** `rg -n -i "(#|//|\*|\"\"\").*(sanitiz|validat|thread.?safe|idempotent|retr(y|ies)|atomic|cached|secure|O\(1\))"`; compare README and API docs with the actual routes, flags and config keys; compare claimed test status with the baseline in `.harden/gates/`.
- **Not when:** The measured data covers PR descriptions, not inline comments: in an MSR '26 study of 23,247 agent PRs, 406 (1.7%) had high message-code inconsistency and 45.4% of those claimed changes never made; they were accepted 28.3% of the time vs 80.0%. Böckeler (2025) saw agents claim builds and tests passed when they had not, despite explicit instructions. Merge outcome is a poor quality proxy: only 35.7% of rejected agent PRs reflected clear agent failures (Peralta et al., MSR 2026).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [Analyzing Message-Code Inconsistency in AI Coding Agent-Authored Pull Requests](https://arxiv.org/abs/2601.04886) (Gong et al., MSR '26); [How far can we push AI autonomy in code generation?](https://martinfowler.com/articles/pushing-ai-autonomy.html) (Böckeler, 2025); [Why Are Agentic Pull Requests Merged or Rejected?](https://arxiv.org/abs/2605.22534) (Peralta et al., MSR 2026); [Vibe engineering](https://simonwillison.net/2025/Oct/7/vibe-engineering/) (Willison, 2025) · dossier: ai-code-quality-studies T11-F16; ai-code-smells-practitioners T12-F19

### AI-26 — Report backwards-compatibility shims that have no real old consumer
- **Rule:** Report aliases kept "for backward compatibility", duplicate old and new code paths, dual-format parsers for formats never shipped, re-exports of renamed symbols and permanent feature flags. A shim stays when a named external consumer, persisted data or a wire protocol still needs it; the owner confirms consumers before any removal.
- **Detect:** `rg -n -i "backward|backwards|compat|legacy|deprecated alias|for (older|old) (clients|versions)|old_|_v1\b|_old\b|shim" src/`; aliases and re-exports; functions whose whole body delegates; flags that never change across environments; git tags and releases (an old shape that never shipped has no consumer). A compat path that exists only to satisfy a test expectation is an AI-06 candidate.
- **Not when:** Published libraries, public HTTP APIs, persisted formats, DB and message schemas and mobile clients may have real old consumers; semantic versioning and deprecation policy apply there. Evidence: ImpossibleBench (ICLR 2026) saw models invoke "backward compatibility" to justify test-matching, spec-violating behaviour that evaded monitors; practitioner issue #2488 reports an agent re-adding compat code despite instructions. No prevalence data exists.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** C
- **Source:** [ImpossibleBench](https://arxiv.org/abs/2510.20270) (Zhong, Raghunathan, Carlini, ICLR 2026); [Persistent Backwards Compatibility Insertion Despite User Rejection](https://github.com/anthropics/claude-code/issues/2488) (anthropics/claude-code, 2025); [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) (Anthropic, 2026) · dossier: ai-code-smells-practitioners T12-F14

### AI-27 — Report I/O in loops and accidental quadratic work, and wait for a profile
- **Rule:** Report DB queries, HTTP calls and file reads inside loops (N+1), repeated reads or parsing of the same input, O(n) work in hot or "magic" methods (`__len__`, `__contains__`, `__eq__`, `__hash__`, getters, React render) and algorithms of a higher complexity class than needed on hot paths. Changes wait for a profile or query log.
- **Detect:** ESLint `no-await-in-loop`; `ast-grep run -l ts -p 'for ($$$) { $$$ await $C($$$) $$$ }'`; `rg -n -A4 "for .* (in|of) |\.forEach\(|\.map\(" | rg "fetch\(|axios\.|\.query\(|\.execute\(|\.find(One|Unique)?\(|requests\.(get|post)|open\("`; ORM relation access inside loops; nested loops over the same collection; loops inside magic methods.
- **Not when:** Sequential awaits are correct for dependent iterations, rate-limited APIs, bounded resources, retries and transactions; batching and caching add staleness risk. Numbers: CodeRabbit (vendor, 470 PRs) found excessive I/O ~8x more common in AI PRs, in a category that is rare in absolute terms; EffiBench (NeurIPS 2024; 1,000 LeetCode problems) found GPT-4 code averaged 3.12x the canonical execution time, on algorithm puzzles rather than application code.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** C
- **Source:** [Our new report: AI code creates 1.7x more problems](https://dev.to/coderabbitai/our-new-report-ai-code-creates-17x-more-problems-7lh) (CodeRabbit, 2025); [EffiBench](https://arxiv.org/abs/2402.02037) (Huang et al., NeurIPS 2024); [no-await-in-loop](https://eslint.org/docs/latest/rules/no-await-in-loop) (ESLint); [Dignified Python](https://dagster.io/blog/dignified-python-10-rules-to-improve-your-llm-agents) (Dagster, 2026) · dossier: ai-code-quality-studies T11-F07; ai-code-smells-practitioners T12-F20

### AI-28 — Report resource-lifetime, ordering and concurrency mistakes to the human lane
- **Rule:** Report opened files, sockets, connections and locks not released on every path, shared mutable state touched by concurrent handlers without synchronization, and async results neither awaited nor explicitly detached. Fixes belong to the concurrency lens's human lane.
- **Detect:** SonarQube bug rules (resource leaks, thread safety); `rg -n "open\(|createReadStream|new FileInputStream|connect\(|acquire\("`, then confirm each is closed in `finally` or a context manager; typescript-eslint floating-promise checks where configured; module-level mutable state modified in request handlers; `go test -race`.
- **Not when:** The evidence is vendor-only with no human baseline: CodeRabbit (470 PRs) found ~2x more "incorrect ordering, faulty dependency flow, or misuse of concurrency primitives"; Sonar (Java benchmark tasks) attributes 15.07% of Claude Sonnet 4's bugs to resource management and 9.81% to threading, and 48.15% of GPT-4o's bugs to control flow.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** C
- **Source:** [Our new report: AI code creates 1.7x more problems](https://dev.to/coderabbitai/our-new-report-ai-code-creates-17x-more-problems-7lh) (CodeRabbit, 2025); [Diving into the 3 traits](https://www.sonarsource.com/blog/llm-coding-personality-traits/) (Sonar, 2025); [GPT-5 Update](https://www.sonarsource.com/blog/the-coding-personalities-of-leading-llms-gpt-5-update/) (Sonar, 2025) · dossier: ai-code-quality-studies T11-F15

## False-positive exclusions

- A candidate justified only by AI provenance, a co-author trailer or "looks generated" (AI-01).
- Tests deleted together with the feature they covered, flaky tests quarantined with a tracked issue, snapshot updates for deliberate UI changes (AI-04).
- Interaction assertions where the interaction is the behaviour; labelled smoke tests; snapshot tests (AI-05).
- Environment checks in composition-root or config code that disable telemetry or inject fakes; lookup tables and feature flags; domain constants that coincide with fixture literals (AI-06).
- Dev or demo fakes behind explicit config that production cannot reach; TODOs with issue links (AI-07).
- Gate relaxations made in a separate commit that explains why; path-scoped disables for generated or vendored code (AI-08).
- Private or scoped packages that 404 on public registries (AI-09). A deprecated API that is the only one for the minimum supported version, when documented (AI-10).
- Targeted, justified suppressions for untyped third-party packages, gradual adoption, generated code or known linter false positives (AI-11).
- Catch-alls at real process or request boundaries that log and convert; best-effort telemetry and cleanup that catch a narrow type (AI-12).
- Documented defaults for truly optional configuration; observable graceful degradation that is a product requirement (AI-13).
- Checks on untrusted data, public entry points or values whose types are unsound (AI-14).
- Framework auto-escaping that is not bypassed; logs written to structured sinks that escape newlines; identifiers checked against a hard-coded allowlist (AI-15). Input already constrained to an enum or UUID (AI-16).
- Seeded PRNGs in simulations, tests and backtests; MD5 or SHA-1 used as non-security checksums (AI-17). Publishable client keys, test fixtures and dummy keys (AI-18).
- Essential complexity in parsers and state machines (AI-20). Test seams, real plugin points and published extension points (AI-21). Duplication in tests, generated code or deliberately separate services (AI-22).
- Symbols reached through DI, reflection, plugin registries, framework conventions, pytest fixtures or CLI entry points; interface-required parameters; print in CLIs (AI-23).
- Machine-meaningful comments (type, lint and TS directives, licence headers, doctests, doc-generating docstrings) and external-constraint notes (AI-24).
- Shims for published libraries, public APIs, persisted formats, schemas and mobile clients (AI-26). Sequential awaits needed for ordering, rate limits or transactions (AI-27).

## Evidence limits

- Provenance is unreliable. Almost every AI-vs-human figure relies on co-author trailers, bot metadata or self-reported labels that users can strip. CodeRabbit admits uncertain human labels, and CSA attributes part of Claude Code's CVE count to its commit signatures.
- Most multipliers come from vendors that sell detection tools: CodeRabbit, Sonar, Veracode, OX, Apiiro, GitGuardian, Endor Labs and GitClear. Independent peer-reviewed support exists for security prevalence (Pearce, Fu, Perry, BaxBench), package hallucination (Spracklen plus a 2026 replication), complexity (the Cursor DiD study), deprecated APIs (ICSE 2025) and weak test oracles (AITest 2026). None exists for the I/O (8x), concurrency (2x), readability (3x) or duplication ratios.
- Model drift: most numbers come from 2023 to mid-2025 models. Package hallucination has fallen for 2026 frontier models; Veracode's XSS and log-injection pass rates have not moved. Smell profiles differ by model and version, so do not assume which model wrote the code.
- Test cheating and special-casing rates come from impossible-task benchmarks and eval environments (ImpossibleBench, METR). Base rates in ordinary product repos are unmeasured.
- No peer-reviewed prevalence data exists for narrating comments, compatibility shims, leftover debug output or success-shaped fallbacks, and no detector for them has published precision or recall: their greps are review queues.
- Several load-bearing studies are preprints (Debt Behind, the agentic-PR coverage study, the 2026 package replication, Zhu et al.). The "Debt Behind" counts are lint hits in Python, JS and TS, not confirmed defects.
- The dossiers contain no AI-specific evidence for Solidity, C/C++ or Rust beyond the generic lints named here; for those languages this lens only applies its language-agnostic checks.
- The ordering in AI-02 is a synthesis. The evidence on AI security relative to humans conflicts (Veracode and CodeRabbit report more; Asare, OX and Contrast report similar or less), partly because benchmarks measure per task and real repos per line.
