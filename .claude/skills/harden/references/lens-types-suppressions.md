# Lens: Types and suppressions

> Purpose: treat type checking and static analysis as bounded, calibrated gates; find stale or broad suppressions, unpinned or stale analyzers, missing baselines, escape hatches, unparsed boundaries and silent defaults, and never let a "the types guarantee it" claim delete a runtime check.
> Read when: a TypeScript/JavaScript, Python, Rust, C/C++, Go, C#, Java or PHP file is in scope, or the repository has type-checker or linter configs, inline suppressions or analyzer baseline files.

## Procedure

You are a fresh-context, read-only lens subagent with Read, Grep and Glob only (detection step 8). Never edit tracked files, never change an analyzer config, never run an autofix mode, and never run a tool mode that writes into the tree (`--suppress-all`, `--suppress-rule`, `--prune-suppressions`, `--writebaseline`, `--generate-baseline`, type-coverage `--update-if-higher`); the orchestrator applies the same limits to the detector commands below and writes their raw output only under `.harden/tools/`. The unseeded pass reads no tool output and no prior findings.

1. **Load scope.** Read `.harden/inventory.json` (languages, configured tools, typecheck and lint commands, generated and vendor dirs) and the slice and exclude globs from the orchestrator. Read the project's own analyzer configs and baselines: `tsconfig*.json`, `eslint.config.*`, mypy/pyright/Ruff sections, Cargo `[lints]` and `clippy.toml`, `.clang-tidy`, CMake/Makefile/meson warning flags, golangci-lint config, baseline files. Project wins: a check the project deliberately turned off is reported with its size, never switched on.
2. **Record versions and effective config** (for example `tsc --showConfig` output from `.harden/tools/`) in every candidate's evidence. Counts and coverage percentages are comparable only under the same pinned tool version and config (TY-07).
3. **Detector commands (run by the orchestrator in detection step 4; read their outputs from `.harden/tools/`).** Exact commands, pinned versions and flags live in the language file (lang-typescript.md, lang-python.md, lang-rust.md, lang-cpp.md, lang-go.md); this lens names the tool and rule id. Extra checks go on the command line or through a temporary config under `.harden/tools/`, never into the project's files. A detector with no output file there is "not run": say so in the candidate notes, never treat it as clean. A blanket suppression whose tool is not installed is still a TY-04 candidate, never demoted for that reason: note that its hidden rules are listed at apply time by a pinned ephemeral run of that tool (TY-04).
   - TS/JS: tsc `--noEmit`, then once per beyond-strict flag (TY-11); ESLint unused-directive reporting at error severity plus `--report-unused-inline-configs` (TY-03); typescript-eslint ban-ts-comment, no-explicit-any, no-unsafe-*, consistent-type-assertions, no-non-null-assertion, no-unnecessary-condition, switch-exhaustiveness-check; eslint-comments no-unlimited-disable and require-description; type-coverage `--strict --detail`.
   - Python: mypy `--warn-unused-ignores`, `--check-untyped-defs` and `--strict` (sizing only), error codes `ignore-without-code` and `exhaustive-match`, `--warn-unreachable`, `--any-exprs-report` and `--lineprecision-report` into `.harden/tools/`; pyright reportUnnecessaryTypeIgnoreComment, reportUnnecessaryComparison, reportUnnecessaryCast, reportMatchNotExhaustive, reportUnknownMemberType; Ruff RUF100 and PGH003.
   - Rust: cargo clippy with allow_attributes and allow_attributes_without_reason; read the enabled lint groups (TY-08).
   - C/C++: compare warning flags with the OpenSSF set (TY-08, TY-06); clang-tidy `NOLINT` forms (TY-04); `-Wimplicit-fallthrough` (TY-17).
   - Go: golangci-lint nolintlint with require-specific, require-explanation and `allow-unused: false`.
   - C#, Java, PHP, only when present: Roslyn nullable analysis, NullAway with JSpecify, PHPStan reportUnmatchedIgnoredErrors.
   - Any other language (Solidity included): no tool is named here; record the coverage gap in the candidate notes.
4. **Census with Grep** using the ripgrep patterns in each rule's Detect line: bare or broad suppressions (TY-04), escape hatches (TY-13), I/O boundaries (TY-16), catch-all defaults (TY-17), unpinned analyzers (TY-07). Config age via `git log` (TY-07) and baseline trend via `git log -p` (TY-05) are detector commands too: read them from `.harden/tools/`. A grep hit is a lead to confirm by reading the code, and a miss proves nothing.
5. **Manual checks the tools do not make:**
   - trace the origin of every value behind an "unnecessary" condition before proposing its deletion (TY-15);
   - for each `!` or fallback a fix would remove, write down current and intended behaviour for an absent or unexpected value (TY-14);
   - follow each boundary value to its first typed use and check for a schema parse, not a cast (TY-16);
   - for any check you would recommend as blocking, classify a random sample of its hits (TY-02);
   - confirm each unused-suppression hit against the whole build matrix CI runs (TY-03).
6. **Prioritise** null safety (TY-10), then escape hatches (TY-13, TY-14), then boundary parsing (TY-16), as TY-01 orders. Group candidates per module so the change phase can deliver small per-module commits (TY-02).
7. **Return candidates plus files_read as your final message** (the orchestrator merges them into `.harden/candidates.json`; files_read lists every file and line range you read). Each candidate follows the findings schema (`assets/findings.schema.json`): `lens: "types-suppressions"`, `rule_ref: "TY-NN"` (or `project:<tool>/<rule>` for a hit of a rule the project already enables), `verified: false`, `status: "candidate"`, the tier, class and fix risk of the rule, and evidence items of kind `tool` (command, rule id, tool version, output path), `source` (file:line) and `git` (baseline or config history). One candidate per site; config-level items get one candidate per rule and config file. Never edit, never claim a fix, and never emit a candidate whose fix deletes a runtime check, assertion or test because the types cover it (TY-01).

## Rules

### TY-01 — A clean type-check is evidence against one bounded defect class, not proof of correctness
- **Rule:** Static type checkers caught about 15% of fixed public bugs (400 JavaScript bugs with Flow 0.30 and TypeScript 2.0, ICSE 2017; corrective defects in 210 Python projects with mypy, TSE 2021), null handling most often (Khan, Python), so never propose deleting or weakening a runtime test, assertion or check because "the types now guarantee it"; route every such case through TY-15. Spend type-hardening effort in this order: null safety (TY-10), escape hatches (TY-13, TY-14), boundary parsing (TY-16).
- **Detect:** Screen your own candidates for fixes that remove a check on type grounds. In the change phase, `git diff <base>...HEAD -- '*test*' '*spec*'` and `git diff <base> | rg '^-.*(assert|expect\(|should|raise|throw)'` list removed assertions; reject any commit justified by "the type system guarantees it".
- **Not when:** A check whose origin a manual trace proves type-safe in fully typed internal code may really be dead (TY-15). Both detection studies used 2016-era checkers and call their figures lower bounds; current checkers may catch more.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [To Type or Not to Type](https://earlbarr.com/publications/typestudy.pdf) (Gao, Bird, Barr, ICSE 2017); [Type-Related Defects in Python Projects](https://rebels.cs.uwaterloo.ca/papers/tse2021_khan.pdf) (Khan et al., TSE 2021); [Impact of Programming Languages on Code Quality: A Reproduction](https://arxiv.org/abs/1901.10220) (Berger et al., TOPLAS 2019); [Rebuttal to Berger et al.](https://arxiv.org/abs/1911.07393) (Ray, Devanbu, Filkov, 2019); [How Many of All Bugs Do We Find?](https://software-lab.org/publications/ase2018_static_bug_detectors_study.pdf) (Habib, Pradel, ASE 2018); [To Type or Not to Type? JS vs TS on GitHub](https://arxiv.org/abs/2203.11115) (Bogner, Merkel, MSR 2022) · dossier: types-static-analysis T18-F01, T18-F13

### TY-02 — Gate each check on its measured false-positive rate before recommending it as blocking
- **Rule:** Before recommending that a check become blocking, triage a random sample of its current hits on this codebase: recommend build-breaking only at zero effective false positives, advisory review-time only under 10% (cases where the developer disagrees or will not act), and off otherwise. Deliver accepted fixes as small per-module changes that already contain the fix, never as a bare findings list or dashboard.
- **Detect:** Run the candidate rule ephemerally (ESLint with a one-rule `--rule` override and JSON output, mypy `--enable-error-code <code>`, clang-tidy `-checks=-*,<check>`), classify the sample as real problem or not worth changing (about 20 hits is the dossier's heuristic, not a sourced figure), and record the counts in the candidate.
- **Not when:** The thresholds are one very large company's policy, and Google calls its 10% cutoff "chosen somewhat arbitrarily". A solo developer may accept more noise from high-severity checks: Infer's concurrency analysis kept a fix rate of about 50%, valued because those bugs are hard to debug. Even precise detectors catch few bugs (27 of 594 Defects4J Java bugs, ASE 2018).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Lessons from Building Static Analysis Tools at Google](https://storage.googleapis.com/gweb-research2023-media/pubtools/4365.pdf) (Sadowski et al., CACM 2018); [What Developers Want and Need from Program Analysis](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/07/What-Developers-Want-and-Need-from-Program-Analysis-An-Empirical-Study.pdf) (Christakis, Bird, ASE 2016); [Why Don't Software Developers Use Static Analysis Tools to Find Bugs?](https://research.google/pubs/why-dont-software-developers-use-static-analysis-tools-to-find-bugs/) (Johnson et al., ICSE 2013); [Scaling Static Analyses at Facebook](https://6826.csail.mit.edu/2020/papers/facebook-infer-cacm.pdf) (Distefano et al., CACM 2019) · dossier: types-static-analysis T18-F10

### TY-03 — Remove suppressions that suppress nothing, after a full-matrix check
- **Rule:** Run every available unused-suppression detector at error severity and propose deleting each suppression it reports, but only after it reported the same suppression across the whole CI matrix (language versions, platforms, feature flags, preprocessor configurations). Take tool capabilities from the tool docs: mypy does report unused ignores, although the FSE 2025 study says it lacks such a mechanism.
- **Detect:** ESLint `reportUnusedDisableDirectives` at "error" (the default is "warn") plus `--report-unused-inline-configs error`; ESLint bulk suppressions exit non-zero on unused entries; TypeScript reports "Unused '@ts-expect-error' directive"; mypy `--warn-unused-ignores`; pyright reportUnnecessaryTypeIgnoreComment (default "none" in every mode, strict included, so enable it explicitly); Ruff RUF100; golangci-lint nolintlint `allow-unused: false`; PHPStan reportUnmatchedIgnoredErrors left on. Plain `@ts-ignore` and Rust `#[allow]` never self-report: converting them (to `@ts-expect-error`, or to `#[expect]` checked by `clippy::allow_attributes`) is a TY-04 change.
- **Not when:** A suppression unused under one configuration may be needed under another: other Python or TypeScript versions (the TS 3.9 notes accept `@ts-ignore` during upgrades), platform stubs, Rust cfg features, C preprocessor branches. Ruff marks some RUF100 fixes unsafe (other comments sharing the line). The prevalence data is one ecosystem: 50.8% of 1,873 Pylint suppressions were useless (10 Python projects, FSE 2025).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [An Empirical Study of Suppressed Static Analysis Warnings](https://software-lab.org/publications/fse2025_suppressions.pdf) (Hu, Wang, Rubin, Pradel, FSE 2025); [ESLint CLI reference](https://eslint.org/docs/latest/use/command-line-interface) (ESLint v10.11.0, 2026); [Configure Rules](https://eslint.org/docs/latest/use/configure/rules) (ESLint, 2026); [Bulk Suppressions](https://eslint.org/docs/latest/use/suppressions) (ESLint, 2026); [Pyright configuration](https://raw.githubusercontent.com/microsoft/pyright/main/docs/configuration.md) (Microsoft, 2026); [RUF100 unused-noqa](https://docs.astral.sh/ruff/rules/unused-noqa/) (Astral, 2026); [The mypy command line](https://mypy.readthedocs.io/en/stable/command_line.html) (mypy 2.3.1, 2026); [Announcing Rust 1.81.0](https://blog.rust-lang.org/2024/09/05/Rust-1.81.0/) (Rust Release Team, 2024); [nolintlint configuration](https://golangci-lint.run/docs/linters/configuration/) (golangci-lint, 2026); [The Baseline](https://phpstan.org/user-guide/baseline) (PHPStan, 2026) · dossier: types-static-analysis T18-F12, T18-F03, T18-F09

### TY-04 — Every suppression names the exact rule, covers the smallest scope and gives a reason
- **Rule:** Flag every suppression that does not name the exact rule or code, cover only the next line or expression, and give a reason; propose the narrow form (`# type: ignore[code]`, `# noqa:` with a code, `eslint-disable-next-line <rule> -- reason`, `//nolint:<linter>` with an explanation, `NOLINT(<check>)`, `#[expect(lint, reason = "…")]`, `@SuppressWarnings` on the variable rather than the class), and send each rewrite through the change protocol's suppression approval (PC-08: each approved line recorded with `run_state.py allow-line <path> --text "<line>" --reason <finding id>`). For TypeScript use this order: a real fix; else `@ts-expect-error -- reason` through that same approval; `@ts-ignore` only where this rule's Not when allows it; never a new `@ts-nocheck` (ban-ts-comment's recommended config bans it). When the tool behind a blanket suppression (a bare `eslint-disable`, `# type: ignore` or `# noqa`) is not installed, do not demote the item for that reason (eval-v2-calibration E02-F05). Inside the approved item, the orchestrator removes the blanket directive, runs the tool through a pinned ephemeral runner at an exact version (PF-21) with the project's config, or a temporary config under `.harden/tools/` when the project has none (procedure step 3), and records the rule ids it reports inside the formerly suppressed scope. The narrowed suppression names those ids and carries this rule's reason in the same commit; a rule id without its reason leaves the finding open. If the run reports nothing there, the suppression suppresses nothing: handle it under TY-03. The run stays within the Phase 0 network and side-effect decisions; when they forbid it, report the item with its hidden rules unlisted and name the skipped run under Limits.
- **Detect:** TS/JS: `rg -n '@ts-ignore|@ts-nocheck'`, `rg -n '@ts-expect-error\s*$'`, `rg -nP 'eslint-disable(-next-line|-line)?\s*(\*/|$)'`; typescript-eslint ban-ts-comment (recommended bans ts-ignore and ts-nocheck and allows ts-expect-error with a description of at least 3 characters, 10 in strict); eslint-comments no-unlimited-disable and require-description. Python: `rg -nP '#\s*type:\s*ignore(?!\[)'`, `rg -nP '#\s*noqa(?!:)'`, Ruff PGH003, mypy `ignore-without-code`. Go: `rg -nP '//nolint(?!:)'`, nolintlint require-specific and require-explanation (both default false). C/C++: `rg -nP 'NOLINT(NEXTLINE|BEGIN)?(?!\()'` (whitespace before "(" silently makes it a plain `NOLINT`). Rust: `rg -n '#!?\[allow\('`, clippy allow_attributes_without_reason. Java: `rg -n -B1 '@SuppressWarnings' -g '*.java'`, flagging class-level annotations. Missing tool: the pinned ephemeral run's raw output goes under `.harden/tools/` with tool@version, and its rule ids inside the formerly suppressed lines are the narrowing list. In a narrowing commit, read every added suppression line from `git diff -U0 <sha>^ <sha> | rg '^\+.*(eslint-disable|@ts-expect-error|type:\s*ignore|noqa|nolint|NOLINT|#!?\[(allow|expect)\()'`: each names a rule id and gives a reason.
- **Not when:** The TypeScript team accepts `@ts-ignore` for unowned code in large projects and during compiler upgrades: report those, do not convert them. TypeScript has no per-error-code suppression because its codes are not stable across versions, so the description stands in for the rule name. Narrowing a broad suppression exposes what it hid (one file-level Pylint suppression hid 56 later warnings beyond its original 3); each exposed warning becomes its own candidate, never a new broad suppression. Mandatory reasons can decay into boilerplate ("-- legacy"). The dossier's TypeScript order puts "a more tactical `as any`" (Cavanaugh) before `@ts-expect-error`; this skill drops it, because protocol-change PC-08 bans new escape-hatch types.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [An Empirical Study of Suppressed Static Analysis Warnings](https://software-lab.org/publications/fse2025_suppressions.pdf) (Hu et al., FSE 2025); [mypy error codes](https://mypy.readthedocs.io/en/stable/error_codes.html) (mypy, 2026); [PGH003 blanket-type-ignore](https://docs.astral.sh/ruff/rules/blanket-type-ignore/) (Astral, 2026); [ban-ts-comment](https://typescript-eslint.io/rules/ban-ts-comment/) (typescript-eslint, 2026); [TypeScript 3.9 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-9.html) (Microsoft, 2020); [Comment on TypeScript #19139](https://github.com/microsoft/TypeScript/issues/19139#issuecomment-690530124) (Cavanaugh, 2020); [@ts-ignore is almost always the worst option](https://evanhahn.com/ts-ignore-is-almost-always-the-worst-option/) (Hahn, 2025); [Configure Rules](https://eslint.org/docs/latest/use/configure/rules) (ESLint, 2026); [eslint-comments rules](https://eslint-community.github.io/eslint-plugin-eslint-comments/rules/) (ESLint Community, 2026); [nolintlint configuration](https://golangci-lint.run/docs/linters/configuration/) (golangci-lint, 2026); [Suppressing undesired diagnostics](https://clang.llvm.org/extra/clang-tidy/) (LLVM, 2026); [Announcing Rust 1.81.0](https://blog.rust-lang.org/2024/09/05/Rust-1.81.0/) (Rust, 2024); [Clippy allow_attributes_without_reason](https://rust-lang.github.io/rust-clippy/master/index.html#allow_attributes_without_reason) (Clippy, 2026); [Effective Java, Item 27](https://www.informit.com/articles/article.aspx?p=2861454&seqNum=2) (Bloch, 2018) · dossier: types-static-analysis T18-F11 (and its Contradictions entry), practitioner voice; eval-v2-calibration E02-F05

### TY-05 — Tighten by baseline or scope, and let a baseline only shrink
- **Rule:** Never propose tightening a finished codebase big-bang. Recommend either a committed, location-keyed baseline (ESLint bulk suppressions in `eslint-suppressions.json`, basedpyright baseline, PHPStan baseline, golangci-lint `new-from-merge-base`/`new-from-rev`, Betterer, eslint-seatbelt per-file counts, clang-tidy-diff.py on changed lines) or strictness scoped per file or module (a separate strict tsconfig with an allow-list, C# `#nullable enable`, mypy per-module sections, pyright `strict` paths, Sorbet `# typed:` sigils), so new and changed code is clean from day one. Flag any baseline that grew or was regenerated to absorb new errors: it may only shrink.
- **Detect:** Look for `eslint-suppressions.json`, `.basedpyright/baseline.json`, `phpstan-baseline.neon`, `.betterer.results` or a ratchet TSV; `git log -p --stat -- <baseline>` must show only removals after creation. CI must fail on unmatched entries: ESLint does by default; PHPStan needs reportUnmatchedIgnoredErrors not set to false. Size a proposed baseline from tool output only.
- **Not when:** Count ratchets get gamed ("Add one, remove one was very common") and are opaque, so prefer baselines keyed by location. Ratchets stop spread but do not remove old instances (qntm: about 67 calls left "kind of lingering"). Line-keyed baselines break under refactoring (basedpyright matches file, rule and column instead); how ESLint v10 bulk suppressions match after code moves was not verified.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Bulk Suppressions](https://eslint.org/docs/latest/use/suppressions) (ESLint v10.11.0, 2026); [Baseline](https://docs.basedpyright.com/latest/benefits-over-pyright/baseline/) (basedpyright, 2026); [The Baseline](https://phpstan.org/user-guide/baseline) (PHPStan, 2026); [Configuration file](https://golangci-lint.run/docs/configuration/file/) (golangci-lint, 2026); [Scaling Static Analyses at Facebook](https://6826.csail.mit.edu/2020/papers/facebook-infer-cacm.pdf) (Distefano et al., CACM 2019); [Notion's ratcheting system](https://www.notion.com/blog/how-we-evolved-our-code-notions-ratcheting-system-using-custom-eslint-rules) (Notion, 2025); [Sorbet strictness levels](https://sorbet.org/docs/static) (Stripe, 2026); [Ratchets in software development](https://qntm.org/ratchet) (qntm, 2021); [Strict null checking VS Code](https://code.visualstudio.com/blogs/2019/05/23/strict-null) (VS Code team, 2019); [HN Normal_gaussian](https://news.ycombinator.com/item?id=46857352) (2026); [HN arnorhs](https://news.ycombinator.com/item?id=46854450) (2026) · dossier: types-static-analysis T18-F09, practitioner voice

### TY-06 — A kept check fails CI; blanket -Werror stays out of shipped build files
- **Rule:** Report every check the project keeps at warning level: it must fail CI (ESLint `--max-warnings 0`, rustc/clippy `-D warnings` in CI, `clang-tidy --warnings-as-errors=<checks>`, `-Werror` in a CI or developer preset) or be turned off. Report blanket `-Werror` hard-coded in build files that downstream users or packagers compile, and recommend selective `-Werror=<flag>` or a CI-only toggle instead.
- **Detect:** `eslint --no-warn-ignored -f json "${F[@]}" | jq '[.[].warningCount]|add'`, with `F` the in-scope JS and TS files (detection step 4; never `.`), should be 0, or each warning rule set to "off" or "error"; `rg -n -- '--max-warnings|-D warnings|--warnings-as-errors|-Werror' .github/ .gitlab-ci.yml Jenkinsfile`; `rg -n -- '-Werror(\s|"|$)' CMakeLists.txt '*.cmake' Makefile* meson.build configure.ac setup.py build.rs`; CMake `COMPILE_WARNING_AS_ERROR` can be overridden with `--compile-no-warning-as-error`.
- **Not when:** Apps built only by their own team may keep blanket `-Werror` in CI. Making everything an error before the baseline is clean reproduces the Linux 5.15 episode ("nearly all of our CI to go red"): pair this rule with TY-05.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Lessons from Building Static Analysis Tools at Google](https://storage.googleapis.com/gweb-research2023-media/pubtools/4365.pdf) (Sadowski et al., CACM 2018); [Notion's ratcheting system](https://www.notion.com/blog/how-we-evolved-our-code-notions-ratcheting-system-using-custom-eslint-rules) (Notion, 2025); [Compiler Options Hardening Guide for C and C++](https://best.openssf.org/Compiler-Hardening-Guides/Compiler-Options-Hardening-Guide-for-C-and-C++.html) (OpenSSF, 2026); [Gentoo common mistakes](https://devmanual.gentoo.org/ebuild-writing/common-mistakes/index.html) (Gentoo, 2026); [Linux kernel -Werror compromise](https://www.theregister.com/2021/09/08/compromise_linux_kernel_compiler_warnings/) (The Register, 2021) · dossier: types-static-analysis T18-F07; eval-v2-calibration E02-F08

### TY-07 — Pin analyzer versions and revisit stale configs
- **Rule:** Report analyzers (compiler, type checker, linter, shared presets such as typescript-eslint's strict configs, which change outside semver majors) that are not pinned exactly through a lockfile plus exact specifiers or a toolchain file, and recommend upgrading them only in dedicated reviewed changes. Compare the analyzer config with the presets of the installed versions and report options deprecated for the next major (TypeScript 6.0 deprecates `--moduleResolution node`, `--baseUrl`, `--target es5`, `--module amd/umd/systemjs` and `esModuleInterop false` for removal in 7.0, where `"ignoreDeprecations": "6.0"` stops working). Because `strict` and mypy `--strict` gain checks over time, compare counts across runs only under the same pinned version and config.
- **Detect:** `jq '.devDependencies|to_entries[]|select(.key|test("typescript|eslint|biome|oxlint"))' package.json`, flagging `^` or `~` (including `@typescript-eslint/*`); `rg -n 'mypy|pyright|ruff' requirements*.txt pyproject.toml`, flagging unpinned entries; a missing `rust-toolchain.toml`; `git log -1 --format='%cs %s' -- tsconfig*.json eslint.config.* .eslintrc* mypy.ini pyproject.toml clippy.toml .clang-tidy`; deprecation diagnostics from `tsc --noEmit` or an existing `ignoreDeprecations`.
- **Not when:** Pinning delays new checks and security fixes, and automated bumps add noise. Beller's "configs, once committed, never change" data is from 2016 (Java, JS, Ruby, Python analyzers); the instability of TypeScript error codes is a design statement (Cavanaugh, 2020), not a measurement.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A

### TY-08 — Enable curated diagnostic sets; pick aggressive checks one by one

### TY-13 — Inventory escape hatches and ratchet them down

### TY-14 — Never turn a crash into a silent default
- **Rule:** When a fix removes a non-null assertion, write down the current behaviour (a crash) and the intended behaviour for an absent value, and keep the failure loud unless the owner confirms that absence is a valid state; never mechanically rewrite `x!.y` as `x?.y` or `x?.y ?? fallback`. Never accept typescript-eslint no-non-null-assertion's suggestion fixer, which rewrites `!.` to `?.`. Treat the reverse direction, replacing `default: return fallback` with a throwing assertNever, as a behaviour change too.
- **Detect:** For each proposed `!` removal, compare old and new outcomes for a null or undefined input, and flag any `?.` or `??` that replaces a `!` without an approved test showing the new behaviour. For each proposed exhaustiveness change (TY-17), check whether out-of-range runtime values used to receive a fallback.
- **Not when:** When the owner confirms that absence is expected, an optional chain or default with a test is the right fix. typescript-eslint calls the optional chain "safer" because it no longer crashes; that is true, and so is the cost: the failure becomes silent. Either way the change is behavioural: its own commit, a test, explicit approval.

### TY-15 — Keep a runtime check a type-aware rule calls unnecessary until its origin is proven type-safe
- **Rule:** Do not propose deleting a condition, comparison, cast or branch reported as always true or false, unnecessary or unreachable until a manual trace shows the value's origin is type-safe. TypeScript does not aim for soundness, and the TS 3.9 notes show a library keeping runtime asserts for JavaScript callers its types already forbid.
- **Not when:** In fully typed internal code with a traced type-safe origin the rule is usually right, and deleting the dead check is a structural change. Keeping every defensive check adds noise, and widening a type may produce more errors elsewhere.

### TY-16 — Parse, don't validate: convert untrusted data once, at each I/O boundary

- **Detect:** TS: `rg -n 'JSON\.parse\(|\.json\(\)|process\.env\.|axios\.|fetch\(' -g '*.ts'`. Python: `rg -n 'json\.loads\(|os\.environ|requests\.|httpx\.|\.fetchone\(|\.fetchall\(' -g '*.py'`. ## False-positive exclusions

- A suppression that looks unused under one configuration but is needed under another: other language versions, platform stubs, Rust cfg features, C preprocessor branches (TY-03). Confirm across the whole CI matrix first.
- `@ts-ignore` in unowned code or during a compiler upgrade: report, do not convert (TY-04).
- A TypeScript suppression without an error code: TypeScript has none to give; judge the description instead (TY-04).
- Entries already in a committed baseline: known debt; only new, grown or regenerated entries are findings (TY-05).
- A check the project deliberately turned off: report its size, never override the config.
- Blanket `-Werror` in a CI-only preset, or in an app built only by its own team (TY-06).
- `-Weverything` where the project addresses every new diagnostic as it lands (TY-08).
- `any`, casts and `unknown` at FFI boundaries, around untyped libraries and for generics that cannot yet be expressed; cast-based constructors of branded types (TY-13, TY-19).
- An "unnecessary condition" whose value comes from an untyped origin: the check is live (TY-15).
- Default branches over open sets such as server-grown API enums or plugin IDs (TY-17).
- Annotations read at runtime by pydantic, FastAPI, dataclasses or ORMs: changing them is a behaviour change, not type hygiene (TY-12).
- A lower error count or higher type coverage from a different tool version or config: not comparable, never an improvement (TY-07).
- Any grep hit from a Detect pattern before the code was read: a lead, not a finding.

## Evidence limits

- Bug share of static types: Gao et al. (ICSE 2017; 400 public JavaScript bugs; Flow 0.30 and TypeScript 2.0) found 60 each detectable, 15% (95% CI 11.5–18.5%); among bugs neither checker caught, 55% were specification errors and 78% errors implementing the specification. Khan et al. (TSE 2021; 210 Python projects; mypy) found 15% of corrective defects (11% of all), with null handling caught most. Both are lower bounds on 2016-era checkers.
- Static bug detectors found 27 of 594 Defects4J bugs (4.5%; Java; ASE 2018). Cross-language comparisons find "exceedingly small" effects (TOPLAS 2019; the original authors agree the effects are small). Bogner & Merkel (MSR 2022; 604 GitHub repos) found a higher mean bug-fix commit ratio in TypeScript than JavaScript (0.206 vs 0.126). The "38% of Airbnb bugs" figure has no traceable method: never cite it.
- False-positive budgets: Google (CACM 2018) is one company's policy; its 2009 FindBugs Fixit fixed 16% (640) of 3,954 reviewed warnings. Microsoft (ASE 2016; 375 of 2,000 invited developers): 90% accept up to 5% false positives, 47% up to 15%, 24% up to 20%. Infer (CACM 2019): near-zero batch fix rate from only 20–30 assigned issues, over 70% at diff time.
- Suppressions: the usefulness data (FSE 2025) covers 10 Pylint-using Python projects: 50.8% of 1,873 suppressions useless (36.5% at file level to 60.7% at block level); in 1,537 histories, 59 suppressions hid at least 184 later warnings, 36 of those 59 after a change by a different author, 230.8 days later on average; 7,357 suppressions across 46 Python projects, one per six code files. Staleness in ESLint, TypeScript or Rust suppressions is unmeasured. The paper's statement that mypy lacks unused-ignore reporting contradicts the mypy docs: trust tool docs for capabilities.
- NullAway (ESEC/FSE 2019; Uber; Java): remaining production NPEs came from unchecked third-party libraries (64%), deliberate suppressions (17%) and reflection or post-checking code modification (17%).
- Config staleness (Beller et al., SANER 2016; Java, JavaScript, Ruby, Python analyzers) is ten-year-old data.
- No study quantifies extra defects caught by beyond-strict TypeScript flags, by strict-type-checked over recommended-type-checked, or by type-design practices (discriminated unions, newtypes, branded types): TY-09, TY-11, TY-18 and TY-19 rest on vendor guidance and practitioner consensus.
- Whether baselines and ratchets drive legacy violations to zero is anecdotal (Notion positive, qntm "lingering").
- That AI-written code carries more escape hatches is supported only by practitioner anecdotes; Mündler et al. 2025 was not verified.
- A missing tool never demoting a blanket suppression (TY-04: a pinned ephemeral run lists what it hides, and the narrowed form carries its reason in the same commit) comes from the skill's own v2 evaluation (eval-v2-calibration E02-F05, 4 instances, grade C), not from an external study.
- Not assessed: Rust-based Python checkers (Pyrefly, Ty, Zuban), Oxlint and Biome type-aware rules, Kotlin (detekt baseline), Go beyond golangci-lint, Java Error Prone rollout, Solidity analyzers, and ESLint v10 bulk-suppression matching under refactoring.
- The Python Typing Survey 2025 (1,241 self-selected responses): 86% use type hints "always" or "often"; 58% use mypy. It describes adoption, not defect outcomes.
- Tool facts were checked on 2026-09-23 against TypeScript 6.0 (strict on by default), typescript-eslint v8.70.1, ESLint v10.11.0, mypy 2.3.1, Clang-Tidy docs 24.0.0git, the OpenSSF guide dated 2026-08-20 and Zod 4. They apply when those versions are in use; re-check flags and defaults otherwise.
