# Language: C and C++

> Purpose: detect the C/C++ toolchain before relying on it, then run warnings, sanitizers, clang-tidy, clangd, dead-code and fuzz tooling with the limits their own docs state, and report the language traps that need an owner.
> Read when: a C or C++ source, header or build file is in scope (`.c`, `.cc`, `.cpp`, `.cxx`, `.h`, `.hh`, `.hpp`, `.hxx`, `CMakeLists.txt`, `CMakePresets.json`, `compile_commands.json`).

## Contents
- Tooling baseline: CP-01–06 toolchain detection, versions, warnings baseline, sanitizer matrix, clang-tidy selection, complexity ranking
- Autofix safety: CP-07–09 one fix-it check per commit, known-unsafe fix-its, clang-format
- Refactoring engines: CP-10–14 clangd rename, post-edit verification, extract tweaks, engine-less operations, Windows paths
- Dead code and dependencies: CP-15–18 compiler-proven unused code, whole-program candidates, unused parameters, include cleanup
- Language traps: CP-19–36 library and flag hardening, assertions and contracts, ownership, lifetimes, bounds, class semantics, casts, initialisation, integers, error model, concurrency, headers, const, format strings
- Test, mutation and fuzz tooling: CP-37–42 targeting, sanitizer fuzz builds, harness rules, triage, budgets, regression replay
- Evidence limits

## Tooling baseline

### CP-01 — Detect the toolchain before any build-dependent rule
- **Rule:** Detect, never assume, which compilers, analysers and build metadata exist, and record each version under `.harden/tools/`. When no working compiler is found, run only text-based detection, mark every rule that needs a build "not run: toolchain absent" in the report's Limits, and keep every C/C++ change report-only: each engine or fix-it edit needs a compile gate, and none can run. Fall back to WSL2 or Docker only for a tool whose official docs exclude Windows.
- **Detect:** `uname -s` (MINGW64 means native Windows); `wsl --status`; `clang-cl --version`; `cl` (VS 2022 17.0 or later); `gcc --help=hardened` on GNU/Linux; presence of `compile_commands.json`, `CMakePresets.json`, `.clang-tidy`, `.clang-format`; existing sanitizer setup: `rg -n 'fsanitize' CMakeLists.txt CMakePresets.json cmake .github`.
- **Not when:** A toolchain that exists only inside WSL2 is usable, but record per tool whether it ran natively or under WSL2, and expect file-system overhead when the repository lives on NTFS. A red build baseline is handled by the preflight protocol as a report-only run.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [An Empirical Study of Refactoring Engine Bugs](https://arxiv.org/html/2409.14610v1) (Wang et al., 2024); [/fsanitize (Enable sanitizers)](https://learn.microsoft.com/en-us/cpp/build/reference/fsanitize) (Microsoft, 2026); [AFL++ INSTALL.md](https://github.com/AFLplusplus/AFLplusplus/blob/stable/docs/INSTALL.md) (AFL++ team, 2026) · dossier: agent-refactoring-engines G105-F02; fuzz-property-hardening G206-F16, G206-F20, G206-F09

### CP-02 — Use the project's tools and pin every version you record
- **Rule:** Prefer the project's own compiler, presets, `.clang-tidy`, `.clang-format` and pinned tool versions; pass detection-only flags on the command line or in a build directory under the run's scratch directory `<scratch_dir>` (`scratch_dir` in `.harden/active`, printed by `run_state.py status`; outside the repository, protocol-preflight PF-21), never by editing the project's configuration. Record the exact version of every tool run: clang-tidy checks and options differ by release, the clang-tidy docs describe trunk (24.0.0git) while the newest LLVM release was 23.1.2 (released 2026-09-22) when checked on 2026-09-23; re-check it before a run. IWYU 0.26 pairs with Clang 22. No dossier verifies a `pnpm dlx`, `uvx` or `cargo install` package for clang-tidy, clangd, cppcheck or IWYU: do not improvise one. The only verified ephemeral download is the clangd 22.1.6 release asset `clangd-windows-22.1.6.zip` (28,198,778 bytes, 2026-05-28): unzip it under `.harden/tools/clangd/`, where tool binaries stay (never in `<scratch_dir>` or another directory: protocol-preflight PF-21; eval-v2-calibration E02-F08), and check the size.
- **Detect:** Compare each tool's version with the project's pin (Firefox, for example, pins clang-tidy 22.1.8 in `tools/clang-tidy/config.yaml`); `clang-tidy --list-checks -checks='-*,bugprone-*,clang-analyzer-core.*' -p build` shows which checks the binary actually has.
- **Not when:** A project with no pinned version: record what ran and flag results as version-dependent (newer modernize-use-emplace also flags temporaries inside emplace calls). clang-change-namespace, clang-move and clang-apply-replacements are not in the clangd zip.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Clang-Tidy documentation](https://clang.llvm.org/extra/clang-tidy/) (LLVM, 2026); [Firefox tools/clang-tidy/config.yaml](https://raw.githubusercontent.com/mozilla-firefox/firefox/main/tools/clang-tidy/config.yaml) (Mozilla, 2026); [clangd release 22.1.6](https://github.com/clangd/clangd/releases/tag/22.1.6) (clangd, 2026); [include-what-you-use README](https://github.com/include-what-you-use/include-what-you-use) (IWYU project, 2026) · dossier: lang-cpp T23-F07, T23-F08; agent-refactoring-engines G105-F08; dead-code-tools T07-F11; eval-v2-calibration E02-F08

### CP-03 — Record a warnings baseline in a scratch build before changing code
- **Rule:** Build once out of tree, in a build directory under `<scratch_dir>` (CP-02), with the target warnings and count them per warning and per file: GCC/Clang `-Wall -Wextra -Wpedantic -Wshadow -Wold-style-cast -Woverloaded-virtual -Wformat=2 -Wimplicit-fallthrough`; MSVC `/W4 /permissive-`. Fixes go through the trap rules below. Propose `-Werror` or `/WX` for developer and CI builds only, never for distributed source or release builds compiled by toolchains the project does not control.
- **Detect:** Configure with `cmake -S . -B "<scratch_dir>/build-warnings" -DCMAKE_EXPORT_COMPILE_COMMANDS=ON` plus the target warnings and inspect each TU's flags; `cmake --build "<scratch_dir>/build-warnings" 2>&1 | grep -c 'warning:'`. `build` in this file's commands (`-p build`, `build/compile_commands.json`, `cmake --build build`) is the project's own build directory when it already has one, else this scratch build directory; existing suppressions: `rg -n -- '-w\b|-Wno-|/wd[0-9]+|#pragma (GCC|clang) diagnostic ignored|#pragma warning\(disable' CMakeLists.txt cmake src include`; third-party headers must come in through `-isystem`.
- **Not when:** Evidence that fixing warnings pays off "stems from grey literature or is anecdotal" (Kudrjavets et al., 2022). `-Weffc++` and MSVC `/Wall` are documented as too noisy. Prefer GCC's `-Wdelete-non-virtual-dtor` (in `-Wall`, no false positives) over `-Wnon-virtual-dtor`. Microsoft recommends `/WX` for new projects while OpenSSF rejects blanket `-Werror` in distributed source: both hold when `-Werror` stays in developer and CI builds. Editing the project's build files is an owner decision.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Compiler Options Hardening Guide for C and C++](https://best.openssf.org/Compiler-Hardening-Guides/Compiler-Options-Hardening-Guide-for-C-and-C++.html) (OpenSSF, 2026); [Warning level](https://learn.microsoft.com/en-us/cpp/build/reference/compiler-option-warning-level) (Microsoft, 2022); [Lessons from Building Static Analysis Tools at Google](https://cacm.acm.org/research/lessons-from-building-static-analysis-tools-at-google/) (Sadowski et al., 2018); [The Unexplored Terrain of Compiler Warnings](https://arxiv.org/abs/2201.10599) (Kudrjavets et al., 2022) · dossier: lang-cpp T23-F01, T23-F10; eval-v2-calibration E02-F08

### CP-04 — Run the existing tests under a sanitizer matrix
- **Rule:** Run the whole test suite and any fuzz targets, before and after the pass, in out-of-tree builds under `<scratch_dir>` (CP-02): (1) `-fsanitize=address,undefined -fno-omit-frame-pointer -O1 -g -fno-sanitize-recover=all`; (2) `-fsanitize=thread` on its own, with every TU instrumented; MSVC: `/fsanitize=address /Zi` with `/RTC1`, `/ZI` and `/INCREMENTAL` off. Keep `_FORTIFY_SOURCE` out of sanitizer builds and sanitizer runtimes out of shipped binaries. Each report is a finding; its fix follows the trap rules.
- **Detect:** Pair every run with llvm-cov or gcov branch coverage, because sanitizers see only executed paths; triage the first UBSan run by check type.
- **Not when:** Cost: ASan about 2x, TSan 5–15x slower with 5–10x memory (LLVM docs); 2–4x on average (OpenSSF). TSan cannot be combined with ASan or LSan, and uninstrumented libraries make it miss races or report false ones. MSVC offers ASan only (x86/x64): use clang in WSL2 for UB and races. ASan misses library-level UB such as `pop_back()` on an empty vector (CP-19). A first UBSan run can be noisy: about 11k unique warnings from 32 desktop programs (preprint, 2026). With no tests, write smoke tests first or the sanitizers see nothing.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [AddressSanitizer](https://clang.llvm.org/docs/AddressSanitizer.html) (LLVM, 2026); [ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html) (LLVM, 2026); [AddressSanitizer (MSVC)](https://learn.microsoft.com/en-us/cpp/sanitizers/asan) (Microsoft, 2026); [Compiler Options Hardening Guide](https://best.openssf.org/Compiler-Hardening-Guides/Compiler-Options-Hardening-Guide-for-C-and-C++.html) (OpenSSF, 2026); [Undefined Behavior in C and C++: An Experiment With Desktop Use Cases](https://arxiv.org/abs/2606.12064) (Ruohonen, Sierszecki, 2026) · dossier: lang-cpp T23-F06; fuzz-property-hardening G206-F09; eval-v2-calibration E02-F08

### CP-05 — Choose clang-tidy checks by measured signal
- **Rule:** Use the project's `.clang-tidy` when it exists. Otherwise start from `-*` and enable bug-finding checks that large projects run: Chromium's bugprone-use-after-move, bugprone-dangling-handle, bugprone-unused-raii, bugprone-assert-side-effect, bugprone-undefined-memory-manipulation, bugprone-unique-ptr-array-mismatch, bugprone-string-constructor and clang-analyzer-core.uninitialized.\*, plus bugprone-sizeof-expression and bugprone-swapped-arguments (rated "high" in Mozilla's legacy list). Keep contested style checks (magic numbers, trailing return types, use-auto, implicit-bool-conversion, else-after-return) out unless the project uses them, and drop or tune a check whose sampled false-positive rate exceeds about 10% (Google Tricorder's threshold, CACM 2018).
- **Detect:** `run-clang-tidy -p build -checks='<set>' -export-fixes=.harden/tools/clang-tidy.baseline.yaml > .harden/tools/clang-tidy.baseline.txt`; count findings per check and sample about 10 each; bare suppressions: `rg -P -n 'NOLINT(NEXTLINE|BEGIN)?\b(?!\()'`; cppcheck baseline: `cppcheck --enable=style --xml src 2> .harden/tools/cppcheck.baseline.xml` (outputs go to `.harden/tools/`, never the repository root; detection DT-07), then its `generate-baseline-suppressions.py` (main-branch manual; may postdate released versions).
- **Not when:** Practitioner consensus, not a controlled study. Noise depends on the codebase: Mozilla's macros make modernize-use-override noisy while Chromium enables it, and cpp-best-practices' cmake_template starts from `*` and tunes down. On OpenZFS, cross-TU analysis turned about 80 mostly false-positive reports into 300–400. Suppress only with a named check, `// NOLINT(check-name)`, plus a written reason.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [Lessons from Building Static Analysis Tools at Google](https://cacm.acm.org/research/lessons-from-building-static-analysis-tools-at-google/) (Sadowski et al., 2018); [Chromium .clang-tidy](https://raw.githubusercontent.com/chromium/chromium/main/.clang-tidy) (Chromium, 2026); [Firefox tools/clang-tidy/config.yaml](https://raw.githubusercontent.com/mozilla-firefox/firefox/main/tools/clang-tidy/config.yaml) (Mozilla, 2026); [Cppcheck manual](https://github.com/danmar/cppcheck/blob/main/man/manual.md) (Cppcheck project, 2026); [HN comment on OpenZFS cross-TU analysis](https://news.ycombinator.com/item?id=34093384) (ryao, 2022) · dossier: lang-cpp T23-F07; eval-v2-calibration E02-F08

### CP-06 — Rank with complexity checks; never gate on them
- **Rule:** Use readability-function-cognitive-complexity (default threshold 25, SonarSource specification 1.2) and readability-function-size only to rank refactoring candidates, treat Google's "about 40 lines" as a prompt to consider splitting, and refactor a flagged function only when tests cover it.
- **Detect:** `run-clang-tidy -p build -checks='-*,readability-function-cognitive-complexity,readability-function-size'`, cross-referenced with git churn.
- **Not when:** No source consulted derives 25 empirically. Macro-heavy code distorts scores (IgnoreMacros defaults to false). Generated code, table-driven parsers and state machines legitimately exceed the thresholds.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** C
- **Source:** [readability-function-cognitive-complexity](https://clang.llvm.org/extra/clang-tidy/checks/readability/function-cognitive-complexity.html) (LLVM, 2026); [readability-function-size](https://clang.llvm.org/extra/clang-tidy/checks/readability/function-size.html) (LLVM, 2026); [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html) (Google, 2026) · dossier: lang-cpp T23-F19

## Autofix safety

### CP-07 — Apply clang-tidy fix-its one check per commit
- **Rule:** Apply fix-its for one check id at a time, each in its own commit, then rebuild and run the tests, under ASan/UBSan where available. Never run `-fix` with a broad glob and never add `-fix-errors`: without it clang-tidy bails out when the code does not compile. Keep one pinned clang-tidy version for the whole pass.
- **Detect:** `run-clang-tidy -p build -checks='-*,<one-check>' -fix`, then `cmake --build build && ctest --test-dir build`, then commit; use `-export-fixes` plus clang-apply-replacements when the fixes must be reviewed before applying.
- **Not when:** Teams batch trivially safe checks such as modernize-use-nullptr; keep them one check id per commit anyway so a regression bisects to one check. The clang-tidy docs record semantic changes and build breaks for several fix-its, so no fix-it is T0 here. With no working build (CP-01), apply none.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [Clang-Tidy documentation](https://clang.llvm.org/extra/clang-tidy/) (LLVM, 2026); [modernize-loop-convert](https://clang.llvm.org/extra/clang-tidy/checks/modernize/loop-convert.html) (LLVM, 2026); [Firefox tools/clang-tidy/config.yaml](https://raw.githubusercontent.com/mozilla-firefox/firefox/main/tools/clang-tidy/config.yaml) (Mozilla, 2026); [HN comment on clang-tidy output](https://news.ycombinator.com/item?id=42405952) (kimixa, 2024); [llvm-project #33239](https://github.com/llvm/llvm-project/issues/33239) (2017) · dossier: lang-cpp T23-F08; agent-refactoring-engines G105-F08; autofix-trust G105-F07

### CP-08 — Review every hunk from the known-unsafe fix-its
- **Rule:** Review by hand each hunk from: modernize-loop-convert (keep MinConfidence at `reasonable` or `safe`; a loop body that modifies the container changes meaning because `.end()` is evaluated once, and side effects of an overloaded `operator->()` are lost); modernize-use-emplace (set IgnoreImplicitConstructors=true; `emplace_back(Widget(...))` keeps the temporary and gains nothing); modernize-use-transparent-functors (SafeMode; Chromium recorded build breaks); performance-unnecessary-value-param and misc-unused-parameters (they change signatures and can break other TUs); modernize-use-auto (contested); cppcoreguidelines-init-variables (inserts arbitrary defaults).
- **Detect:** After each fix-it commit, read the diff for signature lines, container loops and `emplace` calls; flag any hunk in an exported header.
- **Not when:** A signature change on a function exported from a library is a public API change: report it (T2). modernize-use-emplace and O'Dwyer's "Use push_back by default" conflict; resolve with IgnoreImplicitConstructors=true, as Chromium does.
- **Tier:** T1 · **Class:** structural · **Fix risk:** high · **Grade:** A
- **Source:** [modernize-use-emplace](https://clang.llvm.org/extra/clang-tidy/checks/modernize/use-emplace.html) (LLVM, 2026); [Don't blindly prefer emplace_back to push_back](https://quuxplusone.github.io/blog/2021/03/03/push-back-emplace-back/) (O'Dwyer, 2021); [Chromium .clang-tidy](https://raw.githubusercontent.com/chromium/chromium/main/.clang-tidy) (Chromium, 2026); [performance-unnecessary-value-param](https://clang.llvm.org/extra/clang-tidy/checks/performance/unnecessary-value-param.html) (LLVM, 2026) · dossier: lang-cpp T23-F08, T23-F14

### CP-09 — Run clang-format only where the project enforces it, on touched files
- **Rule:** Run the project's clang-format only when the repository has a `.clang-format` it already enforces, only on files the pass touched, and commit format-only changes separately from semantic ones. clangd tweaks reformat touched lines by `.clang-format` (LLVM style when there is none) and reformatted an untouched signature line in one run: revert such hunks.
- **Detect:** `clang-format --dry-run -Werror` on touched files; compare `git diff --stat` with `git diff -w --stat`; `git ls-files --eol | rg 'w/mixed'`.
- **Not when:** No `.clang-format`, or no enforcement in CI: do not format; only line-ending normalisation applies. Formatting whole files pulls old drift into the commit.
- **Tier:** T0 · **Class:** structural · **Fix risk:** low · **Grade:** C
- **Source:** [HN comment: codemod pipeline with prettier](https://news.ycombinator.com/item?id=40694419) (striking, 2024); [LibCST codemod docs](https://libcst.readthedocs.io/en/latest/codemods.html) (Instagram/Meta, 2026) · dossier: agent-refactoring-engines G105-F14, G105-F08

## Refactoring engines

### CP-10 — Rename only through an indexed clangd, and check its coverage
- **Rule:** Route every C/C++ rename through clangd (clang-rename was removed in LLVM 20): require `compile_commands.json`, start clangd with `--background-index`, and wait for the `$/progress` end notification before renaming. Before applying, compare the files in the WorkspaceEdit with the files from `textDocument/references`; abort if any referencing file is missing.
- **Detect:** CMake projects: `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`; a rename touching more than 50 files fails unless clangd runs with `--rename-file-limit=0` (default 50, release/22.x); a multi-file identifier change with no engine call in the transcript (several Edit or sed calls on one name) is a violation.
- **Not when:** Without an index, clangd returned a single-file edit and no error (one fixture, 2026). clangd documents that references in templates, macro bodies, comments and disabled preprocessor sections may not be renamed, and that overrides are not renamed. References and rename share one index, so a stale index makes both incomplete. Exported names are T2.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [clangd Features: Rename](https://clangd.llvm.org/features) (LLVM, 2026); [Clang 20 Release Notes](https://github.com/llvm/llvm-project/blob/release/20.x/clang/docs/ReleaseNotes.rst) (LLVM, 2025); [ClangdMain.cpp (release/22.x)](https://github.com/llvm/llvm-project/blob/release/22.x/clang-tools-extra/clangd/tool/ClangdMain.cpp) (LLVM, 2026) · dossier: agent-refactoring-engines G105-F08, G105-F11, G105-F01

### CP-11 — After every engine edit, verify what the engine cannot see
- **Rule:** Before a rename or signature change, save a census of the old name across code, strings, build files and scripts; afterwards re-run it and explain or hand-fix every surviving hit, especially inside `#define` bodies and disabled `#if` branches. Then run `clangd --check=<file>` on each touched TU, the full build and the tests. A clean compile is not proof: 66 of 518 catalogued engine bugs (12.7%, Java IDE engines, 2024) were behaviour changes.
- **Detect:** `git grep -n -w -F --untracked OLD > .harden/tools/census-OLD-before.txt` (tracked files plus new files not yet committed, never `.harden/` or ignored files), repeat after into `.harden/tools/census-OLD-after.txt`, diff the two lists; `rg -n '#define' -A5 | rg -w OLD`; `clangd --check=<file>`.
- **Not when:** In code without reflection or macros the census adds noise; keep it as a reviewed list, never a bare count. With no working build (CP-01), stop after the census and report.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [clangd Features: Rename](https://clangd.llvm.org/features) (LLVM, 2026); [An Empirical Study of Refactoring Engine Bugs](https://arxiv.org/html/2409.14610v1) (Wang et al., 2024) · dossier: agent-refactoring-engines G105-F08, G105-F02, G105-F05, G105-F16; eval-v2-calibration E02-F08

### CP-12 — Extract only through clangd tweaks
- **Rule:** Apply extract-function and extract-variable only through clangd tweaks (`clangd.applyTweak`; release/22.x ships ExtractFunction, ExtractVariable, DefineInline, DefineOutline, SwapIfBranches, PopulateSwitch and others). The LLM chooses the range; the engine writes the edit.
- **Detect:** Select the code action by exact kind and exact title with an exact range; print the WorkspaceEdit and assert the expected file and hunk counts; treat a null, empty or unexpectedly broad edit, or an error on clangd's stderr, as a failure; `git diff --stat` must match the plan.
- **Not when:** No clangd tweak exists for inline-function or change-signature (CP-13). A wrong range yields a different but valid refactoring. Extract was the most bug-prone engine refactoring (149 of 518 bugs, Java IDE engines, 2024).
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [clangd Features](https://clangd.llvm.org/features) (LLVM, 2026); [An Empirical Study of Refactoring Engine Bugs](https://arxiv.org/html/2409.14610v1) (Wang et al., 2024) · dossier: agent-refactoring-engines G105-F08, G105-F15, G105-F02

### CP-13 — Engine-less operations follow the fallback protocol
- **Rule:** Change-signature, inline-function, namespace moves and fixes inside macro bodies have no verified engine (clang-change-namespace and clang-move were not executed): edit by hand, one refactoring per commit, in this order: census before and after, moved-block review, review of every changed exported header, compile, tests.
- **Detect:** `git -c color.diff.newMoved=cyan -c color.diff.oldMoved=magenta diff --color=always --color-moved=zebra --color-moved-ws=allow-indentation-change` (moves under 20 alphanumeric characters show as plain adds and deletes); no C/C++ API-surface diff tool is verified, so read exported-header hunks by hand.
- **Not when:** Change-signature on an exported function is a public API change: T2. No study evaluates this protocol; tangled refactorings were strongly associated with lower compilability in agent patches (Multi-SWE-bench, preprint 2026).
- **Tier:** T1 · **Class:** structural · **Fix risk:** high · **Grade:** C
- **Source:** [git-diff --color-moved](https://git-scm.com/docs/git-diff) (Git project, 2026); ["Refactoring Runaway"](https://arxiv.org/abs/2605.22526) (Tian et al., 2026) · dossier: agent-refactoring-engines G105-F16, G105-F08

### CP-14 — On Windows, give native clangd long-form paths and check line endings
- **Rule:** Pass clangd and other native tools repo-relative or long-form Windows paths (`cygpath -m -l`, `pwd -W`), never MSYS `/c/...` paths or 8.3 short names; prefix `MSYS_NO_PATHCONV=1` when an argument starts with `/` or contains `=/`; check line endings after every engine edit. The run's `<scratch_dir>` sits under the OS temp directory (CP-02), so convert it with `cygpath -m -l "<scratch_dir>"` before a native tool sees it.
- **Detect:** `echo "$TEMP"` containing `~` means 8.3 names are in play, in `<scratch_dir>` too; `git ls-files --eol | rg 'w/mixed'`, fixed with the project's formatter or `git add --renormalize` when `.gitattributes` sets `text=auto`.
- **Not when:** WSL2 and Linux CI avoid MSYS conversion. With `core.autocrlf=true`, git normalises at commit, so mixed endings may never reach the repository. The engine failures behind this rule are single-machine reproductions.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [Git for Windows release notes](https://github.com/git-for-windows/build-extra/blob/main/ReleaseNotes.md) (Git for Windows, 2026); [cygpath](https://cygwin.com/cygwin-ug-net/cygpath.html) (Cygwin, 2026); [git-ls-files](https://git-scm.com/docs/git-ls-files) (Git project, 2026) · dossier: agent-refactoring-engines G105-F12; eval-v2-calibration E02-F08

## Dead code and dependencies

### CP-15 — Remove compiler-proven unused static functions and variables, minus side-effect cases
- **Rule:** Treat as T0 only what GCC or Clang proves unused in every shipped build configuration: `-Wunused-function` (static functions only) and `-Wunused-variable`. Keep static objects whose constructors register something, and anything another configuration still uses.
- **Detect:** Build every shipped platform configuration with `-Wall -Wextra`; keep only candidates every build reports; grep for `#ifdef` around every candidate.
- **Not when:** GCC's `-Wunreachable-code` has been a no-op since GCC 4.5 (2010); use Clang's (CP-16). A single-target app may ship one configuration only: confirm before skipping the extra builds. Unused parameters are never T0 (CP-17). Without a compiler (CP-01) nothing here is T0.
- **Tier:** T0 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [GCC Warning Options](https://gcc.gnu.org/onlinedocs/gcc/Warning-Options.html) (GNU, 2026); [Bug 1235717](https://bugzilla.mozilla.org/show_bug.cgi?id=1235717) (Mozilla, ~2016); [Clang Diagnostics Reference](https://clang.llvm.org/docs/DiagnosticsReference.html) (LLVM, 2026) · dossier: dead-code-tools T07-F10, T07-F09; lang-cpp T23-F17

### CP-16 — Treat whole-program unused-code findings as candidates needing layered evidence
- **Rule:** For external-linkage functions and other code the compiler cannot prove dead, collect independent signals before proposing deletion: cppcheck unusedFunction, the linker's removed-section list, Clang `-Wunused-member-function`, `-Wunused-template` and `-Wunreachable-code-aggressive` (none is in `-Wall`), zero coverage, and a whole-repo text search of every configuration, script and build file. Giving file-local entities internal linkage (misc-use-internal-linkage) lets the compiler prove more; propose it only where the project's `.clang-tidy` enables it.
- **Detect:** `mkdir -p "<scratch_dir>/cppcheck-build" && cppcheck --project=build/compile_commands.json --enable=unusedFunction --cppcheck-build-dir="<scratch_dir>/cppcheck-build"` (multi-threaded whole-program analysis silently needs the build dir; it lives in the run's scratch directory, never inside the repository, CP-02); link with `-Wl,--gc-sections -Wl,--print-gc-sections` and read stderr; clang-tidy misc-use-internal-linkage, misc-unused-using-decls, misc-unused-alias-decls, bugprone-unused-local-non-trivial-variable.
- **Not when:** Exported symbols of a shared library are API (T2). unusedFunction has false positives with templates, virtual functions and callbacks. Clang's unreachable-code warnings catch goto-fail-style bugs but are noisy in generated code, macros and platform `#ifdef`s (hundreds in Firefox's generated bindings): report, never gate. A `default:` after an exhaustive enum switch is defensive, not dead (enums can hold any integer value): keep it, marked NOTREACHED-style. `#if 0` blocks are sometimes deliberate documentation: report them for the owner (DC-21). cmake_template disables misc-use-internal-linkage while LLVM keeps it: the project's config decides. Per-function section removal needs `-ffunction-sections` (not verified).
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [Cppcheck manual](https://cppcheck.sourceforge.io/manual.pdf) (Cppcheck team, 2026); [ld Options](https://sourceware.org/binutils/docs/ld/Options.html) (GNU binutils, 2026); [misc-use-internal-linkage](https://clang.llvm.org/extra/clang-tidy/checks/misc/use-internal-linkage.html) (LLVM, 2026); [Bug 1235717: Enable clang's -Wunreachable-code warnings](https://bugzilla.mozilla.org/show_bug.cgi?id=1235717) (Mozilla, ~2016); [Re: perf build: Fix build for clang's -Wunreachable-code](https://lkml.iu.edu/hypermail/linux/kernel/2504.1/08119.html) (LKML, 2025); [CHECK(), DCHECK() and NOTREACHED()](https://chromium.googlesource.com/chromium/src/+/main/styleguide/c++/checks.md) (Chromium, 2026) · dossier: lang-cpp T23-F17; dead-code-tools T07-F10, T07-F18; assertions-defensive-checks G203-F10; eval-v2-calibration E02-F08

### CP-17 — Keep unused parameters that belong to a contract
- **Rule:** For an unused parameter of a virtual function, override, callback or other fixed signature, comment out the name or add `[[maybe_unused]]`; never delete the parameter. Delete a parameter only when every caller is in the same translation unit and the function is not exported.
- **Detect:** `clang-tidy -checks='-*,misc-unused-parameters'` with `IgnoreVirtual=true` (default false); `-Wextra` is what enables `-Wunused-parameter`.
- **Not when:** The check removes a parameter only "if all callers of the function are in the same translation unit and can be updated", and LLVM's own `.clang-tidy` disables it. Any signature change of an exported function is T2.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [misc-unused-parameters](https://clang.llvm.org/extra/clang-tidy/checks/misc/unused-parameters.html) (LLVM, 2026); [GCC Warning Options](https://gcc.gnu.org/onlinedocs/gcc/Warning-Options.html) (GNU, 2026) · dossier: dead-code-tools T07-F10; lang-cpp T23-F17

### CP-18 — Propose include cleanup; never apply fix_includes.py blindly
- **Rule:** Use clang-tidy misc-include-cleaner or IWYU only to propose unused and missing includes in the project's own files. For each IWYU diff, restore includes marked `// IWYU pragma: keep`, map private headers to public ones (`<bits/stl_vector.h>` to `<vector>`), delete unneeded additions and fix forward declarations; then rebuild every configuration and run the tests.
- **Detect:** `run-clang-tidy -p build -checks='-*,misc-include-cleaner'` with IgnoreHeaders covering third-party and system headers (Chromium's pattern), or `iwyu_tool.py -p build`; include-cleaner respects `keep`, `always_keep`, `private` and `export` pragmas.
- **Not when:** LLVM and Firefox disable misc-include-cleaner and Chromium only configures its ignore list: if the project's config disables it, report only. IWYU calls itself experimental; templates, macros and conditional compilation defeat it; a removed include can change which overload or specialization is visible. The gain is fewer hidden transitive dependencies (SF.10), not build time: one team measured almost no CI speed-up.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [include-what-you-use README](https://github.com/include-what-you-use/include-what-you-use) (IWYU project, 2026); [Include Cleaner design](https://clangd.llvm.org/design/include-cleaner) (clangd, 2026); [misc-include-cleaner](https://clang.llvm.org/extra/clang-tidy/checks/misc/include-cleaner.html) (LLVM, 2026); [Don't Use include-what-you-use](https://danra.prose.sh/dont_use_iwyu) (danra, 2024) · dossier: dead-code-tools T07-F11, T07-F21; lang-cpp T23-F18

## Language traps

### CP-19 — Report missing standard-library hardening in production builds
- **Rule:** When a production binary handles untrusted or non-trivial input and lacks library hardening, report it with a staged rollout (tests, then pre-production, then gradual production): libc++ `-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST`, libstdc++ `-D_GLIBCXX_ASSERTIONS`, MSVC STL `_MSVC_STL_HARDENING=1` where available. Keep `_GLIBCXX_DEBUG`, the libc++ debug mode and `_ITERATOR_DEBUG_LEVEL=2` for test builds.
- **Detect:** `jq -r '.[].command' build/compile_commands.json | grep -cE '_LIBCPP_HARDENING_MODE|_GLIBCXX_ASSERTIONS|_MSVC_STL_HARDENING'`; identify the library (`-stdlib=libc++`, libstdc++, MSVC STL); ABI mixing: `rg -n '_GLIBCXX_DEBUG|_ITERATOR_DEBUG_LEVEL' CMakeLists.txt cmake`; propose a canary test that indexes an empty `std::vector` and expects termination.
- **Not when:** Overhead varies: 0.30% average across Google's services (production fleet, 2024; over 1,000 bugs found, baseline segfault rate down 30%) versus "up to 6%" reported for `_GLIBCXX_ASSERTIONS` (OpenSSF, 2026): opt hot paths out only after measuring. `_GLIBCXX_DEBUG` changes container layout; libc++ hardening leaves the ABI alone, but a per-TU override must precede every include. MSVC STL hardening was planned to ship disabled by default; its old IDL=1 mode broke ABI and cost up to 2x. libc++'s observe semantic is for the adoption period only: continuing after a failed check is UB.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Retrofitting spatial safety to hundreds of millions of lines of C++](https://security.googleblog.com/2024/11/retrofitting-spatial-safety-to-hundreds.html) (Google, 2024); [libc++ Hardening Modes](https://libcxx.llvm.org/Hardening.html) (LLVM, 2026); [libstdc++ Macros](https://gcc.gnu.org/onlinedocs/libstdc++/manual/using_macros.html) (GCC); [STL Hardening](https://github.com/microsoft/STL/wiki/STL-Hardening) (Microsoft STL team, 2026) · dossier: lang-cpp T23-F04; assertions-defensive-checks G203-F13

### CP-20 — Report missing release hardening flags
- **Rule:** For GCC/Clang release builds, report absent OpenSSF runtime protections: `-U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=3` (needs `-O1` or higher), `-fstrict-flex-arrays=3`, `-fstack-clash-protection -fstack-protector-strong`, `-Wl,-z,nodlopen -Wl,-z,noexecstack -Wl,-z,relro -Wl,-z,now`, `-Wl,--as-needed -Wl,--no-copy-dt-needed-entries`; `-fPIE -pie` for executables; `-fcf-protection=full` (x86_64) or `-mbranch-protection=standard` (aarch64). On GCC 14+, `-fhardened` with `-Whardened` covers most of them.
- **Detect:** `gcc --help=hardened`; compile_commands.json and link flags; `readelf -d app | grep -E 'BIND_NOW|FLAGS'`; `readelf -lW app | grep GNU_RELRO`; confirm sanitizer configurations do not define `_FORTIFY_SOURCE`.
- **Not when:** The OpenSSF guide covers GCC and Clang only; `-fhardened` is GNU/Linux-only and its set may change between major releases. Full RELRO can slow startup with many shared libraries. `-ftrivial-auto-var-init=zero` hides uninitialized reads from sanitizers: zero in production, `=pattern` in QA builds (Sutter; a practitioner). Its cost ranges from under 0.5% (P2723R1, 2023) to over 10% when Windows initialised all stack types before optimiser work (MSRC, 2020).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Compiler Options Hardening Guide](https://best.openssf.org/Compiler-Hardening-Guides/Compiler-Options-Hardening-Guide-for-C-and-C++.html) (OpenSSF, 2026); [GCC Instrumentation Options: -fhardened](https://gcc.gnu.org/onlinedocs/gcc-16.2.0/gcc/Instrumentation-Options.html) (GCC 16.2, 2026); [P2723R1](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2023/p2723r1.html) (Bastien, 2023); [Solving Uninitialized Stack Memory on Windows](https://www.microsoft.com/en-us/msrc/blog/2020/05/solving-uninitialized-stack-memory-on-windows) (MSRC, 2020) · dossier: lang-cpp T23-F05, T23-F14

### CP-21 — Treat assert() as absent in production; guard memory safety with an always-on check
- **Rule:** CMake's GNU, Clang and MSVC modules add `-DNDEBUG` to Release, RelWithDebInfo and MinSizeRel, so `assert()` does nothing there. Convert an `assert()` that guards a dereference, index, `memcpy`/`memmove` or variable-sized allocation to an always-on aborting mechanism (a CHECK-style macro or the hardened library), in its own commit with a test and a rollout note. Keep plain `assert()` for expensive or diagnostic checks, and make sure some CI job builds and runs the tests with assertions on.
- **Detect:** `grep -rn NDEBUG CMakeLists.txt cmake/`; `cmake -LA -N build | grep FLAGS_RELEASE`; ast-grep for `assert(` directly before a dereference, index, copy or allocation; flag `DCHECK($X)` followed by `if (!$X)` (Chromium: do not handle DCHECK failures; choose one mechanism).
- **Not when:** Data crossing a trust boundary (files, IPC, server-pushed or self-generated config) gets a recoverable check that rejects the item, not CHECK or assert (Chromium; CrowdStrike 2024: a missing runtime bounds check read a 21st field where 20 were supplied). Hot paths can pay: SQLite runs about 3x slower with every assert on. An empty `CMAKE_BUILD_TYPE` adds no NDEBUG.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [assert — cppreference](https://en.cppreference.com/cpp/error/assert) (cppreference, 2026); [Modules/Compiler/GNU.cmake](https://github.com/Kitware/CMake/blob/master/Modules/Compiler/GNU.cmake) (Kitware, 2026); [CHECK(), DCHECK() and NOTREACHED()](https://chromium.googlesource.com/chromium/src/+/main/styleguide/c++/checks.md) (Chromium, 2026); [The Use Of assert() In SQLite](https://www.sqlite.org/assert.html) (SQLite, 2026); [Channel File 291 RCA](https://www.crowdstrike.com/wp-content/uploads/2024/08/Channel-File-291-Incident-Root-Cause-Analysis-08.06.2024.pdf) (CrowdStrike, 2024) · dossier: assertions-defensive-checks G203-F04, G203-F12, G203-F13, G203-F17

### CP-22 — Keep assertion predicates side-effect free
- **Rule:** Before any build's assertion setting changes (NDEBUG, a contract semantic), move every mutation, I/O or mutating call out of `assert`, DCHECK and contract predicates so debug and release builds do the same work.
- **Detect:** `clang-tidy -checks='-*,bugprone-assert-side-effect'` with `CheckFunctionCalls=true` (off by default) and the project's macros added to `AssertMacros` (default `assert,NSAssert,NSCAssert`); run the tests in Debug and in Release and diff the results.
- **Not when:** False positives on calls that are const but not annotated as such. Moving the effect out makes it run in release too, so it is its own commit with a test.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** A
- **Source:** [bugprone-assert-side-effect](https://clang.llvm.org/extra/clang-tidy/checks/bugprone/assert-side-effect.html) (LLVM, 2026); [P2900R14 Contracts for C++](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p2900r14.pdf) (WG21, 2025); [CHECK(), DCHECK() and NOTREACHED()](https://chromium.googlesource.com/chromium/src/+/main/styleguide/c++/checks.md) (Chromium, 2026) · dossier: assertions-defensive-checks G203-F16

### CP-23 — Do not bulk-migrate to C++26 contracts
- **Rule:** Never migrate `assert()` or CHECK to `pre`/`post`/`contract_assert` during a hardening pass. Where contracts already exist, report components whose evaluation semantic is not pinned in the build, destructive predicates, and security checks that rely on a contract while some build could select "ignore".
- **Detect:** `rg -n 'contract_assert|\bpre\s*\(|\bpost\s*\('`, reviewed by hand; the compiler flags that select the semantic per target.
- **Not when:** Not applicable before C++26. Supporters (Sutter; P3846R1) rate contracts far above `assert`; critics (P3835R0; P4334R0, Aug 2026) dispute them; GCC had them in trunk awaiting release in March 2026, so revisit as toolchains mature.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** B
- **Source:** [P2900R14 Contracts for C++](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p2900r14.pdf) (WG21, 2025); [P3835R0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p3835r0.html) (Spicer et al., 2025); [C++26 is done!](https://herbsutter.com/2026/03/29/c26-is-done-trip-report-march-2026-iso-c-standards-meeting-london-croydon-uk/) (Sutter, 2026) · dossier: assertions-defensive-checks G203-F05

### CP-24 — Give every allocation an owner
- **Rule:** Make each `new` or `malloc` result owned at once by a handle: `std::make_unique` by default, `std::make_shared` only for real shared ownership, or a container; raw `T*` and `T&` mean non-owning. Keep allocators, placement new, framework object trees and C APIs inside one audited handle class. Memory unsafety is about 70% of Chromium's high-severity security bugs (912 high or critical bugs since 2015), half of them use-after-free.
- **Detect:** `rg -n '\bnew\s+[A-Za-z_:][A-Za-z0-9_:<>, ]*\s*[\(\{\[]' -g '*.{cpp,cc,cxx,h,hpp}'`; `rg -n '\bdelete\s*(\[\s*\])?\s*[A-Za-z_(*]'`; `rg -n '\b(malloc|calloc|realloc|free)\s*\('`; clang-tidy cppcoreguidelines-owning-memory, cppcoreguidelines-no-malloc, modernize-make-unique, modernize-make-shared, bugprone-unique-ptr-array-mismatch; MSVC `/analyze` C26400, C26409.
- **Not when:** Converting ownership can change destruction order, exception safety and API or ABI: anything crossing an exported signature is T2. shared_ptr cycles leak. Parent-owned framework trees legitimately `new` without `delete`. owning-memory is type-based, not flow-sensitive.
- **Tier:** T1 · **Class:** structural · **Fix risk:** high · **Grade:** A
- **Source:** [C++ Core Guidelines R.11, R.20, R.21, I.11](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#rr-newdelete) (Stroustrup, Sutter, 2026); [Memory Safety (Chromium Security)](https://www.chromium.org/Home/chromium-security/memory-safety/) (Chromium); [cppcoreguidelines-owning-memory](https://clang.llvm.org/extra/clang-tidy/checks/cppcoreguidelines/owning-memory.html) (LLVM, 2026) · dossier: lang-cpp T23-F09

### CP-25 — Hunt lifetime bugs explicitly
- **Rule:** Look for use after `std::move` without reinitialisation; `std::string_view` or `std::span` bound to temporaries or stored as members without a proven owner; `[&]` lambdas that outlive their scope (stored, passed to threads, async or callbacks, returned); iterators or references used after insert, erase or reallocation. Fix each with a test that shows the failure.
- **Detect:** clang-tidy bugprone-use-after-move, bugprone-dangling-handle (add the project's view types to HandleClasses), bugprone-return-const-ref-from-parameter; clang `-Wdangling` (on by default), GCC `-Wdangling-reference` (in `-Wextra`); `rg -n '^\s*(const\s+)?std::(string_view|span<[^>]*>)\s+\w+\s*(;|\{|=)' -g '*.{h,hpp}'`; `rg -n '\[&[^\]]*\]' | rg 'std::thread|std::async|std::function|detach|post\(|then\(|return \['`; confirm with ASan `detect_stack_use_after_return`.
- **Not when:** use-after-move is flow- but not path-sensitive and ignores members and globals; GCC's warning has documented false positives; a real stack use-after-free passed both cppcheck and clang-tidy (practitioner, HN 32823103). Replacing a string_view member with std::string adds allocations and changes aliasing.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [bugprone-use-after-move](https://clang.llvm.org/extra/clang-tidy/checks/bugprone/use-after-move.html) (LLVM, 2026); [bugprone-dangling-handle](https://clang.llvm.org/extra/clang-tidy/checks/bugprone/dangling-handle.html) (LLVM, 2026); [SEI CERT C++ EXP61-CPP](https://cmu-sei.github.io/secure-coding-standards/sei-cert-cpp-coding-standard/rules/expressions-exp/exp61-cpp) (CMU SEI, 2016); [GCC C++ Dialect Options](https://gcc.gnu.org/onlinedocs/gcc-16.2.0/gcc/C_002b_002b-Dialect-Options.html) (GCC 16.2, 2026) · dossier: lang-cpp T23-F11

### CP-26 — Carry bounds in the type
- **Rule:** In internal code, replace `(T*, size)` pairs and raw buffers with `std::span` (views), `std::array` (fixed) or `std::vector` (owned), and memcpy/memset with algorithms or ranges, so the hardened library (CP-19) checks each access. Adopt clang `-Wunsafe-buffer-usage` file by file; opt out only with `#pragma clang unsafe_buffer_usage begin/end` or a project `UNSAFE_BUFFERS()` macro plus a `// SAFETY:` comment.
- **Detect:** `-Wunsafe-buffer-usage` counts per file; clang-tidy cppcoreguidelines-pro-bounds-pointer-arithmetic, -array-to-pointer-decay, -constant-array-index, -avoid-unchecked-container-access, modernize-avoid-c-arrays; MSVC C26481, C26485; `rg -n '\(\s*(const\s+)?\w+\s*\*\s*\w+\s*,\s*(std::)?size_t\s+\w+' -g '*.{h,hpp}'`.
- **Not when:** Spatial-safety bugs were 40% of in-the-wild memory-safety exploits over a decade (Project Zero data, Google 2024), yet compliance is a migration, "not a 'push-button' solution". Exported signatures are T2. `std::array` copies by value; `std::span` needs C++20. The pro-bounds checks are noisy on C-interop code; hot loops may need audited opt-outs.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [C++ Safe Buffers](https://clang.llvm.org/docs/SafeBuffers.html) (LLVM, 2026); [Unsafe buffers (Chromium docs)](https://chromium.googlesource.com/chromium/src/+/main/docs/unsafe_buffers.md) (Chromium, 2026); [Retrofitting spatial safety](https://security.googleblog.com/2024/11/retrofitting-spatial-safety-to-hundreds.html) (Google, 2024) · dossier: lang-cpp T23-F13

### CP-27 — Make class semantics explicit
- **Rule:** Rule of zero, or else rule of five (C.21); a polymorphic base destructor is public and virtual or protected and non-virtual (C.35); each overrider says exactly one of virtual, override or final (C.128); single-argument constructors are explicit unless the conversion is intended (C.46); moves are noexcept (C.66); no const or reference data members in copyable or movable types (C.12).
- **Detect:** clang-tidy cppcoreguidelines-special-member-functions, cppcoreguidelines-virtual-class-destructor, modernize-use-override, google-explicit-constructor, performance-noexcept-move-constructor, bugprone-exception-escape (expensive on large files); `-Wall` (includes `-Wdelete-non-virtual-dtor`), `-Woverloaded-virtual`, clang `-Winconsistent-missing-override`, `-Wsuggest-override`.
- **Not when:** A new virtual destructor adds a vptr and changes layout and ABI: T2 for exported types. `explicit` breaks implicit-conversion call sites (at compile time). noexcept on a move that can throw turns the throw into std::terminate: prove it cannot throw first. Mozilla rated google-explicit-constructor and modernize-use-override low-reliability for its macro-heavy code.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [C++ Core Guidelines C.21, C.35, C.128, C.46, C.66, C.12](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#rc-five) (isocpp, 2026); [GCC C++ Dialect Options](https://gcc.gnu.org/onlinedocs/gcc-16.2.0/gcc/C_002b_002b-Dialect-Options.html) (GCC 16.2, 2026); [performance-noexcept-move-constructor](https://clang.llvm.org/extra/clang-tidy/checks/performance/noexcept-move-constructor.html) (LLVM, 2026) · dossier: lang-cpp T23-F10

### CP-28 — Replace C-style casts and type punning
- **Rule:** Replace C-style casts with the narrowest named cast or with none; replace punning through `reinterpret_cast`, unions or `memcpy` with `std::bit_cast` (C++20; equal sizes, trivially copyable types); never memset or memcpy a non-trivially-copyable type (C.90). Report high cast density in a module as a design finding.
- **Detect:** `-Wold-style-cast`; clang-tidy google-readability-casting, cppcoreguidelines-pro-type-cstyle-cast, -reinterpret-cast, -const-cast, bugprone-undefined-memory-manipulation, readability-redundant-casting; cast count per file.
- **Not when:** Google permits `(void)` casts and `T(x)` for class types, while ES.48/ES.49 flag both and prefer `std::ignore =` over `(void)` on `[[nodiscard]]` results: follow the project's style guide. A mechanical rewrite to reinterpret_cast or const_cast keeps the UB; removing a redundant cast can change overload resolution. Serialization and FFI layers keep their casts, isolated.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [C++ Core Guidelines ES.48 / ES.49 / C.90](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#res-casts) (isocpp, 2026); [Google C++ Style Guide: Casting](https://google.github.io/styleguide/cppguide.html) (Google, 2026); [std::bit_cast](https://en.cppreference.com/w/cpp/numeric/bit_cast) (cppreference) · dossier: lang-cpp T23-F12

### CP-29 — Initialize every object with a meaningful value
- **Rule:** Initialize every local and data member at its declaration (ES.20) with a meaningful value, not an arbitrary 0 that hides a logic error; keep `-ftrivial-auto-var-init` only as a backstop (CP-20), and review init-variables fix-its by hand.
- **Detect:** GCC `-Wuninitialized`/`-Wmaybe-uninitialized`, Clang `-Wuninitialized`/`-Wsometimes-uninitialized`, MSVC C4700/C26494; clang-tidy cppcoreguidelines-init-variables, cppcoreguidelines-pro-type-member-init, clang-analyzer-core.uninitialized.\*; MSan or Valgrind memcheck on the tests (ASan does not catch these reads).
- **Not when:** An initializer turns UB into defined behaviour with a possibly wrong value and can hide the bug from MSan: where the right value is unclear, report the read for the owner. Large buffers in hot loops can cost performance.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** A
- **Source:** [C++ Core Guidelines ES.20](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#res-always) (isocpp, 2026); [C++ safety, in context](https://herbsutter.com/2024/03/11/safety-in-context/) (Sutter, 2024); [HN comment on ASan and uninitialized reads](https://news.ycombinator.com/item?id=43776929) (bri3d, 2025) · dossier: lang-cpp T23-F14

### CP-30 — Do not mix signed and unsigned arithmetic
- **Rule:** Fix mixed signed/unsigned comparisons and arithmetic; at unavoidable `size_t` boundaries use C++20 `std::ssize()` and `std::cmp_less`/`std::cmp_equal`. Use unsigned only for bit patterns and modular arithmetic, not to mean "non-negative".
- **Detect:** `-Wsign-compare` (GCC `-Wall` for C++, Clang `-Wextra`), `-Wsign-conversion`; MSVC C4018, C4389; clang-tidy modernize-use-integer-sign-comparison (replacement only for C++20 or later); manual review of `a.size() - 1` and `i >= 0` loops on unsigned counters.
- **Not when:** The standard library uses unsigned size_type and "no perfect and fully compatible solution is possible" (ES.107); GCC eliminates bounds checks in tight loops more often with `size_t` than `unsigned` indices (practitioner, 2024): keep existing `size_t` loop indices. Changing signedness changes overflow semantics (unsigned wraps, signed overflow is UB), so each fix gets a test.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [Google C++ Style Guide: Integer Types](https://google.github.io/styleguide/cppguide.html) (Google, 2026); [C++ Core Guidelines ES.100–ES.107](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#res-mix) (isocpp, 2026); [std::cmp_equal, cmp_less](https://en.cppreference.com/w/cpp/utility/intcmp) (cppreference); [HN comment on size_t indices](https://news.ycombinator.com/item?id=39682728) (fweimer, 2024) · dossier: lang-cpp T23-F03

### CP-31 — Triage narrowing conversions in stages, never by cast insertion
- **Rule:** Treat `-Wconversion`, `-Wsign-conversion` and bugprone-narrowing-conversions as staged triage: baseline without `-Werror`; fix first the conversions feeding array indexing, object or allocation sizes and security logic; prefer changing declared types; add an explicit cast only where truncation is intended and documented. Never mass-silence with `static_cast`.
- **Detect:** Warning counts per file; `clang-tidy -checks='-*,bugprone-narrowing-conversions'` (IgnoreConversionFromTypes `size_t;ptrdiff_t;size_type;difference_type` for legacy code); watch `git diff -U0 | grep -c 'static_cast<'` in the pass's own diff; clang `-fsanitize=implicit-conversion` or `-fsanitize=integer` in test builds (neither is part of `-fsanitize=undefined`).
- **Not when:** Brownfield code yields "hundreds or thousands" of mostly benign warnings (OpenSSF): start with `-Wsign-conversion` or selected TUs. Casts added to silence the warning hide the truncations it exists to catch, and UBSan's implicit-conversion checks cannot see explicit casts. `gsl::narrow` throws, which changes behaviour. LLM repairs were accepted in 92.73% of code reviews in one industrial case study but trailed optimal human fixes (preprint, 2026).
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** B
- **Source:** [Compiler Options Hardening Guide](https://best.openssf.org/Compiler-Hardening-Guides/Compiler-Options-Hardening-Guide-for-C-and-C++.html) (OpenSSF, 2026); [bugprone-narrowing-conversions](https://clang.llvm.org/extra/clang-tidy/checks/bugprone/narrowing-conversions.html) (LLVM, 2026); [LLM-Based Repair of C++ Implicit Data Loss Compiler Warnings](https://arxiv.org/abs/2601.14936) (You et al., 2026); [HN comment on -Wconversion casts](https://news.ycombinator.com/item?id=35762122) (nwellnhof, 2023) · dossier: lang-cpp T23-F02

### CP-32 — Keep the project's error-handling model
- **Rule:** Detect whether the project uses exceptions or error codes and never switch models during hardening. In code with exceptions, report destructors, moves and swap that can throw and swallowing `catch (...) {}` blocks; noexcept belongs only where throwing is impossible or unacceptable (F.6), never sprinkled.
- **Detect:** Compare `rg -c '\bthrow\b|\btry\s*\{'` with `rg -c 'std::expected|absl::Status|error_code'`; build flags `-fno-exceptions`, `/EHsc`; clang-tidy bugprone-exception-escape, performance-noexcept-move-constructor; `rg -n 'catch\s*\(\s*\.\.\.\s*\)\s*\{\s*\}'`.
- **Not when:** Core Guidelines NR.3 ("Don't avoid exceptions") and Google ("We do not use C++ exceptions") contradict each other: the project's existing policy decides. Hard real-time and embedded code may ban exceptions. exception-escape is expensive and does not treat functions without a visible definition as throwing unless configured.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [C++ Core Guidelines NR.3, F.6, E.12](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#rnr-no-exceptions) (isocpp, 2026); [Google C++ Style Guide: Exceptions](https://google.github.io/styleguide/cppguide.html) (Google, 2026); [bugprone-exception-escape](https://clang.llvm.org/extra/clang-tidy/checks/bugprone/exception-escape.html) (LLVM, 2026) · dossier: lang-cpp T23-F20

### CP-33 — Report concurrency defects; leave the fixes to a human
- **Rule:** Report manual `lock()`/`unlock()` calls (use RAII guards: CP.20, CON51-CPP), condition-variable waits without a predicate loop (CON54-CPP), mutex-protected members without Clang thread-safety annotations, and every TSan finding. Do not change lock scope or add annotations in this pass.
- **Detect:** `rg -n '\.(lock|unlock|try_lock)\s*\(\s*\)'`; clang-tidy concurrency-mt-unsafe, bugprone-unused-raii, bugprone-spuriously-wake-up-functions; clang `-Wthread-safety` after annotation; the TSan build from CP-04.
- **Not when:** Thread-safety annotations are Clang-only, intra-procedural, free at run time and manual to retrofit. Changing lock scope can introduce deadlocks or contention. Chromium rejected bugprone-spuriously-wake-up-functions as noisy for its code.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [C++ Core Guidelines CP.2 / CP.20](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#rconc-raii) (isocpp, 2026); [Thread Safety Analysis](https://clang.llvm.org/docs/ThreadSafetyAnalysis.html) (LLVM, 2026); [SEI CERT C++ Concurrency (CON)](https://cmu-sei.github.io/secure-coding-standards/sei-cert-cpp-coding-standard/rules/concurrency-con/) (CMU SEI, 2016) · dossier: lang-cpp T23-F16

### CP-34 — Keep headers self-contained and free of using-directives
- **Rule:** Remove `using namespace` at global or namespace scope in headers (except `using namespace std::literals`), move non-inline object and function definitions out of headers (SF.2), and make every header compile on its own (SF.11).
- **Detect:** `rg -n -P '^\s*using\s+namespace\s+(?!std::literals)' -g '*.{h,hpp,hh,hxx}'`; clang-tidy google-build-using-namespace, misc-definitions-in-headers; `echo '#include "x.h"' | clang++ -fsyntax-only -x c++ -`.
- **Not when:** Removing a using-directive breaks includers that relied on it (at compile time) and in rare cases changes overload resolution through ADL: run the tests. Headers consumed outside the repository are public API (T2).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [C++ Core Guidelines SF.7](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#rs-using-directive) (isocpp, 2026); [C++ Core Guidelines SF.2 / SF.11](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#rs-inline) (isocpp, 2026); [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html) (Google, 2026) · dossier: lang-cpp T23-F22

### CP-35 — Add const only on changed code and only where the project enforces it
- **Rule:** On files the pass already changes, make locals const by default (Con.1) and member functions const unless they change observable state (Con.2). Do not const-qualify by-value parameters in declarations, locals returned by value (blocks moves), or data members of copyable or movable types (C.12).
- **Detect:** clang-tidy misc-const-correctness (fix-its only for single declarations; skips templates), readability-make-member-function-const, readability-avoid-const-params-in-decls.
- **Not when:** Con.1 asks for const by default, but LLVM disables misc-const-correctness and cmake_template disables readability-avoid-const-params-in-decls: follow the project's `.clang-tidy`; with none, report only. A const member function changes overload selection for const objects.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [C++ Core Guidelines Con.1 / Con.2 / C.12](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#rconst-immutable) (isocpp, 2026); [misc-const-correctness](https://clang.llvm.org/extra/clang-tidy/checks/misc/const-correctness.html) (LLVM, 2026); [LLVM project .clang-tidy](https://raw.githubusercontent.com/llvm/llvm-project/main/.clang-tidy) (LLVM, 2026) · dossier: lang-cpp T23-F15

### CP-36 — Keep format-string checking on
- **Rule:** Keep `-Wformat -Wformat=2 -Werror=format-security` on and annotate the project's printf-like wrappers with `__attribute__((format(printf, ...)))`. Report printf-family code that could move to type-safe formatting (std::format/std::print, iostreams, fmt, or the project's own library) instead of migrating it in this pass.
- **Detect:** Count printf-family calls with rg; grep for non-literal format strings; clang-tidy modernize-use-std-print, modernize-use-std-format.
- **Not when:** std::format needs a recent standard library; its output can differ subtly from printf, so a migration needs golden tests where logs are parsed; with `-Wformat=2` already clean the churn buys little.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Google C++ Style Guide: Architecture Portability](https://google.github.io/styleguide/cppguide.html) (Google, 2026); [Compiler Options Hardening Guide](https://best.openssf.org/Compiler-Hardening-Guides/Compiler-Options-Hardening-Guide-for-C-and-C++.html) (OpenSSF, 2026); [clang-tidy checks list](https://clang.llvm.org/extra/clang-tidy/checks/list.html) (LLVM, 2026) · dossier: lang-cpp T23-F21

## Test, mutation and fuzz tooling

### CP-37 — Spend dynamic verification on new, churned, input-handling code first
- **Rule:** Rank C/C++ files by recency and churn, intersect with code that parses or decodes untrusted bytes, and give the top of the list sanitizer runs, hardened-library builds, fuzzing and tests; a clean static-analysis report is not enough for fresh or AI-written C++. Treat old code that was never fuzzed as new to fuzzing.
- **Detect:** `git log --since="12 months ago" --name-only --pretty=format: -- src/ | sort | uniq -c | sort -rn | head -30`; parsers, decoders and deserialisers; existing harnesses: `rg -l "LLVMFuzzerTestOneInput"`, `fuzz/`, `.clusterfuzzlite/`, a google/oss-fuzz `projects/<name>` entry.
- **Not when:** 77% of 23k OSS-Fuzz bugs were regressions (C/C++ OSS, CCS 2021), but the regression share rises from 20% for a project's first bug to 92% after a few hundred. 5-year-old code had 3.4x (lifetimes from the USENIX study) to 7.4x (Android and Chromium lifetimes) lower vulnerability density than new code, modelled (Google, 2024); "old code is safer" assumes it was exercised. AI-written C++ was about twice as likely to trigger a confirmed runtime violation (8,918 programs, 851 competitive-programming tasks, three open-weight models; preprint 2026).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Regression Greybox Fuzzing](https://mboehme.github.io/paper/CCS21.pdf) (Zhu, Böhme, 2021); [Eliminating Memory Safety Vulnerabilities at the Source](https://security.googleblog.com/2024/09/eliminating-memory-safety-vulnerabilities-Android.html) (Google, 2024); [How Long Do Vulnerabilities Live in the Code?](https://www.usenix.org/conference/usenixsecurity22/presentation/alexopoulos) (Alexopoulos et al., USENIX Security 2022); [The Illusion of Safety](https://arxiv.org/abs/2607.00107) (Mahmud et al., 2026) · dossier: lang-cpp T23-F23; fuzz-property-hardening G206-F17, G206-F02, G206-F03

### CP-38 — Fuzz native code only with sanitizers, using tools that run here
- **Rule:** Build fuzz targets with sanitizers: clang `-fsanitize=fuzzer,address,undefined -g -O1`; on Windows, clang-cl libFuzzer (requires ASan; `/MD` and `/INCREMENTAL` unsupported, so use `/MT`) or MSVC `/fsanitize=address /fsanitize=fuzzer /Zi` (options given separately; experimental, VS 2022 17.0+). AFL++ needs WSL2 or Docker. Keep sanitizer and fuzz builds out of the production configuration.
- **Detect:** `rg -n "fsanitize" fuzz/ CMakeLists.txt Makefile`; on MSVC, flag `/MD` with libFuzzer and `/ZI`, `/RTC1` or `/INCREMENTAL` with ASan; record per tool whether it ran natively or under WSL2.
- **Not when:** `/MT` resolves LLVM (libFuzzer with `/MD` unsupported) versus Microsoft (ASan works with `/MD`); it is a reviewer's resolution, stated by neither vendor. MSVC has no UBSan, MSan or TSan: use clang in WSL2 for those classes. libFuzzer is in maintenance mode but still fixes important bugs. With no compiler (CP-01), skip the step and say so.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [libFuzzer](https://llvm.org/docs/LibFuzzer.html) (LLVM); [/fsanitize (Enable sanitizers)](https://learn.microsoft.com/en-us/cpp/build/reference/fsanitize) (Microsoft, 2026); [AddressSanitizer (MSVC)](https://learn.microsoft.com/en-us/cpp/sanitizers/asan) (Microsoft, 2026); [AFL++ INSTALL.md](https://github.com/AFLplusplus/AFLplusplus/blob/stable/docs/INSTALL.md) (AFL++ team, 2026) · dossier: fuzz-property-hardening G206-F09, G206-F16, G206-F20

### CP-39 — Write harnesses by the documented rules
- **Rule:** Make each `LLVMFuzzerTestOneInput` target deterministic (no rand, clock or environment branches), free of mutable global state between iterations, never calling exit, tolerant of any input (empty, huge, malformed), without disk I/O after initialisation, and under about 1.5 GB of memory.
- **Detect:** `rg -n "\brand\(|srand\(|time\(|exit\(|getenv|fopen\(|static [^c].*=" fuzz/`; replay the corpus twice with `-runs=0` and compare; libFuzzer `exec/s` under 10 signals a problem and about 1000 per core is normal; a crash whose top frame is in the harness, or that happens instantly, is presumed a harness bug.
- **Not when:** Stateful bugs may need a deterministic, input-driven command interpreter inside the harness. Heavyweight targets run far below 1000 exec/s (SQLite's dbsqlfuzz, about 400 per second per instance). The 1.5 GB figure is Google's guidance "as of 2019".
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [What makes a good fuzz target](https://github.com/google/fuzzing/blob/master/docs/good-fuzz-target.md) (Google); [libFuzzer](https://llvm.org/docs/LibFuzzer.html) (LLVM); [LLM-based fuzz target generation](https://google.github.io/oss-fuzz/research/llms/target_generation/) (Google OSS-Fuzz, 2024) · dossier: fuzz-property-hardening G206-F10

### CP-40 — Keep the fuzz pass additive and triage by root cause
- **Rule:** Add harnesses, seed corpora, dictionaries and regression inputs in test-only commits; do not edit production code or existing tests in this step, and leave fixes to a separate reviewed change. For each crash: minimise it, reproduce it twice, bucket by symbolised top frames as a first pass only, and report distinct root causes, each with its minimised input, the public entry point that reaches it and the documented precondition it respects. Never report crash or stack-hash counts as bug counts.
- **Detect:** `git diff --name-only <base>..HEAD` lists only test or fuzz paths; from the CP-41 working directory under `<scratch_dir>`, `./fuzz_target -minimize_crash=1 -runs=100000 crash-<sha1>`; `afl-tmin -i crash -o crash.min -- ./target @@` (WSL2); one root-cause sentence per bucket, merging buckets that share one.
- **Not when:** In one study 57,142 coverage-unique crashing inputs were fixed by 9 patches, with about 46 stack hashes per bug (cxxfilt only, CCS 2018). A crash that needs inputs violating undocumented preconditions is reported as a validation or documentation gap, not dropped. A target reachable only through a new seam in production code waits for a separate change.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [Ideal integration with OSS-Fuzz](https://google.github.io/oss-fuzz/advanced-topics/ideal-integration/) (Google OSS-Fuzz); [Evaluating Fuzz Testing](https://arxiv.org/abs/1808.09700) (Klees et al., 2018); [libFuzzer](https://llvm.org/docs/LibFuzzer.html) (LLVM) · dossier: fuzz-property-hardening G206-F01, G206-F11; eval-v2-calibration E02-F08

### CP-41 — Seed, budget and stop fuzz campaigns on evidence
- **Rule:** Seed each target from the project's fixtures, minimised to one input per behaviour, add a token dictionary for text formats, and also run one campaign from an empty seed. Give each target at least 10–15 minutes, preferably across parallel jobs, stop on a coverage plateau, and record the budget and the plateau evidence.
- **Detect:** tracked seed directories: `grep -oE '^(.*/)?(fixtures|testdata|samples|corpus)/' .harden/tools/inscope.txt | sort -u` (the in-scope list, never `find .`, which also walks `.harden/`); run campaigns and merges from a working directory under `<scratch_dir>` (CP-02): libFuzzer saves crash, timeout and slow inputs under `-artifact_prefix`, empty by default, so in the current directory, and `-jobs` workers write `fuzz-<JOB>.log` there; `./fuzz_target -merge=1 corpus_min/ raw_fixtures/`; `-dict=tokens.dict`; `./fuzz_target corpus/ -max_total_time=900 -jobs=4` while watching `cov:` and `ft:`; flag targets fuzzed under 10 minutes or without plateau evidence.
- **Not when:** CIFuzz's default and minimum is 600 s, and a 15-minute campaign found at least one bug for half of 9 Magma C/C++ libraries (preprint, 2022), but research comparisons use 10–30 trials of 24 h: AFL found 0 crashes at 13 h and 39 at 24 h on gif2png. A never-fuzzed finished project may deserve hours on its top 1–3 targets. Fixtures holding secrets or customer data never enter a committed corpus.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Ideal integration with OSS-Fuzz](https://google.github.io/oss-fuzz/advanced-topics/ideal-integration/) (Google OSS-Fuzz); [Continuous Integration (CIFuzz)](https://google.github.io/oss-fuzz/getting-started/continuous-integration/) (Google OSS-Fuzz); [Effectiveness and Scalability of Fuzzing Techniques in CI/CD Pipelines](https://arxiv.org/abs/2205.14964) (Klooster et al., 2022); [Evaluating Fuzz Testing](https://arxiv.org/abs/1808.09700) (Klees et al., 2018); [libFuzzer](https://llvm.org/docs/LibFuzzer.html) (LLVM) · dossier: fuzz-property-hardening G206-F08, G206-F07; eval-v2-calibration E02-F08

### CP-42 — Replay fuzz regressions without breaking the suite
- **Rule:** Keep every confirmed, minimised crash input as a new file in a replay corpus that the regression tests run (fuzz targets are run, not fuzzed, in regression testing). While the bug is unfixed, keep the input in a quarantine path outside the directory the suite replays, with an issue link, and move it in with the fix commit. Never use tool caches as the regression store.
- **Detect:** Each new corpus file fails on current code for the documented reason; the regression job replays the corpus with `-runs=0`; no known-failing input sits in the auto-replayed directory.
- **Not when:** The quarantine path is the dossier reviewer's workaround, not a sourced practice. Teams that forbid merging known-failing tests stay compatible with a quarantined reproducer plus an issue. SQLite replays only a few thousand "interesting" historical cases out of billions examined.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Ideal integration with OSS-Fuzz](https://google.github.io/oss-fuzz/advanced-topics/ideal-integration/) (Google OSS-Fuzz); [How SQLite Is Tested](https://www.sqlite.org/testing.html) (SQLite) · dossier: fuzz-property-hardening G206-F12, G206-F01

## Evidence limits

- No peer-reviewed, replicated study measures defect reduction from clang-tidy check sets or the C++ Core Guidelines; the strongest numbers are industrial (Google, Chromium, Android, Microsoft) and the warnings evidence is grey literature.
- Static and dynamic tools find different bugs: fuzzer and static-analyser bug sets were "nearly disjoint" on more than 100 known C/C++ vulnerabilities (Hassler et al., preprint 2025), and the AI-written C++ result rests on one preprint on competitive-programming tasks.
- clangd results come from single runs on 2–5 file fixtures (Windows, 2026); no per-operation failure rate exists for any C/C++ engine, and all engine-bug statistics are from Java IDEs. clang-tidy `--fix`, clang-change-namespace and clang-move were not executed.
- Fuzzing finds bugs, but introducing fuzzers did not significantly shorten memory-related CVE lifetimes in the Linux case study (USENIX Security 2022): do not claim lifetime reductions.
- Unverified: the current default of `_MSVC_STL_HARDENING`; the status of C++26 erroneous behaviour (P2795) and standard-library hardening (P3471); whether `--gc-sections` needs `-ffunction-sections`; overhead figures for `-D_FORTIFY_SOURCE=3` and `-fstack-clash-protection`; `-Wunsafe-buffer-usage` effort outside Chromium; SonarSource's C++ cognitive-complexity threshold.
- Not covered by this file's evidence: C/C++ mutation testing, dependency hygiene for C/C++ package managers, and any ephemeral installer for clang-tidy, cppcheck or IWYU.
- Tool behaviour is from 2026 docs (clang-tidy trunk 24.0.0git, clangd 22.1.6, Cppcheck manual 2.21.0, IWYU 0.26, GCC 16.2); re-verify on upgrade.
