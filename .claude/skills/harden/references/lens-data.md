# Lens: Data layer and dataframes

> Purpose: find integrity rules the database does not enforce, write paths that bypass them, unsafe engine and client settings, and dataframe, pipeline and notebook code that returns wrong numbers without raising. Schema changes, leakage and look-ahead are report-only.
> Read when: the scope contains SQL, migrations, ORM models, database or Redis client configuration, pandas/polars/NumPy code, ML or backtest pipelines, or Jupyter notebooks.

## Rules

### DA-01 — Constraints agree across DDL, ORM, API validators and front end
- **Rule:** For every persisted field, compare nullability, length, range, uniqueness and allowed values across the DDL, the ORM model, request validators (pydantic, zod, OpenAPI) and front-end checks. Where the database enforces a rule the app lacks, derive the app validator from the schema (Drizzle `createInsertSchema`: `drizzle-orm/zod` on v1, `drizzle-zod` on 0.x) instead of copying numbers. Where layers disagree on a value, report it: relaxing or aligning the DB is the owner's call, and any DDL goes through DA-05.
- **Detect:** Rails: database_consistency `LengthConstraintChecker`, `NullConstraintChecker`; active_record_doctor `incorrect_length_validation`, `missing_non_null_constraint`, `missing_presence_validation`. Postgres: dump `information_schema.columns` (is_nullable, character_maximum_length, column_default) and `pg_get_constraintdef` for `contype IN ('c','u','f')`, then diff against `rg 'max_length=|constr[(]|Optional[[]'` (pydantic), `rg '[.]max[(]|[.]min[(]|[.]optional[(]|[.]nullable[(]'` (zod), `maxLength|required:` (OpenAPI), `maxlength=|pattern=|required` (HTML). SQLModel: flag code expecting `table=True` models to validate on instantiation (they do not).
- **Not when:** UX policy with no DB twin (password strength); an arbitrary `varchar(n)` where the right fix is relaxing the DB. Mirrored validators change error codes clients may parse, hence behavioural.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [Managing data constraints in database-backed web applications](https://hyperloop-rails.github.io/278.pdf) (Yang et al., ICSE 2020; 12 Rails apps: 24% of app constraints missing in the DB, 88 fields unique only in the app, 133 conflicting length or numeric limits, 49 of 56 reported problems confirmed); [CFinder](https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/3575693.3575699?fields=title,abstract,authors,year,openAccessPdf) (Huang et al., ASPLOS 2023; 210 missing constraints in 8 web apps, 75 of 92 reported confirmed); [database_consistency](https://github.com/djezzzl/database_consistency) (djezzzl); [Drizzle zod](https://orm.drizzle.team/docs/zod) (Drizzle Team, 2026); [SQLModel #52](https://github.com/fastapi/sqlmodel/issues/52) (maintainer, 2022) · dossier: data-layer-hygiene G209-F01

### DA-02 — Uniqueness is enforced by a unique index, not an app check
- **Rule:** Back every uniqueness or "at most one" invariant (emails, usernames, idempotency keys, one-per-user rows, order and trade IDs) with a `UNIQUE` constraint or a (partial) unique index; an app-level check-then-insert lets two connections insert duplicates. Propose the index as a DA-05 migration after counting existing duplicates, paired with DA-04. Rows containing NULL can still duplicate unless the constraint uses `NULLS NOT DISTINCT`.
- **Detect:** `rg 'validates .*uniqueness|validates_uniqueness_of|UniqueValidator'`; Prisma `findFirst(` followed by `create(`; Django `.exists()` followed by `.create(`; `pg_index` rows with `indisunique` for the table; duplicates via `GROUP BY col HAVING count(*)>1`; active_record_doctor `missing_unique_indexes`; database_consistency `MissingUniqueIndexChecker`, `UniqueIndexChecker`, `CaseSensitiveUniqueValidationChecker`. The race itself belongs to the concurrency lens.
- **Not when:** sharded MySQL/Vitess (a per-shard index cannot enforce global uniqueness); soft-delete tables need `WHERE deleted_at IS NULL`; case-insensitive uniqueness needs a `lower()` or citext index.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [Active Record Validations](https://guides.rubyonrails.org/active_record_validations.html) (Rails guides 8.1); [The Perils of Uniqueness Validations](https://thoughtbot.com/blog/the-perils-of-uniqueness-validations) (Prior, thoughtbot, 2013, updated 2025); [active_record_doctor](https://github.com/gregnavis/active_record_doctor) (Navis); [PostgreSQL 18: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (PGDG, 2026); [Yang et al.](https://hyperloop-rails.github.io/278.pdf) (ICSE 2020; 12 Rails apps: 88 app-only unique fields, 19 case-sensitivity mismatches) · dossier: data-layer-hygiene G209-F02

### DA-03 — Invariants kept in hooks are bypassed by bulk and raw writes
- **Rule:** List every invariant enforced only in `save()`, `clean()`, validators, signals or callbacks, then find bulk and low-level writes to the same models; each bypass is a candidate. Propose a DB constraint (DA-05) as the fix; do not convert bulk paths to per-row saves.
- **Detect:** carriers: Django `def save[(]|def clean[(]|@receiver[(](pre|post)_save`, Rails `validates|before_save|after_commit`. Bypasses on those models: queryset `.update(`, `bulk_create(`, `bulk_update(`; Rails `update_all|update_columns?|insert_all|upsert_all|validate: false` (the Rails guide lists 20 validation-skipping entries); SQLAlchemy Core bulk operations (skip ORM events); raw `INSERT`/`UPDATE` passed to `execute(`. Django `save()` never calls `full_clean()`. Check `pg_constraint` for a DB counterpart.
- **Not when:** per-row saves change cost and fire side effects (emails, signals). Django facts come from the 5.2 LTS docs; re-check on 6.x.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [Django 5.2 QuerySet API](https://docs.djangoproject.com/en/5.2/ref/models/querysets/) (DSF); [Django 5.2 Model instances](https://docs.djangoproject.com/en/5.2/ref/models/instances/) (DSF); [Django 5.2 DB optimization](https://docs.djangoproject.com/en/5.2/topics/db/optimization/) (DSF); [Active Record Validations](https://guides.rubyonrails.org/active_record_validations.html) (Rails 8.1); [SQLModel #52](https://github.com/fastapi/sqlmodel/issues/52) (maintainer, 2022) · dossier: data-layer-hygiene G209-F13

### DA-04 — Map integrity errors to specific client errors, not 500s
- **Rule:** On every write path in request and bot command handlers that can violate a unique, FK, `NOT NULL`, `CHECK` or length constraint, catch the integrity error and map it to a specific 409 or 422 with a field-level message. Match Prisma errors for the installed major only (P2002-style codes in v6/v7, dotted `NAMESPACE.SUBCODE` codes in v8).
- **Detect:** per insert or update: `except IntegrityError`, `rescue ActiveRecord::RecordNotUnique|InvalidForeignKey|NotNullViolation`, a driver check on SQLSTATE `23502`, `23503`, `23505`, `23514`, or the Prisma known-request error; generic handlers that turn every DB error into a 500. Proposed test: insert a duplicate or an orphan and assert a 4xx.
- **Not when:** never leak constraint names to clients. In Postgres an error aborts the enclosing transaction (`25P02`), so continuing needs a savepoint.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** B
- **Source:** [Yang et al.](https://hyperloop-rails.github.io/278.pdf) (ICSE 2020; 18% of 114 constraint issues were missing or unclear messages; DB constraint exceptions caught in only 4 cases across thousands of model saves in 12 Rails apps); [PostgreSQL 18 Error Codes](https://www.postgresql.org/docs/current/errcodes-appendix.html) (PGDG); [DB access bugs in Java](https://arxiv.org/html/2405.15008) (Liu et al., TOSEM 2024; constraint violations are 48.4% of 95 schema bugs); [The Perils of Uniqueness Validations](https://thoughtbot.com/blog/the-perils-of-uniqueness-validations) (thoughtbot); [Prisma error reference](https://www.prisma.io/docs/orm/reference/error-reference) (Prisma v8 docs) · dossier: data-layer-hygiene G209-F21

### DA-05 — Constraint and schema additions are owner-applied migrations with preflight queries
- **Rule:** Classify every data-layer fix by one question: does it change results, errors or durability for any input that exists or succeeds today? No (integrity-error handlers, validators mirroring an existing DB constraint): T1; CI gates and linter configs also change nothing, but invariant 2 makes them read-only, so they stay T2 proposals (DA-06). Yes, schema (FKs, indexes, `NOT NULL`, `UNIQUE`, `CHECK`, server defaults, timestamptz conversion): a proposed migration the owner applies, never the skill. Yes, operational (index drops, EAV or polymorphic redesign, pagination contracts, server-, role- or database-level timeouts, pool sizes, Redis persistence, MySQL strict mode): report only. A missing timeout in code the application writes (driver connect or pool acquisition, per-query or per-connection, SQLite `busy_timeout`) is the exception: T1 behavioural under ER-21 (DA-10, DA-12, DA-15).
- **Detect:** preflight per proposal: duplicates (DA-02), orphans (DA-07), `count(*) WHERE col IS NULL` before `NOT NULL`, `PRAGMA foreign_key_check` before enabling SQLite FKs. Lint the proposed DDL with squawk `adding-foreign-key-constraint`, `constraint-missing-not-valid`, `require-concurrent-index-creation`, `adding-not-nullable-field`; Atlas MF101–MF104 (data-dependent), DS102/DS103 (destructive), BC101/BC102 (backward incompatible) need Atlas Pro since v0.38. Postgres lock-safe path: `NOT VALID` then `VALIDATE CONSTRAINT` (`SHARE UPDATE EXCLUSIVE` lock; not-null allowed from PG18); `SET NOT NULL` skips its scan when a valid `CHECK` proves no NULLs; `CREATE INDEX CONCURRENTLY` cannot run in a transaction block, and a failure leaves an invalid index that still costs writes.
- **Not when:** small solo databases with no concurrent traffic can skip `CONCURRENTLY` and `NOT VALID`; failures on existing data still apply.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Atlas analyzers](https://atlasgo.io/lint/analyzers) (Ariga); [PostgreSQL 18: ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html) (PGDG); [PostgreSQL 18: CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html) (PGDG); [Yang et al.](https://hyperloop-rails.github.io/278.pdf) (ICSE 2020; 12 Rails apps: 49% of versions change constraints, over 25% of changes tighten existing fields, 10% of 114 issues were upgrade failures); [SQLite PRAGMA](https://www.sqlite.org/pragma.html) (SQLite) · dossier: data-layer-hygiene G209-F22; eval-v1-calibration E01-F05

### DA-06 — Gate schema drift in CI
- **Rule:** Where versioned migrations exist and CI has no drift check, propose one: `alembic check` (Alembic 1.9.0+; passes only when autogenerate would produce empty migrations), Django `makemigrations --check --dry-run` plus `migrate --check`, Prisma v7 `migrate diff --from-migrations prisma/migrations --to-schema prisma/schema.prisma --exit-code` (exit 2 means a non-empty diff; flags changed in v7 and may change in v8), `sqlc vet` (`sqlc/db-prepare` prepares every query against a live DB), squawk on migration SQL. Run the check first: existing drift is a finding to report, not a red gate to add. Adding the check edits CI config, which local gates cannot prove, so it stays a proposal (CI-03 reports the same missing gate).
- **Detect:** CI files listed in `inventory.json` that lack these commands; each check run once locally by the orchestrator, output kept under `.harden/tools/`.
- **Not when:** a green gate is not equivalence: renames (seen as drop plus add), anonymously named constraints, some Enum types, triggers and manual production hotfixes escape. `drizzle-kit check` checks migration-history consistency only, not DB drift.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Alembic autogenerate](https://alembic.sqlalchemy.org/en/latest/autogenerate.html) (Alembic 1.20); [django-admin 5.2](https://docs.djangoproject.com/en/5.2/ref/django-admin/) (DSF); [Prisma CLI reference](https://www.prisma.io/docs/orm/reference/prisma-cli-reference) (Prisma v7); [drizzle-kit check](https://orm.drizzle.team/docs/drizzle-kit-check) (Drizzle Team); [sqlc vet](https://docs.sqlc.dev/en/latest/howto/vet.html) (sqlc); [Atlas migrate lint](https://atlasgo.io/versioned/lint) (Ariga) · dossier: data-layer-hygiene G209-F15

### DA-07 — References are enforced foreign keys, or reported as unenforced
- **Rule:** Every reference column carries an enforced FK with an explicit `ON DELETE`, unless a documented reason exists. Report relations the database cannot enforce: Prisma `relationMode = "prisma"` (emulation "does not apply to raw queries"), Django `db_constraint=False`, ORM-emulated cascades that raw SQL and bulk deletes bypass, polymorphic associations and EAV tables. Never redesign them in a hardening pass; an FK addition is a DA-05 migration after an orphan count.
- **Detect:** Postgres `*_id` columns with no FK in `information_schema.key_column_usage` (heuristic); orphans via `LEFT JOIN parent p ... WHERE c.parent_id IS NOT NULL AND p.id IS NULL`; SQLite `PRAGMA foreign_key_check`; MySQL `KEY_COLUMN_USAGE` with `REFERENCED_TABLE_NAME`; `rg 'relationMode *= *"prisma"|db_constraint *= *False|FOREIGN_KEY_CHECKS *= *0|polymorphic: true|GenericForeignKey[(]'`; `_type`/`_id` column pairs; key-value tables with an entity FK; active_record_doctor `missing_foreign_keys`; database_consistency `ForeignKeyChecker`; sqlcheck.
- **Not when:** PlanetScale/Vitess and gh-ost setups (FKs add locking; gh-ost does not support them); cross-database references (GitLab uses loose FKs with eventual consistency there); audit logs and generic attachments. A JSONB replacement for EAV has its own cost (Heap, 2016: 584 s vs 300 ms from missing planner statistics; PG14+ expression statistics partly mitigate).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** B
- **Source:** [Smelly Relations](https://zenodo.org/records/1998088) (Sharma et al., ICSE-SEIP 2018; 2,925 systems; 77% of surveyed developers call missing FK constraints a smell; ORMs do not prevent smells); [SQLCheck](https://arxiv.org/abs/2004.10232) (Dintyala et al., SIGMOD 2020; "No Foreign Key" 1,389 times in 1,406 GitHub repos); [Prisma relation mode](https://www.prisma.io/docs/orm/prisma-schema/data-model/relations/relation-mode) (Prisma); [GitLab foreign keys](https://docs.gitlab.com/development/database/foreign_keys/) (GitLab, 2026); [GitLab loose foreign keys](https://docs.gitlab.com/development/database/loose_foreign_keys/) (GitLab); [GitLab polymorphic associations](https://docs.gitlab.com/development/database/polymorphic_associations/) (GitLab); [When To Avoid JSONB](https://www.heap.io/blog/when-to-avoid-jsonb-in-a-postgresql-schema) (Heap, 2016); [Operating without FK constraints](https://planetscale.com/docs/learn/operating-without-foreign-key-constraints) (PlanetScale) · dossier: data-layer-hygiene G209-F03, G209-F18, G209-F12

### DA-08 — Index foreign-key columns on PostgreSQL and SQLite
- **Rule:** On PostgreSQL and SQLite, make each FK's referencing columns the leading columns of some index: neither engine creates one, and a parent delete or key update then scans the child table. MySQL/InnoDB creates the index automatically, and Django creates one by default.
- **Detect:** schemalint `index-referencing-column`; active_record_doctor `unindexed_foreign_keys`; database_consistency `MissingIndexChecker`; the Prisma validation warning under `relationMode="prisma"`; Cybertec's published missing-FK-index query; SQLite `PRAGMA foreign_key_list(t)` against `PRAGMA index_list(t)` and `index_info`, or the sqlite3 CLI `.lint` (check `.help lint` for fkey-indexes). Priority: parents that get deleted, cascades, join-heavy endpoints.
- **Not when:** small tables; relations never joined whose parents are never deleted or re-keyed; Django FKs declared for consistency rather than joins. Every index adds write cost, and adding one is a DA-05 migration.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [PostgreSQL 18: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (PGDG); [SQLite Foreign Key Support](https://www.sqlite.org/foreignkeys.html) (SQLite); [Index your foreign key](https://www.cybertec-postgresql.com/en/index-your-foreign-key/) (Albe, CYBERTEC, 2018; one benchmark: parent DELETE 154.030 ms without vs 0.751 ms with the index); [GitLab foreign keys](https://docs.gitlab.com/development/database/foreign_keys/) (GitLab; missing FK indexes caused project-deletion timeouts); [MySQL 8.4 foreign keys](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html) (Oracle); [Django 5.2 fields](https://docs.djangoproject.com/en/5.2/ref/models/fields/) (DSF); [schemalint rules](https://github.com/kristiandupont/schemalint/blob/main/src/rules/README.md) (Dupont) · dossier: data-layer-hygiene G209-F04

### DA-09 — SQLite: foreign keys on per connection, non-null keys, STRICT for new tables
- **Rule:** In SQLite apps, set `PRAGMA foreign_keys=ON` on every connection outside any transaction (off by default; a no-op inside a transaction); audit with `PRAGMA foreign_key_check`, since `integrity_check` does not find FK errors; add `NOT NULL` to non-`INTEGER` primary keys (an "historical oversight" lets them hold NULL); prefer `STRICT` tables (SQLite 3.37.0+) for new tables. Python 3.12+ also offers `setconfig()` with `SQLITE_DBCONFIG_ENABLE_FKEY`.
- **Detect:** connection factories (`sqlite3.connect(`, `new Database(`, `create_engine(` on sqlite, `drizzle(` over better-sqlite3 or libsql) without `foreign_keys`; from the app's own connection `PRAGMA foreign_keys; PRAGMA foreign_key_check;`; non-STRICT tables via `sqlite_schema` where `sql NOT LIKE '%STRICT%'`; mixed types via `SELECT typeof(col), count(*) FROM t GROUP BY 1`.
- **Not when:** enabling enforcement activates dormant `ON DELETE CASCADE`/`SET NULL` actions and exposes existing orphans (a reasoned implication), so it is a DA-05 change with `foreign_key_check` as preflight; `STRICT` tables cannot be opened before 3.37 and converting means recreating the table; flexible typing is by design.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [Quirks, Caveats, and Gotchas](https://www.sqlite.org/quirks.html) (SQLite); [SQLite PRAGMA](https://www.sqlite.org/pragma.html) (SQLite); [STRICT Tables](https://www.sqlite.org/stricttables.html) (SQLite, 2021); [Foreign Key Support](https://www.sqlite.org/foreignkeys.html) (SQLite); [Python sqlite3](https://docs.python.org/3/library/sqlite3.html) (PSF, 3.14) · dossier: data-layer-hygiene G209-F08

### DA-10 — SQLite with concurrent writers: WAL, busy timeout, immediate transactions
- **Rule:** With more than one writer, report SQLite setups missing WAL mode (never on a network filesystem), a `busy_timeout`, `BEGIN IMMEDIATE` for write transactions (Django 5.1+ `transaction_mode: "IMMEDIATE"`) or short transactions. `synchronous=NORMAL` in WAL is SQLite's recommended balance: commits survive application crashes but may roll back on power loss or an OS crash, so propose `FULL` for fund or order state. A missing `busy_timeout` in the application's own connection setup is a per-connection client timeout: it follows ER-21 as a T1 behavioural item (ER-21's fixed internal default, generous and documented, placed, tested and listed as owner-tunable in the report's "Open owner items" section as ER-21 specifies); WAL mode, `synchronous`, `BEGIN IMMEDIATE` and transaction length stay report-only.
- **Detect:** from the app's connection `PRAGMA journal_mode; PRAGMA busy_timeout; PRAGMA synchronous;`; logs for `database is locked|SQLITE_BUSY`; Django `DATABASES` `OPTIONS` `transaction_mode`; Python sqlite3 `autocommit` and `timeout=` set explicitly (legacy transaction control is still the default); DB file on NFS or SMB; a growing `-wal` file (overlapping readers block checkpoints and the WAL grows without bound).
- **Not when:** single-writer apps. `IMMEDIATE` serializes writers earlier. Backups must include `-wal` and `-shm` or use the backup API.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Write-Ahead Logging](https://www.sqlite.org/wal.html) (SQLite); [PRAGMA synchronous](https://www.sqlite.org/pragma.html) (SQLite); [Django 5.2 databases](https://docs.djangoproject.com/en/5.2/ref/databases/) (DSF); [SQLite on Rails](https://fractaledmind.com/2024/04/15/sqlite-on-rails-the-how-and-why-of-optimal-performance/) (Margheim, 2024; one Rails load test: SQLITE_BUSY 500s at 4 concurrent requests under deferred transactions); [Litestream tips](https://litestream.io/tips/) (Litestream); [Python sqlite3](https://docs.python.org/3/library/sqlite3.html) (PSF) · dossier: data-layer-hygiene G209-F09; eval-v1-calibration E01-F05; pilot-auto-calibration A01-F10

### DA-11 — MySQL: strict SQL mode and FK checks in the sessions the app uses
- **Rule:** On MySQL or MariaDB, verify strict SQL mode in the global and session settings the app actually uses, and flag `sql_mode=''` and `FOREIGN_KEY_CHECKS=0`. Without strict mode MySQL stores adjusted values with only a warning, and rows added while FK checks were off are not re-checked when they are turned back on, so audit what those paths wrote (orphan queries from DA-07).
- **Detect:** `SELECT @@GLOBAL.sql_mode, @@SESSION.sql_mode;` from the app's connection; `rg 'sql_mode|init_command|SET +FOREIGN_KEY_CHECKS *= *0'`. The 8.4 default includes `STRICT_TRANS_TABLES`, but a session can override it.
- **Not when:** legacy apps that rely on lenient coercion; enabling strict mode is a behaviour change, so report only.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A

### DA-12 — Postgres roles and clients have finite timeouts
- **Rule:** Split by where the timeout is set. Server, role or database level: report application roles whose `statement_timeout`, `lock_timeout` and `idle_in_transaction_session_timeout` (plus `transaction_timeout` on PostgreSQL 17+) are 0, the default that disables them, and propose per-role or per-database settings, not postgresql.conf (the docs advise against it for statement, lock and transaction timeouts); these settings and their values stay the owner's decision (T2). Client side: a connection timeout that the application code passes, or omits, when it sets up its driver (node-postgres sets none by default) follows ER-21: a T1 behavioural item with ER-21's fixed internal default (a named constant or the existing config path, never a new exported parameter), placed, tested and listed as owner-tunable in the report's "Open owner items" section as ER-21 specifies. A query or statement timeout the code passes, or omits, when it issues queries follows ER-21 as T1 only with latency data for that query; without it, it stays T2 with the proposed value as its first step, because a query's legitimate duration grows with data the run cannot see (ER-21). Behind a transaction-mode pooler, never set it with a session-level `SET` (DA-15).
- **Detect:** server side, as the app role, `SHOW statement_timeout; SHOW lock_timeout; SHOW idle_in_transaction_session_timeout;`; `pg_db_role_setting` joined to `pg_roles`; `pg_stat_activity` rows `idle in transaction` by transaction age; squawk `require-lock-timeout`, `require-statement-timeout`, `require-timeout-settings` on migrations. Client side, in the code's driver and query setup: `rg 'statement_timeout|query_timeout|connectionTimeoutMillis|connect_timeout'`, and driver constructors with none of them.
- **Not when:** batch jobs, reports and migrations need their own roles or session overrides; PG warns against `idle_session_timeout` through pooling middleware. "30 or 60 seconds" is a practitioner default (Crunchy Data, 2020), not a measurement; a client-side connection value without latency data takes ER-21's generous default, never a tight one.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [PostgreSQL 18: Client Connection Defaults](https://www.postgresql.org/docs/current/runtime-config-client.html) (PGDG); [node-postgres Client](https://node-postgres.com/apis/client) (brianc); [Statement timeout](https://www.crunchydata.com/blog/control-runaway-postgres-queries-with-statement-timeout) (Kerstiens, Crunchy Data, 2020); [Postgres Job Queues & Failure By MVCC](https://brandur.org/postgres-queues) (Leach, 2015; controlled reproduction at about 50 jobs/s: one long transaction raised job-lock time about 15x, 60k queued jobs after an hour, nearly 100,000 dead rows; statement_timeout alone insufficient); [PostgreSQL 18 Error Codes](https://www.postgresql.org/docs/current/errcodes-appendix.html) (PGDG) · dossier: data-layer-hygiene G209-F10; eval-v1-calibration E01-F05; pilot-auto-calibration A01-F10

### DA-22 — Every join states how and its cardinality

- **Rule:** Never strip notebook outputs in a hardening pass without approval: once stripped versions are committed the outputs are gone from history, and in research and backtest notebooks saved figures and tables may be the only record of a result. - **Detect:** `filter=nbstripout` in `.gitattributes` and nbstripout pre-commit hooks; `nbstripout --dry-run notebooks/*.ipynb`; notebooks with outputs and no paired `.py` or `.md`.
- **Not when:** stripping is a legitimate team choice (diff size, leaks, merge conflicts); library-style notebooks whose outputs CI regenerates should be stripped.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** C
- **Source:** [nbstripout](https://github.com/kynan/nbstripout) (kynan, 2026); [Jupytext](https://github.com/mwouts/jupytext) (Wouts); [nbdime](https://nbdime.readthedocs.io/en/latest/) (Jupyter) · dossier: data-pipelines-notebooks G109-F18

### DA-41 — Move shared or result-critical notebook logic into tested modules
- **Rule:** Extract joins, features, labels and PnL logic that notebooks share or that results depend on into imported, tested modules, only after DA-38 re-execution passes and a DA-21 harness exists. The trigger is shared or result-critical logic, not notebooks in general.
- **Detect:** `jupytext --to py` into `<scratch_dir>/notebooks/`, the run's scratch directory outside the repository (never inside the repository, where detectors and test runners would pick the exports up, nor a temp directory of its own: protocol-preflight PF-21; eval-v2-calibration E02-F08), then a duplicate-code checker on the exports (for example `pylint --disable=all --enable=duplicate-code`); join, feature, label and PnL function definitions inside notebooks; equivalents already in `src/` that notebooks re-implement.
- **Not when:** teams that test inside notebooks (nbdev); extraction changes behaviour when code relied on globals from earlier cells, which DA-38 exposes first.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** C
- **Source:** [Pimentel et al., best practice 3](https://leomurta.github.io/papers/pimentel2019a.pdf) (MSR 2019); [I Don't Like Notebooks](https://docs.google.com/presentation/d/1n2RlMdmv1p25Xy5thJUhkKGvjtV-dkAIsUXP-AL4ffI/) (Grus, JupyterCon 2018); [Operationalizing ML](https://arxiv.org/abs/2209.09125) (Shankar et al., 2022; one engineer lost a day and a half to a notebook run with wrong inputs); [nbdev2](https://www.fast.ai/posts/2022-07-28-nbdev2.html) (Husain & Howard, 2022; counterpoint) · dossier: data-pipelines-notebooks G109-F19; eval-v2-calibration E02-F08

## False-positive exclusions

- `*_id` heuristic hits on external identifiers (exchange order IDs, `stripe_customer_id`); references across databases (DA-07).
- App checks that are UX policy (password strength); a Django `CharField` with `unique=True` and `blank=True`, which needs `null=True` to avoid unique violations on blank values (DA-01).
- Missing FK indexes on MySQL/InnoDB and on Django FKs with the default `db_index` (both created automatically) (DA-08).
- Zero-scan indexes that back constraints or serve monthly jobs or replicas; any "unused" verdict from static analysis or a short statistics window (DA-16).
- Single-writer tables and deliberately app-generated IDs (DA-13); Redis keys meant to be permanent (DA-20); small bounded tables (DA-17).
- `timestamp` columns for future civil times or values never used in arithmetic (DA-18); `SELECT *` inside `EXISTS` and ad-hoc scripts (DA-19).
- `str.join` and other non-dataframe `.join` hits (DA-22); joins declared `m:m` on purpose; deliberate reliance on pandas null-key matching (DA-23).
- Defensive `.copy()` in code pinned below pandas 3.0 (DA-24); `inplace=True` on the values-inplace methods (DA-25); style-only PD hits (DA-26); NEP 50 hits in float64/int64-only code (DA-28).
- Sums where missing truly means zero (DA-29); intended index alignment (DA-31).
- Negative shifts that build labels, centred windows in plotting code, exact as-of matches on availability timestamps (DA-36); combined preprocessing that competition rules allow (DA-35).
- Notebook-idiom lint hits (DA-39); notebooks whose outputs CI regenerates (DA-40); teams that test inside notebooks (DA-41).

## Evidence limits

- Cross-layer drift numbers come from Rails (Yang et al.: 12 apps) and web apps (CFinder: 8); no measurement exists for Python or TypeScript stacks, and no open-source equivalent of database_consistency or active_record_doctor was found for SQLAlchemy, Prisma or Drizzle, so DA-01 there is a manual diff.
- The dossier's detection SQL for missing FKs, missing FK indexes, unused indexes and polymorphic pairs was not executed against a live Postgres; only the SQLite claims were reproduced (SQLite 3.45.3). Prefer vetted queries (Cybertec, PG wiki) and tool checkers.
- Schema-smell prevalence (Smelly Relations 2018, SQLCheck 2020) comes from regex extraction of embedded SQL, with no 2024–2026 replication on ORM-heavy code.
- Version-gated facts, as of 2026-09-23 (data-layer-hygiene and data-pipelines-notebooks summaries): Django from the 5.2 LTS docs while 6.1.1 was the current release on PyPI; Prisma v7 docs while npm's `latest` tag pointed to 8.0.0-rc.15 (error codes and migrate-diff flags change); pandas 3.0.6, polars 1.44.2, NumPy 2.x. Before a run, re-check the current releases on PyPI (`pip index versions django`) and npm (`npm view prisma dist-tags`), and read the project's installed versions (procedure step 3). Atlas lint is Pro-only since v0.38 and squawk is Postgres-only, so no free DDL linter for MySQL or SQLite migrations was identified.
- Timeout and pool values for bot or trading workloads are unmeasured; 30–60 s and `(cores * 2) + spindles` are heuristics. A client-side timeout added in code without latency data therefore takes ER-21's generous, owner-tunable default (eval-v1-calibration E01-F05), which bounds the wait but is not a tuned value.
- Ruff covers NaN comparison, NumPy 2 removals, legacy RNG, `inplace` and `.values`, nothing else in this lens. dslinter (last release 2.0.9, June 2022; pins pylint 2.12 and astroid 2.9, Python 3.10 at most) may run only in an isolated legacy environment and its hits are unvalidated hints; leakage-analysis is the only detector with published accuracy.
- The ast-grep and ripgrep patterns here are syntactic, untested against a corpus, and blind to dtypes and data.
- No prevalence study exists for silent join duplication or for look-ahead in open-source backtests; the truncation-invariance test is derived, not validated. The epoch-unit mis-parse in DA-34 is a verifier reproduction on pandas 3.0.6, not documented behaviour. polars `validate` is unsupported in streaming, and no streaming cardinality check was found.
- Notebook figures come from GitHub notebooks (Pimentel, 2019) and biomedical publications (Samuel & Mietchen, 2024); schema-validation benefits come from Google-scale production, extrapolated to small repos.
- Practitioner sources are Lobsters, engineering blogs and incident write-ups; HN, Reddit and Stack Overflow were not reached.
