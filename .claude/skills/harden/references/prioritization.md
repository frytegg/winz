# Prioritization

> Purpose: order verified findings by consequence first and location second, gate every history signal, fall back to a size baseline, apply the cold-code policy per change category, give every finding its tier from one deterministic table, map each tier to applied or report-only for the run's mode, and treat metric thresholds as labelled review triggers.
> Read at: Phase 4 (prioritise), after the verification stage and before the report is written.

## Steps

Run the scripts with `python` on Windows and `python3` on macOS/Linux.

1. Load `.harden/findings.json`, `.harden/inventory.json`, `.harden/config.json` and `.harden/progress.md`. Rank only findings with `"verified": true`; unverified candidates wait for the verification stage.
2. Split findings into two bands (PZ-01, PZ-02). The consequence band holds security findings, correctness defects (data loss, crash, wrong monetary arithmetic), known-vulnerable dependencies and dormant-but-activatable code. Everything else is the maintainability band. Check in `.harden/tools/` that the dependency audit and SAST covered every tracked file; if they did not, send the run back to detection.
3. Record two answers in `.harden/progress.md`: which modules planned work will touch, and which situation applies (release preparation, handover, open-sourcing, pre-audit, maintenance only, prototype becoming a product, agent feature work next). Release preparation is this skill's own trigger ("before a release"). In autonomous mode, the default, both answers come from the run profile `.harden/profile.json` (its `situation` and its future-work list) and no question is asked. A value the profile lacks takes the conservative default: maintenance only, which widens no cold column, and no declared future work. Log the default in `.harden/progress.md` and the report's Limits (user-policy-autonomy U01-F01, U01-F04). With `--interactive`, ask the user both questions. PZ-13, PZ-14 and the Tier table use the answers.
4. Read the history verdict (PZ-03 to PZ-06). If `.harden/inventory.json` is missing, run `python "${CLAUDE_SKILL_DIR}/scripts/inventory.py" --repo . --out .harden/inventory.json`. Note whether history is sufficient, which criterion failed, the squash signals and the agent-adoption marker. Switch off ownership signals where PZ-05 applies.
5. Rank locations.
   - Gate passed: run `python "${CLAUDE_SKILL_DIR}/scripts/rank.py" --since 12.months --top 50` (writes `.harden/rank.json`). Check its exclusions (PZ-06), read the fix commits of the top files (PZ-08) and run the backtest (PZ-09).
   - Gate failed, or history lost the backtest: use the size-descending order that rank.py falls back to (PZ-10) and add the ladder rungs by hand (PZ-11).
6. Set `location_class` on every finding (PZ-13) and list the co-change partners of the top files (PZ-12).
7. Tier every finding with the Tier table below (PZ-24). The table applies the cold-code policy (PZ-14, PZ-15) in a fixed order. On a `cold` file, a structural finding in a category that PZ-14 governs becomes T2 report-only. An `unknown` file counts as warm (PZ-13). T0 items and behavioural items keep their tier at every temperature. The flip conditions come last. Log every change of tier or class in the finding's `notes`, with the id of the rule that caused it. Then decide, with the Autonomous mode table below, whether each finding will be applied or stays report-only in this run's mode; the mode never changes a tier or a class.
8. Check every metric-triggered finding against PZ-16 to PZ-20: use the project's configured threshold where one exists, write the threshold's source and provenance into the finding's evidence detail, and drop any finding that a percentile alone created.
9. Order and cut (PZ-21, PZ-22) with the single ordering key defined in reporting.md RP-06: blocking first, then severity, then confidence rung, then location (consequence band before maintainability band, PZ-01; then `location_class` in the order `hotspot`, then `warm` and `unknown` together (PZ-13 treats `unknown` as warm), then `cold`, and the file's rank in `.harden/rank.json`; then functions inside a file, PZ-20), then PZ-22's dimension order. `findings.py build`, `assemble` and `approvals` write `.harden/findings.json` in this order (the band from `.harden/decisions.json` when an entry sets it, else the consequence lenses and behavioural class), and `mark` keeps it, because protocol-change step 3 builds the apply queue from it (pilot-auto-calibration A01-F34, A01-F60). Introduce no numeric score. Keep at most about 20 main items, move the rest to a "next tier" appendix, and put nits in one collapsed non-blocking list.
10. Write the method-and-limits block and the threshold-policy block at the top of `.harden/report.md` (PZ-17, PZ-23). Then run `python "${CLAUDE_SKILL_DIR}/scripts/validate_findings.py" .harden/findings.json --repo .`, fix every error, and if the nit-cap warning fires, keep the cap's worth of nits in the main list and list the rest in the report's Appendix nit-overflow table (reporting RP-06; eval-v1-calibration E01-F06).

## Tier table

PZ-24 applies this table to every verified finding at step 7. Check the rows top to bottom; the first row whose category fits the finding decides. Evidence rungs are the findings-schema ladder (reporting RP-03), and E-levels are dead-code DC-02's. A `needs_review` or `inference` finding is T2 whatever its row once detection step 12's one reproduction attempt has failed or did not apply (detection DT-27; pilot-auto-calibration A01-F52): a row whose evidence column accepts a source trace means a trace raised to `failing_test`, `reproduction` or `tool_high_precision` before tiering, and `validate_findings.py` rejects a verified T0 or T1 finding left below those rungs (pilot-auto-calibration A01-F11). Every behavioural row also needs a new test that fails at base (PC-14): a behavioural finding for which no such test can be specified is T2 (PC-14's human lane). "Every temperature" means the cold-code policy (PZ-14) never demotes the row. Neither a T1 category approval nor a T1 switch (Autonomous mode below) ever covers an item this table places in T2 (invariant 8), and with `--interactive` a T2 item is never applied: a warn-first mitigation or a safer default for it goes into its report entry as its `Proposed first step:` line for the owner (reporting RP-07; eval-v2-calibration E02-F03). In autonomous mode with `auto_apply.owner_judgement` true, the Owner-judgement lane under Autonomous mode decides each T2 item instead and may apply its most conservative standard option (user-policy-autonomy U01-F06, U01-F11).

Row 21 promises that the skill's evaluation met: an `assert` replaced by the exception it stands for (ER-25); a non-zero exit when the requested output was not written (ER-15); a non-zero exit through the documented error path when an input the caller named could not be read or parsed (ER-15, OP-12; Fail-open kind 2); cancellation allowed to propagate instead of being swallowed by a `return` in `finally` (ER-09); ISO 8601 with `Z` for a round trip the code controls (NM-20); a tolerance where the code reads a computed float as "equal" or "zero" (NM-16); a stale copy of a formula whose sibling was fixed in history (DU-04).

**Fail-open findings.** A finding whose code carries on after a failure (a swallowed or log-only handler, a success-shaped fallback, a check that fails open) is tiered per consequence (PC-25) by what its headline reproduction shows wrong at base. Take the first kind that fits and write the kind and the reliance check into the finding's `notes`, for example `fail-open kind 2; reliance: none (R1-R6 checked)` or `fail-open kind 2; reliance: R1 src/engine.rs:48 comment` (pilot-auto-calibration A01-F09; eval-v3-calibration E03-F01, E03-F02).

1. **Silent containment (kind 1).** The outcome is one the code may keep: a batch item skipped or quarantined while the rest proceeds (ER-14), a last-known-good value kept on reload (OP-13), a best-effort cleanup. Only the record is missing: no line at the project's default log level or on stderr, and no counter or count that the object or the output exposes. The fix records each occurrence through a logger the module or its package already uses (stderr only in code that runs solely under the project's own entry points; never a machine-read stdout, and never a new handler or a direct stderr write in exported library code, where a record with no existing logger is T2 with the record as its `Proposed first step:`, because handlers are the prerogative of the application that uses the library, Python Logging HOWTO), naming the item and the error but no secret or input content (OP-01), as one line per batch with a count where one batch or poll can produce many (OP-10). No result, return value, stdout byte or exit code changes, so it is not a flip: row 22, T1 behavioural, with a test that captures that channel and asserts one record at the stated level naming the item (none at base), not the record's wording (PC-22).
2. **Wrong result presented as valid (kind 2).** The output presents a substituted value as a genuine result: defaults or an empty value in place of an input the caller named, a placeholder number that enters a total or a decision, a label or status naming a source that did not supply the value, exit 0 or a success message after a required step failed (ER-02, ER-15, OP-12; CWE-393). The claim the output makes is the promise, so the fix is row 21's restoring change: T1 behavioural, applied fail-closed in one item. It surfaces the failure through a channel the code already has, the smallest that makes the result truthful. For an input that is itself a failure (a path, flag value or variable the caller named that is missing or unreadable; any file that exists and whose parse raised at base, the error the fallback caught): the error the same function already raises for a sibling failure, else the error class or exit code the project documents for runtime errors, else the entry point's existing error path (a missing boundary handler is its own ER-14 finding); the test asserts the documented outcome at the entry point. Where the PF-14 inventory lists external consumers or live data, only two channels are applied: the error the same function already raises for a sibling failure, which those consumers already handle, and the documented non-zero exit of a CLI command whose input the caller named. Any other channel (a new error from an exported function, a per-item status or `None`) is T2 with the staged path as its `Proposed first step:`, as PEP 479 and Node staged the surfacing of silently swallowed failures (behaviour-changing-fixes G102-F07, G102-F08). A new error that no existing handler of a long-running process would catch (it would end the process) is T2. For one unavailable item inside an otherwise valid result: a status member, `None`, `Option` or `Result` the signature already declares for that item, never a rejection of the whole result unless the docs promise all or nothing (PC-24). Where the gates run no type checker over that value, the demonstrating test or a PF-19 characterization case passes the item through every in-repository consumer of the value (a total, a renderer, a rule); otherwise the item is T2. A channel the signature does not declare yet is row 18 for a public type and T2 otherwise, with that channel as its `Proposed first step:`. A surfacing fix that needs a new public member, field or parameter is row 18. An implicit optional input that is absent (a default path the caller did not name) keeps its fallback, as Python's `configparser.read()` ignores configuration files it cannot open among several candidate locations; its record is a kind 1 fix when none exists, and whether it should fail goes under the report's Open owner items. The surfacing fix and any record added for the kept fallback are separate items and commits.
3. **Tightening (kind 3).** The code processes the input it receives, or proceeds without a check that could not run, and the fix would make it reject or stop where it proceeds today (new validation, a stricter parser, a new bound, a check that fails closed). Row 21 as written: T1 only when the code, its docs or a sibling fix promise the closed behaviour and PC-24 leaves no newly rejected valid class, or the user accepts the class with `--interactive` (PC-24 allows that only when no member is shown to occur); otherwise T2.

**Reliance signals.** A kind 2 or 3 fix is T2 in every mode when any of these holds, and a kind 1 fix is T2 under R1 or R5, because the owner who documented a degradation decides how loud it is:
- R1: the docs, help text, a docstring or a comment at the fallback state it as intended, giving a reason or a promise (for example "so that a typo in the config never stops the engine"); a comment that only restates what the code does (RD-13) and a log message, the defect's own warning included, are not R1;
- R2: an existing test asserts the lenient outcome;
- R3: a consumer in the PF-14 inventory run as documented, reaches the lenient branch (for example a quickstart that runs the command before any config file exists) (a README, CI or example command from `.harden/inventory.json`, a cron line, a dependent module in the repository);
- R4: a previously accepted valid input that PC-24 pins from the project's fixtures, samples or docs reaches the lenient branch and the fix changes its outcome;
- R5: an option, flag or setting controls the leniency;
- R6: the branch runs inside a long-running process (a service, worker, bot, poller or watch loop) on data that arrives at run time (requests, messages, events, polled responses) that the run cannot see.

The T2 entry's `Proposed first step:` gives the staged path: a warning the fix adds that names the change to come and where to comment on it (PEP 387), then enforcement in a later release the owner ships. A log line the defect already emits is never that warning, and no mode applies an enforce stage (PC-14). PF-14's external consumers alone are not a signal for a kind 2 fix through one of the two channels above: they receive a result they cannot tell from a real one. Such a fix gets a line under the report's Open owner items with its old -> new behaviour and the release decision it leaves the owner (SemVer FAQ; PC-14). When a finding's headline is a wrong result and the item is T2, a record-only fix for it is its `Proposed first step:`, never a kind 1 item of its own (E02-F03).

Situations (step 3) change only the cold column. At a handover, comments and docs on cold files are in scope (rows 5 and 7). At release preparation, docs on cold files are in scope (row 7). A prototype becoming a product, and the modules an agent will work on next, count as hot. Before a security audit, compiler warnings and TODOs on cold files are in scope too, and the code freezes afterwards (PZ-14). The situation is the profile's `situation` in autonomous mode and the user's answer with `--interactive` (step 3).

### Autonomous mode

The run mode never changes a tier. Every mode tiers findings with the table above in the same way; only the source of an approval differs, and in autonomous mode `auto_apply.owner_judgement` can approve a T2 item through the Owner-judgement lane below, which gives an applied T2 item the class of its change (invariant 8; user-policy-autonomy U01-F01, U01-F06). Autonomous mode is the default, and in it no question is ever asked. The run profile `.harden/profile.json`, which the owner writes and a script validates before the run, gives every answer this file would ask for: the step 3 situation and future-work list, and the Phase 6 approvals through its `auto_apply` switches (U01-F04). A switch the profile does not set reads as false, the conservative default, and every default taken is logged in `.harden/progress.md` and the report's Limits (U01-F01). Without a valid profile, the run stays report-only for anything that would execute project code, every gate included, so nothing is applied, and its report says so (U01-F04). `--report-only` never applies anything; `--interactive` keeps the live Phase 6 answers.

After step 7, take the first line of this table that fits each finding. Where a Tier table row asks for an approval, an own approval or its own explicit approval, this table says what stands for it in each mode. "Applied" means applied through protocol-change.md exactly as after a live approval: net check and characterization tests per batch, every gate after every commit, and the final end-to-end verifier, which may still revert it (U01-F02).

**Money paths** (pilot-auto-calibration A01-F06 to A01-F08). Whether an item is "on a money, order, key, signing or transaction path", in this table, in the Tier table and in protocol-change.md, is decided from the production files it changes, never the new test files the pass writes: the finding's `file` here (none for an item that only adds tests), and every staged file again at apply time (protocol-change steps 3 and 9). It decides approvals only, never a tier or a class (PZ-24 step 6). With `--interactive`, the user's answer decides each money-path item (SKILL.md Phase 6), and a profile's list only helps pick the files to show.
- When the profile sets `money_paths_globs`, a script matches them: `python "${CLAUDE_SKILL_DIR}/scripts/validate_profile.py" .harden/profile.json --repo . --base <base_sha> --classify <files>` prints `money-path`, `not-money-path` or `judgement` for each file (`--paths-from <list>` takes many). Never match a pattern by eye; a file the script gives no verdict (exit 1 or 2) is classified by judgement.
- The item is on a money path when one of its files prints `money-path`, or when the code its change touches creates, submits, amends or cancels orders, payments, transfers or withdrawals, signs anything, broadcasts transactions, or reads, derives, stores, logs or sends private keys, seed phrases, API keys or secrets. That floor holds whatever the globs say (A01-F08); its evidence is the verifier's `money-path: floor <kind> at <file:line>` line (detection step 11) or, for lines a fix adds at apply time, the orchestrator's own file:line. A lens or verifier judgement that names a floor operation without such a line, and a verified finding whose verifier note has no `money-path:` line, are checked by the orchestrator against the lines the change touches, with file:line; when it cannot tell, the floor holds.
- Otherwise it is not on a money path, even when a lens or verifier judged it money-like; the report lists each such item under Autonomous decisions (reporting RP-07).
- An item is on a **live-effect path** when the lines its change touches do any of six things. (1) They change which private key, seed phrase, API key, token or other secret is read, derived, stored, logged or sent, or where it comes from or goes. (2) They sign, or change what is signed. (3) They build, send or broadcast the request, message or transaction that creates, submits, amends or cancels an order, payment, transfer or withdrawal at a venue, wallet or chain outside the process, that call's timeout, retry and idempotency included (ER-22). (4) They deploy or migrate. (5) They change a call to a chain system contract or precompile that the local test network only emulates (Hedera's token service at `0x167`): its target, selector, arguments or the handling of its response code. Or they change the storage layout of an upgradeable contract whose deployed state only the live chain holds. (6) They change the behaviour of code that runs only under an entry point that signs, deploys or submits: a script or task the profile's `forbidden_commands` refuse, a Hardhat deploy script or task, a Foundry `*.s.sol` script, a migration. A test of such a change exercises only a stub or an emulation of the counterpart, so autonomous mode never applies it (user-policy-autonomy U01-F12). Logic that decides amounts, prices or when to act, and contract functions the local chain executes (a swap, a liquidity function), are money paths, not live-effect paths. A contract function that calls a system contract stays a money path when the change leaves that call as it is and its test puts a local stub at the system contract's address with no fork (U01-F12). A bound or a record added to a read-only call that carries a credential (a timeout on a price request) does none of (1) to (6) (pilot-auto-calibration A01-F27). Every verified finding gets one `notes` entry, `live-effect: <kind> at <file:line>` (kind `key`, `sign`, `submit`, `deploy`, `system-contract` or `live-only`) or `live-effect: none`. A change proven AST-identical to its parent (A01-F01) is on no live-effect path. Otherwise, doubt keeps the item on one.
- The script prints `judgement` for every file when the profile does not set `money_paths_globs`, or when one of its patterns matches no file of the base commit (the list then describes another tree, A01-F07). The lens and verifier judgement then decides, a disagreement takes the reading that withholds, and the default is logged (U01-F01).
- Give every verified finding one `notes` entry: `money-path: glob <pattern>` (followed by `; floor <kind> at <file:line>` when the floor holds too), `money-path: floor <kind> at <file:line>`, `money-path: none`, `money-path: none; judged money-like by <verifier or pass id>: <reason>`, or `money-path: judgement yes` or `no`.
- The globs decide approvals only. What a change must prove still follows what the code does (PC-15's differential, PC-16's scans), and neither the globs nor `auto_apply.money_paths` relaxes U01-F03: a behavioural item on a money path is applied only when PC-14 condition (d) holds: an offline check executes it, its pinned characterization cases accept it (U01-F14), or, with `auto_apply.owner_judgement`, the differential and net check pass.

## Rules

Tier and Class say what a rule lets the skill do. Ordering rules are T2 report-only because they change the report, not the code. The findings they order keep the tier and class their lens rule gave them, except where the cold-code policy (PZ-14) or the Tier table (PZ-24) changes them and logs the change. Fix risk is the risk of the fix the rule governs.

### PZ-01 — Rank consequence before location
- **Rule:** Put security findings, correctness defects (data loss, crash, wrong monetary arithmetic), known-vulnerable dependencies and dormant-but-activatable code (PZ-02) first, ordered by severity, whatever the file's churn, age or size. Use churn and complexity only to order work inside that set, never to drop a file from it, and never lower a security item because the code is old.
- **Detect:** Confirm the dependency audit and SAST ran over the whole repo, not only hotspots. Map entry points (`rg -n '(app|router|server)[.](get|post|put|patch|delete|use)[(]' src`, `rg -n '(process[.]argv|yargs|commander|argparse|click[.]command)' src`) and treat files reachable from them as consequence candidates. Record the CVSS version of every vulnerability score and treat CVSS Base as severity, not risk.
- **Not when:** Pattern-only security hits in cold, well-exercised code go to the report, not to a fix batch. Fixes that tighten behaviour (stricter validation, changed error responses) go to an approval batch. Consequence greps over-match (e.g. "amount" in UI copy); prune them by hand.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [SEC order, Knight Capital](https://www.sec.gov/litigation/admin/2013/34-70694.pdf) (U.S. SEC, 2013: code unused since 2003 stayed "present and callable", a repurposed flag reactivated it, over $460M lost in about 45 minutes); [LOG4J2-313](https://issues.apache.org/jira/browse/LOG4J2-313) (Apache JIRA, 2013: JNDI lookup added in July 2013; the dossier's GitHub check found no commits to `JndiLookup.java` from July 2017 to the December 2021 disclosure); [How Long Do Vulnerabilities Live in the Code?](https://www.usenix.org/conference/usenixsecurity22/presentation/alexopoulos) (Alexopoulos et al., 2022: average lifetime about 4 years, ~2 for Chromium, ~7 for OpenSSL); [Challenges with applying vulnerability prediction models](https://www.microsoft.com/en-us/research/publication/challenges-with-applying-vulnerability-prediction-models/) (Morrison et al., 2015: Windows, file-level precision below 0.5 and recall below 0.2); [Real-World Labelling When Predicting Software Vulnerabilities](https://orbilu.uni.lu/bitstream/10993/40076/1/sample-sigconf%20%283%29.pdf) (Jimenez et al., 2019: MCC 0.77 to 0.08 on the Linux kernel under realistic labelling); [CVSS v4.0 User Guide](https://www.first.org/cvss/v4-0/user-guide) (FIRST, 2025) · dossier: prioritization T19-F09, T19-F19; hotspot-evidence G104-F13, G104-F14; finished-project-scope G101-F06; industry-review-guidelines T02-F07

### PZ-02 — Dormant-but-activatable code is its own category
- **Rule:** Classify code reachable only through a flag, config key, env var, CLI option, disabled route or job, or commented-out code as dormant, never as cold, and rank it in the consequence band. Remove a stale flag and the code it guards together, in one approval batch, after checking the flag's value in every environment config. Never repurpose an existing flag, config key or enum value.
- **Detect:** `grep -rnE "process\.env\.|getenv\(|feature_?flag|isEnabled\(" src`, then each flag's value in every deployed config (a value constant everywhere means one side is dead); `git log -S '<flag-name>'` for keys whose meaning changed; routes, jobs and subcommands that are defined but never registered; commented-out code blocks.
- **Not when:** Kill switches, disaster-recovery paths and platform-specific branches are intentional: keep them, document them and add a test that exercises them. Knight's loss also needed a deployment error, so claim a removed hazard, not a single cause.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** high · **Grade:** B

### PZ-03 — Gate every history signal on sufficiency

### PZ-04 — Detect squash and agent-era history and change what you count
- **Rule:** In a squash-merged history, count each squash commit as one change event per file and switch off authorship and timing metrics. From the date the first agent config file was committed, count change events instead of lines, and state in the method block that event counts inflate too.

### PZ-06 — Strip non-essential change before counting
- **Rule:** Before counting churn, drop merges (`--no-merges --first-parent`), fold renames into the current path (`-M`), ignore whitespace-only edits (`-w --ignore-blank-lines`), skip the revisions listed in `.git-blame-ignore-revs`, and exclude generated, vendored, lock, minified and snapshot paths. - **Detect:** Compare the exclusions in `.harden/rank.json` with `git log --no-merges --first-parent -M -w --ignore-blank-lines --numstat --format='@@%H %ct' -- . Extract ignore-revs SHAs first with `grep -Eo '^[0-9a-f]{40}' .git-blame-ignore-revs > ignore.txt`; a blank line in a raw `grep -f` pattern file filters out every SHA.
- **Not when:** Drop `-w` for Python, YAML, Makefiles and other indentation-sensitive files. Plain `':(exclude)**/*.lock'` misses top-level lockfiles. ### PZ-09 — Backtest the history ranking against size before trusting it

### PZ-13 — Build a temperature map; declared future work overrides history
- **Rule:** Before choosing actions, classify every file as hot (changed in the filtered 12-month window, or on the declared future-work list: the profile's in autonomous mode, the user's with `--interactive`), cold (its dated history shows no change in that window) or dormant (PZ-02). The sufficiency gate and the backtest (PZ-03, PZ-09) decide whether history may rank files, not whether a file changed: a short or failed history still dates each file's last change. An autonomous run never asks, so `unknown` keeps that default reading (user-policy-autonomy U01-F01).
- **Detect:** Take the modules planned work will touch from the profile's future-work list in autonomous mode, or ask the user with `--interactive` (step 3), and record the answer in `.harden/progress.md`. Pending-work hint: `git grep -n -E 'TODO|FIXME|HACK' | cut -d: -f1 | sort | uniq -c | sort -nr`. Findings whose `location_class` is `unknown` while `.harden/rank.json` dates their file are mis-classified.
- **Not when:** The 12-month window and the top-decile cut have no source. Churn looks backward, so for a prototype becoming a product or before agent feature work, declared future change overrides history; if the agent's targets are unknown, limit the pass to tests, dead code and the report. Age is not maturity for a low-usage project. ### PZ-14 — Decide cold-code actions by change category
- **Rule:** The cold-code policy governs structural changes only.
