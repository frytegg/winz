# Lens: Duplication

> Purpose: find the clone groups that carry real risk (inconsistent copies, missed fixes, copies edited in lockstep), triage each one, and never deduplicate to hit a percentage.
> Read when: the duplication lens is in scope, or a detector or linter reports clones, identical branches or identical functions.

## Procedure

You are a fresh-context, read-only lens subagent with Read, Grep and Glob only (detection step 8): you edit nothing and run nothing. Every command this file names (detectors, `git log`, `git blame`, `git diff --no-index`) is an orchestrator-run command, never in a mode that writes into the tree (for example `jscpd --update-baseline`), whose raw output is saved under `.harden/tools/`; you read those files. A detector with no output file is a coverage gap, never a clean result. If you are the unseeded pass, you receive no tool output: compare the copies you read yourself and say so in your limits.

1. **Load scope.** Read `.harden/inventory.json` (languages, generated and vendor dirs, history-sufficiency verdict) and the slice and exclude globs the orchestrator gave you. Check from each run's recorded arguments and per-format rows that the DU-01 exclusions were applied before trusting its output.
2. **Read the detector outputs per language family.** The orchestrator runs them with the exact commands, pinned versions and flags in the language file for each detected language; this lens names the tool and rule id. Record tool version, minimum size and scanned formats for every run.
   - TypeScript, JavaScript and Python: jscpd 5.3.2 token mode, the formats the duplication dossier names (`--format typescript,javascript,python`), kinds `exact`, `renamed` (with `--ignore-identifiers --ignore-literals`) and `gap` (with `--max-gap-lines`).
   - JS/TS: also jscpd AST mode (`--similarity`, kind `ast`); eslint-plugin-sonarjs 4.2.1 rules S1871 `no-duplicated-branches`, S3923 `no-all-duplicated-branches`, S4144 `no-identical-functions`, S2301 `no-selector-parameter` (needs type information), S1192 `no-duplicate-string` (not in `recommended`; enable it for this run only), S9078 `no-duplicate-parameterized-test-case`, S8754 `no-duplicate-test-title`.
   - Python: pylint 4.0.x R0801 `duplicate-code` (default 4 lines; raise it before acting), Ruff SIM114, Ruff FBT001/FBT002.
   - Java and C++: PMD CPD 7.27.0 (`--minimum-tokens` is required; `--ignore-identifiers`/`--ignore-literals` apply to Java and C++ only).
   - SonarQube Server, only when the project already uses it: read its duplication measures; do not reconfigure it.
   - Any other language (Rust, Go, Solidity, ...): jscpd advertises 224 formats, but the dossiers verify no jscpd format id beyond typescript, javascript and python, so use a detector only if its language file names one; otherwise record the coverage gap in the candidate notes.
3. **Build one record per clone group:** every instance as `file:start-end`, clone kind (exact, renamed, gap/similar, ast), a line diff of the instances (the orchestrator's `git diff --no-index` output, or your own side-by-side reading), shared-commit count and clone age from the orchestrator's git outputs (DU-07), and deploy unit and owner of each path (DU-13). Test directories are scanned in a separate run: keep those groups apart (DU-14).
4. **Manual checks the tools do not make:**
   - diff each inconsistent group for a check, error path, rollback or fix present in one copy only (DU-04);
   - trace security commits to clones of the pre-fix fragment (DU-05);
   - write down the one requirement each group encodes, and hunt the same knowledge in other forms (DU-08);
   - list shared helpers steered by mode or boolean parameters (DU-12);
   - in assistant-built code, list same-purpose helpers across modules (DU-17).
5. **Triage** each group with DU-03 into `EXCLUDE`, `MAKE-CONSISTENT`, `MERGE` or `LEAVE+DOCUMENT`, with a one-line written reason. A group whose triage questions are not all answered stays a candidate with confidence `needs_review`.
6. **Return candidates as your final message:** JSON in the findings schema (`assets/findings.schema.json`) plus `files_read` (every file you read, with its line ranges); the orchestrator merges them into `.harden/candidates.json`. Per candidate: `lens: "duplication"`, `rule_ref: "DU-NN"`, `verified: false`, `status: "candidate"`, and the tier, class and fix risk of the rule. One candidate per clone group, anchored at the first instance, with evidence entries of kind `tool` (command, threshold, tool version), `source` (file:line of every sibling instance) and `git` (shared commits, fix commits). Never edit; never claim a fix.
7. **Never report a duplication percentage** without its tool, version, threshold and scanned formats (DU-01), and never use it to rank or justify a merge (DU-02).

## Rules

### DU-01 — Configure detection, scan only code, and state the threshold
- **Rule:** Use a language-aware, token-based detector with a minimum of roughly 50–100 tokens, and scan only programming-language formats: exclude generated, vendored, build output, minified files, lockfiles, data and markup. When hunting inconsistent clones, keep matches inside function boundaries. Print tool, version, minimum size and scanned formats next to every duplication number.
- **Detect:** Compare the run against documented defaults: jscpd 5.3.2 `--min-tokens` 50 and `--min-lines` 5 (`--mode mild` default drops whitespace only); SonarQube 100 tokens over 10 lines (30 for COBOL, 20 for ABAP), or 10 statements for Java, which cannot be overridden; PMD CPD 7.27.0 has no default because `--minimum-tokens` is required; pylint R0801 `--min-similarity-lines` defaults to 4. Read jscpd's per-format rows: a large unexpected gap between formats means non-code text is being counted.
- **Not when:** No threshold has been validated. OMG ASCQM 1.1 (July 2022) defaults of 90% similar elements between two functions and 10% copy-pasted instructions per instance are policy, not findings. Lower thresholds find more inconsistent clones and more noise; Kapser & Godfrey's harmful share moved in opposite directions between 30 and 60 tokens in Apache and Gnumeric (C, 2008). An 8-line pylint setting has no source: choose a value and state it.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [jscpd engine docs](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md) (jscpd 5.3.2, 2026); [jscpd CHANGELOG 5.3.2](https://github.com/kucherenko/jscpd/blob/master/rust/CHANGELOG.md) (jscpd, 2026); [Understanding measures and metrics](https://docs.sonarsource.com/sonarqube-server/2025.4/user-guide/code-metrics/metrics-definition) (SonarSource, 2025.4); [Analysis parameters](https://docs.sonarsource.com/sonarqube-server/2025.4/analyzing-source-code/analysis-parameters) (SonarSource, 2025.4); [Finding duplicated code with CPD](https://docs.pmd-code.org/latest/pmd_userdocs_cpd.html) (PMD 7.27.0, 2026); [Pylint all options](https://pylint.readthedocs.io/en/stable/user_guide/configuration/all-options.html) (PyCQA, 4.0.9); [ASCQM v1.1](https://www.omg.org/spec/ASCQM/1.1/PDF) (OMG, 2022); ["Cloning considered harmful" considered harmful](https://plg.uwaterloo.ca/~migod/papers/2008/emse08-ClonePatterns.pdf) (Kapser, Godfrey, EMSE 2008) · dossier: duplication T08-F11, T08-F17

### DU-02 — Never deduplicate to a percentage target
- **Rule:** Act only on clone groups selected by triage (DU-03). Report the global duplication percentage only as a trend indicator with its threshold; never plan, rank or justify a merge by it, and never treat it as a defect proxy.
- **Detect:** Policy check on the proposed change set: reject a dedupe plan driven by a global percentage or by "all detector hits"; require a triage record for every group proposed for merge.
- **Not when:** Identified groups do carry real cost (Juergens 2009; Mondal 2017 and 2018), so this rule forbids percentage-driven work, not merges. The evidence is mostly Java, C, C# and COBOL from 2005–2018, with little on TypeScript, Python or agent-maintained code.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Clones: what is that smell?](https://cabird.com/pdfs/rahman2012cwt.pdf) (Rahman, Bird, Devanbu, EMSE 2012); [Frequency and risks of changes to clones](https://doi.org/10.1145/1985793.1985836) (Göde, Koschke, ICSE 2011); [Is cloned code really stable?](https://link.springer.com/article/10.1007/s10664-017-9528-y) (Mondal, Rahman, Roy, Schneider, EMSE 2018); [Cloned code: stable code](https://doi.org/10.1002/smr.1551) (Harder, Göde, JSEP 2013); ["Cloning considered harmful" considered harmful](https://plg.uwaterloo.ca/~migod/papers/2008/emse08-ClonePatterns.pdf) (Kapser, Godfrey, EMSE 2008) · dossier: duplication T08-F03

### DU-03 — Triage every clone group: EXCLUDE, MAKE-CONSISTENT, MERGE, LEAVE+DOCUMENT
- **Rule:** Work in order. (0) `EXCLUDE` generated, vendored, lockfile, markup, data and fixture code. (1) `MAKE-CONSISTENT` first when copies differ in an unintended way (DU-04); this is a behaviour change. (2) `MERGE` only when all hold: the copies encode the same knowledge (one requirement change forces editing every copy, DU-08); history shows they changed together or received the same fix (DU-07); the differences parameterise without side effects (DU-06); the copies sit close together and the merge needs no new selector flag and no class-hierarchy change. (3) Otherwise `LEAVE+DOCUMENT` (DU-11): coincidental similarity, independent external requirements, separately deployed or owned components (DU-13), copies already diverging, or merges that need boolean or mode parameters or a pull-up into a superclass.
- **Detect:** From the detector JSON, fill per group: locations, clone kind, line diff of the instances, co-change count. Assign exactly one outcome with a written reason; a group is actionable only when every question above has an answer.
- **Not when:** Fowler and Beck hold that eliminating duplication "is a powerful way to drive out good designs", and PMD that "the most viable solution is to not duplicate". The procedure is a synthesis (grade B) and reviewers may triage one group differently, so record the reason and let the user overrule it.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [Do Code Clones Matter?](https://arxiv.org/pdf/1701.05472) (Juergens et al., ICSE 2009); ["Cloning considered harmful" considered harmful](https://plg.uwaterloo.ca/~migod/papers/2008/emse08-ClonePatterns.pdf) (Kapser, Godfrey, EMSE 2008); [The Pragmatic Programmer, Topic 9](https://media.pragprog.com/titles/tpp20/dry.pdf) (Thomas, Hunt, 2019); [Assessing the Refactorability of Software Clones](https://doi.org/10.1109/tse.2015.2448531) (Tsantalis et al., TSE 2015); [Beck Design Rules](https://martinfowler.com/bliki/BeckDesignRules.html) (Fowler, 2015); [Finding duplicated code with CPD](https://docs.pmd-code.org/latest/pmd_userdocs_cpd.html) (PMD, 2026) · dossier: duplication T08-F01

### DU-04 — Treat inconsistent near-miss and renamed clone groups as latent-bug candidates
- **Rule:** For each renamed (Type-2) or near-miss (Type-3) group, diff the instances for a null or bounds check, exception handling, transaction rollback, validation or escaping, log level or bug fix present in only one copy. If one copy was patched in a bug-fix commit and its sibling was not, flag the sibling as a probable defect. Apply the missing change only as its own behavioural commit with a test that demonstrates the defect; without that test or owner confirmation, report it.
- **Detect:** jscpd kinds `renamed` and `gap` with `--ignore-identifiers --ignore-literals --max-gap-lines` (JS/TS also `--similarity` and kind `ast`); PMD CPD `--ignore-identifiers --ignore-literals` for Java and C++. Diff fragments with `git diff --no-index`; compare each instance's commit set with `git log --format=%H -L <start>,<end>:<file>` and read the fix-commit messages. Exact-match detectors miss these groups by construction.
- **Not when:** Most inconsistencies are intentional: about three quarters in Juergens' five systems, 90% in its clone-aware COBOL system. Wagner (three automotive Java systems, 2016) concludes Type-3 clones "are not a major source of faults in these systems", and Göde & Koschke find unintentional inconsistent changes are few. Never change a difference without evidence that it is unintended.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** high · **Grade:** A
- **Source:** [Do Code Clones Matter?](https://arxiv.org/pdf/1701.05472) (Juergens, Deissenboeck, Hummel, Wagner, ICSE 2009); [On the Relationship of Inconsistent Software Clones and Faults](https://arxiv.org/abs/1611.08005) (Wagner et al., SANER 2016); [Bug Propagation through Code Cloning](https://doi.org/10.1109/icsme.2017.33) (Mondal, Roy, Schneider, ICSME 2017); [jscpd engine docs](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md) and [README](https://github.com/kucherenko/jscpd) (jscpd 5.3.2, 2026); [Frequency and risks of changes to clones](https://doi.org/10.1145/1985793.1985836) (Göde, Koschke, ICSE 2011) · dossier: duplication T08-F02

### DU-05 — Every security fix must reach every clone
- **Rule:** For each security-relevant commit (CVE, auth, access control, escaping or sanitising, crypto, injection), search the whole repository for clones of the pre-fix fragment and confirm that every copy received the fix. Do the same for snippets copied from third-party code, and record each snippet's origin and version so it can be tracked like a dependency. A copy that missed a fix follows the behavioural path of DU-04.
- **Detect:** `git log -i -E --grep='CVE-|security|vuln|xss|csrf|inject|saniti|escape|auth' --format='%h %s'`. For each hit, recover the pre-fix fragment with `git show <sha>^:<file>`, write it under `<scratch_dir>/prefix/`, in the run's scratch directory outside the repository (never into tracked source or `.harden/`, which holds tool binaries, venvs and outputs only: protocol-preflight PF-21), and scan that directory together with the in-scope source files (detection step 4) in a jscpd run of its own, with `--ignore-identifiers --min-tokens 30`, or `rg` for its distinctive identifiers and API calls; Semgrep or CodeQL for the vulnerable API pattern. Find pasted third-party code with `rg -n 'stackoverflow.com|copied from|adapted from'`.
- **Not when:** CWE-1041's mapping status is "Prohibited" ("primarily a quality issue with no direct security implications"): duplication amplifies a vulnerability but is not one by itself. ReDeBug and VUDDY work at OS-distribution scale on mostly C/C++ code; their yield inside one application repository is unmeasured.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** high · **Grade:** A
- **Source:** [ReDeBug: Finding Unpatched Code Clones in Entire OS Distributions](https://doi.org/10.1109/sp.2012.13) (Jang, Agrawal, Brumley, IEEE S&P 2012); [VUDDY](https://doi.org/10.1109/sp.2017.62) (Kim, Woo, Lee, Oh, IEEE S&P 2017); [CWE-1041: Use of Redundant Code](https://cwe.mitre.org/data/definitions/1041.html) (MITRE, CWE 4.20) · dossier: duplication T08-F13; eval-v2-calibration E02-F08

### DU-06 — Merge only when differences parameterise without side effects
- **Rule:** Before a merge, show that every difference parameterises without side effects: argument evaluation order, exception types and timing, shared-state mutation, early returns, resource cleanup and performance-sensitive paths stay identical. Prefer small Type-1/Type-2 production-code clones in the same method, class, file or module. Refuse merges that need a class-hierarchy refactoring (Pull Up Method, Extract Superclass, Template Method) unless every subclass is well covered by tests, and pin current behaviour with characterisation tests first (general practice, not from the cited studies).
- **Detect:** List every difference token by token from detector output plus a diff, and classify each as literal, identifier, expression, call or statement gap. Reject on a statement gap with side effects, divergent exception or cleanup paths, or a needed new hierarchy. Java: JDeodorant refactorability analysis. After a merge, confirm coverage of each former instance's callers did not drop; use mutation testing (Stryker, mutmut, PIT) on high-risk merges.
- **Not when:** All three empirical sources are Java only. Kim et al.'s 49–64% of genealogies that "cannot be easily removed" (two Java projects, 2005) reflects language limits of the time; do not transfer the figure to languages with generics and lambdas. Bavota's SZZ-based fault attribution is noisy.
- **Tier:** T1 · **Class:** structural · **Fix risk:** high · **Grade:** A
- **Source:** [Assessing the Refactorability of Software Clones](https://doi.org/10.1109/tse.2015.2448531) (Tsantalis, Mazinanian, Krishnan, TSE 2015); [When Does a Refactoring Induce Bugs?](https://doi.org/10.1109/scam.2012.20) (Bavota et al., SCAM 2012); [An Empirical Study of Code Clone Genealogies](https://web.cs.ucla.edu/~miryung/Publications/esecfse05-clonegenealogy.pdf) (Kim, Sazawal, Notkin, Murphy, ESEC/FSE 2005); [JDeodorant: Clone Refactoring Support beyond IDEs](http://blog.ieeesoftware.org/2016/10/jdeodorant-clone-refactoring-support.html) (Tsantalis, IEEE Software Blog, 2016) · dossier: duplication T08-F07

### DU-07 — Change history is the merge trigger; the rule of three is the fallback
- **Rule:** Count a group as meeting the history criterion of DU-03 when its instances were edited together in two or more commits or received the same fix. Leave groups never touched since creation and young two-instance clones that are still diverging. When the history-sufficiency verdict says history is thin, fall back to the rule of three: two similar instances stay, a third triggers extraction.
- **Detect:** Per instance, collect the commit set with `git log --format=%H -L <start>,<end>:<file>` and count shared commits with `comm -12`; at file level, intersect `git log --format=%H -- <file>` sets; compare fix-commit subjects (`git log -i --grep=fix`); clone age from `git blame --porcelain`. Use CodeScene change coupling only if the project already has it.
- **Not when:** Squash merges, formatting sweeps and renames inflate co-change, and finished projects may have little post-release history. The rule of three alone is folklore (grade C): Glass's original concerns reuse libraries across applications, and Dodds calls the related WET rule "similarly dogmatic and over prescriptive". No source validates co-change as a merge trigger against defect outcomes.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [An Empirical Study of Code Clone Genealogies](https://web.cs.ucla.edu/~miryung/Publications/esecfse05-clonegenealogy.pdf) (Kim et al., ESEC/FSE 2005); [JDeodorant blog](http://blog.ieeesoftware.org/2016/10/jdeodorant-clone-refactoring-support.html) (Tsantalis, 2016); [Change Coupling](https://codescene.io/docs/guides/technical/change-coupling.html) (CodeScene docs); [Rule of three](https://en.wikipedia.org/wiki/Rule_of_three_(computer_programming)) (Wikipedia); [The Rule of Three](https://blog.codinghorror.com/rule-of-three/) (Atwood, 2013); [AHA Programming](https://kentcdodds.com/blog/aha-programming) (Dodds, 2020) · dossier: duplication T08-F08

### DU-08 — Apply DRY to knowledge, not text
- **Rule:** Merge only duplicates that express the same piece of knowledge, and leave coincidental look-alikes (identical bodies serving different rules, such as the book's `validate_age` and `validate_quantity`). Conversely, hunt knowledge duplicated in different forms even when the text differs: the same constant, regex, URL, limit or schema hand-written in several places (DB schema plus struct, client plus server validation), and give it one authoritative source. Extracting a constant inside one component is in scope; introducing a shared schema or code generation across components is reported (DU-13).
- **Detect:** Per group, write the one requirement or business rule it implements; if the copies map to different rules, owners or tickets, the similarity is coincidental. For knowledge in other forms: sonarjs S1192 `no-duplicate-string` (default threshold 3, not in `recommended`), `rg` for repeated literals such as URLs, and a comparison of hand-written types and validators against DB and OpenAPI schemas.
- **Not when:** The knowledge test is subjective. Kapser & Godfrey rated repeated cross-cutting code (access control, logging, debugging) mostly good: 12 of 13 in Apache at 30 tokens, while Gnumeric at 30 tokens split 2 good and 2 harmful (C, 2008). A shared constant can couple the release cycles of separate services.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [The Pragmatic Programmer, 20th Anniversary Edition, Topic 9](https://media.pragprog.com/titles/tpp20/dry.pdf) (Thomas, Hunt, 2019); [Orthogonality and the DRY Principle](https://www.artima.com/articles/orthogonality-and-the-dry-principle) (Venners with Hunt and Thomas, Artima, 2003); [HN comment](https://news.ycombinator.com/item?id=22022599) (boffinism, 2020); [eslint-plugin-sonarjs](https://www.npmjs.com/package/eslint-plugin-sonarjs) (SonarSource, 4.2.1, 2026) · dossier: duplication T08-F04

### DU-09 — Rank parameterized-code clones first; rank platform, boilerplate and cross-cutting clones last
- **Rule:** Rank first clones that differ only in the function called or an identifier, and merge them by passing the varying call or value as a parameter or higher-order function; prefer a small pure function over a local mini-framework. Rank last platform variation, boiler-plating, cross-cutting checks deliberately repeated at call sites, and replicate-and-specialize clones with non-trivial interleaved changes. Parameterized clones were rated harmful in 5 of 6 (Apache, 30 tokens), 12 of 18 (Apache, 60), 16 of 21 (Gnumeric, 30) and 24 of 34 (Gnumeric, 60).
- **Detect:** Surface Type-2 groups with jscpd `--ignore-identifiers` (kind `renamed`) or PMD CPD `--ignore-identifiers --ignore-literals` (Java, C++). Sort them into "only names or called functions differ" versus "interleaved added statements". For the first kind, confirm that passing the call as an argument keeps evaluation order and exceptions.
- **Not when:** The ratings are the authors' own judgement on two C systems (2008). Fifteen Gnumeric parameterized clones were rated good because identifiers mirrored mathematical notation and gave traceability to the documentation. Other patterns were also often harmful in some samples: verbatim snippets 8 of 9 (Apache, 60) and 14 of 18 (Gnumeric, 30), idioms 12 of 12 (Apache, 60).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** ["Cloning considered harmful" considered harmful](https://plg.uwaterloo.ca/~migod/papers/2008/emse08-ClonePatterns.pdf) (Kapser, Godfrey, EMSE 2008); [Lobsters comment](https://lobste.rs/c/rnuopl) (thev, 2020); [Finding duplicated code with CPD](https://docs.pmd-code.org/latest/pmd_userdocs_cpd.html) (PMD 7.27.0, 2026) · dossier: duplication T08-F05

### DU-10 — Fix exact local duplicates from linters only after ruling out a copy-paste slip
- **Rule:** Before fixing identical if/switch branches, all-identical branches or identical function bodies, use `git blame` and the requirement to confirm that no copy was meant to differ; if one was, it is a DU-04 defect. Merge identical branches with a logical OR only when the conditions are side-effect-free, and replace an identical function with delegation that keeps public or exported names.
- **Detect:** JS/TS: sonarjs S1871 `no-duplicated-branches`, S3923 `no-all-duplicated-branches`, S4144 `no-identical-functions` (all in `recommended`; S4144 flags from 3 lines). Python: Ruff SIM114 `if-with-same-arms` (fix "sometimes available"). For each hit, blame both branches and read the guarding condition.
- **Not when:** Enum-driven switches whose branches name distinct business cases expected to diverge; keep them, and leave any suppression to the owner. No empirical source shows these rules are high-precision or their fixes mechanically safe, so they are not auto-applied. Equivalents in other analyzers were not verified.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [eslint-plugin-sonarjs README and source](https://www.npmjs.com/package/eslint-plugin-sonarjs) (SonarSource, 4.2.1, 2026); [Ruff SIM114](https://docs.astral.sh/ruff/rules/if-with-same-arms/) (Astral, 0.16.8); [Do Code Clones Matter?](https://arxiv.org/pdf/1701.05472) (Juergens et al., ICSE 2009, by analogy) · dossier: duplication T08-F10

### DU-11 — Make every kept clone group findable
- **Rule:** For every `LEAVE+DOCUMENT` group, add a cross-reference comment in each copy naming its siblings and why they stay separate, and propose co-locating instances that live in different modules. Propose explicit detector suppression with a reason (`CPD-OFF`/`CPD-ON`, `jscpd:ignore-start`/`jscpd:ignore-end`) so the remaining report stays actionable; a new suppression goes through the change protocol's approval, never silently. Never keep a clone group that nobody can find.
- **Detect:** Check whether the instances share a module; `rg` for a sibling-reference comment such as "keep in sync with"; audit existing suppressions with `rg -n 'CPD-OFF|jscpd:ignore-start'`, each of which must carry a reason. PMD's CPD-OFF comments work in Java, C/C++, Dart, Go, Groovy, JavaScript, Kotlin, Lua, Matlab, Objective-C, PL/SQL, Python, Scala, Swift, C# and Apex.
- **Not when:** PMD advises using CPD "to help remove duplicates, not to help keep duplicates in sync", so apply this only to groups that fail the merge criteria of DU-03. Comments rot; a "keep in sync" note works only if people or agents read it.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [On the Relationship of Inconsistent Software Clones and Faults](https://arxiv.org/abs/1611.08005) (Wagner et al., SANER 2016); [Late Propagation in Near-Miss Clones](https://doi.org/10.14279/tuj.eceasst.63.913) (Mondal, Roy, Schneider, ECEASST 63, 2014); [Finding duplicated code with CPD](https://docs.pmd-code.org/latest/pmd_userdocs_cpd.html) (PMD 7.27.0, 2026); [jscpd engine docs](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md) (jscpd 5.3.2, 2026) · dossier: duplication T08-F15

### DU-12 — Wrong abstractions: never add a mode flag; report the inverse refactoring
- **Rule:** Never add a selector or boolean mode parameter to a shared function to absorb another caller, and refuse any dedupe that needs one. When an existing shared helper is steered by mode parameters or holds caller-specific branches, report it with the inverse refactoring as the proposed fix: inline it back into each caller, delete in each caller the paths it never takes, and re-extract only what is truly common.
- **Detect:** sonarjs S2301 `no-selector-parameter` (typed linting); Ruff FBT001/FBT002. Manually list shared helpers with more than 3 callers and count branches that test a parameter; the signal is a parameter named like `mode|kind|type|variant|isX|withX` used only in conditionals. In the helper's `git log -p`, each added parameter or branch tied to one caller's ticket confirms the pattern.
- **Not when:** A boolean parameter is not always a wrong abstraction, and Metz allows that "it occasionally makes sense to accumulate a few conditionals to gain insight". No validated metric for a wrong abstraction exists. Practitioners disagree on which direction is riskier (lokar: "Changing abstraction is still high risk"; bazoom42: consolidating drifted duplicates is "pretty difficult and error prone"; dofm: "any stable abstraction is better than duplicated code"). Unresolved: report, do not auto-fix.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** C
- **Source:** [The Wrong Abstraction](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction) (Metz, 2016); [Goodbye, Clean Code](https://overreacted.io/goodbye-clean-code/) (Abramov, 2020); [Ruff FBT001](https://docs.astral.sh/ruff/rules/boolean-type-hint-positional-argument/) (Astral, 0.16.8); [eslint-plugin-sonarjs S2301](https://www.npmjs.com/package/eslint-plugin-sonarjs) (SonarSource, 2026); [AHA Programming](https://kentcdodds.com/blog/aha-programming) (Dodds, 2020); [HN lokar](https://news.ycombinator.com/item?id=48620711) (2026); [HN bazoom42](https://news.ycombinator.com/item?id=48620440) (2026); [HN dofm](https://news.ycombinator.com/item?id=48620517) (2026) · dossier: duplication T08-F06, T08-F07

### DU-13 — Leave clones across ownership or deployment boundaries
- **Rule:** Do not merge clones living in separately deployed, versioned or owned components (microservices, independently published packages, per-platform or per-vendor adapters, plugins) into a new shared library. Report a merge only when the copies must change in lockstep (same knowledge and same lifecycle); contract or schema knowledge for one business entity should still have a single source such as a generated client, which is a design decision for the owner. Keep copied code small and record its origin.
- **Detect:** jscpd `--skip-local` (skips clones whose fragments share a directory) lists cross-boundary clones; `--skip-isolated` excludes independently owned areas. Map each path to deploy unit and owner via CODEOWNERS, per-package manifests and Dockerfiles; if they differ, default to `LEAVE+DOCUMENT` unless co-change (DU-07) shows lockstep edits.
- **Not when:** The Go proverb and Russ Cox concern third-party dependencies, so applying them to internal libraries is an extrapolation. Against copying: "It's (almost) never correct to have duplicate code for the same object" when a DTO represents one business entity (SE.SE, 2016), and duplicated flows ending in "massive production dataloss" (HN hedora, 2026).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** C
- **Source:** [Go Proverbs](https://go-proverbs.github.io/) (Pike, 2015); [Our Software Dependency Problem](https://research.swtch.com/deps) (Cox, 2019); [Is DRY the enemy of software project management?](https://softwareengineering.stackexchange.com/questions/328512/is-dry-the-enemy-of-software-project-management) (Doc Brown, SE.SE, 2016); [Sharing DTO objects between microservices](https://softwareengineering.stackexchange.com/questions/337010/sharing-dto-objects-between-microservices) (SE.SE, 2016); [HN hedora](https://news.ycombinator.com/item?id=48620598) (2026); [HN ted_dunning](https://news.ycombinator.com/item?id=48621634) (2026); ["Cloning considered harmful" considered harmful](https://plg.uwaterloo.ca/~migod/papers/2008/emse08-ClonePatterns.pdf) (Kapser, Godfrey, EMSE 2008) · dossier: duplication T08-F14

### DU-14 — Tests: DAMP over DRY; consolidate only true test clones, and only by the owner
- **Rule:** Do not propose moving test-specific data or assertions into shared setUp, loops or helpers that hide what is tested; builders and factories for value objects are fine. Propose turning Type-2 test clones that differ only in inputs and expected outputs into parameterised or table-driven tests, and deleting a whole redundant test file only with evidence that coverage and the set of asserted behaviours are unchanged. Report these for the owner; existing tests are read-only during the pass. A clone group confined to test files, with an instance in a test file the pass added (characterization and demonstrating tests legitimately repeat setup), is a nit: report it, and never revert or rework an item over it (eval-v2-calibration E02-F07).
- **Detect:** Run the detector on test directories separately and report those groups apart from production figures; do not rely on detector recall in tests. `git diff --diff-filter=A --name-only <base_sha>..HEAD` lists the test files the pass added. Flag test files with suffixes such as `_final`, `_v2` or `_100_percent`. JS/TS: sonarjs S9078 `no-duplicate-parameterized-test-case` and S8754 `no-duplicate-test-title` (both in `recommended` in 4.2.1). Attach test counts, assertions and coverage (`pytest --collect-only -q`, `vitest list`, `go tool cover`) as the evidence the owner needs.
- **Not when:** DAMP is not a licence for whole duplicated test files: large copy-pasted suites, common in generated tests, do need consolidation, by the owner. Fowler warns that adding duplication for clarity "is often papering over a problem".
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [Tests Too DRY? Make Them DAMP!](https://testing.googleblog.com/2019/12/testing-on-toilet-tests-too-dry-make.html) (Snyder, Kuefler, Google, 2019); [Beck Design Rules](https://martinfowler.com/bliki/BeckDesignRules.html) (Fowler, 2015); [A Comparative Study of Test Code Clones and Production Code Clones](https://figshare.com/articles/preprint/A_Comparative_Study_of_Test_Code_Clones_and_Production_Code_Clones/14134901) (van Bladel, Demeyer, JSS 2021); [BytePort issue #383](https://github.com/KooshaPari/BytePort/issues/383) (2026) · dossier: duplication T08-F09; eval-v2-calibration E02-F07

### DU-15 — Leave declarative and tabular repetition unless a value is repeated knowledge
- **Rule:** Leave repetition in route tables, configuration, CSS and style rules, templates, schema or fixture data and explicit lists of cases; it is usually the readable specification. Only a value (URL, limit, key) repeated across entries is knowledge to centralise (DU-08), and these formats stay out of duplication percentages. When copy-pasted config or IaC blocks differ (for example a security setting changed for one environment only), report the drift as a DU-04 candidate; never edit config or IaC.
- **Detect:** Scope scans to programming-language formats (jscpd `--format`). jscpd's health score already ignores duplicated markup, stylesheet and template blocks, and SonarQube does not detect duplication in Terraform-like IaC or CSS. For flagged declarative files decide structure (leave) or repeated value (extract); `rg` repeated literal values across config files; diff repeated per-environment blocks.
- **Not when:** The jscpd and Sonar exclusions are vendor design choices, not findings. Copy-pasted IaC and config blocks do drift, so never skip the diff.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** C
- **Source:** [jscpd engine docs, Health score](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md) (jscpd 5.3.2, 2026); [Understanding measures and metrics](https://docs.sonarsource.com/sonarqube-server/2025.4/user-guide/code-metrics/metrics-definition) (SonarSource, 2025.4); ["Cloning considered harmful" considered harmful](https://plg.uwaterloo.ca/~migod/papers/2008/emse08-ClonePatterns.pdf) (Kapser, Godfrey, EMSE 2008); [HN Tade0](https://news.ycombinator.com/item?id=22023242), [HN wizzzzzy](https://news.ycombinator.com/item?id=22023128), [HN nathell](https://news.ycombinator.com/item?id=22023088) (2020) · dossier: duplication T08-F17

### DU-16 — Recommend a gate on new duplication only
- **Rule:** When the project has no duplication gate, recommend one that fails only on new clones against a recorded baseline, and route legacy clones through triage (DU-03) instead. Do not add the gate or its baseline file yourself: CI changes are reported for the owner. The pass holds its own items to the same new-clones-only standard (eval-v2-calibration E02-F07; protocol-change step 8, PC-02): before each item's commit, not only at batch end, the orchestrator re-runs the duplication detector with the detection step's pinned version, flags and threshold over the scope Phase 2 scanned, so that a copy of untouched code is caught, compares the output with the baseline and keeps the new groups that have an instance in a file the item changes. A new clone the item's added lines introduced in production code is fixed before staging, by calling the code it copies (DU-17); a group formed only because a fix brought existing copies closer (DU-04) becomes a new DU-03 candidate (PC-12), never an in-item merge. A new group confined to test files the item adds is a DU-14 nit.
- **Detect:** Check the CI config for a duplication gate. jscpd 5.3.2: record with `--baseline <file> --update-baseline`, gate with `--baseline <file> --fail-on-new-clones`, or stateless `--baseline-from-ref origin/main` (CI must fetch the ref first, e.g. `fetch-depth: 0`). SonarQube: the "Sonar way" gate allows at most 3.0% duplication on new code and ignores it until at least 20 new lines; confirm the `new_duplicated_lines_density` condition is present. Per item: the output is saved as `.harden/tools/<detector>.<id>-a<n>.*` (protocol-change step 8); for jscpd, `python "${CLAUDE_SKILL_DIR}/scripts/sarif_delta.py" .harden/tools/jscpd.baseline.sarif .harden/tools/jscpd.<id>-a<n>.sarif` lists the new results, and `git diff --name-only HEAD` gives the files the item changes.
- **Not when:** 3% is a vendor default, not an empirically derived limit; percentage gates can be gamed and penalise legitimate boilerplate. Some remaining duplication needs a design decision, not a mechanical dedupe (a forked models package in BytePort #383, 2026).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Understanding quality gates](https://docs.sonarsource.com/sonarqube-server/2026.1/quality-standards-administration/managing-quality-gates/introduction-to-quality-gates) (SonarSource, 2026.1); [jscpd README](https://github.com/kucherenko/jscpd) and [engine docs, Baseline](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md) (jscpd 5.3.2, 2026); [CWE-1041](https://cwe.mitre.org/data/definitions/1041.html) (MITRE, CWE 4.20); [BytePort issue #383](https://github.com/KooshaPari/BytePort/issues/383) (2026) · dossier: duplication T08-F12, practitioner voice; eval-v2-calibration E02-F07

### DU-17 — Assistant-built code: hunt re-implemented helpers and missed siblings; measure, do not assume
- **Rule:** In codebases built with assistants or agents, search for same-purpose helpers re-implemented across modules (date and number formatters, validators, retry and backoff wrappers, API clients, error mappers, config loaders) and send those that encode the same knowledge through DU-03. Merges across modules are T2 per PC-17 (report with a plan); T1 applies only to copies within one module. After any later fix to one copy, verify that every copy was updated; a missed sibling is a DU-04 candidate. Treat "AI code is more duplicated" as unproven for any given repository and measure it.
- **Detect:** jscpd `--ignore-identifiers --max-gap-lines 2 --min-tokens 40 --reporters ai` (JS/TS add `--similarity 0.85`); `rg` for same-purpose names, e.g. `function (format|parse)(Date|Currency|Number)` or `def (retry|with_retry|backoff)`, then compare bodies; ast-grep for structural matches. Consolidate only helpers that implement the same rule.
- **Not when:** Every source attributes code to AI by proxy (adoption timing, tool-mention comments, detector output). GitClear's own multipliers disagree with each other and with its table; Mao et al. (arXiv 2026, jscpd) found human-written code more duplicated (27.57% vs 14.29% duplicated lines); Chen & Jiang (arXiv 2024, 4,892 SWE-Bench Verified patches from 10 agents) found many agents reduced duplication.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** C
- **Source:** [AI Copilot Code Quality: 2025](https://gitclear-public.s3.us-west-2.amazonaws.com/GitClear-AI-Copilot-Code-Quality-2025.pdf) (GitClear, 2025); [The Maintainability Gap](https://www.gitclear.com/the_ai_code_quality_maintainability_gap) (GitClear, 2026); [A Large-Scale Comprehensive Measurement of AI-Generated Code](https://arxiv.org/html/2603.27130v3) (Mao et al., 2026); [An Exploratory Study on LLM-Generated Code and Comments](https://arxiv.org/abs/2607.01867) (Ji et al., 2026); [Evaluating Software Development Agents](https://arxiv.org/abs/2410.12468) (Chen, Jiang, 2024); [HN chuckadams](https://news.ycombinator.com/item?id=48620893) (2026); [HN ctoth](https://news.ycombinator.com/item?id=39178716) (2024) · dossier: duplication T08-F16

## False-positive exclusions

- Generated, vendored, build output, minified, lockfile, data, markup, template, stylesheet and IaC files (DU-01, DU-15); fixture data (DU-03).
- An inconsistency with no evidence that it is unintended: most inconsistencies are deliberate (DU-04).
- Coincidental look-alikes: same text, different requirement, owner or ticket (DU-08).
- Platform-variation, boiler-plate and deliberately repeated cross-cutting clones (DU-09); parameterized clones whose names mirror documented mathematical notation.
- Enum-driven switch branches that name distinct business cases (DU-10).
- Clones across deploy units or owners without lockstep co-change (DU-13).
- Test repetition that keeps each test readable on its own (DU-14).
- Young two-instance clones that are still diverging (DU-07).
- Co-change produced by squash merges, formatting sweeps or renames: not evidence of shared knowledge.
- A lower global duplication percentage: never a finding (DU-02).
- A jscpd per-format row far above the others: suspect counted non-code text before believing it (DU-01).
- An existing suppression marker that carries a reason: respect it (DU-11).

## Evidence limits

- Clone-fault evidence is mostly Java, C, C# and COBOL from 2005–2018; little covers TypeScript, Python, Rust, Go or agent-maintained repositories. Say so when a finding rests on it.
- Juergens et al. (ICSE 2009; 3 C#, 1 COBOL, 1 Java system): 52% of clone groups inconsistent, 28% of those unintentional; about every second to third unintentional change led to a fault; at least 3–23% of inconsistent groups faulty; 107 faults confirmed. The authors call their fault-density comparison "not perfect".
- Wagner et al. (SANER 2016; three automotive Java systems, 253–454 KLOC): 17% of Type-3 groups had faults (3–33%). Juergens (about 0.15) and Wagner (0.17) agree numerically; only their interpretations differ.
- Mondal et al. (ICSME 2017; four Java systems; abstract only): up to 33% of bug-fixed clone fragments carried propagated bugs, mainly near-miss clones created in the same commit.
- Kim et al. (ESEC/FSE 2005; two Java projects): 36–38% of genealogies changed consistently; 48–72% of disappeared genealogies vanished within an average of eight check-ins.
- Stability conflicts: Rahman/Bird/Devanbu (four C projects, 2012) found clones not associated with most bugs; Mondal et al. (12 Java, C, C# systems, 2018, abstract only) found cloned code often more change-prone and trace the disagreement to tools, systems and setups. Act on triaged groups, not on the aggregate.
- Kapser & Godfrey (two C systems, authors' ratings, 2008): Apache 71% good and 14% harmful at 30 tokens, 42% good and 39% harmful at 60; Gnumeric 57% harmful at 30, 42% at 60. The "71% beneficial" figure holds only for Apache at 30 tokens.
- van Bladel & Demeyer (five OSS systems, 2021, abstract only): test code holds twice as many clones as production code, mostly Type-2 and Type-3, and detectors miss more of them.
- GitClear (vendor telemetry, AI inferred from adoption timing): the 2025 report gives 0.45% (2022), 1.80% (2023), 6.66% (2024) of commits with a duplicate block, while its headlines say "4x", "8-fold" and "approximately 10x"; the 2026 page reports block duplication up 81% from 2023. Never quote these as effects of AI in the target repository.
- Abstract-only sources: Mondal 2017 and 2018, Göde & Koschke, Harder & Göde, Tsantalis 2015, Bavota 2012, ReDeBug, VUDDY, van Bladel & Demeyer.
- Semantic (Type-4) clones are outside production detectors: jscpd, CPD and Sonar are token-based, and jscpd `--similarity` covers JS/TS only. Do not claim Type-4 coverage.
- Practitioner reports (HN 2026, grade C) say agents forget to update a duplicated pattern in another monorepo package ([chuckadams](https://news.ycombinator.com/item?id=48620893)) and that LLM refactorings reshape code toward the current task ([dan-robertson](https://news.ycombinator.com/item?id=48621889)); this is a reason to triage group by group and never mass-dedupe, not evidence of a rate.
- The per-item clone check (DU-16) and the nit status of clone groups in the pass's own new test files (DU-14) come from the skill's own v2 evaluation (eval-v2-calibration E02-F07: six revert/redo pairs across three runs after batch-end clone checks, grade C), not from an external study.
- Tool facts were checked on 2026-09-23 against jscpd 5.3.2, eslint-plugin-sonarjs 4.2.1, Ruff 0.16.8, pylint 4.0.9, PMD 7.27.0 and SonarQube Server 2025.4/2026.1 docs. Applies when those versions are in use; re-check flags and defaults otherwise.
