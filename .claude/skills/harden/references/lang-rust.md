## Tooling baseline

Prefer the project's configured tools and versions: the toolchain in `rust-toolchain.toml`, lint levels in `[lints]`/`[workspace.lints]` and `clippy.toml`, `rustfmt.toml`, `deny.toml`, and the CI or xtask commands. Pass extra lint levels (`-W clippy::<lint>`, `-W <rustc_lint>`) on the command line for detection only; never edit the project's configuration. Stable when the evidence was checked: Rust and Clippy 1.98 (2026-08-20); edition 2024 since 1.85.

Version-pinning rule (general form in the detection reference, DT-05): install each tool the project does not declare at an exact version into a root under `.harden/tools/` (PF-21; the hook refuses any other root), record the version in `tool_versions`, and never install unpinned or `@latest`.

```
CARGO_HOME="$HARDEN_CARGO_HOME" cargo install --locked --root .harden/tools/cargo-mutants --target-dir "$HARDEN_CARGO_TARGET_ROOT/cargo-mutants" cargo-mutants@27.1.0              # verified 2026-09-23
CARGO_HOME="$HARDEN_CARGO_HOME" cargo install --locked --root .harden/tools/cargo-semver-checks --target-dir "$HARDEN_CARGO_TARGET_ROOT/cargo-semver-checks" cargo-semver-checks@0.50.0  # verified 2026-09-23
CARGO_HOME="$HARDEN_CARGO_HOME" cargo install --locked --root .harden/tools/cargo-fuzz --target-dir "$HARDEN_CARGO_TARGET_ROOT/cargo-fuzz" cargo-fuzz@0.13.2                    # nightly toolchain; prefer WSL2 (RS-30)
CARGO_HOME="$HARDEN_CARGO_HOME" cargo install --locked --root .harden/tools/<crate> --target-dir "$HARDEN_CARGO_TARGET_ROOT/<crate>" <crate>@<x.y.z>                         # cargo-deny, cargo-audit, cargo-shear, cargo-machete,
                                                                                            # cargo-udeps, cargo-hack, cargo-msrv, cargo-geiger, cargo-llvm-cov
```

Source `.harden/tool-env.sh` first: the variables keep Cargo's registry cache and the temporary build directory inside the run's scratch_dir (protocol-preflight PF-21; eval-v3-calibration E03-F06).

Run each cargo subcommand with `.harden/tools/<crate>/bin` first on `PATH` for that command only. Nightly-only: `cargo +nightly miri test`, `cargo +nightly udeps`, `cargo fuzz`, `cargo shear --expand`; record the nightly version. rust-analyzer: the standalone release of 2026-09-21 (`rust-analyzer-x86_64-pc-windows-msvc.zip` on Windows) or `rustup component add rust-analyzer`.

### RS-01 — Run the project's own toolchain and lint policy first
- **Rule:** Before adding any tool, run what the project declares, on the toolchain `rust-toolchain.toml` pins and with Clippy from that same toolchain: its CI commands, then `cargo clippy --workspace --all-targets --all-features -- -D warnings` as the baseline. Keep the default Clippy groups as the gate; run `clippy::pedantic` only as a triage report and adopt its lints one by one; never enable `clippy::restriction` or `clippy::nursery` as a group. Record warning counts: expect about 21 Clippy warnings per KLOC on a first run (real-world Rust crates, preprint 2023), so triage instead of suppressing.
- **Detect:** `rustup show`; `grep -n '\[lints\]\|\[workspace.lints\]\|workspace = true' Cargo.toml */Cargo.toml`; Clippy `lint_groups_priority` (a group without `priority` overrides lints in undefined order); `grep -rnE '#!\[deny\((warnings|clippy::all)\)\]' --include=*.rs`; pedantic triage `cargo clippy --all-targets -- -W clippy::pedantic 2>&1 | grep -oE 'clippy::[a-z_]+' | sort | uniq -c | sort -rn`.
- **Not when:** Moving an in-source `#![deny(warnings)]` to CI `-D warnings` is a config change to report, not apply; a private binary on a pinned toolchain suffers little from it, and the Design Patterns book's replacement deny list contains removed lints (`const_err`, `private_in_public`). Microsoft enables all of pedantic at warn; when the project does too, follow it.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Clippy: Continuous Integration](https://doc.rust-lang.org/clippy/continuous_integration/index.html) (rust-lang, 2026); [Cargo Book: the `[lints]` section](https://doc.rust-lang.org/cargo/reference/manifest.html) (Rust Project, 2026); [Clippy lint groups](https://doc.rust-lang.org/clippy/) (rust-lang, 2026); [`#![deny(warnings)]` anti-pattern](https://rust-unofficial.github.io/patterns/anti_patterns/deny-warnings.html) (rust-unofficial); [Unleashing the Power of Clippy](https://arxiv.org/abs/2310.11738) (Li et al., 2023); [HN: pedantic as a unit](https://news.ycombinator.com/item?id=49657693) (J. ### RS-02 — Install extra cargo tools pinned, locked and outside the project
- **Rule:** Install every tool the project does not declare with `cargo install --locked --root .harden/tools/<crate> <crate>@<x.y.z>`, with the `.harden/tool-env.sh` prefix and its `CARGO_HOME` and `--target-dir` (PF-21), and never add it to `Cargo.toml`, `[dev-dependencies]` or CI. Versions verified on 2026-09-23: cargo-mutants 27.1.0 (2026-06-02), cargo-semver-checks 0.50.0 (2026-08-01), cargo-fuzz 0.13.2 (2026-06-09), rust-analyzer release 2026-09-21. For every other tool, resolve the current release at run time and record it.
- **Detect:** Compare `tool_versions` with each binary's `--version`; flag an unpinned install, a missing `--locked`, or any tool added to the project's manifests.
- **Not when:** A tool the project already pins (CI, `.cargo/config.toml`, an xtask) runs at the project's version. Without `--locked`, `cargo install` selects the latest dependencies instead of the tool's lockfile (Cargo FAQ).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A

### RS-03 — Read MSRV and edition before proposing any modernisation
- **Rule:** Read `rust-version`, `edition` and `resolver` in every member manifest, and never propose a change that needs a newer compiler than the declared `rust-version` or the pinned toolchain: `#[expect]` needs 1.81, `LazyLock` 1.80, `OnceLock` 1.70, edition 2024 1.85, `package.resolver = "3"` 1.84. Raising `rust-version` or `edition` is a report item. Clippy's `msrv` defaults to `rust-version` and gates 76 lints, so a `clippy.toml` `msrv` that disagrees is a finding.
- **Detect:** `grep -nE '^rust-version|^edition|resolver' Cargo.toml */Cargo.toml`; verify a declared MSRV with `cargo hack check --rust-version --workspace --all-targets` (or `cargo +<msrv> check --locked`); `cargo msrv find` when none is declared; compare `clippy.toml` `msrv`.
- **Not when:** An application with a "latest stable" policy plus `rust-toolchain.toml` needs no separate MSRV. A declared but unverified `rust-version` misleads the resolver and users: report it rather than trust it.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Cargo Book: rust-version](https://doc.rust-lang.org/cargo/reference/rust-version.html) (Rust Project, 2026); [Announcing Rust 1.84.0](https://blog.rust-lang.org/2025/01/09/Rust-1.84.0/) (Rust Release Team, 2025); [Announcing Rust 1.80.0](https://blog.rust-lang.org/2024/07/25/Rust-1.80.0/) (Rust Release Team, 2024); [Clippy lint configuration](https://doc.rust-lang.org/clippy/lint_configuration.html) (rust-lang, 2026); [cargo-hack](https://github.com/taiki-e/cargo-hack) (taiki-e, 2026) · dossier: lang-rust T22-F14, T22-F12

### RS-04 — Judge every Rust finding across the configurations that ship
- **Rule:** Before calling code dead, a fix complete or a gate green, list the configurations that ship (feature sets, `cfg(target_os)` branches and `--target`s) and run the check in each: `cargo check`, `cargo clippy`, `cargo fix` and rust-analyzer each see one configuration per run, and cfg'd-out code is never compiled. Act only on what every configuration agrees on.
- **Detect:** `grep -rn '#\[cfg(' src/ | grep -oE 'feature = "[^"]+"|target_os = "[^"]+"' | sort -u`; `cargo hack check --workspace --all-targets --each-feature` (or `--feature-powerset`); `cargo check --target <t>` per target; gates run with `--all-targets --all-features` at minimum.
- **Not when:** A single-target application with no features ships one configuration; confirm that before skipping the matrix. Running every configuration is expensive; `--each-feature` is the cheaper first pass.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Edition Guide: Advanced migrations](https://doc.rust-lang.org/edition-guide/editions/advanced-migrations.html) (Rust Project, 2026); [cargo-hack](https://github.com/taiki-e/cargo-hack) (taiki-e, 2026); [cargo-udeps](https://github.com/est31/cargo-udeps) (est31, 2026) · dossier: lang-rust T22-F11, T22-F23; dead-code-tools T07-F09; agent-refactoring-engines G105-F06

## Autofix safety

### RS-05 — Run rustfmt only where the project enforces it, on the item's files, in a `style:` commit
- **Rule:** Format only when the project enforces rustfmt (a `cargo fmt --check` step in CI or hooks; a `rustfmt.toml` alone shows use, not enforcement), only the files the item touches, in a `style:` commit placed immediately before the item's semantic commit. Use `cargo fmt`, not bare `rustfmt`: editors that call `rustfmt` directly default to the 2015 style edition, while `cargo fmt` takes the edition from `Cargo.toml`. `cargo fmt --all` formats the whole workspace, and no source here shows `cargo fmt` limited to single files with the crate's edition, so the run is T0 only when every file it would change is one the item touches. Otherwise a whole-repo `cargo fmt --all` is a T1 item that needs its own explicit approval (PC-11): run it only after that approval, as its own `style:` commit.
- **Detect:** `cargo fmt --all -- --check` (non-zero means unformatted) before the item; run `cargo fmt --all` from a clean tree, and before committing check that `git diff --name-only` lists only the item's files, otherwise `git restore` the changed files and treat the run as the T1 whole-repo item; `ls rustfmt.toml .rustfmt.toml` and compare `style_edition` with the crate edition; `git diff --stat` against `git diff -w --stat` to separate format noise from semantic change.
- **Not when:** No enforced formatter: report instead (ANSSI's rustfmt rule is a "should"). Never add a `rustfmt.toml`, change `style_edition` or turn on nightly-only options. A whole-repo reformat pollutes blame and conflicts with open branches; propose a `.git-blame-ignore-revs` entry for it.
- **Tier:** T0 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [The Rust Style Guide](https://doc.rust-lang.org/style-guide/index.html) (Rust style team); [Edition Guide: rustfmt style edition](https://doc.rust-lang.org/edition-guide/rust-2024/rustfmt-style-edition.html) (Rust Project, 2025); [Secure Rust Guidelines: devenv](https://anssi-fr.github.io/rust-guide/devenv.html) (ANSSI, undated); [HN: formatter after each codemod step](https://news.ycombinator.com/item?id=40694419) (2024) · dossier: lang-rust T22-F19; agent-refactoring-engines G105-F14; autofix-trust G105-F08; eval-v1-calibration E01-F02

### RS-06 — Apply Clippy fixes one lint per commit from a clean tree, reviewed
- **Rule:** Never run `cargo clippy --fix` or `cargo fix` across all lints. From a clean tree, without `--allow-dirty` or `--allow-no-vcs`, fix one lint id per commit, review the diff, run the full tests with all features, then commit (ANSSI DENV-AUTOFIX requires every automatic fix to be verified by the developer). `--fix` implies `--all-targets`, so it also rewrites tests, benches and examples: drop hunks in protected test files or skip that lint. Keep `avoid-breaking-exported-api` at its default (true), and never apply API-shaping pedantic fixes (`must_use_candidate`, the cast lints) through `--fix`.
- **Detect:** `git status --porcelain` prints nothing; `cargo clippy --fix -- -W clippy::<one_lint>`, then `git diff --stat` (every hunk must belong to that lint) and `cargo test --workspace --all-features`; repeat per configuration (RS-04), because a fix run sees one.
- **Not when:** The Rust dossier lets style-only lints (for example `uninlined_format_args`) share one commit; this pass still commits one lint id at a time, so a regression bisects to a single lint (PC-09). One practitioner reports `cargo clippy --fix` resolving about 90% of issues when rebuilding older projects on newer toolchains; that is toolchain drift, not lint debt, and one person's report.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [Secure Rust Guidelines: DENV-AUTOFIX](https://anssi-fr.github.io/rust-guide/devenv.html) (ANSSI, undated); [Clippy: Usage](https://doc.rust-lang.org/clippy/usage.html) (rust-lang, 2026); [Clippy lint configuration](https://doc.rust-lang.org/clippy/lint_configuration.html) (rust-lang, 2026); [HN comment](https://news.ycombinator.com/item?id=41220852) (mmastrac, 2024); [Sorald](https://arxiv.org/abs/2103.12033) (Etemadi et al., 2022) · dossier: lang-rust T22-F23, T22-F02, T22-F20; autofix-trust G105-F07

### RS-07 — Audit lint suppressions; convert to `#[expect]` with a reason; never add new ones
- **Rule:** Inventory every `#[allow]`/`#![allow]`, crate-level ones and `dead_code`, `unused`, `clippy::all` and `clippy::pedantic` first. With MSRV 1.81 or later, converting `#[allow(lint)]` to `#[expect(lint, reason = "...")]` is structural; then delete each one the build reports as `unfulfilled_lint_expectations`, once every configuration (RS-04) agrees. Never add an `#[allow]` or `#[expect]` to silence a new warning: fix the cause or report it.
- **Detect:** `grep -rnE '#!?\[allow\(' --include=*.rs | sort | uniq -c`; `cargo clippy -- -W clippy::allow_attributes_without_reason -W clippy::allow_attributes`; `unfulfilled_lint_expectations` warnings after the conversion; the pass's own diff for new suppressions.
- **Not when:** Code compiled only under some cfg or features can fulfil an `#[expect]` in one configuration and not another: keep `#[allow]` or use `cfg_attr`. Generated code (bindgen, prost) legitimately carries a blanket allow at its module boundary. Below MSRV 1.81 keep `#[allow]`. One developer reports an AI agent adding `allow(dead_code)` despite instructions forbidding it (single anecdote, 2026).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [Announcing Rust 1.81.0](https://blog.rust-lang.org/2024/09/05/Rust-1.81.0/) (Rust Release Team, 2024); [Clippy source: attrs](https://raw.githubusercontent.com/rust-lang/rust-clippy/master/clippy_lints/src/attrs/mod.rs) (rust-lang, 2026); [Pragmatic Rust Guidelines: M-LINT-OVERRIDE-EXPECT](https://microsoft.github.io/rust-guidelines/guidelines/universal/) (Microsoft, 2026); [HN comment](https://news.ycombinator.com/item?id=48421662) (duttish, 2026) · dossier: lang-rust T22-F03; dead-code-tools T07-F20

### RS-08 — Report an edition migration; never run it blind
- **Rule:** Moving to edition 2024 changes semantics: `if let` temporaries drop before the `else` branch (this fixes a classic RwLock deadlock but changes lock hold times), references to `static mut` are denied as instantaneous undefined behaviour, `env::set_var` and `remove_var` become unsafe, and `unsafe_op_in_unsafe_fn` warns by default. Report the migration with its measured diff; do not apply it in this pass.
- **Detect:** `grep -n '^edition' Cargo.toml */Cargo.toml`; in a scratch worktree only, `cargo fix --edition --all-features --all-targets` (repeat with `--target` for platform cfg code), then count `grep -rn 'TODO: Audit that the environment access' src/`, `git diff | grep -nE '^\+\s*match '` (the `if_let_rescope` rewrites) and `grep -rnE 'static mut ' src/`.
- **Not when:** The bump raises MSRV to 1.85 (RS-03). The migration does not update doctests, and build-time code generation or macros may need manual work. Simplifying its conservative `match` rewrites adopts the new drop order.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Edition Guide: if let temporary scope](https://doc.rust-lang.org/edition-guide/rust-2024/temporary-if-let-scope.html) (Rust Project, 2025); [static mut references](https://doc.rust-lang.org/edition-guide/rust-2024/static-mut-references.html) (Rust Project, 2025); [Newly unsafe functions](https://doc.rust-lang.org/edition-guide/rust-2024/newly-unsafe-functions.html) (Rust Project, 2025); [Transitioning an existing project](https://doc.rust-lang.org/edition-guide/editions/transitioning-an-existing-project-to-a-new-edition.html) (Rust Project, 2025) · dossier: lang-rust T22-F15

## Refactoring engines

### RS-09 — Route rename, module move, extract and inline through rust-analyzer
- **Rule:** The LLM chooses the operation and its parameters; rust-analyzer produces the edit: `textDocument/rename` (after `prepareRename`), `workspace/willRenameFiles` for module moves, and codeAction plus resolve for `refactor.extract`, `refactor.inline` and `refactor.rewrite`. Wait for indexing to end (`$/progress`) before a rename; select code actions by exact kind and exact title with exact ranges; reject a null, empty or unexpectedly broad WorkspaceEdit, and any rename whose files do not cover every file `textDocument/references` returned. Log tool version, request and returned edit for each commit; an LLM-authored multi-file rename is not allowed.
- **Detect:** `initialize` capabilities (`renameProvider`, `codeActionProvider.codeActionKinds`, `workspace.fileOperations.willRename`); a diff that renames an identifier in more than one file with no engine log in the transcript.
- **Not when:** Claude Code's LSP tool offers diagnostics and navigation only, with no rename or code actions: drive rust-analyzer through a stdio LSP client or a bridge whose `tools/list` shows rename. The rustup proxy fails unless the component is installed. No LSP start-up time was measured, and memory use on large projects is high. On Git Bash pass repo-relative or long-form paths (`cygpath -m -l`), never `/c/...` or 8.3 short names, and check `git ls-files --eol` for `w/mixed` after edits (single-machine observations).
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [rust-analyzer manual: Features](https://rust-analyzer.github.io/book/features.html) (rust-analyzer, 2026); [Claude Code tools reference](https://code.claude.com/docs/en/tools-reference) (Anthropic, 2026); [RefactoringMirror](https://arxiv.org/abs/2411.04444) (Liu et al., 2025); [cygpath](https://cygwin.com/cygwin-ug-net/cygpath.html) (Cygwin, 2026) · dossier: agent-refactoring-engines G105-F06, G105-F01, G105-F10, G105-F11, G105-F15, G105-F12

### RS-10 — After every engine operation, check macro bodies, all targets and features, the name census and the tests
- **Rule:** Treat an engine edit as a proposal. In one fixture run, rust-analyzer rename and module rename skipped a path inside a `macro_rules!` body (E0425, E0433), a limitation its manual does not document. After each operation: grep macro bodies for the old name, run `cargo check --all-targets --all-features` plus the RS-04 configurations, diff a before/after census of the old name across code, strings, `serde(rename` attributes, config and docs, justify every surviving hit, then run the tests. A clean compile is not proof: 66 of 518 catalogued engine bugs (12.7%) were behaviour changes (Eclipse, IntelliJ, NetBeans; 2024 preprint).
- **Detect:** `rg -n -U 'macro_rules!' -A40 | rg -w OLD`; `rg -n -w -F OLD --hidden -g '!target' -g '!.git' > before.txt`, repeated after the edit and diffed; `rg -n 'macro_rules!|serde[(]rename'`.
- **Not when:** The macro miss is one observation on one fixture. In code without macros, serde or string lookups the census adds noise; keep it as a review list, never an automatic fix.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [rust-analyzer manual: Features](https://rust-analyzer.github.io/book/features.html) (rust-analyzer, 2026); [An Empirical Study of Refactoring Engine Bugs](https://arxiv.org/html/2409.14610v1) (Wang et al., 2024) · dossier: agent-refactoring-engines G105-F06, G105-F02, G105-F05

### RS-11 — Use SSR only for pattern migrations; use the fallback protocol where no engine exists
- **Rule:** Use `rust-analyzer ssr '<search> ==>> <replace>'` only to migrate call patterns (a deprecated API to its replacement), after a dry run with `rust-analyzer search '<pattern>'`; in one run it rewrote call sites but not the definition or a macro body, so it is neither a rename nor a change-signature engine. Rust has no change-signature engine: for signature changes and macro-body fixes use the fallback protocol, one refactoring per commit: census, moved-block diff, API-surface diff, `cargo check`, tests.
- **Detect:** `git diff --color-moved=zebra --color-moved-ws=allow-indentation-change` (plain mode cannot show whether a block moved unchanged; moves under 20 alphanumeric characters show as adds and deletes); `cargo semver-checks` for library crates; `rg -n -w NEW` for accidental captures.
- **Not when:** rust-analyzer CLI subcommands carry no stability guarantee: pin the release (RS-02). A cold `rust-analyzer ssr` run took about 47 s on a 2-file crate (one run, Windows, 2026). A public signature change is an API change (RS-14). The API-surface diff flags every intended public rename, so whitelist expected changes. No study evaluates this protocol.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** C
- **Source:** [rust-analyzer manual: SSR](https://rust-analyzer.github.io/book/features.html) (rust-analyzer, 2026); [rust-analyzer CLI flags](https://github.com/rust-lang/rust-analyzer/blob/master/crates/rust-analyzer/src/cli/flags.rs) (rust-analyzer, 2026); [git-diff --color-moved](https://git-scm.com/docs/git-diff) (Git project, 2026); [cargo-semver-checks](https://github.com/obi1kenobi/cargo-semver-checks) (P. Gruevski, 2026) · dossier: agent-refactoring-engines G105-F06, G105-F13, G105-F16

## Dead code and dependencies

### RS-12 — Remove unused imports and locals that rustc reports in every configuration
- **Rule:** Remove imports and local bindings that rustc's `unused_*` lints report identically in every configuration that ships (RS-04). Keep a local whose value acts when dropped (a lock guard, any RAII value): prefix it with `_` instead, and never turn it into `let _ = ...`, which drops the value at once. Import removal in `lib.rs` and `mod.rs` is T1, not T0: they are entry-point modules (PC-10).
- **Detect:** `cargo check --workspace --all-targets --all-features` plus the RS-04 runs, intersecting the unused-import and unused-variable warnings; for each binding, check the value's type for `Drop` or guard semantics (Clippy `let_underscore_lock`, rustc `let_underscore_drop`); route hits in files named `lib.rs` or `mod.rs` to T1.
- **Not when:** A warning that appears in only some configurations marks cfg-specific code: leave it. An unused parameter required by a trait or callback signature gets the `_` prefix, never removal.
- **Tier:** T0 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [rustc warn-by-default lints](https://doc.rust-lang.org/rustc/lints/listing/warn-by-default.html) (Rust Project, 2026); [rustc allowed-by-default lints](https://doc.rust-lang.org/rustc/lints/listing/allowed-by-default.html) (Rust Project, 2026); [Clippy source: let_underscore](https://raw.githubusercontent.com/rust-lang/rust-clippy/master/clippy_lints/src/let_underscore.rs) (rust-lang, 2026); [cargo-hack](https://github.com/taiki-e/cargo-hack) (taiki-e, 2026) · dossier: dead-code-tools T07-F07, T07-F09, T07-F20; lang-rust T22-F11, T22-F08; autofix-trust G105-F09

### RS-13 — Delete dead private items only after exposing stray `pub` and passing the registration vetoes
- **Rule:** `dead_code` covers only unexported items, so a stray `pub` hides dead code. In binaries and internal crates, run with `unreachable_pub`, demote each accidental `pub` to `pub(crate)`, then act on the `dead_code` warnings that appear, plus underscore-prefixed items, `allow(dead_code)` sites and files `cargo shear` reports as unlinked. Veto any item registered or exported outside normal calls: `#[no_mangle]`, `#[export_name]`, `#[used]`, `inventory::submit!`, `linkme`, FFI exports, proc-macro output, benches and examples. Never delete a never-read field kept for its drop behaviour or its auto-trait effect (Send, Sync); to keep tuple-struct numbering, change it to unit type or `PhantomData`.
- **Detect:** `cargo clippy --workspace --all-targets --all-features -- -W unreachable_pub`; `grep -rnE '#!?\[allow\((dead_code|unused)' src/`; `grep -rnE '\b(fn|struct|enum|const|static) _[a-z]' src/`; `cargo shear`; `grep -rnE 'no_mangle|export_name|#\[used\]|inventory::submit!|linkme' src/`; delete in small commits and re-run until the report stops shrinking.
- **Not when:** In a library, `pub` items are API (RS-14). A `dead_code` warning may mean the visibility is wrong rather than the code unneeded (Effective Rust). `unreachable_pub` is allow-by-default because it is noisy on existing code.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [rustc lints: dead_code](https://doc.rust-lang.org/rustc/lints/listing/warn-by-default.html) (Rust Project, 2026); [rustc lints: unreachable_pub](https://doc.rust-lang.org/rustc/lints/listing/allowed-by-default.html) (Rust Project, 2026); [cargo-shear](https://github.com/Boshen/cargo-shear) (Boshen, 2026); [Effective Rust, Item 22](https://effective-rust.com/visibility.html) (D. ### RS-14 — Treat a library's public API as behaviour: report, then prove with cargo-semver-checks
- **Rule:** In a crate other crates consume, do not remove or demote a `pub` item, change a public error type or its Display text, remove a public `Deref` impl, add `#[must_use]` or a `Send` bound to public items, remove duplicate re-export paths or change a public signature in this pass: report each one. Keep Clippy's `avoid-breaking-exported-api` at its default (true). After any change to such a crate, run `cargo semver-checks`: 172 of the top 1,000 crates.io crates (17.2%) shipped at least one semver-violating release, and 464 of 14,389 releases (3.22%) had one (2023 scan).
- **Detect:** Library or application: `[lib]` versus `[[bin]]` and reverse dependencies in the workspace; `cargo semver-checks --baseline-rev <base_sha>` (exit code 100 means deny-level violations); `grep -n 'avoid-breaking-exported-api' clippy.toml`; `grep -rn '^pub use' src/` against module paths; `cargo doc` output before and after.
- **Not when:** Binaries are exempt, and crates whose only consumers live in the same workspace can be analysed as a whole program. cargo-semver-checks cannot yet catch type, generic or lifetime changes, or changes limited to some feature combinations, so a clean run is not proof.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A

### RS-15 — Remove an unused crate only when two tools and a manual check agree
- **Rule:** Run `cargo shear` and `cargo machete` (optionally `cargo +nightly udeps --all-targets --all-features`) and treat only their intersection as candidates. For each, search the crate name (with `-` replaced by `_`) in `src/`, `build.rs`, `benches/`, `examples/` and macros, and check whether it exists only to enable features: Cargo unifies features across the graph, so removing it can change behaviour silently. Remove one crate per commit, rebuild every target and feature, run all tests. Record false positives in the findings, never as new `[package.metadata.cargo-*]` ignore entries. Replacing `lazy_static`/`once_cell` with std `LazyLock`/`OnceLock` follows this rule and needs MSRV 1.80/1.70 (RS-03).
- **Detect:** `cargo shear`, then `cargo shear --fix` only on a clean tree with the `Cargo.toml` diff reviewed; `cargo machete` (run `--with-metadata` only in a disposable git worktree of the run's repository, PF-21: it runs `cargo metadata --all-features` and may modify `Cargo.lock`); `cargo tree -e features -i <crate>`; `cargo clippy -- -W clippy::non_std_lazy_statics`.
- **Not when:** Crates used only by build scripts, macros or doctests (cargo-udeps cannot check doctest-only use), or kept for feature unification or version pinning. rustc's `unused_crate_dependencies` misfires when a dependency is used only by the binary. cargo-shear's README says cargo-udeps no longer works on current cargo; that is untested (udeps was still maintained in April 2026), so a failed udeps run is not evidence. A direct dependency that is also transitive stays in the tree after removal.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B

### RS-16 — Report supply-chain gaps: advisories, sources, lockfile, build scripts
- **Rule:** Run `cargo audit` and `cargo deny check` (with the project's `deny.toml`; without one, in a disposable git worktree of the run's repository after `cargo deny init`, PF-21) and report: advisories; unknown registries or git sources; wildcard and duplicate versions; an untracked `Cargo.lock` in an application; CI or install steps without `--locked`; every crate added or changed since `base_sha`, with its `build.rs` and proc-macro code reviewed. cargo-deny's `sources` and `wildcards` checks only warn by default, and its build-script checks do not protect against actively malicious code. Incidents: `faster_log` and `async_println` exfiltrated crypto private keys at run time (crates.io, Sept 2025; 7,181 and 1,243 downloads); `arrayref` 0.3.10, from an apparently compromised account, pulled in typosquatted `proc-macro1`, whose build script downloads and runs a binary (Aug 2026). Rank these first where the code holds keys.
- **Detect:** `cargo audit`; `cargo deny check`, with `unknown-registry = "deny"`, `unknown-git = "deny"` and `wildcards = "deny"` in that worktree's config; `git ls-files --error-unmatch Cargo.lock`; `cargo tree --duplicates`; `git diff <base_sha> -- Cargo.lock | grep '^+name'`.
- **Not when:** Whether a library commits `Cargo.lock` is disputed (ANSSI: must; Cargo FAQ: depends on the package; Effective Rust: libraries should not): follow the project and report. `Cargo.lock` does not protect library consumers. Advisory fixes change versions and the lockfile, so they go to the human as report items.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [cargo-deny: sources](https://embarkstudios.github.io/cargo-deny/checks/sources/cfg.html) and [bans](https://embarkstudios.github.io/cargo-deny/checks/bans/cfg.html) (Embark Studios); [cargo-audit](https://github.com/rustsec/rustsec/tree/main/cargo-audit) (RustSec); [Secure Rust Guidelines: devenv](https://anssi-fr.github.io/rust-guide/devenv.html) (ANSSI, undated); [Cargo FAQ](https://doc.rust-lang.org/cargo/faq.html) (Rust Project); [arrayref build-time payload](https://safedep.io/arrayref-proc-macro1-rust-build-time-malware/) (SafeDep, 2026); [Malicious crates faster_log and async_println](https://blog.rust-lang.org/2025/09/24/crates.io-malicious-crates-fasterlog-and-asyncprintln/) (crates.io team, 2025) · dossier: lang-rust T22-F13; eval-v1-calibration E01-F10

## Language traps

### RS-17 — Classify every production panic site; propagate failures that external or generated data can trigger
- **Rule:** Inventory panic sites and triage first those reachable from config loading, deserialisation, network handlers and anything behind a fixed capacity limit. Where external or generated input can trigger the failure, propose propagating a `Result`; keep documented invariant panics (a contract violation must panic, with a message). A panic-to-`Result` change is behavioural: own commit, a test that reaches the new error path, and `# Errors`/`# Panics` docs updated to match. Cloudflare's 18 Nov 2025 outage came from one `Result::unwrap()` on an internally generated feature file over a 200-feature limit (impact from 11:28 UTC, all systems back 17:06); its remediation treats generated config like user input.
- **Detect:** `cargo clippy --all-targets --message-format=short -- -W clippy::unwrap_used -W clippy::expect_used -W clippy::panic -W clippy::indexing_slicing -W clippy::unwrap_in_result`; filter test code during triage (the `allow-*-in-tests` keys default to false; do not edit `clippy.toml`); after a change, `-W clippy::missing_errors_doc -W clippy::missing_panics_doc` and `cargo test --doc`.
- **Not when:** Unwrap on a proven invariant is idiomatic, and `slice[i]` is an unwrap too (BurntSushi). Tests, `build.rs`, examples, const contexts, one-shot CLIs and a deliberate crash at server startup are exempt. A converted panic can let a process continue in a state that was impossible before. Classifying by external data is a synthesis, and no study shows restriction lints reduce incidents.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [Cloudflare outage on November 18, 2025](https://blog.cloudflare.com/18-november-2025-outage/) (Cloudflare, 2025); [Secure Rust Guidelines: errors](https://anssi-fr.github.io/rust-guide/errors.html) (ANSSI, undated); [Pragmatic Rust Guidelines: Correctness](https://microsoft.github.io/rust-guidelines/guidelines/correctness/index.html) (Microsoft, 2026); [Using unwrap() in Rust is Okay](https://burntsushi.net/unwrap/) (A. ### RS-18 — Make overflow and lossy casts explicit where values come from outside
- **Rule:** Release builds wrap on overflow without error (`overflow-checks` is off in the release profile by default), and the Rust Book calls relying on that wrap an error. For arithmetic on externally influenced values, sizes, indices, prices and token amounts, choose per documented intent between `checked_*` (propagate the error), `saturating_*` and explicit `wrapping_*`, and make lossy numeric conversions explicit (the Safety-Critical guidelines say `as` should not be used with numeric operands). Int-to-int `as` truncates silently; float-to-int `as` saturates since 1.45, which is defined but may be wrong. The choice changes behaviour: one commit per site family, with a boundary test.
- **Detect:** An audit report, never a gate: `cargo clippy --all-targets -- -W clippy::arithmetic_side_effects -W clippy::cast_possible_truncation -W clippy::cast_sign_loss -W clippy::cast_possible_wrap -W clippy::cast_lossless -W clippy::as_conversions`; `grep -rnE '\bas (u|i)(8|16|32|64|128|size)\b|\bas f(32|64)\b' src/`; `grep -nE 'overflow-checks|debug-assertions' Cargo.toml`, flagging `false` under `[profile.dev]` or `[profile.test]`.
- **Not when:** Hashes, PRNGs and checksums rely on wrap-around: make it explicit with `wrapping_*`, never "fix" it. `arithmetic_side_effects` fires on every `+`, so scope it to chosen modules. Turning on release `overflow-checks` is a profile change with a runtime cost: report it with a measurement. The money rules live in the numeric-money-time lens.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** high · **Grade:** A
- **Source:** [The Rust Programming Language, ch. 3.2](https://doc.rust-lang.org/book/ch03-02-data-types.html) (Rust Project); [Cargo Book: Profiles](https://doc.rust-lang.org/cargo/reference/profiles.html) (Rust Project); [Secure Rust Guidelines: integer operations](https://anssi-fr.github.io/rust-guide/integer.html) (ANSSI, undated); [Safety-Critical Rust Coding Guidelines 0.1](https://coding-guidelines.arewesafetycriticalyet.org/coding-guidelines/expressions/index.html) (Safety-Critical Rust Consortium, 2025); [Announcing Rust 1.45.0](https://blog.rust-lang.org/2020/07/16/Rust-1.45.0/) (Rust Release Team, 2020) · dossier: lang-rust T22-F06

### RS-19 — Review silently discarded results
- **Rule:** Review every `let _ = <expr>` and `.ok();` whose value is a `Result`, a `#[must_use]` type, a lock guard or a future: an unpolled future does no work, and `let _ =` on a guard releases the lock at once. Handling a previously ignored error adds a failure path, so it is behavioural. Adding `#[must_use]` to internal items where ignoring the value is almost certainly a bug is safe; on public items it is an API change (RS-14).
- **Detect:** `grep -rnE 'let _ = ' src/`; `grep -rnE '\.ok\(\);' src/`; `cargo clippy -- -W clippy::let_underscore_must_use -W clippy::let_underscore_untyped -W clippy::unused_result_ok -W let_underscore_drop` (the default run already covers `let_underscore_lock` and `let_underscore_future`); `-W clippy::must_use_candidate` as a report.
- **Not when:** Best-effort cleanup (sending on a closed channel, flushing logs at shutdown) is legitimately ignored: keep it, typed as `let _: Result<_, _> = ...` with a comment. `JoinHandle` is deliberately not `#[must_use]`, because fire-and-forget tasks are legitimate.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [std-dev-guide: When to add #[must_use]](https://std-dev-guide.rust-lang.org/policy/must-use.html) (Rust Library Team); [Clippy source: let_underscore](https://raw.githubusercontent.com/rust-lang/rust-clippy/master/clippy_lints/src/let_underscore.rs) (rust-lang, 2026); [rustc allowed-by-default lints](https://doc.rust-lang.org/rustc/lints/listing/allowed-by-default.html) (Rust Project, 2026) · dossier: lang-rust T22-F08

### RS-20 — Keep error causes; do not reshape error types in this pass
- **Rule:** Report `()` error types (`result_unit_err`), oversized errors (`result_large_err`), `map_err` calls that discard the original error (`map_err_ignore`), `anyhow::Error` or `Box<dyn Error>` in a library's public signatures, and several application-level error crates mixed in one application. In internal code, preserving a discarded cause in the error chain is a T1 behavioural fix; any public error type or Display text change goes to RS-14.
- **Detect:** `result_unit_err` and `result_large_err` run by default; `-W clippy::map_err_ignore`; `grep -rnE 'pub (async )?fn[^{]*anyhow::(Result|Error)' src/`; `grep -nE '^(anyhow|eyre|color-eyre|snafu|thiserror)' Cargo.toml`; a compile-time check `fn _assert<T: Send + Sync + 'static>() {}` with `_assert::<MyError>()`.
- **Not when:** Error shape is disputed (Microsoft recommends situation-specific structs with `is_xxx()` methods, thiserror practice uses enums, practitioners dispute the library/application split): unresolved, so report and do not restructure. Changed error text breaks callers, log parsers and tests.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [Rust API Guidelines: C-GOOD-ERR](https://rust-lang.github.io/api-guidelines/interoperability.html) (Rust Library Team); [thiserror README](https://github.com/dtolnay/thiserror) (D. ### RS-21 — Remove debugging artefacts; report unfinished code
- **Rule:** Remove committed `dbg!` calls, keeping the inner expression (`dbg!` returns its argument). Replace `println!`/`eprintln!` diagnostics in library and service code with the project's existing logging or telemetry, never a new framework. Report `todo!` and `unimplemented!` reachable in production: completing them is feature work.
- **Detect:** `grep -rnE '\b(dbg|todo|unimplemented)!\(' --include=*.rs src/`; in libraries `grep -rnE '\be?print(ln)?!\(' src/`; or `-W clippy::dbg_macro -W clippy::todo -W clippy::unimplemented -W clippy::print_stdout -W clippy::print_stderr`.
- **Not when:** CLI binaries print as their interface. `unreachable!()` on a proven-impossible branch is an invariant assertion. Test code is exempt.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** A

### RS-22 — Audit unsafe code and report it; never write a SAFETY comment without checking the invariant
- **Rule:** In Qin et al.'s sample (850 unsafe usages and 70 memory-safety bugs from 10 programs, 2 vulnerability databases and std; PLDI 2020) every memory-safety bug involved unsafe code. Report: crates with no unsafe that do not forbid `unsafe_code`; unsafe blocks without a `// SAFETY:` comment naming the invariant and where it is enforced; manual `unsafe impl Send/Sync` whose generic parameters lack bounds; `mem::forget`, `Box::leak` and unpaired `into_raw`/`from_raw`; panics inside `Drop`; unsafe blocks that call a closure or trait method mid-update (panic safety). Run Miri on modules with unsafe. A SAFETY comment written after the fact can sound right and be wrong: treat existing ones as claims to check against the code.
- **Detect:** `grep -rnE '\bunsafe\b' --include=*.rs src/ | wc -l`; `-W clippy::undocumented_unsafe_blocks -W clippy::unnecessary_safety_comment -W unsafe_op_in_unsafe_fn -W clippy::non_send_fields_in_send_ty -W clippy::mem_forget` (`missing_safety_doc` runs by default); `grep -rnE 'unsafe impl(<[^>]*>)? *(Send|Sync) for' src/`; `grep -rn 'impl.*Drop for' src/`; `cargo +nightly miri test` (optionally `MIRIFLAGS=-Zmiri-tree-borrows`); `cargo geiger` for dependencies.
- **Not when:** FFI and `-sys` crates need unsafe; Miri cannot run most FFI and covers only executed paths. cargo-geiger counts unsafe usage and does not judge safety. `non_send_fields_in_send_ty` is a heuristic nursery lint and Rudra is archived (2026-04-02), so no maintained tool covers panic safety or higher-order invariants. Banning unsafe is not the goal: Google answered its first near-shipped Rust memory-safety vulnerability (Android, 2025) with unsafe-specific training.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Understanding Memory and Thread Safety Practices and Issues in Real-World Rust Programs](https://songlh.github.io/paper/rust-study.pdf) (Qin et al., PLDI 2020); [std-dev-guide: Safety comments](https://std-dev-guide.rust-lang.org/policy/safety-comments.html) (Rust Library Team); [Miri](https://github.com/rust-lang/miri) (rust-lang); [cargo-geiger](https://github.com/geiger-rs/cargo-geiger) (geiger-rs, 2026); [Rudra](https://github.com/sslab-gatech/Rudra) (SSLab, SOSP 2021); [Secure Rust Guidelines: checklist](https://anssi-fr.github.io/rust-guide/checklist.html) (ANSSI, undated); [Rust in Android](https://blog.google/security/rust-in-android-move-fast-fix-things/) (J. ### RS-23 — Report guards held across `.await` and futurelock-prone `select!` loops
- **Rule:** Report any std or parking_lot guard or `RefCell` borrow held across `.await`, and `tokio::select!` loops where one branch polls a `&mut` future while another awaits a lock, bounded channel or semaphore (futurelock: at Oxide it made "essentially every incoming HTTP request" hang). The documented mitigation is to spawn the future and select on its `JoinHandle`. Narrowing a lock changes atomicity, so concurrency fixes belong to a human.
- **Detect:** Default Clippy runs `await_holding_lock` and `await_holding_refcell_ref`; custom guard types need `await-holding-invalid-types` in `clippy.toml` (propose it, do not edit); `grep -rn 'select!' src/` and read each branch; in async fns, check that `.lock()`, `.read()` and `.write()` guards drop before the next `.await`.
- **Not when:** The lint reports explicitly dropped guards as false positives (rust-clippy #6446). `tokio::sync::Mutex` may be held across `.await`, at a speed cost. Futurelock comes from one organisation's analysis and no lint detects it. All blocking bugs in Qin et al.'s sample were in safe code, so a clean unsafe audit says nothing here.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Clippy source: await_holding_invalid](https://raw.githubusercontent.com/rust-lang/rust-clippy/master/clippy_lints/src/await_holding_invalid.rs) (rust-lang, 2026); [Tokio tutorial: Shared state](https://tokio.rs/tokio/tutorial/shared-state) (Tokio); [RFD 609: Futurelock](https://rfd.shared.oxide.computer/rfd/0609) (D. Pacheco, Oxide, 2025); [Qin et al.](https://songlh.github.io/paper/rust-study.pdf) (PLDI 2020) · dossier: lang-rust T22-F16

### RS-24 — Report Deref-based inheritance
- **Rule:** Report `Deref`/`DerefMut` impls whose target is not a pointer or a transparent newtype: Deref polymorphism is "a surprising idiom" with no real subtyping, and only smart pointers should implement Deref. Replacing it (traits, facade methods, delegation) is a design change for the owner.
- **Detect:** `grep -rnE 'impl(<[^>]*>)? *((std|core)::ops::)?Deref(Mut)? for' src/`; ast-grep `impl Deref for $T { $$$ }`.
- **Not when:** A newtype that deliberately exposes its whole inner API is accepted practice. Removing a public Deref impl is a major semver break (RS-14).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [Rust Design Patterns: Deref polymorphism](https://rust-unofficial.github.io/patterns/anti_patterns/deref.html) (rust-unofficial); [Rust API Guidelines: C-DEREF](https://rust-lang.github.io/api-guidelines/checklist.html) (Rust Library Team) · dossier: lang-rust T22-F24

### RS-25 — Use Clippy size and nesting lints as hints, never `cognitive_complexity` as a gate
- **Rule:** Clippy keeps `cognitive_complexity` in the restriction group "so as to not mislead users into using this lint as a measurement tool": flag any CI gate on it and never cite its score. Use `too_many_lines`, `too_many_arguments`, `type_complexity` and `excessive_nesting` as review triggers only; their defaults (100 lines, 7 arguments, type complexity 250, nesting off until a threshold is set) are conventions, not measured thresholds.
- **Detect:** `cargo clippy -- -W clippy::too_many_lines -W clippy::excessive_nesting` (nesting reports nothing unless the project sets `excessive-nesting-threshold`); `grep -rn 'cognitive_complexity' Cargo.toml clippy.toml .github/`.
- **Not when:** Long exhaustive `match` expressions are often clearer unsplit. Extracting a function can change borrow scopes and drop order: do it through RS-09 with tests.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [Clippy source: cognitive_complexity](https://raw.githubusercontent.com/rust-lang/rust-clippy/master/clippy_lints/src/cognitive_complexity.rs) (rust-lang, 2026); [Clippy lint configuration](https://doc.rust-lang.org/clippy/lint_configuration.html) (rust-lang, 2026); [Clippy source: excessive_nesting](https://raw.githubusercontent.com/rust-lang/rust-clippy/master/clippy_lints/src/excessive_nesting.rs) (rust-lang, 2026) · dossier: lang-rust T22-F18

### RS-26 — Change Rust performance only with measurements
- **Rule:** Remove clones that default Clippy flags (`clone_on_copy`, `unnecessary_to_owned`) as structural fixes. Everything else (nursery `redundant_clone` and `needless_collect` hits, `Vec::with_capacity`, a faster hasher, an allocator swap, `panic = "abort"`) needs a profiled hot path and before/after benchmark numbers, one change at a time; without numbers, report it. Microsoft's gains (up to 25% from mimalloc, about 15% from String fixes on hot paths) are measured on its own programs.
- **Detect:** Default Clippy (perf, complexity, `ptr_arg`); audit run `cargo clippy -- -W clippy::redundant_clone -W clippy::clone_on_ref_ptr -W clippy::needless_collect`; the project's own benchmark harness (criterion or divan) and a profile (cargo flamegraph), with the numbers recorded.
- **Not when:** Cloning outside hot paths is fine (an `Arc` clone is cheap). A fast non-cryptographic hasher on attacker-controlled keys reopens HashDoS. `panic = "abort"` breaks `catch_unwind` isolation. Microsoft's blanket mimalloc advice conflicts with the Performance Book's "depends on the program": the benchmark decides.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B

## Test, mutation and fuzz tooling

The language-neutral policy (scoping, run validation, survivor dispositions, additive test-only commits, expected-to-fail reproducers, root-cause triage) is in the tests lens; these rules add the Rust commands and pitfalls.

### RS-27 — Run cargo-mutants scoped before the change and on the diff after it
- **Rule:** Run cargo-mutants (27.1.0; works natively on Windows) in a disposable git worktree of the run's repository (PF-21): before the change, scope it to the files and functions the pass will edit; after it, give `--in-diff` a diff file. Confirm the unmutated-baseline line before reading `mutants.out/`; keep `--jobs` at 2-3 and the default timeout (5x the baseline test time, at least 20 s), and re-run a cluster of timeouts at lower `-j`. Give each in-scope survivor one disposition in the triage log under `.harden/` instead of gating on a score. The pass never adds mutant skips to the project, in code (`#[mutants::skip]`, `#[mutants::exclude_re]`) or in its config: equivalent and unproductive survivors stay as triage-log rows, and an in-code skip is proposed to the owner. This departs from the dossier's `#[mutants::skip]` with a reason comment (mutation-testing-practice G108-F06, G108-F16) because the pass adds no suppressions (PC-08) and project configs are read-only.
- **Detect:** Pilot `cargo mutants --list`; before `cargo mutants -f src/x.rs -F "<fn regex>" -j2`; after `git diff <base_sha> > change.diff && cargo mutants --in-diff change.diff`; read `missed.txt`, `caught.txt`, `timeout.txt`, `unviable.txt`; count in-scope survivors with no triage-log row (must be 0); `git diff <base_sha> | grep -E '^\+.*mutants::'` must print nothing; report existing `#[mutants::skip]` without an adjacent reason comment.
- **Not when:** The per-survivor gate itself is unvalidated (grade D), and so is the four-way disposition (mutation-testing-practice G108-F01, G108-F16). `--in-diff` matches only code under test, so a test-only diff runs no mutants, and an edit can weaken coverage elsewhere: it does not replace a full run. `--iterate` is a heuristic; re-run without it. On Windows each mutant rebuilds with the default linker (the Wild speed-up is documented for Linux only), so scope with `-f`/`-F` and split with `--shard`. In a 12-mutant toy run, 2 of the 3 missed mutants were equivalent boundary mutants in `clamp()`.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [cargo-mutants: parallelism](https://mutants.rs/parallelism.html), [timeouts](https://mutants.rs/timeouts.html), [--in-diff](https://mutants.rs/in-diff.html), [skip attributes](https://mutants.rs/attrs.html) and [using results](https://mutants.rs/using-results.html) (M. Pool, 2026); [Practical Mutation Testing at Scale](https://arxiv.org/abs/2102.11378) (Petrović et al., TSE 2022); [Prioritizing Mutants to Guide Mutation Testing](https://homes.cs.washington.edu/~rjust/publ/prioritizing_mutants_tcap_icse_2022.pdf) (Kaufman et al., ICSE 2022) · dossier: mutation-testing-practice G108-F06, G108-F15, G108-F02, G108-F11, G108-F01, G108-F16; lang-rust T22-F21; eval-v1-calibration E01-F10

### RS-28 — Check test strength with coverage, Miri and Kani before trusting the suite
- **Rule:** Before refactoring, measure line coverage of the code in scope with cargo-llvm-cov, report tests that pass by construction (they repeat definitions instead of checking behaviour), run Miri over tests that reach unsafe code, and run any existing Kani harnesses. Coverage finds untested code; it never proves protection.
- **Detect:** `cargo llvm-cov --workspace --html` (its branch and doctest coverage are unstable); a heuristic grep for self-comparing asserts; `cargo +nightly miri test`; `cargo kani` for `#[kani::proof]` harnesses.
- **Not when:** Kani and Miri need extra setup or nightly and cover only bounded or executed paths. Kani's std campaign verifies over 16,000 harnesses per change (2026 preprint): an existence proof, not a cost estimate for this pass. Coverage percentages are easy to game.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [cargo-llvm-cov](https://github.com/taiki-e/cargo-llvm-cov) (taiki-e); [Pragmatic Rust Guidelines: M-TAUTOLOGICAL-TESTS](https://microsoft.github.io/rust-guidelines/guidelines/ai/index.html) (Microsoft, 2026); [Kani: A Model Checker for Rust](https://arxiv.org/abs/2607.01504) (Delmas et al., 2026); [Miri](https://github.com/rust-lang/miri) (rust-lang) · dossier: lang-rust T22-F21, T22-F09

### RS-29 — Add proptest properties as new test files, from documented intent
- **Rule:** Add property tests only as new test files. Derive expected behaviour from docs, specs or an independent reference, record each property's provenance, and start with no-panic (only documented errors on any input in the documented domain), round-trip (serialise/deserialise, `to_*`/`from_*`) and invariant properties; compare against a model (proptest-state-machine) where a simpler reference exists. Hunt with `PROPTEST_CASES=1000 cargo test` from the environment and commit at the default 256 cases. Never commit a still-failing case to `proptest-regressions/`: every `cargo test` replays it and there is no per-case expected-failure marker, so keep the reproducer in a quarantine path with an issue link until the fix lands; commit the file once the case passes (proptest recommends committing it).
- **Detect:** `rg -n "proptest!|#\[proptest\]"` for existing properties; `ls proptest-regressions/`; confirm each new property fails on a deliberate bug in a scratch worktree (PF-21), never in the repository's working tree; prefer building strategies over filtering generated values.
- **Not when:** The quarantine path is the dossier reviewer's workaround, not a sourced practice. Properties read off the implementation encode current behaviour, bugs included. A reference that shares code with the implementation can be wrong the same way. The strongest PBT data are for Python (about 50x the mutant kills of an average unit test; 40 projects, 2022 corpus, correlational); Rust-specific yield is unmeasured. AWS ShardStore's 16 prevented issues came from proptest and stateless model checking together.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [proptest: failure persistence](https://proptest-rs.github.io/proptest/proptest/failure-persistence.html) (proptest); [proptest Config](https://docs.rs/proptest/latest/proptest/test_runner/struct.Config.html) (proptest 1.11.0); [Property-Based Testing in Practice](https://harrisongoldste.in/papers/icse24-pbt-in-practice.pdf) (Goldstein et al., ICSE 2024); [An Empirical Evaluation of Property-Based Testing in Python](https://cseweb.ucsd.edu/~mcoblenz/assets/pdf/OOPSLA_2025_PBT.pdf) (Ravi, Coblenz, OOPSLA 2025); [Lightweight Formal Methods for a Key-Value Storage Node in Amazon S3](https://cdn.amazon.science/77/5e/4a7c238f4ce890efdc325df83263/using-lightweight-formal-methods-to-validate-a-key-value-storage-node-in-amazon-s3-2.pdf) (Bornholt et al., SOSP 2021) · dossier: fuzz-property-hardening G206-F01, G206-F04, G206-F05, G206-F06, G206-F12, G206-F13, G206-F18; eval-v2-calibration E02-F08

### RS-30 — Fuzz Rust input handling with cargo-fuzz under a sanitizer, preferably in WSL2
- **Rule:** Aim fuzz targets at code that parses or decodes untrusted bytes (`serde_json::from_*` call sites, `from_bytes`, protocol and file readers), one format per target, as new files under `fuzz/`. cargo-fuzz needs nightly, and its docs contradict each other on Windows (README: Unix-like only; book: Windows through the MSVC AddressSanitizer), so run it in WSL2 and treat native Windows as experimental. Keep harnesses deterministic (no clock, randomness, environment or global state), let the sanitizer be the oracle for unsafe code, seed from existing fixtures, and give each target at least 10-15 minutes, stopping on a coverage plateau.
- **Detect:** `rg -n "fuzz_target!" fuzz/`; seeds from the tracked seed directories, `awk -F/ '{p=""; for(i=1;i<NF;i++){p=p $i "/"; if($i~/^(fixtures|testdata|samples|corpus)$/) print p}}' .harden/tools/inscope.txt | sort -u` (never `find .`, which also walks `.harden/`), minimised with `cargo fuzz cmin <target>`; crashes minimised with `cargo fuzz tmin <target> <artifact>` and bucketed by root cause, never by crash count (57,142 coverage-unique crashes were fixed by 9 patches; cxxfilt, CCS 2018); a crash inside harness code is a harness bug until shown otherwise.
- **Not when:** No input-handling surface, effectful targets without a seam, or less than about 10 minutes per target: skip and say why. Never commit a still-failing input into an auto-replayed corpus (as in RS-29); the quarantine path is the dossier reviewer's workaround, not a sourced practice. Fixtures with secrets or customer data must not enter a committed corpus.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [cargo-fuzz README](https://github.com/rust-fuzz/cargo-fuzz) (rust-fuzz, 2026); [Rust Fuzz Book: setup](https://rust-fuzz.github.io/book/cargo-fuzz/setup.html) (rust-fuzz); [What makes a good fuzz target](https://github.com/google/fuzzing/blob/master/docs/good-fuzz-target.md) (Google); [Evaluating Fuzz Testing](https://arxiv.org/abs/1808.09700) (Klees et al., CCS 2018); [CIFuzz](https://google.github.io/oss-fuzz/getting-started/continuous-integration/) (Google OSS-Fuzz) · dossier: fuzz-property-hardening G206-F16, G206-F09, G206-F10, G206-F03, G206-F08, G206-F07, G206-F11, G206-F20; eval-v2-calibration E02-F08

## Evidence limits

- Versions and release dates are a 2026-09-23 snapshot; re-resolve them before each run.
- The rust-analyzer observations (macro-body rename miss, 47 s cold SSR run, SSR scope) come from one fixture on one Windows machine. No study measures per-operation failure rates of Rust engines; all engine-bug counts are for Java IDE engines.
- No peer-reviewed study shows that restriction lints (`unwrap_used`, `indexing_slicing`, `arithmetic_side_effects`) reduce production incidents; the evidence is one incident (Cloudflare, 2025) and anecdotes. Clippy's threshold defaults have no Rust-specific empirical validation.
- Whether cargo-udeps works on cargo 1.98 is untested; the false-positive profile of rustc `unused_crate_dependencies` is only partly documented. No false-positive rates exist for cargo-shear or cargo-machete on real projects.
- Rudra is archived and nothing maintained covers its panic-safety and higher-order-invariant checks. Futurelock is one organisation's analysis.
- The ANSSI guide is undated and labelled "(unstable)"; the Safety-Critical Rust guidelines are v0.1 and only their titles were read. The Clippy warning-density, PanicFI and Kani papers are preprints.
- The semver figures come from a blog post on the top 1,000 crates (Nowak, Gruevski et al., 2023).
- Mutation numbers for Rust come from a 12-mutant toy run; PBT effectiveness data are for Python and fuzzing yield data for C/C++ OSS-Fuzz projects. The native-Windows status of cargo-fuzz is contradictory, and that of Miri and Kani was not researched.
- Practitioner voice comes from Hacker News, engineering blogs and incident reports; Reddit, Lobsters and the Rust Users Forum were not covered.
