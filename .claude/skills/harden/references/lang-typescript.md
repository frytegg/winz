# Language: TypeScript / JavaScript

> Pinned tooling, autofix safety, refactoring engines, dead-code and dependency tools, language traps and mutation tooling for TypeScript and JavaScript (Node, browser, React tooling), as of 2026-09-23.
> Read when: a TypeScript or JavaScript file (.ts, .tsx, .mts, .cts, .js, .jsx, .mjs, .cjs) or a package.json is in scope.

## Contents
- Tooling baseline: TS-01–05 (type-check gate, version matrix, typed lint, strictness flags, other linters)
- Autofix safety: TS-06–12 (the T0 list, then cleanups that change behaviour)
- Refactoring engines: TS-13–20 (engine map, moves, census, gates, formatting, fallback)
- Dead code and dependencies: TS-21–27 (Knip, order, library API, dynamic references, dependencies, suppressions)

- Evidence limits

## Tooling baseline

Run the project's own scripts and lockfile versions first (`pnpm exec <tool>`, or `npx <tool>` resolving to `node_modules`). Use `npx <tool>` only when `node_modules/.bin/<tool>` exists; otherwise the tool is one the project lacks. Never add, upgrade or reconfigure a tool in the hardening branch. For a tool the project lacks, run it ephemerally with an exact version, and save tool@version beside every raw output in `.harden/tools/`. Detectors never run on `.` (detection step 4; eval-v2-calibration E02-F08): `F` below holds the in-scope files, `mapfile -t F < <(grep -E '\.(ts|tsx|mts|cts|js|jsx|mjs|cjs)$' .harden/tools/inscope.txt)`, and ESLint gets `--no-warn-ignored`, so files its config ignores are skipped without a warning (check that `--help` lists the flag; otherwise pass detection step 4's directories form). Compiler and lint flags passed on the command line are for detection only.

```
pnpm exec tsc -p tsconfig.json --noEmit --pretty false > .harden/tools/tsc.txt
pnpm exec eslint --no-warn-ignored -f json -o .harden/tools/eslint.json "${F[@]}"
pnpm dlx knip@6.38.0 > .harden/tools/knip.txt
pnpm dlx knip@6.38.0 --production --strict > .harden/tools/knip-prod.txt
python "${CLAUDE_SKILL_DIR}/scripts/ts_program.py" --out .harden/tools/ts-program.json   # offline: export references and module graph from the project's own typescript (DC-02)
pnpm dlx type-coverage@2.30.1 --detail --strict > .harden/tools/type-coverage.txt
pnpm dlx madge@8.0.0 --circular --extensions ts,tsx src/ > .harden/tools/madge.txt
```

### TS-01 — A clean `tsc --noEmit` is the first gate, not the audit
- **Rule:** Record the `tsc --noEmit` error count for every tsconfig at baseline and treat each error as a candidate bug. Report any tsconfig that sets `strict: false` or turns off a strict-family flag without a justifying comment; never flip the flag in the pass. For JavaScript, measure with `checkJs` or per-file `// @ts-check` as a dry run.
- **Detect:** `pnpm exec tsc -p tsconfig.json --noEmit --pretty false | grep -c 'error TS'`; `git grep -nE '"(strict|strictNullChecks|noImplicitAny)"\s*:\s*false' -- 'tsconfig*.json' '*/tsconfig*.json'`; JS: `pnpm exec tsc --noEmit --allowJs --checkJs` when the project declares typescript, otherwise `npx --package=typescript@<x.y.z> -- tsc --noEmit --allowJs --checkJs` (PF-21); check that CI runs tsc, because esbuild, swc and Vite strip types without checking them.
- **Not when:** Types are a floor, not proof: they would have caught 15% of public JS bugs (Gao et al., ICSE 2017), and TS apps were not less bug-prone than JS apps (604 projects, MSR 2022, correlational). Global `checkJs` on a large JS codebase can yield thousands of errors: report the count, never bulk-fix.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [TSConfig: strict](https://www.typescriptlang.org/tsconfig/#strict) (Microsoft, 2026); [To Type or Not to Type](https://earlbarr.com/publications/typestudy.pdf) (Gao, Bird & Barr, 2017); [JS vs TS software quality](https://arxiv.org/abs/2203.11115) (Bogner & Merkel, 2022) · dossier: lang-typescript T20-F01; eval-v1-calibration E01-F10; eval-v2-calibration E02-F08

### TS-02 — Pin every tool and check the compiler and linter compatibility matrix
- **Rule:** Resolve versions before running anything. typescript-eslint 8.70.1 supports TypeScript `>=4.8.4 <6.1.0`, npm `latest` for typescript was 7.0.2 on 2026-09-23 (resolve it with `pnpm view typescript version`), and ESLint 10 accepts flat config only (v9 reached end of life on 2026-08-06). On a TS 7 project, typed lint needs the TS team's recipe (`"typescript": "npm:@typescript/typescript6@^6.0.2"` plus `"@typescript/native": "npm:typescript@^7.0.2"`): report it, never install it in the pass. Pin ephemeral tools exactly and read Knip's report before acting on it.
- **Detect:** `pnpm ls typescript typescript-eslint eslint`; `node -p "require('typescript/package.json').version"`; `npx eslint --version`; `ls .eslintrc* 2>/dev/null` (legacy config, ignored by ESLint 10); ESLint 10 needs Node ≥20.19, ≥22.13 or ≥24.
- **Not when:** A project already pinned to a working combination keeps it. The alias alone leaves only a `tsc6` binary. Knip releases have regressed (#2024, #1930; both closed). These versions are a snapshot: re-check the registries when they move.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Dependency Versions](https://typescript-eslint.io/users/dependency-versions/) (typescript-eslint, 2026); [Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) (Microsoft, 2026); [ESLint v10 migration guide](https://eslint.org/docs/latest/use/migrate-to-10.0.0) (ESLint, 2026); [Knip releases](https://github.com/webpro-nl/knip/releases) (webpro-nl, 2026) · dossier: lang-typescript T20-F03, T20-F20; dead-code-tools T07-F02

### TS-03 — Type-aware lint in report mode, including rules no preset enables
- **Rule:** Run typescript-eslint `recommendedTypeChecked` as the minimum typed-lint pass, plus the no-preset rules `switch-exhaustiveness-check`, `require-array-sort-compare` and `strict-boolean-expressions`, as detection only. Weigh `strictTypeChecked` findings only where the team is proficient in TS; its presets are not semver-stable. A project with no typed-lint config gets that reported as a finding.
- **Detect:** `pnpm exec eslint --no-warn-ignored -f json -o .harden/tools/eslint.json "${F[@]}"`; confirm the rules are live with `npx eslint --print-config src/index.ts | grep -E 'no-floating-promises|no-unsafe'`; add one rule ad hoc with `--rule '{"@typescript-eslint/<rule>":"error"}'`.
- **Not when:** Typed lint costs about one type-check per run; one practitioner reports ESLint as "a 5 minute affair" on a large codebase (HN, 2025). JS files need `disableTypeChecked` or `checkJs`. strict-type-checked noise pushes teams to disable rules wholesale.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Linting with Type Information](https://typescript-eslint.io/getting-started/typed-linting/) (typescript-eslint, 2026); [Shared Configs](https://typescript-eslint.io/users/configs/) (typescript-eslint, 2026); [Rules index](https://typescript-eslint.io/rules/) (typescript-eslint, 2026) · dossier: lang-typescript T20-F03; eval-v2-calibration E02-F08

### TS-04 — Size strictness flags by error count; do not mass-add return types
- **Rule:** Beyond `strict`, measure `noImplicitOverride`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noFallthroughCasesInSwitch` and `noImplicitReturns` by error count and report them as opt-in; the project decides. Do not add `explicit-function-return-type` or `explicit-module-boundary-types` as hardening; export annotations are required only in libraries using `isolatedDeclarations`. Never fix index-access errors with `!`.
- **Detect:** `pnpm exec tsc -p . --noEmit --noUncheckedIndexedAccess | grep -c 'error TS'` (repeat per flag); `grep -rnE '\]!' src`; libraries: `npx tsc --noEmit --declaration --isolatedDeclarations`.
- **Not when:** Sources disagree: `@tsconfig/strictest` enables all these flags, Total TypeScript calls `noImplicitReturns` and `noFallthroughCasesInSwitch` (with the unused-* flags) "too 'noisy'", and the TS team keeps `noUncheckedIndexedAccess` out of `strict` as noisy. `exactOptionalPropertyTypes` needs schema libraries that tell `?` from `| undefined` (check the installed Zod for `.exactOptional()`). A project rule requiring return types everywhere is a legitimate local policy (Google), not a gap.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [TypeScript 4.1: Checked Indexed Accesses](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-1.html) (Microsoft, 2020); [TSConfig Cheat Sheet](https://www.totaltypescript.com/tsconfig-cheat-sheet) (Pocock, 2024); [strictest.json](https://github.com/tsconfig/bases/blob/main/bases/strictest.json) (tsconfig/bases); [Google TypeScript Style Guide](https://google.github.io/styleguide/tsguide.html) (Google) · dossier: lang-typescript T20-F02, T20-F24

### TS-05 — Biome and oxlint complement typed ESLint; they do not replace it
- **Rule:** Before relying on Biome or oxlint instead of typed ESLint, run both on the same commit and diff the hit sets for the promise and `any` rules. Formatting belongs to Prettier's or Biome's `--check`, not to ESLint plugins.
- **Detect:** `npx eslint --no-warn-ignored -f json "${F[@]}"` with only the typed rules; `npx oxlint --type-aware -f json` (needs TS 7 plus `oxlint-tsgolint`) or `biome lint --reporter=json`; compare counts rule by rule.
- **Not when:** Parity figures are vendor self-reports: Biome's `noFloatingPromises` catches "about 75%" of typescript-eslint's cases (Biome, June 2025) and is a nursery rule with an unsafe "Add await" fix; oxlint claims 59 of 61 type-aware rules. On small projects typed ESLint takes seconds and a second linter adds config drift.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Biome v2](https://biomejs.dev/blog/biome-v2/) (Biome, 2025); [Biome noFloatingPromises](https://biomejs.dev/linter/rules/no-floating-promises/) (Biome, 2026); [Oxlint type-aware linting](https://oxc.rs/docs/guide/usage/linter/type-aware.html) (Oxc, 2026) · dossier: lang-typescript T20-F21; eval-v2-calibration E02-F08

## Autofix safety

Apply fixes one rule id at a time; never a blanket `eslint --fix`, `knip --fix` or Biome unsafe fix. A lint suggestion is never T0. Only TS-06 here (and the formatter run in TS-19) is T0; every other cleanup below changes behaviour or needs owner judgement.

### TS-06 — T0: remove compiler-proven unused locals and imports, minus side-effect and entry-point cases
- **Rule:** Remove imports, locals and private members that tsc reports as never read under `noUnusedLocals` and `noUnusedParameters`, or that `@typescript-eslint/no-unused-vars` flags, one commit per rule id, after a green baseline, through the TS language server's remove-unused-imports action or a minimal edit. Rename required-but-unused parameters with `_` instead of deleting them. Keep bare imports (`import './polyfill'`, `import './x.css'`), and never add `"sideEffects": false` without listing CSS and polyfill files. Import removal is T1, not T0, in entry-point modules (`index.ts`, `index.js`) and in any project whose tsconfig sets both `experimentalDecorators` and `emitDecoratorMetadata` (PC-10).
- **Detect:** Run `pnpm exec tsc --noEmit -p tsconfig.json` as is, then with `--noUnusedLocals --noUnusedParameters`, then with `--allowUnreachableCode false --allowUnusedLabels false`; the errors that appear only with a flag are that flag's hits. Select hits by flag, not by error code: the codes usually quoted (TS6133, TS7027, TS7028) were not verified against a docs page. Hits from the unreachable-code and unused-label run are T1 dead-code candidates, not T0. Also `@typescript-eslint/no-unused-vars` with the base rule off and `reportUsedIgnorePattern: true`; `grep -rnE "^import ['\"]" src`; `grep -nE '"(experimentalDecorators|emitDecoratorMetadata)"' tsconfig*.json`; after cleanup, diff the production build's CSS and JS asset list.
- **Not when:** Parameters fixed by a callback, interface or override signature; `catch (e)` bindings flagged by the `caughtErrors: "all"` default; exports (Knip, TS-21). The TS unreachable check covers syntactic unreachability only, not type-based.
- **Tier:** T0 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [TSConfig Reference](https://www.typescriptlang.org/tsconfig/#allowUnreachableCode) (Microsoft, 2026); [no-unused-vars](https://typescript-eslint.io/rules/no-unused-vars/) (typescript-eslint, 2026); [Tree Shaking guide](https://webpack.js.org/guides/tree-shaking/) (webpack, 2026); [consistent-type-imports](https://typescript-eslint.io/rules/consistent-type-imports/) (typescript-eslint, 2026) · dossier: dead-code-tools T07-F03, T07-F06; agent-refactoring-engines G105-F03; autofix-trust G105-F07, G105-F09

### TS-07 — `||`→`??`, `==`→`===` and truthiness rewrites are behaviour changes
- **Rule:** Never bulk-apply `prefer-nullish-coalescing`, `eqeqeq` or `strict-boolean-expressions` changes; for each site, list which falsy values (`''`, `0`, `NaN`, `false`) the left operand can hold and decide whether the falsy fallback was intended. Keep `x == null` as the null-or-undefined idiom.
- **Detect:** `prefer-nullish-coalescing` and `eqeqeq` with `['error','always',{null:'ignore'}]` in report mode; `grep -rnE '\|\| (0|""|false|\[\]|\{\})' src`.
- **Not when:** Conversion is safe only when the left operand's type is `object | null | undefined`. ESLint's `eqeqeq` autofixes only `typeof` and same-type-literal comparisons, and says its other suggestions "can change runtime behavior"; `prefer-nullish-coalescing` skips conditional tests by default for the same reason.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** high · **Grade:** A
- **Source:** [prefer-nullish-coalescing](https://typescript-eslint.io/rules/prefer-nullish-coalescing/) (typescript-eslint, 2026); [eqeqeq](https://eslint.org/docs/latest/rules/eqeqeq) (ESLint, 2026); [Google TypeScript Style Guide](https://google.github.io/styleguide/tsguide.html) (Google) · dossier: lang-typescript T20-F12

### TS-08 — `return await` inside try/catch/finally is a fix, not a cleanup
- **Rule:** In async functions, a promise returned inside `try`, `catch` or `finally` must be awaited so the local catch and finally see its outcome; never strip that `await` as redundant. Apply `@typescript-eslint/return-await` fixes (`in-try-catch` or `error-handling-correctness-only`) one by one as behaviour changes, and retire core `no-return-await` (deprecated).
- **Detect:** `@typescript-eslint/return-await: ['error', 'error-handling-correctness-only']` in report mode; ast-grep `try { $$$ return $CALL($$$) $$$ } catch ($E) { $$$ }` in async functions; `git grep -n 'no-return-await'`.
- **Not when:** Outside try/catch the choice is style: Node Best Practices says "Always do return await" for stack traces, while the typescript-eslint default forbids it there; do not churn either way. The fix routes errors into the local catch, so check what callers expected.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [return-await](https://typescript-eslint.io/rules/return-await/) (typescript-eslint, 2026); [Node.js Best Practices](https://github.com/goldbergyoni/nodebestpractices) (Goldberg et al.) · dossier: lang-typescript T20-F05; eval-v2-calibration E02-F08

### TS-09 — Do not parallelise `await`-in-loop as a cleanup
- **Rule:** Treat `no-await-in-loop` as a review prompt and report each hit; replacing a sequential loop with `Promise.all` is a concurrency change for the owner. Record for each hit the data dependency, external rate limit, retry or backoff, bounded resource, side-effect order and wanted error semantics (fail-fast, or `Promise.allSettled` to collect).
- **Detect:** `no-await-in-loop` in report mode, or ast-grep `for ($$$) { $$$ await $X $$$ }`.
- **Not when:** Independent, idempotent iterations (read-heavy fan-out) are a clear win once the owner confirms them. `Promise.all` rejects on the first failure and does not cancel the rest, so partial side effects remain; exchange and API clients are the high-risk case.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [no-await-in-loop](https://eslint.org/docs/latest/rules/no-await-in-loop) (ESLint, 2026); [Promise.all()](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/all) (MDN, 2026) · dossier: lang-typescript T20-F19

### TS-10 — "Unnecessary" conditions are unnecessary only where types are sound
- **Rule:** Use `@typescript-eslint/no-unnecessary-condition` as a dead-branch finder only with `noUncheckedIndexedAccess` on and no `as` or `any` on the data path; apply its suggestions (it has no autofix) one at a time. Never remove a null check or `?.` on data that crosses a trust boundary without runtime validation.
- **Detect:** `pnpm exec eslint --no-warn-ignored --rule '{"@typescript-eslint/no-unnecessary-condition":"error"}' "${F[@]}"`; trace each flagged value to its source: JSON.parse, fetch, env, DB rows or an `as` cast mean keep the guard and fix the type.
- **Not when:** The rule trusts declared types ("TypeScript optimistically assumes that indexed access will always return a value"); open false positive on `foo[bar] ??= 0` (#6632). A removed guard passes tests and fails on malformed production input.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** high · **Grade:** A
- **Source:** [no-unnecessary-condition](https://typescript-eslint.io/rules/no-unnecessary-condition/) (typescript-eslint, 2026); [Issue #6632](https://github.com/typescript-eslint/typescript-eslint/issues/6632) (typescript-eslint, 2023) · dossier: lang-typescript T20-F11; eval-v2-calibration E02-F08

### TS-11 — Type-only import conversions add or drop module loads
- **Rule:** Report, do not apply, a switch to `verbatimModuleSyntax` or a `consistent-type-imports` fix run: previously elided imports start executing, a top-level `import type` drops a module load, and decorator-referenced imports break under `emitDecoratorMetadata`. Enforce with one mechanism, not both (duplicate reports).
- **Detect:** migration size `pnpm exec tsc --noEmit --verbatimModuleSyntax | grep -c 'error TS'`; `grep -rn 'emitDecoratorMetadata' tsconfig*.json`.
- **Not when:** Node type stripping and esbuild, swc, Babel or Vite require explicit `type` imports, so a project on them already needs this. CommonJS emit from ESM syntax errors under the flag. Inline `import { type X }` still leaves `import {} from 'm'`. NestJS, TypeORM and older Angular DI rely on decorator metadata.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [TSConfig: verbatimModuleSyntax](https://www.typescriptlang.org/tsconfig/verbatimModuleSyntax.html) (Microsoft, 2026); [consistent-type-imports](https://typescript-eslint.io/rules/consistent-type-imports/) (typescript-eslint, 2026); [Node.js: Modules: TypeScript](https://nodejs.org/api/typescript.html) (Node.js, 2026) · dossier: lang-typescript T20-F17

### TS-12 — React hooks lint: report mode, never `--fix`
- **Rule:** Where React is present, run eslint-plugin-react-hooks 7.x `recommended` (7.1.1 was current on 2026-09-23) in report mode, with compiler-rule severities overridden to `warn` for the first run, and triage every diagnostic by hand. Never run `eslint --fix` on these rules, never enable `enableDangerousAutofixThisMayCauseInfiniteLoops`, and do not enable `recommended-latest` in the pass.
- **Detect:** `pnpm ls eslint-plugin-react-hooks` (below 6.1 lacks the compiler rules); `pnpm exec eslint --no-warn-ignored -f json -o .harden/tools/eslint-react.json "${F[@]}"`; `rg -n "eslint-disable.*react-hooks/" -g '*.{ts,tsx,js,jsx}'`; `rg -n enableDangerousAutofixThisMayCauseInfiniteLoops`.
- **Not when:** The preset sets some compiler rules to `error`, so enabling it as-is in CI can block a working project. The compiler-backed rules are young: 180 react/react issues carry the Compiler and Bug labels (91 open, 2026-09-23). Effect and dependency fixes belong to the frontend lens.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [eslint-plugin-react-hooks](https://react.dev/reference/eslint-plugin-react-hooks) (React, 2026); [CHANGELOG](https://github.com/facebook/react/blob/main/packages/eslint-plugin-react-hooks/CHANGELOG.md) (Meta/React, 2026); [ExhaustiveDeps source](https://github.com/react/react/blob/main/packages/eslint-plugin-react-hooks/src/rules/ExhaustiveDeps.ts) (React, 2026) · dossier: frontend-react-hygiene G110-F01, G110-F02; eval-v2-calibration E02-F08

## Refactoring engines

### TS-13 — The agent chooses the refactoring; an engine produces the edit
- **Rule:** Route every multi-file rename, file move, extract and inline through a TypeScript engine (TS-14); the agent picks the operation and parameters and logs tool, version, request and returned edit per commit. A hand-written multi-file rename is a violation wherever an engine supports it. Claude Code's LSP tool offers diagnostics and navigation only, so call the engine directly.
- **Detect:** Flag a diff that renames or moves an identifier across more than one file with no matching engine call in the transcript (several Edit or `sed` calls replacing the same identifier).
- **Not when:** Quantitative support is Java/IntelliJ only: 13 of 176 ChatGPT and 9 of 137 Gemini refactorings were unsafe and replay through IntelliJ avoided all 22 (2025); renaming errors were the second-largest cause of LLM refactoring test failures (10 Java projects, 2026). Local single-file renames are safe as plain edits. Engines have bugs too (TS-17).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [RefactoringMirror](https://arxiv.org/abs/2411.04444) (Liu et al., 2025); [RefactorAssist](https://arxiv.org/abs/2608.00924) (Cordeiro et al., 2026); [Claude Code tools reference](https://code.claude.com/docs/en/tools-reference) (Anthropic, 2026) · dossier: agent-refactoring-engines G105-F01, G105-F17, G105-F10

### TS-14 — Which TypeScript engine does which operation
- **Rule:** Rename: the TS language server (`tsc --lsp --stdio` on TS 7; tsserver or the LanguageService on TS 6 and earlier). File move: LSP `workspace/willRenameFiles` (TS 7) or `LanguageService.getEditsForFileRename` (TS 6). Extract, inline and move-to-file: only the TS 6.0 LanguageService (`getApplicableRefactors`, then `getEditsForRefactor`, e.g. through ts-morph 28's `getLanguageService().compilerObject`). Change signature: no engine; use TS-20.
- **Detect:** `node -p "require('typescript/package.json').version"`. TS 7.0 has no stable programmatic API (an unstable `./unstable/*` API ships without refactor, rename or code-action methods) and its LSP returns no `refactor` actions. Pass the project's `FormatCodeSettings` and apply text changes last to first.
- **Not when:** ts-morph and the LanguageService apply TS 6.0 semantics even where the repo pins TS 7 (TS 7 turns 6.0 deprecations into errors, e.g. TS5102 on `baseUrl`). TS 7.1 is expected to ship a new API: re-check then. Monorepos and project references were not tested.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) (Microsoft, 2026); [protocol.ts, release-6.0](https://github.com/microsoft/TypeScript/blob/release-6.0/src/server/protocol.ts) (Microsoft, 2026); [tsc/internal/ls](https://github.com/microsoft/TypeScript/tree/main/tsc/internal/ls) (Microsoft, 2026) · dossier: agent-refactoring-engines G105-F03

### TS-15 — Moves are the least reliable operation; never ts-morph `move()` with path aliases
- **Rule:** Before moving a file, check tsconfig `paths`. With aliases, never use ts-morph `sourceFile.move()`: it updates relative specifiers only and left `@util/math` broken (TS2307). Use `willRenameFiles` or `getEditsForFileRename`, then search strings and config for the old path before building.
- **Detect:** `grep -n '"paths"' tsconfig*.json`; after the move, `npx tsc --noEmit -p .` (TS2307) and `rg -n -F "from '@alias/oldname'"` (and with double quotes); check package.json `exports`, jest `moduleNameMapper` and barrel re-exports; `git diff --color-moved=zebra` to confirm the moved body is unchanged.
- **Not when:** Both correct engines turn an alias import into a relative one, a style change lint may reject. Move is the third most bug-prone type among Java IDE engine bugs (80 of 518, 15.44%; Wang et al., 2024).
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [ts-morph: Source Files](https://ts-morph.com/details/source-files) (ts-morph, 2026); [ts-morph #837](https://github.com/dsherret/ts-morph/issues/837) (dsherret, 2020); [Refactoring Engine Bugs](https://arxiv.org/html/2409.14610v1) (Wang et al., 2024) · dossier: agent-refactoring-engines G105-F03, G105-F18

### TS-16 — Take a textual census before and after every rename or move
- **Rule:** Save a whole-repo census of the old name (code, strings, config, templates, docs) before the engine runs, re-run it after, and justify or hand-fix every surviving hit. A green tsc is not evidence: the TS 7 LSP rename left `(m as any)['computeTotal']`, tsc reported 0 errors, and the program output changed.
- **Detect:** `rg -n -w -F OLD --hidden -g '!node_modules' -g '!.git' > before.txt`; TS/JS reflective sweep `rg -n "[[]['\"]OLD['\"][]]|Reflect[.]"`; diff against the post-edit census, then run the tests.

### TS-17 — Gate every engine operation: type-check, tests, diff review

- **Not when:** The evidence is Java IDE engines: of 518 engine bugs, 242 (46.7%) were compile errors and 66 (12.7%) behaviour changes, with Extract, Inline and Move the most bug-prone (Wang et al., 2024). These are bug counts, not per-use rates; engines may still be far safer than LLM edits.

### TS-18 — Check the WorkspaceEdit before applying it

### TS-20 — No engine for change-signature: use the fallback; codemods only for migrations
- **Rule:** For operations without an engine (change signature, alias repairs), apply in order: census, moved-block diff, declaration-emit API diff, `tsc`, tests, one refactoring per commit. ## Language traps

### TS-28 — Every Promise is handled; no async callbacks in void slots
- **Rule:** Every Promise is awaited, returned, `.catch`-ed with real handling, or passed to a documented fire-and-forget helper that catches internally. No `arr.forEach(async …)`, async event listeners or Promise conditions. Fix sites one at a time: adding `await` changes timing and error propagation.
- **Detect:** `no-floating-promises`, `no-misused-promises`, `await-thenable` (recommended-type-checked); `grep -rnE '\.forEach\(\s*async' src`; `grep -rnE '^\s*void [a-zA-Z_.]+\(' src`, then check that each voided call catches internally.
- **Not when:** `void` silences the rule but "doesn't handle it": accept it only where the callee catches. Thenable query builders (Knex) trip the rule on every builder. Never add `await` inside a non-async React `useEffect` callback. The rule docs call it hard to enable on large projects.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [no-floating-promises](https://typescript-eslint.io/rules/no-floating-promises/) (typescript-eslint, 2026); [no-misused-promises](https://typescript-eslint.io/rules/no-misused-promises/) (typescript-eslint, 2026); [Node.js CLI: --unhandled-rejections](https://nodejs.org/api/cli.html#--unhandled-rejectionsmode) (Node.js, 2026) · dossier: lang-typescript T20-F04

### TS-29 — Process handlers exit; throw Errors with causes
- **Rule:** `uncaughtException` and `unhandledRejection` handlers may log, flush and clean up synchronously, then must exit non-zero: a log-only `unhandledRejection` handler disables Node's default crash (Node ≥15, default mode `throw`). Throw and reject only `Error` instances, chain with `{ cause: err }`, and justify every empty catch in a comment.
- **Detect:** `grep -rnE "process\.on\(['\"](uncaughtException|unhandledRejection)" src`, then read each handler; `grep -rnE 'unhandled-rejections=(warn|none)|NODE_OPTIONS' package.json Dockerfile* *.yml`; `only-throw-error`, `prefer-promise-reject-errors`, `use-unknown-in-catch-callback-variable`, ESLint `preserve-caught-error` (in `eslint:recommended` since v10); `grep -rnE "throw ['\"\x60]" src`.
- **Not when:** Libraries must not install process handlers. Wrapping errors changes what upstream `instanceof` and `err.code` checks see: check callers first. Some libraries throw non-Errors (`allowRethrowing`).
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [Using 'uncaughtException' correctly](https://nodejs.org/api/process.html#warning-using-uncaughtexception-correctly) (Node.js, 2026); [Node.js CLI: --unhandled-rejections](https://nodejs.org/api/cli.html#--unhandled-rejectionsmode) (Node.js, 2026); [preserve-caught-error](https://eslint.org/docs/latest/rules/preserve-caught-error) (ESLint, 2026) · dossier: lang-typescript T20-F06, T20-F07

### TS-30 — Contain `any`; record type coverage, especially in agent-written code
- **Rule:** Record baseline type coverage and `any` counts, and flag `any` spread with `no-explicit-any` and the `no-unsafe-*` family. File the `any`s of each declaration (function, type or variable) as one finding, apart from any suppression that hides them (TY-04): replacing them needs `tsc`, not the linter. Replace each with `unknown` or a precise type, narrowed only by checks the code already makes (`typeof`, `Array.isArray`, `instanceof`, `in`, equality, or a type predicate whose body is such a check), and add no cast (`as`), non-null assertion, `any` or suppression; `tsc` stays green. A value that comes from an `any`-returning source (`JSON.parse`, `.json()`, Storage, an untyped package) gets `unknown`, never a precise type: assigning `any` to a precise type is an unchecked assertion (TS-31). In an exported declaration, only a top-level parameter of an exported function or method may change, from `any` to `unknown`, which every existing call still satisfies, checked against the PF-15 API snapshot; when that snapshot was not taken, no exported declaration changes; any other exported change (a return type, a property, a callback's parameter) is a public API change (T2, TS-42). The class follows the proof. Structural: the JavaScript emitted for each touched file is identical to base's, or, when a type predicate or restructured control flow changes the emitted code, a PC-15 differential over at least 1,000 seeded generated arguments (non-objects, `null`, arrays, missing and wrongly typed fields) plus every example and fixture of that input in the repository is byte-identical in return values, thrown error types and messages. Behavioural: a narrowing that needs a runtime check the code does not make (TS-31, PC-24). Propose a CI ratchet at the recorded baseline; do not add it.
- **Detect:** `pnpm dlx type-coverage@2.30.1 --detail --strict`; `grep -rnE '(:\s*any\b|\bas any\b|<any>|any\[\])' src | wc -l`; `JSON.parse`, `.json()` and Storage return `any` by default. Emit check, run from the repository root so `require` finds the project's `typescript`: `pnpm exec tsc -p tsconfig.json --showConfig > .harden/tools/tsconfig-resolved.json` (or its package manager's equivalent, DT-05), `git show <base_sha>:<file> > "<scratch_dir>/emit/<name>.base.<ext>"` (the file's own extension), then `node -e "const ts=require('typescript'),fs=require('fs');const c=ts.convertCompilerOptionsFromJson(JSON.parse(fs.readFileSync(process.argv[1],'utf8')).compilerOptions,'.').options;for(const k of ['noEmit','sourceMap','inlineSourceMap','inlineSources','declaration','declarationMap'])delete c[k];c.removeComments=true;const o=process.argv.slice(2).map(f=>ts.transpileModule(fs.readFileSync(f,'utf8').replace(/\r\n/g,'\n'),{compilerOptions:c,fileName:f}).outputText);console.log(o[0]===o[1]?'identical':'differs');process.exitCode=o[0]===o[1]?0:1" .harden/tools/tsconfig-resolved.json "<scratch_dir>/emit/<name>.base.<ext>" <file> > .harden/tools/emit-<id>.txt`. The PF-15 API snapshot diff shows only the allowed parameter changes.
- **Not when:** Agents used `any` 9x more than humans while their TS PRs were accepted 1.8x more often (preprint, 2026); that review misses it is an inference. Less `any` correlated weakly with smell metrics and not with bug proneness (rho 0.17–0.26, 604 projects, MSR 2022). `any` is accepted during migration and for untyped packages; ts-reset suits apps, not libraries. A validator that collects errors before throwing often needs restructured control flow before `tsc` accepts `unknown` without a cast; without the byte-identical differential it is behavioural or reported. In the autonomous pilot a config validator's nine `any`s stayed because the only finding filed was the file's blanket `eslint-disable`, whose narrowing needed ESLint; the v3 runs set the `unknown` route aside as adding runtime checks (pilot-auto-calibration A01-F15).
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [Do's and Don'ts](https://www.typescriptlang.org/docs/handbook/declaration-files/do-s-and-don-ts.html) (Microsoft); [Avoiding anys](https://typescript-eslint.io/blog/avoiding-anys) (Goldberg, 2025); [type-coverage](https://github.com/plantain-00/type-coverage) (plantain-00, 2026); [Type Constructs in AI-Generated Code](https://arxiv.org/abs/2602.17955) (Lee et al., 2026); [TypeScript 3.0 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-0.html) (Microsoft, 2018: "`unknown` is the type-safe counterpart of `any`"; "Anything is assignable to `unknown`"); [The Basics](https://www.typescriptlang.org/docs/handbook/2/basic-types.html) (TypeScript Handbook, Microsoft: "Type annotations never change the runtime behavior of your program"); [Narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html) (TypeScript Handbook, Microsoft: TypeScript "looks at these special checks (called type guards)"); [no-unsafe-assignment](https://typescript-eslint.io/rules/no-unsafe-assignment/) (typescript-eslint, 2026: "Disallow assigning a value with type `any` to variables and properties") · dossier: lang-typescript T20-F08; pilot-auto-calibration A01-F15

### TS-31 — Validate untrusted data at trust boundaries instead of asserting it
- **Rule:** Replace `JSON.parse(x) as T`, `(await res.json()) as T`, `process.env.X!` and `{} as Foo` at trust boundaries with runtime validation, preferring a validator the project already uses (schema library, JSON Schema + Ajv, or OpenAPI/GraphQL codegen). ### TS-33 — Silent coercion: `sort()` without a comparator, objects in template strings
- **Rule:** Every `sort` or `toSorted` on a non-string array needs a comparator (`require-array-sort-compare`, in no preset: `[1,2,3,10,20,30].sort()` gives `[1,10,2,20,3,30]`). Template literals must not receive objects, nullish or `any` values (`restrict-template-expressions`, `no-base-to-string`).
- **Detect:** `grep -rnE '\.(sort|toSorted)\(\s*\)' src`; the three rules ad hoc with `--rule`.
- **Not when:** A comparator changes output order, which is the fix: check snapshots, persisted orderings and pagination cursors first. `ignoreStringArrays` defaults to true. strict-type-checked's `allowNumber: false` is noisy.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [require-array-sort-compare](https://typescript-eslint.io/rules/require-array-sort-compare/) (typescript-eslint, 2026); [restrict-template-expressions](https://typescript-eslint.io/rules/restrict-template-expressions/) (typescript-eslint, 2026) · dossier: lang-typescript T20-F18

### TS-34 — TS-only runtime syntax: find it everywhere, convert only low-risk cases
- **Rule:** Find enums, runtime namespaces, parameter properties and `import =` with `--erasableSyntaxOnly` (TS ≥5.8); they are mandatory fixes only under Node type stripping or single-file transpilers. Never use `const enum` across package boundaries. Convert internal string enums to literal unions or `as const` objects only where low-risk.
- **Detect:** `pnpm exec tsc --noEmit --erasableSyntaxOnly | grep -c 'error TS'`; `grep -rnE '\b(const\s+)?enum\s+\w+' src`; `no-unsafe-enum-comparison` (recommended-type-checked).
- **Not when:** Google still permits plain enums. Converting a numeric enum drops reverse mappings and changes `Object.keys/values` output and serialised values; in a library it is an API break (T2). Member-level JSDoc and `@deprecated` are lost in unions. Node v26 removed `--experimental-transform-types`.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [Node.js: Modules: TypeScript](https://nodejs.org/api/typescript.html) (Node.js, 2026); [Announcing TypeScript 5.8](https://devblogs.microsoft.com/typescript/announcing-typescript-5-8/) (Microsoft, 2025); [Handbook: Enums](https://www.typescriptlang.org/docs/handbook/enums.html) (Microsoft) · dossier: lang-typescript T20-F16

### TS-35 — Deprecated APIs and TS 7-unsupported options are an upgrade report
- **Rule:** Report `@deprecated` API use (`no-deprecated`, strict-type-checked) and tsconfig options TS 7 no longer supports (`target: es5`, `downlevelIteration`, `moduleResolution: node/node10/classic`, `module: amd/umd/systemjs/none`, `baseUrl`, `esModuleInterop` or `allowSyntheticDefaultImports: false`; `outFile` is gone since 6.0) as an upgrade item, not a pass edit.
- **Detect:** `grep -nE '"(baseUrl|outFile|downlevelIteration)"|"moduleResolution"\s*:\s*"(node|node10|classic)"|"target"\s*:\s*"es5"|"(esModuleInterop|allowSyntheticDefaultImports)"\s*:\s*false' tsconfig*.json`; `npx tsc -v`.
- **Not when:** Removing `baseUrl` means rewriting `paths`; changing `moduleResolution` can change which files resolve. Vue, MDX, Astro, Svelte and Volar-based tooling, and Angular editor support, still need TS 6.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) (Microsoft, 2026); [Announcing TypeScript 6.0](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/) (Microsoft, 2026); [no-deprecated](https://typescript-eslint.io/rules/no-deprecated/) (typescript-eslint, 2026) · dossier: lang-typescript T20-F20

### TS-36 — Barrel files and import cycles are module-structure reports
- **Rule:** Report barrel files in application code (an `index.ts` re-exporting siblings) and value-level import cycles, with measured cost. Do not remove barrels or break cycles in the pass: both change module evaluation order and initialisation side effects.
- **Detect:** `find src -name 'index.[jt]s*' -exec grep -lE '^export (\*|\{[^}]*\}) from' {} +`; `pnpm dlx madge@8.0.0 --circular --extensions ts,tsx src/` with `.madgerc` `skipTypeImports`; measure test wall time, dev-server module count and `tsc --extendedDiagnostics` before any proposal.
- **Not when:** The evidence is dev server, test and CI time: Atlassian reports 75% fewer build minutes and 88% fewer tests run; the test-count reduction depends on its affected-test selection; Hagemeister's numbers come from a synthetic benchmark; production bundlers may tree-shake barrels. One barrel at a library entry point is fine. madge last released 8.0.0 (Aug 2024); `import/no-cycle` is expensive, CI-only. Cycle harm is anecdotal.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** C
- **Source:** [Faster builds by removing barrel files](https://www.atlassian.com/blog/atlassian-engineering/faster-builds-when-removing-barrel-files) (Atlassian, 2025); [The barrel file debacle](https://marvinh.dev/blog/speeding-up-javascript-ecosystem-part-7/) (Hagemeister, 2023); [madge README](https://github.com/pahen/madge) (pahen) · dossier: lang-typescript T20-F14, T20-F15

## Test, mutation and fuzz tooling

Generic mutation triage (dispositions, killing-test quality, LLM-written tests) belongs to the tests lens; this section covers the JS/TS tools. No JS/TS fuzzer was researched; fast-check appears only as an equivalence falsifier (TS-40).

### TS-37 — StrykerJS: framework runner, per-test coverage, checker, line ranges
- **Rule:** Use StrykerJS 10.0.0 with the Vitest or Jest runner, `coverageAnalysis: "perTest"`, the TypeScript checker and line-range `--mutate`, never the `command` runner. On 10.0.0 pin exact versions from the `vitest` 4 and `typescript` 6 lines (Vitest 5 and TS 7 break runs) and list plugins explicitly under pnpm. Install only in a disposable git worktree of the run's repository (PF-21), so the manifest and lockfile changes never reach the hardening branch.
- **Detect:** `pnpm add -D @stryker-mutator/core@10.0.0 @stryker-mutator/vitest-runner@10.0.0 @stryker-mutator/typescript-checker@10.0.0 vitest@<x.y.z> typescript@<x.y.z>` (4.x and 6.x), run in that worktree; config `{"plugins":["@stryker-mutator/vitest-runner","@stryker-mutator/typescript-checker"],"testRunner":"vitest","checkers":["typescript"],"coverageAnalysis":"perTest","reporters":["clear-text","json"]}`; `pnpm exec stryker run --mutate "src/calc.ts:6-8"`; grep `stryker.config.*` for `"command"` or `"coverageAnalysis": "off"`.
- **Not when:** The pins are a 2026-09-23 snapshot resting on open issues (#6210, #6111, #6213) and one toy run; StrykerJS 10 needs Node ≥22. The command runner "disables almost all performance enhancements" (#4414), and Karma setups run for hours.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [StrykerJS v10.0.0](https://github.com/stryker-mutator/stryker-js/releases/tag/v10.0.0) (Stryker, 2026); [StrykerJS configuration](https://stryker-mutator.io/docs/stryker-js/configuration/) (Stryker, 2026); [StrykerJS #6111](https://github.com/stryker-mutator/stryker-js/issues/6111) (2026); [StrykerJS #4414](https://github.com/stryker-mutator/stryker-js/issues/4414) (2023) · dossier: mutation-testing-practice G108-F04, G108-F14, G108-F03; eval-v1-calibration E01-F10

### TS-38 — Validate a Stryker run before reading any survivor
- **Rule:** Accept a run only if the unmutated baseline passes, at least one mutant is killed, no covered Survived mutant has `testsCompleted: 0`, and Timeouts neither cluster on non-loop code nor exceed about 5% of mutants (a heuristic). Keep the default timeout (net time × 1.5 + 5,000 ms), re-run timeout clusters at lower concurrency, and re-run each survivor alone with `--coverageAnalysis off` before writing a test.
- **Detect:** list `status=='Survived' && testsCompleted===0` in `reports/mutation/mutation.json`; "Ran 0.00 tests per mutant" is a red flag; `npm ls vitest typescript @stryker-mutator/core`; `stryker run --mutate "src/f.ts:7:10-7:19" --coverageAnalysis off`; run the covering tests three times.
- **Not when:** With StrykerJS 10.0.0 and Vitest 5 one project's score fell from 47.36 to 2.96 (2,637 mutants, #6210); on 9.6.1 with Vitest 4.1.4 about 5.5% of covered mutants were Survived with no test run (#6213); perTest verdicts can flip between identical runs (#6073).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [StrykerJS #6210](https://github.com/stryker-mutator/stryker-js/issues/6210) (2026); [StrykerJS #6213](https://github.com/stryker-mutator/stryker-js/issues/6213) (2026); [StrykerJS #6073](https://github.com/stryker-mutator/stryker-js/issues/6073) (2026); [StrykerJS configuration](https://stryker-mutator.io/docs/stryker-js/configuration/) (Stryker, 2026) · dossier: mutation-testing-practice G108-F03, G108-F15

### TS-39 — Mutate the lines about to change, before changing them; no global score gate
- **Rule:** Before a refactor, run Stryker scoped to the planned line ranges and triage those survivors. Use `--incremental` only after the change, and `--force` when tests, snapshots, dependencies or env changed. Never gate on `thresholds.break` or any global score; a score may stay as a trend check.
- **Detect:** `pnpm exec stryker run --mutate "src/x.ts:40-95"` before the edit; afterwards `--incremental`, or `--force` if the diff touches tests, `__snapshots__`, lockfiles or env config; check `thresholds.break` (default null).
- **Not when:** Incremental mode ignores changes outside mutated and test files, `.snap` edits and dependency updates. Changed-line mutants correlate only weakly with commit-relevant ones (Kendall/Pearson 0.15–0.4, 25 projects, ICSME 2020): also mutate direct callers when affordable. No known industrial deployment computes mutation adequacy (ICSE 2022).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [StrykerJS incremental mode](https://stryker-mutator.io/docs/stryker-js/incremental/) (Stryker, 2026); [Commit-Aware Mutation Testing](https://mpapad.github.io/publications/pdfs/ICSME2020.pdf) (Ma et al., 2020); [Prioritizing Mutants](https://homes.cs.washington.edu/~rjust/publ/prioritizing_mutants_tcap_icse_2022.pdf) (Kaufman et al., 2022) · dossier: mutation-testing-practice G108-F02, G108-F01

### TS-40 — Record survivors with reasons, never disable them in the project; equivalence needs an argument, not an LLM verdict
- **Rule:** Record an equivalent survivor in the triage log under `.harden/` with a reason naming which of reachability, infection or propagation fails, and an unproductive one (logging, cache or memo writes, sleeps and timeouts, metrics) with its arid-class reason. Exclude unproductive classes only through `ignorers` or `mutator.excludedMutations` in the pass's own Stryker config in the disposable worktree (TS-37), each with a one-line reason. The pass never adds `// Stryker disable` comments or Stryker settings to the project: it proposes an in-code disable (`// Stryker disable next-line <Mutator>: <reason>`) to the owner instead. This departs from the dossier's in-code disables (mutation-testing-practice G108-F16) because the pass adds no suppressions (PC-08) and project configs are read-only. An LLM "equivalent" verdict ranks candidates and never closes one; a bounded fast-check differential run can refute equivalence.
- **Detect:** `git diff <base_sha> | grep -E '^\+.*Stryker disable'` must print nothing; `rg -n --pcre2 "Stryker disable(?!.*:)"` lists existing reasonless disables as report items; `rg -n "(log|logger|console)\.(debug|info|warn|trace)|sleep\(|setTimeout|deadline|metrics\.|counter\.inc"` on survivor lines.
- **Not when:** A log line carrying an audit requirement is not arid; Google's arid rules are tuned to its own environment. Mutants excluded in the pass's config stay visible as `ignored` in its report. Zero-shot GPT-4 equivalence detection reached about 0.56 macro-F1 (3,302 Java pairs, ISSTA 2024). Fuzzing refutes equivalence, never proves it.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [StrykerJS: disable mutants](https://stryker-mutator.io/docs/stryker-js/disable-mutants/) (Stryker, 2026); [Practical Mutation Testing at Scale](https://arxiv.org/abs/2102.11378) (Petrović et al., 2022); [LLMs for Equivalent Mutant Detection](https://arxiv.org/abs/2408.01760) (Tian et al., 2024) · dossier: mutation-testing-practice G108-F18, G108-F12, G108-F16

### TS-41 — Pilot the mutation cost before the full run
- **Rule:** Pilot one file with `--dryRunOnly` and extrapolate: time ≈ fixed overhead + mutants × covering-test runtime / workers. Batch line ranges into one run to pay the fixed start-up once; if the estimate exceeds the budget, suppress arid mutants before narrowing scope, and record what stayed unmeasured.
- **Detect:** `pnpm exec stryker run --mutate <one file> --dryRunOnly`; record overhead, mutants per line and seconds per mutant.
- **Not when:** Per-mutant cost spans orders of magnitude: about 0.16 s (Vitest 4, 2,637 mutants in about 7 min, #6210), about 14 s (CRA/Jest perTest, #3320), about 34 s (Karma, #5462); about 25 s fixed overhead on one toy project. The budget max(10 min, 3 × suite runtime) is unvalidated (grade D).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** C
- **Source:** [StrykerJS #3320](https://github.com/stryker-mutator/stryker-js/issues/3320) (2021); [StrykerJS #5462](https://github.com/stryker-mutator/stryker-js/issues/5462) (2025); [StrykerJS #6210](https://github.com/stryker-mutator/stryker-js/issues/6210) (2026) · dossier: mutation-testing-practice G108-F11

## Public API changes

### TS-42 — Additive public changes (a union member, an option with a default) are T1 with approval
- **Rule:** When the fix for a verified finding needs to widen an exported type, file it as T1 behavioural for the user's approval, not as a T2 contract change: a new member of an exported union, or a new optional parameter or options field whose default reproduces the old behaviour exactly. It qualifies when every changed declaration only adds such a member, parameter or field, every consumer in the repository still type-checks and handles the new member, and a new test shows the old call behaving as before and the new member or option working. Removing, renaming or narrowing a member, making a parameter required, or a default that changes the old behaviour stays T2 (PF-15). No option is added without a verified finding that needs it (invariant 5).
- **Detect:** Re-run the PF-15 TypeScript snapshot command into `.harden/tools/api-<id>` and read every line of `diff -r .harden/tools/api-base .harden/tools/api-<id>`: each change only adds a union member, an optional parameter or an optional property. `pnpm exec tsc -p tsconfig.json --noEmit` exits 0 and the TS-32 command reports no new hit; `git grep -n -w '<TypeName>'` lists the consumers, and one that branches on the members without an exhaustive check handles the new member in the same fix. package.json `private`, `exports` and `main` decide whether consumers exist outside the repository (TS-23).
- **Not when:** In a published library (TS-23) consumers outside the repository are not type-checked here and may depend on the old set of members (Hyrum's law): say so in the approval question and leave the version decision to the owner. The tier comes from the skill's own paired evaluation (n = 2 runs per cell), not from an external study.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** B
- **Source:** [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) (Anthropic); [Semantic Versioning 2.0.0](https://semver.org/) (Preston-Werner); [Hyrum's Law](https://www.hyrumslaw.com/) (Wright); [Narrowing: Exhaustiveness checking](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#exhaustiveness-checking) (Microsoft) · dossier: skill-design T31-F01; behaviour-changing-fixes G102-F07; lang-typescript T20-F10; eval-v1-calibration E01-F07

## Evidence limits

- Versions are a 2026-09-23 snapshot (typescript 7.0.2 and 6.0.2, typescript-eslint 8.70.1, ESLint 10.11.0, Knip 6.38.0, StrykerJS 10.0.0, eslint-plugin-react-hooks 7.1.1). When typescript-eslint will support TS 7 is unknown; TS 7.1 is expected to add a new API and may change TS-14.
- Engine results are single fixture runs (2–5 files, one Windows machine); monorepos, project references and pnpm workspaces were not tested. No per-operation failure rate exists for any TS engine; engine-bug and LLM-refactoring figures are Java/IntelliJ.
- Types-and-bugs evidence is thin and conflicting: Gao (15% of public JS bugs), Bogner (no bug-proneness difference, correlational), and a 2026 preprint (Tang et al.) whose prose and table disagree (27.8% vs 27.2% tooling/config bugs). No study measures incidents prevented by `no-floating-promises` or the yield of retrofitting stricter flags.
- No independent precision or recall exists for Knip, nor for Biome or oxlint parity (vendor self-reports only).
- Barrel-file evidence covers dev servers, tests and CI minutes, not production bundles.
- StrykerJS pins rest on open issues and one toy run; the per-survivor gate and the time budget are unvalidated; no JS/TS fuzzing tool was researched.
- Practitioner voice comes from Hacker News, GitHub issues and engineering blogs; Reddit, Lobsters and StackExchange were not sampled.
