# Lens: Performance

> Purpose: find scalability defects that a measurement can confirm (N+1 and chatty I/O, blocking I/O on async paths, unbounded caches, histories, queues and listeners, accidentally quadratic code, over-fetching) and hold every performance change to a profile, a same-machine A/B and behaviour preservation.
> Read when: the scope has request handlers, database or ORM access, async code, long-running processes, loops over collections from a store or network, benchmarks or performance CI jobs, or any change justified by speed.

## Procedure

You are a fresh-context, read-only lens subagent (detection step 8). Your tools are Read, Grep and Glob: never edit or write a file, never run a command, and never start the application, a load test or a profiler against a running service. Write the exact measurement command into `notes`: the verifier never executes a command proposed in notes (detection step 11), so the report lists it for the user, and the change phase measures only approved items (PE-17).

1. **Load scope.** Read `.harden/inventory.json`, `.harden/config.json` (scope, exclude_globs), `.harden/prescan.json` and the raw detector outputs in `.harden/tools/` (none in an unseeded pass, DT-21). Classify each deployable unit as long-running (server, worker, bot, daemon), short-lived (CLI, build script, batch job) or library; several rules apply to one class only (see each Not when).
2. **Collect existing measurement evidence before reading code:** profiles, traces, APM or Sentry exports, benchmark suites and saved results, load-test scripts, CI benchmark jobs, and any record of production data sizes. Cite what exists and record what is missing (PE-22). Comments such as `// faster` are claims to verify (PE-16).
3. **Detector commands (run by the orchestrator in detection step 4; read their outputs from `.harden/tools/`).** Exact commands, pinned versions and flags live in the language file of each detected language; this lens names the tool and rule id. A detector with no output is a limit line.
   - Python: Ruff `ASYNC210`, `ASYNC230`, `ASYNC240`, `ASYNC251`, `B019`, `RUF017`. `PERF401`–`PERF403` are constant-factor hints only; `PERF203` is enforced only for target versions below 3.11.
   - TypeScript/JavaScript: ESLint `no-await-in-loop`; eslint-plugin-n `n/no-sync` (`allowAtRootLevel: true`); eslint-plugin-unicorn `prefer-set-has`; eslint-plugin-regexp `no-super-linear-backtracking` and `no-super-linear-move`; oxlint `oxc/no-accumulating-spread`.
   - Rust: the Clippy `perf` group. Go: no static rule in this evidence base; review benchmarks for `b.Loop` (Go 1.24+) and benchstat use.
   - C#: the `.Result`/`.Wait()`/`GetAwaiter().GetResult()` search in handlers (PE-04). C and C++ build files: the fast-math search (PE-19).
   - Rails and Django: note whether strict loading or `FETCH_RAISE` (Django 6.1+) is already used in tests; do not enable it (PE-03).
   - Every language: the ast-grep patterns in each rule's Detect line are detector commands; run the rg patterns yourself through the Grep tool. They are leads, not proof: read the code behind every hit. Solidity: the evidence base names no tool for this lens.
4. **Manual checks the tools do not make:**
   - for each loop hit, whether n is bounded by design or can reach the largest production size found in step 2 (PE-08, PE-09);
   - whether the code runs on a request or event-loop path, or only at startup, in a CLI or a build script (PE-04);
   - for each loop await, the four questions of PE-10; for each cache, the PE-14 checklist;
   - for each module-level map, queue or listener registration, and each list or map that gains an entry per poll, tick or request, a matching eviction, bound or removal (PE-05, PE-06);
   - every list and export endpoint, and whether its result size is bounded (PE-11, PE-12);
   - existing benchmarks against PE-18, CI benchmark gates against PE-20, load-test scripts against PE-21.
5. **Grade evidence honestly.** A static or grep hit without a profile, trace or scaling measurement gets confidence `inference` or `needs_review`, never `tool_high_precision`. Drop constant-factor candidates that no profile places on a hot path (PE-01, PE-16). A structural defect class (PE-03 to PE-13) may be emitted from review alone, but its notes must name the measurement that will confirm it; for an unbounded cache or history (PE-05) that is the size-observable test, with the proposed cap and where it will be set.
6. **Return candidates plus files_read as your final message**; the orchestrator merges them into `.harden/candidates.json`. files_read lists every file you read with its line ranges (DT-02). Candidates follow the findings schema of blueprint section 5 (`assets/findings.schema.json`): `lens: "performance"`, `rule_ref: "PE-NN"`, the rule's tier, class and fix risk, `verified: false`, `status: "candidate"`, `file` and `line` at `base_sha`, and evidence entries with file:line (`source`), the tool command and output path (`tool`), or an existing profile or benchmark file (`repro` or `doc`). In the notes, write the before/after measurement to run (PE-09, PE-17) and the behaviour traps to check (PE-19). Never edit; never claim a speedup nobody measured.
7. **Hand off by name only.** Event-loop blocking, queue bounds and fan-out combinators are shared with the concurrency lens; ReDoS and request-size limits as an attack surface are shared with the security lens. Emit one candidate per location and cross-reference the other lens instead of duplicating it.

## Rules

### PE-01 — No performance change without measured evidence
- **Rule:** Change code for speed only when a profile or trace from a realistic workload shows that the target dominates the metric that matters, and attach a before/after measurement to every performance change (PE-17). Flag the structural defect classes (PE-03 to PE-13) from review, but drop any candidate that is not on a measured path or does not scale with production data sizes. Constant-factor and micro-level changes always need the profile first. An unbounded cache or history in a long-running process (PE-05) grows with run time, which counts as scaling; it is never dropped for lack of a profile or soak run, because PE-05's size-observable test is its measurement.
- **Detect:** For every diff, commit or comment justified by speed, look for a linked profile (flame graph, pprof, py-spy, Scalene) and a same-machine before/after benchmark. List candidates with `git log -p | grep -inE 'perf|optimi|faster|speed'` (a heuristic), then check each for attached evidence.
- **Not when:** Duffy (2010) and Muratori (2023) argue that "profile first" misses "peanut butter" slowness spread thinly across the code; a flat profile points to structural causes rather than proving there is nothing to fix, and Knuth himself says an "easily obtained" 12% is not marginal. Resolution: defect classes may be flagged from review, while their fixes still need measurement. Coz (SOSP 2015): optimising the code a conventional profiler shows as hot "may have no impact on performance", so judge the end-to-end metric, not the hot spot.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Revisiting Knuth's "Premature Optimization" Paper](https://probablydance.com/2025/06/19/revisiting-knuths-premature-optimization-paper/) (Skarupke, 2025, quoting Knuth 1974); [Knuth: the context](https://hlopko.com/2019/08/03/premature-optimization/) (Hlopko, 2019); [Notes on Programming in C](https://www.lysator.liu.se/c/pikestyle.html) (Pike, 1989); [Coz: Finding Code that Counts with Causal Profiling](https://arxiv.org/abs/1608.03676) (Curtsinger, Berger, SOSP 2015); [The "premature optimization is evil" myth](https://joeduffyblog.com/2010/09/06/the-premature-optimization-is-evil-myth/) (Duffy, 2010); [Is premature optimization really the root of all evil?](https://softwareengineering.stackexchange.com/questions/80084/is-premature-optimization-really-the-root-of-all-evil) (SE answers, 2008); [GSO](https://arxiv.org/abs/2505.23671) (Shetty et al., 2025); [GSO leaderboard](https://gso-bench.github.io/) (read 2026-09-23) · dossier: performance-review T04-F01, T04-F21; eval-v2-calibration E02-F01

### PE-02 — Match the profiler to the cost, profile a release build, and know the blind spots
- **Rule:** Accept profile evidence only from a release or production build with symbols, with one profile type collected at a time, and from a profiler that matches the cost: a CPU profile leaves out time spent waiting, so I/O-bound services need off-CPU, idle or blocking views. Read flame graphs by frame width (how often a frame was sampled); the x-axis is not time.
- **Detect:** For each profile cited as evidence, check the build type (`cargo --release`, `NODE_ENV=production`, Go without `-race`), CPU versus wait coverage (py-spy `--idle`; Go block and mutex profiles, "not enabled by default"), and runtime fit: py-spy or Scalene (Python), pprof (Go), perf, samply, cargo-flamegraph, DHAT or heaptrack (Rust), node `--prof`/`--cpu-prof` and DevTools (Node.js). For Rust, the Rust Performance Book recommends `debug = "line-tables-only"` in `[profile.release]` and `-C force-frame-pointers=yes`.
- **Not when:** Sampling profilers can miss short or inlined functions. Profiling costs something in production (Go says so; Scalene's README gives "typically no more than 10-20%" and a 35% slowdown on pyperformance). Clinic.js "is not being actively maintained" and its results "may not be accurate": prefer the built-in Node profilers. Gregg's per-language tool list is partly dated (it still lists the archived pyflame).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Diagnostics](https://go.dev/doc/diagnostics) (Go Authors); [Flame Graphs](https://www.brendangregg.com/flamegraphs.html) (Gregg); [The Rust Performance Book: Profiling](https://nnethercote.github.io/perf-book/profiling.html) (Nethercote et al.); [py-spy](https://github.com/benfred/py-spy) (Frederickson); [Scalene](https://github.com/plasma-umass/scalene) (Berger et al., OSDI 2023); [Clinic.js](https://github.com/clinicjs/node-clinic) (clinicjs); [Profiling Node.js Applications](https://nodejs.org/en/learn/getting-started/profiling) (Node.js) · dossier: performance-review T04-F02

### PE-03 — Remove N+1 and chatty I/O
- **Rule:** Replace per-item database queries, ORM lazy loads, HTTP calls or small writes inside loops with eager loading (`select_related`/`prefetch_related`/`includes`/`Include`), a bulk or batched call, or one set-based query. Record the query count and the rows or bytes loaded before and after, because over-eager loading is a defect too. Turning per-item awaits into parallel calls falls under PE-10, not this rule.
- **Detect:** ast-grep `rule: {pattern: 'await $PROMISE', inside: {kind: for_in_statement, stopBy: end}}`, widened with `any:` over `for_statement`, `while_statement` and `do_statement`, then read each hit for a DB, ORM or HTTP call; Python ORM `.objects.get`/`.filter` inside `for` loops. Runtime (proposed in `notes`): Django 6.1+ `QuerySet.fetch_mode(models.FETCH_RAISE)` in tests of hot paths, django-debug-toolbar; Rails `strict_loading_by_default = true` with `strict_loading_mode = :n_plus_one_only`; Sentry's N+1 detector (sequential similar DB spans, total over 50 ms, usually five spans) or APM query counts per request.
- **Not when:** Very small, bounded N. Over-correction: Yang et al. also document slow eager loading (Spree: 405 products pulled "13811 related variants products containing 276220 option_values", "making the page freeze"; the fix delayed loading), and Azure warns "complex joins can become expensive". Django fetch modes do not exist before 6.1. Enabling strict loading app-wide is a separate owner decision: its violation action defaults to `:raise`, thoughtbot recommends log mode in production "to avoid crashing the application", and FactoryBot setups can need a workaround.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [How not to structure your database-backed web applications](https://hyperloop-rails.github.io/220-HowNotStructure.pdf) (Yang et al., ICSE 2018); [Detecting performance anti-patterns for ORM applications](https://petertsehsun.github.io/publication/icse2014/) (Chen et al., ICSE 2014); [Chatty I/O antipattern](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/chatty-io/) (Microsoft, 2017, updated 2026); [Fetch modes](https://docs.djangoproject.com/en/stable/topics/db/fetch-modes/) (Django 6.1); [Database access optimization](https://docs.djangoproject.com/en/stable/topics/db/optimization/) (Django 6.1); [N+1 Queries](https://docs.sentry.io/product/issues/issue-details/performance-issues/n-one-queries/) (Sentry); [Strict loading in Rails 8](https://thoughtbot.com/blog/strict-loading-in-rails-8-a-railsy-way-to-avoid-n-1-queries) (Bireke, thoughtbot, 2025) · dossier: performance-review T04-F05

### PE-04 — Report blocking synchronous I/O on async functions, event loops and request threads
- **Rule:** Flag sync fs APIs, `execSync`/`spawnSync`/`execFileSync`, `crypto.pbkdf2Sync` and zlib `*Sync` calls in Node request paths; `requests`/`urllib`, `open()` and `time.sleep` inside `async def`; `.Result`/`.Wait()` in .NET request handlers. One blocking call stalls every request that shares the thread or loop. Propose the library's async API, and a thread-pool wrapper only when no async API exists. Report, do not apply: event-loop blocking fixes belong to the concurrency human lane, and turning an exported function async is a public API change.
- **Detect:** Ruff `ASYNC210`, `ASYNC230`, `ASYNC240`, `ASYNC251`; ESLint `n/no-sync` with `allowAtRootLevel: true`; `rg -nE '\b(readFileSync|writeFileSync|existsSync|execSync|spawnSync|pbkdf2Sync|inflateSync|deflateSync)\('`; C# `\.Result\b|\.Wait\(\)|GetAwaiter\(\)\.GetResult\(\)` in handlers. Runtime (proposed): `node --trace-sync-io` while exercising request paths; event-loop lag or request queue length under load.
- **Not when:** CLI tools, build scripts and startup code; sync calls at module top level are why `allowAtRootLevel` exists. Azure: short, uncontended I/O (small files on SSD) "might be more performant as synchronous operations", async wrappers around sync methods consume more resources, and unblocking threads can shift load onto a downstream resource that then starves or throttles. Measure before proposing.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Synchronous I/O antipattern](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/synchronous-io/) (Microsoft, 2017, updated 2026); [Don't Block the Event Loop (or the Worker Pool)](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop) (Node.js); [ASYNC210 blocking-http-call-in-async-function](https://docs.astral.sh/ruff/rules/blocking-http-call-in-async-function/) (Astral, Ruff 0.16.8); [n/no-sync](https://github.com/eslint-community/eslint-plugin-n/blob/master/docs/rules/no-sync.md) (eslint-community) · dossier: performance-review T04-F07

### PE-05 — Bound caches and histories, and remove per-request listeners, in long-running processes
- **Rule:** In servers, workers, daemons and bots, give every memo cache a maxsize or TTL, replace `functools` caches on instance methods (the global cache keeps every `self` alive), give write-only module-level maps and in-memory histories that grow on every poll, tick or request an eviction path or a cap, and remove listeners added per request without a matching removal. Treat MaxListenersExceededWarning as a leak signal, never as a limit to raise. A bound changes hit rate, eviction and what readers see, so it is a T1 behavioural item (PC-14: its own commit, approval, a demonstrating test):
  - **Cap:** a documented cap the owner can configure. Place the knob where no exported signature changes, as for ER-21's timeout: the project's existing config or settings path, a parameter with a default on a non-exported function or constructor, or else a named module-level constant; exposing it through an exported signature follows PC-17 and never holds the bound back. Without hit-rate data, still bound it: the unbounded growth is the defect and the exact cap is the owner's tuning. Pick a default above the largest working set the repository's tests, fixtures or docs show, say where it is set, and list it as owner-tunable under the report's Open owner items (RP-07).
  - **Demonstrating test:** a size-observable test is sufficient evidence. Drive N simulated TTL buckets, polls or requests, with N above the cap, and assert the entry count stays at or below the cap. It fails on the parent, where the count grows with N. Read the count through state the code already holds (the cache's or attribute's length) or through a non-exported seam, never through a test-only branch in production code (invariant 2). No soak run, heap profile or production measurement is needed to apply the item.
  - **Public attribute:** a bound on a public attribute that callers read (a `history` list) changes no signature and stays T1 behavioural; it is not T2 for being visible. Pin what readers see below the cap with a characterization test (PF-19) before the fix, name the change in the `Behaviour change:` line, and show the affected files when asking for approval (`--interactive`).
  - **Removal instead of a bound:** when the cache only saves allocation or recomputation and a differential test shows the output byte-identical with and without it (PC-15), removing the cache is T1 structural: keep `rule_ref: PE-05`, set `class: structural`, and prove it as PE-14 and PE-19 describe, with the existing tests untouched and green (invariant 1).
  - **Speed cost:** a slowdown from the bound or the removal is judged against a budget stated in the item before measuring (PE-17), not rejected because any slowdown is significant.
- **Detect:** Ruff `B019`; `rg -nE 'lru_cache\(maxsize=None\)|@(functools\.)?cache\b|setMaxListeners\((0|Infinity)\)'`; ast-grep for module-level `new Map()` with `.set` but no `.delete`/`.clear`; `.on(`/`addEventListener(` inside handlers with no matching removal; instance fields or module-level lists, vectors and maps that gain an entry on each poll, tick or request (`append`, `push`, `insert`, `set`) with no trim, cap or eviction anywhere in the file. Soak evidence (proposed, optional: the Rule's size-observable test is enough to apply the fix): tracemalloc `snapshot2.compare_to(snapshot1, 'lineno')`; Node `v8.writeHeapSnapshot()` or `--heapsnapshot-signal` compared in the DevTools Comparison view; Go heap pprof over time.
- **Not when:** Short-lived CLIs. `functools.cache` is "smaller and faster than lru_cache() with a size limit" and fine for a small, finite key space. A smaller cache means more origin loads: Discord's smaller LRU gave smaller GC spikes but "higher 99th latency times" (Go service, 2020), so size the bound from measured hit rates when they exist; without them, the Rule's documented, owner-tunable default applies. The size-observable test, the cap tier and structural removal come from the skill's own paired evaluation (n = 3 runs per cell), not from an external study.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [functools](https://docs.python.org/3/library/functools.html) (PSF, 3.14.7); [B019 cached-instance-method](https://docs.astral.sh/ruff/rules/cached-instance-method/) (Astral); [Events](https://nodejs.org/api/events.html) (Node.js v26.10.0); [No Caching antipattern](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/no-caching/) (Microsoft, 2017, updated 2026); [Why Discord is switching from Go to Rust](https://discord.com/blog/why-discord-is-switching-from-go-to-rust) (Howarth, Discord, 2020) · dossier: performance-review T04-F09; eval-v2-calibration E02-F01

### PE-06 — Report unbounded queues with the backpressure a bound would add
- **Rule:** Flag `asyncio.Queue()`, `queue.Queue()` and `deque()` created without a bound in long-running processes; an asyncio queue with maxsize of zero or less "is infinite". Report the proposed bound together with what happens when it is reached: `await put()` blocks, which can deadlock a producer that is also the consumer. Never apply the bound in the pass.
- **Detect:** `rg -nE 'asyncio\.Queue\(\s*\)|queue\.Queue\(\s*\)|deque\(\s*\)'`; for each hit, name the producers and consumers and whether any task is both.
- **Not when:** Short-lived CLIs, and queues whose producer is bounded by design. The concurrency lens covers bounding queues, buffers and fan-out: emit one candidate and cross-reference it.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [asyncio Queues](https://docs.python.org/3/library/asyncio-queue.html) (PSF, 3.14.7) · dossier: performance-review T04-F09

### PE-07 — Replace quadratic accumulation idioms, never by autofix alone
- **Rule:** Replace string, bytes or tuple concatenation in a loop with `join`, `StringIO`/`BytesIO`, `bytearray` or a list; `sum(list_of_lists, [])` with a comprehension or `itertools.chain`; `list.pop(0)`/`insert(0, x)` with `collections.deque`; spreads into a reduce or loop accumulator (`{...acc}`, `[...acc, x]`) with in-place mutation. Do not rely on interpreter-specific in-place optimisation: the current Python docs call repeated concatenation quadratic "in the general case" and promise nothing else.
- **Detect:** Ruff `RUF017`; `ast-grep -p '$S += $T' --lang python` limited to matches inside `for` loops, then confirm `$S` is a str, bytes or tuple; `rg -nE '\.pop\(0\)|\.insert\(0,' --glob '*.py'`; oxlint `oxc/no-accumulating-spread`; JS `.shift()`/`.unshift(` inside loops. Ruff `PERF401`–`PERF403` are constant-factor hints (PE-16), not quadratic detectors.
- **Not when:** Tiny bounded loops, where the change is cosmetic. The autofixes are unsafe: Ruff marks the RUF017 fix "always ... unsafe" (the replacement accepts any iterable, so "code that previously raised an error may silently succeed", and it can remove comments), and both "better" examples in the oxc rule doc are broken (the array version returns `push()`'s numeric length; the object version never returns `acc`). Java `String +=` in loops is not verified in this evidence base.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [Common Sequence Operations, note 6](https://docs.python.org/3/library/stdtypes.html) (PSF, 3.14.7); [Programming FAQ](https://docs.python.org/3/faq/programming.html) (PSF); [collections.deque](https://docs.python.org/3/library/collections.html) (PSF, 3.14.7); [RUF017 quadratic-list-summation](https://docs.astral.sh/ruff/rules/quadratic-list-summation/) (Astral); [oxc/no-accumulating-spread](https://oxc.rs/docs/guide/usage/linter/rules/oxc/no-accumulating-spread.html) (Oxc); [Ruby reject!](https://www.tumblr.com/accidentallyquadratic/157496054437/ruby-reject) (Elhage, 2017) · dossier: performance-review T04-F04

### PE-08 — Replace linear lookups inside loops with a one-time index
- **Rule:** When a loop over one collection searches another of similar size (`in` on a list, `Array.includes`/`indexOf`/`find`/`filter`, a nested loop matching by id) and n is not provably small, build a Set, Map, dict or HashSet once and look up in it. Quadratic code passes tests at small n and fails in production; confirm the growth with PE-09 before fixing.
- **Detect:** ast-grep (JS/TS) `{any: [{pattern: '$A.includes($B)'}, {pattern: '$A.indexOf($B)'}, {pattern: '$A.find($$$)'}], inside: {any: [{kind: for_in_statement}, {kind: for_statement}, {kind: while_statement}], stopBy: end}}`, plus `.filter`/`.map` callbacks that contain `.find` or `.includes`; Python `$X in $L` inside `for` loops, then confirm `$L` is a list or tuple; eslint-plugin-unicorn `prefer-set-has` (skips arrays checked only once; its autofix needs review).
- **Not when:** n bounded by design; Pike: "Fancy algorithms are slow when n is small, and n is usually small." A Set or Map costs allocation and needs hashable keys. JS Set and Map compare object keys by identity, while the original `find()` predicate may compare by value: keep the equality semantics (PE-19).
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [Why Accidentally Quadratic?](https://www.tumblr.com/accidentallyquadratic/113840433022/why-accidentally-quadratic) (Elhage, 2015); [O(n^2), again, now in WMI](https://randomascii.wordpress.com/2019/12/08/on2-again-now-in-wmi/) (Dawson, 2019); [How I cut GTA Online loading times by 70%](https://nee.lv/2021/02/28/How-I-cut-GTA-Online-loading-times-by-70/) (t0st, 2021); [Toddler](https://doi.org/10.1109/icse.2013.6606602) (Nistor et al., ICSE 2013); [How we decreased GitLab repo backup times from 48 hours to 41 minutes](https://about.gitlab.com/blog/how-we-decreased-gitlab-repo-backup-times-from-48-hours-to-41-minutes/) (Nayak, Kraft, GitLab, 2025); [prefer-set-has](https://github.com/sindresorhus/eslint-plugin-unicorn/blob/main/docs/rules/prefer-set-has.md) (eslint-plugin-unicorn); [HN thread on Knuth's paper](https://news.ycombinator.com/item?id=44386236) (sfn42, 2025) · dossier: performance-review T04-F03

### PE-09 — Confirm scaling defects with doubling runs at production size
- **Rule:** Before fixing a suspected super-linear defect, measure it at n, 2n, 4n and 8n or more (at least 4 sizes, up to the largest observed production size when one is known) and let `scripts/doubling.py` judge the growth exponent b = log2(t(2n)/t(n)) of the two largest steps: about 1 means linear, about 2 quadratic, and its verdict `superlinear` (both steps at b ≥ 1.5) confirms the defect. Prefer operation counts at base, which are deterministic: count the inner operation (the predicate, comparison or lookup call, or each element read) through a counting wrapper or proxy around the inputs, or through a comparator or callback the function already accepts, never by editing production code; one run per size is enough and repeated counts must agree. Counts through the inputs see only the work done on them, and a rewrite can copy its input first, so they confirm a defect but never measure its fix: a rewrite is measured by timings (PE-17). A timing needs at least 3 discarded warm-up runs, then at least 10 timed repetitions per size in one process, judged by their median and spread; one timing per size is not a doubling run. A verdict other than `superlinear` or `not-superlinear` is a measurement still to make, never weaker evidence: measure again with operation counts, larger n or more repetitions. A timing verdict `not-superlinear` below the largest production size, or where none is known, does not clear a loop that scans the whole collection for each element: count it. Keep the count harness, in a new test file, as a regression check at a large n that asserts an operation count, never a wall-clock time (PE-20); keep a timing harness only as a benchmark file the project's test command does not run.
- **Detect:** Within the Phase 0 side-effect limits, the harness, kept in the run's scratch_dir and run against a base worktree there (PC-15) and later against the candidate, writes by absolute path `{"kind": "count" | "time", "unit": "<unit>", "samples": {"<n>": [<value>, ...]}}` to `<repo>/.harden/tools/doubling-<id>-base.samples.json`; then, run from the repository root, `python "${CLAUDE_SKILL_DIR}/scripts/doubling.py" <repo>/.harden/tools/doubling-<id>-base.samples.json --json --out .harden/tools/doubling-<id>-base.json` (exit 0 conclusive, 3 not yet conclusive, 2 bad input), and the same with `-head` after the fix. Timing harnesses per stack: criterion `BenchmarkId` over sizes, pytest parametrize with the benchmark fixture, Go sub-benchmarks per size, hyperfine over generated inputs (`--warmup 3`; it runs at least 10 times by default and `--export-json` keeps each time), Vitest bench, or a loop around `performance.now()` or `time.perf_counter()`. Flag the verdict `superlinear`. Take n from production records, not test fixtures: practitioners report worst-case sizes "several times the expected case".
- **Not when:** Constant factors, JIT tiers, garbage collection and caches distort timings at small n. They set the constant of the power law, not its exponent, which is why counts, medians and the two largest steps decide: the autonomous pilot's single timings (18, 71, 196 and 135 ms from n = 2,000 to 16,000) fell at the last step and parked a quadratic loop (pilot-auto-calibration A01-F13). Code that is quadratic in theory is fine when n is bounded by design. The 1.5 cut (halfway between linear and quadratic), the 10-repetition minimum (hyperfine's default) and the 0.5 relative-IQR noise limit are conventions, not validated thresholds. The technique rests on practitioner case studies and textbook practice, not controlled studies, and no source gives a principled "small n" threshold. Doubling cannot separate a logarithmic factor from the exponent (an n log n cost reads as b of about 1.1; Sedgewick and Wayne: "Cannot identify logarithmic factors with doubling hypothesis"), so `not-superlinear` means below the threshold, not linear.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B

### PE-10 — Report awaits in loops; parallelise only with a bound and chosen failure semantics
- **Rule:** Never replace a sequential loop await with an unbounded `Promise.all` or `asyncio.gather` over an input-sized array. Report each candidate with answers to four questions: does iteration i use the result of i−1; does a rate limit apply; is the array bounded; what must happen on partial failure. Propose bounded concurrency (p-limit, `asyncio.Semaphore`), and `allSettled` when every result is needed, because `Promise.all` rejects on the first rejection, which changes behaviour relative to the loop.
- **Detect:** ESLint `no-await-in-loop`; the ast-grep loop rule of PE-03; read each hit and answer the four questions in the candidate.
- **Not when:** Dependent iterations, retries, rate-limited APIs, and promises that allocate a bounded resource (RAM, file descriptors, network bandwidth), all listed in ESLint's "When Not To Use It"; ordered side effects and transactions. Parallel requests can overload downstream services and cause a retry storm (Azure's antipattern catalogue). Concurrency changes are the human lane.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [no-await-in-loop](https://eslint.org/docs/latest/rules/no-await-in-loop) (ESLint); [Promise.all()](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/all) (MDN); [Performance testing and antipatterns](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/) (Microsoft, updated 2026) · dossier: performance-review T04-F08, T04-F07

### PE-11 — Project, filter and aggregate in the data store; stream large results
- **Rule:** Fetch only the needed columns (`values()`/`values_list()`, `only()`/`defer()`, explicit select lists), filter and aggregate in the query rather than in memory, and iterate large results (`iterator()`) instead of materialising them. Compare the bytes read from the store with the bytes returned, before and after.
- **Detect:** `rg -niE 'select \*'`; EF `AsEnumerable()` or `.ToList()` before `.Where(` (Azure: "The call to AsEnumerable is a hint that there's a problem"); in-memory filtering or summing of full query results; bytes from the store versus bytes in the response per endpoint (Azure's method); `EXPLAIN` or `QuerySet.explain()` on the new query (proposed).
- **Not when:** Azure: "Offloading processing to the database isn't always the best option" (Busy Database), so measure the database side too. Adding a limit or pagination is PE-12, not this rule.
- **Tier:** T1 · **Class:** structural · **Fix risk:** high · **Grade:** B
- **Source:** [Extraneous Fetching antipattern](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/extraneous-fetching/) (Microsoft, 2022, updated 2026); [Database access optimization](https://docs.djangoproject.com/en/stable/topics/db/optimization/) (Django 6.1) · dossier: performance-review T04-F06

### PE-12 — Report unbounded list endpoints for an owner decision
- **Rule:** List every user- or API-facing list or export endpoint whose result grows with the data and has no limit or pagination, and report it with a proposed limit. Never add pagination or a limit in the pass: it changes the response contract, and Yang et al. file pagination under content-display trade-offs.
- **Detect:** Django `.all()` iterated in list views with no slice or paginator; Prisma/TypeORM `findMany()`/`find()` with no `take`/`limit` in handlers; a route or OpenAPI inventory of list and export endpoints, each checked for a size bound.
- **Not when:** Small, fixed reference tables. Internal jobs that must process every row: stream them instead (PE-11).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** B

### PE-13 — Create expensive, thread-safe clients once and reuse them
- **Rule:** Move construction of HTTP clients, connection pools, cloud SDK clients, Redis clients and compiled templates or schemas out of handlers and loops into one shared instance, but only when the class is documented as thread-safe or shareable. Never mutate the shared instance per request: setting default headers before each request "can create a race condition".
- **Detect:** Inside handlers and loops: `new HttpClient(`, `axios.create(`, `new Pool(`, `createClient(`, `new S3Client(`, `redis.createClient(`; Python `requests.get(` in loops with no Session, `boto3.client(` in per-request functions. Runtime (proposed): socket or handle exhaustion, TIME_WAIT counts (netstat/ss), time spent in connect and close in thread profiles.
- **Not when:** Azure: "If a class isn't shareable (not thread-safe), then this antipattern doesn't apply." Scarce resources such as database connections go back to the pool and are not held. A long-lived HTTP client can miss DNS changes; Microsoft recommends `IHttpClientFactory` or `PooledConnectionLifetime`.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [Improper Instantiation antipattern](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/improper-instantiation/) (Microsoft, 2017, updated 2026) · dossier: performance-review T04-F10

### PE-14 — Adding a cache is a behaviour change, not a free speedup
- **Rule:** Add or keep a cache only when all of these hold: measurement shows the same expensive request repeated; a TTL or eviction policy exists; every write path invalidates it; hit and miss counters exist; a cache failure falls back to the source while the origin is protected (Azure suggests a Circuit Breaker); a test shows the staleness is acceptable. Apply a new cache only as its own behavioural commit, with the owner approving the staleness window. Removing an existing cache that only saves allocation or recomputation is T1 structural when a differential test shows the output byte-identical with and without it (PC-15); a cache whose removal changes any output is removed as a behavioural item. Judge the removal's slowdown against a budget stated before measuring (PE-17).
- **Detect:** Answer the checklist for each existing or proposed cache. With production data, check the repeat rate of the cached query (Azure's example reads `sys.dm_exec_cached_plans` UseCounts) and the hit rate (Redis INFO `keyspace_hits`/`keyspace_misses`).
- **Not when:** Not caching static reference data is itself an antipattern (Azure No Caching): the rule is "cache with a policy and evidence", not "never cache". Azure says to instrument first to confirm the application is really CPU bound before caching computations, and warns that a cache can shift overload to the web front end. Cache size trades off against GC and tail latency (Discord, PE-05).
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** high · **Grade:** B
- **Source:** [No Caching antipattern](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/no-caching/) (Microsoft, 2017, updated 2026); [Why Discord is switching from Go to Rust](https://discord.com/blog/why-discord-is-switching-from-go-to-rust) (Howarth, Discord, 2020) · dossier: performance-review T04-F11; eval-v2-calibration E02-F01

### PE-15 — Bound CPU-heavy work reachable from untrusted input
- **Rule:** On request and event-loop threads, enforce a maximum input or body size before parsing, and replace regexes with super-linear backtracking. Even O(n) work can block a server: Node's guide measured JSON.parse of a 50 MB string at 1.3 s. A new or lower limit is a visible behaviour change: set it above the observed production maximum and document it. Report moving large computations to workers, a queue or chunks as a restructuring; do not apply it.
- **Detect:** eslint-plugin-regexp `no-super-linear-backtracking` and `no-super-linear-move`; the body-size limit configured on the HTTP framework, and whether someone raised it; `JSON.parse`/`json.loads` on raw request bodies with no size check; CPU-heavy handlers (image, crypto, compression, large sorts) with no worker offload; load tests with large payloads (proposed).
- **Not when:** Frameworks often have a default already (Express body-parser: `'100kb'`); verify before "adding" one. Static ReDoS detection "can only detect very simple cases", so a clean run proves nothing. The security lens covers the same inputs as an attack surface: emit one candidate.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [Don't Block the Event Loop (or the Worker Pool)](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop) (Node.js); [regexp/no-super-linear-backtracking](https://ota-meshi.github.io/eslint-plugin-regexp/rules/no-super-linear-backtracking.html) (eslint-plugin-regexp); [body-parser README](https://github.com/expressjs/body-parser) (Express project) · dossier: performance-review T04-F18

### PE-16 — No readability-costing micro-optimisation without a benchmark on a profiled hot path
- **Rule:** Prefer the idiomatic form. Flag changes whose only purpose is speed and that add complexity without a benchmark: manual unrolling, a cached array length (`for (let i=0, n=a.length; …)`), switch instead of polymorphism, bit tricks, hand-inlining, exceptions replaced by sentinels. Propose reverting existing micro-hacks that complicate the code and carry no benchmark, backed by a PE-17 A/B showing no regression. Check lint performance rules against the target runtime version.
- **Detect:** Diff and blame review; `rg -n '// faster|// optimization|# perf hack'`, then ask for the measurement (in autonomous mode, a question under Needs your decision, reporting RP-07); Ruff `target-version` against `PERF203` (enforced only below Python 3.11) and `PERF401` (its doc: "~10% faster on Python 3.11, and ~25% faster on Python 3.10").
- **Not when:** Measured compute kernels (games, codecs, numeric inner loops): Muratori reports 1.5x (switch) up to 20–25x (AVX) over virtual dispatch in a tight shape-area loop; where a profile shows such a kernel dominates, keep the less idiomatic form with a benchmark and a comment. Clippy `perf` lints are the counter-case: "usually easy to apply, and it is recommended to do so". Not every performance fix hurts readability: most fixes in Selakovic & Pradel change a few lines "without significantly affecting the complexity".
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B

### PE-17 — Prove every performance change with a same-machine A/B and a statistical comparison
- **Rule:** For every performance change, including reverting an old optimisation, measure both variants on the same machine and build type, with warm-up runs, at least 10 (ideally 20) repetitions per variant, the median or mean with spread or a confidence interval, and a statistical comparison (Mann-Whitney U or bootstrap) against a noise threshold declared in advance. Store the raw results with the change. Never re-run until a "significant" result appears. For a memory or growth fix (a PE-05 bound, or a cache removed under PE-14), the gate is a slowdown budget, not "any significant slowdown": state the budget in the item before measuring (the owner's figure when the repository states one, otherwise a proposed figure shown with the Phase 6 category batch, whose approval covers it), and revert only when the measured slowdown exceeds that budget by more than the declared noise threshold. A significant slowdown inside the budget is reported with its numbers, not reverted. A benchmark gate the project itself configures still decides as configured (invariant 4).
- **Detect:** Require attached raw data, for example `hyperfine --warmup 3 --export-json perf.json 'old' 'new'`; `go test -run '^$' -bench . -count 20` for both variants, then `benchstat old.txt new.txt`; `pytest --benchmark-autosave`, then `--benchmark-compare --benchmark-compare-fail=min:5%`; `cargo bench` (Criterion: bootstrap resampling, outliers kept, a noise band such as ±1% ignored); Vitest 5 `bench.compare()` with `writeResult`/`bench.from()`. Reject a single-run timing, "it felt faster", or a benchmark run only after the change.
- **Not when:** The Rust Performance Book: "Mediocre benchmarking is far better than no benchmarking"; full rigour may be unaffordable, but the direction and size of the effect must still exceed run-to-run noise. For service defect classes (PE-03, PE-11), before/after query counts or bytes transferred can suffice. For an asymptotic rewrite (PE-07, PE-08) whose outputs a PC-15 differential shows byte-identical, PE-09's verdicts are its measurement: `superlinear` at base, from counts or timings, and `not-superlinear` for the candidate from timings at the same sizes, since counts through the inputs miss work a rewrite does on a copy. The differential's corpus holds the repository's fixtures, at least 1,000 seeded generated inputs and the equality edge cases of the new index's key, so that PE-19's identity-versus-equality trap shows: for a JavaScript Set or Map, NaN (equal to itself there, never under `===`), missing (`undefined`, `null`) and duplicate keys, and object keys the old predicate compared by value. A same-machine timing with this rule's warm-up and repetitions, at the smallest and the largest input size the repository's tests, fixtures or docs show, then checks the constant factor against a slowdown budget stated in the item before measuring, as for a PE-05 bound; a slowdown beyond the budget by more than the declared noise threshold keeps the item report-only. A speedup figure in the report still needs the full comparison (pilot-auto-calibration A01-F13). Layout randomisation (Stabilizer) is research tooling, not standard practice.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [Producing Wrong Data Without Doing Anything Obviously Wrong!](https://users.cs.northwestern.edu/~robby/courses/322-2013-spring/mytkowicz-wrong-data.pdf) (Mytkowicz et al., ASPLOS 2009); [Stabilizer](https://people.cs.umass.edu/~emery/pubs/stabilizer-asplos13.pdf) (Curtsinger, Berger, ASPLOS 2013); [benchstat](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat) (Go Authors, 2026); [Criterion.rs: Analysis Process](https://bheisler.github.io/criterion.rs/book/analysis.html) (Criterion.rs); [hyperfine](https://github.com/sharkdp/hyperfine) (Peter, v1.20.0); [pytest-benchmark usage](https://pytest-benchmark.readthedocs.io/en/latest/usage.html) (Mărieș, 5.3.0); [Learning Performance-Improving Code Edits](https://arxiv.org/abs/2302.07867) (Shypula et al., ICLR 2024); [The Rust Performance Book: Benchmarking](https://nnethercote.github.io/perf-book/benchmarking.html) (Nethercote et al.); [Set](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Set) (MDN, 2026: "NaN is considered the same as NaN (even though NaN !== NaN)"; object keys "are compared by reference, not by value") · dossier: performance-review T04-F13, T04-F16; eval-v2-calibration E02-F01; pilot-auto-calibration A01-F13

### PE-18 — Check that a microbenchmark measures what it claims
- **Rule:** Before trusting any benchmark, existing or written for PE-17, confirm that the result is consumed (returned, sent to a Blackhole, passed to `black_box`, or run under Go 1.24+ `b.Loop`) so dead-code elimination cannot remove the work; inputs are not compile-time constants; setup sits outside the timed region; JIT tiers are warmed up; GC and allocation effects are considered; the build is a release or production build. While it runs, confirm the actual limiter with system tools ("active benchmarking"). Existing benchmark files are read-only: report their defects.
- **Detect:** Read the benchmark code for unused results, Go `b.N` loops with no sink, literal inputs, setup inside the timed loop, debug builds or `NODE_ENV` other than `production`, and implausible results (sub-nanosecond per operation). During runs (proposed): `perf stat`, `vmstat`, `iostat`.
- **Not when:** Application-level benchmarks avoid many microbenchmark artefacts but are slower and noisier; Grambow et al. find microbenchmarks can stand in for them only "if frequent false-positive alarms can be tolerated". For an agent-produced speedup, also check for special-casing of the benchmark input or harness: GSO added a "Hack Detector" against "deceptive optimizations (e.g., memoization, harness hijacking)" in November 2025.

### PE-19 — A performance fix must preserve behaviour
- **Rule:** Keep the full suite green and add a differential test comparing old and new output on representative and random inputs the new code has not seen (the old function as oracle, or property tests with Hypothesis or fast-check), so that input-specific memoisation or special-casing fails. Review the known traps: fail-fast `Promise.all`, stale cache reads, API contract changes from pagination or limits, unsafe autofixes, floating-point reassociation or fast-math, identity versus equality after a switch to Set or Map, and order changes from parallelisation. Never enable `-ffast-math`, `-Ofast` or an equivalent: GCC says it "can result in incorrect output" for code relying on exact IEEE or ISO math rules.
- **Detect:** Suite result before and after; the differential test; `rg -nE -- '-ffast-math|-Ofast|fast-math|unsafe-math'` in build files (an existing hit is reported, not changed); `ruff check --unsafe-fixes` only with review; an OpenAPI diff showing no response-contract change.
- **Not when:** Deliberate functional trade-offs (pagination, removing an expensive feature check) are not performance fixes: in Yang et al. the largest speedup (39x) came from removing a feature. Report them for owner sign-off (PE-12). A cap on a cache or history is not such a trade-off: it is a T1 behavioural memory fix applied under PE-05 with its own test, while removing a cache whose output stays byte-identical follows this rule as a structural change. Correctness and performance fixes can undo each other: Ruby's `reject!` was quadratic from 1.9.3 through 2.3 because of a correctness fix.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B

### PE-20 — Do not gate CI on tight wall-clock thresholds on shared runners
- **Rule:** Report CI benchmark jobs that fail on a small wall-clock percentage on shared runners. Recommend same-job relative A/B runs, dedicated or bare-metal runners, instruction-count metrics or confirmation reruns, with a threshold set above the measured noise. Replace a noisy gate rather than deleting it, because deletion removes protection. Bencher (a vendor) reports more than 30% variance on GitHub Actions runners against under 2% on bare metal; Mozilla waits for 12 further data points, uses thresholds of 0.25% (AWSY) to 2%, and still triages false alerts.
- **Detect:** Benchmark jobs in `.github/workflows` or `.gitlab-ci.yml` that run on shared runners (`runs-on: ubuntu-latest`) with small-percentage fail thresholds; the run-to-run coefficient of variation of an unchanged benchmark, compared with the threshold. Instruction-count tools: Cachegrind, Gungraun (formerly iai-callgrind).
- **Not when:** Instruction counts have lower variance but are not time: they miss cache, memory and I/O effects. With α = 0.05, about 5% of unchanged benchmarks show "significant" changes (benchstat). Which signal should gate CI is unresolved in the sources: report, do not auto-fix.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Continuous Benchmarking](https://bencher.dev/docs/explanation/continuous-benchmarking/) (Bencher, vendor); [Performance Sheriffing](https://firefox-source-docs.mozilla.org/testing/perfdocs/perf-sheriffing.html) (Mozilla); [benchstat](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat) (Go Authors, 2026) · dossier: performance-review T04-F15

### PE-21 — Judge service latency by percentiles under open-model load
- **Rule:** For services, accept a latency claim only from open-model (constant-arrival-rate) load that measures from the intended send time, recorded in HdrHistogram-style histograms, with p50, p95 and p99 plus throughput at several load steps, before and after, in the same environment. Averages are not evidence; a closed-loop tool without correction under-reports the tail (coordinated omission).
- **Detect:** Read load-test scripts and reports for closed-loop load (fixed connections, each waiting for its response) with no correction, mean-only reporting, and a single load level. Tools: k6 `constant-arrival-rate`, Gatling, HdrHistogram, APM percentiles. wrk2 explains coordinated omission, but its last commit is from 2019-09-24: prefer a maintained open-model tool for new work.
- **Not when:** Libraries and CLIs (use PE-17). Full load testing may be too heavy for a small project's pass; for the defect classes, before/after query counts or bytes transferred can be enough evidence.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [wrk2](https://github.com/giltene/wrk2) (Tene); [Chatty I/O antipattern, example diagnosis](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/chatty-io/) (Microsoft); [Performance testing and antipatterns](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/) (Microsoft, updated 2026); [Constant arrival rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/) (Grafana k6) · dossier: performance-review T04-F16

### PE-22 — Triage services at the resource level before choosing code targets
- **Rule:** For deployed services, check utilisation, saturation and errors of every resource (CPU, memory, disk, network, connection and thread pools, locks) in production telemetry before picking code targets, so the pass does not tune CPU code when a pool or a disk is the limit. When no telemetry exists, record that as a finding and limit the performance scope to static defect classes plus local benchmarks.
- **Detect:** A per-resource checklist table from APM or OS tools (vmstat, iostat, sar, pool metrics, database wait statistics).
- **Not when:** Libraries and CLIs. Resource metrics do not reveal algorithmic inefficiency in code that is not yet under load. Gregg's claim that USE "solves about 80% of server issues with 5% of the effort" is the author's own, not a study.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [The USE Method](https://www.brendangregg.com/usemethod.html) (Gregg); [Performance testing and antipatterns](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/) (Microsoft, updated 2026) · dossier: performance-review T04-F19

## False-positive exclusions

- Sync I/O at module top level, during startup, in CLI tools and in build scripts (PE-04).
- Unbounded caches, maps and queues in short-lived CLIs and scripts (PE-05, PE-06); `functools.cache` over a small, finite key space.
- N+1 patterns, loops and linear lookups whose n is tiny or bounded by design; judge n from the largest observed production size, not from fixtures (PE-03, PE-08, PE-09).
- An eager load that would pull a larger object graph than the lazy path it replaces (the Spree case): not an N+1 fix (PE-03).
- Sequential awaits that are dependent, rate-limited, ordered, transactional or hold a bounded resource (PE-10).
- Small, fixed reference tables without pagination (PE-12); internal jobs that must see every row (stream them, PE-11).
- Ruff `PERF401`–`PERF403` hits presented as quadratic defects; `PERF203` hits on target versions 3.11 or later (PE-07, PE-16).
- A "missing" request-body limit where the framework default applies (Express body-parser `'100kb'`) (PE-15).
- Non-thread-safe classes constructed per use, and database connections taken from a pool per use (PE-13).
- Clippy `perf` lint fixes, and measured compute kernels that carry a benchmark and a comment: not micro-hacks (PE-16).
- A hot frame in a CPU profile of a service that mostly waits: not evidence of the bottleneck (PE-02).
- A lower mean latency from a closed-loop load test, or a single-run timing: not an improvement (PE-17, PE-21).

## Evidence limits

- Yang et al. (ICSE 2018; 12 Rails apps): 64 fixes across 9 ORM anti-patterns gave a median 2x server-side speedup, and more than 78% of fixes changed under 5 lines. The 39x maximum came from removing a feature; the 40 fixes that changed neither display nor functionality averaged 2.2x (max 9.2x). N+1 appeared in 15 problematic actions and 9 issues; in Lobsters, eager loading merged 51 queries and cut load time from 1.10 s to 0.34 s. Missing pagination caused 15 of 34 non-scaling actions. The 4.17 s to 0.69 s average covers all 39 fixed actions, feature removal and pagination included.
- Chen et al. (ICSE 2014, abstract only): fixing detected ORM anti-patterns improved response time by up to 98%.
- Azure Architecture Center figures are lab load tests from pages first written in 2017 (Extraneous Fetching 2022), refreshed in 2026: batching 410 to 3,970 req/min (45 SELECTs, up to 1,000 simulated users); async I/O "nearly tenfold" throughput with a hard-coded 2-second sleep and up to 4,000 users; projection 100 to 350 req/s; database aggregation about 2,000 to more than 25,000 req/min and 280 KB to 53 bytes per transaction; per-request HttpClient failing at about 30 users against 500 req/s shared; caching 1 ms to 0.05 ms maximum response time. They show orders of magnitude, not field rates.
- Selakovic & Pradel (ICSE 2016; 98 fixed issues in 16 JavaScript projects; engines of about 2015): only 42.68% of optimisations improved performance consistently across all versions of V8 and SpiderMonkey.
- Measurement bias: Mytkowicz et al. (ASPLOS 2009) found none of 133 surveyed papers adequately considered it, and changing environment size moved run time "frequently by about 33% and once by almost 300%". Stabilizer (ASPLOS 2013; LLVM on SPEC CPU2006): link order moved performance by up to 57%, and -O3 over -O2 was indistinguishable from noise.
- Case studies, not rates: Toddler (ICSE 2013; Java) found 42 new bugs in six projects, of which developers had fixed 10 and confirmed 6 more; GitLab (2025) measured 6.12 ± 0.10x at 100,000 refs over 10 runs and cut a backup from 48 h to 41 min; GTA Online (2021) gained 69.4% load time; Dawson's WMI case (2019) spent 96.5% of CPU samples in one loop.
- wrk2's coordinated-omission example (tool author, 1.4 s server stall): corrected p99 about 1.27 s against an uncorrected 6.04 ms.
- AI-specific figures date quickly. EffiBench (NeurIPS 2024; 1,000 LeetCode problems): GPT-4 code averaged 3.12x the execution time of canonical solutions. EffiBench-X (2025): the best model reached about 62% of human efficiency. The GSO paper (2025) reported under 5% agent success, but the GSO leaderboard lists up to 47.06% Opt@1 on 2026-07-12 (single attempt reaching at least 95% of the human speedup and passing correctness tests). PIE (ICLR 2024; C++ under gem5, best of eight) reached a 6.86 mean speedup. Use these only as the reason to measure, never as a property of the target repository.
- Knuth (1974) was checked through two concordant secondary sources, not the original. Java string concatenation in loops (SonarSource S1643), Jin et al. (PLDI 2012) and Laaber et al. (EMSE 2019) were not verified. No source gives a principled small-n threshold or a validated CI benchmarking recipe for a solo developer without bare-metal runners.
- Own calibration, not an external study: the size-observable test for caches and histories, the configurable-cap tier, structural removal of a byte-identical cache and the slowdown budget (PE-01, PE-05, PE-14, PE-17, PE-19) come from the skill's paired evaluation v2. With the skill, 6 of 9 unbounded-cache and history instances were left unfixed, one after reverting a fix over a 7.6% text-report slowdown (p = 0.007); the baseline fixed all 9 with tests and no hidden regression (n = 3 runs per cell). The calibration is unmeasured until a v3 evaluation runs. (eval-v2-calibration E02-F01)
- Own calibration, not an external study: the doubling-run definition (operation counts, or medians of at least 10 timed repetitions; the verdict of the two largest steps) and the doubling verdicts as the measurement of an output-identical asymptotic rewrite (PE-09, PE-17, prioritization row 24) come from the autonomous pilot (n = 1), where one timing per size parked a quadratic loop that the v3 runs had measured and fixed in 3 of 3. They are unmeasured until the second autonomous pilot. (pilot-auto-calibration A01-F13)
