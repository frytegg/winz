# Lens: Dead code

> Find unused, unreachable, commented-out and test-only code, unused dependencies, stale flags and orphaned identifiers; grade how certain each one's deadness is and give it the tier that evidence allows.
> Read when: any source file, dependency manifest or feature-flag configuration is in scope (every language).

## Procedure

You are a fresh-context, read-only lens subagent with Read, Grep and Glob only (detection step 8). Never edit a file, never run a tool's fix mode, never delete anything. Your only output is your final message: candidates plus files_read.

1. Load the slice manifest the orchestrator gave you, `.harden/inventory.json` (languages, manifests, test globs, generated and vendor dirs), `.harden/config.json` (scope, `exclude_globs`) and the raw detector output in `.harden/tools/`, unless you are the unseeded pass, which reads no tool output and no prior findings (detection step 8). Note `base_sha`.
2. Decide the project shape before hunting exports: published library, application, or private monorepo analysed as a whole (DC-11, DC-12). List the build configurations that ship (DC-10).
3. Detector commands (run by the orchestrator in detection step 4; read their outputs from `.harden/tools/`). Each language present gets its detectors, in report mode only. The exact pinned commands live in the language files (lang-typescript.md, lang-python.md, lang-rust.md, lang-cpp.md, lang-go.md, lang-solidity.md). Flags passed on the command line are for detection only; the project's own tool configuration never changes.
   - TS/JS: tsc with `noUnusedLocals`, `noUnusedParameters`, `allowUnreachableCode: false` (TS6133, TS7027, TS7028); ESLint `no-unused-vars` or `@typescript-eslint/no-unused-vars`, `no-unreachable`; knip in default mode and with `--production` (add `--include-entry-exports` for applications); offline, when knip cannot run, `.harden/tools/ts-program.json` from `ts_program.py` (per-export `status`: `unreferenced`, `test-only`, `imported-only`, `same-file-only`, `referenced`, `public-api`, `not-analysed`; `entry_resolution`; `unreachable_production_files`; `dynamic_imports`; DC-02). Do not use depcheck, unimported or tsr (archived).
   - Python: Ruff F401, F841, ERA001; vulture (keep its confidence value); deadcode (Python) DC01–DC13 with `--dry` only; deptry DEP001–DEP004 inside the project venv.
   - Rust: rustc `dead_code`, `unused_variables`, `unreachable_code`, `unreachable_pub` (allow-by-default); clippy; cargo-shear, cargo-machete, cargo-udeps (nightly). Do not run cargo-machete `--with-metadata` in the working tree: it may modify Cargo.lock. Offline whole-program evidence (DC-02 E1): in a scratch worktree, demote each `unreachable_pub` item to `pub(crate)` and read the `dead_code` warnings of `cargo check --workspace --all-targets --all-features --offline` (DC-12, RS-13). The orchestrator does this in detection step 4, in a git worktree under the scratch_dir, only under the Phase 0 environment policy (build scripts run; DT-06), and removes the worktree afterwards; the demotion is never committed.
   - Go: `deadcode` with and without `-test`, `-whylive`; staticcheck U1000 (`-matrix` when build tags exist); gopls `unusedfunc`; `go mod tidy -diff`, never plain `go mod tidy`.
   - C/C++: `-Wall -Wextra` (`-Wunused-function`, `-Wunused-variable`, `-Wunused-parameter`); Clang `-Wunreachable-code`; cppcheck `--enable=unusedFunction` with `--cppcheck-build-dir`; clang-tidy `misc-unused-parameters`, `misc-include-cleaner`; IWYU; linker `--gc-sections --print-gc-sections`.
   - Solidity: Slither `dead-code`, `unused-state`; `slither-check-upgradeability` for proxies.
   - Java/Maven: `mvn dependency:analyze`, DepClean (dependencies only).
   - Where SonarQube is already configured: S1481, S1854, S1128, S1068, S1144, S1172, S125.
   The orchestrator saves every raw output with the tool version under `.harden/tools/`. A detector with no output file there is "not run": say so in `notes`, never treat it as clean (invariant 3).
4. Do the checks tools cannot: whole-repo text search with Grep (DC-08), dynamic-reference checklist (DC-09), constant guards and duplicated jumps (DC-07), commented-out code (DC-21), flag call sites (DC-22), removed schema identifiers (DC-23), env and config keys (DC-25), dynamic CSS classes (DC-26). The history facts of DC-17 and DC-18 come from `.harden/tools/dead-history.json` (`dead_history.py`: orphaning or introducing commit, later first-parent commits, explicit-removal text, unmerged refs, markers, future-work coverage, `wip`); read them from there, or record "git history not checked" in `notes`.
5. Classify each candidate (DC-01), give it an evidence level (DC-02), apply the exclusions below, and take tier, class and fix risk from the governing rule. A candidate that meets a T2 condition in any rule is T2.
6. Return candidates plus files_read as your final message (the orchestrator merges them into `.harden/candidates.json`; files_read lists every file and line range you read). Each candidate follows the findings schema (assets/findings.schema.json): `lens: "dead-code"`; `rule_ref` = `DC-NN` or `project:<tool>/<rule>`; `file` and `line` at `base_sha`; `tier`, `class`, `fix_risk`; `confidence` = `tool_high_precision` only for E0 compiler or linter diagnostics, `needs_review` for other tool output, `inference` for anything resting on reading alone (DC-30); verification raises commented-out code to at least `tool_high_precision` through DT-27's deterministic check (eval-v1-calibration E01-F06); `evidence` items of kind `tool` (command, rule id, version), `source` (file:line of each reference found or ruled out) and `git` (orphaning commit); `verified: false`; `status: "candidate"`. Put the evidence class, E-level and the missing evidence ("flag state unknown", "external consumers unknown") in `notes`.
7. For test-only code (DC-14), name every test case that would be deleted (file, test name and the number of cases per file) so the orchestrator can put the DC-15 deletion to the user and record each approved file with `run_state.py allow-test-deletion <path> --cases <n> --reason <finding id>`.
8. Group candidates in removal order (files, exports and symbols, dependencies) and state that later passes will surface more (DC-29). Stop there.

## Rules

### DC-01 — A detector finding is a candidate, never a verdict
- **Rule:** Put every candidate in one evidence class before acting: (1) compiler-provable (unreachable statement, unused local, import or private member, dead store); (2) statically unreferenced but externally visible (export, public method, file, dependency); (3) reachable but not exercised at runtime; (4) obsolete by intent (retired flag, finished migration); (5) commented-out code. Record tool, version, rule id and confidence; a confidence label alone never authorises a deletion, and an unclassified candidate stays T2.
- **Detect:** Class 1: compiler and linter diagnostics (DC-03, DC-07). Class 2: knip, vulture below 100%, Go `deadcode`, deptry DEP002, cargo-machete or cargo-shear. Class 3: runtime data only. Class 4: flag state, migration records, git history. Class 5: DC-21.
- **Not when:** Classes blur: unreachable code may be a bug (DC-07); runtime-unused code may be seasonal or exception handling (DC-16). Outside class 1, measured precision is modest: 24 of 76 UCDetector dead-class warnings were truly unnecessary (32%; Java, recommender-preselected sample, TOSEM 2020); 9 of 27 unused but maintained methods were confirmed unnecessary and 4 more already gone (one industrial system, ICSE 2012).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Is Static Analysis Able to Identify Unnecessary Source Code?](https://www.se.cs.uni-saarland.de/publications/docs/HNR+19.pdf) (Haas et al., 2020); [How Much Does Unused Code Matter for Maintenance?](https://teamscale.com/publications/2012-how-much-does-unused-code-matter-for-maintenance.pdf) (Eder et al., 2012); [deadcode command](https://pkg.go.dev/golang.org/x/tools/cmd/deadcode) (Go team, 2026) · dossier: dead-code-evidence T06-F01, T06-F04; dead-code-certainty G102-F02

### DC-02 — Map evidence level to tier
- **Rule:** E0 = proven unused by compiler or language; E1 = production-mode whole-program tool finding plus a clean whole-repo text search, with build, tests and app start green at apply time; E2 = E1 plus corroboration from git history or the owner; E3 = runtime evidence over a full business cycle. The whole-program finding comes from the language's dedicated tool (Knip in production mode, Go `deadcode`) or, when that tool cannot run (not installed and the Phase 0 network decision forbids the download), from the project's own compiler run offline over every project configuration. For TypeScript and JavaScript that is `ts_program.py` status `unreferenced` (no reference of any kind outside the declaration, imports and re-exports included) or `test-only`, and it counts only when its `entry_resolution` is `complete` or `none` and the export has an identifier name (default exports and CommonJS exports are `not-analysed`). An export of a file that no production module imports (`unreachable_production_files`) counts only as a DC-13 unused-file candidate: DC-13's per-file search is clean, the file lies in no framework convention directory, and each `dynamic_imports` entry is named in `notes` with the reason it cannot load the file (DC-09). For Rust it is rustc `dead_code` on the item after DC-12's demotion to `pub(crate)` in a scratch worktree (RS-13), run under the Phase 0 environment policy because `cargo check` runs build scripts. Either counts only when every in-scope file of the language sits in an analysed program, or when the whole-repo search finds the name in none of the files outside them. A text census or a model's reading never reaches E1 (DC-30). Python has no offline equivalent in its standard library, so without vulture or deadcode already in the project environment its candidates stay below E1. Map E0 in the DC-03 classes to T0; E1 or E2 with every veto passed to T1, one commit per finding class; everything else (public API, flags, unknown purpose, any known false-positive class, reachable code without E3) to T2.
- **Detect:** Record class, E-level, tool and rule id, grep result and git result per candidate; the apply phase rejects a deletion commit that contains a T2 candidate. Offline TypeScript evidence: `.harden/tools/ts-program.json` (`python "${CLAUDE_SKILL_DIR}/scripts/ts_program.py"`), its per-export `status` and its `files_outside_programs`; offline Rust evidence: the `cargo check --workspace --all-targets --all-features --offline` log of the scratch worktree where the item was demoted to `pub(crate)`, naming it under `dead_code`. Cite either as a `tool` evidence item that the verifier re-runs (for TypeScript, `ts_program.py --symbol NAME@PATH --out .harden/tools/ts-program-<id>.json`, which leaves the full run's file in place; DT-28).
- **Not when:** The matrix is a synthesis: no study validates it end to end and no source gives a numeric certainty threshold. Projects with runtime logs (Google Sensenmann, Meta SCARF) justify more aggressive deletion, and a human owner with context can promote items out of T2. The compiler's reference search sees static imports, re-exports and uses inside the analysed programs only: names built from strings, non-literal dynamic imports and framework conventions stay DC-08 and DC-09's job (Knip's plugins model some of them; `ts_program.py` models none), and an export a package entry exposes is public API (DC-11). In the autonomous pilot, D01 and D02 stayed T2 because Knip could not be downloaded and because DC-17 read the whole three-week-old history as recent, although the project's own TypeScript 5.9.3 answered the reference question offline (pilot-auto-calibration A01-F16, n = 1).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [Dead Code Removal at Meta](https://users.encs.concordia.ca/~pcr/paper/Shackleton2023FSE-industry-preprint.pdf) (Shackleton et al., 2023); [A Multi-Study Investigation Into Dead Code](https://www.cs.wm.edu/~denys/pubs/TSE'18-DeadCode.pdf) (Romano et al., 2020); [Is Static Analysis Able to Identify Unnecessary Source Code?](https://www.se.cs.uni-saarland.de/publications/docs/HNR+19.pdf) (Haas et al., 2020); [Using the Language Service API](https://github.com/microsoft/TypeScript/wiki/Using-the-Language-Service-API) (Microsoft, 2020); [typescript.d.ts 5.9.3](https://cdn.jsdelivr.net/npm/typescript@5.9.3/lib/typescript.d.ts) (Microsoft, 2025); [Entry files](https://knip.dev/explanations/entry-files) (Knip, 2026) · dossier: dead-code-certainty G102-F01; dead-code-evidence T06-F21; pilot-auto-calibration A01-F16

### DC-03 — Remove compiler-proven unused locals, imports and unexported items, minus side-effect cases
- **Rule:** Treat as T0 only compiler-proven unused locals, imports and unexported (private or static) items, and only after the DC-04 exclusions (the same scope as protocol-change PC-10(d)). The proofs: tsc `noUnusedLocals` (TS6133), rustc `dead_code` and `unused_variables` (unexported items), the Go compiler's unused import and variable errors, gcc/clang `-Wunused-function` (static functions) and `-Wunused-variable`, Ruff F401 outside `__init__.py`. When an unused binding's initializer is a call, drop the binding and keep the call.
- **Detect:** The diagnostics above; ESLint `no-unused-vars` or `@typescript-eslint/no-unused-vars` (base rule off); ast-grep `$X = $CALL($$$)` to find initializers whose call must stay.
- **Not when:** vulture's 100% tier means "guaranteed to be unused within the analyzed files", not a compiler proof: its arguments go to DC-06, its unreachable code to DC-07. Unused parameters are never T0. A proof holds for the configuration built (DC-10), and compiler lints can regress (rustc 1.80 false `dead_code`, issue #128272), so gates still run after each T0 commit. Ruff F841 is proven but its fix is unsafe-labelled (DC-05).
- **Tier:** T0 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [rustc lint listing: dead_code](https://doc.rust-lang.org/rustc/lints/listing/warn-by-default.html) (Rust Project, 2026); [TSConfig noUnusedLocals](https://www.typescriptlang.org/tsconfig/#noUnusedLocals) (Microsoft, 2026); [Go FAQ](https://go.dev/doc/faq) (Go project, 2026); [Ruff F401](https://docs.astral.sh/ruff/rules/unused-import/) (Astral, 2026); [GCC Warning Options](https://gcc.gnu.org/onlinedocs/gcc/Warning-Options.html) (GNU, 2026) · dossier: dead-code-evidence T06-F15; dead-code-certainty G102-F03; dead-code-tools T07-F03

### DC-04 — Never auto-remove code that exists for its side effect
- **Rule:** Exclude from T0 and keep: bare imports (`import './polyfill'`, CSS imports, `import 'reflect-metadata'`, Django `from . import signals` inside `ready()`); re-exports in Python `__init__.py`; guard and RAII bindings (`let _guard = m.lock()`, `using`, `with`); Rust fields read only through `Drop` or kept for auto traits (Send, Sync, Unpin); C++ static objects whose constructors register something; stores that zero secrets (CWE-14: optimisers remove them as dead stores). Import removal, reordering or value-to-type-only conversion is never T0 (T1 at most, as in protocol-change PC-10(a)) in entry-point or side-effect modules: `__init__.py`, `index.ts`/`index.js`, `lib.rs`, `mod.rs`, any bare `import 'x'`, and TypeScript compiled with `experimentalDecorators` plus `emitDecoratorMetadata`. Where a re-export is intended, propose making it explicit (`from m import x as x` or `__all__`) as T1.
- **Detect:** Ruff F401 hits in `__init__.py`; bare first-party `import pkg.module`; `grep -nE "^import ['\"]"`; package.json `"sideEffects"`; `impl Drop` on field types; globals with non-trivial constructors; flag `__init__.py`, `index.(ts|js)`, `lib.rs` and `mod.rs` among the files an import change touches; `jq '.compilerOptions|{experimentalDecorators,emitDecoratorMetadata}' tsconfig.json`. After any import change, compare the production build's emitted CSS and JS asset list.
- **Not when:** Truly unused imports with no side effect, outside the entry-point and side-effect modules above, are T0 under DC-03. Never propose `"sideEffects": false` without listing the CSS and polyfill files. Secret zeroing needs a primitive the compiler cannot elide (`explicit_bzero`, `SecureZeroMemory`, the `zeroize` crate).
- **Tier:** T1 · **Class:** structural · **Fix risk:** high · **Grade:** A
- **Source:** [Ruff F401](https://docs.astral.sh/ruff/rules/unused-import/) (Astral, 2026); [Tree Shaking](https://webpack.js.org/guides/tree-shaking/) (webpack, 2026); [Django Signals](https://docs.djangoproject.com/en/5.2/topics/signals/) (DSF, 2025); [CWE-14](https://cwe.mitre.org/data/definitions/14.html) (MITRE, v4.20); [consistent-type-imports](https://typescript-eslint.io/rules/consistent-type-imports/) (typescript-eslint, 2026) · dossier: dead-code-tools T07-F06; dead-code-evidence T06-F15; dead-code-certainty G102-F03; autofix-trust G105-F09

### DC-05 — Every autofix other than DC-03's needs a reviewed diff
- **Rule:** Start from a clean tree (`git status --porcelain` prints nothing). Apply as T1 with a reviewed diff: Ruff F841 (unsafe-labelled because it may delete attached comments; never pass `--unsafe-fixes` unreviewed), Knip `--fix` one fix type per commit (dependencies, exports, types; files last, only with `--allow-remove-files`), deadcode (Python) `--fix` after `--dry`, `cargo shear --fix`, IWYU `fix_includes.py`, `go mod tidy` after `-diff`.
- **Detect:** The fix-safety labels in each tool's docs; `git diff --stat` per fix type.
- **Not when:** Knip removes only the `export` keyword and leaves the now-local code; re-run the local linters afterwards (DC-12). After IWYU, restore `// IWYU pragma: keep` lines, delete unneeded additions, fix forward declarations, replace private headers (`<bits/stl_vector.h>` with `<vector>`) and rebuild every configuration.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [Knip Auto-fix](https://knip.dev/features/auto-fix) (Knip, 2026); [Ruff F841](https://docs.astral.sh/ruff/rules/unused-variable/) (Astral, 2026); [include-what-you-use README](https://github.com/include-what-you-use/include-what-you-use) (IWYU project, 2026); [deadcode (Python)](https://github.com/albertas/deadcode) (albertas, 2026) · dossier: dead-code-tools T07-F21, T07-F11; dead-code-evidence T06-F18

### DC-06 — Remove unused parameters only from private functions; rename fixed-signature ones
- **Rule:** Keep parameters of overrides, interface implementations, callbacks, framework hooks, virtual functions and exported or public functions; mark them unused instead (`_name`, `[[maybe_unused]]`, a commented-out name in C++). Remove one only when every caller is private and visible (clang-tidy removes it only "if all callers of the function are in the same translation unit").
- **Detect:** tsc `noUnusedParameters`; ESLint `no-unused-vars` `args` (default `after-used`); rustc `unused_variables`; `-Wextra` `-Wunused-parameter`; clang-tidy `misc-unused-parameters` (`IgnoreVirtual`); Sonar S1172; vulture 100% argument findings. Per hit, look for non-call references (passed as a callback) and framework registration.
- **Not when:** Express error middleware needs all four arguments to be recognised. Removing a parameter silently shifts positional arguments in dynamic languages. An unused parameter can be a bug (it should have been used); report it like DC-07.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [no-unused-vars](https://eslint.org/docs/latest/rules/no-unused-vars) (ESLint, 2026); [TSConfig noUnusedParameters](https://www.typescriptlang.org/tsconfig/#noUnusedParameters) (Microsoft, 2026); [Using middleware](https://expressjs.com/en/guide/using-middleware.html) (Express); [misc-unused-parameters](https://clang.llvm.org/extra/clang-tidy/checks/misc/unused-parameters.html) (LLVM, 2026) · dossier: dead-code-evidence T06-F16; dead-code-tools T07-F10, T07-F05

### DC-07 — Treat unreachable code as a possible defect before deleting it
- **Rule:** For each unreachable block, establish whether it was meant to run: an early return or `goto`, an always-true or always-false condition, a duplicated jump, a wrong constant. If it was meant to run, report a defect (restoring it is a behavioural fix for the owner); delete it only when history shows the intent is obsolete. Keep resilience code such as an enum-exhaustive `default` (CERT MSC12-EX1) and exhaustiveness guards (`assertNever`, `unreachable!()`).
- **Detect:** tsc `allowUnreachableCode: false` (TS7027, syntactic only); ESLint `no-unreachable`; rustc `unreachable_code`; Clang `-Wunreachable-code` (not in `-Wall`; GCC documents no working equivalent); vulture 100% unreachable; deadcode (Python) DC13; grep `if (false)`, `if False:`, `if 0`, `#if 0` and consecutive identical `goto`; `git log -L` to see when reachability was lost.
- **Not when:** Never delete an unreachable `yield`: removing it turns an async generator into a coroutine (vulture #422). `#ifdef`-disabled code is exempt (MSC12-EX3, DC-10). Clang's warning is noisy in generated code, macros and platform `#ifdef`s. Apple's 2014 "goto fail" duplicated jump made signature verification unreachable; deleting the dead check would have hidden it (inference, not measured).
- **Tier:** T1 · **Class:** structural · **Fix risk:** high · **Grade:** A
- **Source:** [MSC12-C](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/recommendations/miscellaneous-msc/msc12-c) (SEI CERT, 2016); [Apple's SSL/TLS bug](https://www.imperialviolet.org/2014/02/22/applebug.html) (Langley, 2014); [Clang Diagnostics Reference](https://clang.llvm.org/docs/DiagnosticsReference.html) (LLVM, 2026); [Bug 1235717](https://bugzilla.mozilla.org/show_bug.cgi?id=1235717) (Mozilla, 2016); [vulture #422](https://github.com/jendrikseipp/vulture/issues/422) (2026) · dossier: dead-code-evidence T06-F02; dead-code-tools T07-F10, T07-F18; dead-code-certainty G102-F03

### DC-08 — Veto any deletion above E0 with a whole-repo text search
- **Rule:** Search every tracked file (config, templates, SQL and migrations, CI, Dockerfiles, docs, scripts, fixtures) for the symbol, its snake, kebab and camel variants, the file basename, and any route, CLI, event or package name. A hit outside the definition and the tests being deleted moves the item to T2 until explained; if external consumers exist and cannot be searched, note "external consumers unknown" and keep it at T2. A clean search is necessary, never sufficient.
- **Detect:** `git grep -n -I -w` (or `rg -n -w --hidden -g '!.git'`) per variant, excluding the defining file; search string-building prefixes (concatenation, f-strings, template literals); for HTTP handlers, route strings and client code.
- **Not when:** Generic names (`get`, `run`) give false "alive" hits; accept that such items stay. Text search cannot see names held in databases, remote config or other repositories (DC-09, DC-25): a "truly unused" function called through a string path in a config file broke an admin tool (Reddit, 2025).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Automating dead code cleanup](https://engineering.fb.com/2023/10/24/data-infrastructure/automating-dead-code-cleanup/) (Meta, 2023); [Answer by piwi](https://softwareengineering.stackexchange.com/a/343657) (SE, 2017); [Ever removed "unused" code](https://www.reddit.com/r/learnprogramming/comments/1lbuach/ever_removed_unused_code_and_instantly_took_down/) (Reddit, 2025) · dossier: dead-code-evidence T06-F06; dead-code-tools T07-F13; dead-code-certainty G102-F04

### DC-09 — Run the dynamic-reference checklist before deleting any symbol, file or class
- **Rule:** Search the candidate's module and its importers for reflection, dependency injection and container registration, serialisation, plugin registries, framework decorators and conventions, and string-built names. Any hit keeps the item at T2; the exclusions list below gives the full set of classes.
- **Detect:** Python `getattr(`, `setattr(`, `importlib.import_module`, `__import__(`, `globals()[`, `entry_points`, route/receiver/task/fixture/click decorators; JS/TS `eval(`, `new Function(`, non-literal `import(`/`require(`, `obj[name](`; Java/Kotlin `Class.forName`, `getDeclaredMethod`, `@Autowired`, `@Inject`, `@Bean`, `@Component`, `@Scheduled`, `@EventListener`, `@JsonProperty`, `ServiceLoader`; C# `Activator.CreateInstance`, `Type.GetType(`, `DynamicDependency`; Go `reflect.`, `//go:linkname`, `plugin.Open`; manifests: routes, DI modules, pyproject entry points, package.json `bin`/`exports`, cron and serverless definitions, R8/ProGuard keep files.
- **Not when:** A tool that models the mechanism (a configured Knip plugin, a vulture whitelist) clears that class; deletion is then possible at E2. Go `deadcode` handles reflection and interface calls soundly but not `//go:linkname` or assembly. Meta runs over 300 dynamic-usage pattern detectors; in a Java debloater benchmark, dynamic class loading made every evaluated tool unsound (2025 preprint).
- **Tier:** T1 · **Class:** structural · **Fix risk:** high · **Grade:** A
- **Source:** [Is Static Analysis Able to Identify Unnecessary Source Code?](https://www.se.cs.uni-saarland.de/publications/docs/HNR+19.pdf) (Haas et al., 2020); [Dead Code Removal at Meta](https://users.encs.concordia.ca/~pcr/paper/Shackleton2023FSE-industry-preprint.pdf) (Shackleton et al., 2023); [Prepare .NET libraries for trimming](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/prepare-libraries-for-trimming) (Microsoft, 2026); [Add keep rules](https://developer.android.com/topic/performance/app-optimization/add-keep-rules) (Android, 2026); [Deblometer](https://arxiv.org/abs/2510.20679) (Klauke et al., 2025); [Finding unreachable functions with deadcode](https://go.dev/blog/deadcode) (Donovan, 2023) · dossier: dead-code-evidence T06-F05; dead-code-certainty G102-F05, G102-F21; dead-code-tools T07-F13, T07-F08

### DC-10 — Declare code dead only if it is dead in every shipped build configuration
- **Rule:** List the configurations (OS and architecture, build tags, Cargo features, `#ifdef` macros, target frameworks, dev/prod and SSR/client switches), run each analyzer once per configuration and keep only the intersection of the dead sets.
- **Detect:** Search `//go:build`, `#if`/`#ifdef`, `#[cfg(`, `cfg!(`, `process.env.NODE_ENV`, `import.meta.env`, `__DEV__`, `sys.platform`, `RuntimeInformation.IsOSPlatform`; staticcheck `-matrix`/`-merge`; `GOOS=… deadcode -tags=…`; `cargo check` per feature set; `tsc -p` per tsconfig; `dotnet build` per target framework; C/C++ builds per platform with warnings on.
- **Not when:** A single-target app may ship one configuration; confirm that before skipping runs. A configuration nobody builds any more is itself a candidate (report it). cargo-udeps does not account for build scripts or feature flags.
- **Tier:** T1 · **Class:** structural · **Fix risk:** high · **Grade:** A
- **Source:** [deadcode command](https://pkg.go.dev/golang.org/x/tools/cmd/deadcode) (Go team, 2026); [Build tags](https://staticcheck.dev/docs/running-staticcheck/cli/build-tags/) (Staticcheck, 2026); [go-tools #983](https://github.com/dominikh/go-tools/issues/983) (2021); [MSC12-C](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/recommendations/miscellaneous-msc/msc12-c) (SEI CERT, 2016) · dossier: dead-code-evidence T06-F19; dead-code-tools T07-F09

### DC-11 — Do not delete a library's unused public API; report it for deprecation
- **Rule:** Decide first whether the project is consumed externally. If it is, unused exported or public items are API, not dead code: report them (T2) with a deprecation recommendation (JSDoc `@deprecated`, Python `DeprecationWarning`, Java `@Deprecated(forRemoval=true)`, Rust `#[deprecated]`, C# `[Obsolete]`). Removal belongs in a major release after at least one minor release that carries the deprecation (SemVer).
- **Detect:** package.json `name` without `private: true`, `main`/`exports`/`types`/`bin`; Cargo `[lib]`; importable Go packages; pyproject publishing config; Maven, Gradle or NuGet publication; OpenAPI, proto and GraphQL schemas; public routes, CLI flags, config schemas. Tool defaults encode this: Knip skips entry-file exports, Staticcheck U1000 treats every exported identifier as used (since 2020.2), rustc `dead_code` covers only unexported items, and Go `deadcode` run on a library lists its API as unreachable (golang/go#66073).
- **Not when:** A private, self-contained application, or a monorepo whose consumers are all analysed together (Knip workspaces), treats internal packages as application code (DC-12). Public API that only tests exercise may reveal test gaps rather than dead code (Go `deadcode -test` doc).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [Semantic Versioning 2.0.0](https://semver.org/) (Preston-Werner); [JEP 277](https://openjdk.org/jeps/277) (OpenJDK, 2017); [Knip configuration](https://knip.dev/reference/configuration) (Knip, 2026); [Staticcheck 2020.2](https://staticcheck.dev/changes/2020.2/) (Honnef, 2020); [golang/go#66073](https://github.com/golang/go/issues/66073) (2024) · dossier: dead-code-evidence T06-F07; dead-code-tools T07-F12; dead-code-certainty G102-F10

### DC-12 — In an application, un-export first and delete only what the compiler then proves unused
- **Rule:** For an application or binary crate, reduce visibility first (Knip `--fix-type exports` removes the `export` keyword; Rust `#![warn(unreachable_pub)]`, then `pub(crate)`), let the compiler prove the now-local symbol unused, and delete it in a separate commit.
- **Detect:** `knip --include-entry-exports` for self-contained apps; rustc `unreachable_pub` (allow-by-default); then the DC-03 diagnostics.
- **Not when:** Deep-path or dynamic importers break when a symbol is un-exported. Knip's fix list also removes unused enum and namespace members outright, which is a deletion, not an un-export. In library crates `pub` items are API (DC-11).
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [Knip Auto-fix](https://knip.dev/features/auto-fix) (Knip, 2026); [rustc allowed-by-default lints](https://doc.rust-lang.org/rustc/lints/listing/allowed-by-default.html) (Rust Project, 2026); [Knip: Resolve reported issues](https://knip.dev/guides/handling-issues) (Knip, 2026) · dossier: dead-code-certainty G102-F10; dead-code-tools T07-F07, T07-F12

### DC-13 — Delete unused files only after the tool's configuration is credible
- **Rule:** Never act on files flagged by a first, unconfigured run. Resolve configuration hints (entry and project patterns, path aliases, plugins) and generate generated files first; remaining unused files are T1 in their own reviewed commit, while files in directories a framework loads by convention (routes/pages, migrations, models, fixtures, `__mocks__`) stay T2.
- **Detect:** `knip --files` once no configuration hints remain and after a generate or build step; per file `git grep -n -e <basename> -e <relative-path>` and a check against convention globs; cargo-shear also reports unlinked `.rs` files.
- **Not when:** Knip's common causes of false "unused file" reports: missing generated files, dynamic import specifiers, unsupported script arguments, missing or incomplete plugins, auto-mocking or auto-imports. No independent measurement of Knip's file-level precision exists.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [Knip: Resolve reported issues](https://knip.dev/guides/handling-issues) (Knip, 2026); [Knip Auto-fix](https://knip.dev/features/auto-fix) (Knip, 2026); [cargo-shear README](https://github.com/Boshen/cargo-shear) (Boshen, 2026) · dossier: dead-code-certainty G102-F11; dead-code-evidence T06-F18; dead-code-tools T07-F01

### DC-14 — Tests are not a liveness signal; find test-only code with a production-mode pass
- **Rule:** Run a production-only reachability pass that excludes tests, stories, mocks and dev tooling, and diff it against the default pass. Code reachable only from tests is dead production code that shares its fate with the tests that exist only for it (removed under DC-15). Keep tagged test seams.
- **Detect:** `knip` vs `knip --production` (production entries marked `!`; `--strict` implies `--production`); `deadcode ./...` vs `deadcode -test ./...`; Python: `vulture src/` vs `vulture src/ tests/`; a build graph without test targets. Exclude Knip `@internal`, Guava `@VisibleForTesting`, test-only naming conventions and test-support directories (builders, fakes).
- **Not when:** In a library, public API exercised only by tests may be used externally (DC-11). AndroidX `@VisibleForTesting` only marks relaxed visibility, so the element may still have production callers. Some test-only code pins an API contract meant for future use.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [Knip Production Mode](https://knip.dev/features/production-mode) (Knip, 2026); [Sensenmann: Code Deletion at Scale](https://testing.googleblog.com/2023/04/sensenmann-code-deletion-at-scale.html) (Norman, Google, 2023); [Knip JSDoc & TSDoc tags](https://knip.dev/reference/jsdoc-tsdoc-tags) (Knip, 2026); [VisibleForTesting](https://guava.dev/releases/snapshot-jre/api/docs/com/google/common/annotations/VisibleForTesting.html) (Google, 2026) · dossier: dead-code-tools T07-F04; dead-code-evidence T06-F08; dead-code-certainty G102-F06

### DC-15 — The only permitted test deletion: tests of symbols deleted in the same dead-code commit
- **Rule:** Tests are read-only by default (agents cheat mainly by modifying tests: over 79% of cheating by Claude models and Qwen3-Coder on deliberately impossible tasks, ImpossibleBench 2025): no test file deleted or renamed, no test case deleted or skipped, no assertion changed, no skip/xfail/only marker added. Test deletion happens only in the `refactor(dead-code):` commit that deletes the production symbols the deleted test cases reference (G102-F14 TE-2), and only in test files the user approved and the orchestrator recorded with `run_state.py allow-test-deletion <path> --cases <n> --reason <finding id>`. There, a test case may be deleted only if it references at least one symbol deleted in that commit; import lines that refer only to deleted symbols may go, and everything else stays byte-identical, so the change to each file is deletion-only. Every surviving production line a deleted test covered must stay covered (per-test contexts), and where mutation testing exists no mutant in those lines may go from killed to survived; otherwise keep the test and demote the deletion to T2. Deleting a test for any other reason stays the owner's action (T2, TQ-24).
- **Detect:** `git diff --cached --name-status -M --diff-filter=DMR -- <test globs>` outside a `refactor(dead-code):` commit, or on a path not recorded with `allow-test-deletion`, is a violation; `diff_guard.py` (PC-06) and `git diff --cached --numstat -- <path>` (0 added lines) show that each recorded file's change is deletion-only; `git show HEAD:path` for the pre-image; unchanged assertion-node counts (ast-grep, tree-sitter); pytest-cov `pytest --cov --cov-context=test` (or coverage.py `[run] dynamic_context = test_function`), then `coverage json --show-contexts`; mutation runs with the production files passed explicitly (`cargo mutants --file`, `mutmut run --paths-to-mutate`, `stryker run --incremental`).
- **Not when:** Table-driven Go tests, parametrised pytest and snapshot files do not map to one AST node per case: treat each row or snapshot as a case, or fall back to T2. Per-test line attribution for JS, Go and Rust was not verified. Coverage alone is not enough: line-coverage-adequate greedy minimisation that removed about 70% of tests lost about 12.5% of fault detection on average (3.5–21%; 7 Java suites, SWQD 2020). cargo-mutants' in-diff mode runs no mutants for a test-only diff.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** C
- **Source:** [ImpossibleBench](https://arxiv.org/abs/2510.20270) (Zhong et al., 2025); [An Evaluation of Test Suite Minimization Techniques](https://teamscale.com/hubfs/26978363/Publications/2020-test-suite-minimization-swqd.pdf) (Noemmer, Haas, 2020); [Piranha](https://manu.sridharan.net/files/ICSE20-SEIP-Piranha.pdf) (Ramanathan et al., 2020); [Coverage.py contexts](https://coverage.readthedocs.io/en/latest/contexts.html) (Batchelder, 2026); [cargo-mutants in-diff](https://mutants.rs/in-diff.html) (2026) · dossier: dead-code-certainty G102-F14, G102-F15

### DC-16 — Use execution evidence in one direction only
- **Rule:** A covered line, smoke-run hit or log entry proves code is live and vetoes deletion; no hit never proves it dead. Reachable-but-suspected-unused code needs runtime evidence over a window covering every business cycle (month, quarter and year ends, DST changes, leap day, DR drills); without telemetry, as in most finished projects, report it (T2). Uncovered error-handling, recovery, failover, migration, fallback, retry, admin, kill-switch and scheduled-job paths always stay T2.
- **Detect:** Coverage with per-test contexts over unit, integration and smoke suites (coverage.py `dynamic_context = test_function`, `go test -coverprofile`, c8/istanbul); any covered line marks the candidate live. Grep uncovered candidates for `catch|except|rescue|recover|fallback|retry|migrat|rollback|cron|schedule|yearly|monthly` and paths such as recovery, failover, `*_backup*`.
- **Not when:** Dynamic debloaters removed up to 94% of code that should be retained, error handling above all (11 C programs, program specialisation, 2026 preprint). Study windows were long: 2 years and 19 versions (Eder), 6–16 months covering year closing (Haas). With binary-run logs in a high-churn monorepo, Googlers found "dead for six months" reliable (Sensenmann thread).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** B
- **Source:** [Revisiting Code Debloating with Ground Truth-based Evaluation](https://arxiv.org/abs/2604.17717) (Bilal et al., 2026); [Is Static Analysis Able to Identify Unnecessary Source Code?](https://www.se.cs.uni-saarland.de/publications/docs/HNR+19.pdf) (Haas et al., 2020); [Answer by 9000](https://softwareengineering.stackexchange.com/a/343663) (SE, 2017); [HN kortilla](https://news.ycombinator.com/item?id=35759063) (2023) · dossier: dead-code-certainty G102-F07; dead-code-evidence T06-F09; dead-code-tools T07-F14

### DC-17 — Use git history as context and veto, never as proof of deadness
- **Rule:** Work in progress stays T2. Judge it from the commit history of the base branch, never from calendar time or the repository's age. The event is the commit that removed the last reference outside the defining file (the orphaning commit) or, for code never referenced outside its file, the commit that introduced it. The code is work in progress when any of these holds: the event is the base commit itself (no later first-parent commit); a branch, tag or stash that the base does not contain still references it; a work-in-progress marker (`TODO`, `FIXME`, `WIP`, "not yet used", "will be used", "placeholder") sits in or just above its definition or in the introducing commit's message; its file matches the owner's declared future work; it was never referenced outside its file and the owner declared no future work (a profile `future_work` that is absent or empty counts as no answer, because the profile template pre-fills `[]`; only a non-empty list or a live answer with `--interactive` is one); or the history walk was truncated or named no event. Otherwise it is not work in progress, however young the repository. If the orphaning commit's message names the removal (remove, delete, drop, deprecate, clean up, retire, obsolete) or the retired feature, and nothing references the code since, raise it from E1 to E2. "Not touched in a long time" is never a reason to delete on its own.
- **Detect:** `python "${CLAUDE_SKILL_DIR}/scripts/dead_history.py" --symbols-from .harden/tools/ts-program.json --out .harden/tools/dead-history.json` (or `NAME@PATH` arguments for other languages): it runs `git log --first-parent -S<symbol>`, counts `git grep -c -w -F` occurrences outside the defining file at each candidate commit and its parent, `git rev-list --count --first-parent <event>..<base>`, the unmerged-ref check, the marker search and the future-work match, and prints `wip` with its reasons; `git log -1 --format=%ad -- <file>` as context only.
- **Not when:** Stability predicts deletion poorly: a stability-plus-centrality recommender reached 2.7% average precision against historical cleanups (Haas, TOSEM 2020). Revival is bimodal: in 23 Java desktop apps 67–100% of dead methods were born dead and revival was 0–14% in 13 apps, but above 50% in 4 apps whose developers wrote code ahead of use (EMSE 2023); the same study found dead methods rarely revived and mostly stillborn, and those later revived stayed dead for a shorter time than those later buried, although dead methods generally survive a long time before either; no source says when revival happens, so the veto rests on observable signals (the tip, unmerged refs, markers, declared future work) rather than on elapsed time. No source gives a commit-count or calendar threshold: one later first-parent commit is this skill's floor (pilot-auto-calibration A01-F17, n = 1), and a squashed history gives few events to measure. A text count of occurrences cannot tell a call from a comment or a string, so a hit keeps the code referenced.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [On the spread and evolution of dead methods](https://link.springer.com/article/10.1007/s10664-023-10303-0) (Caivano et al., 2023); [Is Static Analysis Able to Identify Unnecessary Source Code?](https://www.se.cs.uni-saarland.de/publications/docs/HNR+19.pdf) (Haas et al., 2020); [git-diff](https://git-scm.com/docs/git-diff) (Git project, 2026); [git-log](https://git-scm.com/docs/git-log) (Git project, 2026); [git-grep](https://git-scm.com/docs/git-grep) (Git project, 2026) · dossier: dead-code-certainty G102-F08; pilot-auto-calibration A01-F17

### DC-18 — Name the retired feature before deleting a non-trivial unit; owner confirmation adds one level at most
- **Rule:** For anything larger than a local or an import, find the commit and ticket that introduced it and the change that orphaned it, and frame the removal as "feature X was retired in <commit>; Y only served X". Code that has had no call site in any commit since the one that introduced it is a named reason too: frame it as "Y was added in <commit> and never called". If neither reason can be named, report "purpose unknown" (T2). A named reason lifts only this rule's T2: the tier then follows DC-02 and the other vetoes (DC-08 to DC-13), and DC-17's work-in-progress veto (its tip, unmerged-ref, marker and future-work tests) still keeps such code at T2. Owner confirmation raises a candidate one evidence level but never replaces DC-08 or DC-09; with no reachable owner, reachable-but-suspected code stays T2.
- **Detect:** `git log -S'<symbol>' --oneline --all`; `git log -L :<func>:<file>`; `git blame -w -C` on former call sites; CODEOWNERS and `git shortlog -sn -- <path>`; an `owner-confirmed: yes | no | unreachable` note per candidate. Never called: `git log -S'<symbol>' -p --all` shows every hit inside the definition, its imports or re-exports, and none at a call site; cite that output in the `git` evidence item.
- **Not when:** Archaeology is unnecessary for E0 items. In small projects the author may be the only oracle. Owners are fallible: "even the most experienced developers do not know the whole code base" (Haas); in one industrial system maintainers did not know why a method was unused in 48% of cases (Eder, 2012).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [Answer by Cort Ammon](https://softwareengineering.stackexchange.com/a/343662) (SE, 2017); [git-log](https://git-scm.com/docs/git-log) (Git project, 2026); [How Much Does Unused Code Matter for Maintenance?](https://teamscale.com/publications/2012-how-much-does-unused-code-matter-for-maintenance.pdf) (Eder et al., 2012) · dossier: dead-code-evidence T06-F20; dead-code-certainty G102-F09; eval-v1-calibration E01-F07; pilot-auto-calibration A01-F17

### DC-19 — Calibrate trust per tool from its documented soundness
- **Rule:** Go `deadcode` on `main` packages is E1 (sound for reflection and interface calls, blind to assembly and `go:linkname`) and T2 on library-only packages. vulture items below 100% ("very rough" estimates) are T2 unless they reach E2. Knip is E1 only once configuration hints and plugins are resolved. cppcheck `unusedFunction` run with `-j` and no `--cppcheck-build-dir` is invalid. cargo-machete alone ("fast (yet imprecise)") is T2 until cargo-udeps or cargo-shear confirms. Staticcheck U1000 never reports exported identifiers; gopls `unusedfunc` is less precise than `deadcode`.
- **Detect:** Store the tool version with each finding (`knip --reporter json`, `vulture --min-confidence`, `deadcode -json`); run `deadcode -whylive=<pkg>.<Func>` on surprising results.
- **Not when:** Tool behaviour changes between versions: pin versions and re-check this mapping on upgrades (Knip has shipped regressions, e.g. #2024 from 6.27.0, now closed). On one lint-clean Flask app, vulture's 60% tier gave 192 findings, "almost entirely false positives" (HN, 2021). depcheck (archived 2025-06-16), unimported and tsr are archived and point to Knip.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Finding unreachable functions with deadcode](https://go.dev/blog/deadcode) (Donovan, 2023); [Vulture README](https://github.com/jendrikseipp/vulture) (Seipp, 2026); [Cppcheck manual](https://cppcheck.sourceforge.io/manual.pdf) (Cppcheck, 2026); [cargo-machete README](https://github.com/bnjbvr/cargo-machete) (Bouvier, 2026); [HN caymanjim](https://news.ycombinator.com/item?id=27059063) (2021) · dossier: dead-code-certainty G102-F21; dead-code-tools T07-F08, T07-F05, T07-F02, T07-F07

### DC-20 — Remove unused dependencies only after a non-import usage check, per ecosystem
- **Rule:** Find unused, missing and misplaced dependencies with the ecosystem tool, then check each candidate for non-import use: CLI binaries in scripts, plugins and presets named in config, drivers loaded by name or URL, build-script-generated code, renamed packages, peer and type-only packages, reflection-loaded frameworks, doc-test-only crates; those stay T2. Move test tools misfiled as runtime dependencies to dev dependencies instead of deleting them, and declare used-but-undeclared (transitive) imports explicitly.
- **Detect:** knip dependencies (prefer `--production --strict`); deptry DEP001 missing, DEP002 unused, DEP003 transitive, DEP004 misplaced dev (inside the venv; `package_module_name_map` where names differ); `cargo shear` (`--expand` on nightly), `cargo +nightly udeps`, cargo-machete; `go mod tidy -diff`; `mvn dependency:analyze`, DepClean. Grep each package and import name across `*.json`, `*.y*ml`, `*.toml`, `*.cfg`, JS configs, `.github/**`, `Dockerfile*`, `Makefile`, `INSTALLED_APPS`.
- **Not when:** Deliberate security pins (overrides, resolutions) and peer requirements look unused. A direct dependency also pulled in transitively stays installed, and removal can change resolution and the lockfile, so it needs its own commit plus a frozen-lockfile install, build, test and start. ### DC-21 — Delete commented-out code after reviewing each hit
- **Rule:** Treat commented-out code blocks and constant-false guards kept "just in case" as removal candidates; version control keeps them. Review every hit by hand and keep licence headers, docstring and API-doc examples, and prose notes that explain why an obvious approach must not be used. In AI-assisted projects this also cleans agent context: defective commented-out code raised generated defects by up to 58.17% relative to a control, and instructions to ignore it cut defects by at most 21.84% (Copilot and Cursor with GPT-4o and Claude 3.5 Sonnet, Python, FSE 2026).
- **Detect:** Ruff ERA001; eradicate (review before `--in-place`); deadcode (Python) DC12; Sonar S125 where configured; elsewhere a grep heuristic for comment lines that start with a keyword (`if`, `for`, `return`, `import`, `def`, `class`, `function`, `const`, `let`, `var`) and end in `;`, `:`, `{`, `(` or `)`.
- **Not when:** Detectors misfire on prose that parses as code. C code disabled with `#if 0` or a compiled `if` block is tolerated by CERT (MSC12-EX2; MSC04-C prefers these to comments) and is sometimes deliberate documentation: report it (T2). Prevalence: 84.62% of 6,403 Python repositories and 13.09% of Python files contain commented-out code (same study).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Comment Traps](https://arxiv.org/html/2512.20334) (Huang et al., 2026); [Ruff ERA001](https://docs.astral.sh/ruff/rules/commented-out-code/) (Astral, 2026); [eradicate](https://github.com/PyCQA/eradicate) (PyCQA, 2026); [MSC04-C](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/recommendations/miscellaneous-msc/msc04-c) (SEI CERT, 2016); [Answer by Loren Pechtel](https://stackoverflow.com/a/758645) (SO, 2009) · dossier: dead-code-evidence T06-F14; dead-code-tools T07-F19, T07-F18

### DC-22 — Report stale feature flags unless the deployed value is known; never repurpose one
- **Rule:** Without the live value (remote config, environment, database), report the flag with both branches described (T2). Only a compile-time or in-repo constant flag with no override path may be removed (T1): remove the check, the losing branch, code that becomes unreachable, flag-specific tests (under DC-15), the definition and its config, and keep the surviving branch's behaviour exactly. Kill switches, circuit breakers and ops or permission toggles are never stale.
- **Detect:** Flag reads (`isEnabled(`, `isFeatureEnabled(`, `getFlag(`, `variation(`, `useFlag(`, `featureFlags.`, `process.env.(FEATURE|FF|ENABLE)_`) compared against every environment's config; flags read once or compared with a constant; `git log -S<flag>`; tests pinning either value. Polyglot Piranha can rewrite once the value is known (supported languages and flag APIs only).
- **Not when:** Removing the wrong branch inverts behaviour; a flag may be copied elsewhere for a side effect, so search every use. Keeping the old path switchable for a couple of release cycles is defended for critical systems (HN). Piranha needed the flag, its treatment and its owner as input; with those, 65% of diffs for 1,381 flags landed unchanged and over 85% compiled and passed tests (Uber, ICSE-SEIP 2020). Knight Capital lost $460M in about 45 minutes when a repurposed flag reactivated code unused since 2003 on one of eight servers (SEC, 2013).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** B
- **Source:** [Piranha](https://manu.sridharan.net/files/ICSE20-SEIP-Piranha.pdf) (Ramanathan et al., 2020); [uber/piranha](https://github.com/uber/piranha) (Uber); [Feature Toggles](https://martinfowler.com/articles/feature-toggles.html) (Hodgson, 2016); [SEC Release 34-70694](https://www.sec.gov/files/litigation/admin/2013/34-70694.pdf) (SEC, 2013); [HN ori_b](https://news.ycombinator.com/item?id=11716216) (Hacker News) · dossier: dead-code-evidence T06-F11, practitioner voice; dead-code-tools T07-F17; dead-code-certainty G102-F13

### DC-23 — Never reuse a removed wire or persisted identifier
- **Rule:** A deleted protobuf field number must be reserved, and its name too when TextProto or JSON encodings are used (name reuse is unsafe only there); report missing `reserved` entries. Flag diffs where a flag, enum value, column, event name, error code or route keeps its name or number but changes meaning, and check `git log -S'<name>' --all` before any "new" name or number.
- **Detect:** `.proto` history for deleted fields without `reserved`; `git log -S`; review of enum and flag diffs.
- **Not when:** Official support covers protobuf only (grade A there); the other identifier kinds rest on the Knight incident and on analogy (grade B). Inside one process with no persisted or wire format and no stale deployments, reuse is confusing but not dangerous.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Language Guide (proto 3)](https://protobuf.dev/programming-guides/proto3/) (Google); [SEC Release 34-70694](https://www.sec.gov/files/litigation/admin/2013/34-70694.pdf) (SEC, 2013) · dossier: dead-code-evidence T06-F12

### DC-24 — Report dormant, untested code: test it or remove it
- **Rule:** Items that are statically unreferenced, or reachable only through a disabled flag, and have 0% coverage are "dormant untested": report them with the recommendation to add a test or remove them. Anyone who changes shared logic that dormant code depends on must re-test or delete it.
- **Detect:** Cross the coverage report with the static dead-code report; search comments near definitions for keep markers (`unused|not used|legacy|deprecated|keep for|may need|todo: remove|dead`).
- **Not when:** Writing tests for code nobody wants is waste; deletion is usually better. Knight's failure also needed a manual deploy that missed one of 8 servers and no second technician, so dormant code was necessary, not sufficient. Dead methods are rarely revived (23 Java desktop apps, EMSE 2023), which weakens "keep it for later".
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [SEC Release 34-70694](https://www.sec.gov/files/litigation/admin/2013/34-70694.pdf) (SEC, 2013); [Dead methods in Java desktop applications](https://doi.org/10.1007/s10664-023-10303-0) (Caivano et al., 2023); [HN dekhn](https://news.ycombinator.com/item?id=35757803) (2023) · dossier: dead-code-evidence T06-F13

### DC-25 — Never delete config keys or env vars because no read appears in code
- **Rule:** Report env var entries (`.env.example`, compose files, manifests, CI env blocks) and config keys with no code reads, with the grep evidence attached (T2): libraries read variables implicitly, and names can live in databases.
- **Detect:** Collect names from `.env.example`, compose files, k8s manifests and CI env blocks; grep each across the repo.
- **Not when:** Implicit readers include requests (`REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, proxy variables) and AWS SDKs (`AWS_PROFILE`). A truly orphaned key adds confusion; removing it is reasonable only when an owner with deployment access confirms, in a separate commit. No empirical study of unused config keys exists.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** C
- **Source:** [Requests: Advanced Usage](https://requests.readthedocs.io/en/latest/user/advanced/) (requests, 2026); [AWS SDKs and Tools settings reference](https://docs.aws.amazon.com/sdkref/latest/guide/settings-reference.html) (AWS, 2026); [Dead Code Removal at Meta](https://users.encs.concordia.ca/~pcr/paper/Shackleton2023FSE-industry-preprint.pdf) (Shackleton et al., 2023) · dossier: dead-code-certainty G102-F17

### DC-26 — Keep CSS classes that may be built at runtime
- **Rule:** PurgeCSS and Tailwind read sources as plain text and cannot see concatenated or interpolated class names. Before reporting CSS as unused, check for dynamic class construction; such classes need a static lookup map or an explicit safelist, never deletion.
- **Detect:** Grep template literals in `className`/`class` and `'bg-' +` style concatenation; compare the production CSS selector list before and after; visually smoke-test pages with dynamic variants.
- **Not when:** Classes added by third-party scripts or CMS content outside the scanned files are also invisible and need safelisting (PurgeCSS patterns or `/* purgecss start ignore */`; Tailwind `@source inline()`).
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** A
- **Source:** [Detecting classes in source files](https://tailwindcss.com/docs/detecting-classes-in-source-files) (Tailwind CSS v4.3, 2026); [Safelisting](https://purgecss.com/safelisting.html) (PurgeCSS, 2026) · dossier: dead-code-tools T07-F23

### DC-27 — Never remove, reorder or retype state variables in upgradeable contracts
- **Rule:** Treat any contract that inherits Initializable or UUPSUpgradeable, or is deployed behind a proxy, as having a frozen storage layout: report Slither `unused-state` hits there (T2). Removing an "unused" state variable shifts later slots and mixes up stored values.
- **Detect:** Slither `--detect dead-code,unused-state`; `slither-check-upgradeability` (`missing-variables`, `order-vars-contracts`).
- **Not when:** A non-upgradeable contract not yet deployed can drop unused state. Unused internal functions (`dead-code`) do not affect storage and follow the normal rules. Storage gaps and ERC-7201 namespaced storage are the documented alternatives for layout changes.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [Slither Detector Documentation](https://github.com/crytic/slither/wiki/Detector-Documentation) (Trail of Bits, 2026); [Writing Upgradeable Contracts](https://docs.openzeppelin.com/upgrades-plugins/writing-upgradeable) (OpenZeppelin, 2026); [Upgradeability Checks](https://github.com/crytic/slither/wiki/Upgradeability-Checks) (crytic, 2026) · dossier: dead-code-tools T07-F22

### DC-28 — Keep dead-code suppressions central, justified and pruned
- **Rule:** Prefer fixing the tool's configuration (entry patterns, plugins, aliases) over ignoring findings. Propose each confirmed false positive as a checked-in allowlist entry with its reason (vulture whitelist module, Knip config, cargo-machete, cargo-shear or cargo-udeps metadata ignore lists, deptry `per_rule_ignores`, R8 keep rules, .NET `DynamicallyAccessedMembers` or `RequiresUnreferencedCode`, `DynamicDependency` only as a last resort) rather than scattered inline suppressions. Report stale entries whose target no longer exists or is now referenced; the lens proposes entries and never adds them.
- **Detect:** `git grep -nE "noqa: (F401|F841|DC)|eslint-disable.*no-unused|@public|@internal|allow\(dead_code\)|IWYU pragma: keep|purgecss (start )?ignore|NOSONAR"`; `whitelist.py`; Knip `ignore*` keys and tag hints; ESLint `reportUsedIgnorePattern`; vulture run over the whitelist to find stale entries.
- **Not when:** The `_` prefix is the compiler-sanctioned marker for a required but unused binding (TS, Rust, Ruff `dummy-variable-rgx`) and not a smell. An inline suppression is more discoverable for a single local case; allowlists rot without review.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [Knip JSDoc & TSDoc tags](https://knip.dev/reference/jsdoc-tsdoc-tags) (Knip, 2026); [Vulture README](https://github.com/jendrikseipp/vulture) (Seipp, 2026); [no-unused-vars](https://eslint.org/docs/latest/rules/no-unused-vars) (ESLint, 2026); [Prepare .NET libraries for trimming](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/prepare-libraries-for-trimming) (Microsoft, 2026) · dossier: dead-code-tools T07-F20; dead-code-evidence T06-F22

### DC-29 — Remove in small, top-down passes and re-run; a green suite is not proof
- **Rule:** Order removals top-down: unreachable files and modules, then unresolved imports, exports and symbols, then dependencies; re-run every detector after each batch until two consecutive runs show nothing new, and delete dead cycles as a unit. Use one category, feature or flag per commit, with the evidence (tool, rule id, searches) in the message. Do not add tombstones, deprecation logging or scream tests automatically: they change behaviour and pay off only in a deployed, watched service.
- **Detect:** `git log --stat` shows one concern per commit; after each batch, build every configuration (DC-10), run the full suite, do a production build and compare emitted assets and bundle sizes, smoke-run the real entry points; each commit reverts cleanly (`git revert --no-commit`, then build and test).
- **Not when:** Staging is overkill for E0 items. Tests cover only part of what deletions touch: 58% of direct and 20% of transitive dependency calls (521 Java projects, JSS); over 85% of Piranha's diffs passed tests but only 65% landed unchanged (Uber, 2020). On a small codebase with high coverage, tests do catch most mistakes.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Knip: Resolve reported issues](https://knip.dev/guides/handling-issues) (Knip, 2026); [Dead Code Removal at Meta](https://users.encs.concordia.ca/~pcr/paper/Shackleton2023FSE-industry-preprint.pdf) (Shackleton et al., 2023); [Can We Trust Tests To Automate Dependency Updates?](https://arxiv.org/abs/2109.11921) (Hejderup, Gousios, 2021); [Software Engineering at Google, Ch. 15](https://abseil.io/resources/swe-book/html/ch15.html) (Wright, 2020) · dossier: dead-code-tools T07-F01, T07-F15; dead-code-evidence T06-F10; dead-code-certainty G102-F18

### DC-30 — An LLM's reading that code "looks unused" is not evidence
- **Rule:** Count only compiler results, tool output, grep results, execution data, git history and owner statements as evidence; a prose-only rationale ("appears unused") keeps the item at T2 with confidence `inference`. Never delete a failing test or a feature to make a gate pass.
- **Detect:** Every candidate's `evidence` holds at least one non-LLM item (`tool`, `source`, `git`); reject candidates whose only support is narrative.
- **Not when:** LLMs help triage tool output (explaining likely reflective use, grouping candidates) as long as the decision rests on non-LLM evidence. DCE-LLM's 94% F1 was measured on online-judge snippets labelled by vulture and IntelliJ output (NAACL 2025), so it inherits the tools' blind spots; no study measures agent dead-code deletion on real projects.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [DCE-LLM](https://aclanthology.org/2025.naacl-long.501.pdf) (Chen et al., 2025); [HN wongarsu](https://news.ycombinator.com/item?id=45809242) (2025); [Evidence Calibrated Dead Code Detection](https://www.researchsquare.com/article/rs-9609115/v1) (Oh, 2026) · dossier: dead-code-certainty G102-F19; dead-code-evidence T06-F04

### DC-31 — Prioritise removals that pay off; reject any deletion whose risk is not low
- **Rule:** Rank candidates in frequently changed code that newcomers read ahead of stable, rarely read modules. The benefit of each deletion is modest, so never justify a risky deletion by "dead code is harmful" alone.
- **Detect:** Join candidates with the churn ranking in `.harden/rank.json`; record lines, files and dependencies removed plus build time and artifact size before and after.
- **Not when:** Evidence scope: dead code worsened comprehension of unfamiliar code but not effort, nor modifiability of familiar code (83 students, TSE 2020); only 7.6% of changes touched unused code and 3.6% of maintenance was wasted (one industrial system, ICSE 2012); 30% of Meta engineers who find the codebase hard cite dead code (2023); removing dead methods from 23 Java desktop apps cut compile time and binary size (EASE 2024, abstract only). Ranking by churn is an inference from Eder, and the order compiler-proven, dependencies, files, app exports is a synthesis.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [A Multi-Study Investigation Into Dead Code](https://www.cs.wm.edu/~denys/pubs/TSE'18-DeadCode.pdf) (Romano et al., 2020); [How Much Does Unused Code Matter for Maintenance?](https://teamscale.com/publications/2012-how-much-does-unused-code-matter-for-maintenance.pdf) (Eder et al., 2012); [A Folklore Confirmation on the Removal of Dead Code](https://doi.org/10.1145/3661167.3661188) (Romano et al., 2024) · dossier: dead-code-evidence T06-F03; dead-code-certainty G102-F20; dead-code-tools T07-F18

## False-positive exclusions

A candidate in any of these classes is T2 unless a tool that models the mechanism cleared it and the evidence reaches E2 (DC-09).
- Reflection, dependency injection and container registration; `getattr`, `globals()`, `importlib`, `Class.forName`, `reflect.` dispatch; a module-level `__getattr__`.
- Serialised DTOs used outside the analysed code; dataclass, pydantic and TypedDict fields; enums used through iteration or `Object.values`.
- System-border interfaces, plugin and extension points, abstract types referenced only inside their own hierarchy.
- Framework conventions: file-based routing, Flask/FastAPI routes, Django views and signal modules imported in `ready()`, pytest fixtures, auto-imports, auto-mocks, and convention directories (routes/pages, migrations, models, fixtures, `__mocks__`).
- Dynamic or template-string imports; CommonJS member access (`const mod = require('./mod'); mod.fn()`).
- Rust macro-generated references, `build.rs`-generated code, renamed crates (cargo-machete without `--with-metadata`), doc-test-only dependencies.
- CLI entry points and binaries referenced from package.json scripts, CI, Dockerfiles or Makefiles; plugins and presets named in config files; peer and type-only packages.
- Side-effect imports, re-exports, guard and RAII bindings, Rust drop and auto-trait fields, C++ self-registering statics, unreachable `yield`, secret-zeroing stores (DC-04, DC-07).
- Missing generated files and uncommitted build artefacts; names built by string concatenation or stored in a database or remote config.
- Code live in another build configuration; `#ifdef`-disabled code; callers through `go:linkname` or assembly.
- Public API of a published library, SDK, service contract, CLI flag set or config schema (DC-11).
- Resilience defaults and exhaustiveness guards; rare-path code (DR, failover, year-end, audit, migration, admin, error handlers).
- Test seams tagged `@internal` or Guava `@VisibleForTesting`, and test-support builders and fakes.
- Kill switches, circuit breakers and ops or permission toggles.
- CSS classes built at runtime or injected by third-party scripts or CMS content.
- Environment variables read implicitly by libraries (`REQUESTS_CA_BUNDLE`, `AWS_PROFILE`).
- Storage variables of upgradeable contracts.
- Fixed-signature parameters: Express four-argument error middleware, callbacks, overrides, virtual functions.
- Items the project marks as intentionally unused (`_` prefix, `#[allow(dead_code)]`, `# noqa`, allowlist entries): respect them and audit stale ones under DC-28.

## Evidence limits

- No independent precision or recall figures exist for Knip, project-level vulture, Go `deadcode`, deptry, cargo-shear, cargo-machete or cargo-udeps (as of 2026-09). Issue-tracker counts (Knip: 172 of 1,285 issues mention "false positive") are not precision rates.
- The published precision numbers are not comparable: UCDetector 32% (independent, Java, recommender-preselected); DCF 84% and Lacuna 82.5% precision / 97.2% recall (each measured by its own authors; Lacuna on 39 TodoMVC apps); depcheck about 25% misclassified (independent, CommonJS).
- Harm and removal-benefit evidence is narrow: students (Romano), one industrial system (Eder), and Java desktop apps from one research group, partly read from abstracts only.
- No source gives a numeric certainty threshold or a runtime observation window; the studies used 2 years, 6–16 months, or practitioners' 3–6 months.
- The deletion matrix (DC-02), the tiering, the test-deletion carve-out (DC-15) and the commented-out code study (Python, 2024-era models) are unvalidated or unreplicated.
- SonarSource rule descriptions (S125, S1172, S1854 and others) could not be read; only rule names were verified.
- Not covered: in-code dead-code tools for Java, Kotlin, C# and PHP; Go blank imports as side-effect imports; the need for `-ffunction-sections` with `--gc-sections`; rustc `unused_crate_dependencies`; Semgrep.
- cargo-udeps' viability is disputed (cargo-shear's README says it no longer works with recent cargo; its own README documents workspace use): unresolved, cross-check rather than trust either.
- Tool behaviour is from 2026 docs (Knip 6.38.0, vulture 2.16, deptry 0.25.1, cargo-machete 0.9.2, x/tools v0.50.0); re-verify on upgrade.
