# Lens: Concurrency and async

> Purpose: find atomicity and order violations across awaits, locks and threads, unowned async work, event-loop blocking, lock misuse, missing timeouts and swallowed cancellation, and invariants only the datastore can hold. Concurrency fixes are a high-risk human lane.
> Read when: the scope contains async/await, promises, futures, tasks, coroutines, goroutines, threads, locks, channels, queues, retries, or rows mutated by concurrent requests.

## Rules

### CC-01 — Concurrency fixes are a human lane
- **Rule:** Report each concurrency defect with its shared state, the interleaving and a proposed minimal, local patch; do not apply changes to synchronization, scheduling or task structure. Require a test that reproduces the interleaving (fails before, passes after) and a re-check of CC-03 and CC-14 for every variable and lock the patch touches. First patches are often wrong: in Mozilla (C/C++, 2008) 17 of 57 bugs got at least one buggy patch, and of the 23 buggy patches 6 only lowered the bug's probability, 5 introduced new concurrency bugs and 12 new non-concurrency bugs.
- **Detect:** Process check on each CC candidate's `notes`: names a test route (`go test -race -count=100`, ThreadSanitizer, loom, or a deterministic ordering hook); the patch touches only the synchronization it claims to fix; the shared variables and locks are listed.
- **Not when:** The interleaving cannot be reproduced without heavy instrumentation: record the reasoning and prefer moving state to a single owner over lock tweaks. The only T1 rules in this lens (CC-07, CC-20, CC-21) change task lifetime, timeouts or cancellation propagation, not locks or ordering.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [Learning from Mistakes: real-world concurrency bugs](https://people.cs.uchicago.edu/~shanlu/paper/asplos122-lu.pdf) (Lu et al., ASPLOS 2008); [Understanding Real-World Concurrency Bugs in Go](https://songlh.github.io/paper/go-study.pdf) (Tu et al., ASPLOS 2019); [loom](https://github.com/tokio-rs/loom) (tokio-rs, 2026) · dossier: concurrency-async T29-F24

### CC-02 — Record runtime versions before judging an idiom
- **Rule:** Record the go.mod `go` line, the Cargo.toml `edition`, the JDK version, the Python version and whether the free-threaded build is used, and the .NET target framework before reporting any concurrency idiom. Drop fixes the runtime made obsolete. On free-threaded Python, report cross-thread shared mutation that relied on the GIL: built-in type locking is "a description of the current implementation, not a guarantee".
- **Detect:** Manifests and `.harden/inventory.json`; `python -VV` and `sys._is_gil_enabled()` on 3.13+. Obsolete: `i := i` loop copies on Go ≥ 1.22; `synchronized` → ReentrantLock rewrites for virtual-thread pinning on JDK ≥ 24 (JEP 491); if-let guard workarounds on Rust 2024; ConfigureAwait deadlock fixes in ASP.NET Core app code.
- **Not when:** Libraries that still support old toolchains keep the old defensive idioms. Free threading was experimental in 3.13 and is officially supported but optional (not default) from 3.14, so report GIL reliance only where that build is used or targeted.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Fixing For Loops in Go 1.22](https://go.dev/blog/loopvar-preview) (Go blog, 2023); [JEP 491](https://openjdk.org/jeps/491) (OpenJDK, JDK 24); [Python support for free threading](https://docs.python.org/3/howto/free-threading-python.html) (PSF, 3.14.7); [What's New in Python 3.14](https://docs.python.org/3/whatsnew/3.14.html) (PSF, 2025); [Rust 2024 if let temporary scope](https://doc.rust-lang.org/edition-guide/rust-2024/temporary-if-let-scope.html) (Rust project, 2025); [ConfigureAwait FAQ](https://devblogs.microsoft.com/dotnet/configureawait-faq/) (Toub, 2019) · dossier: concurrency-async T29-F20

### CC-03 — Check-then-act across a suspension point is an atomicity violation
- **Rule:** Flag shared state read before an `await`, `yield`, lock release or thread hand-off that decides a write after it (check-then-act, read-modify-write, TOCTOU); single-threaded async code is not race-free. Recommend making check and act one atomic step: memoize the in-flight promise or future instead of the value, re-read after the await, hold one lock over both steps, or move the state to a single owner.
- **Detect:** ESLint `require-atomic-updates` (not in `eslint:recommended`; triage every hit); `ast-grep -p '$X += await $E'` and `ast-grep -p '$X = $X + await $E'`; cache shape `if (!$C.has($K)) { … await … }` followed by `$C.set($K, …)`; Python `rg -n "(self\.\w+|\w+)\s*[-+*/]?=\s*await" --type py`; manual table per awaiting function of globals, fields, caches and rows read before and written after each await.
- **Not when:** Locals nothing else can reach during the await; benign races by design such as last-writer-wins on idempotent caches; property false positives of `require-atomic-updates` (ESLint #11899; consider `allowProperties: true`). Do not default to a lock: 73% of non-deadlock bugs were fixed without adding or changing locks (C/C++, 2008), while Mutex was the most used primitive in Go non-blocking-bug patches (2019).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Learning from Mistakes](https://people.cs.uchicago.edu/~shanlu/paper/asplos122-lu.pdf) (Lu et al., 2008); [require-atomic-updates](https://eslint.org/docs/latest/rules/require-atomic-updates) (ESLint, 2026); [require-atomic-updates false positive #11899](https://github.com/eslint/eslint/issues/11899) (ESLint GitHub, 2019); [CWE-367](https://cwe.mitre.org/data/definitions/367.html) (MITRE, CWE 4.20) · dossier: concurrency-async T29-F01

### CC-04 — Invariants over persistent state belong in the datastore
- **Rule:** Flag invariants over persistent state (uniqueness, balances, stock, coupons, one-time tokens) enforced only by ORM validations or by read-check-write in application code. Recommend a unique constraint, an atomic upsert (`INSERT … ON CONFLICT`), a conditional `UPDATE … WHERE`, `SELECT … FOR UPDATE`, or `SERIALIZABLE` with retry, with the check and the act inside one transaction.
- **Detect:** `rg -n "validates_uniqueness_of|validates .*uniqueness|unique=True"`, then confirm a matching unique index in migrations or schema; read-check-write on one row (`SELECT`/`find`/`get`, an `if`, then `UPDATE`/`save`) with no `FOR UPDATE`, conditional `WHERE`, version column or `SERIALIZABLE`, and whether check and write share a transaction; `rg -n "balance|stock|quantity|inventory|redeem|used_at"` and confirm each decrement is one conditional statement (`UPDATE … SET qty = qty - 1 WHERE id = ? AND qty >= 1`). Recommend as the verification test N parallel identical requests (for example Turbo Intruder single-packet mode) asserting the invariant; the lens itself sends no requests.
- **Not when:** Validations that stay safe under concurrency: Feral CC found up to 86.9% of Rails validation usage by volume safe (67 apps, 2015); uniqueness under insertion and foreign keys under deletion are the unsafe remainder. Raising isolation alone does not fix a check made in a separate transaction. A new unique constraint fails on existing duplicates and needs a data-cleanup migration.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [ACIDRain](http://www.bailis.org/papers/acidrain-sigmod2017.pdf) (Warszawski, Bailis, SIGMOD 2017); [Feral Concurrency Control](http://www.bailis.org/papers/feral-sigmod2015.pdf) (Bailis et al., SIGMOD 2015); [INSERT ON CONFLICT](https://www.postgresql.org/docs/current/sql-insert.html) (PostgreSQL 18 docs); [Smashing the state machine](https://portswigger.net/research/smashing-the-state-machine) (Kettle, PortSwigger, 2023); [CWE-362](https://cwe.mitre.org/data/definitions/362.html) (MITRE, CWE 4.20) · dossier: concurrency-async T29-F18

### CC-05 — Every async result has an owner that observes its failure
- **Rule:** Flag every promise, future, task or coroutine that is not awaited, returned, combined, or handed to an owner that observes its failure. Since Node 15 an unhandled rejection is raised as an uncaught exception by default, so a floating promise is a latent crash as well as a lost error. Split by what the fix needs. A missing `await` or an unhandled promise whose result must be observed, with a mechanical fix (await or return it, attach a handler that observes the failure, keep a reference to an asyncio task), is ER-11 or CC-07: T1 behavioural, fixed at every temperature. This rule (T2) applies only when the fix requires a semantics choice the owner must make: fail-fast `Promise.all` or `allSettled`, cancelling siblings or letting them finish, ordering (awaiting serializes or reorders work that now runs concurrently, while observing with `.catch` or an error handler keeps scheduling), rate limits or concurrency bounds. Report that choice to the human. State in `notes` which case applies; the Tier table re-maps a candidate filed here whose fix needs no such choice to ER-11 or CC-07 (prioritization row 15). A comment, commit message or doc saying the work is deliberately not awaited is a claim (invariant 6, detection DT-29), never such a choice by itself. Choose the fix in this order, and record the stated intent and the fix taken in `notes` and in the `Behaviour change:` line. (1) Take a mechanical fix that keeps every success-path outcome (the output and its order as a reader sees it, the exit code, the data written) and, at every caller, still ends a failure in a failure outcome (an error the caller reports, or the exit code the code's docs give a runtime error), never in success. In Node.js, `await` keeps the success-path outcomes in a run that ends when its work ends (a command, a batch job) and calls no `process.exit()` while the work is pending: such a process exits only when its event loop has no more work, so it already waits for that work. In another runtime, `await` qualifies this way only when that runtime's documentation shows the same exit behaviour. On a request, tick or event path of a long-running process, `await` qualifies only when the awaited work is local and bounded (no network call, and no retry or backoff without a timeout the code sets) and its added latency, measured on success and on a failure with PE-17's method, stays within a budget stated in the item before measuring. A handler that observes the failure and keeps the scheduling qualifies when the failure still reaches the caller or ends in the outcome the code's docs promise for a runtime error. (2) A fix that changes the fail mode is tiered by prioritization row 21, whatever the stated intent: a handler that turns the failure into a successful exit is a fail-closed to fail-open flip, and when the base already survives the failure (a process-level `unhandledRejection` listener that does not end the process, or `--unhandled-rejections` set to `warn`, `warn-with-error-code` or `none` in the start command or `NODE_OPTIONS`), a fix that makes the failure reach a caller is a fail-open to fail-closed flip. (3) When no mechanical fix meets (1), or a latency check fails at apply time, the choice is the owner's: this rule, T2 (protocol-change step 3 decides an approved item again).
- **Detect:** typescript-eslint `no-floating-promises` (`recommended-type-checked`, needs type information); Clippy `let_underscore_future` (warn by default); Error Prone `FutureReturnValueIgnored`; `VSTHRD110`; Python tests under `python -X dev -W error::RuntimeWarning`, confirming the run actually fails because the "never awaited" warning comes from a finalizer and may only print "Exception ignored"; review every `void promise`, `_ = task` and `let _ = fut` for an error handler.
- **Not when:** Intentional fire-and-forget (telemetry, cache warm-up) marked with `void` plus a `.catch`. typescript-eslint says the rule "can be difficult to enable on large existing projects" and may be relaxed where global unhandled-rejection handlers are registered.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [no-floating-promises](https://typescript-eslint.io/rules/no-floating-promises/) (typescript-eslint, 2026); [Node.js v15.0.0 release](https://nodejs.org/en/blog/release/v15.0.0) (Node.js, 2020); [Clippy let_underscore_future](https://rust-lang.github.io/rust-clippy/master/index.html#let_underscore_future) (Rust Clippy, 2026); [FutureReturnValueIgnored](https://errorprone.info/bugpattern/FutureReturnValueIgnored) (Google Error Prone, 2026); [VSTHRD analyzers index](https://raw.githubusercontent.com/microsoft/vs-threading/main/docfx/analyzers/index.md) (Microsoft, 2026); [Developing with asyncio](https://docs.python.org/3/library/asyncio-dev.html) (PSF, 3.14.7); [process](https://nodejs.org/api/process.html) (Node.js v26.10.0 docs, 2026: the process exits on "The `process.exit()` method being called explicitly" or "The Node.js event loop no longer having any additional work to perform"; `process.exit()` exits "even if there are still asynchronous operations pending"); [Command-line options](https://nodejs.org/api/cli.html) (Node.js v26.10.0 docs, 2026: under the default `throw` mode an unhandled rejection is raised as an uncaught exception only "If this hook is not set") · dossier: concurrency-async T29-F02; eval-v1-calibration E01-F01; pilot-auto-calibration A01-F12

### CC-06 — Async callbacks passed where the caller ignores the result
- **Rule:** Flag async functions passed to `Array.forEach`/`filter`/`some`, event-emitter and DOM listeners, `setTimeout` and constructors, and C# `async void` methods that are not UI event handlers (an exception there cannot be caught by the caller and terminates the app). Recommend the replacement that keeps the original intent: `for…of` with `await` (serial), a bounded `Promise.all` (parallel, fails fast, CC-09 and CC-23), or a `Task`-returning method. Choosing among these is the owner's semantics choice and stays here (T2, as in CC-05). When the fix only adds a handler that observes the rejection and keeps the callback's scheduling (an async listener whose body gains one), it is ER-11: T1 behavioural, fixed at every temperature.
- **Detect:** typescript-eslint `no-misused-promises` (`checksVoidReturn` defaults to true; type-checked); `ast-grep -p '$A.forEach(async ($$$) => $$$)'`; `VSTHRD100`, `VSTHRD101` and `rg -n "async void" --type cs`, keeping non-event-handlers; Kotlin/Java listener callbacks that launch coroutines without a scope.
- **Not when:** .NET UI event handlers must be `async void`. Do not satisfy the linter by serializing work that was meant to run in parallel, or with an unbounded `Promise.all` over user-sized input.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [no-misused-promises](https://typescript-eslint.io/rules/no-misused-promises/) (typescript-eslint, 2026); [A Study and Toolkit for Asynchronous Programming in C#](https://dig.cs.illinois.edu/papers/ICSE14_Semih.pdf) (Okur et al., ICSE 2014); [ASP.NET Core Async Guidance](https://raw.githubusercontent.com/davidfowl/AspNetCoreDiagnosticScenarios/master/AsyncGuidance.md) (Fowler, living doc) · dossier: concurrency-async T29-F04; eval-v1-calibration E01-F01

### CC-07 — Keep a strong reference to every asyncio task
- **Rule:** Flag `asyncio.create_task`/`ensure_future` results that are not stored: the event loop keeps only weak references, so an unreferenced task can be garbage-collected mid-execution without any error. Fix with the documented pattern (add the task to a `background_tasks` set and `add_done_callback(background_tasks.discard)`), and make the reference visibly intentional, because a later cleanup may delete the "unused" reference. Apply it at every temperature: the cold-code policy never demotes it.
- **Detect:** Ruff `RUF006`; `rg -n "^\s*(asyncio\.|loop\.|self\._?loop\.)?(create_task|ensure_future)\(" --type py` for statement-level calls; assignments to a local that goes out of scope at once.
- **Not when:** The task is already owned (stored elsewhere or inside a TaskGroup). Converting to `asyncio.TaskGroup` (3.11+) is not drop-in (the block waits for all children and cancels siblings on failure): report it under CC-08 instead. A module-level set leaks memory if tasks never finish.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** A
- **Source:** [Coroutines and Tasks: create_task](https://docs.python.org/3/library/asyncio-task.html) (PSF, 3.14.7); [asyncio-dangling-task RUF006](https://docs.astral.sh/ruff/rules/asyncio-dangling-task/) (Astral, 2026); [The Heisenbug lurking in your async code](https://textual.textualize.io/blog/2023/02/11/the-heisenbug-lurking-in-your-async-code/) (McGugan, 2023); [Lobsters thread](https://lobste.rs/s/vqttsw/heisenbug_lurking_your_python_async_code) (Lobsters, 2023) · dossier: concurrency-async T29-F03; eval-v1-calibration E01-F01

### CC-08 — Every spawned task has an owner and a shutdown path
- **Rule:** Flag unscoped spawns of work that must finish: `GlobalScope.launch`, a bare `create_task`, `go func()` without a join, `Task.Run` without an await, `tokio::spawn` with a dropped JoinHandle. Report who should own each one (TaskGroup/nursery, `coroutineScope`, errgroup, JoinSet, or an application-level scope) and how shutdown cancels it.
- **Detect:** detekt `GlobalCoroutineUsage` (not active by default) and `rg -n "GlobalScope\.(launch|async)"`; Ruff `RUF006` plus `create_task(` outside a TaskGroup; each `go func` checked for a WaitGroup, errgroup or ctx owner; `tokio::spawn(` with the handle discarded; `Task.Run(` without an await; an ownership table for the survivors.
- **Not when:** Long-lived background services legitimately outlive a request and need an application scope. Scoping changes latency (the parent now waits) and can deadlock if a child waits on the parent. The benefit is argued, not measured, and structured concurrency does not prevent data races.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** B
- **Source:** [Notes on structured concurrency](https://vorpus.org/blog/notes-on-structured-concurrency-or-go-statement-considered-harmful/) (Smith, 2018); [GlobalScope](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/-global-scope/) (JetBrains, 2026); [detekt coroutine rules](https://detekt.dev/docs/rules/coroutines) (detekt 2.0.0-alpha.6); [Lobsters: structured concurrency](https://lobste.rs/s/8msejg/notes_on_structured_concurrency_go) (Lobsters, 2021) · dossier: concurrency-async T29-F16

### CC-09 — Choose fan-out combinators by failure and cancellation semantics
- **Rule:** For each fan-out, state whether the siblings have side effects and whether they must be cancelled or allowed to finish on failure, then check the combinator: `Promise.all` fails fast without cancelling the rest (`allSettled` waits for all); `asyncio.gather` does not cancel siblings while `TaskGroup` does; `errgroup.WithContext` cancels the shared context on the first error; Rust `try_join!` and `select!` drop, and so cancel, the remaining futures. Flag side-effecting race losers that keep running and shutdown steps silently cancelled by a fail-fast join (an Oxide production bug).
- **Detect:** `rg -n "Promise\.(all|race|any)\(|asyncio\.gather\(|asyncio\.wait\(|try_join!|join_all\(|select!|errgroup\."`; per hit answer: side effects? cancel or finish on failure? do race losers still hold resources?
- **Not when:** Pure reads whose results are simply discarded may fail fast without cancelling. TaskGroup and errgroup cancellation helps only if children honour cancellation (CC-21). C# `Task.WhenAll`/`WhenAny` semantics are unverified here: report, do not assert.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Promise.all()](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/all) (MDN, 2026); [Coroutines and Tasks: gather, TaskGroup](https://docs.python.org/3/library/asyncio-task.html) (PSF, 3.14.7); [errgroup](https://pkg.go.dev/golang.org/x/sync/errgroup) (Go team, x/sync v0.23.0); [Cancelling async Rust](https://sunshowers.io/posts/cancelling-async-rust/) (Rain, Oxide, 2025) · dossier: concurrency-async T29-F05

### CC-10 — Never block the event loop or an async runtime worker
- **Rule:** Flag synchronous file, network, subprocess and sleep calls, and CPU-heavy work (large JSON parse or stringify, crypto, compression, catastrophic regexes) on an event loop or async worker reachable from request handling. Recommend offloading (`run_in_executor`/`to_thread`, `spawn_blocking`, rayon or a dedicated thread, `worker_threads`) or splitting the work into chunks.
- **Detect:** Ruff `ASYNC210`, `ASYNC212`, `ASYNC220`–`ASYNC222`, `ASYNC230`, `ASYNC240`, `ASYNC250`, `ASYNC251`; asyncio debug mode logs callbacks over 100 ms; Node `rg -n "\b(readFileSync|writeFileSync|existsSync|execSync|spawnSync|pbkdf2Sync|scryptSync|randomFillSync|inflateSync|deflateSync|gunzipSync)\b"`, kept only when reachable from handlers; Rust `std::thread::sleep`, `std::fs::`, `reqwest::blocking` in async fns; detekt `SleepInsteadOfDelay`; `VSTHRD103`.
- **Not when:** Small sync calls at startup, before the server listens. Offloading moves code to another thread and can create data races on state that used to be confined to the loop; adding an await changes timing (CC-03). "No more than 10 to 100 microseconds between each .await" is one Tokio maintainer's rule of thumb, not a measured threshold.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Don't Block the Event Loop](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop) (Node.js, 2026); [Developing with asyncio](https://docs.python.org/3/library/asyncio-dev.html) (PSF, 3.14.7); [Ruff rules](https://docs.astral.sh/ruff/rules/) (Astral, 2026); [Async: What is blocking?](https://ryhl.io/blog/async-what-is-blocking/) (Ryhl, 2020); [detekt coroutine rules](https://detekt.dev/docs/rules/coroutines) (detekt 2.0.0-alpha.6) · dossier: concurrency-async T29-F06

### CC-11 — Remove sync-over-async outside entry points
- **Rule:** Flag blocking waits on async work in request or UI paths: .NET `Task.Result`, `.Wait()`, `GetAwaiter().GetResult()`; Python `asyncio.run`/`run_until_complete` reachable from a running loop; Rust `block_on` inside an async runtime. Recommend async all the way, or one blocking bridge isolated at the program entry point.

### CC-12 — No thread-blocking lock across a suspension point
- **Rule:** Flag a std or parking_lot `Mutex`, `threading.Lock`, `synchronized` region or `RefCell` borrow held across an await, and network I/O or sleeps inside any critical section. ### CC-13 — Check where each lock guard is actually released
- **Rule:** Flag unnamed RAII lock temporaries, `let _ = mutex.lock()`, guards created in a `match` or `if let` scrutinee that stay alive into arms that lock again, and guards whose implicit drop happens after a second acquisition of the same lock. In the Rust study (PLDI 2020), 30 of 38 lock-related blocking bugs were double locks and 21 of 59 blocking bugs were fixed by changing a guard's lifetime.
- **Detect:** Clippy nursery `significant_drop_in_scrutinee`, `significant_drop_tightening` (opt-in); rustc and Clippy `let_underscore_lock` (deny by default); `#![warn(if_let_rescope)]` on edition-2021 crates; `rg -n "match .*\.(lock|read|write)\(\)"`, `rg -n "if let .*\.(lock|read|write)\(\)"`; C++ clang-tidy `bugprone-unused-raii`, `rg -n "^\s*(std::)?(lock_guard|unique_lock|scoped_lock)(<[^>]*>)?\s*[({]"`, and manual `lock()`/`unlock()` calls (CP.20).
- **Not when:** Rust 2024 changed only the if-let case, not `match` scrutinees: check the edition first (CC-02). Nursery lints can be noisy. Moving a drop earlier can open an atomicity window (CC-03).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A

### CC-14 — Prevent deadlocks by structure, not by runtime detection
- **Rule:** Flag separate acquisitions of several mutexes where one call (`std::lock`, `std::scoped_lock`) or a documented global order is missing, any pair of locks taken in both orders, and calls to unknown code (callbacks, virtual or interface methods, event emits, logging hooks) while a lock is held. ### CC-18 — Go: audit the recurring concurrency patterns
- **Rule:** Check Go code for: loop-variable capture in closures (only when the go.mod `go` line is below 1.22); a shared `err` or named result written from goroutines; `WaitGroup.Add` inside the goroutine (prefer `wg.Go(f)` on Go ≥ 1.25); mutexes copied by value; maps or slices written concurrently; channels that may be closed twice (`sync.Once`); unbuffered result channels paired with a select or timeout, which leak the goroutine (use capacity 1); context cancel functions never called. ### CC-19 — Race detectors must run repeatedly over tests that are concurrent

### CC-20 — Every external wait has a finite timeout
- **Rule:** Flag HTTP, RPC, database, queue, lock and subprocess waits with no finite timeout or deadline: `requests` never times out unless told to, and gRPC sets no deadline by default. Prefer propagating one remaining budget (context, CancellationToken, AbortSignal, cancel scope) over resetting a timeout per call. Take the value from measured latency when it exists (ER-21's percentile method). When none exists, do not leave the wait unbounded or wait for the owner to supply a number: add ER-21's fixed internal default as a T1 behavioural item, placed, sized, tested and reported as ER-21 specifies (a named constant or the existing config path, never a new parameter of an exported signature; generous, never tight; a new test that shortens the bound through a test-only seam against a stub that never answers; the value listed as owner-tunable in the report's "Open owner items" section; pilot-auto-calibration A01-F10). Database waits follow the same split as ER-21: connect, pool-acquisition and per-connection lock-wait timeouts the application code passes are this rule's T1 item, and a per-query or per-statement value is T1 only with latency data for that query (DA-10, DA-12, DA-15).

Without it, the default is a stop-gap the owner tunes: never a tight value, and never a reason to lower an existing finite one, because too-tight timeouts cause false failures and retry storms. ### CC-21 — Let cancellation propagate
- **Rule:** Flag handlers that catch and swallow cancellation: `asyncio.CancelledError` (explicitly, via `except BaseException` or a bare `except`), Kotlin `CancellationException` (including `runCatching` around suspend calls and `catch (e: Exception|Throwable)` in suspend functions), and .NET `OperationCanceledException` in loops that should stop. ### CC-22 — Rust async: cancel-correct state and cancel-safe select! branches
- **Rule:** In each Rust async fn that mutates shared state, check the state is valid at every `.await`: a `.take()` or `mem::replace` followed by an await leaves it invalid if the future is dropped there (an Oxide production bug). - **Not when:** Pinning a future outside the loop and passing `&mut fut` is standard Tokio advice to keep progress, yet it is the shape that enables futurelock: unresolved, report and do not auto-fix. ### CC-23 — Bound every queue, buffer, pool and fan-out
- **Rule:** Flag unbounded queues, channels and executor queues, fan-out over unbounded input, and stream writes that ignore backpressure. ### CC-24 — Retries and redelivery need idempotency
- **Rule:** Flag generic retry wrappers around non-idempotent side effects, and queue, stream or webhook consumers with no dedupe key. Recommend a caller-provided idempotency key or message-ID dedupe; SQS standard queues are at-least-once by contract.
- **Detect:** `rg -n "@retry|tenacity|backoff\.on_exception|axios-retry|p-retry|retry\(|Polly|RetryPolicy|withRetry"` and check whether each wrapped call mutates; `rg -n "receive_message|consume|@KafkaListener|on_message|subscribe\("` and check each for a dedupe key or naturally idempotent writes; check public mutating endpoints for an idempotency-key contract.
- **Not when:** Naturally idempotent operations. Idempotency storage adds latency, needs a retention policy and has its own race: two in-flight requests with one key need a lock or a unique insert (CC-04). Adding a key to an API contract is a public API change.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [Amazon SQS at-least-once delivery](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html) (AWS, 2026); [Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) (Featonby, Amazon Builders' Library); [Designing robust and predictable APIs with idempotency](https://stripe.com/blog/idempotency) (Leach, Stripe, 2017); [TaxDC](https://ucare.cs.uchicago.edu/pdf/asplos16-TaxDC.pdf) (Leesatapornwongsa et al., 2016) · dossier: concurrency-async T29-F19

### CC-25 — .NET: do not "optimize" async plumbing as hardening
- **Rule:** Do not propose `ConfigureAwait(false)` for app-level code (ASP.NET Core, UI apps), and do not elide `async`/`await` in methods that contain `using`, `try`, argument validation or AsyncLocal access. Recommend `ConfigureAwait(false)` only in general-purpose library code.
- **Detect:** `VSTHRD111` for library projects only; reject any proposed patch in this pass that adds `.ConfigureAwait(false)` to app code or removes `async` from such methods.
- **Not when:** Libraries consumed by WinForms, WPF or legacy ASP.NET, where a missing `ConfigureAwait(false)` plus a caller's `.Result` can deadlock (Okur's scenario). The claim that eliding async saves an allocation on hot paths is unverified.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [ConfigureAwait FAQ](https://devblogs.microsoft.com/dotnet/configureawait-faq/) (Toub, Microsoft, 2019); [ASP.NET Core Async Guidance](https://raw.githubusercontent.com/davidfowl/AspNetCoreDiagnosticScenarios/master/AsyncGuidance.md) (Fowler, living doc); [A Study and Toolkit for Asynchronous Programming in C#](https://dig.cs.illinois.edu/papers/ICSE14_Semih.pdf) (Okur et al., ICSE 2014) · dossier: concurrency-async T29-F21

## False-positive exclusions

- Locals that nothing else can reach during an await, and benign last-writer-wins races on idempotent caches (CC-03).
- `require-atomic-updates` hits on object properties of race-free code (ESLint #11899, accepted, then archived without a fix in that thread); triage each one.
- Intentional fire-and-forget marked with `void` plus a `.catch`; projects with registered global unhandled-rejection handlers (CC-05).
- .NET UI event handlers declared `async void` (CC-06).
- Small synchronous calls at startup, before the server listens (CC-10).
- One blocking bridge at a true program entry point; the classic ConfigureAwait deadlock in ASP.NET Core app code, which has no SynchronizationContext (CC-11, CC-25).
- Clippy `await_holding_lock` on a guard that is explicitly dropped before the await; a std Mutex in async code that is never held across an await (CC-12).
- Obsolete idioms: `i := i` copies on Go ≥ 1.22; `synchronized` pinning on JDK ≥ 24; if-let guard scope on Rust 2024 (not `match`) (CC-02, CC-13).
- `except Exception` in Python 3.8+ (does not catch CancelledError); suppression paired with `uncancel()` (CC-21).
- Fail-fast combinators over pure reads whose results are discarded (CC-09).
- ORM validations that stay safe under concurrency (Feral CC: up to 86.9% by volume in 67 Rails apps); naturally idempotent operations (CC-04, CC-24).
- Long-lived background services owned by an application-level scope (CC-08).
- Libraries that still support old toolchains keeping old defensive idioms (CC-02).
- goleak reports caused by in-flight goroutines of `t.Parallel()` tests (CC-18).
- TSan reports involving code not built with `-fsanitize=thread` (CC-19).
- `recursive_mutex` used for the re-entrancy cases CP.22 allows (CC-14).
- Lock-free structures justified by benchmarks and model checking; double-checked locking in the conventional form CP.111 allows (CC-17).
- Hits from nursery lints (`significant_drop_in_scrutinee`, `significant_drop_tightening`) that do not re-acquire the lock (CC-13).

## Evidence limits

- The atomicity and deadlock numbers come from 105 multithreaded C/C++ bugs in MySQL, Apache, Mozilla and OpenOffice (Lu et al., ASPLOS 2008): 97% of the 74 non-deadlock bugs are atomicity or order violations, 66% involve one variable, and 92% of all examined bugs manifest once a partial order among at most 4 memory accesses is enforced. The async (single-threaded) form of CC-03 rests on ESLint's documentation, not on a prevalence study.
- No peer-reviewed prevalence study of JS/TS promise bugs exists in the dossier; CC-05 and CC-06 rest on official tool docs. Fixing a mechanical floating-promise or task-reference defect at every temperature (ER-11, CC-07) comes from the skill's own paired evaluation (eval-v1-calibration E01-F01, n = 2 runs per cell), not from an external study; it changes when a fix is applied, never the evidence the rules cite.
- C# numbers are from Windows Phone apps (Okur et al., ICSE 2014): 19% of async methods (460 of 2,383) are non-handler `async void`, in 76% of the 167 apps that use async/await (corpus of 1,378); 115 long-running operations in 22% of those 167 apps; the "5 deadlock cases" are pattern instances found by analysis, not observed production deadlocks.
- ACIDRain (SIGMOD 2017): 22 verified attacks in 12 e-commerce apps deployed on over 2M sites; all manifest at default isolation and 17 even at the strongest isolation, because of incorrect transaction use. PortSwigger (2023) measured about a 1 ms median spread for 20–30 requests with the single-packet attack.
- TaxDC (ASPLOS 2016, 104 bugs in Cassandra, HBase, Hadoop MapReduce and ZooKeeper): 47% lead to silent failures, 9% are a missing reply with no timeout, 63% need a hardware fault, and more than 60% are triggered by a single untimely message. It covers distributed concurrency bugs in general, not retries or idempotency, which is why CC-24 is grade B.
- Fix-quality data is Mozilla-only (2008) and fix-size data (average 6.8 lines) covers Go blocking bugs only (2019). Rust lock data is from one study (PLDI 2020).
- Dynamic detectors only see executed interleavings; a clean run is not absence. The goroutineleak profile's false-positive and false-negative rates are not reported. Clang thread-safety analysis is intra-procedural with no alias analysis.
- Unmeasured or unresolved: the defect-rate effect of structured concurrency; any lint for Rust futurelock or cancel-correctness; how much GIL-reliant Python breaks under the free-threaded build. The concurrency dossier has no method for choosing timeout values; Brooker's false-timeout-rate percentile is verified in the error-handling dossier (T14-F11) and needs measured latency. Without it, CC-20 adds ER-21's generous, owner-tunable default (eval-v1-calibration E01-F05), which bounds the wait but is not a tuned value.
- Not verified, so never assert: C# `Task.WhenAll`/`WhenAny` cancellation semantics; Kotlin `runBlocking` inside coroutines; Java `StructuredTaskScope`; Python `Condition.wait_for`; Go `OnceValue`; immunity of trio/anyio nurseries to the create_task GC issue; allocation savings from eliding async.
- The ripgrep and ast-grep patterns in this file are heuristics that were not tested against a corpus. The `python -X dev -W error::RuntimeWarning` recipe may not fail the run.
- The 10–100 µs between awaits (Tokio maintainer) and the 100 ms slow-callback log (asyncio debug default) are a rule of thumb and a logging default, not validated thresholds.
