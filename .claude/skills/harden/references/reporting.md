# Reporting and before/after evidence

> Purpose: fill `.harden/findings.json`, write `.harden/report.md` and `.harden/report.sarif`, and claim only deltas that survive re-measurement.
> Read at: Phase 5 (report first, and the whole of `--report-only`) and Phase 8 (final report after the applied tiers).

## Steps

Run scripts with `python` on Windows and `python3` on macOS/Linux. If the shell does not expand `${CLAUDE_SKILL_DIR}`, use `$HOME/.claude/skills/harden`. `<base>` is `base_sha` from `.harden/active`. Where `jq` is absent, do the same JSON read with `python -c`.

**Phase 5: report first (no edit to target code)**
1. Re-read `.harden/progress.md`. Load `.harden/findings.json`, `.harden/inventory.json`, `.harden/prescan.json`, `.harden/rank.json` and the raw outputs in `.harden/tools/`. Only findings with `verified: true` enter the report; unverified detections stay in `.harden/candidates.json`.
2. For each finding, write the impact, trigger conditions and entry point in `notes` first. Then set `severity` and `severity_criterion` (RP-01, RP-02), `conditions`, `confidence` with matching `evidence` (RP-03), `blocking` and `unblock_condition` only under RP-05, `cwe` when one applies (RP-18) and `fingerprint` (RP-19).
3. Validate. Fix every error and read every warning. Exit 0 = valid, 1 = invalid, 2 = unreadable:
   `python "${CLAUDE_SKILL_DIR}/scripts/validate_findings.py" .harden/findings.json --repo .`
   Never lower a severity or raise a confidence to get past an error (RP-04).
4. Write `.harden/report.sarif` (RP-19). It holds each tool's SARIF from `.harden/tools/`, plus one run under a synthetic `tool.driver` named `harden` for hand-written findings. List the failed tool runs for Limits:
   `jq '[.runs[].invocations[]? | select(.executionSuccessful != true)]' .harden/report.sarif`
5. Write `.harden/report.md` from `assets/report-template.md`, in this order:
   - Header: commit range `<base>..HEAD`, `tool_versions`, config hashes (`sha256sum <config files>`), runtime.
   - Summary (RP-08): the first section, one screen that states the mode and the end-to-end verdict ("not run yet" at this phase) and says what changed, what needs your decision and what was not checked.
   - Scope, baseline and method, with the method-and-limits and threshold-policy blocks (prioritization.md PZ-17, PZ-23).
   - The decision groups (RP-07), ordered by RP-06.
   - Open owner items (RP-07): one-line references to the finding ids that leave a value or decision with the owner.
   - Autonomous decisions (RP-07): the profile the run used, the categories and items it approved, what stayed report-only and why, how money paths were decided and where the profile's `money_paths_globs` and a judgement disagree, the questions answered by a conservative default, and the commands the profile forbade. In interactive and report-only mode, one line naming the mode.
   - Reverted by end-to-end verification (RP-07): "not run yet" at this phase.
   - Before/after table, holding baseline values only at this phase (RP-12).
   - Limits (RP-09) and residual risk (RP-10).
   - Appendix, with the nit-overflow table: every reported nit past the cap of 10 (RP-06).
6. Self-check the report. Every hit is a violation to fix:
   - the RP-06 loop over reported nit ids prints a `missing` line (a reported finding absent from `report.md`)
   - the RP-08 label count over the Summary is not 4, or the Summary is not the first H2 section
   - `grep -nE 'CVSS:[34]\.[01]/|(score|severity|risk).{0,15}[0-9]+\.[0-9]' .harden/report.md` (RP-01)
   - `grep -niE 'maintainability index|\bMI\b' .harden/report.md` (RP-13)
   - `grep -niE 'reduc(ed|es) (code )?smells|improv(ed|es) (the )?(design|quality|maintainability)' .harden/report.md` (RP-15)
   - `grep -nE '\b(consider|could|might want to)\b' .harden/report.md`. Free-floating advice: attach it to a finding id or delete it (RP-16).
   - `python "${CLAUDE_SKILL_DIR}/scripts/residual_check.py"` exits 1: a Residual risk cell claims more than the ledger and the tool outputs show; fix `.harden/tools/residual.json` and render the table again (RP-10).
7. Show the report. With `--report-only`, stop here: this report is the final report. In autonomous mode (the default), ask nothing and wait for nobody: the category rows of `.harden/approvals.md` come from the profile's `auto_apply` switches (protocol-change step 3; user-policy-autonomy U01-F01, U01-F04), and the run goes on to Phase 7. With `--interactive`, record the user's decision for each category batch in `.harden/approvals.md` as accepted, rejected or pending, with counts per rule.

## Rules

These rules never edit target code, so each rule is T2 · report-only. The tiers and classes they mention are those of the findings being reported.

### RP-01 — Severity is a small ordinal label, never a decimal score
- **Rule:** Give every finding one of `critical|high|medium|low|nit` and order by that label, never by a number. Treat a one-level disagreement between two assessments as noise. When the project really needs a CVSS vector (for example, it issues CVEs), attach it as metadata with its CVSS-B/BT/BE/BTE suffix. Never use it as the ordering key.
- **Detect:** `validate_findings.py` rejects values outside the enum. `grep -nE 'CVSS:[34]\.[01]/|(score|severity|risk).{0,15}[0-9]+\.[0-9]' .harden/report.md` must return nothing, or only suffixed CVSS vectors.
- **Not when:** Ordinal labels are noisy too: about 51% of duplicate bug reports in OpenOffice, Mozilla and Eclipse carry inconsistent severity (EMSE 2016). The scale avoids false precision; it does not cure disagreement. 80% of Wunder et al.'s evaluators still found CVSS useful. The evidence comes from vulnerability and bug-tracker severity, so applying it to code-quality severity is an inference.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Shedding Light on CVSS Scoring Inconsistencies](https://arxiv.org/abs/2308.15259) (Wunder et al., IEEE S&P 2024: 68% of 59 re-surveyed participants changed their own severity after 9 months); [SSVC: Items With the Same Priority](https://certcc.github.io/SSVC/topics/items_with_same_priority/) (CERT/CC: CVSS errors of "around +/- 1.5 to 2.5" that "often cross decision boundaries"); [Towards Improving CVSS](https://www.sei.cmu.edu/library/towards-improving-cvss/) (CMU SEI, 2018); [On the unreliability of bug severity data](https://link.springer.com/article/10.1007/s10664-015-9409-1) (Tian et al., EMSE 2016); [CVSS v4.0 Specification](https://www.first.org/cvss/v4.0/specification-document) (FIRST, 2024) · dossier: final-report-and-impact G204-F01

### RP-02 — Severity quotes the rubric line it meets; preconditions go on a second axis
- **Rule:** State the impact, trigger conditions and reachable entry point in `notes` first. Then quote, in `severity_criterion`, the first rubric line those facts meet. The rubric is a synthesis and is not validated:
  - critical = verified data loss, corruption, security compromise or crash on a default path;
  - high = wrong result on a realistic path;
  - medium = failure that needs unusual state or input;
  - low = maintainability or evolvability cost only;
  - nit = no expected impact.

  Put every other likelihood factor (difficulty, attacker position, rare configuration) in `conditions` (`none|some|significant|undetermined`). It never goes into the severity.

  Exception: on-chain contract findings use the published impact scale named by W3-03 (lens-web3.md), quoted in `severity_criterion`; for them the scale's likelihood adjustments apply (for example, front-running lowered one level on private-mempool chains).
- **Detect:** `validate_findings.py` errors on a non-nit finding with an empty `severity_criterion`. Read 3 random findings and check that the quoted criterion literally matches the described impact. For a contract finding, `severity_criterion` names the platform whose rubric it follows.
- **Not when:** Nits need no criterion. A rubric reduces variance but does not settle disagreement: in Wunder et al., documentation use was the strongest predictor of scoring performance, yet their model explains only R² = 0.118. Fund-loss rubrics from audit contests do not map one-to-one onto code-quality defects, so the exception covers on-chain contract findings only; those platforms disagree about likelihood (Sherlock does not consider it for severity), which is why the rubric is named.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Shedding Light on CVSS Scoring Inconsistencies, Table 7](https://arxiv.org/abs/2308.15259) (Wunder et al., 2024); [NATS Server Security Assessment, appendix A](https://github.com/trailofbits/publications/blob/master/reviews/2025-04-ostif-nats-securityreview.pdf) (Trail of Bits, 2025: separate Severity and Difficulty); [Semgrep rule metadata](https://docs.semgrep.dev/contributing/contributing-to-semgrep-rules-repository) (Semgrep, 2026); [OWASP WSTG Reporting Structure](https://raw.githubusercontent.com/OWASP/wstg/master/document/5-Reporting/01-Reporting_Structure.md) (OWASP); [Sherlock judging guidelines](https://docs.sherlock.xyz/audits/judging/guidelines) (Sherlock: likelihood not considered in severity); [SonarQube software qualities](https://docs.sonarsource.com/sonarqube-server/quality-standards-administration/managing-rules/software-qualities) (SonarSource, 2026: Info "no expected impact"); [Immunefi Severity Classification v2.3](https://immunefi.com/immunefi-vulnerability-severity-classification-system-v2-3/) (Immunefi, n.d.: the contract impact classes W3-03 quotes) · dossier: final-report-and-impact G204-F02, G204-F20; industry-review-guidelines T02-F03; web3-audit-practice G207-F16

### RP-03 — Confidence comes from the evidence ladder, never from self-rating
- **Rule:** Set `confidence` to the highest rung the evidence actually reaches, and back it with the matching `evidence` kind. The rungs, highest first:
  1. `failing_test` (evidence kind `test`)
  2. `reproduction` (kind `repro`)
  3. `tool_high_precision` (kind `tool`)
  4. `needs_review`
  5. `inference`

  Call a finding "confirmed" only at the top two rungs. Never ask the model how confident it is, and never print bare probabilities in the report.

  Comments, commented-out code and unused imports reach at least `tool_high_precision` (kind `tool`) through detection DT-27's deterministic path: the quoted text plus an AST-identical or compiler-clean check re-run in this session. Never place them at `needs_review`, which is for mechanisms that are hard to demonstrate, and never leave such an item unapplied because of that label.
- **Detect:** `validate_findings.py` errors when a rung lacks its evidence kind, and when a reported finding lacks `verified: true`. `grep -nE '% confident|likely \(0?\.[0-9]' .harden/report.md` must return nothing. The DT-27 `jq` check lists no comment, commented-out-code or unused-import finding at `needs_review`.
- **Not when:** A rule's `precision` is its author's estimate for the whole rule, not a measurement of each finding, so `tool_high_precision` still needs the verifier's file:line check. Xiong et al. tested 2023-era models on general QA and found that calibration improves with capability. No study compares reader trust across confidence vocabularies. The DT-27 path proves only that the deletion changes no code; whether the comment goes is still the lens rule's test.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [SARIF support for code scanning](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/sarif-support-for-code-scanning) (GitHub Docs: orders results by level and rule `precision`); [SonarQube security hotspots](https://docs.sonarsource.com/sonarqube-server/user-guide/security-hotspots) (SonarSource, 2026); [Bandit manual](https://bandit.readthedocs.io/en/latest/man/bandit.html) (PyCQA: separate severity and confidence levels); [Can LLMs Express Their Uncertainty?](https://arxiv.org/abs/2306.13063) (Xiong et al., ICLR 2024: verbalized confidence overconfident); [How we made our AI code review bot stop leaving nitpicky comments](https://www.greptile.com/blog/make-llms-shut-up) (Greptile, vendor, 2024: LLM self-rating "nearly random") · dossier: final-report-and-impact G204-F03, G204-F20; skill-design T31-F10; eval-v1-calibration E01-F06

### RP-04 — Critical, high and blocking findings carry proof, or are reported as questions
- **Rule:** Present a critical, high or blocking finding as established only at `failing_test`, `reproduction` or `tool_high_precision`. Do not delete an unproven defect, such as one backed only by a code-path trace or without a context trail (callers, tests, history). Keep its rubric severity, set it to `needs_review` and status `deferred` with "unproven" in `notes`, and list it as a question under "Needs your decision".
- **Detect:** `validate_findings.py` errors on an established critical, high or blocking finding without a proof rung, and warns on deferred ones. Re-run every `repro` command and confirm the recorded output. As a heuristic only: if functional findings far outnumber evolvability findings, re-check them for false positives.
- **Not when:** Races and environment-specific failures cannot be reproduced cheaply. Keep them as questions. The proof requirement rests on audit-contest rubric conventions and one maintainer's bounty statistics. No study tests its effect on reader trust.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [Sherlock judging guidelines](https://docs.sherlock.xyz/audits/judging/guidelines) (PoC recommended "to avoid placing the burden of proof on the judge"); [Code4rena severity categorization](https://docs.code4rena.com/competitions/severity-categorization) (no "hand-wavy hypotheticals"); [Death by a thousand slops](https://daniel.haxx.se/blog/2025/07/14/death-by-a-thousand-slops/) (Stenberg, curl, 2025: about 5% of 2025 bounty submissions genuine by early July); [What Types of Defects Are Really Discovered in Code Reviews?](https://doi.org/10.1109/TSE.2008.71) (Mäntylä & Lassenius, TSE 2009: 75% of defects in 9 industrial C/C++ and 23 student Java reviews did not affect visible functionality); [GitLab Code Review Guidelines](https://docs.gitlab.com/development/code_review/) ("If you don't understand a piece of code, say so.") · dossier: final-report-and-impact G204-F04; industry-review-guidelines T02-F13, T02-F15; web3-audit-practice G207-F16

### RP-05 — Blocking is narrow and states what unblocks it
- **Rule:** Set `blocking: true` only for a verified correctness, security or data-integrity defect, or for a behaviour change the pass itself introduced. Put the exact event that clears it in `unblock_condition`. Style, naming, docs, micro-optimisations and "possible in theory" findings never block. Leave the field absent on every other finding (non-blocking).
- **Detect:** `validate_findings.py` errors on a blocking finding without `unblock_condition`, or on a blocking nit, and warns on a blocking readability-docs finding. Then list all blocking items with `jq -r '.findings[] | select(.blocking==true) | [.id,.lens,.severity] | @tsv' .harden/findings.json` and reject any style, naming or doc item.
- **Not when:** On public-API or regulated projects, a doc or naming error can break a contract and may block. Allow a project-local override and say so in the report. Contest rubrics (Sherlock, Code4rena) are only analogues, tuned for fund loss.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [Conventional Comments](https://conventionalcomments.org/) ("(blocking)" / "(non-blocking)"; nitpicks "non-blocking by nature"); [How to write code review comments](https://google.github.io/eng-practices/review/reviewer/comments.html) (Google: Nit / Optional / FYI); [Sherlock judging guidelines, VII](https://docs.sherlock.xyz/audits/judging/guidelines) (categories "not considered valid"); [Code4rena severity categorization](https://docs.code4rena.com/competitions/severity-categorization) (informational issues "discouraged") · dossier: final-report-and-impact G204-F21; industry-review-guidelines T02-F03

### RP-06 — Order by one key (blocking, severity, confidence, location, dimension); cap nits; "no issues" is a valid result
- **Rule:** Within each decision group, and for the prioritised list (prioritization.md step 9), sort by this key, each level breaking ties in the one before:
  1. blocking items first;
  2. severity (`critical`, `high`, `medium`, `low`, `nit`);
  3. confidence rung (RP-03, highest first);
  4. location, as in prioritization.md step 9: consequence band before maintainability band (PZ-01), then `location_class` (`hotspot`, then `warm` and `unknown` together, because PZ-13 treats `unknown` as warm, then `cold`) and the file's rank in `.harden/rank.json`, then functions inside a file (PZ-20);
  5. dimension (PZ-22): design, functionality and concurrency, complexity, tests, naming, comments, style.

  No numeric score is introduced to rank items. Label nits as nits. The cap of 10 limits the main list (the "Informational and nits" group) only: list every further reported nit, in the same order, in the report's Appendix nit-overflow table (id, file:line, rule, title). No reported finding is left out of `report.md`, and all of them also stay in SARIF. Severity `nit` sets order and placement, never the tier: a nit whose rule is T0, or T1 in an approved category, is applied like any other finding and listed under Applied. Name every in-scope module and lens, if only as "reviewed: no issues".
- **Detect:** `python "${CLAUDE_SKILL_DIR}/scripts/validate_findings.py" .harden/findings.json --nit-cap 10` warns above the cap. Every reported nit appears in `report.md`: `jq -r '.findings[] | select(.severity=="nit" and .status!="candidate" and .status!="rejected") | .id' .harden/findings.json | while read -r id; do grep -qwF -- "$id" .harden/report.md || echo "missing $id"; done` prints nothing. Check the order against the key by eye, and check that every scope item in `.harden/config.json` appears in the report.
- **Not when:** Nits have some long-term maintenance value (Bosu et al.), so cap and demote them rather than delete them. The cap of 10 is a convention, not a measured threshold; Anthropic's REVIEW.md example uses five. The cap has to be structural, because the Greptile vendor could not prompt away nits without also losing critical comments. Keys 4 and 5 are conventions: Google ranks only design first, and the rest of the dimension order is its checklist's section order. In the skill's v1 evaluation, a cap that also bounded `report.md` hid one reported item, and comment fixes labelled as nits were left unapplied (n = 2 per cell). Ordering `unknown` with `warm` follows PZ-13: in the same evaluation, reading the `unknown` of a short history as cold left zero-risk items unfixed.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Characteristics of Useful Code Reviews](https://www.microsoft.com/en-us/research/publication/characteristics-of-useful-code-reviews-an-empirical-study-at-microsoft/) (Bosu et al., MSR 2015, 1.5M Microsoft comments: usefulness falls as files per change rise); [What Makes a Code Review Useful to OpenDev Developers?](https://arxiv.org/abs/2302.11686) (Turzo & Bosu, EMSE 2023); [Greptile blog](https://www.greptile.com/blog/make-llms-shut-up) (vendor, 2024: 79% of its bot's comments were nits); [Code Review, REVIEW.md nit volume](https://code.claude.com/docs/en/code-review) (Anthropic, 2026); [What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html) (Google: design is "the most important thing") · dossier: final-report-and-impact G204-F08; industry-review-guidelines T02-F03, T02-F01; skill-design T31-F11; eval-v1-calibration E01-F06, E01-F01

### RP-07 — Group the report by the decision the reader must take
- **Rule:** Use these H2 groups in this order:
  1. Applied, review before merge: one row per commit of a finding that carries a `review` object (findings schema). The rows come in this order: changes that break a public API, a serialized field, a CLI output, an error string or an exit code (subject with `!`); additive public API changes; contract sources (each takes effect only when the owner redeploys, and any source change, a comment included, changes the deployed bytecode's metadata hash); money-path items; owner-judgement items (T2 applied by an autonomous run); other behavioural fixes; a whole-repository format run last. Within each kind, the RP-06 order applies. Each row gives the finding id, the `Behaviour change:` line, the option taken and the alternatives the owner can still choose (user-policy-autonomy U01-F11), the demonstrating test or proof, and the one-line undo `git revert <sha>`. - **Not when:** Counts can be gamed, for example by splitting fixes or by weakening a rule in config instead of removing suppressions. That is why the suppression row needs the config diff. No study validates this exact list.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [-2000 Lines Of Code](https://www.folklore.org/Negative_2000_Lines_Of_Code.html) (Hertzfeld, folklore.org, event of 1982); [Is Self-Admitted Technical Debt Tested?](https://arxiv.org/abs/2609.13485) (Yoshimoto et al., 2026 preprint, 8 Java projects: 3.4% of debt-removal commits add targeted tests); [SARIF v2.1.0 Plus Errata 01, §3.35](https://docs.oasis-open.org/sarif/sarif/v2.1.0/errata01/os/sarif-v2.1.0-errata01-os-complete.html) (OASIS, 2023) · dossier: final-report-and-impact G204-F17; llm-refactoring T10-F08; autofix-trust G105-F22

### RP-13 — Maintainability Index and density ratios are never improvement evidence
- **Rule:** Never report a before/after Maintainability Index. When the pass added or deleted code, never present a density or ratio as a delta: debt ratio, duplicated-lines density, line coverage, weaknesses per KLOC. If a ratio has to appear, show its numerator and denominator for both runs and flag a denominator that shrank.
- **Detect:** Run `grep -niE 'maintainability index|\bMI\b' .harden/report.md`. Every % or ratio row carries n/N for both runs. For coverage, run `grep -E '^(LF|LH):' lcov.info | awk -F: '{s[$1]+=$2} END{print s["LH"]"/"s["LF"]}'` at both runs, and note a drop in LF.
- **Not when:** Densities are legitimate for comparing modules of different sizes at one point in time, which is how ISO/IEC 5055 uses them. MI being built into radon and Visual Studio is not evidence that it is valid.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Do AI Agents Really Improve Code Readability?](https://arxiv.org/abs/2603.13723) (Horikawa et al., MSR 2026: MI decreased in 56.1% of 403 AI-agent readability commits); [Think Twice Before Using the Maintainability Index](https://avandeursen.com/2014/08/29/think-twice-before-using-the-maintainability-index/) (van Deursen, 2014: every component is size-correlated); [Impact of Refactoring On Internal and External Measures](https://arxiv.org/abs/1502.03526) (Kannangara & Wijayanayake, 2015: MI "improved" while external measures did not); [SonarQube metric definitions](https://docs.sonarsource.com/sonarqube-server/user-guide/code-metrics/metrics-definition) (SonarSource, 2026: ratios divide by LOC or executable lines) · dossier: final-report-and-impact G204-F13, G204-F14; standards T01-F01

### RP-14 — Coverage percentage is not the test-quality delta
- **Rule:** Instead of a coverage-percentage change, report the tests added (each linked to a finding id) and the mutation results on touched lines (killed/total, with survivors listed). When no mutation tool ran, report the hand-seeded net check's killed/seeded count, or "safety net unmeasured" with its reason, in Limits (i). Use coverage only to point at completely untested code.
- **Detect:** Where a mutation tool exists (e.g. Stryker, PIT, mutmut or cargo-mutants; the language reference gives the command), run it on `git diff --name-only <base>..HEAD`. Every `test` evidence item in `findings.json` belongs to a finding.
- **Not when:** Equivalent mutants inflate the survivor count, and runtime can be high on large touched areas. The coverage-effectiveness question is debated: Google's mutation authors call it "a matter of ongoing debate".
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Coverage Is Not Strongly Correlated with Test Suite Effectiveness](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf) (Inozemtseva & Holmes, ICSE 2014: 31,000 suites over five systems up to 724k LOC; low-to-moderate correlation once suite size is controlled; effectiveness measured by mutants); [Does mutation testing improve testing practices?](https://arxiv.org/abs/2103.07189) (Petrović et al., Google, ICSE 2021); [Practical Mutation Testing at Scale](https://arxiv.org/abs/2102.11378) (Petrović et al., 2021: changed code only); [Code Coverage Best Practices](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html) (Google Testing Blog, 2020); [TestCoverage](https://martinfowler.com/bliki/TestCoverage.html) (Fowler, 2012) · dossier: final-report-and-impact G204-F15; industry-review-guidelines T02-F12; standards T01-F02; pilot-auto-calibration A01-F22

### RP-15 — No "reduced smells" or "improved design" claims
- **Rule:** Describe each refactoring by the verified structural fact it produced. Example: "X split into Y and Z; tests T pass; rule R absent at this fingerprint under the pinned detector". Never describe it as "reduced smells", "improved design" or "improved maintainability". Never present totals of smells, rule violations or debt minutes as a quality score.
- **Detect:** `grep -niE 'reduc(ed|es) (code )?smells|improv(ed|es) (the )?(design|quality|maintainability)' .harden/report.md`. Each hit needs a pinned-tool fingerprint delta and a test reference, or a rewrite.
- **Not when:** Chávez et al. (via AlOmar) report that 55% of floss-refactoring operations improved internal attributes, and agentic refactoring shows small significant structural gains (preprint). The rule limits claims, not refactoring itself.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Understanding the impact of refactoring on smells](https://doi.org/10.1145/3106237.3106259) (Cedrim et al., ESEC/FSE 2017, 16,566 refactorings in 23 projects: 9.7% removed smells, 33.3% introduced new ones); [Are SonarQube Rules Inducing Bugs?](https://arxiv.org/abs/1907.00376) (Lenarduzzi et al., SANER 2020, 202 Java rules on 21 OSS projects: fault-prediction power "extremely low"); [From Human to Machine Refactoring](https://arxiv.org/abs/2601.13139) (Midolo et al., 2026 preprint: GPT-4o reduced smells but decreased readability) · dossier: final-report-and-impact G204-F16; standards T01-F15

### RP-16 — "Fixed" means changed and verified; a headline reproduction still reproducing means `partial`
- **Rule:** Set status `applied`, which the report calls "fixed", only when a commit changed code at the flagged location (or its message explains the causal link), the gates passed after it, and the end-to-end verifier did not revert it (protocol-change PC-26). A finding whose commits the verifier reverted is `reverted`; one that keeps another commit of its own is `partial`, with the reverted line named in `notes`. When the finding records a headline reproduction (a `repro` evidence item, such as a command that prints a wrong value and exits 0), `applied` also requires that the demonstrating test covers that exact reproduction and that the command, re-run at HEAD, no longer shows the defect. Judge each consequence the finding names on its own, with PC-14's restores-promised-behaviour test. A finding whose commits landed while its headline reproduction or another consequence still reproduces is `partial`: keep its `commit`, name the open consequence and the re-run command with its exit code in `notes`, list it first under Open owner items (RP-07), and never call it fixed. Record the `commit`, the verification command and an excerpt of its output. Use one finding per commit. Every "passes", "fixed" or "clean" claim sits next to its command and exit code. Every resolution rate states its definition and n/N. The report lists the commits and `git diff --stat <base>..HEAD`, and says that undo is `git revert <sha>`.
- **Detect:** `git log --oneline <base>..HEAD` shows one finding id per commit. `git cat-file -e <sha>` succeeds for every `commit` (`validate_findings.py --repo .` also checks this). `git diff <base>..HEAD -- <file>` touches the flagged range. For every `applied` finding with a `repro` evidence item, re-run that command at HEAD: output that still shows the defect makes the finding `partial`. No `applied` finding's `commit` appears among the `reverts` of `.harden/verify.json`.
- **Not when:** Code at a flagged line can change for unrelated reasons, and a valid fix can land elsewhere; that is why the causal-link note exists. Published AI-review resolution rates (about 19% to 74%) come from different tools, populations and definitions. They are not benchmarks. The `partial` status is the skill's own v2 calibration (n = 3 per cell), not yet re-measured: in that evaluation, a finding's headline reproduction still reproduced after its fix in 2 of 3 runs of one fixture. Covering every consequence asks for more behavioural change per item and more approvals.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Automated Code Review In Practice](https://arxiv.org/abs/2412.18531) (Cihan et al., ICSE-SEIP 2025, Beko: 73.8% "Resolved" labels that the authors say may be misused); [RovoDev Code Reviewer](https://arxiv.org/abs/2601.01129) (Atlassian, ICSE-SEIP 2026: 38.7% of comments triggered code changes); [AutoCommenter](https://arxiv.org/abs/2405.13565) (Google, 2024: about 40% estimated); [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices) (Anthropic, 2026: "show evidence rather than asserting success"); [When and How Context Rot Appears in Coding Agents](https://arxiv.org/abs/2607.17937) (Xue, 2026 single-author preprint: 38 of 44 failed rows ended with a success claim) · dossier: final-report-and-impact G204-F07, G204-F06; skill-design T31-F13, T31-F20; eval-v2-calibration E02-F02; user-policy-autonomy U01-F02

### RP-17 — Every unapplied or partial finding has an explicit status and a reason
- **Rule:** Give every finding that was not applied one of `reported`, `deferred`, `blocked`, `reverted` or `rejected`, and every finding applied only in part the status `partial` (RP-16), with the reason in `notes` or `verifier_note`. A `reverted` finding names the gate or end-to-end check that failed and, when the end-to-end verifier reverted it, the revert commit and the verifier's reason (protocol-change PC-26); a `partial` finding names the consequence still open. An item an autonomous run kept report-only is `reported`, with the reason from its `report-only` row in `.harden/approvals.md` (user-policy-autonomy U01-F03). Mirror each "safe" or "won't fix" decision in SARIF as a `suppressions[]` entry with `status` and `justification`. Fill statuses from evidence (gate results, the diff guard), not by asking the user to label every item.
- **Detect:** `validate_findings.py` warns on deferred, blocked, rejected or reverted findings without a reason. `jq -r '.findings[] | select(.status=="partial" and (.notes // "") == "") | .id' .harden/findings.json` prints nothing. Each `sha` among the `reverts` of `.harden/verify.json`, other than a revert commit the verifier made earlier and undid in a range revert, is the `commit` of a finding with status `reverted` or `partial` (compare the first 7 characters). `jq '[.runs[].results[] | select(.suppressions != null) | select(any(.suppressions[]; (.justification // "") == ""))] | length' .harden/report.sarif` returns 0.
- **Not when:** This adds bookkeeping. Making a human label every item degrades label quality (Beko study), which is why statuses come from evidence. `partial` mirrors Trail of Bits' "Partially Resolved"; applying it on a re-run reproduction is the skill's own v2 calibration, not yet re-measured.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [NATS Server Security Assessment, appendix G](https://github.com/trailofbits/publications/blob/master/reviews/2025-04-ostif-nats-securityreview.pdf) (Trail of Bits, 2025: Undetermined / Unresolved / Partially Resolved / Resolved); [SonarQube security hotspots](https://docs.sonarsource.com/sonarqube-server/user-guide/security-hotspots) (To review / Acknowledged / Fixed / Safe); [SARIF v2.1.0 Plus Errata 01, §3.35](https://docs.oasis-open.org/sarif/sarif/v2.1.0/errata01/os/sarif-v2.1.0-errata01-os-complete.html) (suppression status and justification); [Automated Code Review In Practice, threats to validity](https://arxiv.org/html/2412.18531v2) (Cihan et al., 2025); [Handling pushback in code reviews](https://google.github.io/eng-practices/review/reviewer/pushback.html) (Google: cleanup promised for later "never happens") · dossier: final-report-and-impact G204-F19, G204-F11; industry-review-guidelines T02-F18; eval-v2-calibration E02-F02; user-policy-autonomy U01-F02, U01-F03

### RP-18 — Use CWE and ISO/IEC 25010 as vocabulary, never as a compliance claim
- **Rule:** When a CWE applies, put its id in `cwe`. File the finding under one of the four ISO/IEC 5055 characteristics:
  - Reliability (CWE-1306);
  - Maintainability (CWE-1307);
  - Security (CWE-1308);
  - Performance Efficiency (CWE-1309).

  Use ISO/IEC 25010 names only as vocabulary. Never write that the project is compliant, conformant or certified to any ISO standard on the strength of an agent review.
- **Detect:** `grep -niE 'ISO[ /-]*(IEC )?[0-9]+.{0,40}(complian|conform|certif)' .harden/report.md` returns nothing. `validate_findings.py` checks the `CWE-<n>` format.
- **Not when:** These caveats limit the mapping:
  - ISO/IEC 5055 is anchored to ISO/IEC 25010:2011 ("4 of the 8" characteristics). The 2023 model has 9, and 5055 measures neither of the new Flexibility and Safety.
  - MITRE's CWE-1307 omits CWE-1121 (McCabe complexity), which CISQ 2019 and OMG ASCQM v1.1 include. Map complexity by the ASCQM list.
  - MITRE marks quality weaknesses such as CWE-1085 as prohibited for vulnerability mapping, so never call them vulnerabilities.
  - iso25000.com places Testability under Maintainability; arc42 disagrees.
  - The ISO texts themselves were not read.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [List of Weaknesses Included in the CISQ Automated Source Code Quality Measures](https://www.it-cisq.org/pdf/cisq-weaknesses-in-ascqm.pdf) (CISQ, 2019); [Automated Source Code Quality Measures v1.1](https://www.omg.org/spec/ASCQM/1.1/PDF) (OMG, 2022); [ISO 5055: The First Standard of its Kind](https://www.it-cisq.org/2021/09/iso-5055-automated-source-code-quality-measures-the-first-standard-of-its-kind/) (CISQ, 2021); [CWE-1307](https://cwe.mitre.org/data/definitions/1307.html) (MITRE, CWE 4.20, 2026); [CWE-1085](https://cwe.mitre.org/data/definitions/1085.html) (MITRE, 2026); [ISO/IEC 25010](https://iso25000.com/index.php/en/iso-25000-standards/iso-25010?start=5) (iso25000.com) · dossier: standards T01-F01, T01-F09

### RP-19 — Ship a SARIF 2.1.0 companion
- **Rule:** Mirror every reported finding in `.harden/report.sarif`:
  - one run per tool, with `tool.driver` `name` and `version`, plus one run under a synthetic `tool.driver` for hand-written findings;
  - every result carries `partialFingerprints`;
  - the final run sets `baselineState`;
  - each invocation records `executionSuccessful` and `toolExecutionNotifications`;
  - suppressed results carry `suppressions[].status` and `justification`;
  - the finding id, severity and confidence rung go in each result's properties bag.
- **Detect:** Both commands must return 0:
  - `jq '[.runs[].results[] | select(.partialFingerprints == null and .fingerprints == null)] | length' .harden/report.sarif`
  - `jq '[.runs[].results[] | select(.baselineState == null)] | length'` on the final run.

  Failed invocations must be named in Limits (RP-09).
- **Not when:** Many linters need a converter. GitHub code scanning uses only `primaryLocationLineHash`, and it keeps only the top 5,000 results per run, prioritised by severity. No study shows that SARIF raises reader trust; its value here is that it makes the before/after claims auditable.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [SARIF Version 2.1.0 Plus Errata 01](https://docs.oasis-open.org/sarif/sarif/v2.1.0/errata01/os/sarif-v2.1.0-errata01-os-complete.html) (OASIS, 2023); [SARIF support for code scanning](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/sarif-support-for-code-scanning) (GitHub Docs, 2026) · dossier: final-report-and-impact G204-F11, G204-F12

### RP-20 — Report per-rule precision and track effective false positives across runs
- **Rule:** For each tool rule or lens category with hits, report one row: hits, sample size, true positives in the sample, and the decision. The decision is "fix in pass" at about 90% or more true positives in the sample; below that, report counts only. After the user decides, record accepted and rejected counts per category in `.harden/approvals.md` and compute rejected / (accepted + rejected). On a later run that finds a previous `approvals.md`, demote any category above 0.10 once n ≥ 10, and say so in the report. Rows the profile wrote (`auto (profile)` in the quote cell) set policy before any finding was seen and judge none of them, so leave them out of the ratio (user-policy-autonomy U01-F04); an autonomous run still reports the per-rule table.
- **Detect:** The report contains the per-rule table, and `.harden/approvals.md` holds per-category counts. No demotion rests on an `auto (profile)` row.
- **Not when:** A solo developer's reject can mean "not now", since developer actions reflect workflow pressure (Karakaya et al., EASE 2026). With few findings the ratio is noise. Google's 10% bar was "initially chosen ... somewhat arbitrarily".
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Lessons from Building Static Analysis Tools at Google](https://research.google/pubs/lessons-from-building-static-analysis-tools-at-google/) (Sadowski et al., CACM 2018: an effective false positive is a finding developers took no positive action on; analyzers above 10% are disabled); [Tricorder](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/43322.pdf) (Sadowski et al., ICSE 2015); [Error Prone: Criteria for new checks](https://errorprone.info/docs/criteria) (Google: WARNING checks right "at least 90% of the time"); [AutoCommenter](https://arxiv.org/abs/2405.13565) (Google, AIware 2024: useful ratio rose from 54% to 66% after non-actionable categories were suppressed) · dossier: final-report-and-impact G204-F05; standards T01-F15; user-policy-autonomy U01-F04

## Evidence limits
- **Severity.** The reliability evidence comes from CVSS and bug-tracker labels. No study measures agreement on non-security code-quality severity, so the rubric in RP-02 is unvalidated.
- **Syntheses, not tested designs.** The five-rung confidence ladder, the decision groups, the valid-delta list and the nit cap of 10 are syntheses or conventions (grades B to C).
- **Own calibration.** Limiting the nit cap to the main list, the deterministic confidence path for comments and unused imports, ordering `unknown` files with warm ones and the Open owner items section (RP-03, RP-06, RP-07) come from the skill's own v1 evaluation (3 fixtures, n = 2 per cell), not from an external study. The one-screen Summary with its three labelled lines, the `partial` status heading Open owner items and the `Proposed first step` line on T2 entries (RP-07, RP-08, RP-16, RP-17) come from its v2 evaluation (3 fixtures, n = 3 per cell) and are not yet re-measured.
- **Self-rating.** The evidence against self-rated severity is weak: a vendor anecdote (Greptile), 2023-era models on general QA (Xiong), and label agreement of 0.44-0.62 against developer labels that are themselves not ground truth (Karakaya, EASE 2026).
- **Proof for high findings (RP-04).** It rests on audit-contest rubrics and curl's bounty statistics, not on a trust study.
- **Delivery.** The evidence (Facebook, Google, Meta) comes from large companies with review workflows. Whether it transfers to a solo developer reading one report is unmeasured.
- **Fingerprints.** How often line-hash fingerprints split unchanged issues into absent plus new after refactors is unmeasured.
- **Coverage.** The coverage-effectiveness correlation is debated. Other studies, not re-checked here, report stronger correlations.
- **Effective false positives.** Google's 10% bar was set somewhat arbitrarily, and a solo developer's accept or reject is a noisy signal.
- **ISO.** ISO/IEC 25010:2023 and 5055:2021 were not read; the mapping comes from CISQ 2019 and OMG ASCQM v1.1. No peer-reviewed link between ISO 5055 weakness density and defects or effort was found.
- **SSVC.** The decision-oriented alternative to CVSS reached only fair agreement in its pre-v1 draft pilot.
- **Offline evidence (pilot-auto-calibration A01-F18, A01-F21).** The heuristic metric's numbers are not lizard's or any linter's, and the per-module end-to-end statement matches changed functions by name at file level, without source maps; both are this skill's own design, measured once (n = 1).
- **Autonomous mode.** The Applied, review before merge section and the `review` object it reads (user-policy-autonomy U01-F06, U01-F11 to U01-F13), the `Mode:` line, the Autonomous decisions and Reverted by end-to-end verification sections, item (j) of Limits, the `reverted` status set from the verifier's record and the exclusion of profile rows from the RP-20 ratio (RP-07, RP-08, RP-09, RP-16, RP-17, RP-20) follow the owner's policy (user-policy-autonomy U01-F01 to U01-F04). They are not a tested report design and have not been measured.
