# Lens: Numeric, money and time

> Purpose: find exact quantities held in binary floats, precision lost at parse, serialization and cast boundaries, silent overflow, undocumented or wrong rounding direction, token and feed scale mismatches, wall-clock durations, naive or unit-less timestamps, and numeric code changed without golden values. These bugs produce wrong values rather than crashes, so tests and generic linters rarely catch them.
> Read when: the scope handles money, prices, fees, balances, token amounts, order sizes, rounding, big integer IDs, timestamps, durations, timeouts, time zones or scheduled events, in any language.

## Rules

### NM-01 — Pin golden values before any numeric or time change
- **Rule:** Before proposing any numeric or time change, require characterization tests with golden outputs recorded over real historical inputs, in new test files. Then report each money, rounding or time module that lacks a property, invariant or fuzz test for: allocations sum to the total; parse/format round-trips are the identity; deposit-then-withdraw never profits; the pool invariant never decreases under repeated minimal operations; results match an arbitrary-precision oracle; behaviour holds under several host time zones and frozen clocks around DST and leap days. Per-operation tests miss cumulative adversarial effects (Check Point on Balancer, 2025).
- **Detect:** Per module, look for Hypothesis, fast-check, proptest, cargo-fuzz, Echidna, Medusa, Foundry invariant tests, freezegun or libfaketime in the tests; a missing test is the finding.
- **Not when:** Invariants need domain knowledge and weak ones give false comfort (Balancer had audits): propose them for the owner to confirm. Long fuzz campaigns cost CI time; propose them for nightly runs.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Balancer hack analysis](https://blog.trailofbits.com/2025/11/07/balancer-hack-analysis-and-guidance-for-the-defi-ecosystem/) (Trail of Bits, 2025); [Balancer rounding exploitation](https://research.checkpoint.com/2025/how-an-attacker-drained-128m-from-balancer-through-rounding-error-exploitation/) (Check Point, 2025); [It's About Time](https://rohan.padhye.org/files/datetimebugs-msr25.pdf) (Tiwari et al., MSR 2025); [Real-World Numerical Bug Characteristics](https://web.cs.ucdavis.edu/~rubio/includes/ase17.pdf) (Di Franco et al., ASE 2017) · dossier: numeric-money-time G103-F20

### NM-02 — Exact quantities that are booked, settled or ordered are not binary floats
- **Rule:** Flag binary floats (float, double, f32, f64, JS number) holding values that are booked, settled, sent as orders or compared for equality: fiat money, token amounts, order price and quantity, fees, balances, booked PnL. Recommend integer minor units with an explicit scale (int, BigInt, i128/u128, uint256) or a decimal type (Python `decimal.Decimal`, Rust `rust_decimal`, JS big.js, decimal.js or bignumber.js). C++ has no standard decimal type; C23 `_Decimal32/64/128` exist only in C and only when `__STDC_IEC_60559_DFP__` is defined.
- **Detect:** No lint in TS, Python, Rust, C++ or Solidity flags this; use untested name heuristics plus the value-flow table. TS: `ast-grep -p 'parseFloat($X)'`, `ast-grep -p 'Number($X)'`, `rg -n "(price|amount|qty|quantity|size|balance|fee|notional|pnl)\w*\??\s*:\s*number" -t ts`. Python: `rg -n "float\(.*(price|amount|qty|balance|fee|notional)" -t py`, float64 money columns in pandas or NumPy. Rust: `rg -n "(price|amount|qty|balance|fee)\w*\s*:\s*f(32|64)" -t rust`. C++: `rg -n "(double|float)\s+\w*(price|amount|qty|balance|fee)"`. SQL: money columns REAL, DOUBLE PRECISION or FLOAT.
- **Not when:** Model outputs and approximate quantities where float error "is swamped by the errors in your models" (HN practitioners). Integer cents struggle with division, interest and VAT, minor-unit exponents differ per currency, and 18-decimal token amounts overflow int64, so pick the representation per domain. Decimal types are slower (CWE-1339 mitigation note). The representation change stays T2; an exact equality check on such a value that the code relies on is also an NM-16 candidate, whose tolerance fix can be T1 under the step 7 promise test.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [FLP02-C](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/recommendations/floating-point-flp/flp02-c) (SEI CERT); [CWE-1339](https://cwe.mitre.org/data/definitions/1339.html) (MITRE, 4.20); [decimal](https://docs.python.org/3/library/decimal.html) (PSF, 3.14); [CCXT CONTRIBUTING](https://raw.githubusercontent.com/ccxt/ccxt/master/CONTRIBUTING.md) (CCXT, 2026); [Supported currencies](https://docs.stripe.com/currencies) (Stripe, 2026); [HN 22322636](https://news.ycombinator.com/item?id=22322636) (2020); [Real-World Numerical Bug Characteristics](https://web.cs.ucdavis.edu/~rubio/includes/ase17.pdf) (Di Franco et al., ASE 2017) · dossier: numeric-money-time G103-F01; eval-v1-calibration E01-F07

### NM-03 — Construct exact values from strings or integers, never through a float
- **Rule:** Flag exact types built from floats. Python: `Decimal('0.1')`, not `Decimal(0.1)`; parse JSON with `json.loads(..., parse_float=Decimal)`. Rust: rust_decimal `from_str`, `from_i128_with_scale` or `Decimal::new`, not `from_f64` or `from_f64_retain`. JS: strings into big.js or decimal.js with `Big.strict`; decimal strings into ethers `parseUnits`. `Decimal(float('1.1'))` is `Decimal('1.100000000000000088817841970012523233890533447265625')`; rust_decimal `from_f64` drops digits past about 15.95 significant digits but keeps any error already accumulated in float arithmetic.
- **Detect:** Ruff `RUF032` (its fix is marked unsafe because it changes the value; do not apply it); `rg -n "Decimal\((float|str\(float)" -t py`; `json.loads` on exchange payloads without `parse_float=Decimal`; `rg -n "from_f(32|64)(_retain)?|Decimal::try_from\(.*f64" -t rust`; `ast-grep -p 'new Big($X)'` and `ast-grep -p 'new Decimal($X)'` with non-string arguments; `rg -n "parse(Units|Ether)\([^'\"]+\.toString\(\)" -t ts`. For a reproduction, a new test can trap `decimal.FloatOperation`.
- **Not when:** The source really is a float (a model output): rust_decimal `from_f64` is the reasonable conversion there. Trapping FloatOperation in production turns silent drift into exceptions; propose it in tests first.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [decimal constructor and FloatOperation](https://docs.python.org/3/library/decimal.html) (PSF, 3.14); [RUF032](https://docs.astral.sh/ruff/rules/decimal-from-float-literal/) (Astral); [big.js Big.strict](https://mikemcl.github.io/big.js/) (Mclaughlin, v7); [rust_decimal::Decimal](https://docs.rs/rust_decimal/latest/rust_decimal/struct.Decimal.html) (1.43.0); [ethers units.ts](https://raw.githubusercontent.com/ethers-io/ethers.js/main/src.ts/utils/units.ts) (ethers v6.17.0); [json parse_float](https://docs.python.org/3/library/json.html) (PSF) · dossier: numeric-money-time G103-F02

### NM-04 — JS integers above 2^53−1 never pass through Number
- **Rule:** In JS/TS, flag any path where an integer that can exceed 2^53−1 becomes a Number: exchange order and trade IDs, Snowflake IDs, wei amounts, nanosecond timestamps. `JSON.parse('1234567890123456789')` returns 1234567890123456800, and an off-by-a-few ID still looks valid, so cancels fail (community Gate.io SDK, 2026, still open). Recommend a `JSON.parse` reviver reading `context.source` (Stage 4, Baseline since 2025-03-31: Chrome 114, Firefox 135, Safari 18.4; works on Node 24.13), `lossless-json` on older runtimes, IDs kept as strings, and `Number.isSafeInteger` asserts where a number is unavoidable.
- **Detect:** ESLint `no-loss-of-precision` checks source literals only, so a clean run says nothing about parsed data. `rg -n "JSON\.parse\(|\.json\(\)|response\.data" -t ts` in adapters, cross-checked against int64 fields in the API schema; `ast-grep -p 'Number($X.orderId)'`; `rg -n "parseInt\(.*[Ii]d\b" -t ts`. Reproduce with a fixture ID of 1234567890123456789.
- **Not when:** Switching number to string or bigint changes equality (`0n == 0` is true, `0n === 0` is false), Map keys and `JSON.stringify` (throws on BigInt): change only at the parse boundary, with tests. If the type is exported or persisted it is a public API or schema change: report as T2. json-bigint has had no release since 1.0.0 (2020-07-14); keep it for legacy code only.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [RFC 7493 §2.2](https://www.rfc-editor.org/rfc/rfc7493.html) (IETF, 2015); [Number.MAX_SAFE_INTEGER](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/MAX_SAFE_INTEGER) (MDN); [proposal-json-parse-with-source](https://github.com/tc39/proposal-json-parse-with-source) (TC39); [JSON.parse](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/JSON/parse) (MDN); [X IDs](https://docs.x.com/fundamentals/x-ids) (X); [Snowflakes](https://docs.discord.com/developers/reference) (Discord); [no-loss-of-precision](https://eslint.org/docs/latest/rules/no-loss-of-precision) (ESLint v10.11); [gateio-api #101](https://github.com/sieblyio/gateio-api/issues/101) (sieblyio, 2026) · dossier: numeric-money-time G103-F03

### NM-05 — Send exact amounts and 64-bit IDs as strings at serialization boundaries
- **Rule:** Report outbound payloads that send exact amounts or 64-bit IDs as JSON numbers (RFC 7493 recommends strings for integers beyond 2^53−1) or let an SDK stringify floats: `str(0.1 + 0.2)` is `0.30000000000000004`, which can get orders rejected or mis-sized. Recommend pre-formatted decimal strings snapped to tickSize and stepSize. Treat a change of an int64 field between number and string as a breaking change covered by contract tests.
- **Detect:** Python `rg -n "str\((price|qty|quantity|amount)" -t py`; TS `rg -n "JSON\.stringify\(" -t ts`, `ast-grep -p 'String($X)'` and `$X.toString()` on number amounts (can produce exponent notation); contract tests with recorded fixtures.
- **Not when:** Strings push parsing onto every consumer and lose schema numeric typing unless annotated (for example `x-bigint`). Do not generalise "APIs are moving to string int64": one exchange spec (Gemini Titan, July 2026, reported in a third-party issue) does so. The binance-connector-python `str(val)` report (2026, Informational) is unconfirmed by maintainers, though the code path exists.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [RFC 7493](https://www.rfc-editor.org/rfc/rfc7493.html) (IETF, 2015); [json](https://docs.python.org/3/library/json.html) (PSF); [binance-connector-python #514](https://github.com/binance/binance-connector-python/issues/514) (2026); [pmxt #1878](https://github.com/pmxt-dev/pmxt/issues/1878) (2026) · dossier: numeric-money-time G103-F21

### NM-06 — Integer overflow in value-handling code fails loudly
- **Rule:** Report silent wraparound on money and size paths. Rust release builds wrap because Cargo's release profile defaults to `overflow-checks = false`; recommend `overflow-checks = true` for financial crates (Solana Foundation examples set it in 49 Cargo.toml files) or explicit `checked_*`, `saturating_*`, `wrapping_*`. Solidity 0.8 does not check inside `unchecked`, on explicit conversions (which "always truncate") or on bitwise operators: each `unchecked` block needs a written bounds proof, each downcast OZ SafeCast. C/C++: checked-arithmetic helpers (CWE-190 names SafeInt and IntegerLib). NumPy: `np.array([2**31-1], dtype=np.int32) + 1` gives `[-2147483648]` with no warning (NumPy 2.4.3, win32).
- **Detect:** `rg -n "overflow-checks" -g Cargo.toml` (absent means false in release); Clippy `arithmetic_side_effects` (restriction, since 1.64.0) scoped to money modules; `rg -n "unchecked\s*\{" -g "*.sol"`; `rg -n "\bu?int(8|16|32|40|48|64|96|112|128|160|192|224)\(" -g "*.sol"`; Decurity `basic-arithmetic-underflow` (low confidence per its own metadata); `rg -n "int32|uint32|int16|astype\(np\.u?int(8|16|32)" -t py`; manual review of C/C++ size and amount arithmetic.
- **Not when:** Hash, PRNG and checksum code wraps on purpose (expect explicit `wrapping_*` there). Turning checks on changes silent wrap into a panic or revert and costs runtime and gas (RFC 560). Whether to enforce or only flag overflow checks is unresolved in the evidence: report, do not auto-fix.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Cargo Profiles](https://doc.rust-lang.org/cargo/reference/profiles.html) (Rust project); [RFC 0560](https://rust-lang.github.io/rfcs/0560-integer-overflow.html) (Rust, 2014); [Clippy operators](https://raw.githubusercontent.com/rust-lang/rust-clippy/master/clippy_lints/src/operators/mod.rs) (Clippy); [counter/anchor Cargo.toml](https://raw.githubusercontent.com/solana-foundation/program-examples/main/basics/counter/anchor/Cargo.toml) (Solana Foundation); [Checked or Unchecked Arithmetic](https://docs.soliditylang.org/en/latest/control-structures.html) (Solidity 0.8); [SafeCast.sol](https://raw.githubusercontent.com/OpenZeppelin/openzeppelin-contracts/master/contracts/utils/math/SafeCast.sol) (OpenZeppelin); [Smart Contract Top 10 SC08](https://owasp.org/www-project-smart-contract-top-10/) (OWASP, 2025); [Data types](https://numpy.org/doc/stable/user/basics.types.html) (NumPy 2.5); [CWE-190](https://cwe.mitre.org/data/definitions/190.html) (MITRE) · dossier: numeric-money-time G103-F09

### NM-07 — Lossy numeric casts are explicit and checked
- **Rule:** Flag casts that can lose range or precision without a check. Rust `as` truncates integers (`1234u16 as u8 == 210`), saturates out-of-range floats, maps NaN to 0 and rounds int-to-float ties to even (`123_456_789i32 as f32 == 123_456_790f32`): prefer `TryFrom`/`try_into`. C/C++: CERT FLP36-C shows `long` 1234567890 converted to `float` off by 46. Solidity: SafeCast. JS: no `Number(bigint)` in arithmetic.
- **Detect:** Clippy `cast_possible_truncation`, `cast_precision_loss`, `cast_sign_loss`, `cast_possible_wrap` (pedantic) scoped to money and time modules; `rg -n " as (u|i)(8|16|32|64|128)\b| as f(32|64)\b" -t rust`; clang-tidy `bugprone-narrowing-conversions` (alias `cppcoreguidelines-narrowing-conversions`); the Solidity downcast pattern in NM-06; `ast-grep -p 'Number($X)'` filtered to bigint operands.
- **Not when:** Casts provably in range; the pedantic cast lints are noisy, so keep them to money and time paths. `try_from` adds an error path (wrong value becomes an error): the change needs a test for that path.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [Operator expressions](https://doc.rust-lang.org/reference/expressions/operator-expr.html) (Rust Reference); [casts/mod.rs](https://raw.githubusercontent.com/rust-lang/rust-clippy/master/clippy_lints/src/casts/mod.rs) (Clippy); [FLP36-C](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/rules/floating-point-flp/flp36-c) (SEI CERT); [bugprone-narrowing-conversions](https://clang.llvm.org/extra/clang-tidy/checks/bugprone/narrowing-conversions.html) (LLVM); [CWE-681](https://cwe.mitre.org/data/definitions/681.html) and [CWE-197](https://cwe.mitre.org/data/definitions/197.html) (MITRE) · dossier: numeric-money-time G103-F10

### NM-08 — Rounding direction in value-moving math is explicit, favours the protocol, and is backed by invariants
- **Rule:** Every rounding in deposits, withdrawals, mints, redeems, swaps, fees, interest and liquidations (on-chain and in off-chain ledgers) needs an explicit direction that favours the protocol or vault over the caller, through a helper that takes it as an argument (OZ `Math.mulDiv(x, y, d, Rounding.Ceil)`). Require with it documented rounding invariants with informal proofs and multi-operation invariant tests: Trail of Bits calls "rounding must favor the protocol" "insufficient to capture edge cases that may occur during a multi-operation user flow". A deliberate exception needs a bound: worst-case loss per call times the calls an attacker can make in one transaction. Treat comments calling rounding impact "minimal", "negligible" or "dust" as findings: Balancer v2 `_upscale` rounded down under such a comment and lost over $100M (Trail of Bits, nine networks) to $128.64M (Check Point, six networks) on 3 Nov 2025, with 8-9 wei balances giving up to 10% loss per operation across a 65-operation `batchSwap`; KyberSwap Elastic lost over $48M (23 Nov 2023) through `mulDivFloor` where rounding up was needed, combined with a missed tick-crossing check.
- **Detect:** `rg -n "mulDown|divDown|mulDivDown|mulDivFloor|mulWadDown|divWadDown|Rounding\.(Floor|Trunc)|mulDivUp|mulWadUp|divUp" -g "*.sol"` plus plain `/` in value-moving functions; record the intended beneficiary per site; `roundme analyze` for compound formulas (early-stage: one release, 0.1.0, Nov 2023); `rg -n -i "(round|precision|dust|truncat).{0,80}(minimal|negligible|insignificant|small enough|doesn.t matter)"`; check for Echidna, Medusa or Foundry invariant tests such as deposit-then-redeem never returns more than deposited.
- **Not when:** Favouring the protocol leaves 1-wei dust and breaks exact-output operations such as "withdraw max", which need a UX workaround. A 1-unit change breaks integrators and immutable contracts often cannot take it: report a mitigation. Off-chain there is no ERC-4626-style standard, so the rule is an extrapolation there: use `needs_review`.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [ERC-4626](https://eips.ethereum.org/EIPS/eip-4626) (Ethereum EIPs, 2021); [ScalingHelpers.sol](https://github.com/balancer/balancer-v2-monorepo/blob/master/pkg/solidity-utils/contracts/helpers/ScalingHelpers.sol) (Balancer); [Balancer hack analysis](https://blog.trailofbits.com/2025/11/07/balancer-hack-analysis-and-guidance-for-the-defi-ecosystem/) (Trail of Bits, 2025); [Balancer rounding exploitation](https://research.checkpoint.com/2025/how-an-attacker-drained-128m-from-balancer-through-rounding-error-exploitation/) (Check Point, 2025); [Understanding the Balancer v2 Exploit](https://www.openzeppelin.com/news/understanding-the-balancer-v2-exploit) (OpenZeppelin, 2025); [KyberSwap incident](https://blocksec.com/blog/kyberswap-incident-masterful-exploitation-of-rounding-errors-with-exceedingly-subtle-calculations) (BlockSec, 2023); [Math.sol](https://raw.githubusercontent.com/OpenZeppelin/openzeppelin-contracts/master/contracts/utils/math/Math.sol) (OpenZeppelin); [roundme](https://github.com/crytic/roundme) (Trail of Bits, 2023) · dossier: numeric-money-time G103-F06

### NM-09 — One documented rounding policy per domain; defaults differ per ecosystem
- **Rule:** Report domains (order sizing, fees, tax, interest, display, settlement) without one documented policy: mode, scale, and the pipeline point where rounding happens, implemented in one helper per language. Flag ad-hoc `round()`, `toFixed()`, `Math.round(x*100)/100` and `(int)(x+0.5)`. Order price and quantity must be snapped to tickSize and stepSize in decimal arithmetic with an explicit direction (Binance: `price % tickSize == 0`, `quantity % stepSize == 0`). ### NM-10 — Multiply before dividing with a full-precision mulDiv; flag quotients that can round to zero
- **Rule:** In integer and fixed-point arithmetic, flag division before multiplication and any quotient that can be 0 for realistic inputs and then serves as a multiplier, share count or fee. Integer division truncates toward zero in Solidity, Rust, C++ and BigInt, so `(a / n) * k` is 0 when `n > a`. Recommend a full-precision (512-bit intermediate) mulDiv so reordering cannot overflow.
- **Detect:** Slither `divide-before-multiply` (Medium severity, Medium confidence); ast-grep `($A / $B) * $C` for Solidity and TS bigint, `($A // $B) * $C` for Python; Clippy `integer_division` flags every division (triage list only); clang-tidy `bugprone-integer-division` catches only integer division in a float context, and C/C++ has no dedicated check. Manual: for each division, can the result be 0?
- **Not when:** Deliberate truncation, such as bucketing into epochs. Naive reordering can overflow fixed-width integers and in Solidity 0.8+ revert (a DoS); Slither itself says "unless the limit of a smaller type makes this dangerous", so recommend mulDiv, not reordering.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A

- **Detect:** `rg -n "timezone\(timedelta\(hours|FixedOffset|UTC[+-][0-9]|[+-]0[0-9]:00['\"]|Etc/GMT[+-]" -g "*.{py,ts,js,rs}"`; `rg -n "\.replace\(year=" -t py`; schema review of scheduled and expiry columns. - **Not when:** Instants that already happened (UTC or epoch integers are correct and simpler). Fixed offsets for zones without DST (the MSR 2025 false positive was UTC+8 for Shanghai).

## False-positive exclusions

- Floats in models, forecasts and approximate estimates that are never booked, settled, sent as orders or compared for equality (NM-02).
- Display-only conversions to Number or float that never feed back into arithmetic (NM-02, NM-12).
- rust_decimal `from_f64` on values that really are floats, such as model outputs (NM-03).
- Hash, PRNG and checksum code that wraps on purpose (NM-06).
- Casts provably in range (NM-07); pedantic Clippy cast hits outside money and time paths.
- Exact float comparison against sentinels or exactly representable values (NM-16).
- Deliberate truncation, such as bucketing timestamps into epochs (NM-10).
- float32 for ML features (NM-15).
- Immutable token decimals pinned explicitly and tested at listing time (NM-13).
- Trapped-Inexact proposals on legitimately inexact operations such as division and interest (NM-14).
- Naive datetimes for wall-clock concepts such as opening hours (NM-19); UTC or epoch integers for instants that already happened (NM-22).
- Fixed offsets for zones without DST (NM-22); expect most fixed-offset and `replace(year=...)` hits to be false (1 of 23 and 2 of 37 true in MSR 2025).
- JS Date holding epoch-millisecond instants with no parsing or calendar math (NM-20).
- Wall-clock timestamps that leave the process, including signed exchange request timestamps (NM-18).
- Solidity `unchecked` blocks that carry a written bounds proof (NM-06).

## Evidence limits

- No lint in TS, Python, Rust, C++ or Solidity detects a binary float used for money or token amounts. Every rg and ast-grep pattern in this file is an untested heuristic with unmeasured precision and recall.
- The headline numerical-bug figures (77% wrong results, 4% detectable by simple patterns, accuracy bugs 14%) come from 269 bugs in numerical libraries (NumPy, SciPy, LAPACK, GSL, Elemental; ASE 2017). The authors note such bugs are less numerous in general-purpose applications; applying them to app or bot code is an extrapolation.
- The date/time figures come from 151 bugs in open-source Python software (MSR 2025); other languages are covered by analogy only.
- No peer-reviewed study measures float-for-money or ID-precision bugs in application or bot code. The off-chain evidence is practitioner issues, several open or unconfirmed (Gate.io community SDK #101, binance-connector-python #514, WooCommerce #65997).
- Balancer v2 loss figures differ by source: over $100M across nine networks (Trail of Bits), over $120M including forks (OpenZeppelin), $128.64M across six networks (Check Point). The root cause is consistent.
- The OWASP Smart Contract Top 10 (2025) has an integer overflow category (SC08) but none for precision loss or rounding direction.
- "Favour the protocol" has no off-chain standard equivalent to ERC-4626 beyond the Money and allocation pattern; NM-08 is extrapolated to off-chain ledgers.
- Unresolved in the evidence: whether to enforce or only flag Rust release overflow checks; which JS decimal library to recommend (TC39 Decimal is Stage 1, Amount Stage 2, and the libraries round differently by default); when Temporal can be recommended without a polyfill.
- Version facts were checked on 2026-09-23 (ethers 6.17.0, viem 2.56.8, rust_decimal 1.43.0, NumPy docs 2.5, ESLint docs 10.11, Solidity 0.8.37/0.8.38, CWE 4.20). Re-check before citing a version gate on a later run.
- roundme has one release (0.1.0, Nov 2023) and Decurity `basic-arithmetic-underflow` is rated low confidence by its own metadata; treat their hits as `needs_review`.
- Not verified, so never assert: the Resupply (June 2025), Sonne Finance (May 2024) and Raft (Nov 2023) incidents; the Effective Java 3rd-edition item number.
- The step 7 promise test and the T1 tiers it grants in NM-16 and NM-20 come from the skill's own paired evaluation (eval-v1-calibration E01-F07, n = 2 runs per cell), not from an external study; it changes when a fix is offered, never the evidence a rule cites.
