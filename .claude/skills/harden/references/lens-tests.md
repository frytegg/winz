# Lens: Tests

> Purpose: decide whether the existing suite can serve as the behaviour oracle for the pass, find tests that cannot fail and code that no test protects, and propose only new, test-only safety nets (characterization, pinning, killing, property and fuzz tests).
> Read when: the repository has test files or a test command, or the pass will add tests or run mutation, property or fuzz testing.

- False-positive exclusions
- Evidence limits

## Rules

### TQ-01 — Existing tests are the frozen oracle
- **Rule:** Never remove or change a line of an existing test; the one exception is lens-dead-code DC-15's deletion-only change in a `refactor(dead-code):` commit. An existing test file only gains lines under protocol-change PC-06's checked additions (user-policy-autonomy U01-F07): in a `test(<scope>): strengthen` commit that changes no production file, or as a behavioural fix's demonstrating test case when the base version of every strengthened file still passes with the fix (`strengthen.py replay`). A structural change must pass the suite with every existing test line unchanged and the same collected-test count, less the cases recorded for DC-15. When a candidate would force an existing test line to change, classify the cause as an observable behaviour change (escalate) or an implementation-coupled test (report under TQ-20).
- **Detect:** Flag commits in `git log --name-only --format='--%h' <base>..HEAD` that mix test paths with non-test paths, other than DC-15 `refactor(dead-code):` commits on recorded paths and behavioural commits whose test changes are checked additions (PC-06). For each production-only step, `git diff --quiet <step-base> -- <test globs>` must succeed. Compare `pytest --collect-only -q`, `go test -list . ./...` (top-level tests only) and `jest --listTests` (a file count, not a test count) before and after. `diff_guard.py` flags removed or changed lines of existing tests, and additions its checks refuse, over base..HEAD plus the working tree and for each commit; `strengthen.py replay` runs the base versions of strengthened files; `gates.py --min-count-from baseline` compares test counts per item.
- **Not when:** A deliberate public-API change needs mechanical test updates; that is a T2 API finding. Test setup may legitimately change when a constructor gains a dependency (Trenk 2013), but the pass still reports it rather than editing. The rule rests on the definition of refactoring and Google guidance, not on an experiment.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [SWE at Google ch. 12](https://abseil.io/resources/swe-book/html/ch12.html) (Google, 2020); [Definition Of Refactoring](https://martinfowler.com/bliki/DefinitionOfRefactoring.html) (Fowler, 2004); [TotT: Test Behavior, Not Implementation](https://testing.googleblog.com/2013/08/testing-on-toilet-test-behavior-not.html) (Trenk, Google, 2013) · dossier: test-quality T13-F01; dead-code-certainty G102-F14; user-policy-autonomy U01-F07

### TQ-02 — Trust only a recorded multi-run, random-order baseline
- **Rule:** Before a finding relies on the suite as an oracle, confirm a recorded baseline of several full runs (time-boxed, e.g. 3-10). At least one run must use random order and one must use CI's parallelism, and the baseline must record per-test outcomes, the collected count, runtime and coverage. Exclude any test that is unstable across runs from the oracle and report it (TQ-03); a red or unstable baseline means report-only.
- **Detect:** pytest-randomly (the seed is printed; reproduce with `--randomly-seed`); `jest --randomize` (jest-circus only; `--seed=<n>`); `go test -shuffle=on -count=N -race`. Diff per-test outcomes across the JUnit/JSON reports in `.harden/gates/`, and take the count from `pytest --collect-only -q`.
- **Not when:** Very slow E2E suites may allow only one or two runs; say so. Gruber et al. estimate that about 170 reruns are needed for 95% confidence that a passing test is not flaky (876,186 Python tests, ICST 2021), so the baseline is only a lower bound, and the report must say so.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Flaky Tests at Google](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html) (Micco, Google, 2016: about 1.5% of runs flaky, almost 16% of tests with some flakiness); [An Empirical Analysis of Flaky Tests](https://mir.cs.illinois.edu/lamyaa/publications/fse14.pdf) (Luo et al., FSE 2014: 78% of flaky tests were flaky when first written); [Flaky Tests in Python](https://arxiv.org/abs/2101.09077) (Gruber et al., ICST 2021); [Jest CLI](https://jestjs.io/docs/cli) (Jest); [go command](https://pkg.go.dev/cmd/go) (Go); [pytest-randomly](https://github.com/pytest-dev/pytest-randomly) (pytest-dev) · dossier: test-quality T13-F02

### TQ-03 — Treat an unstable test as an open defect report
- **Rule:** Never turn the suite green by adding retries or reruns, raising timeouts, skipping, marking a test non-strict xfail or deleting it. Give each unstable test a root-cause category (async wait, concurrency, order dependency, time, network, randomness, resource leak, infrastructure) and report it as a possible product bug. Quarantine is acceptable only as an owner-tracked, time-boxed state, never as the fix.
- **Detect:** `rg -n "@pytest\.mark\.flaky|--reruns|reruns=|jest\.retryTimes|retries:|@RepeatedTest|@Disabled|@Ignore|t\.Skip\(|\bit\.skip|\bxit\(|xfail\("` over tests and CI config. Diff the pass's own changes for added retries, timeouts or skips. Categories follow Luo et al.: Async Wait accounted for 45% of 161 categorised fix commits in 51 mostly-Java Apache projects.
- **Not when:** Reruns and quarantine are documented mitigations at Google and Uber, so an existing ticketed quarantine is not a finding by itself. A recorded temporary exclusion to unblock main is legitimate. Buildkite did this in 2026, and the cause turned out to be a use-after-free in a C extension.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [Flaky Tests at Google](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html) (Micco, Google, 2016); [How a flaky test exposed a Redis client use-after-free](https://buildkite.engineering/how-a-flaky-test-exposed-a-redis-use-after-free/) (Robinson, Buildkite, 2026); [Flaky tests](https://docs.pytest.org/en/stable/explanation/flaky.html) (pytest docs); [Flaky Tests Overhaul at Uber](https://www.uber.com/blog/flaky-tests-overhaul/) (Uber, 2024) · dossier: test-quality T13-F03

### TQ-04 — Fix order dependence through isolation, never by pinning order
- **Rule:** When random order exposes a failure, report the isolation defect (the polluting test's cleanup, the fixture scope, or shared module-level or global state) together with the reproducing seed. Report any ordering pin as a finding; the pass never adds one.
- **Detect:** Reuse the TQ-02 random-order runs. Run each suspect test alone (`pytest path::test`, `go test -run '^Name$'`, `jest -t 'name'`). `rg -n "pytest\.mark\.order|@TestMethodOrder|@FixMethodOrder|@Order\(|pytest-order"`. Look for module-level mutable state, and for `setUpClass`/`beforeAll`/session fixtures that tests write to.
- **Not when:** A deliberate scenario sequence belongs in one test or an explicit sequence, not in runner order. Order dependence caused 59% of 7,571 flaky Python tests (ICST 2021) but 12% of 161 fix commits in mostly-Java projects (FSE 2014); weight Python suites accordingly.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Flaky Tests in Python](https://arxiv.org/abs/2101.09077) (Gruber et al., ICST 2021); [An Empirical Analysis of Flaky Tests](https://mir.cs.illinois.edu/lamyaa/publications/fse14.pdf) (Luo et al., FSE 2014); [Flaky tests](https://docs.pytest.org/en/stable/explanation/flaky.html) (pytest docs) · dossier: test-quality T13-F05

### TQ-05 — Report nondeterminism sources in tests
- **Rule:** Report fixed sleeps, wall-clock reads, unseeded randomness, real network/disk/process use in small tests, and exact float equality, starting with tests that were unstable in TQ-02. New tests written by the pass use condition waits or fake timers, injected clocks, seeded generators and tolerances from the start.
- **Detect:** In test files, run `rg -n "Thread.sleep|time.sleep|asyncio.sleep|\bsleep\(|setTimeout\(|Date.now\(|new Date\(\)|datetime.now|time.Now\(|Math.random|random.(random|randint|choice)|requests.(get|post)|fetch\(|http.Get"`. Also look for exact float comparisons: `assertEquals(double, double)` without a delta, or `==` between floats (pytest.approx is the tolerance tool).
- **Not when:** Leave tests that exist to check real timing (TTL, rate limits, performance) or real network contracts; label them as larger or integration tests. Fake timers can hide real concurrency bugs.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [An Empirical Analysis of Flaky Tests](https://mir.cs.illinois.edu/lamyaa/publications/fse14.pdf) (Luo et al., FSE 2014: 54% of Async Wait fixes used waitFor); [SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html) (Google, 2020); [Flaky Tests in Python](https://arxiv.org/abs/2101.09077) (Gruber et al., ICST 2021); [Flaky tests](https://docs.pytest.org/en/stable/explanation/flaky.html) (pytest docs) · dossier: test-quality T13-F04

### TQ-06 — Audit focused, disabled, commented-out and non-strict xfail tests
- **Rule:** Report a committed focused test (`.only`, `fit`, `fdescribe`) as blocking: it silently disables the rest of the suite, so the baseline stays invalid until the owner removes it. Removing the marker edits an existing test, so it is a T2 finding for the owner, never offered as an approvable test-only commit (invariant 2, PF-13). Report every skip or ignore that lacks a reason and a ticket, every commented-out test, and every non-strict xfail; strict xfail turns an unexpected pass into a failure.
- **Detect:** ESLint `jest/no-focused-tests`, `jest/no-disabled-tests`, `jest/no-commented-out-tests`, or the `vitest/*` equivalents. `rg -n "\b(describe|it|test)\.only\(|\bfit\(|\bfdescribe\(|\.(skip)\(|\bxit\(|\bxdescribe\(|@Disabled|@Ignore\b|t\.Skip\(|pytest\.mark\.(skip|skipif|xfail)|#\[ignore\]"`. pytest `strict_xfail` (older name `xfail_strict`), or `strict = true` from pytest 9.0. Compare collected and executed counts in CI reports.
- **Not when:** Platform- or environment-conditional skips that give a reason are fine, as is Rust `#[ignore]` on slow tests that run separately. Long-disabled tests that fail again go through TQ-03; they are not re-skipped.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [jest/no-focused-tests](https://github.com/jest-community/eslint-plugin-jest/blob/main/docs/rules/no-focused-tests.md) (jest-community); [How to use skip and xfail](https://docs.pytest.org/en/stable/how-to/skipping.html) (pytest docs); [pytest changelog](https://docs.pytest.org/en/stable/changelog.html) (pytest 9.0.0, 2025); [@vitest/eslint-plugin](https://github.com/vitest-dev/eslint-plugin-vitest) (Vitest) · dossier: test-quality T13-F18; eval-v1-calibration E01-F04

### TQ-07 — Find tests that cannot fail, and pin their contract in place or in a new test file
- **Rule:** Report tests that cannot fail: tests with no assertion, assertions swallowed by try/catch, conditional assertions that may never run, async assertions never awaited or returned, and tests that assert only on their own mocks. Rank them by the criticality of the code they claim to cover. The fix for each confirmed one is test-only and, where protocol-change PC-06's checked additions allow it, in place (user-policy-autonomy U01-F07): assertions added at the tail of the hollow test's body, in their own `test(<scope>): strengthen <test> (<finding id>)` commit, that pin the contract the hollow test claims to check (taken from its name, docstring and calls, and from the code's docs), assert observable behaviour through the public API (TQ-16), pass against the base's production code, and fail on a deliberate fault in that contract under which the hollow test's base version passes (TQ-17). When those checks refuse the lines the contract needs (a nested block, a new helper, a mock), the fix is a new test file that pins the same contract the same way. When the expected values are copied from current output, label the added assertions or the new file a characterization test and send any output that contradicts the hollow test's stated contract to the suspected-bugs list (TQ-18). Deleting the hollow test stays the owner's T2 item (under Needs your decision, RP-07), never applied by the pass (TQ-24).
- **Detect:** Jest rules `jest/expect-expect`, `jest/valid-expect`, `jest/valid-expect-in-promise`, `jest/no-conditional-expect`. Vitest rules `vitest/expect-expect`, `vitest/valid-expect`, `vitest/no-conditional-expect`, `vitest/require-awaited-expect-poll`. PMD `UnitTestShouldIncludeAssert` (named JUnitTestsShouldIncludeAssert before PMD 7.7.0), with `extraAssertMethodNames` set for custom helpers. Python: ast-grep for `def test_` with no `assert`, `pytest.raises` or `self.assert*`, and `rg -n "except.*:\s*(pass|\.\.\.)" tests/`. Each candidate names the contract, the assertions to add at the hollow test's tail (or the new file's path) and the deliberate fault. The orchestrator applies that fault in a scratch worktree: the hollow test staying green is the reproduction. At apply time the strengthened test (or the new file) must fail under the same fault, while the hollow test's base version still passes under it, and pass after the restore.
- **Not when:** Intentional smoke tests ("does not throw") are legitimate; report them only if the intent is implicit rather than written as `expect(fn).not.toThrow()` or `assertDoesNotThrow`. Custom assertion helpers produce false positives until they are configured. A contract that cannot be pinned without changing an existing test line, fixture or test config, or without a production seam, gets no pinning test: mark the item blocked and report the seam (TQ-25). The pinning-test remedy rests on this skill's own paired evaluation, not on the studies cited for detection (grade B, n = 2 per cell): the one run that added a pinning file was graded fixed, and the five runs that only reported the hollow test left no oracle behind. In the first autonomous pilot (n = 1) a pinning file next to the untouched hollow test was graded partial (D22), which the in-place remedy addresses; the in-place remedy is unmeasured.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [Assertions Are Strongly Correlated with Test Suite Effectiveness](https://people.ece.ubc.ca/amesbah/resources/papers/fse15.pdf) (Zhang & Mesbah, FSE 2015, 6,700 suites of five Java projects); [Unit Testing Ch. 1 excerpt](https://enterprisecraftsmanship.com/files/Unit-Testing-Chapter-1-Excerpt.pdf) (Khorikov, 2020); [eslint-plugin-jest](https://github.com/jest-community/eslint-plugin-jest) (jest-community); [PMD Java Best Practices](https://docs.pmd-code.org/latest/pmd_rules_java_bestpractices.html) (PMD 7.27.0) · dossier: test-quality T13-F07, T13-F15; eval-v1-calibration E01-F04; user-policy-autonomy U01-F07

### TQ-08 — Find pseudo-tested methods in critical code
- **Rule:** For critical covered code, check whether a method's body can be replaced by a default or a no-op without any test failing (extreme mutation). Report pseudo-tested methods by criticality; do not treat every one as a defect.
- **Detect:** Java: PIT with the pitest-descartes engine. Other languages: in a scratch worktree only, replace a covered function body with a default return, run the tests that cover it, then discard the worktree.
- **Not when:** Niedermayr et al. found pseudo-tested ratios of 6-53% for most study objects (mean 11.41% in unit tests, 35.48% in system tests) and judged the unit-test level acceptable. Vera-Pérez et al. found pseudo-tested methods in all subjects (28K+ methods), and found that developers often would not pay to fix them. Report low-criticality cases only in aggregate.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Will My Tests Tell Me If I Break This Code?](https://arxiv.org/pdf/1611.07163) (Niedermayr et al., CSED 2016); [A Comprehensive Study of Pseudo-tested Methods](https://arxiv.org/abs/1807.05030) (Vera-Pérez et al., EMSE 2019); [pitest-descartes](https://github.com/STAMP-project/pitest-descartes) (STAMP) · dossier: test-quality T13-F07

### TQ-09 — Use coverage to find untested code, never as a target
- **Rule:** Use line and branch coverage only as a negative indicator: to find untested code, ranked by criticality and churn, and to show that the pass's own diff did not reduce it. Never add tests just to raise a percentage, and never introduce a project-wide coverage target as part of hardening (this skill's policy; Google: project-wide goals above 90% are "most likely not worth it"). Gate the pass's diff with the project's own threshold if it has one; Google's 2020 guidance calls per-commit goals of 99% reasonable and 90% a good lower threshold.
- **Detect:** coverage.py (branch), vitest/jest `--coverage`, `go tool cover -func`, JaCoCo, llvm-cov. diff-cover against the base for the pass's diff. Rank uncovered files with `.harden/rank.json`.
- **Not when:** Low coverage is a real signal. Chen et al. (ASE 2020) find coverage-guided test selection as strong as mutation-guided "at least until coverage is satisfied", and Khorikov calls coverage below about 60% a certain sign of trouble. High coverage alone means nothing.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Coverage Is Not Strongly Correlated with Test Suite Effectiveness](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf) (Inozemtseva & Holmes, ICSE 2014: 31,000 suites of five systems, low-moderate correlation once size is controlled); [Code Coverage Best Practices](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html) (Google, 2020); [Code Coverage at Google](https://homes.cs.washington.edu/~rjust/publ/google_coverage_fse_2019.pdf) (Ivanković et al., FSE 2019); [Unit Testing Ch. 1 excerpt](https://enterprisecraftsmanship.com/files/Unit-Testing-Chapter-1-Excerpt.pdf) (Khorikov, 2020); [diff-cover](https://github.com/Bachmann1234/diff_cover) (Bachmann1234); [Revisiting Fault Detection, Adequacy and Size](https://rahul.gopinath.org/resources/ase2020/chen2020revisiting.pdf) (Chen et al., ASE 2020) · dossier: test-quality T13-F06

### TQ-10 — Scope mutation testing and gate on survivors, not a score
- **Rule:** Once coverage has done its job, run mutation testing scoped to the lines the pass will touch and to critical modules. Never gate on, or chase, a global mutation score; the gate is the set of individual survivors on in-scope lines (TQ-15; the per-survivor gate itself is grade D, G108-F01). Keep an existing project score threshold only as a separate non-regression trend check.
- **Detect:** Scope with StrykerJS `--mutate` file:line ranges, mutmut function globs, cargo-mutants `-f`/`-F`, PIT `targetClasses`, Stryker.NET `--since`, Infection `--git-diff-lines`, gremlins `--diff`, Mull `gitDiffRef`, or `forge test --mutate` (Foundry 1.8+, preview). Flag any plan or CI that treats "score >= N" as enough evidence to refactor: Stryker `thresholds.break`, PIT `mutationThreshold`, Infection `--min-msi`, gremlins `--threshold-efficacy`.
- **Not when:** Cost can be high: one practitioner saw a TypeScript suite of about 2 minutes take 20-25 minutes under Stryker, and another team running PIT doubts it has ever found a likely production bug. A project-level score is still useful as a trend.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Does mutation testing improve testing practices?](https://arxiv.org/pdf/2103.07189) (Petrović et al., ICSE 2021: at Google, mutants were coupled to 70% of 1,502 high-priority bugs, on changes that tests already covered); [Practical Mutation Testing at Scale](https://arxiv.org/abs/2102.11378) (Google, TSE 2022); [Prioritizing Mutants](https://homes.cs.washington.edu/~rjust/publ/prioritizing_mutants_tcap_icse_2022.pdf) (Kaufman et al., ICSE 2022: no known industrial use computes mutation adequacy); [Are Mutation Scores Correlated with Real Fault Detection?](https://mpapad.github.io/publications/pdfs/ICSE2018.pdf) (Papadakis et al., ICSE 2018); [StrykerJS configuration](https://stryker-mutator.io/docs/stryker-js/configuration/) (Stryker) · dossier: test-quality T13-F08; mutation-testing-practice G108-F01

### TQ-11 — Measure before the change, on the lines about to change
- **Rule:** Run the mutation measurement before the change, scoped to the lines or functions the pass plans to modify, and use diff or incremental modes only after it. Re-run without diff/incremental mode when tests, snapshots, dependencies, environment config or callers changed, because those modes see only the current tree and miss such changes.
- **Detect:** Before the change: Stryker `--mutate "src/x.ts:40-95"`, cargo-mutants `-f`/`-F`, mutmut function globs, PIT `targetClasses`. After it: Stryker `--incremental` (add `--force` if tests, `__snapshots__`, lockfiles or env changed), `cargo mutants --in-diff <diff file>`, Stryker.NET `--since`, Infection `--git-diff-lines`.
- **Not when:** Mutants located on the changed code correlate only weakly (0.15-0.4) with commit-relevant mutants (Ma et al., 83 commits, 25 projects), so for risky refactors also mutate direct callers and callees if affordable. Pre-change scoping cannot test code the change adds.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [StrykerJS incremental mode](https://stryker-mutator.io/docs/stryker-js/incremental/) (Stryker); [cargo-mutants --in-diff](https://mutants.rs/in-diff.html) (Pool); [PIT incremental analysis](https://github.com/hcoles/pitest-site/blob/master/quickstart/incremental_analysis.markdown) (pitest); [Commit-Aware Mutation Testing](https://mpapad.github.io/publications/pdfs/ICSME2020.pdf) (Ma et al., ICSME 2020) · dossier: mutation-testing-practice G108-F02; test-quality T13-F08

### TQ-12 — Validate the mutation run before triaging any survivor
- **Rule:** Treat a run as a measurement only when the unmutated baseline passes, at least one mutant is killed, there is no unexplained mass of Timeout/Incompetent/RuntimeError results, every covered Survived mutant ran tests, and the tool and runner versions are a known-good pair. Use per-test coverage with the framework-specific runner (not a generic command runner), and keep each tool's relative timeout defaults. Before writing a test for a survivor, re-run that survivor alone with per-test coverage off.
- **Detect:** StrykerJS `mutation.json`: flag `status=='Survived' && testsCompleted===0`; "Ran 0.00 tests per mutant" is a red flag. cosmic-ray INCOMPETENT should be about 0. cargo-mutants must print "Unmutated baseline ... ok". gremlins "Not covered" near the total, while `go test -cover` shows coverage, means an invalid run. Grep `stryker.config.*` for `"testRunner": "command"` or `"coverageAnalysis": "off"`. Re-run timeout clusters at lower concurrency (the trigger of about 5% of mutants is a heuristic, grade D).
- **Not when:** Tool defects are version-specific. For example, StrykerJS 10.0.0 with Vitest 5 dropped one project's score from 47.36 to 2.96 (#6210, still open on 2026-09-23); known-bad pairs live in the language files. Genuine infinite-loop mutants on loop conditions are real Timeout kills.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [StrykerJS #6210](https://github.com/stryker-mutator/stryker-js/issues/6210), [#6213](https://github.com/stryker-mutator/stryker-js/issues/6213), [#6073](https://github.com/stryker-mutator/stryker-js/issues/6073), [#4414](https://github.com/stryker-mutator/stryker-js/issues/4414) (StrykerJS issues, 2023-2026); [Mitigating Flaky Tests in Mutation Testing](https://mir.cs.illinois.edu/marinov/publications/ShiETAL19FlakyMutation.pdf) (Shi et al., ISSTA 2019: scores varied about 4 points between runs, PIT, 30 projects); [Cosmic Ray concepts](https://github.com/sixty-north/cosmic-ray/blob/master/docs/source/concepts.rst) (sixty-north); [cargo-mutants timeouts](https://mutants.rs/timeouts.html) (Pool) · dossier: mutation-testing-practice G108-F03, G108-F14, G108-F15

### TQ-13 — Cut the mutant count before sampling
- **Rule:** Reduce cost first by suppressing unproductive ("arid") mutants: logging/tracing calls, collection capacity or reserve arguments, memoisation/cache lookups, sleeps, deadlines and timeouts, and metrics counters. Give each suppression a one-line reason, test at most one mutant per line, and keep these settings in the pass's own run configuration, never in project files. Pilot the cost with a dry run first, and use uniform random sampling only to estimate a module or project score, never to certify that a line is protected.
- **Detect:** Suppression settings: StrykerJS `ignorers`/`mutator.excludedMutations`, cargo-mutants `skip_calls`, mutmut `do_not_mutate_patterns`. Find arid survivors with `rg -n "(log|logger|console)\.(debug|info|warn|trace)|with_capacity|reserve\(|sleep\(|setTimeout|deadline|metrics\.|counter\.inc"`. Flag per-line claims based on a sample (Gambit `-n`, cargo-mutants `--shard`). Pilot with `--dryRunOnly`, `cargo mutants --list` or `gremlins unleash --dry-run`.
- **Not when:** Google calls some of its most valuable arid heuristics "unsound" and environment-specific, and a log line that carries an audit requirement is not arid. Severity-first and span skipping (slither-mutate, mewt, Foundry) hide mutants until the suite improves. Pilot time budgets are unvalidated (grade D).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Practical Mutation Testing at Scale](https://arxiv.org/abs/2102.11378) (Google, TSE 2022: median mutants per changelist fell from 820 to 7, and the productive share rose from 15% to 89%); [Mutation Testing](https://testing.googleblog.com/2021/04/mutation-testing.html) (Petrović, Google, 2021); [cargo-mutants skip_calls](https://mutants.rs/skip_calls.html) (Pool); [Operator-Based vs Random Mutant Selection](https://taoxie.cs.illinois.edu/publications/icse10-mutation.pdf) (Zhang et al., ICSE 2010); [How Hard Does Mutation Analysis Have to Be?](https://rahul.gopinath.org/resources/issre2015/gopinath2015howhard.pdf) (Gopinath et al., ISSRE 2015: about 1,000 sampled mutants gave errors as low as ±2% empirically) · dossier: mutation-testing-practice G108-F12, G108-F13, G108-F11

### TQ-14 — Close an equivalent mutant only with a written R/I/P argument
- **Rule:** Close a survivor as equivalent only with a written argument that names which property fails: R (the mutated code is unreachable), I (the mutation does not change state) or P (the changed state never reaches an observable output). Back the argument with a mechanical check where one exists. Use an LLM "equivalent" verdict to rank candidates, never to close them, and budget about 5 minutes of human time per survivor (range: under 1 minute to over 1 hour).
- **Detect:** Each equivalence row in the triage log starts with "R:", "I:" or "P:" plus one sentence. Where compilation is cheap, compile the original and the mutant with optimisation and compare the output (TCE). Run bounded differential property tests of original versus mutant (fast-check, Hypothesis, proptest) as a falsification attempt. For LLM-generated mutants, strip comments and drop textual duplicates first.
- **Not when:** A differential run can only refute equivalence. Rates vary by language and suite: median 2.97% of all mutants and about 8-24% of covered survivors (7 Java projects, ISSTA 2024), versus at least 7% found by TCE (C, 2015). LLM evidence covers 2023-2024 models only: GPT-4-0613 zero-shot reached a macro-F1 of about 0.56 on 3,302 Java pairs.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Equivalent Mutants in the Wild](https://homes.cs.washington.edu/~rjust/publ/equi_mutants_ems_issta_2024.pdf) (Kushigian et al., ISSTA 2024); [LLMs for Equivalent Mutant Detection](https://arxiv.org/abs/2408.01760) (Tian et al., ISSTA 2024); [Mutation-Guided LLM Test Generation at Meta](https://arxiv.org/abs/2501.12862) (Foster et al., FSE Companion 2025, industry track); [Trivial Compiler Equivalence](https://mpapad.github.io/publications/pdfs/ICSE2015B.pdf) (Papadakis et al., ICSE 2015); [Equivalent mutants](https://stryker-mutator.io/docs/mutation-testing-elements/equivalent-mutants/) (Stryker) · dossier: mutation-testing-practice G108-F18, G108-F17; test-quality T13-F08

### TQ-15 — Record one disposition per in-scope survivor
- **Rule:** In a triage log under `.harden/`, give every survivor on an in-scope line exactly one disposition: (a) real gap: a killing test in a separate test-only commit before the refactor (TQ-16); (b) equivalent: the R/I/P argument (TQ-14); (c) unproductive but killable: an arid reason and no test; (d) unclear intended behaviour: no test, reported as "weakly tested behaviour", with the line treated as unprotected. The gate is zero in-scope survivors without a log row. Propose in-code suppressions (`// Stryker disable next-line <Mutator>: <reason>`, `#[mutants::skip]`, `# pragma: no mutate`) to the owner instead of adding them.
- **Detect:** Each row holds the tool id, file:line, mutator, disposition, evidence (test name and commit, or reason) and a re-run confirmation. Count in-scope survivors with no row. Re-run after each commit, because survivor lists go stale: in one industrial study, 64% of surfaced mutants had their mutated code change during review (1,538 merge requests, ICSE-SEIP 2023).
- **Not when:** Category (d) will be large in code without specs, and a human must resolve it. Pushing every survivor into (a) produces change-detector tests. No study validates this gate; it is a synthesis that matches Google and Meta practice.
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** D
- **Source:** [Please fix this mutant](https://homes.cs.washington.edu/~rjust/publ/mutation_testing_resolution_icse_2023.pdf) (Petrović et al., ICSE-SEIP 2023); [Mutation Testing in Industry at Facebook](https://arxiv.org/abs/2010.13464) (Beller et al., ICSE-SEIP 2021); [Are Mutants a Valid Substitute for Real Faults?](https://homes.cs.washington.edu/~rjust/publ/mutants_real_faults_fse_2014.pdf) (Just et al., FSE 2014); [StrykerJS disable mutants](https://stryker-mutator.io/docs/stryker-js/disable-mutants/) (Stryker) · dossier: mutation-testing-practice G108-F16, G108-F01, G108-F18

### TQ-16 — Make killing tests assert observable, specified behaviour
- **Rule:** A test written to kill a survivor must assert externally observable, specified behaviour through the public API; it must fail on its mutant, pass on the original three times in a row, and still pass after the planned refactor. Reject oracles built on log text, collaborator call order, internal capacity, private state or snapshots of internal structures. An LLM-generated killing test must also build and have its oracle reviewed against the spec or docs; otherwise it becomes a labelled characterization test (TQ-18) or is dropped.
- **Detect:** Review each killing-test diff and reject assertions on logger or console output, `verify()`/`toHaveBeenCalledTimes` on internal collaborators used as the only oracle, private-field reads, and capacity checks. Apply the planned refactor in a scratch worktree and re-run the new test. Reject tests that compute their expected values by calling the code under test.
- **Not when:** Interaction assertions are the right oracle when the interaction is the behaviour, such as an email sent or a message published. Boundary tests such as `isAdult(18)` are legitimate. "Three passes" is a heuristic. The observable-behaviour clauses are grade C in the dossier (G108-F19); only the LLM-test filters are grade B (G108-F20).
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** C
- **Source:** [Mutation Testing](https://testing.googleblog.com/2021/04/mutation-testing.html) (Petrović, Google, 2021); [TotT: Change-Detector Tests Considered Harmful](https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html) (Eagle, Google, 2015); [Mutation-Guided LLM Test Generation at Meta](https://arxiv.org/abs/2501.12862) (Foster et al., FSE Companion 2025, industry track: engineers accepted 73% of its tests); [Automated Unit Test Improvement at Meta](https://arxiv.org/abs/2402.09171) (Alshahwan et al., FSE 2024: 57% of raw tests passed reliably) · dossier: mutation-testing-practice G108-F19, G108-F20; test-quality T13-F09

### TQ-17 — See every new test and property fail
- **Rule:** Before counting a test or property the pass adds, make it fail at least once: in a scratch worktree, break the behaviour it claims to protect, confirm that it fails for the right reason, then discard the worktree. For a property, also show that the generator reaches the target code, through distribution statistics or coverage of the property run, with health checks on and inputs bounded rather than filtered.
- **Detect:** For each new test id, log a named deliberate fault, a red run and a green run after restore; alternatively, the new test kills at least one relevant mutant in a scoped run. Afterwards, `git status` must show production files clean. Also check `pytest --hypothesis-show-statistics` and `rg -n "suppress_health_check|HealthCheck\.(filter_too_much|too_slow)|\.filter\(|assume\(|vm\.assume\("` in new tests, and add per-handler call counters for Foundry invariants.
- **Not when:** Contract, smoke and infrastructure tests can be hard to break locally; record why. If no break is observable, the code may be dead (see the dead-code lens). No controlled study backs this discipline: in one practitioner's single project (2026), an AI-written suite with 98% coverage caught 30 of 40 injected bugs.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [AI-generated tests as ceremony](https://blog.ploeh.dk/2026/01/26/ai-generated-tests-as-ceremony/) (Seemann, 2026); [Improving AI-generated tests using mutation testing](https://blog.senko.net/improving-ai-generated-tests-using-mutation-testing) (Rašić, 2026); [Code Coverage Best Practices](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html) (Google, 2020); [Property-Based Testing in Practice](https://harrisongoldste.in/papers/icse24-pbt-in-practice.pdf) (Goldstein et al., ICSE 2024: 11 of 30 users said they did not think hard enough about effectiveness); [Hypothesis API](https://hypothesis.readthedocs.io/en/latest/reference/api.html) (Hypothesis); [Invariant testing](https://getfoundry.sh/forge/invariant-testing) (Foundry) · dossier: test-quality T13-F15; fuzz-property-hardening G206-F13

### TQ-18 — Label tests written from observed behaviour as characterization tests
- **Rule:** Treat every test the pass writes from observed behaviour as a characterization test. Label it in its name, docstring or tag so it is never read as a specification, and keep it asserting current behaviour as the refactoring safety net. Send any surprising behaviour it reveals (odd edge-case output, a swallowed error, an off-by-one) to the report's suspected-bugs list for a human; never fix that behaviour in the pass and never present it as intended.
- **Detect:** For each new test, record where the expected value came from: a spec, docs, a domain rule or an independent calculation (specification test), or a copy of what the code returned (characterization test). Grep new tests for literals that exactly match printed output. Flag assertions that check only a stub's return value.
- **Not when:** Freezing current behaviour, bugs included, is what Feathers recommends before refactoring legacy code; the danger is only a later reading as a specification. The evidence that LLM oracles capture actual rather than expected behaviour comes from a 2024 preprint (24 Java repositories).
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [Do LLMs generate test oracles that capture actual or expected behaviour?](https://arxiv.org/abs/2410.21136) (Konstantinou et al., 2024); [Characterization Testing](https://michaelfeathers.silvrback.com/characterization-testing) (Feathers, 2016); [Test Smells in LLM-Generated Unit Tests](https://arxiv.org/abs/2410.10628) (Ouédraogo et al., TOSEM 2026); [Characterization test](https://en.wikipedia.org/wiki/Characterization_test) (Wikipedia) · dossier: test-quality T13-F14; mutation-testing-practice G108-F19

### TQ-19 — Encode documented intent in properties and harnesses
- **Rule:** Derive every property, invariant and list of allowed exceptions from docs, specs, type contracts or an independent reference, never from reading the implementation, and record that provenance next to the property. Treat each failure as unvalidated until it is matched to a documented sentence; with no such sentence, label it "ambiguous intent" for a human. Reject tautological properties that compute the expected value with the function under test.
- **Detect:** Run `rg -n "assert\s+(\w+)\((.*)\)\s*==\s*\1\("`, then review by hand. Every property cites the doc, spec or reference it encodes, and every failure records the sentence it violates.
- **Not when:** Doc-only properties miss undocumented behaviour that callers rely on; cover that with characterization tests (TQ-18), which are not properties. The LLM evidence is thin. About 56% of sampled agent bug reports were valid (n = 50 of 984, 100 Python packages, 2025 workshop paper). GPT-4 wrote correct property-based tests for 21% of doc-extractable properties (10 Python libraries, 2024 preprint).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Agentic Property-Based Testing](https://arxiv.org/abs/2510.09907) (Maaz et al., 2025); [Can LLMs Write Good Property-Based Tests?](https://arxiv.org/abs/2307.04346) (Vikram et al., 2024); [Do LLMs generate test oracles that capture actual or expected behaviour?](https://arxiv.org/abs/2410.21136) (Konstantinou et al., 2024) · dossier: fuzz-property-hardening G206-F18; test-quality T13-F16

### TQ-20 — Prefer state over interactions and real collaborators over doubles
- **Rule:** Report change-detector tests, meaning tests that verify internal call sequences or reach into the private members of in-process collaborators. Also report tests where every collaborator is mocked or where stubbing outweighs the assertions. In tests the pass writes, prefer the real implementation, then a fake (ideally the library owner's), then a mock of a thin wrapper you own, and mock only out-of-process dependencies whose interactions are observable.
- **Detect:** Per file, count interaction checks (`verify(`, `InOrder`, `toHaveBeenCalled`, `toHaveBeenCalledWith`, `assert_called`, `assert_called_once_with`, `EXPECT_CALL`) against state assertions. Run `rg -n "jest\.mock\(|vi\.mock\(|mock\.patch\(|@patch\(|Mockito\.mock\(|@Mock\b|gomock|mockall"` and check what is mocked, such as third-party SDK types or the project's own database in integration tests. Find private access: `setAccessible(true)`, `@VisibleForTesting`, `obj._private`, `(x as any).privateField`.
- **Not when:** The mockist (London) school tests interactions deliberately; where that is the dominant project convention, report nothing. Interaction checks are right when the interaction is the behaviour, when call counts matter, or when real and fake implementations are infeasible. Real dependencies are slower and can add flakiness.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [TotT: Change-Detector Tests Considered Harmful](https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html) (Eagle, Google, 2015); [SWE at Google ch. 13](https://abseil.io/resources/swe-book/html/ch13.html) (Google, 2020); [When to Mock](https://enterprisecraftsmanship.com/posts/when-to-mock/) (Khorikov, 2020); [TotT: Don't Mock Types You Don't Own](https://testing.googleblog.com/2020/07/testing-on-toilet-dont-mock-types-you.html) (Trenk & Kennedy, Google, 2020); [Are Coding Agents Generating Over-Mocked Tests?](https://arxiv.org/html/2602.00409v1) (Hora & Robbes, MSR 2026: agents added mocks in 36% of their test commits vs 26% for non-agents, across 2,168 TS/JS/Python repositories with 2025 commits) · dossier: test-quality T13-F09, T13-F10

### TQ-21 — Never regenerate snapshots to go green
- **Rule:** Never run a snapshot update during the pass (`jest -u`/`--updateSnapshot`, or an approval tool's "accept all"). A snapshot that changes under a structural change is a behaviour change to investigate. Report snapshots longer than a few dozen lines and commits that only rewrote snapshots, and propose narrower assertions.
- **Detect:** ESLint `jest/no-large-snapshots` (with `maxSize`) and `jest/no-interpolation-in-snapshots`. `git ls-files -- '*.snap' | while IFS= read -r f; do wc -l "$f"; done | sort -n | tail` (tracked snapshots only, never `find .`, which also walks `.harden/` and `node_modules`). `git log --stat -- '*.snap' '**/__snapshots__/**'`. Run Jest with `--ci` in automation.
- **Not when:** A huge snapshot can still flag an unexpectedly wide change, and golden-master tests are a recognised characterization technique. Prefer narrowing a snapshot to deleting it.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [Snapshot Testing](https://jestjs.io/docs/snapshot-testing) (Jest docs); [Effective Snapshot Testing](https://kentcdodds.com/blog/effective-snapshot-testing) (Dodds, 2017: a 640-line snapshot that nobody reviewed); [eslint-plugin-jest](https://github.com/jest-community/eslint-plugin-jest) (jest-community) · dossier: test-quality T13-F13; eval-v2-calibration E02-F08

### TQ-22 — Use test-smell detectors for triage only
- **Rule:** Use test-smell detectors (tsDetect, PyNose, lint rules) only for triage. Confirm each smell by hand against an observed cost (flakiness, change-proneness, an unreadable failure) before reporting it, and never bulk auto-refactor smells with a tool or an LLM. Report branching logic in test bodies and tests that check several unrelated behaviours; framework parameterisation is not branching.
- **Detect:** ESLint `jest/no-conditional-in-test` or `vitest/no-conditional-in-test`. ast-grep for `if`/`for`/`while`/`try` in test bodies, excluding `@pytest.mark.parametrize`, `test.each` and Go table-driven loops. Look for tests named after a method that contain several act/assert phases. tsDetect and PyNose have had no commits since 2022.
- **Not when:** Panichella et al. (EMSE 2022) found several smells "ubiquitous on developer-written tests but virtually never correlated" with real flaws. Spadini et al. (ICSME 2018, ten systems) still link Indirect Testing, Eager Test and Assertion Roulette to change- and defect-proneness. DAMP versus DRY is contested, so follow the project's convention.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B

### TQ-23 — Never reshape the suite toward a ratio
- **Rule:** Never restructure the test portfolio toward a pyramid, trophy or honeycomb ratio, and never delete end-to-end tests to fix a shape. Report only demonstrated problems: slow or flaky large tests that assert fine-grained logic, and integration seams covered only by mocked tests.
- **Detect:** Classify tests by what they touch (process, network, disk, database, browser). Take runtimes from `pytest --durations=25`, `go test -json` or JUnit XML. Cross-check with the TQ-02 instability data; over one week at Google (2017), 0.5% of small, 1.6% of medium and 14% of large tests were flaky.
- **Not when:** No controlled study settles the ideal ratio. Google calls its 80/15/5 mix "a very rough guideline".

### TQ-24 — Propose deleting a test only with evidence that its protection is subsumed
- **Rule:** Propose deleting a test only when it tests removed code, or when other tests fully cover its lines and its killed-mutant set. Never propose deletion because a test fails, is flaky or is hard to read. For a hollow test that the pass pinned in a new file (TQ-07), run this check against that file and report deleting the hollow test as its own T2 item for the owner, separate from the approval of that pinning file; the pass never applies it. Strengthening a hollow test in place is TQ-07's T1 fix, not a deletion. The pass deletes a test only under lens-dead-code DC-15: in the `refactor(dead-code):` commit that deletes the production symbols the deleted test cases reference (G102-F14 TE-2), in files the user approved and the orchestrator recorded with `run_state.py allow-test-deletion <path> --cases <n> --reason <finding id>`, with a deletion-only change to each file. Deleting a test for any other reason, subsumed protection included, stays the owner's action (T2).
- **Detect:** Per-test coverage contexts: coverage.py `dynamic_context = test_function` or pytest-cov `--cov-context=test`, then `coverage html --show-contexts`. Run the scoped mutation suite with and without the test; the killed set must not shrink. `git log -S '<tested symbol>'` shows whether the tested code is gone.
- **Not when:** For an obviously tautological test, such as one asserting that a stub returns its stubbed value, a manual review plus one mutation check is enough. No empirical study of what happens after test deletion was found. T13-F19 puts a deletion in its own commit with no production code; this skill follows G102-F14 instead, where tests share the fate of the code they test (Sensenmann, and Piranha's "Delete tests related to feature flags").
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** C

### TQ-25 — Keep generative testing additive and test-only
- **Rule:** Add property tests, fuzz harnesses, seed corpora, dictionaries and regression inputs only as new files in test or fuzz locations; never edit production code, existing tests or the production build configuration for them. Commit each confirmed failure as a new regression test in a test-only commit (TQ-30), and leave the fix to a separate reviewed change outside the pass. When a target needs a testability seam, skip it and report the seam.
- **Detect:** Every path in `git diff --name-only <base>..HEAD` is under tests/, test/, __tests__/, spec/, fuzz/, testdata/fuzz/, proptest-regressions/ or corpus/. `git diff --diff-filter=M --name-only <base>..HEAD -- <test globs>` is empty. Review harnesses for monkeypatching of production modules.
- **Not when:** Sanitizer and fuzzer builds change compiler flags, which is allowed only as a build variant outside the production configuration. "Additive only" is this skill's design choice; the sources support the mechanism.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [Go Fuzzing](https://go.dev/doc/security/fuzz/) (Go); [Ideal integration with OSS-Fuzz](https://google.github.io/oss-fuzz/advanced-topics/ideal-integration/) (Google); [How SQLite Is Tested](https://www.sqlite.org/testing.html) (SQLite); [Hypothesis: replaying failures](https://hypothesis.readthedocs.io/en/latest/tutorial/replaying-failures.html) (Hypothesis) · dossier: fuzz-property-hardening G206-F01

### TQ-26 — Aim property tests where a property is obvious
- **Rule:** Add property tests opportunistically, in this order: no unexpected exceptions (only documented exception types over the documented input domain), then round-trip, then inclusion and type/shape invariants, and only then richer semantics. When a simpler trustworthy counterpart exists (a naive implementation, a previous version, an uncached path or a reference library), prefer a differential property against it. Skip or narrow the step, stating why, when no property or reference can be stated, when targets are effectful with no seam, or when the budget is too small.
- **Detect:** Candidates: `rg -n "def (to|from)_(json|dict|bytes)|serialize|deserialize|encode|decode|parse|format|dump|load"`; `_fast`/`_optimized`/`legacy`/`cached` twins; pure functions over collections, numbers or money. Existing properties: `rg -n "@given\(|test\.prop\(|fc\.assert\(|proptest!"`. Hypothesis ghostwriter output is a draft only, and the oracle must never call the implementation under test.
- **Not when:** Generators are costly, and round-trip properties miss bugs that are symmetric in both directions. A reference that shares code with the implementation can be wrong in the same way, and writing a new reference may be too much new code for this pass. Numeric code is a good target, but not the only one.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Property-Based Testing in Practice](https://harrisongoldste.in/papers/icse24-pbt-in-practice.pdf) (Goldstein et al., ICSE 2024: 30 Jane Street interviews, mostly OCaml; differential properties 17/30, round-trip 11/30); [An Empirical Evaluation of PBT in Python](https://cseweb.ucsd.edu/~mcoblenz/assets/pdf/OOPSLA_2025_PBT.pdf) (Ravi & Coblenz, OOPSLA 2025: each property-based test killed about 50x the mutants of an average unit test, 40 Python projects mostly under 10k LOC, correlational); [In praise of property-based testing](https://increment.com/testing/in-praise-of-property-based-testing/) (MacIver, 2019); [ShardStore](https://cdn.amazon.science/77/5e/4a7c238f4ce890efdc325df83263/using-lightweight-formal-methods-to-validate-a-key-value-storage-node-in-amazon-s3-2.pdf) (Bornholt et al., SOSP 2021); [Hypothesis ghostwriter](https://hypothesis.readthedocs.io/en/latest/reference/integrations.html) (Hypothesis) · dossier: test-quality T13-F16; fuzz-property-hardening G206-F03, G206-F04, G206-F05, G206-F20

### TQ-27 — Separate hunting settings from committed settings
- **Rule:** Run the one-shot hunt from an uncommitted local profile: about 1,000 examples per property, deadlines off, statistics printed. Commit properties at the library defaults or lower (Hypothesis 100, fast-check 100, proptest 256, Foundry 256 fuzz runs), with deterministic seeding on CI.
- **Detect:** In committed tests, flag `rg -n "max_examples\s*=\s*\d{4,}|numRuns:\s*\d{4,}"` and any suppressed deadline or health check without a justification. Hypothesis already defaults to `deadline=None` and `derandomize=True` on CI; locally the defaults are 200 ms and False.
- **Not when:** The saturation data come from mutants: in Ravi & Coblenz, 76% of kills came within 20 inputs, 86% within 100 and 96% within 350, in a sweep capped at 500 inputs. Bugs that need rare structured inputs call for coverage-guided back ends (HypoFuzz, Hypothesis `fuzz_one_input`).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [An Empirical Evaluation of PBT in Python](https://cseweb.ucsd.edu/~mcoblenz/assets/pdf/OOPSLA_2025_PBT.pdf) (Ravi & Coblenz, OOPSLA 2025); [Hypothesis API](https://hypothesis.readthedocs.io/en/latest/reference/api.html) (Hypothesis); [fast-check Parameters](https://fast-check.dev/docs/api/interfaces/Parameters/) (fast-check); [proptest Config](https://docs.rs/proptest/latest/proptest/test_runner/struct.Config.html) (proptest); [Schemathesis config optimization](https://schemathesis.readthedocs.io/en/stable/guides/config-optimization/) (Schemathesis) · dossier: fuzz-property-hardening G206-F06

### TQ-28 — Make fuzz harnesses deterministic and run them under sanitizers
- **Rule:** Each harness must be deterministic for a given input (no rand, clock or environment-dependent branches), carry no mutable global state across iterations, never call `exit`, tolerate any input, do no disk I/O after initialisation, stay under about 1.5 GB of memory, and handle one format per target. Fuzz native code (C/C++, unsafe Rust, native extensions) only under sanitizers, at least ASan and ideally UBSan, in a build configuration separate from production. Treat a crash that happens instantly or inside harness code as a harness bug until proven otherwise.
- **Detect:** Run `rg -n "\brand\(|srand\(|time\(|random\.|Math\.random|exit\(|process\.exit|getenv|fopen\(|static [^c].*=" fuzz/`. Replay the corpus twice with `-runs=0` and compare. In libFuzzer, under 10 exec/s signals a problem (about 1,000 per core is normal). Run `rg -n "fsanitize" fuzz/ CMakeLists.txt build.rs Makefile`. Windows toolchain details live in the C++ language file.
- **Not when:** Stateful bugs justify a deterministic, input-driven command interpreter inside the harness. Heavyweight targets are legitimately slower; SQLite's dbsqlfuzz runs about 400 cases per second.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [What makes a good fuzz target](https://github.com/google/fuzzing/blob/master/docs/good-fuzz-target.md) (Google); [libFuzzer](https://llvm.org/docs/LibFuzzer.html) (LLVM); [LLM-based fuzz target generation](https://google.github.io/oss-fuzz/research/llms/target_generation/) (Google OSS-Fuzz); [AddressSanitizer (MSVC)](https://learn.microsoft.com/en-us/cpp/sanitizers/asan) (Microsoft, 2026); [AFL++ fuzzing in depth](https://github.com/AFLplusplus/AFLplusplus/blob/stable/docs/fuzzing_in_depth.md) (AFL++) · dossier: fuzz-property-hardening G206-F10, G206-F09

### TQ-29 — Spend the fuzzing budget on never-fuzzed, churned input handling
- **Rule:** Put the budget on code never fuzzed or property-tested; give code already under continuous fuzzing time only for a new harness shape (new entry points, structure-aware inputs, new properties). Aim at parsers, decoders, validators and file or protocol readers, the most churned first. Give each target at least 10-15 minutes, seed it from minimised fixtures plus a token dictionary and one empty-seed run, stop at a coverage plateau, and record both the budget and the plateau evidence.
- **Detect:** Find existing harnesses and properties with `rg -l "LLVMFuzzerTestOneInput|func Fuzz[A-Z]|@given\(|fc\.(assert|property)|test\.prop\(|proptest!|fuzz_target!|atheris\.Setup|function invariant_|function testFuzz"`, plus `fuzz/`, `testdata/fuzz/`, `.clusterfuzzlite/` or a google/oss-fuzz `projects/<name>` entry. Take churn from `.harden/rank.json`. Judge the plateau from the libFuzzer `cov:`/`ft:` counters or the AFL++ `afl-whatsup` last-new-find time. Flag targets fuzzed for under 10 minutes or without plateau evidence.
- **Not when:** Research comparisons use 10 or more trials of 24 h (AFL found 0 crashes in gif2png at 13 h and 39 at 24 h), so a never-fuzzed project may deserve hours on its top 1-3 targets. Never copy fixtures that hold secrets or customer data into a committed corpus.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Regression Greybox Fuzzing](https://mboehme.github.io/paper/CCS21.pdf) (Zhu & Böhme, CCS 2021: 77% of 23k OSS-Fuzz bugs were regressions); [Exponential Cost of Vulnerability Discovery](https://mboehme.github.io/paper/FSE20.EmpiricalLaw.pdf) (Böhme & Falk, FSE 2020); [Leveling Up Fuzzing](https://security.googleblog.com/2024/11/leveling-up-fuzzing-finding-more.html) (Google, 2024: 26 new vulnerabilities in heavily fuzzed projects); [CIFuzz](https://google.github.io/oss-fuzz/getting-started/continuous-integration/) (Google: 600 s minimum); [Fuzzing in CI/CD](https://arxiv.org/abs/2205.14964) (Klooster et al., 2022 preprint, 9 Magma C/C++ libraries); [Evaluating Fuzz Testing](https://arxiv.org/abs/1808.09700) (Klees et al., CCS 2018); [Ideal integration with OSS-Fuzz](https://google.github.io/oss-fuzz/advanced-topics/ideal-integration/) (Google) · dossier: fuzz-property-hardening G206-F02, G206-F03, G206-F07, G206-F08, G206-F17

### TQ-30 — Turn each confirmed failure into a replayable regression test marked expected-to-fail
- **Rule:** Encode each confirmed, minimised failure as a new test in the project's native replay mechanism, marked expected-to-fail with an issue link so the suite stays green: pytest `xfail(strict=True, raises=...)`, Hypothesis `@example(...).xfail(raises=...)`, Vitest `test.fails`, or Go `t.Skip` with a reason. These markers go only in new test files, and each marker line that `diff_guard.py` reports as HARD `marker_added` (pytest `xfail`, Go `t.Skip`) is recorded with `run_state.py allow-line <path> --text "<line>" --reason <finding id>` after the user approves it; otherwise the final diff_guard run fails. Never commit a still-failing input into an auto-replay store (Go `testdata/fuzz`, `proptest-regressions/`), and never rely on tool caches (the Hypothesis database, `@reproduce_failure` blobs) as the regression store.
- **Detect:** `rg -n "@reproduce_failure"` must return nothing. Each new regression test must fail on current code for the documented reason. Put fast-check counterexamples into `examples:` or an explicit unit test, and minimised libFuzzer/AFL++ files into a replay corpus. Turn Schemathesis curl reproducers and Foundry `-vvvv` sequences into concrete tests.
- **Not when:** Go and proptest have no per-input expected-failure marker. Guard the whole fuzz test with `t.Skip` and an issue link, keep the reproducer outside the auto-replay directory until the fix, or ship it with the fix; this is a reviewer's resolution, not sourced. Some teams refuse known-failing tests even when marked; there, commit only the reproducer file together with an issue.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Hypothesis: replaying failures](https://hypothesis.readthedocs.io/en/latest/tutorial/replaying-failures.html) (Hypothesis); [Hypothesis API](https://hypothesis.readthedocs.io/en/latest/reference/api.html) (Hypothesis); [proptest failure persistence](https://proptest-rs.github.io/proptest/proptest/failure-persistence.html) (proptest); [How to use skip and xfail](https://docs.pytest.org/en/stable/how-to/skipping.html) (pytest docs); [Vitest test API](https://vitest.dev/api/test) (Vitest); [Read test reports](https://fast-check.dev/docs/tutorials/quick-start/read-test-reports/) (fast-check); [Go Fuzzing](https://go.dev/doc/security/fuzz/) (Go) · dossier: fuzz-property-hardening G206-F12, G206-F01

### TQ-31 — Triage generative failures by root cause, never by crash count
- **Rule:** Minimise each failing input, reproduce it at least twice, bucket by symbolised top stack frames as a first pass only, and confirm distinct root causes by inspection. Report only findings reachable through a public entry point with inputs that respect the documented preconditions, each with a root-cause sentence and a reproduction command. Never present unique-crash or stack-hash counts as bug counts.
- **Detect:** Minimise with libFuzzer `-minimize_crash=1`, `afl-tmin` or `cargo fuzz tmin`; Go and the property-based testing libraries shrink automatically. Bucket by the top 3 frames, then merge buckets that share a root cause. Record the public entry point and the input domain, and group API-fuzzing failures by failure point.
- **Not when:** Precondition filtering can discard real bugs, so report undocumented preconditions as documentation or validation gaps. A fix or bisect is outside the pass, so a reasoned root-cause statement is accepted as confirmation.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Evaluating Fuzz Testing](https://arxiv.org/abs/1808.09700) (Klees et al., CCS 2018: 57,142 coverage-unique crashes on cxxfilt were fixed by 9 patches); [No Time to Rest Yet](https://arxiv.org/abs/2204.08348) (Kim et al., ISSTA 2022: 3-7x fewer failure points than errors); [libFuzzer](https://llvm.org/docs/LibFuzzer.html) (LLVM); [Agentic Property-Based Testing](https://arxiv.org/html/2510.09907) (Maaz et al., 2025) · dossier: fuzz-property-hardening G206-F11

### TQ-32 — Run API schema fuzzers only against disposable instances
- **Rule:** Run OpenAPI or GraphQL schema fuzzers (Schemathesis, RESTler) only against a disposable local or staging instance with a disposable database, never production, starting with a short run or RESTler's smoke-test mode. Triage 5xx and crash-class failures first, and record schema-conformance mismatches separately from code bugs.
- **Detect:** Before starting, confirm that the host, the credentials and the database are not production. Classify results into three groups: 5xx/crash, schema conformance, and auth/setup noise. For Schemathesis, use `--report junit` with `--max-examples` or `--max-time`.
- **Not when:** Schema fixes (documentation) and handler fixes (behaviour) both stay out of the pass. Rankings disagree: the authors' own evaluation reports 1.4-4.5x more defects than the next fuzzer on 16 services, while an independent study (20 services, Schemathesis 3.7.1) ranks it sixth of ten on unique 500 errors.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Deriving Semantics-Aware Fuzzers from Web API Schemas](https://arxiv.org/abs/2112.10328) (Hatfield-Dodds & Dygalo, ICSE 2022 Companion); [No Time to Rest Yet](https://arxiv.org/abs/2204.08348) (Kim et al., ISSTA 2022); [RESTler](https://github.com/microsoft/restler-fuzzer) (Microsoft Research); [Schemathesis triage](https://schemathesis.readthedocs.io/en/stable/guides/triage/) (Schemathesis) · dossier: fuzz-property-hardening G206-F14

### TQ-33 — Solidity: add fuzz and handler-based invariant tests
- **Rule:** Add Foundry stateless fuzz tests and handler-based invariant tests. For the hunting run, size a local profile above the defaults (fuzz 256 runs; invariant 256 runs at depth 100), constrain inputs with `bound()` rather than `vm.assume()`, and cross-check with Echidna or Medusa. Spend most of the effort on stating invariants taken from the protocol's documented rules (TQ-19).
- **Detect:** Run `rg -n "function (testFuzz|invariant)_|targetContract\(|vm\.assume\(" test/`. Read the `[fuzz]`/`[invariant]` sections of `foundry.toml`. Log per-handler call counts. Echidna defaults are `testLimit: 50000` and `seqLen: 100`; keep a `corpusDir` for replay. Replay a failure with `forge test --match-test <name> -vvvv`.
- **Not when:** `fail_on_revert = false` can hide handlers that almost always revert. Invariants read from the current code encode current behaviour. Trail of Bits' claim that "writing good invariants is 80% of the work" is a fuzzing-tool vendor's opinion, based on an n = 2 rediscovery experiment.
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Invariant testing](https://getfoundry.sh/forge/invariant-testing) (Foundry); [Fuzz testing](https://getfoundry.sh/forge/fuzz-testing) (Foundry); [Echidna default.yaml](https://github.com/crytic/echidna/blob/master/tests/solidity/basic/default.yaml) (Trail of Bits); [Why fuzzing over formal verification?](https://blog.trailofbits.com/2024/03/22/why-fuzzing-over-formal-verification/) (Trail of Bits, 2024); [Medusa](https://github.com/crytic/medusa) (Trail of Bits) · dossier: fuzz-property-hardening G206-F15

## False-positive exclusions

- Explicit does-not-throw smoke tests, and assertion helpers that the linter has not been configured to recognise (TQ-07).
- Conditional skips that carry a reason, and Rust `#[ignore]` on slow tests that run separately (TQ-06).
- Tests that deliberately check real timing (TTL, rate limits, performance) or real network contracts (TQ-05).
- Framework parameterisation (`parametrize`, `test.each`, Go table-driven loops), which is not branching logic (TQ-22).
- Interaction assertions where the interaction is the behaviour, and suites whose project convention is the mockist style (TQ-20).
- An existing quarantine that is ticketed and time-boxed (TQ-03).
- Boundary mutants such as `<` to `<=` in clamp-style code; in one toy cargo-mutants run, 2 of 3 misses were of this kind. Close them only with an R/I/P argument (TQ-14).
- Timeouts on genuine loop-condition mutants, which are real kills (TQ-12).
- Survivors killed by tests the tool did not run, such as integration suites or tests in other packages (by default, gremlins runs only the tests of the package that holds the mutant). Confirm with the full suite before reporting (TQ-12).
- Crashes that happen instantly or inside harness code, which are presumed harness bugs (TQ-28).
- Schema-conformance mismatches, which are not code bugs (TQ-32).
- Unique-crash and stack-hash counts, which are not bug counts (TQ-31).

## Evidence limits

- **Baseline.** The baseline is a lower bound: 95% confidence that a passing test is not flaky takes about 170 reruns (Python, ICST 2021).
- **Mutation thresholds.** No study supports any mutation-score threshold; Stryker's 80/60 defaults are conventions. The per-survivor gate (TQ-15) and every time budget are unvalidated (grade D).
- **Tool bugs.** False survivors caused by tool bugs are quantified only for StrykerJS/Vitest and for flaky suites. StrykerJS issues #6210, #6213 and #6073 were open on 2026-09-23.
- **Windows.** gremlins misbehaves natively (much slower, or no coverage detected), and Mull, mewt and dextool run on Linux/macOS only. For MSVC-only C/C++, record "no mutation tool; safety net unmeasured".
- **Mocking.** Hora & Robbes' within-repository 36% vs 28% is the median over 179 higher-activity repositories only. The 282 lower-activity repositories showed 27% vs 24%, which the authors call not meaningful.
- **Property-based testing.** The evidence is correlational: Python, a 2022 corpus, projects mostly under 10k LOC, and mutants rather than real bugs. For exception, inclusion and type properties, the paper's abstract says "over 19 times" and its conclusion "over 14 times". Teralizer measured only automated generalisation of mature tests (+0.05 to 0.07 points).
- **Fuzzing yield.** Yield data come from C/C++ open source; no source measures a one-shot pass on TypeScript, Python business logic or Solidity. CI budgets (600 s, or 15 minutes in a preprint on 9 libraries) and research budgets (24 h, 10+ trials) serve different purposes.
- **Fuzzing severity.** Severity claims from fuzzing are weak: only 42% (143) of 339 CVEs assigned in fuzzing research were valid and fixed (SoK, S&P 2024). The reporting reference sets severity.
- **LLM-written tests and properties.** The evidence covers 2023-2024 models, libraries and preprints. No study evaluates an agent separating characterization tests from specification tests, or catching tautologies, in a full workflow.
- **Missing evidence.** No study of test-deletion outcomes was found, and SonarQube rule ids for tests without assertions, with sleeps or with skips were not reached.
