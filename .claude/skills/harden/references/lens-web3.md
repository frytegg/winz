# Lens: Web3

> Review smart contracts and the off-chain code around them (bots, keepers, relayers, deploy scripts) beyond what analyzers catch: privilege, value flows, oracles, signatures, upgradeability and keys, with every severity graded against a named rubric.
> Read when: the repo contains Solidity or Vyper contracts, or off-chain code that signs transactions, reads chain state or holds exchange API keys.

## Contents
- Procedure
- Rules: method (W3-01 to W3-03); privilege and centralisation (W3-04 to W3-07); value, logic and arithmetic (W3-08 to W3-18); cross-chain (W3-19); upgradeability and audit scope (W3-20 to W3-23); off-chain keys and bots (W3-24 to W3-28)
- False-positive exclusions
- Evidence limits

## Procedure

You are a fresh-context, read-only lens subagent (detection step 8). You detect and triage; the orchestrator runs the tools, verifies, ranks and applies.

1. **Stay read-only.** Your tools are Read, Grep and Glob: never edit or write a file, run a command, send a transaction or print key material. The orchestrator writes raw tool output to `.harden/tools/` (SARIF or JSON), records every pinned tool version for `tool_versions`, and never runs fix or format modes or deploy scripts against a live network.
2. **Load inputs.** Read `.harden/inventory.json`, `.harden/prescan.json` and the Solidity language file. That file holds the exact Slither, Aderyn and forge lint commands, pinning, inline-suppression syntax, and the compiler-version, pragma and known-bug checks. Also read the TypeScript or Python language file when off-chain code is in scope. The project's own configured analyzers run first, with its config; no rule here overrides it.
3. **Apply the deployment gate before anything else.** Look for deployed addresses in deploy artifacts, broadcast logs, config and the README. Run the source part of the proxy check (W3-20) with the Grep tool and find the audit baseline (W3-23).
   - The tier printed in a rule block applies to contracts that are not yet deployed.
   - For a deployed contract, every contract-source finding is T2 and gets a fix classification: source-only for the next deploy, requires upgrade, or requires migration (W3-23).
   - In upgradeable code, every storage-affecting change is T2 (W3-20, W3-21).
4. **Detector commands (run by the orchestrator in detection step 4; read their outputs from `.harden/tools/`)** (W3-01). Commands live in the language files; detector, printer and lint ids are in each rule. Skip them in an unseeded pass (DT-21); a detector with no output is a limit line.
   - Contracts: Slither detectors and the `vars-and-auth`, `modifiers` and `variable-order` printers; Aderyn; forge lint. `slither-check-upgradeability` and `@openzeppelin/upgrades-core validate` where proxy signals exist. `forge test --match-test invariant` metrics where invariant tests exist (W3-09): these `forge test` runs belong to the orchestrator under the Phase 0 side-effect check, never to this subagent. Medusa, Echidna or Halmos only if the project already configures them.
   - Off-chain bots, keepers, relayers and deploy scripts (TS/JS/Python): run the ripgrep sweeps in W3-24 to W3-28 yourself through the Grep tool; detect-secrets over git history (W3-24) is a detector command.
   - On-chain reads (`cast implementation`, `cast storage`, `cast call`, `cast code`): read calls only, run by the orchestrator only when the user supplied an RPC URL and addresses. Otherwise record the gap for Limits.
5. **Do the manual review in W3-02 order** and produce its three artefacts. The analyzer pass replaces none of its steps.
6. **Triage every hit at file:line** as a true positive, accepted with a written reason, or a false positive (W3-01). Apply the exclusions below, file each confirmed lead under the most specific W3 rule, and keep the tool's detector id in the evidence.
7. **Return candidates plus files_read as your final message**; the orchestrator merges them into `.harden/candidates.json`. files_read lists every file you read with its line ranges (DT-02). One candidate per location, in the findings schema (`assets/findings.schema.json`):
   - `lens: "web3"`; `rule_ref` = W3-NN, or `project:<tool>/<rule>` for a project-configured tool; `file` repo-relative; `line` at `base_sha`.
   - `severity` and `severity_criterion` per W3-03 (quote the Immunefi impact class and name the rubric); the attack precondition in `conditions`.
   - `evidence[]`: `tool` (command plus detector id), `source` (file:line trace), `git` (commit or diff), or `test` (a proposed failing property or unit test).
   - `confidence` from the evidence ladder; `tier`, `class` and `fix_risk` from the rule block after the deployment gate; `location_class` from `.harden/rank.json` when present, else `unknown`.
   - Start `notes` with `operational:` for centralisation, key and signer findings (W3-05, W3-07, W3-24 to W3-28), so the report keeps them in their own section.
   - `verified: false` and `status: "candidate"`. Never write a key, mnemonic or API secret into any field; cite file:line and commit instead.
8. **Record coverage for Limits** in the same final message: checklist items not reached, tools not run, on-chain checks skipped, invariants not encoded, formal tools not run. When exchange API keys or order-submission code are in scope, record "order lifecycle, reconciliation and exposure controls not checked". When contract files in a language other than Solidity or Vyper are present (for example Move, as in Cetus, or Rust programs for Solana), record "on-chain code in <language> not analysed". Never report a clean run as "hardened" or "secure".

## Rules

### W3-01 — Analyzer output is a baseline, never evidence of hardening
- **Rule:** Run Slither, Aderyn and forge lint as a baseline and triage every hit at file:line as a true positive, accepted with a written reason, or a false positive; never auto-apply every suggested fix. Never call a contract codebase "hardened" or "secure" because the analyzers came back clean: that verdict needs the W3-02 checklist log and property tests (W3-09).
- **Detect:** The violation is a report whose only evidence is analyzer output, or an inline suppression (`slither-disable-next-line`, `forge-lint: disable-next-line`) with no reason next to it.
- **Not when:** Never skip the analyzers: they stay cheap and reliable for reentrancy, unchecked returns and similar low-level classes. The low recall figures measure default detectors on real exploits. Chaliasos (ICSE '24): 5 tools could have prevented 8% of 127 DeFi attacks ($149M of $2.3B), all reentrancy. Web3Bugs (ICSE '23, 2021–2022 bugs): 79.5% of in-scope exploitable bugs were beyond tools (271 of 341 Code4rena bugs, 35 of 44 exploits). Durieux (ICSE 2020, 2019 tool versions): 9 tools tagged 97% of 47,518 contracts as vulnerable, yet together detected 42% of an annotated set. The high figures assume human-written properties: about 78% of the most important findings in 23 Trail of Bits audits were reachable by static plus dynamic analysis, while about 49% of all 246 findings were nearly impossible for tools (2019). 76% of surveyed auditors spend at most 20% of audit time on tools (Chaliasos).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Smart Contract and DeFi Security Tools](https://arxiv.org/abs/2304.02981) (Chaliasos et al., ICSE 2024); [Demystifying Exploitable Bugs in Smart Contracts](https://zhangzhuosjtu.github.io/res/ICSE23.pdf) (Zhang et al., ICSE 2023); [Empirical Review of Automated Analysis Tools](https://arxiv.org/abs/1910.10601) (Durieux et al., ICSE 2020); [246 Findings From Our Smart Contract Audits](https://blog.trailofbits.com/2019/08/08/246-findings-from-our-smart-contract-audits-an-executive-summary/) (Trail of Bits, 2019); [SEAL Security Testing](https://frameworks.securityalliance.org/security-testing/overview) (Security Alliance, 2025); [Slither Usage](https://github.com/crytic/slither/wiki/Usage) (Crytic, 2026); [Forge lint](https://getfoundry.sh/forge/linting) (Foundry, 2026) · dossier: web3-audit-practice G207-F01; lang-solidity-go T24-F01

### W3-02 — Run the manual review in a fixed order and log every step
- **Rule:** Review in this order: (1) docs, README and NatSpec, extracting invariants, trust assumptions, supported tokens and chains (the README wins over code comments); (2) actors and privileges (W3-04, W3-05); (3) value-moving paths against the invariants (W3-08); (4) oracles (W3-11), external calls and tokens (W3-13), bridges (W3-19); (5) signatures (W3-14), ordering (W3-12), DoS (W3-15); (6) upgradeability and initialization (W3-20 to W3-22); (7) arithmetic (W3-16, W3-17); (8) an adversarial pass from each actor's side; (9) tests and coverage, then tools; (10) past findings on similar protocols. Log every OWASP SC01–SC10 (2026) item as checked, not applicable, or a finding.
- **Detect:** Three artefacts must exist: invariants and assumptions quoted from the docs, an actor/privilege table, and the SC01–SC10 log; a missing one is a coverage gap for Limits. Mapping: SC01 → W3-04/05; SC02 → W3-08; SC03 and SC04 → W3-11; SC05 → W3-04/08; SC06 and SC08 → W3-13; SC07 and SC09 → W3-16/17; SC10 → W3-20 to W3-22.
- **Not when:** No study compares review orderings; this is practitioner convention (Solcurity, and the Cyfrin checklist, which opens with "Attacker's Mindset"). Scale the depth to the value at risk. Hackathon code often has no docs: reconstruct intent from the tests and mark those invariants as inferred.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [Solcurity](https://github.com/transmissions11/solcurity) (transmissions11, 2021); [Cyfrin audit-checklist](https://github.com/Cyfrin/audit-checklist) (Cyfrin, 2024); [Sherlock Judging Guidelines](https://docs.sherlock.xyz/audits/judging/guidelines) (Sherlock, 2025); [EthTrust Security Levels v3](https://entethalliance.github.io/wg-ethtrust-site/spec/v3/) (EEA, 2025); [OWASP Smart Contract Top 10:2026](https://scs.owasp.org/sctop10/) (OWASP, 2026) · dossier: web3-audit-practice G207-F02

### W3-03 — Grade every finding on a named, published impact scale
- **Rule:** Give every contract finding an impact class quoted from Immunefi v2.3 Smart Contracts and use the schema severity of the same name: critical (direct theft of user funds other than unclaimed yield, permanent freezing, protocol insolvency), high (theft of unclaimed yield, temporary freezing), medium (unable to operate for lack of token funds, griefing), low (fails to deliver promised returns without losing value). Write out the attack precondition, set a likelihood per CodeHawks (direct call = high; special conditions such as a non-standard token = medium; rare circumstances = low), and name the rubric in `severity_criterion`, because the platforms disagree about likelihood. This scale explicitly overrides reporting RP-02 for on-chain contract findings (RP-02 states the same exception), so the likelihood adjustments below stay consistent with the reporting rubric.
- **Detect:** A finding without a written attack path cannot be high (Code4rena: an attack path "that does not have hand-wavy hypotheticals"). For a quantifiable loss, apply Sherlock's test: high above 1% and $10 of principal, medium above 0.01% and $10. For DoS, Sherlock allows medium when funds are locked for more than a week or a time-sensitive function is blocked, and high when both apply. Lower front-running one level on private-mempool chains (Sherlock). Keep admin, centralisation and key-compromise risks in the operational section (W3-05).
- **Not when:** Sherlock states that likelihood is not considered for severity, and all these rubrics were built to settle contest and bounty payouts under contest assumptions (trusted admins, reorgs invalid). The combined scheme is a synthesis, not a published method. Off-chain findings use the operational section plus Immunefi's Websites and Apps classes.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [Immunefi Severity Classification v2.3](https://immunefi.com/immunefi-vulnerability-severity-classification-system-v2-3/) (Immunefi, n.d.); [Sherlock Judging Guidelines](https://docs.sherlock.xyz/audits/judging/guidelines) (Sherlock, 2025); [Code4rena Severity Categorization](https://docs.code4rena.com/competitions/severity-categorization) (Code4rena, 2026); [How to evaluate a finding severity](https://docs.codehawks.com/hawks-auditors/how-to-evaluate-a-finding-severity) (CodeHawks, 2025) · dossier: web3-audit-practice G207-F16

### W3-04 — Build an access-control matrix for every state-changing entry point
- **Rule:** For every external or public non-view function, record the state it writes, the `msg.sender` or role check that guards it, and who holds that role. Flag writes to privileged state (owner, implementation, oracle, fee, minter, pause, allowlist) without authorization; `tx.origin` used for authorization; hooks and callbacks that do not check the caller (flash-loan callbacks, Uniswap v4 hooks, ERC-721/1155 receivers, bridge receive handlers); initializers anyone can call (W3-22); an unprotected or undocumented `selfdestruct`; and stale allowlist members.
- **Detect:** Slither printers `vars-and-auth` and `modifiers`; Slither detectors `suicidal`, `arbitrary-send-eth`, `arbitrary-send-erc20`, `arbitrary-send-erc20-permit`, `unprotected-upgrade`, `tx-origin`, `protected-vars`, `controlled-delegatecall`; forge lint `tx-origin`; `rg -n 'tx[.]origin' -g '*.sol'`. Read every callback entry point for an explicit `msg.sender == expectedCaller` check. Maps to OWASP SC01:2026 and EthTrust v3 [Q] Enforce Least Privilege and [S] No tx.origin.
- **Not when:** Functions permissionless by design (keeper pokes, liquidations, harvests): adding auth breaks liveness, so confirm intent from the docs first. EthTrust allows `tx.origin` under [Q] Verify tx.origin Usage, and `selfdestruct` under [M] Protect Self-destruction with [M] Document Special Code Use; since EIP-6780, `selfdestruct` deletes code only in the creation transaction. Scope: access control was 10% of 246 Trail of Bits audit findings (2019), a quarter of them high severity with low difficulty.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [SC01:2026 Access Control](https://scs.owasp.org/sctop10/SC01-AccessControlVulnerabilities/) (OWASP, 2026); [EthTrust v3](https://entethalliance.github.io/wg-ethtrust-site/spec/v3/) (EEA, 2025); [246 Findings](https://blog.trailofbits.com/2019/08/08/246-findings-from-our-smart-contract-audits-an-executive-summary/) (Trail of Bits, 2019); [Slither Printer documentation](https://github.com/crytic/slither/wiki/Printer-documentation) (Crytic, 2025); [Security Considerations](https://docs.soliditylang.org/en/latest/security-considerations.html) (Solidity docs, 2026); [EIP-6780](https://eips.ethereum.org/EIPS/eip-6780) (Ballet, Buterin, Feist, 2023); [Ronin Network - REKT](https://rekt.news/ronin-rekt/) (rekt.news, 2022) · dossier: web3-audit-practice G207-F03; lang-solidity-go T24-F05

### W3-05 — Inventory privileged powers and report centralisation in its own section
- **Rule:** List every privileged power (upgrade, mint, pause, sweep/rescue, oracle/fee/parameter setters, role admin) with its on-chain holder (EOA, Safe k-of-n, or timelock) and its level on Trail of Bits' maturity scale (L1 single EOA, L2 multisig, L3 timelock plus separated roles, L4 immutable). Flag EOA-held upgrade or mint power, sensitive operations without a timelock, low multisig thresholds, and bot hot keys that hold admin roles. Report all of these in a separate "centralisation / operational risk" section, never as dropped QA.
- **Detect:** Slither `vars-and-auth`. With an RPC: `cast call <addr> 'owner()(address)'` or `hasRole(bytes32,address)`; `cast code <holder>` (empty code means an EOA); Safe `getThreshold()` and `getOwners()`; a timelock between the owner and sensitive setters (EthTrust [Q] Use TimeLock Delays for Sensitive Operations); bot and keeper addresses cross-referenced against admin roles.
- **Not when:** Contest rubrics assume trusted admins on purpose (Code4rena files centralisation under QA, Sherlock assumes admin functions are "used correctly", Immunefi excludes centralisation and leaked-key impacts by default), so a rubric-only review under-reports this risk. Timelocks slow emergencies; Trail of Bits' L3 answer is a pause guardian with no timelock. Scope: key compromise was 43.8% of stolen crypto in 2024 (Chainalysis, all platforms); off-chain incidents were 80.5% of 2024 DeFi funds lost (Halborn); Wintermute lost over $160M through a hot wallet that was a vault admin, Radiant over $53M through a 3-of-11 multisig.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Maturing your smart contracts beyond private key risk](https://blog.trailofbits.com/2025/06/25/maturing-your-smart-contracts-beyond-private-key-risk/) (Trail of Bits, 2025); [$2.2 Billion Stolen in 2024](https://www.chainalysis.com/blog/crypto-hacking-stolen-funds-2025/) (Chainalysis, 2024); [Top 100 DeFi Hacks Report 2025](https://www.halborn.com/reports/top-100-defi-hacks-2025) (Halborn, 2025); [Code4rena Judging Criteria](https://docs.code4rena.com/competitions/judging-criteria.md) (Code4rena, 2026); [Immunefi v2.3](https://immunefi.com/immunefi-vulnerability-severity-classification-system-v2-3/) (Immunefi, n.d.); [Wintermute - REKT](https://rekt.news/wintermute-rekt-2/) (rekt.news, 2022); [Radiant Capital - REKT 2](https://rekt.news/radiant-capital-rekt2/) (rekt.news, 2024) · dossier: web3-audit-practice G207-F11

### W3-06 — Emit an event for every privileged state change
- **Rule:** Emit an event for every privileged or critical state change (roles, owners, fees, limits, pauses) immediately after the change, named in the past tense, and give every ABI-visible item NatSpec. Events are what off-chain monitoring watches after deployment.
- **Detect:** Slither `events-access`, `events-maths`; forge lint `missing-events-access-control`, `missing-events-arithmetic`, `event-fields` (the Slither and forge lint ids differ); Aderyn `state-variable-changes-without-events`; `external`/`public` functions, events and errors with no `///` or `/** */` comment before them.
- **Not when:** Events cost gas and change bytecode, so on a deployed immutable contract this waits for a redeploy (deployment gate). Moving an existing emit across an external call changes what `reentrancy-events` reports and what indexers see.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** A
- **Source:** [Style Guide: NatSpec](https://docs.soliditylang.org/en/latest/style-guide.html) (Solidity docs, 2026); [OpenZeppelin GUIDELINES.md](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/master/GUIDELINES.md) (OpenZeppelin, 2026); [Development guidelines](https://secure-contracts.com/development-guidelines/guidelines.html) (Trail of Bits, n.d.); [Slither Detector Documentation](https://github.com/crytic/slither/wiki/Detector-Documentation) (Crytic, 2026); [Aderyn detectors](https://cyfrin.gitbook.io/cyfrin-docs/project-configuration/list-of-supported-detectors) (Cyfrin, 2026); [Forge lint](https://getfoundry.sh/forge/linting) (Foundry, 2026) · dossier: lang-solidity-go T24-F13

### W3-07 — Multisig admin actions need a documented signing procedure
- **Rule:** Where W3-05 finds powers held by a multisig, check for a documented signing procedure: calldata decoded and verified independently of the signing UI, the on-device Safe transaction hash compared with one computed independently, dedicated signing devices, thresholds matched to the blast radius, a timelock review window for sensitive operations, and drilled playbooks for lost keys and a compromised communication channel. Report a missing procedure; writing it is the owner's job.
- **Detect:** Look for a SIGNING.md, runbook or incident-response doc covering these items. With an RPC, read the Safe threshold and owner count and check for a timelock between the Safe and sensitive setters.
- **Not when:** Timelocks and high thresholds slow incident response (Trail of Bits' answer is a low-threshold pause guardian), and small teams cannot staff many independent signers. Scope: in 2025 Bybit's signers approved a masked transaction and $1.43B was lost (rekt; Chainalysis reports $1.5B); SEAL: multisigs "fail operationally more often than cryptographically".
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [SEAL Multisig for Protocols](https://frameworks.securityalliance.org/multisig-for-protocols/overview) (Security Alliance, 2025); [SEAL Wallet Security](https://frameworks.securityalliance.org/wallet-security/overview) (Security Alliance, 2025); [Bybit - REKT](https://rekt.news/bybit-rekt/) (rekt.news, 2025); [Crypto Crime Mid-year Update 2025](https://www.chainalysis.com/blog/2025-crypto-crime-mid-year-update/) (Chainalysis, 2025); [EthTrust v3](https://entethalliance.github.io/wg-ethtrust-site/spec/v3/) (EEA, 2025) · dossier: web3-audit-practice G207-F22

### W3-08 — Check every state-changing path against invariants derived from the docs
- **Rule:** Derive the accounting invariants from the docs (sum of balances equals totalSupply; totalAssets covers all redeemable shares; total withdrawals never exceed deposits plus realized yield; no account ends an action above the allowed LTV; share price does not fall outside loss events) and check every state-changing function against them, functions added later first (donations, reserves, rebalancers, emergency paths). A function that reduces balance, debt or collateral without the main path's health or solvency check is a finding (the Euler pattern). On-chain invariant guards are an owner decision.
- **Detect:** Build a function × invariant table; for each value-reducing function, confirm it runs the same accounting hook as the main path. Encode each invariant as a test (W3-09). Maps to OWASP SC02:2026.
- **Not when:** Invariants are only as good as the spec: undocumented economics make them guesses, so mark those as inferred. On-chain guards cost gas and can revert falsely. Scope: in Trace2Inv (FSE 2024, 27 exploits, all before 2024) one guard would have blocked 18 and combined guards up to 23, with false-positive rates as low as 0.32%; missing logic or sanity checks was the largest root cause in Chaliasos (42 of 127 attacks); Euler lost about $197M through `donateToReserves`.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [SC02:2026 Business Logic](https://scs.owasp.org/sctop10/SC02-BusinessLogicVulnerabilities/) (OWASP, 2026); [Trace2Inv](https://arxiv.org/abs/2404.14580) (Chen et al., FSE 2024); [Euler Finance - REKT](https://rekt.news/euler-rekt/) (rekt.news, 2023); [Smart Contract and DeFi Security Tools](https://arxiv.org/abs/2304.02981) (Chaliasos et al., ICSE 2024) · dossier: web3-audit-practice G207-F04

### W3-09 — Encode the invariants as handler-based invariant tests
- **Rule:** Write each W3-08 invariant in plain English, then as a Foundry handler-based suite (handlers bound inputs, use several actors and keep ghost variables for sums; `targetContract` points at the handler, restricted by `targetSelector`), run it at the Foundry config defaults (`runs=256`, `depth=500`, `fail_on_revert=false`, `shrink_run_limit=5000`, `show_metrics=true`) and confirm from the metrics that every selector is called and not mostly reverting. Reuse the properties through Chimera in Medusa or Echidna for longer coverage-guided campaigns, measure property strength with mutation testing, and keep every counterexample as a regression unit test. A property that fails on the base commit is reported as a W3-08 finding with its counterexample.
- **Detect:** `rg -n 'function invariant_' -g '*.sol'` (no hits is a gap); handler suites contain `targetContract(address(handler))`; in `forge test --match-test invariant` metrics, a selector with zero calls or about 100% reverts is a gap; `forge config | rg invariant` for the effective settings; Medusa's coverage HTML.
- **Not when:** Fuzzers find only violations of properties someone wrote. The invariant guide's `depth = 100` is an example, not the default: copying it cuts depth fivefold. No source gives an invariant count or an hour budget: run a short campaign per step, aim to surface issues within 5 minutes (Echidna's design goal, no upper bound) and let coverage decide whether to extend. Echidna's "up to 63%" of severe flaws for user-defined properties is an estimate (ISSTA '20), not a replicated measurement; Echidna now gets minor fixes only and Trail of Bits develops Medusa (2025).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** B
- **Source:** [Foundry config reference: testing](https://getfoundry.sh/config/reference/testing) (Foundry, 2026); [Foundry invariant testing](https://getfoundry.sh/forge/invariant-testing) (Foundry, 2026); [Echidna](https://agroce.github.io/issta20.pdf) (Grieco et al., ISSTA 2020); [How to write good properties](https://secure-contracts.com/program-analysis/echidna/basic/property-creation.html) (Trail of Bits, 2024); [Echidna FAQ](https://raw.githubusercontent.com/crytic/building-secure-contracts/master/program-analysis/echidna/frequently_asked_questions.md) (Trail of Bits, 2024); [Unleashing Medusa](https://blog.trailofbits.com/2025/02/14/unleashing-medusa-fast-and-scalable-smart-contract-fuzzing/) (Trail of Bits, 2025); [Chimera](https://github.com/Recon-Fuzz/chimera) (Recon, 2025); [Find Highs Before External Auditors](https://dacian.me/find-highs-before-external-auditors-using-invariant-fuzz-testing) (Dacian, 2024); [SEAL Security Testing](https://frameworks.securityalliance.org/security-testing/overview) (Security Alliance, 2025) · dossier: web3-audit-practice G207-F12

### W3-10 — Escalate to symbolic or formal tools only where sampling cannot reach, and list what was abstracted
- **Rule:** Recommend symbolic or formal checking only for math-heavy code that random sampling rarely reaches (fixed-point and share conversion, tick or curve math, rounding, custom overflow checks) and for protocols where a single violated invariant means insolvency. For any existing or new proof, list what was abstracted or summarised and treat excluded libraries as unverified.
- **Detect:** A scoping table of every math and library file imported, vendored ones included, marked fuzzed, symbolically checked, formally verified or unverified. Grep Certora `.spec` and `.conf` files for summaries (`NONDET`, `DISPATCHER`, `ALWAYS`) and harness abstractions; record the Halmos `--loop` bound. Halmos and Kontrol reuse Foundry tests; Halmos unrolls loops to a bound, needs fixed-size dynamic arrays, performs poorly with `bound()` (prefer `vm.assume`) and reports only `Panic(1)` assertion failures.
- **Not when:** Formal methods are expensive and need expertise; for hackathon-scale code W3-09 is the better use of time. Bounded results and summaries give false confidence: Certora's 2022 Balancer solvency proof abstracted StableMath, and Balancer lost $128M in November 2025 to one-directional rounding in `_upscale()`. No source compares the yield of Halmos, Kontrol and Certora on finished code.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** C
- **Source:** [Symbolic testing with Halmos](https://a16zcrypto.com/posts/article/symbolic-testing-with-halmos-leveraging-existing-tests-for-formal-verification/) (a16z crypto, 2023); [Halmos getting started](https://raw.githubusercontent.com/a16z/halmos/main/docs/getting-started.md) (a16z, 2025); [Kontrol documentation](https://docs.runtimeverification.com/kontrol) (Runtime Verification, 2025); [Balancer - REKT II](https://rekt.news/balancer-rekt2/) (rekt.news, 2025); [Cetus - REKT](https://rekt.news/cetus-rekt/) (rekt.news, 2025); [SEAL Security Testing](https://frameworks.securityalliance.org/security-testing/overview) (Security Alliance, 2025) · dossier: web3-audit-practice G207-F13

### W3-11 — Price sources must be manipulation-resistant, fresh and bounded
- **Rule:** Flag any price used for collateral, minting, liquidation or redemption that (a) comes from state manipulable within one block (AMM reserves via `getReserves` or `slot0`, pool `balanceOf`, a vault's own `totalAssets/totalSupply`), (b) uses Chainlink `latestRoundData` without comparing `updatedAt` with that feed's heartbeat or without a bounds check (at least > 0), (c) uses `latestAnswer`, which carries no timestamp, (d) on an L2 ignores the sequencer uptime feed and its grace period, or (e) relies on the aggregator's `minAnswer/maxAnswer` as circuit breakers. Stale or out-of-bounds data must fail safe: pause or revert.
- **Detect:** `rg -n 'getReserves[(]|slot0[(]|latestAnswer[(]|latestRoundData[(]|balanceOf[(]address[(]this[)][)]' -g '*.sol'`; for each `latestRoundData`, confirm a per-feed staleness threshold and a range check; on L2 deployments, confirm the sequencer-uptime check; trace every price in collateral or mint math back to its source. Maps to OWASP SC03/SC04:2026 and EthTrust [Q] Protect against Oracle Failure.
- **Not when:** Spot prices are fine for non-collateral uses such as UI quotes. TWAPs lag and can still be pushed over several blocks on illiquid pools (EthTrust notes the staleness trade-off). Heartbeats can last several hours (Chainlink) and a threshold tighter than the heartbeat causes false reverts, so each feed's threshold is the owner's call. Scope: oracle manipulation was the second-largest root cause in Chaliasos (29 of 127 attacks), which the paper says current tools cannot detect.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [SC03:2026 Price Oracle Manipulation](https://scs.owasp.org/sctop10/SC03-PriceOracleManipulation/) (OWASP, 2026); [So you want to use a price oracle](https://www.paradigm.xyz/2020/11/so-you-want-to-use-a-price-oracle) (samczsun, 2020); [Chainlink Data Feeds](https://docs.chain.link/data-feeds) and [API reference](https://docs.chain.link/data-feeds/api-reference) (Chainlink, 2026); [Solcurity](https://github.com/transmissions11/solcurity) (transmissions11, 2021); [EthTrust v3](https://entethalliance.github.io/wg-ethtrust-site/spec/v3/) (EEA, 2025); [Smart Contract and DeFi Security Tools](https://arxiv.org/abs/2304.02981) (Chaliasos et al., ICSE 2024) · dossier: web3-audit-practice G207-F05, practitioner voice

### W3-12 — User-facing value paths take a caller bound and a deadline
- **Rule:** Every user-facing function whose outcome depends on price or state another actor can change in the same block (swaps, zaps, vault operations routed through AMMs, mint-at-price, liquidation rewards) must take a caller-supplied bound (`minAmountOut`/`maxAmountIn`, `minShares`/`maxAssets`) and a deadline. Also flag a hard-coded `0` minimum, `deadline: block.timestamp` in internal router calls, get-or-create sequences that can be front-run, deploy and initialize in separate transactions, and bots on public-mempool chains that send value-extracting transactions through a public route.
- **Detect:** `rg -n 'amountOutMin(imum)? *[:=] *0|minAmountOut *[:=] *0|deadline *: *block[.]timestamp' -g '*.sol'`; check that each external function calling a DEX or vault takes a user-supplied bound, that deploy scripts deploy and initialize the proxy in one transaction, and which RPC bot code sends through. Maps to EthTrust v3 [Q] Protect against Ordering Attacks (v2's "Front-Running") and [Q] Protect against MEV Attacks.
- **Not when:** Uniswap's own guide uses `amountOutMinimum: 0` and `deadline: block.timestamp` as demo shortcuts while calling the zero minimum "a significant risk in production", so demo code in production is a finding, not intent. Private-mempool chains reduce ordering risk without removing it (Sherlock lowers severity one level). Private RPCs require trusting builders, and over-tight bounds cause failed transactions and missed liquidations.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [Uniswap v3 single-hop swapping](https://developers.uniswap.org/docs/protocols/v3/guides/swapping/single-hop-swapping) (Uniswap Labs, 2026); [EthTrust v3](https://entethalliance.github.io/wg-ethtrust-site/spec/v3/) (EEA, 2025); [Cyfrin audit-checklist](https://github.com/Cyfrin/audit-checklist) (Cyfrin, 2024); [Sherlock Judging Guidelines](https://docs.sherlock.xyz/audits/judging/guidelines) (Sherlock, 2025); [Flashbots Protect](https://docs.flashbots.net/flashbots-protect/overview) (Flashbots, 2026) · dossier: web3-audit-practice G207-F07

### W3-13 — Treat every external call as untrusted
- **Rule:** Finish all checks and state writes before any external call (ETH send, token transfer, ERC-721/1155/777 hook, arbitrary call); where that is impossible, put a reentrancy guard on every function that shares the state, with `nonReentrant` as the first modifier. Check every low-level call and send result, route ERC-20 operations through SafeERC20, confirm code exists at low-level call targets, and never call a caller-supplied router or target address with the contract's privileges. Support only the token behaviours the README declares (fee-on-transfer, rebasing, missing return value, ERC-777 hooks) and document the rest.
- **Detect:** Slither `reentrancy-eth`, `reentrancy-no-eth`, `reentrancy-benign`, `reentrancy-events`, `unchecked-transfer`, `unchecked-lowlevel`, `unchecked-send`, `unused-return`, `controlled-delegatecall`, `arbitrary-send-erc20`, `erc20-interface`; forge lint `reentrancy-eth`, `reentrancy-balance`, `reentrancy-no-eth`, `non-reentrant-not-first`, `erc20-unchecked-transfer`, `unchecked-call`; Aderyn `unchecked-return`; `rg -n '[.]call[{(]|[.]delegatecall[(]' -g '*.sol'`. By hand: cross-function reentrancy (two functions share state, one guarded) and "safe" helpers that hide callbacks (`_safeMint` would have let an attacker mint 39 Hashmasks against a cap of 20). Maps to OWASP SC06/SC08:2026, EthTrust [S] Check External Calls Return and [S] Use Check-Effects-Interaction.
- **Not when:** Replacing `send`/`transfer` (deprecated in solc 0.8.31) with `call{value:}` forwards all gas and re-opens reentrancy unless checks-effects-interactions or a guard is present. Guards add gas and can block legitimate callbacks; `nonReentrant` on view-like paths can break integrations. A guard fails when the compiler is wrong (Vyper 0.2.15, 0.2.16, 0.3.0; Curve pools exploited 30 July 2023), and hand-written transient guards that `delete` a `transient` variable hit the solc 0.8.28–0.8.33 via-IR bug (OpenZeppelin's ReentrancyGuardTransient does not use `delete`). Document best-effort calls such as optional hooks instead of forcing a revert (EthTrust [M] Handle External Call Returns); an ERC-20 `.transfer(` is not an address transfer.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [SC06:2026 Unchecked External Calls](https://scs.owasp.org/sctop10/SC06-UncheckedExternalCalls/) (OWASP, 2026); [EthTrust v3](https://entethalliance.github.io/wg-ethtrust-site/spec/v3/) (EEA, 2025); [Security Considerations](https://docs.soliditylang.org/en/latest/security-considerations.html) (Solidity docs, 2026); [Slither Detector Documentation](https://github.com/crytic/slither/wiki/Detector-Documentation) (Crytic, 2026); [Forge lint](https://getfoundry.sh/forge/linting) (Foundry, 2026); [The Dangers of Surprising Code](https://samczsun.com/the-dangers-of-surprising-code/) (samczsun, 2021); [Sherlock Judging Guidelines](https://docs.sherlock.xyz/audits/judging/guidelines) (Sherlock, 2025); [Solidity v0.8.31 release](https://github.com/ethereum/solidity/releases/tag/v0.8.31) (ethereum/solidity, 2025); [Vyper nonreentrancy post-mortem](https://hackmd.io/@vyperlang/HJUgNMhs2) (Vyper team, 2023); [ReentrancyGuardTransient.sol v5.7.0](https://raw.githubusercontent.com/OpenZeppelin/openzeppelin-contracts/v5.7.0/contracts/utils/ReentrancyGuardTransient.sol) (OpenZeppelin, 2026) · dossier: web3-audit-practice G207-F15, G207-F16; lang-solidity-go T24-F03, T24-F04, T24-F05

### W3-14 — Signed actions bind domain, nonce, deadline and every value-relevant parameter
- **Rule:** Every signature-authorised action must bind an EIP-712 domain with chainId and verifyingContract, a per-signer nonce or used-hash mapping consumed on use, a deadline, and every economically relevant parameter. Verify with OpenZeppelin ECDSA or `SignatureChecker` (which supports ERC-1271 wallets), never with raw `ecrecover` lacking an `address(0)` check, and never use signature bytes as the replay-protection key. Keep the domain separator tied to `block.chainid` and the proxy's address, and never pass consecutive dynamic arguments to `abi.encodePacked`.
- **Detect:** `rg -n 'ecrecover[(]' -g '*.sol'` (every hit is a candidate); `rg -n 'DOMAIN_SEPARATOR|_domainSeparatorV4|EIP712|nonces[[]' -g '*.sol'`, then confirm the nonce is consumed on the same path; any `mapping(bytes => bool)` keyed on signature bytes; Slither `encode-packed-collision`; by hand, every value-affecting field is in the typehash, and any hand-rolled cached domain separator (OpenZeppelin's upgradeable EIP712 rebuilds from live values). Maps to EthTrust v3 [S] Encode Hashes with chainid, [M] Proper Signature Verification, [M] No Improper Usage of Signatures for Replay Attack Protection.
- **Not when:** Intentionally reusable signatures such as standing allowlists are allowed when documented and shown safe (EthTrust [Q] Intended Replay). OpenZeppelin 5.x rejects malleable high-s signatures today but marks that check deprecated for removal in v6.0, so code relying on it for replay protection breaks on upgrade. ERC-1271 support widens the attack surface to contract wallets. Dacian's catalogue ties each missing binding to real contest findings (missing nonce, cross-chain replay, missing parameter, no expiry, `ecrecover` returning zero, malleability).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [EthTrust v3](https://entethalliance.github.io/wg-ethtrust-site/spec/v3/) (EEA, 2025); [OpenZeppelin 5.x Cryptography](https://docs.openzeppelin.com/contracts/5.x/api/utils/cryptography) (OpenZeppelin, 2025); [Signature Replay Attacks](https://dacian.me/signature-replay-attacks) (Dacian, 2023); [Solcurity](https://github.com/transmissions11/solcurity) (transmissions11, 2021); [Cyfrin audit-checklist](https://github.com/Cyfrin/audit-checklist) (Cyfrin, 2024) · dossier: web3-audit-practice G207-F06

### W3-15 — Flag denial-of-service vectors in loops, push payments and griefable state
- **Rule:** Flag loops over storage arrays or sets that any user can grow, external calls inside loops, push payments to arbitrary addresses (prefer pull), `msg.value` read inside loops or batched `delegatecall`, low-level calls that copy unbounded return data, and griefable state such as dust positions that block liquidation or a front-run that fills a queue. Grade them with W3-03.
- **Detect:** Slither `calls-loop`, `costly-loop`, `msg-value-loop`, `delegatecall-loop`, `return-bomb`; `rg -n 'for *[(].*[.]length' -g '*.sol'`, then check whether a non-privileged path can grow each array; list caller-chosen recipients inside loops.
- **Not when:** Loops over arrays that only an admin can grow are fine. Pagination and pull patterns change UX and ABI, and gas limits differ by chain. SWC-128 is a legacy registry, not updated since 2020. Scope: samczsun's 2021 MISO finding put about $350M (109k ETH) at risk because `msg.value` persists across a `delegatecall` batch.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [SWC-128](https://swcregistry.io/docs/SWC-128) (SWC Registry, 2020); [Security Pitfalls & Best Practices 101](https://secureum.substack.com/p/security-pitfalls-and-best-practices-101) (Secureum, 2021); [Two Rights Might Make A Wrong](https://samczsun.com/two-rights-might-make-a-wrong/) (samczsun, 2021); [Slither Detector Documentation](https://github.com/crytic/slither/wiki/Detector-Documentation) (Crytic, 2025); [Sherlock Judging Guidelines](https://docs.sherlock.xyz/audits/judging/guidelines) (Sherlock, 2025); [Immunefi v2.3](https://immunefi.com/immunefi-vulnerability-severity-classification-system-v2-3/) (Immunefi, n.d.) · dossier: web3-audit-practice G207-F08

### W3-16 — Round in the protocol's favour and prove that repeated operations create no free value
- **Rule:** Multiply before dividing (also inside wmul/wdiv helpers); round shares minted and assets paid out down, fees and shares burned up; normalise mixed-decimals tokens instead of hard-coding 1e18; guard downcasts with SafeCast; revert when a computed deduction rounds to zero; and give ERC-4626 vaults an inflation defence (virtual shares and assets via `_decimalsOffset`, or a dead deposit). Document the intended rounding direction for each `mulDiv` and pair every rounding change with an invariant test over repeated and multi-operation flows (W3-09): OWASP SC07 asks both to decide the direction and to prove that repeated interactions cannot create free value.
- **Detect:** Slither `divide-before-multiply`, `incorrect-equality`; forge lint `divide-before-multiply`, `unsafe-typecast`; `rg -n 'uint(8|16|32|40|48|64|96|112|128|160|192|224)[(]' -g '*.sol'` for unchecked downcasts; `rg -n '1e18|10[*][*]18' -g '*.sol'` near token amounts; ERC-4626 vaults with neither `_decimalsOffset` nor a dead deposit. Treat a divide-before-multiply reorder as a bug fix with a test, never as a refactor.
- **Not when:** Changing rounding shifts outputs by a few wei: it breaks exact-value tests and integrators and, in upgradeable systems, can create accounting discontinuities (deployment gate). Reordering multiply and divide changes results and can overflow (Slither: "unless the limit of a smaller type makes this dangerous"). Some user-favourable rounding is a deliberate UX choice with bounded cost. Scope: OWASP SC07 cites zkLend (about $9.5M) and Bunni ($8.4M) in 2025; Balancer lost $128M in November 2025 through one-directional rounding despite over a dozen audits.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** B
- **Source:** [SC07:2026 Arithmetic Errors](https://scs.owasp.org/sctop10/SC07-ArithmeticErrors/) (OWASP, 2026); [ERC-4626](https://docs.openzeppelin.com/contracts/5.x/erc4626) (OpenZeppelin, 2025); [Precision Loss Errors](https://dacian.me/precision-loss-errors) (Dacian, 2023); [Slither Detector Documentation](https://github.com/crytic/slither/wiki/Detector-Documentation) (Crytic, 2026); [Balancer - REKT II](https://rekt.news/balancer-rekt2/) (rekt.news, 2025) · dossier: web3-audit-practice G207-F14, G207-F13; lang-solidity-go T24-F07

### W3-17 — Every unchecked block and special-code use carries a written justification
- **Rule:** Every `unchecked` block must carry a comment explaining why overflow cannot happen, and every use of special code (assembly, `delegatecall`, CREATE2, `block.timestamp`/`block.number`, oracles, pseudo-randomness, external calls, overflow-capable math) must say why it is needed and how misuse is prevented. Report missing justifications; the owner writes them.
- **Detect:** `rg -n -B2 -A6 'unchecked \{' -g '*.sol' -g '!lib/**' -g '!node_modules/**'` over the whole repository (Foundry `src/`, Hardhat `contracts/` and monorepo packages alike) for blocks with no justification; `rg -n 'assembly|delegatecall|create2|new [A-Z][A-Za-z]*\{salt|block\.(timestamp|number)|unchecked' -g '*.sol'`, then confirm a justification comment or `@dev` NatSpec per hit. Maps to EthTrust v3 [M] Document Special Code Use and [M] Safe Overflow/Underflow.
- **Not when:** From solc 0.8.22, loop-increment `unchecked` blocks are redundant when the compiler's conditions hold (see the Solidity language file); removing them is a separate cleanup, not a missing justification.

### W3-18 — A hardening pass adds no unchecked blocks, assembly or gas-golfing
- **Rule:** Never convert checked arithmetic to `unchecked`, introduce inline assembly or apply other gas-golfing during a hardening pass. Put gas-severity lints on an optional list with measured evidence, and require existing assembly to be marked `("memory-safe")` only when it truly is and to have a tested non-assembly reference.
- **Detect:** `rg -n 'assembly' -g '*.sol' -g '!lib/**' -g '!node_modules/**'` over the whole repository (each block needs a justification and a test against a Solidity reference); forge lint gas findings (`asm-keccak256`, `custom-errors`, `cache-array-length`, `costly-loop`) go to the optional list with `forge snapshot --diff` evidence; the pass's own diff contains no new `unchecked {` or `assembly` line.
- **Not when:** forge lint ships a gas lint that pushes toward assembly, OpenZeppelin tolerates guideline breaks for "significant efficiency gains" with explanatory comments, and for high-volume protocols gas is a user-facing cost: report such a trade-off to the owner, do not make it. Newer compilers already apply some of these optimizations (loop increments from 0.8.22, small custom-error reverts from 0.8.26). This is consensus guidance, not measured evidence.

### W3-19 — Cross-chain handlers authenticate the source and never trust default values
- **Rule:** Authenticate every inbound cross-chain message by source chain, source sender and the endpoint `msg.sender`; make sure no default or zero value (root, confirmAt, validator, sender) can count as proven; and bind replay protection to chainId plus a per-message nonce or processed hash. With an RPC, compare validator and relayer sets with the active operators.
- **Not when:** Much bridge risk lies in validator key custody (W3-05, W3-24, W3-25). Messaging-framework defaults vary by version, so check the framework's docs for the version in use. ### W3-20 — Detect proxies before touching storage, and validate layouts mechanically
- **Rule:** Before proposing or making any change to a state variable, inheritance order, base contract or storage struct, establish whether the contract is upgradeable or sits behind a proxy (UUPS, Transparent, Beacon, Diamond, or a custom `delegatecall` proxy). If it is, never reorder, insert, remove or retype variables: append only or use an ERC-7201 namespace, shrink `__gap` to match, and validate the layout mechanically before and after.
- **Detect:** Source: `rg -n 'Initializable|UUPSUpgradeable|ERC1967|TransparentUpgradeableProxy|__gap|erc7201:|diamondCut|facetAddress|delegatecall' -g '*.sol'`. With an RPC: `cast implementation <addr>`, `cast implementation --beacon <addr>`, the ERC-1967 admin slot via `cast storage`, the Diamond loupe `facets()`. Maps to OWASP SC10:2026.
- **Not when:** A zero ERC-1967 admin slot does not prove the contract is not a proxy: UUPS proxies usually have no admin, so rely on the implementation slot. Non-upgradeable contracts have no layout constraint, but fixing a deployed one means a redeploy or migration. Trail of Bits (2018) advised against delegatecall upgradeability in favour of migration; treat that as a dated dissent, since OWASP SC10:2026 and OpenZeppelin treat audited standard proxy patterns as current practice. Scope: Audius lost 18.56M AUDIO (about $6M valued, $1M realised) to a known proxy/Initializable storage collision after audits.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A

### W3-21 — Cleanups that look safe can change storage layout or ABI
- **Rule:** In upgradeable or deployed code, never apply a cleanup that changes storage layout or ABI: removing an "unused" state variable or a `__gap` array, reordering state variables, converting a storage variable to `constant` or `immutable` (the compiler reserves no slot for constants), or renaming or removing public/external functions or events (they are selectors and topics). Report these to the owner; in non-upgradeable, not-yet-deployed code they are ordinary changes for the other lenses. OpenZeppelin major-version bumps are covered by SO-15 in the Solidity language file (grade C), not here.
- **Detect:** Before any Solidity edit from any lens, run the W3-20 proxy check, snapshot `forge inspect <C> storageLayout` and `forge inspect <C> methodIdentifiers`, and require both identical afterwards unless an approved break is intended. Tool hits that invite these edits: Slither `unused-state`, `constable-states`, `immutable-states`, `naming-convention`; forge lint `unused-state-variables`, `could-be-constant`, `could-be-immutable`; Aderyn `unused-state-variable`.
- **Not when:** OpenZeppelin's upgrade plugins flag `immutable` in implementations as unsafe by default, because the value lives in bytecode shared by every proxy. Unused internal functions in abstract bases or libraries may exist for inheritors, and unused errors or events in interfaces may belong to a published ABI or EIP. Reordering state variables in a non-upgradeable contract can still change packing and gas. Grade B because the constant/immutable clause rests on T24-F10 (downgraded to B); the storage-layout and ABI guard alone is grade A (G207-F09, T24-F08, T24-F09).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** B
- **Source:** [Writing Upgradeable Contracts](https://docs.openzeppelin.com/upgrades-plugins/writing-upgradeable) (OpenZeppelin, 2026); [Upgrades FAQ](https://docs.openzeppelin.com/upgrades-plugins/faq) (OpenZeppelin, 2026); [forge inspect](https://getfoundry.sh/forge/reference/forge-inspect) (Foundry, 2026); [Slither Detector Documentation](https://github.com/crytic/slither/wiki/Detector-Documentation) (Crytic, 2026); [Forge lint](https://getfoundry.sh/forge/linting) (Foundry, 2026); [Aderyn detectors](https://cyfrin.gitbook.io/cyfrin-docs/project-configuration/list-of-supported-detectors) (Cyfrin, 2026) · dossier: lang-solidity-go T24-F08, T24-F09, T24-F10; web3-audit-practice G207-F09

### W3-22 — Initializers are locked, complete and run atomically with deployment
- **Rule:** In upgradeable code, require that the implementation constructor calls `_disableInitializers()` (annotated `@custom:oz-upgrades-unsafe-allow constructor`), `initialize()` carries `initializer` and later versions use increasing `reinitializer(n)`, every parent `__X_init` runs exactly once, and UUPS `_authorizeUpgrade` is overridden with access control. Implementations contain no `selfdestruct` and no `delegatecall` to caller-controlled targets, deploy scripts deploy and initialize the proxy in one transaction, and upgrades that change validation logic are reviewed like new code.
- **Detect:** `slither-check-upgradeability` (missing-init-modifier, missing-calls, multiple-calls, initialize-target, initializer-missing); `rg -n 'function initialize' -g '*.sol'`, each hit checked for a modifier; `rg -n '_disableInitializers' -g '*.sol'`; `rg -n '_authorizeUpgrade' -A3 -g '*.sol'` (an empty body with no auth is a finding); init calldata passed to the proxy constructor in deploy scripts; with an RPC, `cast call <proxy> 'owner()(address)'` returns the expected owner.
- **Not when:** Non-upgradeable contracts correctly initialize in the constructor. A deployed implementation cannot be patched in place: the fix is a new implementation plus an upgrade, itself risky, so the deployment gate makes it T2 (Nomad lost $190M after a routine upgrade's initialization set a `0x00` trusted root). Scope: OWASP SC10:2026 cites Kinto ($1.55M, July 2025) and a 2025 campaign against uninitialized ERC-1967 proxies ($10M+ across protocols).
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [Writing Upgradeable Contracts](https://docs.openzeppelin.com/upgrades-plugins/writing-upgradeable) (OpenZeppelin, 2025); [OpenZeppelin 5.x Proxy API](https://docs.openzeppelin.com/contracts/5.x/api/proxy) (OpenZeppelin, 2025); [The Proxy Hack](https://audita.io/blog-articles/the-proxy-hack-uninitialized-contracts-costing-defi-10m-in-losses) (Audita, 2025); [Nomad Bridge - REKT](https://rekt.news/nomad-rekt/) (rekt.news, 2022); [SC10:2026](https://scs.owasp.org/sctop10/SC10-ProxyAndUpgradeabilityVulnerabilities/) (OWASP, 2026); [EthTrust v3](https://entethalliance.github.io/wg-ethtrust-site/spec/v3/) (EEA, 2025) · dossier: web3-audit-practice G207-F10

### W3-23 — Code changed after the audit, upgraded, or outside audit scope is unaudited
- **Rule:** Treat as unaudited any code changed after the last audit baseline, every upgrade transaction, and dependencies and math libraries outside the audit's stated scope, vendored or forked copies included. Record the audit commit, the scope list and every out-of-scope import, and for deployed contracts classify each fix as source-only for the next deploy, requires upgrade (then W3-20 to W3-22 apply), or requires migration.
- **Detect:** `git diff <audited_commit>..HEAD --stat -- '*.sol' '*.vy'` (the pathspec matches at any depth, so Foundry `src/`, Hardhat `contracts/` and monorepo layouts are all covered; every changed file gets the full W3-02 checklist); compare the audit's scope table with `rg -n '^import' -g '*.sol' -g '!lib/**' -g '!node_modules/**'`, the remappings and `lib/`; with an RPC, compare `cast implementation <proxy>` with the verified source of the audited commit. Vendored copies of pinned libraries are reported under SO-15 in the Solidity language file. Never describe such code as audited in the report.
- **Not when:** When a full re-review is too costly, a diff-scoped review is the proportionate minimum. Audits still correlate with lower losses: in Halborn's top-100 DeFi hacks (2014–2024, $10.77B), only 20% of hacked protocols were audited and they account for 10.8% of value lost, a correlational figure from hacked protocols only. Cases: Euler's later EIP-14 change was reviewed separately and the bug missed (Sherlock paid a $4.5M claim); Nomad's routine upgrade, foreshadowed by audit issue QSP-19; Cetus (Sui/Move) failed in a library outside the scope of an audit completed 41 days earlier.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Euler Finance - REKT](https://rekt.news/euler-rekt/) (rekt.news, 2023); [Nomad Bridge - REKT](https://rekt.news/nomad-rekt/) (rekt.news, 2022); [Cetus - REKT](https://rekt.news/cetus-rekt/) (rekt.news, 2025); [Top 100 DeFi Hacks Report 2025](https://www.halborn.com/reports/top-100-defi-hacks-2025) (Halborn, 2025); [EthTrust v3](https://entethalliance.github.io/wg-ethtrust-site/spec/v3/) (EEA, 2025) · dossier: web3-audit-practice G207-F24

### W3-24 — Keep signing keys out of the repo, env files, images, CLI flags and logs
- **Rule:** Off-chain signing keys that control mainnet value (deployer, keeper, liquidation or arbitrage bot, relayer) must not appear in plaintext in the repo, `.env`, Docker `ENV`/`ARG`, CLI flags (`--private-key`) or logs: deployments use a hardware wallet or an encrypted keystore (`cast wallet import`), and bots use a KMS- or HSM-backed signer (AWS KMS key spec `ECC_SECG_P256K1`, Google Cloud KMS) or a remote signer such as OpenZeppelin Relayer. A committed key goes into the report for a human to rotate and move to proper custody; never print, move or rewrite it.
- **Detect:** `rg -n --hidden -g '!node_modules' -g '!.git' 'PRIVATE_KEY|privateKeyToAccount[(]|new (ethers[.])?Wallet[(]|fromMnemonic|MNEMONIC|--private-key'`; `rg -n 'ENV .*KEY|ARG .*KEY' -g 'Dockerfile*'`; detect-secrets over git history; whether loggers can serialise config that contains keys, and whether the signer is built directly from `process.env`. Cite file:line and commit, never the value.
- **Not when:** Env vars may hold KMS or service credentials rather than raw signing keys (OpenZeppelin Relayer suggests env vars and service accounts for service credentials; OWASP discourages env vars for secrets; Foundry says keys encrypted, not plaintext env vars). KMS adds a round-trip per signature, which matters for latency-sensitive arbitrage, and a compromised IAM principal can still use the key. For testnet and hackathon work an encrypted keystore is proportionate; Anvil's default keys are public and never belong on a public network. Scope: private-key compromise was 43.8% of stolen crypto in 2024 (Chainalysis: $2.2B over 303 incidents, centralized services included).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Foundry key management](https://getfoundry.sh/guides/best-practices/key-management) (Foundry, 2026); [Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) (OWASP, 2025); [AWS KMS key spec reference](https://docs.aws.amazon.com/kms/latest/developerguide/symm-asymm-choose-key-spec.html) (AWS, 2026); [OpenZeppelin Relayer Signers](https://docs.openzeppelin.com/relayer/configuration/signers) (OpenZeppelin, 2026); [$2.2 Billion Stolen in 2024](https://www.chainalysis.com/blog/crypto-hacking-stolen-funds-2025/) (Chainalysis, 2024) · dossier: web3-audit-practice G207-F17

### W3-25 — Segregate keys by function and blast radius
- **Rule:** Bot and keeper hot keys hold only operational roles, never owner, admin, upgrader or minter; use separate keys per bot, per chain role and per environment; cap hot-wallet balances with top-ups from a colder wallet; revoke roles and allowlist entries when a key or partner is retired; and never use keys from vanity generators or other unvetted tools. Separate config entries per key are the in-repo part; on-chain role changes belong to the owner.
- **Detect:** Extract every signer address from bot and service configs; with an RPC, check `owner()`, each admin, upgrader and minter `hasRole(...)` and each allowlist (a bot address there is a finding); detect one key shared across processes or environments; `rg -n -i 'profanity|vanity' .`.
- **Not when:** More keys means more nonce management (W3-28), funding and monitoring. A bot that must pause gets a narrow pause role, not owner. Scope: Wintermute lost over $160M through a Profanity vanity key on a hot wallet that was also a vault admin; Ronin's allowlist entry "was never revoked".
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Wintermute - REKT](https://rekt.news/wintermute-rekt-2/) (rekt.news, 2022); [Ronin Network - REKT](https://rekt.news/ronin-rekt/) (rekt.news, 2022); [Maturing your smart contracts beyond private key risk](https://blog.trailofbits.com/2025/06/25/maturing-your-smart-contracts-beyond-private-key-risk/) (Trail of Bits, 2025); [Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) (OWASP, 2025); [Foundry key management](https://getfoundry.sh/guides/best-practices/key-management) (Foundry, 2026) · dossier: web3-audit-practice G207-F18

### W3-26 — Scope centralized-exchange API keys to least privilege
- **Rule:** Keep monitoring keys read-only and trading keys without withdrawal permission; require an IP allowlist, plus an address allowlist where the exchange offers one, for any key that can withdraw; give each bot or strategy its own key with an expiry where supported; and store keys like passwords. Check code and config for one key per purpose and for key material in logs, and put exchange-side settings in the report as items for the owner to confirm.
- **Detect:** `rg -n -i 'api[_-]?key|api[_-]?secret' --hidden -g '!node_modules'`; confirm each bot reads its own key variable and that telemetry never serialises the exchange client config; add a report item asking the owner to confirm on the exchange dashboard that withdrawals are off and an IP allowlist is set.
- **Not when:** IP allowlisting needs static egress IPs, and strategies that need automated withdrawals rely on address allowlists instead. Binance gives unrestricted-IP HMAC keys read-only permission and recommends against other permissions without IP restrictions; Kraken offers granular permissions, an IP whitelist and key expiry.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [How to create API keys on Binance](https://www.binance.com/en/support/faq/how-to-create-api-keys-on-binance-360002502072) (Binance, 2026); [How to create an API key](https://support.kraken.com/hc/en-us/articles/360000919966-How-to-create-an-API-key) (Kraken, 2026) · dossier: web3-audit-practice G207-F19

### W3-27 — Base no value-moving off-chain decision on a single RPC response
- **Rule:** For liquidations, arbitrage, deposit confirmation before release, and oracle or pool reads, use a quorum of independent providers (for example ethers v6 `FallbackProvider` with a quorum of at least 2), your own node, or cross-checks of critical reads, and read at a `finalized` or `safe` tag before irreversible actions. Provider quorum and block tag can change behind a config flag; running your own node is the owner's decision.
- **Detect:** `rg -n 'JsonRpcProvider[(]|WebSocketProvider[(]|createPublicClient[(]|http[(]|FallbackProvider[(]|fallback[(]' -g '*.ts' -g '*.js' -g '*.py'`; for each value-moving path, count the independent providers (a single vendor URL is the finding) and check the block tag (`latest` before an irreversible action is the finding). MEV-sensitive sends follow W3-12.
- **Not when:** A quorum adds latency and can lose competitive races, vendors may share upstream infrastructure, and waiting for finality delays action. Sherlock treats reorg and liveness issues as invalid, so contest-audited code may never have been checked for them. No loss data on RPC-caused losses was found.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** C
- **Source:** [ethers v6 FallbackProvider](https://docs.ethers.org/v6/api/providers/fallback-provider/) (ethers.js, 2026); [Nodes and clients](https://ethereum.org/en/developers/docs/nodes-and-clients/) (ethereum.org, 2026); [cast implementation (block tags)](https://getfoundry.sh/cast/reference/implementation) (Foundry, 2026); [Sherlock Judging Guidelines](https://docs.sherlock.xyz/audits/judging/guidelines) (Sherlock, 2025) · dossier: web3-audit-practice G207-F20

### W3-28 — One nonce authority per hot key
- **Rule:** Give each hot key exactly one nonce authority (a serialized nonce manager in one process, or a relayer), never let two instances sign with the same key using independently fetched nonces, resync from the chain on nonce errors, and replace stuck transactions at the same nonce with a bumped fee.
- **Detect:** `rg -n 'getTransactionCount[(]|nonce *:' -g '*.ts' -g '*.js' -g '*.py'`: per-call nonces inside concurrent code (`Promise.all`, worker pools) are a finding; check manifests for more than one replica sharing a key; check that error handlers recognise nonce errors and resync.
- **Not when:** An in-memory manager is lost on restart and must resync (ethers `NonceManager.reset()`); viem's nonce manager works only with local accounts; relayers add a dependency. Wrapping the signer is a small code change, but it is a concurrency fix, which this skill leaves to a human. No loss data specific to nonce handling was found.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** C
- **Source:** [ethers v6 NonceManager](https://docs.ethers.org/v6/api/providers/#NonceManager) (ethers.js, 2026); [viem createNonceManager](https://viem.sh/docs/accounts/local/createNonceManager) (viem, 2026); [OpenZeppelin Relayer](https://docs.openzeppelin.com/relayer) (OpenZeppelin, 2026) · dossier: web3-audit-practice G207-F21

## False-positive exclusions

- Functions permissionless by design: keeper pokes, liquidations, harvests (W3-04).
- `tx.origin` under a documented EthTrust [Q] Verify tx.origin Usage case, and a protected, documented `selfdestruct` (W3-04).
- Spot prices used only for non-collateral purposes such as UI quotes (W3-11).
- Signatures that are intentionally reusable and documented as safe under EthTrust [Q] Intended Replay (W3-14).
- Loops over arrays only an admin can grow (W3-15).
- Token behaviours the README does not declare: report a documentation gap, not an exploit (W3-13).
- ERC-20 `.transfer(` hits in address `send`/`transfer` sweeps, and best-effort calls whose ignored failure is documented (W3-13).
- Constructor initialization in non-upgradeable contracts (W3-22).
- Unused internal functions in abstract bases or libraries, and unused errors or events in interfaces that belong to a published ABI or EIP (W3-21).
- Anvil default keys used only against a local node, and encrypted keystores for testnet or hackathon work (W3-24).
- Env vars that hold KMS or service credentials rather than raw signing keys (W3-24).
- Front-running on a private-mempool chain: lower it one level, do not drop it (W3-03, W3-12).
- None of these closes a finding on its own: a zero ERC-1967 admin slot, since UUPS proxies have none (W3-20); a clean analyzer run (W3-01); a contest rubric that excludes centralisation or admin risk (W3-05); an audit report for code that changed since (W3-23).

## Evidence limits

- Detection figures come from specific populations: Chaliasos (5 tools, 127 attacks from one historical dataset), Web3Bugs (2021–2022, mostly Code4rena, which may over-represent logic bugs), Durieux (2019 tool versions), Trail of Bits (23 audits, 2019). Newer tools may do better. No public precision data exists for forge lint or Aderyn; Slither's 10.9% false-positive rate is a 2019 benchmark by its own vendor.
- Loss statistics are correlational or broad: Halborn's audited-share and multisig figures cover the top-100 hacks of 2014–2024, and Chainalysis's 43.8% includes centralized services.
- The OWASP Smart Contract Top 10:2026 is forward-looking; the pages read give no survey respondent count or per-category loss totals, and category statistics are noisy (OWASP files Balancer, November 2025, under SC01, while rekt.news attributes it to rounding).
- W3-03 is a grade-C synthesis; Immunefi v2.3 is undated and the Cantina rubric was unavailable (404).
- No source gives an invariant count, a fuzzing hour budget or a yield curve, and none compares Halmos, Kontrol and Certora. Trace2Inv's 27 exploits all predate 2024; replication on later ones is unknown.
- W3-27 and W3-28 rest on official docs only; no loss data exists for single-RPC trust or nonce races.
- The OpenZeppelin Relayer signer page read was the main-branch doc (stable is v1.5.x): confirm signer availability for the version in use. Cetus is Sui/Move: its scope lesson transfers, its tooling does not. No Vyper-specific analyzer was evaluated.
- Proxy detection covers common patterns only (slither-check-upgradeability, OpenZeppelin plugins); custom `delegatecall` proxies need manual reading.
- EthTrust v3 (March 2025) was the latest release as of 2026-09-23; check the EEA page before relying on it. v2 names such as [Q] Protect against Front-Running and "Signature Management" no longer exist.
- Practitioner forum voice (HN, Reddit, Ethereum StackExchange) and Code4rena Supreme Court verdicts were not reachable during research.
