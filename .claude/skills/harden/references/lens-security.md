# Lens: Security

> Find the security defects a finished project still carries (untrusted-input sinks, missing object-level authorization, fail-open paths, leaked secrets, vulnerable or phantom dependencies, unsafe CI) and prove each one before it is reported.
> Read when: the security lens is in scope, i.e. the project takes untrusted input, authenticates users, holds credentials, pulls third-party dependencies, builds containers or runs CI workflows.

## Contents
- Procedure
- Rules: proof and triage (SE-01, SE-02); input sinks (SE-03 to SE-06); authorization and binding (SE-07 to SE-09); failure paths, crypto and tokens (SE-10 to SE-13); outbound calls, limits and logs (SE-14 to SE-16); secrets (SE-17 to SE-19); supply chain (SE-20 to SE-26); CI and packaging (SE-27, SE-28)
- False-positive exclusions
- Evidence limits

## Procedure

You are a fresh-context, read-only lens subagent working on the slice the orchestrator gave you (detection step 8). You detect and triage; the orchestrator runs the tools, verifies, ranks and applies. Your tools are Read, Grep and Glob: never edit or write a file and never run a command. A detector whose output is missing from `.harden/tools/` becomes a coverage gap (step 8), not a guess.

1. **Load inputs.** Read `.harden/inventory.json` (languages, manifests, lockfiles, CI files, Dockerfiles), `.harden/prescan.json`, and the language file for each detected language. Exact tool commands live in the language files; this lens names the tool and rule ids. The orchestrator runs the project's own configured security tools first, with the project's config (detection step 3); read their outputs from `.harden/tools/`. No rule here overrides that config.
2. **Stay read-only.** Never edit, commit, rewrite history or touch credentials. The orchestrator's detector runs keep the same limits: no fix modes (`npm audit fix`, `--fix`), and no package installs to enable a scanner, because dependency install scripts execute code (SE-23). It writes raw tool output only to `.harden/tools/` (SARIF or JSON), pins every tool version and records it for `tool_versions`.
3. **Detector commands, language-agnostic (run by the orchestrator in detection step 4; read their outputs from `.harden/tools/`).** In an unseeded pass (DT-21), skip them. Their commands are in the rules because no language file owns them:
   - secrets: gitleaks over history and tree, plus Semgrep `p/secrets` (SE-17);
   - dependencies: OSV-Scanner over every lockfile (SE-20);
   - CI: zizmor over `.github/workflows/` (SE-27);
   - where Scorecard can run: `Pinned-Dependencies`, `Token-Permissions`, `Dangerous-Workflow`, `Binary-Artifacts`, `Dependency-Update-Tool`;
   - the Detect-line commands the Grep tool cannot run: `git log` and `git ls-files` (SE-17, SE-19, SE-22, SE-28), `docker history` on an existing image (SE-19), `pnpm --version` (SE-23) and registry metadata queries (SE-25).
4. **Detector commands, per language (run by the orchestrator in detection step 4; read their outputs from `.harden/tools/`).** Commands are in the language file:
   - All languages: Semgrep `p/owasp-top-ten`; CodeQL `<lang>-security-extended` suite where a database can be built.
   - Python: Bandit B102, B113, B301, B303, B307, B310, B311, B324, B501, B506, B602, B608; pip-audit; deptry; `bare-except` (Ruff or Pylint).
   - JS/TS: CodeQL `js/xss`; ESLint `no-empty`; npm audit (production scope, then full); pnpm and `.npmrc` settings (SE-23, SE-24); knip.
   - Go: govulncheck (call-stack reachability). Rust: cargo audit, cargo deny, cargo-udeps; OSV-Scanner call analysis is experimental for Rust and executes dependency `build.rs`, so it never runs in this pass (SE-20).
   - Java, .NET, PHP, Ruby: CodeQL injection and unsafe-deserialization queries; DepClean for Maven.
   - Containers: Trivy or Grype, and only on an image that is already built.
5. **Do the manual sweeps no tool covers.** These are route inventory and per-ID ownership (SE-07), request binding (SE-08), failure paths in auth, validation and payment code (SE-10), token validation (SE-13), outbound URLs and limits (SE-14, SE-15) and log calls (SE-16). Run each rule's `rg` patterns through the Grep tool and read every hit. A rule's shell commands (`git`, `gitleaks`, `docker`, `grep -L`) are detector commands: read their output from `.harden/tools/` or list them as not run.
6. **Triage every lead before returning it** (SE-01, SE-02). For code alerts, trace a source to the sink and check sanitization, benign context and trust boundary. For advisories, triage shipped, then reachable, then exploitable (SE-20). File each confirmed lead under the most specific SE rule, and keep the tool's own rule id in the evidence.
7. **Return candidates in the findings schema, plus files_read, as your final message; the orchestrator merges them** into `.harden/candidates.json`. files_read lists every file you read with its line ranges (DT-02). Follow `assets/findings.schema.json`, one candidate per location:
   - `lens: "security"`; `rule_ref` = SE-NN, or `project:<tool>/<rule>` for a project-configured tool;
   - `file` repo-relative and `line` at `base_sha`; `cwe` when the rule names one;
   - `evidence[]`: `tool` (command plus rule id), `source` (the trace), `git` (history hit), or `test` (a proposed failing test);
   - `confidence` from the evidence ladder; `tier`, `class` and `fix_risk` copied from the rule block;
   - `verified: false`, `status: "candidate"`.
   Never write a secret value into any field, command or message. Cite file:line, commit and scanner rule id instead.
8. **Record coverage gaps for Limits** in the same message. List scanners whose output is missing and why (no CodeQL database, no network, no built image), ecosystems without reachability analysis, and any history not scanned. Never report zero alerts as "secure".

## Rules

### SE-01 — Prove every security finding before it is reported or fixed
- **Rule:** Hold every candidate, whether it comes from a tool, a human note or an AI pass, to a proof bar: file:line, a concrete source-to-sink trace or a failing test or PoC, and the affected asset. Label anything below that bar a hypothesis (`confidence: inference`) and never apply it. When AI assistants wrote much of the code, look first at the categories with measured AI weakness: XSS, hardcoded secrets and invented dependencies.
- **Detect:** Check every candidate before emitting it: `evidence[]` holds a `source` trace, a `tool` rule id with a triage note, or a `test`, and `severity_criterion` is filled. Where practical, express a confirmed vulnerability as a regression test the apply phase can add before the fix.
- **Not when:** The AI-code evidence is mixed. The CCS 2023 user study used codex-davinci-002 (2022). Veracode 2025 (vendor, 100+ LLMs: 45% of samples failed security tests) and GitGuardian 2026 (vendor: 3.2% secret-leak rate for Claude Code-assisted commits against a 1.5% baseline, correlational) are vendor data. Unproven reports cost owners time: curl ended its bounty on 31 Jan 2026 after its confirmed rate fell from above 15% to below 5% of submissions (2025).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Do Users Write More Insecure Code with AI Assistants?](https://arxiv.org/abs/2211.03622) (Perry et al., CCS 2023); [2025 GenAI Code Security Report](https://www.veracode.com/blog/genai-code-security-report/) (Veracode, 2025); [State of Secrets Sprawl 2026](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2026/) (GitGuardian, 2026); [The end of the curl bug-bounty](https://daniel.haxx.se/blog/2026/01/26/the-end-of-the-curl-bug-bounty/) (Stenberg, 2026) · dossier: security-hardening T15-F22

### SE-02 — SAST output is a lead, not a verdict
- **Rule:** Run at least one semantic engine (CodeQL security-extended and/or Semgrep) plus the language's security linter. Triage every alert by tracing a concrete untrusted source to the flagged sink, or by showing the path is unreachable or constant. File a confirmed alert under the matching SE sink rule, which sets its tier; alerts that match no rule stay report-only, and a bare suppression (no rule id, no reason) is itself a finding.
- **Detect:** Run Semgrep `p/owasp-top-ten` (SARIF), CodeQL `<lang>-security-extended.qls` and Bandit. For each alert record the source, the path, the sink and any sanitizer on the path. Check the three dominant false-positive causes, measured on CodeQL Java alerts (500 sampled false-positive paths, 2026 preprint): missed sanitization 36.6%, benign context 29.4%, missing trust-boundary modeling 27.6%. Flag `nosemgrep` or `nosec` comments without a rule id.
- **Not when:** Recall is low. A single SAST tool warned in the vulnerable function for 52% of vulnerability-contributing commits, and at least 76% of the warnings there were irrelevant (ISSTA 2024, 92 C/C++ projects). CodeQL detected 171 of 3,993 CVEs (2026 preprint, 114 versions). security-extended trades precision for coverage, and Semgrep CE is intraprocedural only. Authorization and business logic are invisible to these tools, so SE-07 stays manual.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Static Analysis Tools for Secure Code Review](https://arxiv.org/abs/2407.12241) (Charoenwet et al., ISSTA 2024); [Longitudinal Analyses of SAST Tools](https://arxiv.org/abs/2605.07900) (Noirot Ferrand et al., 2026); [CodeQL False Positives for Java](https://arxiv.org/abs/2609.04535) (Sajadi et al., 2026); [CodeQL query suites](https://docs.github.com/en/code-security/code-scanning/managing-your-code-scanning-configuration/codeql-query-suites) (GitHub); [Semgrep Pro Engine intro](https://docs.semgrep.dev/semgrep-code/semgrep-pro-engine-intro) (Semgrep); [SP 800-218 SSDF](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218.pdf) (NIST, 2022) · dossier: security-hardening T15-F01

### SE-03 — Parameterize every path from untrusted data to an interpreter
- **Rule:** Where untrusted data reaches SQL or NoSQL, a shell, `eval`/`exec`/`new Function` or a template engine, convert the call to a server-side parameterized query, an argument-vector process call with no shell, or a built-in library function. Check identifiers that cannot be parameterized (table or column names, sort order) against a hard-coded allowlist. Escaping is only a fallback, and input validation is not the primary defense.
- **Detect:** Run Bandit B602, B608, B102 and B307, Semgrep `p/owasp-top-ten`, and the CodeQL sql-injection and command-injection queries. Then read every hit of these sweeps. Shell calls: `rg -n 'shell\s*=\s*True|os\.system\(|os\.popen\(|child_process\.(exec|execSync)\(|Runtime\.getRuntime\(\)\.exec|\bsystem\(|popen\('`. Dynamic code: `rg -n '\beval\(|new Function\(|\bexec\(|vm\.runIn'`. SQL built with f-strings, `+`, `%` or `.format(` inside `execute`/`query`/`raw` calls. ORM escape hatches: `$queryRawUnsafe`, `.raw(`, `text(` with f-strings, `extra(`.
- **Not when:** A query built only from constants is a false positive. Replacing `shell=True` with an argv list removes globbing, pipes and `$VAR` expansion, which changes visible behaviour.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html) (MITRE/CISA, 2025: CWE-89 #2, CWE-78 #9, CWE-94 #10); [Query Parameterization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Query_Parameterization_Cheat_Sheet.html) (OWASP); [OS Command Injection Defense Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html) (OWASP); [Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html) (OWASP); [Bandit blacklist calls](https://bandit.readthedocs.io/en/latest/blacklists/blacklist_calls.html) (PyCQA) · dossier: security-hardening T15-F12

### SE-04 — Route every HTML escape hatch and DOM sink through a text sink or a sanitizer
- **Rule:** Check every HTML escape hatch (`dangerouslySetInnerHTML`, `v-html`, `bypassSecurityTrustAs*`, `unsafeHTML`, `|safe`, `mark_safe`, `{{{ }}}`) and DOM sink (`innerHTML`, `outerHTML`, `document.write`, `insertAdjacentHTML`) that can carry user or third-party data. Switch each one to a text sink (`textContent`), or sanitize with DOMPurify immediately before insertion and change nothing afterwards. Allowlist the schemes of user-supplied `href`/`src` so that `javascript:` and `data:` fail.
- **Detect:** Escape hatches: `rg -n 'dangerouslySetInnerHTML|v-html|bypassSecurityTrust|unsafeHTML|\.innerHTML\s*=|\.outerHTML\s*=|insertAdjacentHTML|document\.write\(|\|\s*safe\b|mark_safe\(|\{\{\{'`. URL sinks: `rg -n 'href=\{|:href=|\[href\]|window\.location\s*=|location\.href\s*='`, then look for a scheme allowlist. CodeQL `js/xss` and Semgrep `p/owasp-top-ten` cover part of this.
- **Not when:** Developer-authored static HTML in the repo is acceptable through an escape hatch. `textContent` renders tags literally, and sanitizing can strip formatting users rely on; both are visible changes.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [Cross Site Scripting Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html) (OWASP); [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html) (MITRE/CISA, 2025: CWE-79 #1); [2025 GenAI Code Security Report](https://www.veracode.com/blog/genai-code-security-report/) (Veracode, 2025, vendor: XSS defence failed in 86% of relevant AI samples) · dossier: security-hardening T15-F13

### SE-05 — Trace request-influenced paths into filesystem calls
- **Rule:** Report every place where a request-derived value reaches a file API (open, read, send, upload destination), with the source-to-sink trace. The evidence base gives detection only and no sourced remediation pattern, so this rule never edits.
- **Detect:** Run `rg -n '(open|readFile|sendFile|send_file|Path)\(.*(req|request|params|args)'` and trace each hit. Check upload handlers for a size limit (SE-15). In the 2025 CWE Top 25, CWE-22 (path traversal) is #6 and CWE-434 (unrestricted upload) is #12.
- **Not when:** The trace shows only constants or server-side configuration on the path.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html) (MITRE/CISA, 2025) · dossier: security-hardening T15-F21

### SE-06 — Never deserialize untrusted data with native object serializers
- **Rule:** Where the bytes can cross the trust boundary, replace native object deserializers with JSON plus schema validation, a safe loader (`yaml.safe_load`), or a signed payload with a type allowlist. The deserializers in scope are Python `pickle`, `yaml.load` without a safe loader and `jsonpickle`; Java `ObjectInputStream.readObject` and `XMLDecoder`; .NET `BinaryFormatter` and Json.NET with `TypeNameHandling` other than None; PHP `unserialize`; Ruby `Marshal.load`.
- **Detect:** Run Bandit B301 and B506, the CodeQL unsafe-deserialization queries and Semgrep `p/owasp-top-ten`. Sweep with `rg -n 'pickle\.loads?\(|cPickle|jsonpickle\.decode|yaml\.load\(|yaml\.unsafe_load|ObjectInputStream|readObject\(|XMLDecoder|BinaryFormatter|TypeNameHandling\.(All|Auto|Objects|Arrays)|\bunserialize\(|Marshal\.load|shelve\.open|torch\.load\('`, including downloaded model or pickle files in ML code.
- **Not when:** Data that only your own process writes and reads inside one trust boundary is lower risk; report it low. Migrating a persisted format needs a one-time converter, which makes it a data migration (T2). `yaml.safe_load` rejects custom tags the app may rely on.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [Deserialization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Deserialization_Cheat_Sheet.html) (OWASP); [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html) (MITRE/CISA, 2025: CWE-502 #15); [Bandit blacklist calls](https://bandit.readthedocs.io/en/latest/blacklists/blacklist_calls.html) (PyCQA) · dossier: security-hardening T15-F14

### SE-07 — Audit object- and function-level authorization on every route that takes an ID
- **Rule:** Inventory every route, handler, RPC and GraphQL resolver. For each one that takes a client-supplied identifier, confirm three things: a server-side check ties the record to the caller (ownership, tenant or role) before any read, update or delete; non-public functions deny by default; and every client-side check has a server-side counterpart. Report each gap with a proposed two-user negative test (user A cannot read or modify B's object; a non-admin cannot call admin functions), and never invent the policy.
- **Detect:** Build the route inventory from the framework's route list or its route decorators and registrations. Grep identifier inputs (`req.params`, `request.args`, `@PathVariable`, `params[:id]`, GraphQL `args.id`) that are followed by a data access (`findById`, `get(`, `SELECT ... WHERE id =`) with no owner or tenant filter (`user_id`, `owner`, `tenant_id`) and no policy call nearby. A custom Semgrep rule can encode "fetch-by-id without owner filter" for the project's ORM. Generic scanners cannot find this, because it depends on business rules.
- **Not when:** New checks can lock out admins, shared resources, background jobs and service-to-service calls, so the owner decides. Random GUIDs make enumeration harder, but they are not authorization.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [OWASP Top 10:2025 A01](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/) (OWASP, 2025: 40 CWEs, 1,839,701 occurrences); [ASVS 5.0.0 V8](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x17-V8-Authorization.md) (OWASP, 2025: 8.2.2, 8.3.1 L1); [API1:2023 BOLA](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization) (OWASP, 2023); [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html) (MITRE/CISA, 2025: CWE-862 #4, CWE-639 #24); [First American leak](https://krebsonsecurity.com/2019/05/first-american-financial-corp-leaked-hundreds-of-millions-of-title-insurance-records/) (Krebs, 2019: ~885M documents, sequential IDs); [SEC 2021-102](https://www.sec.gov/newsroom/press-releases/2021-102) (SEC, 2021) · dossier: security-hardening T15-F15

### SE-08 — Bind request bodies through allowlists and return only the fields needed
- **Rule:** Report handlers that bind request bodies straight into entities or models, and responses that serialize whole models. The fix is an explicit allowlist or DTO (Rails strong params, Laravel `$fillable`, Spring `setAllowedFields` or DTOs, Django explicit fields, `_.pick`) plus a response that carries only the fields the client needs. Both change the request/response contract, so the owner decides.
- **Detect:** Run `rg -n '\.(create|update|insert|build|new)\(\s*(req|request)\.(body|params|json)|Object\.assign\([^,]+,\s*req\.body|\{\s*\.\.\.req\.body|\$guarded\s*=\s*\[\s*\]|permit!'`. For whole-model responses, look for `res.json(user)` and `fields = '__all__'`.
- **Not when:** Allowlisting breaks clients that currently set extra fields. Internal admin tools that bind all fields are acceptable only behind strong authorization (SE-07).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [ASVS 5.0.0 V15](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x24-V15-Secure-Coding-and-Architecture.md) (OWASP, 2025: 15.3.1 L1, 15.3.3 L2); [Mass Assignment Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Mass_Assignment_Cheat_Sheet.html) (OWASP) · dossier: security-hardening T15-F16

### SE-09 — Block prototype pollution when JS/TS code merges user-controlled objects
- **Rule:** Never recursively merge or set user-controlled objects without rejecting `__proto__`, `constructor` and `prototype`. Use `Map`/`Set` or `Object.create(null)` for data keyed by user input.
- **Detect:** Run `rg -n '_\.(merge|defaultsDeep|set)\(|deepmerge\('` and look for hand-written recursive merges over request data. Use ESLint framework plugins where the project configures them.
- **Not when:** Freezing prototypes can break libraries, and `--disable-proto=delete` is only a defense-in-depth measure. Neither replaces the key check.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [ASVS 5.0.0 V15](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x24-V15-Secure-Coding-and-Architecture.md) (OWASP, 2025: 15.3.6 L2); [Prototype Pollution Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Prototype_Pollution_Prevention_Cheat_Sheet.html) (OWASP) · dossier: security-hardening T15-F16

### SE-10 — Make security-relevant failure paths fail closed
- **Rule:** In authentication, authorization, validation, payment and crypto code, an exception must lead to deny, to rollback of every part of the transaction, or to an error, never to allow or continue. Return generic errors to clients with no stack traces, SQL, file paths or tokens. Keep a last-resort handler that logs unhandled exceptions on the server, and keep debug modes off in production.
- **Detect:** Swallowing handlers: `rg -n 'catch\s*(\([^)]*\))?\s*\{\s*\}|except(\s+\w+)?\s*:\s*pass|except\s*:\s*$|rescue\s*=>\s*\w+\s*$|_ = err'`; in auth, validation or payment code, read each catch for `return true`, `next()` or `allow`. Leaks: `rg -n '(res\.(send|json)|return|Response)\(.*(err\.stack|traceback|e\.message|exception)'`. Debug flags: `rg -n 'DEBUG\s*=\s*True|app\.run\(.*debug\s*=\s*True|app\.debug\s*=\s*true|showStackError|display_errors'`. Confirm a global handler exists (Express error middleware, `process.on('unhandledRejection')`, Django or Flask handlers, Spring `@ControllerAdvice`). Linters: ESLint `no-empty`, `bare-except`.
- **Not when:** Components that fail open on purpose for availability (feature flags, rate limiters, optional telemetry) are fine when documented, and flipping them can cause outages. Flipping a fail-open path to fail-closed is T1 only when the code, its docs or a sibling fix promise the closed behaviour (for example a check whose name, docstring or docs say it denies); any other flip is T2, and its warn-first step is proposed in its report entry, never applied (prioritization Tier table rows 19 and 21; PC-14). Generic client errors need correlation IDs in the logs. The last-resort handler is an ASVS L3 requirement.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [OWASP Top 10:2025 A10](https://top10.owasp.org/2025/A10_2025-Mishandling_of_Exceptional_Conditions/) (OWASP, 2025: 24 CWEs, "also known as failing closed"); [ASVS 5.0.0 V16](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md) (OWASP, 2025: 16.5.1, 16.5.3 L2; 16.5.4 L3); [ASVS 5.0.0 V13](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x22-V13-Configuration.md) (OWASP, 2025: 13.4.2 L2) · dossier: security-hardening T15-F17; eval-v2-calibration E02-F03

### SE-11 — Generate secrets with a CSPRNG and compare them in constant time
- **Rule:** Tokens, reset and invite codes, session IDs, OTPs, nonces and keys come from a CSPRNG with at least 128 bits of entropy: Python `secrets`, Java `SecureRandom`, Node `crypto.randomBytes(16+)`. Never use `Math.random`/`random`, and do not use UUIDs as secret tokens. Compare MACs, signatures and tokens in constant time: `hmac.compare_digest`, `crypto.timingSafeEqual`, `MessageDigest.isEqual`.
- **Detect:** Look for `rg -n 'Math\.random\(|random\.(random|randint|choice|getrandbits)\(|\brand\(\)|mt_rand\(|new Random\('` near token, reset, invite, session, OTP or key code. For timing, run `rg -n '(token|signature|hmac|digest|secret)\s*(===?|!==?)\s*'`. Also run Bandit B311.
- **Not when:** A non-crypto RNG for UI shuffles or cache keys is fine, and these hits are frequent false positives. OWASP's Cryptographic Storage sheet lists `crypto.randomUUID()` as secure, but ASVS 11.5.1 says UUIDs do not meet its 128-bit rule. Accept UUIDs as identifiers, not as secrets.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** high · **Grade:** A
- **Source:** [ASVS 5.0.0 V11](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x20-V11-Cryptography.md) (OWASP, 2025: 11.5.1 L2, 11.2.4 L3); [Cryptographic Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) (OWASP); [Best Practices Badge criteria](https://www.bestpractices.dev/en/criteria/0) (OpenSSF: crypto_random); [Bandit blacklist calls](https://bandit.readthedocs.io/en/latest/blacklists/blacklist_calls.html) (PyCQA) · dossier: security-hardening T15-F19

### SE-12 — Report weak password storage and weak algorithms together with a migration path
- **Rule:** Report password storage that does not follow OWASP's order of preference: Argon2id (m=19 MiB, t=2, p=1); else scrypt (N=2^17, r=8, p=1); for legacy systems, bcrypt with a work factor of at least 10 and its 72-byte limit; PBKDF2-HMAC-SHA256 with at least 600,000 iterations when FIPS-140 is required. Also report ECB mode, MD5 or SHA-1 used for security, and homemade crypto; prefer GCM/CCM and Curve25519. Changing a stored hash or cipher is a data migration, so hand it to the owner with OWASP's rehash-on-login or hash-layering path.
- **Detect:** Run `rg -n -i 'md5|sha1\b|sha-1|DES\b|RC4|AES/ECB|MODE_ECB|createCipher\('`, then `rg -n -i 'hash.*password|password.*hash'` and check the algorithm and parameters. Also run Bandit B324 and B303 and the Semgrep and CodeQL crypto queries.
- **Not when:** MD5 or SHA-1 used for cache keys or corruption checksums is fine. Stronger KDF parameters add login latency and server cost.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [ASVS 5.0.0 V11](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x20-V11-Cryptography.md) (OWASP, 2025: 11.3.1 L1, 11.4.2 L2); [Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) (OWASP); [Cryptographic Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) (OWASP) · dossier: security-hardening T15-F19

### SE-13 — Validate self-contained tokens (JWT/JWS/PASETO) completely
- **Rule:** Verify the signature or MAC before reading any claim, and pin an algorithm allowlist that excludes `none`. Take keys only from pre-configured sources, and allowlist or ignore `jku`, `x5u` and `jwk`. Enforce `exp`/`nbf`, and check `aud` and the token type or purpose.
- **Detect:** Run `rg -n "jwt\.decode\(|verify_signature.?\s*:\s*False|verify\s*=\s*False|algorithms\s*=\s*None|ignoreExpiration\s*:\s*true|ignoreNotBefore|alg.*none"`. In Node `jsonwebtoken`, `jwt.decode()` does not verify the signature. Check every verify call for an explicit `algorithms=[...]` and an audience or issuer.
- **Not when:** Strict `aud`/`exp` checks can reject tokens that are accepted today (clock skew, issuers with several audiences), so allow a small leeway and monitor the rollout. Some libraries already enforce these checks by default; read the defaults of the installed version before reporting.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [ASVS 5.0.0 V9](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x18-V9-Self-contained-Tokens.md) (OWASP, 2025: 9.1.1-9.1.3, 9.2.1 L1; 9.2.2-9.2.3 L2); [node-jsonwebtoken README](https://github.com/auth0/node-jsonwebtoken) (auth0) · dossier: security-hardening T15-F20

### SE-14 — Give user-influenced outbound URLs a destination policy (SSRF)
- **Rule:** Where the server fetches a URL that user input influences, report the destination policy it needs: an allowlist of destinations (deny-lists are bypass-prone), or at minimum blocking private, loopback and metadata ranges (169.254.169.254) after DNS resolution. Automatic redirects should be off, and the URL should be built from validated parts. Report disabled TLS verification in the same sweep; the allowed destinations are the owner's decision.
- **Detect:** Outbound calls: `rg -n '(requests|httpx)\.(get|post|put|request)\(|fetch\(|axios(\.\w+)?\(|http\.Get\(|urlopen\(|HttpClient|RestTemplate|WebClient'`; trace whether any part of the URL is user-controlled. TLS: `rg -n 'verify\s*=\s*False|rejectUnauthorized\s*:\s*false|InsecureSkipVerify\s*:\s*true|NODE_TLS_REJECT_UNAUTHORIZED'`. Also run Bandit B501 and B310.
- **Not when:** Webhook and URL-preview features cannot use strict allowlists (OWASP "Case 2"). Network egress controls outside the codebase may be the better fix.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [SSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) (OWASP); [ASVS 5.0.0 V15](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x24-V15-Secure-Coding-and-Architecture.md) (OWASP, 2025: 15.3.2 L2); [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html) (MITRE/CISA, 2025: CWE-918 #22); [Bandit plugins](https://bandit.readthedocs.io/en/latest/plugins/index.html) (PyCQA) · dossier: security-hardening T15-F21

### SE-15 — Put a timeout on every network call and a limit on every user-driven input
- **Rule:** Give every outbound network call a timeout. Give every request body, upload, query result and loop over user input an explicit size or rate limit, including pagination caps and rate limits on auth endpoints. Propose values derived from observed latencies and volumes rather than guessed ones: for a timeout, pick an acceptable false-timeout rate and take the matching latency percentile (p99.9 for 0.1%), as ER-21 does. A timeout with no latency data takes ER-21's fixed internal default: generous, documented where it is set, owner-tunable, and never a new parameter of an exported signature (eval-v1-calibration E01-F05; pilot-auto-calibration A01-F10); a size or rate limit with no volume data is an owner decision.
- **Detect:** Check each hit of the SE-14 outbound-call sweep for a timeout argument, and run Bandit B113 (request_without_timeout). In the framework config, look for body and upload size limits, pagination caps and auth-endpoint rate limits. When the errors-resilience lens also runs, the timeout half of a hit is ER-21's; merge the two.
- **Not when:** Limits that are too tight cause spurious failures. A p99.9 close to p50 needs padding, and clients with large network latency need more (error-handling T14-F11).
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html) (MITRE/CISA, 2025: CWE-770 #25); [ASVS 5.0.0 V15](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x24-V15-Secure-Coding-and-Architecture.md) (OWASP, 2025: 15.2.2 L2); [Bandit plugins](https://bandit.readthedocs.io/en/latest/plugins/index.html) (PyCQA); [Timeouts, retries, and backoff with jitter](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf) (Brooker, AWS Builders' Library, 2019: "we choose an acceptable rate of false timeouts (such as 0.1%)… (p99.9 in this example)") · dossier: security-hardening T15-F21; error-handling T14-F11; eval-v1-calibration E01-F05; pilot-auto-calibration A01-F10

### SE-16 — Keep secrets and sensitive data out of logs, neutralize CR/LF, and log auth failures
- **Rule:** Remove, mask or hash these values in log calls: passwords, session IDs, access or refresh tokens, API keys, connection strings, full Authorization or Cookie headers, payment data and most PII. Do not log whole request, response or env objects, and encode or strip CR/LF in user-controlled log fields. Log authentication and authorization failures.
- **Detect:** Sensitive values: `rg -n -i '(log|logger|console|print|warn|error|info|debug)[\w.]*\(.*(password|passwd|secret|token|api[_-]?key|authorization|cookie|session|credential|connection[_-]?string|card)'`. Whole objects: `rg -n '(log|logger|console)\.[a-z]+\((req|request)(\.headers)?\)|process\.env\)|os\.environ\)'`. Check the logger's redaction config (pino `redact`, structlog processors, logback masking), and check that the auth path logs failures.
- **Not when:** Over-redaction weakens incident investigation; hash identifiers to keep them correlatable. Downstream alerts may depend on the fields you remove. A logged failed-login username can contain a mistyped password.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** A
- **Source:** [Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) (OWASP); [ASVS 5.0.0 V16](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md) (OWASP, 2025: 16.2.5, 16.3.1, 16.3.2, 16.4.1 L2); [CWE-532](https://cwe.mitre.org/data/definitions/532.html) (MITRE) · dossier: security-hardening T15-F18

### SE-17 — Scan the tree, the full history and built artifacts for secrets
- **Rule:** Scan the working tree, the entire git history (all branches and tags) and any built artifact or image with a high-recall pattern scanner. Use a verifying scanner only to prioritise, never to dismiss. Treat unverified hits in non-test code as real until a human confirms otherwise. A placeholder that production code uses as the fallback for a missing credential (an env read with a literal default) is also a separate T1 behavioural candidate under OP-12 (`lens: "ops-config"`, fix risk medium): remove the fallback, so a missing credential either fails with an error naming the key or, where the call works without one, is not sent. Neither that fix nor its tier depends on whether the provider accepts the value, so it needs no live call. Deleting the literal itself follows the PC-21 placeholder exception (eval-v2-calibration E02-F04): inside that approved T1 item, the literal may be deleted in the same commit that removes its last use only when it is verifiably a placeholder, meaning it carries a test-shaped marker (`test`, `fixture`, `example`, `dummy`, `changeme`, `xxx`, `not_a_real`), a secret scanner's verified mode does not match it, and the user confirms the call in the item's approval, which shows the file:line, the marker and the scanner result, never the value. The verified-mode scan is the exception's only live call and runs only with the user's go-ahead (Detect) and network allowed (SKILL.md Phase 0 step 4); without it the literal is not verifiably a placeholder. A verified or unknown status vetoes the exception, and a non-match never clears a value without a marker. Anything that could be a live credential stays under PC-21: its line is never touched, a fallback fix that needs that line is reported instead of applied, and the SE-18 rotation item goes to the human.
- **Detect:** History: `gitleaks git -v --report-path .harden/tools/gitleaks.json`; tree: `gitleaks dir -v .`; later runs add `--baseline-path` so only new hits show. Run `semgrep scan --config p/secrets`. Env files ever committed: `git log --all --full-history --oneline -- '*.env' '**/.env' '.env*'` and `git ls-files | grep -iE '(^|/)\.env($|\.)' | grep -v example`. `trufflehog git <repo-url> --results=verified` tests each credential against its provider's API, so run it only with the user's go-ahead, and review the unverified and unknown results as well.
- **Not when:** Propose test fixtures to the owner for a baseline or an inline `#gitleaks:allow`, never a disabled rule. Precision is low: Gitleaks had 46% precision and 88% recall (ESEM 2023, 9 tools on one benchmark), and 99.7% of 1,100 hand-labelled TruffleHog detections on Docker Hub images were non-credentials (2026 preprint). Verified-only triage missed 46% of critical secrets (GitGuardian 2026, vendor). Gitleaks now receives security patches only and its author ships Betterleaks, so pin the version and name the tool you used.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Secret Detection Tools compared](https://arxiv.org/abs/2307.00714) (Basak et al., ESEM 2023); [State of Secrets Sprawl 2026](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2026/) (GitGuardian, 2026); [gitleaks README](https://github.com/gitleaks/gitleaks) (gitleaks); [trufflehog README](https://github.com/trufflesecurity/trufflehog) (Truffle Security); [Highest-Exposure Docker Hub Images](https://arxiv.org/abs/2608.02669) (Kapelinski et al., 2026); [ASVS 5.0.0 V13](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x22-V13-Configuration.md) (OWASP, 2025: 13.3.1 L2) · dossier: security-hardening T15-F02; eval-v1-calibration E01-F07; eval-v2-calibration E02-F04

### SE-18 — A real leaked secret is fixed by rotation, and a human owns it
- **Rule:** For each confirmed secret, emit a rotation item for the owner: revoke and rotate, then move the value to a secret store or runtime injection, then optionally rewrite history, and only with explicit approval. Deleting the line in a new commit is never the fix. The pass never rotates, rewrites or force-pushes.
- **Detect:** For each hit, record the file, the commit, whether it is still in HEAD, and whether the repo is or was public, forked or mirrored. The human checks liveness with trufflehog's verified status or the provider console. Include CI logs, because the tj-actions exfiltration went through workflow logs.
- **Not when:** Test or dummy keys are allowlisted, not rotated; a verified placeholder that production code falls back to may be deleted with its last use under the PC-21 placeholder exception (SE-17). For a private repo whose key is already rotated, rewriting history may be unnecessary and harmful (broken SHAs and PR links). Leaked credentials stay live: more than 64% of credentials valid in 2022 were still valid in January 2026 (GitGuardian 2026, vendor).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** A
- **Source:** [Removing sensitive data from a repository](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository) (GitHub Docs); [Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) (OWASP); [State of Secrets Sprawl 2026](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2026/) (GitGuardian, 2026); [tj-actions compromise](https://www.cisa.gov/news-events/alerts/2025/03/18/supply-chain-compromise-third-party-tj-actionschanged-files-cve-2025-30066-and-reviewdogaction) (CISA, 2025) · dossier: security-hardening T15-F03; eval-v2-calibration E02-F04

### SE-19 — Keep secrets out of build definitions and committed config
- **Rule:** Report credentials in Dockerfile `ENV`/`ARG` or image layers, compose files, CI workflow YAML, IaC and committed `.env` files. The target is BuildKit secret mounts (`RUN --mount=type=secret,...`) at build time, runtime injection or a secret manager at run time, and only a `.env.example` with empty values in git. A committed real secret also triggers SE-18.
- **Detect:** Dockerfiles: `grep -nEi '^\s*(ENV|ARG)\s+[A-Z0-9_]*(PASS|SECRET|TOKEN|KEY|CRED)' <dockerfiles>`. An existing image: `docker history --no-trunc <image>`. Committed env files: `git ls-files | grep -iE '(^|/)\.env($|\.)' | grep -v '\.example$'`. Workflows: zizmor `hardcoded-container-credentials` and `unredacted-secrets`. Compose and IaC files: `gitleaks dir`.
- **Not when:** Runtime environment variables remain the norm on most PaaS, and OWASP flags a leakage risk, not a ban. For a solo project, an uncommitted `.env` loaded at runtime can be an acceptable trade-off. Non-secret ARGs are fine.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Build secrets](https://docs.docker.com/build/building/secrets/) (Docker Docs); [Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) (OWASP); [State of Secrets Sprawl 2025](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2025/) (GitGuardian, 2025, vendor: AWS IAM keys in 8% of private repos); [zizmor audit rules](https://docs.zizmor.sh/audits/) (zizmor) · dossier: security-hardening T15-F04

### SE-20 — Run SCA with more than one tool, then triage: shipped, reachable, exploitable
- **Rule:** Scan every lockfile and manifest with OSV-Scanner plus the ecosystem's native auditor. Triage each advisory in order: is the package in the production artifact, is the vulnerable symbol reachable (call analysis where it exists, else a grep for the affected API the advisory names), and is it exploitable. Order the fix queue by that triage, report non-applicable advisories to the owner as proposed ignore-file entries (ID, reason, review date), and never silence a scanner.
- **Detect:** Run `osv-scanner scan source -r .` (Go call analysis is on by default). Never add `--call-analysis=all` or `--call-analysis=rust` in this pass: Rust call analysis executes dependency `build.rs` ("Running call analysis for Rust will execute build scripts", dependency-hygiene T16-F08), so run it only inside a sandbox the user approves; native Windows has none. Native auditors (commands in the language file): Go govulncheck; Python pip-audit; Rust cargo audit and cargo deny; npm `npm audit --omit=dev --audit-level=high`, then a full `npm audit` to see dev-tool exposure separately. Include transitive dependencies: across about 1,000 OSS projects, for most programming languages studied, vulnerable dependencies were mostly transitive (2025 preprint).
- **Not when:** Reachability never closes an advisory on its own when the project ships binaries to customers or faces a compliance deadline. The OpenSSF badge (no unpatched medium+ advisory public for more than 60 days) and ASVS 15.2.1 do not mention reachability, so that call belongs to the owner. Known CVEs in build tooling rarely affect the shipped app, but dev dependencies still run code on developer and CI machines (SE-23); keep the two threats apart.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [SCA Tools compared](https://arxiv.org/abs/2108.12078) (Imtiaz et al., ESEM 2021: one app, 9 tools, 17-332 Maven and 32-239 npm vulnerable dependencies); [govulncheck tutorial](https://go.dev/doc/tutorial/govulncheck) (Go team); [OSV-Scanner source scanning](https://google.github.io/osv-scanner/usage/scan-source) (Google); [2024 Dependency Management Report](https://www.endorlabs.com/lp/2024-dependency-management-report) (Endor Labs, 2024, vendor: under 9.5% exploitable at function level); [Best Practices Badge criteria](https://www.bestpractices.dev/en/criteria/0) (OpenSSF); [Scorecard checks](https://github.com/ossf/scorecard/blob/main/docs/checks.md) (OpenSSF); [Vulnerable Dependencies in OSS](https://arxiv.org/abs/2512.03868) (Kumar et al., 2025) · dossier: security-hardening T15-F05; dependency-hygiene T16-F08

### SE-21 — Remediate with the smallest bump, one dependency per commit, and escalate majors
- **Rule:** Fix a vulnerable dependency with the smallest version bump that clears the advisory. Commit it under DP-10's rules: one dependency (or one coherent family) per commit, touching only the manifest, the lockfile and minimal adaptation code, with the full build, tests, production build and start passing before and after. Never run bulk or forced remediation such as `npm audit fix --force`. When only a major version clears the advisory, report it as T2 with the breaking changes listed. The bump runs only after the item is approved and the orchestrator records `run_state.py allow-config-edit <manifest or lockfile> --reason <finding id>` (SKILL.md invariant 2); without that record the hook and diff_guard refuse the edit.
- **Detect:** Diff the lockfile and classify each changed package as patch, minor or major. Flag any major bump, and any changed package that the advisory did not name.
- **Not when:** No breakage rate predicts a given project. Endor Labs (vendor) found potentially breaking changes in 95% of 1,250 remediation updates from 15 problem libraries. Ochoa et al. (EMSE 2022, 119,879 Maven upgrades) found 7.9% of 293,817 clients affected. The project's tests decide, so a bump is behavioural even when it clears only an advisory.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** B
- **Source:** [npm-audit](https://docs.npmjs.com/cli/v11/commands/npm-audit) (npm Docs: `--force` allows "SemVer-major changes"); [Breaking Bad?](https://arxiv.org/abs/2110.07889) (Ochoa et al., EMSE 2022, DOI 10.1007/s10664-021-10052-y); [2024 Dependency Management Report](https://www.endorlabs.com/lp/2024-dependency-management-report) (Endor Labs, 2024) · dossier: security-hardening T15-F06; dependency-hygiene T16-F16

### SE-22 — Commit lockfiles and install from them in frozen mode
- **Rule:** Report an application with no committed lockfile. Report CI or deploy steps that install without frozen mode (`npm ci`, pnpm from the committed `pnpm-lock.yaml`, pip with hashes or `pylock.toml`, `go.sum`, `Cargo.lock`). Report a lockfile with no update bot (Dependabot or Renovate), because a lockfile that never updates freezes vulnerabilities in place.

### SE-23 — Turn off dependency install scripts by default
- **Rule:** Disable dependency lifecycle scripts by default, and allowlist only the packages that need builds. pnpm 10+ disables dependency postinstall scripts, with the allowlist in `allowBuilds` (`onlyBuiltDependencies` in older configs); for npm, `ignore-scripts=true` in `.npmrc` covers preinstall, install and postinstall. Blocking postinstall alone is not enough, because the November 2025 Shai-Hulud variant moved to pre-install.
- **Detect:** Run `grep -n ignore-scripts .npmrc`. Check `pnpm --version` (10+) and the `allowBuilds`/`onlyBuiltDependencies`, `blockExoticSubdeps` and `trustPolicy` settings. Give Rust `build.rs` in dependencies the same scrutiny. For Python, `--only-binary=:all:` avoids source builds.
- **Not when:** Packages that compile native addons break until they are allowlisted. Go does not run code at build time by design.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** B
- **Source:** [OWASP Top 10:2025 A03](https://top10.owasp.org/2025/A03_2025-Software_Supply_Chain_Failures/) (OWASP, 2025: Shai-Hulud reached over 500 package versions); [Supply chain security](https://pnpm.io/supply-chain-security) (pnpm); [Shai-Hulud Worm](https://unit42.paloaltonetworks.com/npm-supply-chain-attack/) (Unit 42, 2025); [HN: Shai-Hulud Returns](https://news.ycombinator.com/item?id=46032539) (Hacker News, 2025) · dossier: security-hardening T15-F08; frontend-react-hygiene practitioner voice; lang-solidity-go T24-F22

### SE-24 — Report release-age cooldowns for version updates instead of setting them
- **Rule:** Report whether version updates wait for a release-age cooldown (pnpm `minimumReleaseAge`, Dependabot `cooldown`, pip `--uploaded-prior-to P<n>D`), and confirm that security updates bypass it, as Dependabot does and as the OpenSSF wording ("components without known vulnerabilities") implies. The length is unresolved: propose a value and let the owner choose. Do not auto-set it.
- **Detect:** Run `grep -n -A3 cooldown .github/dependabot.yml` and check pnpm `minimumReleaseAge`. For Python, run `grep -rn 'uploaded-prior-to\|exclude-newer' pyproject.toml pip.conf uv.toml`. Also run zizmor `dependabot-cooldown`.
- **Not when:** The defaults differ. pnpm: 1 day by default since v11 (0 before; `minimumReleaseAge` added in v10.16.0). Dependabot and the OpenSSF Concise Guide use about 3 days (the guide's item was added 2026-09-19). Woodruff argues for 7 days from a 10-incident table in which 8 of 10 malicious windows were under a week. Critics say cooldowns free-ride on early adopters and delay real fixes.

### SE-25 — Verify every direct dependency is real, intended and from the expected registry
- **Rule:** For each direct dependency, confirm three things: it exists on the official registry, its repository link and maintainers match the project the code expects, and its publish history is plausible. Flag names one edit away from a popular package, and internal names that could resolve from a public index; this matters most in AI-assisted code. Replacing a dependency is the owner's call.

- **Not when:** Legitimate new packages exist. Download counts can be gamed: the empty `huggingface-cli` package, a name models had hallucinated, got more than 30k downloads in three months (Lasso, vendor). No large-scale in-the-wild slopsquatting numbers were found.

- **Source:** [We Have a Package for You!](https://arxiv.org/abs/2406.10279) (Spracklen et al., USENIX Security 2025: 16 LLMs, 576k samples, hallucinated packages at least 5.2% for commercial and 21.7% for open-source models); [AI package hallucinations](https://www.lasso.security/blog/ai-package-hallucinations) (Lasso, 2024); [ASVS 5.0.0 V15](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x24-V15-Secure-Coding-and-Architecture.md) (OWASP, 2025: 15.2.4 L3); [HN: Dependency Confusion](https://news.ycombinator.com/item?id=26087868) (Hacker News, 2021) · dossier: security-hardening T15-F09

### SE-26 — Remove unused dependencies and move build-only tools to dev dependencies
- **Rule:** Remove dependencies the shipped code does not use, and move build-only tools to dev dependencies. Confirm each removal with a clean install, a full build, tests and a runtime smoke run. The edit runs only after the item is approved and the orchestrator records `run_state.py allow-config-edit <manifest or lockfile> --reason <finding id>` (SKILL.md invariant 2); without that record the hook and diff_guard refuse it. DP-01 and DP-03 give the removal and move proofs.
- **Detect:** JS/TS: knip; review its output and never run a blind `--fix`. Python: deptry (DEP002 unused; DEP004 dev dependency imported). Rust: `cargo +nightly udeps` and `cargo deny check bans`. Maven: DepClean. Also look for vendored or copied libraries.
- **Not when:** Dynamic loading, plugins, framework conventions, CLI tools called from scripts and peer dependencies all fool detectors. cargo-udeps needs nightly and misses some crates. Removing an optional runtime dependency can break a path that tests do not cover. The 75.1% bloat figure is Maven-only (9,639 artifacts, EMSE 2021).
- **Tier:** T1 · **Class:** structural · **Fix risk:** medium · **Grade:** B
- **Source:** [Bloated Dependencies in Maven](https://arxiv.org/abs/2001.07808) (Soto-Valero et al., EMSE 2021); [OWASP Top 10:2025 A03](https://top10.owasp.org/2025/A03_2025-Software_Supply_Chain_Failures/) (OWASP, 2025); [Knip: Handling Issues](https://knip.dev/guides/handling-issues) (knip.dev); [deptry](https://deptry.com/) (deptry); [cargo-udeps](https://github.com/est31/cargo-udeps) (est31) · dossier: security-hardening T15-F10

### SE-27 — Harden CI workflows
- **Rule:** Report third-party actions not pinned to a full commit SHA with a version comment, and a default token that is not read-only (top-level `permissions: contents: read`, write granted per job). Report attacker-controlled context such as `${{ github.event.* }}` interpolated straight into `run:` instead of passed through `env:`, and `pull_request_target`/`workflow_run` jobs that check out and run PR code. Local gates cannot prove workflow edits, so these stay proposals.
- **Detect:** Run `zizmor .github/workflows/` with the audits `unpinned-uses` (applies when zizmor is v1.20.0+, which requires hash pins for all actions by default), `excessive-permissions`, `template-injection`, `dangerous-triggers`, `artipacked`, `secrets-inherit` and `cache-poisoning`. Tag or branch pins: `grep -rnE 'uses: [^@]+@(v?[0-9]+(\.[0-9]+)*|main|master)\s*$' .github/workflows/`. Risky triggers: `grep -rn 'pull_request_target\|workflow_run' .github/workflows/`. Context in scripts: `grep -rnE 'run:.*\$\{\{\s*github\.event' .github/workflows/`.
- **Not when:** SHA pins are not transitive, because composite actions can call unpinned actions. Bots that auto-update pins partly bring the risk back, and pins need an update process. Reduced permissions break jobs that legitimately write, such as releases and PR comments.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** A
- **Source:** [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use) (GitHub Docs); [tj-actions compromise](https://www.cisa.gov/news-events/alerts/2025/03/18/supply-chain-compromise-third-party-tj-actionschanged-files-cve-2025-30066-and-reviewdogaction) (CISA, 2025); [Scorecard checks](https://github.com/ossf/scorecard/blob/main/docs/checks.md) (OpenSSF); [zizmor audit rules](https://docs.zizmor.sh/audits/) (zizmor); [HN: arianvanp](https://news.ycombinator.com/item?id=43372045) (Hacker News, 2025); [HN: frenchtoast8](https://news.ycombinator.com/item?id=43369373) (Hacker News, 2025) · dossier: security-hardening T15-F11

### SE-28 — Check production packaging and deploy configuration
- **Rule:** Report debug modes left on in production, served VCS metadata (`.git`), source maps or debug endpoints, and committed binaries that cannot be reviewed. Report containers running as root, unpinned base images, unscanned images, and deployments that ship more than the app needs.
- **Detect:** Committed binaries: `git ls-files | grep -Ei '\.(exe|dll|so|dylib|jar|war|class|pyc|whl|bin|o|a)$'` or Scorecard `Binary-Artifacts`. Dockerfiles without a `USER` directive: `grep -L '^USER ' <dockerfiles>`. Unpinned base images: `grep -nE '^FROM [^@]+(:latest)?\s*$'`. Check that `.dockerignore` excludes `.git`, `.env` and tests. Run Trivy or Grype on an image that is already built.
- **Not when:** Committed test-fixture binaries are legitimate; document them. Public source maps are sometimes deliberate. Running as non-root can break file permissions or low-port binding. OS-package CVE counts raise the same reachability question as SE-20: in the 52,895 highest-exposure Docker Hub repositories, 96.3% of images carried a known package vulnerability (2026 preprint).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [ASVS 5.0.0 V13](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x22-V13-Configuration.md) (OWASP, 2025: 13.4.1 L1, 13.4.2 L2); [Scorecard checks](https://github.com/ossf/scorecard/blob/main/docs/checks.md) (OpenSSF); [Docker Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html) (OWASP); [Highest-Exposure Docker Hub Images](https://arxiv.org/abs/2608.02669) (Kapelinski et al., 2026) · dossier: security-hardening T15-F23

## False-positive exclusions

- Queries, commands and file paths built only from constants or server-side configuration (SE-03, SE-05).
- Table, column or sort identifiers already checked against a hard-coded allowlist (SE-03).
- Developer-authored static HTML passed through an escape hatch (SE-04).
- MD5, SHA-1 or non-crypto RNGs used for cache keys, corruption checksums or UI shuffles (SE-11, SE-12).
- Native deserialization of data that only the same process writes and reads inside one trust boundary: downgrade it to low rather than dropping it (SE-06).
- Intentional fail-open behaviour that is documented: feature flags, rate limiters, optional telemetry (SE-10).
- JWT checks the library already enforces by default at the installed version (SE-13).
- Webhook and URL-preview fetches, where a strict allowlist is impossible: report the residual risk instead (SE-14).
- Test fixtures and dummy keys: propose them for the scanner baseline, never rotate them (SE-17, SE-18). A dummy key that production code falls back to is still an OP-12 fix candidate (SE-17); its literal is deleted only under the PC-21 placeholder exception.
- Non-secret build ARGs (SE-19).
- Advisories on packages absent from the production artifact, for the shipped-app threat only. Install-time malware in dev dependencies stays in scope (SE-20, SE-23).
- Committed binaries that are documented test fixtures, and source maps that are deliberately public (SE-28).
- Before dismissing a SAST alert, name which of the three documented causes applies: missed sanitization, benign context or missing trust-boundary modeling (SE-02).
- None of these closes a finding on its own: a random GUID in place of an ownership check (SE-07), a zero-alert scan (SE-02), or a verifier reporting "unverified" (SE-17).

## Evidence limits

- This lens is not a pentest. It finds defects visible in source, history and config, and it cannot confirm exploitability at runtime.
- SAST recall figures are narrow. The ISSTA 2024 data cover C/C++ only. The CodeQL longitudinal and false-positive studies (2026), the Docker Hub study (2026) and the vulnerable-dependencies study (2025) are unreviewed preprints.
- Vendor sources: Veracode, GitGuardian, Endor Labs and Lasso. Treat their percentages as directional.
- The placeholder test in SE-17 (a test-shaped marker plus no verified-mode match) comes from the skill's own v2 evaluation (eval-v2-calibration E02-F04, grade C), where nine runs handled one seeded placeholder credential in four ways; the marker list is a heuristic, so a value that fails either check stays under PC-21.
- Free function-level SCA reachability was verified only for Go (govulncheck, OSV-Scanner) and, experimentally, for Rust, where it executes dependency `build.rs` and so stays outside this pass unless the user provides a sandbox. For Rust without it, and for JS/TS, Python and Java, the fallback is a manual grep for the advisory's affected API.
- The AI-code evidence is mixed: the CCS 2023 study used a 2022 model, and the GitGuardian comparison is correlational. The balance between LLM review and SAST is unsettled.
- Cooldown lengths rest on one 10-incident practitioner compilation. The pnpm default (1 day since v11, 0 before; `minimumReleaseAge` added in v10.16.0) comes from pnpm's settings docs (dependency-hygiene T16-F10).
- The dossier did not re-verify the pip-audit, cargo audit and `cargo audit fix` flags. Confirm them against the tool's help at the pinned version.
- Remediation evidence is thin in places. No sourced remediation pattern exists for path traversal or unrestricted upload (SE-05 is report-only), and the dependency-bloat figures are Maven-only.
- Practitioner voice comes mostly from Hacker News and engineering blogs. Reddit, Lobsters and Security StackExchange were not reachable during research.
