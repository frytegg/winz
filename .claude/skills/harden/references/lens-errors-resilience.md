# Lens: Errors and resilience

> Finds error handlers that hide failures, error paths that report success, remote calls without timeouts or with unsafe retries, panics and exits on production paths, and checks that a build can strip or that sit at the wrong trust boundary.
> Read when: in-scope code catches or returns errors, calls a network service, database or subprocess, retries, loads external or self-generated data, or uses assertions.

## Rules

### ER-01 — Empty and log-only handlers are defects until justified
- **Rule:** Make every catch, except or `if err != nil` handler recover with consistent state, propagate, or translate the error into one that fits its context. Treat an empty, `pass`-only or log-only handler as a defect unless continuing is provably correct and a comment says why. Replacing `pass` with a log call (Ruff S110's suggested fix) does not resolve it: Yuan et al. count a log-only handler as ignoring the error.
- **Detect:** ESLint `no-empty` (skips any block holding a comment; `allowEmptyCatch` must stay off), Ruff `S110`/`S112`, Bandit `B110`/`B112`, PMD `EmptyCatchBlock`, SpotBugs `DE_MIGHT_IGNORE`/`DE_MIGHT_DROP`, clang-tidy `bugprone-empty-catch`, golangci-lint `errcheck`. Linters miss log-only handlers (Ruff `BLE001` exempts `exc_info` logging), so add ast-grep: `catch ($E) { $L.$M($$$) }` whose one statement is a logger or console call; a Python `except` body that is one `logger.*` or `print` call; Go `if err != nil { log.$M($$$) }` with no return. Per hit: does execution continue as if the operation succeeded (a later read of an unset variable, a half-mutated collection, a half-committed multi-step write)?
- **Not when:** a cleanup failure that cannot affect later behaviour (CERT ERR00-J-EX0), but never a close, flush or fsync error on a written file; an optional-feature probe whose comment says why ignoring is safe; a batch item skipped or quarantined while the rest proceeds (ER-14), which is resolved by recording each skip with the item and the error through a logger the code already uses, results unchanged, rather than by failing the batch (prioritization Fail-open findings, kind 1; eval-v3-calibration E03-F01). Yuan's checker skipped FileNotFound and shutdown, close and cleanup methods and still had 19% false positives, so confirm each hit by hand.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [Simple Testing Can Prevent Most Critical Failures](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-yuan.pdf) (Yuan et al., OSDI 2014: of 48 catastrophic failures among 198 user-reported failures in Cassandra, HBase, HDFS, MapReduce and Redis, 92% mishandled an explicitly signalled non-fatal error and 25% ignored it); [ERR00-J](https://cmu-sei.github.io/secure-coding-standards/sei-cert-oracle-coding-standard-for-java/rules/exceptional-behavior-err/err00-j) (SEI CERT, n.d.); [CWE-390](https://cwe.mitre.org/data/definitions/390.html) (MITRE, 2026); [Review of de Pádua & Shang, MSR 2018](https://neverworkintheory.org/2021/09/16/exception-handling-practices-and-post-release-defects.html) (Wilson, 2021; 3 Java/C# projects, Dummy Handler strongly related to post-release defects); [try-except-pass S110](https://docs.astral.sh/ruff/rules/try-except-pass/) (Astral) · dossier: error-handling T14-F01; assertions-defensive-checks G203-F15; eval-v3-calibration E03-F01

### ER-02 — Remove success-shaped fallbacks
- **Rule:** Replace a handler that returns a neutral value (`None`, `[]`, `{}`, `0`, `""`, `false`), a `.catch(() => null)`, an `.ok()` or `unwrap_or_default()` on an error that matters, or an `_`-discarded error with propagation, or with an assertion when the failure is impossible. Keep a fallback only as a documented degradation that emits a metric and has a test.
- **Detect:** Ruff `S110`/`S112`/`BLE001` plus a grep for `return None|[]|{}|0|""|False` inside handlers; ESLint `no-empty` plus a grep for comment-only catch blocks and `.catch(() => null|undefined|[]|{})`; golangci-lint `errcheck`, `nilerr`; Rust grep for `.ok()`, `unwrap_or_default()` and `let _ =` on fallible calls. Trace each caller: does it treat the neutral value as a real result?
- **Not when:** cached or degraded results, provider failover and best-effort cleanup at shutdown can be correct product behaviour. A fallback that the docs, help text, a docstring or a comment state as intended, with a reason or a promise, or that an option controls, is the owner's to remove (T2); its report entry proposes a signal for it. An undocumented fallback that presents a substituted value as a genuine result (defaults for an input the caller named, a placeholder number in a total, a source label the value did not earn, exit 0 after a failure) is surfaced through a channel the code already has, in one T1 commit and with no new flag, when no other reliance signal holds and, with external consumers or live data, only through the error the same function already raises or a named CLI input's documented exit (invariant 5; prioritization Fail-open findings, kind 2; pilot-auto-calibration A01-F09). An implicit optional input that is absent may keep its default, as `configparser.read()` ignores candidate files it cannot open while required files go through `read_file()`.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** high · **Grade:** A
- **Source:** [Simple Testing Can Prevent Most Critical Failures](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-yuan.pdf) (Yuan et al., OSDI 2014; 35% of the 48 catastrophic failures came from three trivial handler patterns); [The Power of 10](https://web.eecs.umich.edu/~imarkov/10rules.pdf) (Holzmann, 2006; ignore a return value only through an explicit `(void)` cast); [HN comment on agent fallbacks](https://news.ycombinator.com/item?id=48420230) (SubiculumCode, 2026; anecdote); [CWE-393](https://cwe.mitre.org/data/definitions/393.html) (MITRE, CWE 4.20: a return value "that does not indicate the true result of execution"); [PEP 20](https://peps.python.org/pep-0020/) (Peters, 2004: "Errors should never pass silently. Unless explicitly silenced."); [configparser](https://docs.python.org/3/library/configparser.html) (Python docs, current) · dossier: assertions-defensive-checks G203-F15; pilot-auto-calibration A01-F09; eval-v3-calibration E03-F01, E03-F02

### ER-03 — A clean lint does not clear TODO and "cannot happen" handlers
- **Rule:** Resolve every handler holding `TODO`, `FIXME`, `XXX`, `HACK`, "should never happen" or "can't happen": recover, propagate or translate, or leave a comment that says why ignoring is safe with no TODO left. Handle errors that "can never happen" defensively.
- **Detect:** ``rg -n -U --pcre2 'catch\s*(\([^)]*\))?\s*\{[^}]*?(TODO|FIXME|XXX|HACK|never happen|can.?t happen|impossible)'`` (JS/TS/Java/C#/C++); ``rg -n -U --pcre2 'if err != nil \{[^}]*?(TODO|FIXME|XXX)'`` (Go); the same keywords in Python `except` bodies. Linter defaults hide these: ESLint `no-empty` skips any commented block; clang-tidy `bugprone-empty-catch` skips `@TODO`/`@FIXME` by default (clear `IgnoreCatchWithKeywords` for the lens run only); PMD `EmptyCatchBlock` flags commented blocks by default but skips variables named `ignored` or `expected`.
- **Not when:** a comment that explains why the error is safe to ignore is legitimate (ESLint's stated reason for its exemption). The empirical base is one failure in one study.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** C
- **Source:** [Simple Testing Can Prevent Most Critical Failures](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-yuan.pdf) (Yuan et al., OSDI 2014; a TODO-plus-log handler took down a 4,000-node production cluster, 2% of 48 catastrophic failures); [no-empty](https://eslint.org/docs/latest/rules/no-empty) (ESLint); [bugprone-empty-catch](https://clang.llvm.org/extra/clang-tidy/checks/bugprone/empty-catch.html) (LLVM); [PMD error-prone rules](https://pmd.github.io/pmd/pmd_rules_java_errorprone.html) (PMD) · dossier: error-handling T14-F02

### ER-04 — Catch precise types; keep catch-alls at boundaries
- **Rule:** Replace `catch Exception/Throwable/SystemException`, bare `except:`, `except BaseException`, `catch (...)` and a JS `catch (e)` that swallows everything with the precise types the try body can raise. Keep one deliberate catch-all per process or request boundary that logs with the stack and then rethrows, returns a generic error or exits. Never combine an over-broad catch with exit or abort.
- **Detect:** Ruff `BLE001`, `E722`; .NET `CA1031`; PMD `AvoidCatchingGenericException` configured to include Throwable (applies to PMD 7.18.0+, where `AvoidCatchingThrowable` is deprecated); `rg -n 'catch\s*\(\s*(final\s+)?(Exception|Throwable|RuntimeException|SystemException)\b'`; `rg -n 'catch\s*\(\s*\.\.\.\s*\)'`. Highest priority is a broad catch that terminates: `rg -n -U --pcre2 'catch\s*\(\s*(Throwable|Exception)[^)]*\)\s*\{[^}]*(System\.exit|halt\(|abort\(|process\.exit|os\.Exit|sys\.exit)'`. In JS, check that the handler discriminates with `instanceof` or `code` and rethrows the rest.
- **Not when:** the catch-all is the boundary handler (ER-14); Ruff exempts re-raise and `exc_info` logging. In Python and JS callee exceptions are undocumented, so a narrowed catch must still cover every exception the body can raise (the CA1031 example says the same).
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [Simple Testing Can Prevent Most Critical Failures](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-yuan.pdf) (Yuan et al., OSDI 2014; 8% of the 48 catastrophic failures were aborts in over-broad catches, e.g. an HDFS `catch (Throwable)` that "brought down every datanode"); [CWE-396](https://cwe.mitre.org/data/definitions/396.html) (MITRE, 2026); [PEP 8](https://peps.python.org/pep-0008/) (PSF, 2025); [CA1031](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1031) (Microsoft, 2026); [Fail Fast](https://www.martinfowler.com/ieeeSoftware/failFast.pdf) (Shore, IEEE Software column, 2004) · dossier: error-handling T14-F03

### ER-05 — Do not catch programming errors in order to keep going
- **Rule:** Report handlers that catch bug-signalling exceptions (null dereference, index out of range, class cast, `TypeError`, `AttributeError`, `AssertionError`) and continue. The fix belongs at the cause or in a precondition, with the error left to reach the top-level handler; catch only exogenous failures (I/O, network, parsing external data) and vexing ones that have no Try-style API.
- **Detect:** `rg -n 'catch\s*\(\s*(NullPointerException|NullReferenceException|IndexOutOfRangeException|ArrayIndexOutOfBoundsException|ClassCastException|IllegalStateException|AssertionError)'`; Python `rg -n 'except\s*\(?\s*(TypeError|AttributeError|NameError|AssertionError|IndexError)'`; JS catch blocks that wrap only property or JSON-shape access; Rust `catch_unwind` or Go `recover()` followed by normal work. Decide per hit: external input (then ER-17) or a code defect.
- **Not when:** Python EAFP lookups catching `KeyError`/`IndexError`; `recover()` at an isolation boundary (Effective Go). The dossier says this needs judgement, not a mechanical ban.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [The Error Model](https://joeduffyblog.com/2016/02/07/the-error-model/) (Duffy, 2016); [Vexing exceptions](https://ericlippert.com/2008/09/10/vexing-exceptions/) (Lippert, 2008); [Best practices for exceptions](https://learn.microsoft.com/en-us/dotnet/standard/exceptions/best-practices-for-exceptions) (Microsoft, 2025); [To panic! or Not to panic!](https://doc.rust-lang.org/book/ch09-03-to-panic-or-not-to-panic.html) (Rust project) · dossier: error-handling T14-F05

### ER-06 — Preserve the cause when translating or rethrowing
- **Rule:** Keep the original error and its stack: Python `raise New(...) from err`; JS `new Error(msg, { cause: err })`; C# bare `throw;` or an innerException; Go `fmt.Errorf("...: %w", err)` compared with `errors.Is`/`errors.As`, never `==`; Java the cause in the constructor. Throw only Error or Exception objects, and log with the traceback (`logger.exception`, `exc_info`).
- **Detect:** ESLint `preserve-caught-error` (applies to ESLint v9.35.0+, now in `@eslint/js` recommended); typescript-eslint `only-throw-error`; Ruff `B904`, `TRY400`; .NET `CA2200`; golangci-lint `errorlint`; ``rg -n 'throw\s+("|`|\x27)'`` for thrown strings; ``rg -n 'throw\s+(ex|e|err)\s*;'`` in C#.
- **Not when:** wrapping with `%w` makes the wrapped error part of your API, so do not wrap where that exposes implementation details (`%v` is sometimes right); causes can leak internals into responses unless a boundary sanitizes them (ER-18).
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** A
- **Source:** [preserve-caught-error](https://eslint.org/docs/latest/rules/preserve-caught-error) (ESLint); [Best practices for exceptions](https://learn.microsoft.com/en-us/dotnet/standard/exceptions/best-practices-for-exceptions) (Microsoft, 2025; `throw e` restarts the stack trace); [B904](https://docs.astral.sh/ruff/rules/raise-without-from-inside-except/) (Astral); [Working with Errors in Go 1.13](https://go.dev/blog/go1.13-errors) (Go team, 2019) · dossier: error-handling T14-F09

### ER-07 — Handle each error once
- **Rule:** In internal layers, either handle an error (inspect it and decide: recover or degrade) or return or rethrow it with added context, not both. Log it where it is finally handled or at a module, API, thread or queue boundary.
- **Detect:** ast-grep `catch ($E) { $$$A; $LOG.$M($$$); $$$B; throw $X; }` (Java/TS); Python except bodies holding both a `logger.`/`logging.` call and `raise`; Go `if err != nil { log.$M($$$); return $$$, err }`; the same error logged more than once per request.
- **Not when:** log-and-throw at a subsystem boundary where callers may drop context is a deliberate, defended practice; removing a log reduces observability if the top-level handler does not log. The defect correlation held in only 1 of 3 projects.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** C
- **Source:** [Don't just check errors, handle them gracefully](https://dave.cheney.net/2016/04/27/dont-just-check-errors-handle-them-gracefully) (Cheney, 2016); [Uber Go Style Guide](https://github.com/uber-go/guide/blob/master/style.md) (Uber); [Review of de Pádua & Shang](https://neverworkintheory.org/2021/09/16/exception-handling-practices-and-post-release-defects.html) (Wilson, 2021) · dossier: error-handling T14-F10

### ER-08 — Keep try blocks to the statements the handler was written for
- **Rule:** Move success-path code out of the try block (after it, or into `else`) so the handler cannot absorb errors it was not written for.
- **Detect:** ast-grep `try { $$$BODY } catch ($E) { $$$ }` where BODY has more than about 5 statements or more than one call that can raise the handled type; Python `try:` bodies spanning several unrelated calls under one except. Work out which statement the handler targets from its exception type or log message.
- **Not when:** transactional code that must roll back several statements together (ER-19). The size threshold is a heuristic, PEP 8 binds only Python, and the defect correlation (3 projects) is not causal.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** C
- **Source:** [PEP 8](https://peps.python.org/pep-0008/) (PSF, 2025; "limit the try clause to the absolute minimum"); [Review of de Pádua & Shang](https://neverworkintheory.org/2021/09/16/exception-handling-practices-and-post-release-defects.html) (Wilson, 2021); [Simple Testing Can Prevent Most Critical Failures](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-yuan.pdf) (Yuan et al., 2014; over-catching as code evolves) · dossier: error-handling T14-F04

### ER-09 — No return, break, continue or throw inside finally
- **Rule:** Move control flow out of `finally` and keep it for cleanup; these statements silently discard the in-flight exception or return value. The Go equivalent is a deferred function that overwrites a named error return.
- **Detect:** Ruff `B012` (CPython 3.14+ also emits a SyntaxWarning); ESLint `no-unsafe-finally`; PMD `DoNotThrowExceptionInFinally`, `ReturnFromFinallyBlock`; .NET `CA2219`; confirm each hit by hand.
- **Not when:** PEP 765 found 46 correct uses (mostly in tests) and 8 defensible ones. The fix changes which exception or value propagates, and callers may have adapted to the swallowed behaviour.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [PEP 765](https://peps.python.org/pep-0765/) (PSF, 2024; in the 8,000 most popular PyPI packages, 149 of 203 finally control-flow statements, 73%, were incorrect); [no-unsafe-finally](https://eslint.org/docs/latest/rules/no-unsafe-finally) (ESLint); [jump-statement-in-finally B012](https://docs.astral.sh/ruff/rules/jump-statement-in-finally/) (Astral); [Best practices for exceptions](https://learn.microsoft.com/en-us/dotnet/standard/exceptions/best-practices-for-exceptions) (Microsoft, 2025) · dossier: error-handling T14-F15

### ER-10 — Consume every error-carrying return value
- **Rule:** Check, propagate, or explicitly discard with a written justification every error-carrying return value. Triage each `_ =`, `x, _ :=`, `let _ =` and `(void)` discard.
- **Detect:** golangci-lint `errcheck` (`-blank` covers `_` assignments), `rowserrcheck`, `nilerr`; Rust `unused_must_use` (warn by default; check it is not allowed) and each `let _ =`; C/C++ `[[nodiscard]]`, `-Wunused-result`, clang-tidy `bugprone-unused-return-value`/`cert-err33-c`; Java SpotBugs `RV_RETURN_VALUE_IGNORED*`, Error Prone `CheckReturnValue`, `FutureReturnValueIgnored` (File.delete/mkdir booleans, Futures).
- **Not when:** errcheck's built-in exclude list (stdlib functions documented never to return errors); a close error after read-only use. Gunawi et al. suspect many drops are intentional, so read the context; `if err != nil { return err }` everywhere adds noise without context (ER-06).
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [EIO: Error Handling is Occasionally Correct](https://www.usenix.org/legacy/event/fast08/tech/full_papers/gunawi/gunawi.pdf) (Gunawi et al., FAST 2008; Linux 2.6 file systems and storage drivers: 1,153 of 9,022 error-propagating calls, 13%, drop the error code, writes more often than reads); [CWE-252](https://cwe.mitre.org/data/definitions/252.html) (MITRE, 2026); [errcheck](https://github.com/kisielk/errcheck) (kisielk); [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) (Go team; "Do not discard errors using _ variables") · dossier: error-handling T14-F07; assertions-defensive-checks G203-F09

### ER-11 — No floating promises or futures
- **Rule:** Await, return, combine (`Promise.all`/`allSettled`) or attach a rejection handler to every promise, and never pass an async function to a void-returning callback (`forEach`, event emitters) without handling rejections. `void promise` satisfies the linter but handles nothing at runtime. A missing `await` or an unhandled promise whose result must be observed, fixed mechanically (await or return it, or attach a handler that observes the failure), is a T1 behavioural item fixed at every temperature: the cold-code policy never demotes it (unreferenced asyncio tasks: CC-07). A fix that requires a semantics choice the owner must make (fail-fast `Promise.all` or `allSettled`, cancelling siblings or letting them finish, ordering, rate limits) is reported under CC-05 (T2).
- **Detect:** typescript-eslint `no-floating-promises` (`ignoreVoid` defaults to true) and `no-misused-promises`; `rg -n '\.forEach\(\s*async'`; `rg -n '^\s*void\s+\w+\('` (each needs an explicit `.catch`); check that a `process.on('unhandledRejection')` handler logs and exits rather than swallowing; Error Prone `FutureReturnValueIgnored`; Python `asyncio.create_task(` results never awaited or stored.
- **Not when:** deliberate fire-and-forget (telemetry, cache warm-up) marked `void` with an explicit `.catch`. Adding `await` changes timing and can serialize work that ran concurrently: when it would, choosing the combinator or the order is the owner's decision (CC-05, T2). A comment or commit message saying the call is deliberately not awaited does not make it that decision by itself: CC-05 gives the order in which the fix is chosen (pilot-auto-calibration A01-F12).
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [no-floating-promises](https://typescript-eslint.io/rules/no-floating-promises/) (typescript-eslint); [no-misused-promises](https://typescript-eslint.io/rules/no-misused-promises/) (typescript-eslint); [Node.js CLI --unhandled-rejections](https://nodejs.org/api/cli.html) (Node.js v26 docs; default `throw` since v15 raises an unhandled rejection as an uncaught exception unless an `unhandledRejection` hook is set) · dossier: error-handling T14-F08; eval-v1-calibration E01-F01; pilot-auto-calibration A01-F12

### ER-12 — Release resources on every exit path
- **Rule:** Acquire files, sockets, HTTP response bodies, DB connections, statements and rows, locks and temp files in a scoped construct (`with`, try-with-resources, `using`, `defer` right after a successful acquire, RAII, `finally`), not with a manual close at the end of the happy path.
- **Detect:** Ruff `SIM115`; SpotBugs `OS_OPEN_STREAM`, `ODR_OPEN_DATABASE_RESOURCE`; PMD `CloseResource`; golangci-lint `bodyclose`, `sqlclosecheck`, `rowserrcheck`; `rg -n -A3 'os\.(Open|Create)\(|\.Lock\(\)'` then check that `defer ...Close()` or `Unlock()` follows the err check; C# `using`/`await using`; JS/TS `rg -n 'createReadStream|createWriteStream|\.connect\(|getConnection\('` without try/finally or `using`; C++ raw new/delete or `fopen` without an RAII wrapper.
- **Not when:** the resource escapes (returned, yielded or stored in a field). Close, flush and fsync errors on written files must still be handled.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** A
- **Source:** [CWE-404](https://cwe.mitre.org/data/definitions/404.html) (MITRE, 2026; free "at all exit points ... including error conditions"); [CWE-1306](https://cwe.mitre.org/data/definitions/1306.html) (CISQ Reliability); [SIM115](https://docs.astral.sh/ruff/rules/open-file-with-context-handler/) (Astral); [Simple Testing Can Prevent Most Critical Failures](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-yuan.pdf) (Yuan et al., 2014; an HBase lock-release failure that was only logged "can deadlock all servers accessing the table") · dossier: error-handling T14-F14

### ER-13 — Test the error paths before changing them
- **Rule:** Every handler that makes a recovery decision (retry, fallback, rollback, degrade, terminate) needs a test that injects the failure and asserts the outcome. Report uncovered handlers that do more than rethrow, and add a failure-injection test before changing any handler's propagation; do not pin currently wrong behaviour as the expected result.
- **Detect:** coverage (JaCoCo, coverage.py with `branch=True`, c8/istanbul, `go test -coverprofile`, cargo llvm-cov) intersected with handler locations from ast-grep (`catch ($E) { $$$ }`, `except $T: $$$`, `if err != nil { $$$ }`); mutation tools on exception paths (PIT, Stryker, mutmut, cargo-mutants); tests that assert error outcomes (`assertThrows`, `pytest.raises`, `expect(...).rejects`, `errors.Is`).
- **Not when:** Lima et al. is a Java-only preprint, and coverage alone had an "insignificant correlation" with post-release bugs in 100 Java projects (Kochhar et al. 2017, as cited by Lima).
- **Tier:** T1 · **Class:** structural · **Fix risk:** low · **Grade:** A
- **Source:** [Simple Testing Can Prevent Most Critical Failures](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-yuan.pdf) (Yuan et al., 2014; statement-coverage testing or careful review would have caught the handler fault in 23% of the 48 catastrophic failures, and 77% of all 198 failures reproduce in a unit test); [Assessing Exception Handling Testing Practices](https://arxiv.org/abs/2105.00500) (Lima et al., 2021 preprint; 27 Java libraries, lowest quartile covers 25% of throw and 17% of catch instructions against a median 82% overall); [Transient fault handling](https://learn.microsoft.com/en-us/azure/architecture/best-practices/transient-faults) (Microsoft Azure, 2026) · dossier: error-handling T14-F19

### ER-14 — One boundary handler per entry point; fail the smallest unit
- **Rule:** Give each entry point (main, HTTP or RPC handler, queue consumer, cron job, thread or goroutine spawn) exactly one last-resort handler that logs with the stack, then fails the smallest unit whose state can be discarded: the request (generic 5xx), the batch item (quarantine it and continue), the transaction or contract call (revert), or the process (exit non-zero under a supervisor) when memory or shared state may be corrupt or the runtime says resuming is unsafe. Security decisions fail closed. Never abort a cluster or fleet on a non-fatal error, and never resume normal work on state you cannot trust.
- **Detect:** map entry points to their boundary handler (Express/Fastify error middleware, ASP.NET exception middleware, `sys.excepthook`/`threading.excepthook`, `Thread.setDefaultUncaughtExceptionHandler`, goroutine `defer recover()` wrappers, `catch_unwind` or `CatchPanicLayer`); `rg -n 'uncaughtException|unhandledRejection|sys[.]excepthook|threading[.]excepthook|setDefaultUncaughtExceptionHandler|set_exception_handler|recover[(][)]'` and read what each does after logging; `go func` in servers without recover (an unrecovered goroutine panic ends the process); `recover()` that discards the value; `panic = "abort"` without a supervisor; `--unhandled-rejections` set to warn or none.
- **Not when:** a single process with no supervisor, where exit means downtime (report; a supervisor comes first); Go `net/http` isolates a handler panic to its request but closes the connection instead of sending a 5xx, and is unsafe if the handler may have corrupted shared state; code that cannot restart (embedded, flight) needs an explicit logged recovery path instead.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [Node.js process](https://nodejs.org/api/process.html) (Node.js v26; "not safe to resume normal operation after 'uncaughtException'"); [ASVS 5.0 V16](https://raw.githubusercontent.com/OWASP/ASVS/master/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md) (OWASP, 2025; 16.5.4, L3, a last-resort handler so an error does not take down the whole process); [Fail Fast](https://www.martinfowler.com/ieeeSoftware/failFast.pdf) (Shore, 2004; "a crash is never appropriate", one global handler); [Effective Go](https://go.dev/doc/effective_go) (Go team); [Crash-Only Software](https://www.usenix.org/legacy/events/hotos03/tech/full_papers/candea/candea.pdf) (Candea & Fox, HotOS 2003); [net/http Handler](https://pkg.go.dev/net/http#Handler) (Go team) · dossier: error-handling T14-F17; assertions-defensive-checks G203-F14, G203-F09; observability-config T28-F12

### ER-15 — Error paths never report success
- **Rule:** A failing CLI or batch job exits non-zero, writes diagnostics to stderr and keeps primary output on stdout. A boundary handler returns failure, never 200 or an empty result, and logs the error with its stack (Python: `exc_info`) plus a metric. Remove `exit(0)` from error branches.
- **Detect:** `rg -n '(process[.]exit|sys[.]exit|os[.]Exit)[(]0[)]'` inside error handling; `except Exception`/`BaseException` at handler, worker or loop level that returns success or an empty result; catch-alls that log and swallow a thrown `AssertionError`, which silently defeats the check. Write into `notes` a proposed command that triggers a failure and checks that `echo $?` is non-zero and that `cmd 2>/dev/null` hides the diagnostics; the verifier never executes it (starting a bot or service can place orders or send messages), and the report lists it for the user.
- **Not when:** per-request or per-job containment that reports failure for that unit is what ASVS 16.5.4 describes.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** B
- **Source:** [Command Line Interface Guidelines](https://clig.dev/) (Prasad et al.; "Return zero exit code on success, non-zero on failure", errors to stderr); [ASVS 5.0 V16](https://raw.githubusercontent.com/OWASP/ASVS/master/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md) (OWASP, 2025); [Fail Fast](https://martinfowler.com/ieeeSoftware/failFast.pdf) (Shore, 2004) · dossier: observability-config T28-F12; assertions-defensive-checks G203-F14

### ER-16 — No unwrap, panic or exit on external data or in libraries
- **Rule:** On production paths, propagate failures of I/O, parsing, deserialization, config and caller input (`?` plus context in Rust, returned errors in Go, raised exceptions elsewhere). Keep `unwrap`, `expect`, `assert!` and `panic` for documented internal invariants (prefer `expect("why this cannot fail")`), tests, and startup code that cannot proceed; document remaining library panics under `# Panics`. Put `os.Exit`, `log.Fatal`, `sys.exit` and `process.exit` only in the entry point, and use checked type assertions (Go comma-ok).
- **Detect:** Clippy `unwrap_used`, `expect_used`, `panic`, `indexing_slicing`, `missing_panics_doc` with `allow-unwrap-in-tests`/`allow-expect-in-tests`, then trace each value (from I/O, external text, deserialization or config: finding; from internal logic: `expect("invariant: ...")`); golangci-lint `forcetypeassert`; `rg -n '\bpanic\('` outside `package main` and `init()`; `rg -n 'log\.Fatal|os\.Exit\(' --glob '!**/main.go' --glob '!**/cmd/**'`; `rg -n 'sys\.exit\(|os\._exit\(' --glob '!**/__main__.py'`; `rg -n 'process\.exit\('` outside the CLI entry point; Swift/Kotlin `!!`, `try!`, `as!`; TS non-null assertions `!.`.
- **Not when:** whether to ban `unwrap` outright is unresolved (BurntSushi and the Rust Book accept it for invariants; others want a ban), so follow the project's Clippy config and do not impose a ban. Converting a panic into `Result` changes a signature (T2 when it is public API) and can turn a loud crash into silent wrong behaviour if callers ignore the error (ER-10). For bad config the stronger fix is ER-17.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** B
- **Source:** [Cloudflare outage on November 18, 2025](https://blog.cloudflare.com/18-november-2025-outage/) (Cloudflare, 2025; `Result::unwrap()` panicked on a generated feature file past a 200-feature limit, about 3 h of core traffic impact); [Uber Go Style Guide](https://github.com/uber-go/guide/blob/master/style.md) (Uber); [Using unwrap() in Rust is Okay](https://burntsushi.net/unwrap/) (Gallant, 2022); [ANSSI Secure Rust Guidelines](https://github.com/ANSSI-FR/rust-guide/blob/master/src/en/errors.md) (ANSSI, 2026; LANG-LIMIT-PANIC); [Effective Go](https://go.dev/doc/effective_go#panic) (Go team; "real library functions should avoid panic") · dossier: error-handling T14-F06; assertions-defensive-checks G203-F06, G203-F09

### ER-17 — Parse and bound external and self-generated data at the boundary
- **Rule:** Parse data that crosses a trust or version boundary into precise types before any side effect: user input, network, files, env, persisted state from other releases, IPC from lower-privileged processes, and your own generated config, feature files, rules and server-pushed experiments. Enforce explicit size, count and schema limits against hard-coded capacities, and never assert, unwrap, CHECK or panic on such data. On invalid input reject the item with a typed error and alert; on hot reload keep the last-known-good version, at cold start refuse to start, and never apply partially.
- **Detect:** enumerate ingest points with `rg -n 'JSON\.parse\(|json\.loads?\(|yaml\.(safe_)?load\(|serde_json::from_|toml::from_str|Unmarshal\(|ObjectMapper|pickle\.load|protobuf.*Parse'`; per point check (a) a schema or typed parse (zod/valibot, pydantic, typed serde structs, JSON Schema) before use, (b) explicit bounds, (c) the reject path, (d) no `as`, `cast` or `any` and no unchecked index into parsed arrays (Rust `.get(i)`), (e) validation buried in business logic (shotgun parsing); fixed capacities indexed by counts read from data (`MAX_`, `with_capacity(`, preallocated arrays). Semgrep taint mode can automate part of this.
- **Not when:** stricter parsing can reject inputs that were silently accepted before, so roll it out in log-only or shadow mode first; last-known-good without an alert on each rejection masks a broken generator; building last-known-good storage or kill switches is a design change to report, not to build in this pass.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** B
- **Source:** [Cloudflare outage on November 18, 2025](https://blog.cloudflare.com/18-november-2025-outage/) (Cloudflare, 2025; remediation hardens generated config "in the same way we would for user-generated input"); [Channel File 291 RCA](https://www.crowdstrike.com/wp-content/uploads/2024/08/Channel-File-291-Incident-Root-Cause-Analysis-08.06.2024.pdf) (CrowdStrike, 2024; 21 fields defined, 20 supplied, runtime bounds check missing); [Google Cloud incident, 12 June 2025](https://status.cloud.google.com/incidents/ow5i3PPK96RduMcb1SsW) (Google Cloud; blank policy fields hit an unguarded null path); [Parse, don't validate](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/) (King, 2019); [CHECK(), DCHECK() and NOTREACHED()](https://chromium.googlesource.com/chromium/src/+/main/styleguide/c++/checks.md) (Chromium; "a bad server-side rollout shouldn't be able to bring down the client") · dossier: error-handling T14-F16; assertions-defensive-checks G203-F12

### ER-18 — Return generic errors at external trust boundaries
- **Rule:** At HTTP APIs, public CLIs and UIs, return a generic, stable error (for example RFC 9457 problem details with a correlation id) and log the full exception, stack and context server-side only. ### ER-19 — Make multi-step state changes atomic or compensating; fail closed on security checks
- **Rule:** Report functions that mutate state in two or more steps without a transaction or write-then-rename, and whose handlers do not roll back or compensate before rethrowing: after an exception, callers must be able to assume no partial side effects. A failing security or authorization check must deny.
- **Detect:** functions with two or more writes (`\.(save|insert|update|delete|put|write|publish|send|charge)\(`) not wrapped in `BEGIN|transaction|@Transactional|atomic|session.begin|TransactionScope`; catches there without compensation plus rethrow; writes straight to the target path instead of temp-then-rename; auth checks inside try blocks whose catch lets the request proceed.
- **Not when:** fail-open is a documented choice for a non-security availability gate (Google's June 2025 remediation makes Service Control fail open). Transactions change locking, isolation and performance.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** B

### ER-20 — Match error types to the code's role

- **Detect:** `rg -n 'anyhow::(Result|Error)|Box<dyn (std::error::)?Error'` in pub signatures of Rust library crates; golangci-lint `wrapcheck`, `err113`, `errorlint`, and exported Go functions returning `database/sql` or driver errors via `%w`; Java/C# public methods throwing vendor exceptions across module boundaries; TS libraries throwing plain objects or strings (`only-throw-error`).

### ER-21 — Put an explicit, finite timeout on every remote or cross-process call
- **Rule:** Give every HTTP, gRPC, DB, cache, queue, SMTP and subprocess call a connect timeout and a request timeout, or pass down the caller's remaining deadline; never rely on library defaults. When measured downstream latency exists (metrics, traces, load-test or benchmark output), derive each value from it (for example p99.9 when 0.1% false timeouts is acceptable) and keep it at or below the caller's own deadline. When no latency data exists, still fix the call: the unbounded wait is the defect and the exact value is the owner's tuning. Use a fixed internal default, placed where no exported declaration changes: a named constant private to the module that makes the call (the default choice: unexported in JavaScript and TypeScript, a leading underscore in Python, not `pub` in Rust, so the PF-15 snapshot is unchanged), the project's existing config or settings path when it already carries such values, or a parameter with a default on a non-exported function or constructor. Never add a parameter, option or field to an exported function, class or type for it (in TypeScript even a private field of an exported class changes the emitted declarations, PF-15): the fix needs no public knob, so prioritization's additive-API row 18 never applies to it, and exposing the value is a separate proposal for the owner (pilot-auto-calibration A01-F10). Make the default generous, because a timeout that is too short fails slow but legitimate calls and, with retries, adds load: per attempt, at least 60 s for a whole request and response, or, where the client has per-phase settings, about 10 s to connect and at least 60 s between reads (undici's connect default is 10 s; nginx's `proxy_read_timeout` and an AWS Application Load Balancer's idle timeout default to 60 s, so a default-configured gateway in front of the server has usually closed a silent connection by then); at least ten times the slowest latency the repository documents, logs or its tests and golden captures show, when that is larger. When the caller already carries a deadline or cancellation signal (a context, an `AbortSignal`, a cancel scope), pass its remaining budget down instead (ER-24, CC-20), with no constant and no floor. Document it where it is set, in one line saying it is not derived from latency data. A client's built-in default is not a timeout the code sets (this Rule's first sentence), but where it is finite, such as the 300 s header and body timeouts undici applies behind Node's global `fetch`, write it into the finding's `notes` and the `Behaviour change:` line as the old bound, because the fix then shortens the effective wait; the Not when's "never lower an existing finite value" means a value the code or its config sets. This is a T1 behavioural item: show the proposed default in the Phase 6 category batch, whose approval covers it (in autonomous mode, `auto_apply.behavioural`). Commit it alone with a new test that shortens the bound through a test-only seam (fake timers, a spy on the timer or signal factory, or the private constant patched on its module where the language allows it without a new export, such as Python's `monkeypatch.setattr`; never a new public parameter and never a new export from a module the PF-15 snapshot covers) and shows the call now fails with a timeout error against a local stub on the loopback address that accepts the connection and never answers (no live endpoint). When the fix starts its own timer, the same test file shows that a call the stub answers leaves no timer holding the process open, for example no pending timer under fake timers once the call resolves (in Node, prefer `AbortSignal.timeout`, else clear the timer in a `finally`; eval-v3-calibration E03-F03). List the value and where to change it as owner-tunable in the report's "Open owner items" section, as a one-line reference to the finding id. Set read, write and idle timeouts on server listeners. Database timeouts count here when the application code passes them: driver connect and pool acquisition timeouts, a per-connection lock wait such as SQLite's `busy_timeout` (DA-10), and, with latency data for the query, per-query or per-statement values (DA-12, DA-15).
- **Detect:** Ruff `S113`, Bandit `B113`, Pylint `W3101` (add other clients to `timeout-methods`), and `urlopen(`/`socket.create_connection(` without a timeout; golangci-lint `noctx`, `contextcheck`, `rg -n 'http\.(Get|Post|Head|PostForm)\(|http\.DefaultClient|&http\.Client\{\s*\}|http\.ListenAndServe\('`; each `fetch(` without a `signal:` such as `AbortSignal.timeout(...)`, and axios, got or undici instances without `timeout`; gRPC calls without `context.WithTimeout`, `deadline=` or `withDeadlineAfter`; DB and Redis connect, pool-acquire and per-query or statement timeouts that the code passes (DA-12, DA-15). Build a table: dependency, configured timeout, observed p99 (write "no data" when none exists; the Rule's no-data default then applies). Put the proposed value and its config location in the candidate's `notes`. Confirm each hit at `failing_test` (the demonstrating test the verifier specifies), at `tool_high_precision` (Ruff `S113`, Bandit `B113` or Pylint `W3101`, re-run this session with its output under `.harden/tools/`; a `noctx` or `contextcheck` hit reports a missing `context.Context`, not a missing timeout, and is a lead) or at `reproduction`: a local stub on the loopback address that accepts the connection and never answers keeps the call pending past a stated bound, run within the Phase 0 side-effect limits with no live endpoint. A grep hit or a hand trace alone is a lead, which the orchestrator turns into that reproduction before verification, because an `inference` finding is T2 whatever its row (prioritization PZ-24 step 2; pilot-auto-calibration A01-F11); where Phase 0 forbids running project code, the hit keeps its rung and goes to Limits.
- **Not when:** calls that create orders, payments, transfers or signed transactions: T2 unless an idempotency key and a reconcile-on-timeout path already exist (ER-23, CC-24), because a new timeout turns a slow success into an unknown outcome that a retry wrapper or SDK retry then resubmits ("A timeout or failure doesn't necessarily mean that side effects haven't happened", Brooker). Streams, uploads, downloads the code does not bound, long polls and batch jobs need idle or progress timeouts (at least the Rule's 60 s between reads, and above any hold time the request asks of the server, such as a long poll's `timeout` or `wait` parameter, or the heartbeat interval of a stream) plus resume, never a short total; long jobs need cancellation. A per-query or per-statement database timeout without latency data for that query stays the owner's (T2, the proposed value as its `Proposed first step:`): a query's legitimate duration grows with data the run cannot see, and "short deadlines can cause some more expensive requests to fail consistently" (Ulrich, Google SRE book); driver connect, pool-acquisition and lock-wait timeouts stay T1. ### ER-22 — Bound retries, add jitter, retry at one layer under a budget, only on transient errors
- **Rule:** Every retry is bounded (a maximum attempt count, 3 in the cited examples, plus a total deadline), uses exponential backoff with jitter (full jitter: `sleep = random_between(0, min(cap, base * 2 ** attempt))`), runs at one layer of the stack, sits under a per-client or per-process budget, and fires only on transient errors (429, 5xx, connection errors) while honouring `Retry-After`; never retry validation or auth errors. Prefer the SDK's or a vetted library's retry to a hand-written loop.
- **Detect:** `rg -n -i 'retry|retries|backoff|attempt|tenacity|@retry|axios-retry|p-retry|Polly|resilience4j|urllib3.util.Retry|max_retries'`, plus `while (true)` or `for {` loops holding a sleep and a remote call. Per site check (a) max attempts or deadline, (b) exponential delay with a random part, (c) the predicate excludes 4xx other than 429 (HTTP 408 is common but not in the sources), (d) `Retry-After`, (e) whether an SDK underneath already retries (AWS SDK, Azure SDK, gRPC retry policy, requests `HTTPAdapter(max_retries=...)`), (f) whether a budget or token bucket exists.
- **Not when:** calls that create orders, payments, transfers or signed transactions: T2 unless an idempotency key and a reconcile-on-timeout path already exist (ER-23, CC-24), since a retry after a timeout can resubmit an operation that already succeeded. Circuit breakers versus token buckets is unresolved (Azure recommends breakers, AWS prefers token buckets, Brooker's 2022 simulation finds a trade-off), so report and do not add either; the 3-attempt, 10% and 60-per-minute figures are illustrative, not optima; eventual consistency blurs "never retry 4xx"; for interactive requests failing fast can beat a slow retried success; retry only idempotent operations (ER-23).
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [Timeouts, retries, and backoff with jitter](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf) (AWS, 2019; three retries at each layer of a five-deep stack raise database load 243x); [Handling Overload](https://sre.google/sre-book/handling-overload/) and [Addressing Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/) (Google SRE book, 2016; a 10% per-client retry ratio limits growth to 1.1x; example budget 60 retries per minute per process); [Exponential Backoff And Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/) (Brooker, 2015; full jitter more than halved calls with 100 contending clients, simulation); [Fixing retries with token buckets and circuit breakers](https://brooker.co.za/blog/2022/02/28/retries.html) (Brooker, 2022); [Google Cloud incident, 12 June 2025](https://status.cloud.google.com/incidents/ow5i3PPK96RduMcb1SsW) (no randomized backoff; up to about 2 h 40 min to recover in us-central-1); [REL05-BP03](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_limit_retries.html) (AWS Well-Architected) · dossier: error-handling T14-F12, T14-F13; observability-config T28-F05

### ER-23 — Retry only idempotent operations
- **Rule:** Report every automatic retry or redelivery path around a mutation (POST or PATCH, payment, order or trade submission, email, "create", webhook receiver, queue consumer, scheduled job) that lacks idempotency: a stable client-generated key (never a timestamp) made once per logical operation outside the retry loop, stored atomically with the side effect, returning the original result on replay, and rejecting the same key with different parameters.
- **Detect:** cross-reference ER-22 retry sites with method and operation semantics; `rg -n 'allowed_methods=.*POST|method_whitelist|retryOn.*POST|retryCondition'`; retry decorators on `create*`, `send*`, `charge*`, `place*`, `insert*`, `publish*`; queue consumers without dedup on message id; check the key is generated outside the loop and that the server persists and checks it.
- **Not when:** naturally idempotent operations (reads, full-replace PUT, set-state). Keys need server-side storage, a TTL and concurrency control, which is a design change; removing a retry from a non-idempotent call can lower success rates if nothing replaces it; AWS lists applying idempotency indiscriminately as an anti-pattern.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** high · **Grade:** B
- **Source:** [Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) (Featonby, AWS, n.d.); [Designing robust and predictable APIs with idempotency](https://stripe.com/blog/idempotency) (Leach, Stripe, 2017); [Requests Automatic Retries](https://requests.readthedocs.io/en/latest/user/advanced/) (requests; the official example retries `allowed_methods={'POST'}` with no caveat); [REL04-BP04](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_prevent_interaction_failure_idempotent.html) (AWS Well-Architected) · dossier: error-handling T14-F13; observability-config T28-F06

### ER-24 — Propagate cancellation and deadlines
- **Rule:** Treat interruption and cancellation as signals, not errors: in Java restore the interrupt flag (`Thread.currentThread().interrupt()`) or rethrow; in .NET catch `OperationCanceledException` and let cancellation unwind; in Go check `ctx.Done()`/`ctx.Err()` in long loops and pass the incoming context to outbound calls; in asyncio do not swallow `CancelledError`. Servers stop work once the caller's deadline has passed.
- **Detect:** ``rg -n -U --pcre2 'catch\s*\(\s*(final\s+)?InterruptedException\s+\w+\s*\)\s*\{(?![^}]*(interrupt\(\)|throw))'``; golangci-lint `contextcheck`, `noctx`, and `rg -n 'context\.Background\(\)|context\.TODO\(\)'` outside main and tests; .NET `catch (Exception)` that would swallow cancellation and async methods that do not forward a CancellationToken; asyncio bare `except` or `except BaseException` around awaits.
- **Not when:** top-level thread loops that end on interrupt. Propagating cancellation can surface new error types to callers that used to see slow success; the defect evidence is one of three projects in one study.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** B
- **Source:** [ERR00-J](https://cmu-sei.github.io/secure-coding-standards/sei-cert-oracle-coding-standard-for-java/rules/exceptional-behavior-err/err00-j) (SEI CERT); [Best practices for exceptions](https://learn.microsoft.com/en-us/dotnet/standard/exceptions/best-practices-for-exceptions) (Microsoft, 2025); [gRPC Deadlines](https://grpc.io/docs/guides/deadlines/) (gRPC); [Addressing Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/) (Google SRE book, 2016; check the deadline left at each stage) · dossier: error-handling T14-F22

### ER-25 — Never put a required check in an assertion a build can strip
- **Rule:** A check that validates input, enforces authorization or is needed for correct behaviour must be explicit and always on, raising a typed error: Python `assert` vanishes under `-O`, C/C++ `assert` under `NDEBUG`, Java `assert` is off unless run with `-ea`, and Rust `debug_assert!` is off in the default release profile. Keep strippable assertions only for internal invariants whose removal is harmless. How often production uses `-O` is disputed, so argue from what the check protects, not from how common `-O` is.
- **Detect:** Ruff `S101`, `B011`, `F631` or Bandit `B101` on non-test code, triaged one by one (the condition involves request, user, env, file, network, DB or deserialized data, permissions or money: convert; a pure relation between internal values: keep with a `noqa` reason); run the suite under `python -O -m pytest` and diff; C/C++: confirm what production compiles (`grep -rn NDEBUG CMakeLists.txt cmake/`, `cmake -LA -N build | grep FLAGS_RELEASE`; CMake adds `-DNDEBUG` to Release, RelWithDebInfo and MinSizeRel only when one of them is selected); Java `rg -n '^\s*assert\s'`, especially argument checks in public methods.
- **Not when:** test code and `TYPE_CHECKING` blocks. If production really ran with `-O` or NDEBUG, converting activates checks that never ran, so test first and treat it as a promotion (ER-28). Hot paths can pay real costs (SQLite runs about 3x slower with all its asserts on).
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** A
- **Source:** [The assert statement](https://docs.python.org/3/reference/simple_stmts.html#the-assert-statement) (PSF; no code emitted under optimization); [B101 assert_used](https://bandit.readthedocs.io/en/latest/plugins/b101_assert_used.html) (PyCQA; projects lost protections this way); [Does anyone use -O in deployments?](https://discuss.python.org/t/does-anyone-use-o-or-oo-or-pythonoptimize-1-in-their-deployments/37671) (discuss.python.org, 2023; mixed answers); [assert](https://en.cppreference.com/cpp/error/assert) (cppreference); [GNU.cmake](https://github.com/Kitware/CMake/blob/master/Modules/Compiler/GNU.cmake) (Kitware); [Programming With Assertions](https://docs.oracle.com/javase/8/docs/technotes/guides/language/assert.html) (Oracle; disabled by default, still so in JDK 25); [Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html) (Rust project; release `debug-assertions = false`); [Fail Fast](https://www.martinfowler.com/ieeeSoftware/failFast.pdf) (Shore, 2004; "disable assertions in the field. Don't do that!") · dossier: error-handling T14-F18; assertions-defensive-checks G203-F03, G203-F04, G203-F06, G203-F11

### ER-26 — Keep memory-safety and security guards always on
- **Rule:** Report C/C++ guards that sit right before a dereference, an index, `memcpy`/`memmove` or a variable-sized allocation and exist only as `assert()`; they belong in an always-on mechanism (a CHECK-style macro, libc++ hardening 'fast' mode, or C++26 `contract_assert` under enforce or quick-enforce). In Rust, keep `assert!` wherever unsafe code relies on it and never downgrade it to `debug_assert!` there.
- **Detect:** ast-grep for `assert(` preceding a deref, index, `memcpy`/`memmove` or sized allocation; the `_LIBCPP_HARDENING_MODE` setting; whether some CI job builds without NDEBUG; `debug_assert!` near `unsafe {`; whether `overflow-checks` is on in release for security-relevant arithmetic; grep `contract_assert` and `pre(`/`post(` plus the flags that select each target's semantic. Exact commands are in the C/C++ and Rust language files.
- **Not when:** hot paths with measured cost may keep debug-only checks if tests and fuzzing run that build (ER-29). Do not bulk-migrate `assert()` or CHECK to C++26 contracts as the fix: the feature is contested and toolchains are immature; where contracts exist, pin the semantic per component and never rely on an ignorable contract as the only security check.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Retrofitting spatial safety](https://security.googleblog.com/2024/11/retrofitting-spatial-safety-to-hundreds.html) (Google, 2024; hardened libc++ cost 0.30% on average across Google's services, partly because the compiler drops redundant checks, found over 1,000 bugs and cut the baseline segfault rate 30%); [Hardening Modes](https://libcxx.llvm.org/Hardening.html) (LLVM libc++); [Macro std::assert](https://doc.rust-lang.org/std/macro.assert.html) and [Macro std::debug_assert](https://doc.rust-lang.org/std/macro.debug_assert.html) (Rust project; downgrade "only in safe code!"); [P3835R0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p3835r0.html) (Spicer et al., 2025) · dossier: assertions-defensive-checks G203-F04, G203-F06, G203-F05

### ER-27 — Keep assertion predicates free of side effects
- **Rule:** Move any mutation, I/O, iterator or stream consumption, or mutating call out of assertion and contract predicates and out of Solidity `require`/`assert` arguments, before any build's assertion setting (`-O`, NDEBUG, `debug-assertions`, a contract semantic, Java `-ea`) is relied on or changed.
- **Detect:** clang-tidy `bugprone-assert-side-effect` with `CheckFunctionCalls=true` and the project's macros in `AssertMacros`; Clippy `debug_assert_with_mut_call`; Slither `assert-state-change`; ast-grep for Python `assert` containing `.pop(`, `.remove(`, `next(`, `.send(`, `.write(` or a walrus; run the suite in both modes (`python` vs `python -O`, Debug vs Release, `cargo test` vs `cargo test --release`) and diff.
- **Not when:** the tools misfire on calls that are const but not annotated as such.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** A
- **Source:** [bugprone-assert-side-effect](https://clang.llvm.org/extra/clang-tidy/checks/bugprone/assert-side-effect.html) (LLVM); [Programming With Assertions](https://docs.oracle.com/javase/8/docs/technotes/guides/language/assert.html) (Oracle; `assert names.remove(null)` marked broken); [debug_assert_with_mut_call](https://rust-lang.github.io/rust-clippy/master/index.html#debug_assert_with_mut_call) (Clippy); [P2900R14](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p2900r14.pdf) (WG21, 2025; Principle 6) · dossier: assertions-defensive-checks G203-F16

### ER-28 — Stage every added or promoted always-on check
- **Rule:** Treat a new always-on check on a production path, or a promotion from debug-only, as a behaviour change that ships in stages: tests and fuzzing, then a pre-production soak, then gradual production rollout. Use a non-fatal (observe or report) phase only where a safe fallback exists, and only for a set period; never leave observe mode on permanently, and never downgrade a check that fires in production to debug-only.
- **Detect:** attach a rollout note (exercising tests or fuzzers, stages) to every check this pass proposes to add or promote (ER-17, ER-25); in existing code flag permanent observe-mode configuration and any CHECK-to-DCHECK or `assert!`-to-`debug_assert!` change made after production firings.
- **Not when:** small teams without telemetry use a longer pre-production soak instead; no source bounds how long a non-fatal phase may last in memory-safe languages. In C/C++ continuing past a failed memory-safety check is UB, so keep any non-fatal phase short or use a canary. A size cap on an in-process cache or history is not a check in this sense: it evicts old entries rather than rejecting input, so it ships under PE-05 as a T1 behavioural item proven by a size-observable test, with no soak stage. Surfacing a failure the code already detects (a caught read or parse error, a missing value it substitutes) through an error channel the code already has adds no condition, so it is not a new check either: prioritization's Fail-open findings decide it (pilot-auto-calibration A01-F09).
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** B
- **Source:** [Retrofitting spatial safety](https://security.googleblog.com/2024/11/retrofitting-spatial-safety-to-hundreds.html) (Google, 2024; tests, bake, then production over several months, with no non-fatal phase reported); [CHECK(), DCHECK() and NOTREACHED()](https://chromium.googlesource.com/chromium/src/+/main/styleguide/c++/checks.md) (Chromium; `NotFatalUntil` only where recovery is possible); [Hardening Modes](https://libcxx.llvm.org/Hardening.html) (LLVM; observe only during adoption); [Channel File 291 RCA](https://www.crowdstrike.com/wp-content/uploads/2024/08/Channel-File-291-Incident-Root-Cause-Analysis-08.06.2024.pdf) (CrowdStrike, 2024; staged deployment rings) · dossier: assertions-defensive-checks G203-F13; eval-v2-calibration E02-F01; pilot-auto-calibration A01-F09

### ER-29 — Exercise every debug-only check in CI or fuzzing
- **Rule:** Keep O(1) checks that protect memory, security or persistent state always on, and make expensive ones debug- or test-only. Report any debug-only check that no CI job or fuzz target builds with checks enabled: it is effectively dead code.
- **Detect:** inventory `debug_assert!`, DCHECK, `assert` under NDEBUG, `if __debug__`, `icontract.SLOW` and libc++ debug mode; grep the CI config for a Debug CMake build, `cargo test` without `--release` or with `-C debug-assertions`, Python without `-O`, `ICONTRACT_SLOW`, and fuzzers built with assertions; flag always-on O(n) checks in hot loops as candidates for debug-only after profiling.
- **Not when:** many checks assumed expensive are cheap (Google's 0.30%), so measure before moving any check to debug-only; the Rust docs say assertion cost "is not measurable in general".
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [CHECK(), DCHECK() and NOTREACHED()](https://chromium.googlesource.com/chromium/src/+/main/styleguide/c++/checks.md) (Chromium; DCHECK only when "too expensive"); [Hardening Modes](https://libcxx.llvm.org/Hardening.html) (LLVM; debug mode for tests and CI); [TIGER_STYLE.md](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/TIGER_STYLE.md) (TigerBeetle, 2026); [How SQLite Is Tested](https://www.sqlite.org/testing.html) (SQLite; asserts only in SQLITE_DEBUG builds, about 3x slower) · dossier: assertions-defensive-checks G203-F18

### ER-30 — Keep unreachable-by-construction branches, marked to fail loudly
- **Rule:** Do not delete defensive branches to raise coverage or silence "condition always true" lints, and do not leave them as unmarked silent fallbacks. Mark them with something that throws when reached: an `ALWAYS`/`NEVER`-style wrapper, `NOTREACHED()`, `typing.assert_never` (Python 3.11+), Rust `unreachable!`, or a TS helper `function assertNever(x: never): never { throw new Error(...) }`. The handbook's `const _exhaustiveCheck: never = shape` is compile-time only and returns normally at runtime.
- **Detect:** collect `no-unnecessary-condition` or "always true/false" hits, branches coverage never executed, and `default:`/`else`/`case _` arms that return a neutral value; classify each: defensive against untrusted data or unsound types (keep, mark, and force it in a test if possible), impossible under sound types (throwing exhaustiveness check), dead after a refactor (hand to the dead-code lens). Exclude marked lines explicitly (coverage.py `exclude_also` with `'raise AssertionError'`), not with broad pragmas.
- **Not when:** each coverage exclusion needs a reason, because exclusions can hide real dead code.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** low · **Grade:** B
- **Source:** [The Use Of assert() In SQLite](https://www.sqlite.org/assert.html) (SQLite; `ALWAYS`/`NEVER` macros); [How SQLite Is Tested](https://www.sqlite.org/testing.html) (SQLite; MC/DC discourages defensive branches that fuzzing benefits from); [CHECK(), DCHECK() and NOTREACHED()](https://chromium.googlesource.com/chromium/src/+/main/styleguide/c++/checks.md) (Chromium; enums "can technically hold any integer value"); [typing.assert_never](https://docs.python.org/3/library/typing.html#typing.assert_never) (PSF); [Narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html) (Microsoft) · dossier: assertions-defensive-checks G203-F10

### ER-31 — Remove a check as redundant only when five conditions hold
- **Rule:** Delete a runtime check only if (1) a sound compile-time mechanism or a static tool guarantees its condition, (2) every producer of the value is in the same trust domain, (3) it is not the last guard before UB, unsafe code, a security decision or a persistent write, (4) it has no side effects, and (5) a type carries the guarantee, not an earlier `validate()` call. Otherwise keep it, or merge duplicate handling into one assertion. In TypeScript a `no-unnecessary-condition` hit is not proof when the value comes from `JSON.parse`, `.json()`, a fetch or axios response, `as`/`as unknown as`/`any`, a `Record<string, T>` lookup or `arr[i]` without `noUncheckedIndexedAccess`, a third-party `.d.ts`, or postMessage/IPC.
- **Detect:** write the provenance chain per candidate (producers, type at each hop, boundaries crossed, casts used) and confirm it with the strictest checker available (mypy or pyright strict, `tsc --strict --noUncheckedIndexedAccess`, rustc). Annotation-only guarantees (TS types, C# nullable reference types, Java `@NonNull`) do not count at public APIs or on external data.
- **Not when:** re-checking at a trust boundary is legitimate defence in depth (Chromium allows CHECKing data "after the caller should've validated it"). No study measures the effect of removing redundant checks.
- **Tier:** T1 · **Class:** structural · **Fix risk:** high · **Grade:** B
- **Source:** [JPL Coding Standard for C, Rule 16](https://yurichev.com/mirrors/C/JPL_Coding_Standard_C.pdf) (NASA JPL, 2009); [The Power of 10](https://web.eecs.umich.edu/~imarkov/10rules.pdf) (Holzmann, 2006); [Parse, don't validate](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/) (King, 2019; "a bug waiting to happen"); [no-unnecessary-condition](https://typescript-eslint.io/rules/no-unnecessary-condition/) (typescript-eslint; "may report inaccurately"); [Type Compatibility: soundness](https://www.typescriptlang.org/docs/handbook/type-compatibility.html) (Microsoft); [Nullable reference types](https://learn.microsoft.com/en-us/dotnet/csharp/nullable-references) (Microsoft) · dossier: assertions-defensive-checks G203-F11, G203-F07

### ER-32 — Do not both assert a condition and silently handle it
- **Rule:** Decide whether a condition is an internal invariant (one check, no fallback, failing per ER-14) or an expected condition (handle it, do not assert it). Convert over-defensive guards deep in internal code, such as early neutral returns on None or empty values that every caller already excludes, into one invariant at the module seam instead of deleting them; delete only when ER-31 holds.
- **Detect:** ast-grep or Semgrep for an assertion followed by a guard on the same expression (C++ `DCHECK($X); ... if (!$X)`, Rust `debug_assert!($X); ... if !$X`, TS `invariant($X...); ... if (!$X)`, Python `assert $X` then `if not $X`); internal (non-exported, non-handler) functions with early neutral returns, traced to their callers.
- **Not when:** JPL-style `if (!c_assert(p >= 0)) return ERROR;` is legitimate where crashing is not an option, because it is one always-on mechanism with a tested recovery path; Chromium's `NotFatalUntil` rollouts require a best-effort early return.
- **Tier:** T1 · **Class:** behavioural · **Fix risk:** medium · **Grade:** C
- **Source:** [CHECK(), DCHECK() and NOTREACHED()](https://chromium.googlesource.com/chromium/src/+/main/styleguide/c++/checks.md) (Chromium; "Do not handle DCHECK() failures"); [Making reliable distributed systems](https://erlang.org/download/armstrong_thesis_2003.pdf) (Armstrong, thesis, 2003; "Do not program defensively"); [JPL Rule 16](https://yurichev.com/mirrors/C/JPL_Coding_Standard_C.pdf) (NASA JPL, 2009); [HN comment on AI defensive checks](https://news.ycombinator.com/item?id=48644604) (datadrivenangel, 2026; anecdote) · dossier: assertions-defensive-checks G203-F17

### ER-33 — No assertion quotas; add a check only where you can state its invariant
- **Rule:** Do not add assertions to reach a density number, and do not report low density as a defect. Treat a complex, stateful function with no checks as a prompt: write the invariant in one sentence before proposing a check, and reject tautological asserts.
- **Detect:** diagnostic only, never a gate: functions with zero checks and high cognitive complexity or mutation of more than one field; candidate sites (grade C) are updates of two or more related fields without a post-state check, encode/decode pairs without a symmetric check, and enum switches without a throwing default; Clippy `assertions_on_constants` and Ruff `F631` for tautologies.
- **Not when:** a repository with its own density rule (JPL or TigerBeetle style) follows that rule.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** low · **Grade:** B
- **Source:** [Assertions and code quality (MSR-TR-2006-54)](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-2006-54.pdf) (Kudrjavets, Nagappan, Ball, 2006; two Visual Studio components, per-file Spearman -0.209 to -0.384 against fault density, and the authors doubt density mandates); [Assert Use in GitHub Projects](https://api.openalex.org/works/doi:10.1109/icse.2015.88) (Casalnuovo et al., ICSE 2015, C/C++; count-model effect "negligible overall" per Counsell's quotation); [Revisiting Assert Use](https://api.openalex.org/works/doi:10.1145/3084226.3084259) (Kochhar & Lo, 2017; 185 Java projects, "small yet significant"); [Assert Use and Defectiveness in Industrial Code](https://arxiv.org/abs/2104.01514) (Counsell et al., 2017; "only limited evidence") · dossier: assertions-defensive-checks G203-F01, G203-F02

### ER-34 — Solidity: require or custom errors for input, assert for invariants
- **Rule:** Report `assert` whose condition uses caller input, `msg.sender`, `msg.value`, `tx.origin`, parameters, block values or external-call results (these belong in `require` or a custom error, available from 0.8.4), and any state change or costly call inside `require` or `assert` arguments. Any change to revert data is ABI-visible.
- **Detect:** Slither `assert-state-change`; grep `assert(` conditions that reference those values; the solc SMTChecker to confirm the remaining asserts are true invariants.
- **Not when:** deployed contracts (the change applies to new deployments only); off-chain decoders and tests that match revert strings break when revert data changes.
- **Tier:** T2 · **Class:** report-only · **Fix risk:** medium · **Grade:** A
- **Source:** [Panic via assert and Error via require](https://docs.soliditylang.org/en/latest/control-structures.html#panic-via-assert-and-error-via-require) (Solidity, 0.8.x; "should never create a Panic, not even on invalid external input"); [Custom Errors in Solidity](https://soliditylang.org/blog/2021/04/21/custom-errors/) (Solidity team, 2021); [Slither detector documentation](https://github.com/crytic/slither/wiki/Detector-Documentation#assert-state-change) (Trail of Bits) · dossier: assertions-defensive-checks G203-F08

## False-positive exclusions

- Test code: asserts, `unwrap`/`expect`/`panic` and broad catches in tests (Clippy `allow-unwrap-in-tests`/`allow-expect-in-tests`; Ruff `S101` excluded for tests); asserts in `TYPE_CHECKING` blocks. (error-handling T14-F06, T14-F18; assertions-defensive-checks G203-F03)
- A handler whose comment explains why ignoring is safe, and cleanup failures that cannot affect later behaviour; never close, flush or fsync errors on written files. (T14-F01, T14-F02, T14-F14)
- One deliberate catch-all at a process, request or worker boundary that logs with the stack and fails the unit. (T14-F03, T14-F17)
- errcheck's built-in exclude list: stdlib functions documented never to return errors. (T14-F07)
- Python EAFP lookups that catch `KeyError` or `IndexError`. (T14-F05)
- Fire-and-forget promises marked `void` with an explicit `.catch`. (T14-F08)
- Retries around naturally idempotent operations: reads, full-replace PUT, set-state. (T14-F13; observability-config T28-F06)
- Go `panic` on genuinely impossible states or init failure, and internal panics recovered at a boundary that is the unit of failure. (G203-F09)
- Log-and-throw at module, library, API, thread or queue boundaries. (T14-F10)
- Resources that escape the function (returned, yielded, stored in a field). (T14-F14)
- Try blocks that wrap several statements which must roll back together. (T14-F04)
- Detailed errors on internal service-to-service APIs and internal developer CLIs (ER-18). (T14-F20)
- Streams, uploads and batch jobs that use idle or progress timeouts instead of a total timeout. (T14-F11; T28-F04)
- Repositories that mandate an assertion density: follow the local rule. (G203-F01)
- Marked unreachable branches (`NOTREACHED()`, `assert_never`, `unreachable!`, a throwing `assertNever`) reported by coverage or "always true" lints. (G203-F10)

## Evidence limits

- Yuan et al.'s percentages are shares of 48 catastrophic failures in five distributed Java/C data systems; the authors warn the results may not generalise, and Demirbas (2015) warns the "easily detectable" 23% may reflect hindsight bias.
- de Pádua & Shang (MSR 2018) was read only as an abstract and one secondary review: most of its 17 anti-patterns were not significant, and Log-and-Throw and Ignoring InterruptedException held in 1 of 3 projects.
- Assertion-defect studies are correlational, date from 2006 to 2017, cover only C/C++ and Java, and are confounded by developer ownership and experience; none covers Python, TS/JS, Rust or Go. No study measures which kinds of check catch bugs, or the effect of removing redundant checks.
- Incident reports (Cloudflare 2025, Google Cloud 2025, CrowdStrike 2024, AWS 2021) are single cases: they show mechanisms, not rates, and may omit organisational causes.
- Retry figures (3 attempts, 10% ratio, 60 per minute) are illustrative examples from Google SRE and Azure. There is no evidenced method for choosing timeouts on non-RPC operations (DB queries, disk I/O, lock waits, subprocesses); Dai et al. were read as an abstract only. ER-21's no-data default bounds an unbounded wait but is not a tuned value. Its floors (about 10 s to connect, at least 60 s per request or between reads) are anchored on undici's connect default and on the 60 s read and idle defaults of nginx and AWS Application Load Balancers, and the factor of ten over documented latency is a convention. The evaluations show only that a bounded default breaks no hidden test: all six v1 baseline runs used 10 s (n = 2 per cell) and 9 of 9 v3 skill runs a 10 s constant or option (n = 3 per cell); the 60 s floor itself is unmeasured. (eval-v1-calibration E01-F05; pilot-auto-calibration A01-F10; eval-v3-calibration E03-F03)
- No study shows that converting panics or swallowed errors into propagated errors in a finished system reduces incidents rather than exposing latent failures: require a failure-injection test (ER-13) or shadow logging before changing propagation.
- No standard cross-language detector exists for log-only handlers; Yuan's Java-bytecode checker had 19% false positives, and the grep and ast-grep patterns in this file are untested for precision.
- No peer-reviewed 2024 to 2026 numbers exist on AI-generated error handling or over-defensive code; the evidence is practitioner anecdote. Python `-O` prevalence is anecdotal, and C++26 contract toolchain maturity is unsettled.
