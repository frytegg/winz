# cc-skills-hooks

## Summary
Dossier: C:/Users/Utilisateur/.claude/skills/execution/research/cc-skills-hooks.md. Sources: raw docs fetched 2026-09-30, binary greps, 12 headless probe runs (~USD 1.33) on 2.1.285 and then 2.1.286; the binary auto-updated mid-session.
1. Skill-frontmatter hooks register when the skill is invoked and persist across turns and compaction in that process. /clear and any restart or --resume drop them (F06, F07).
2. In a skill, SessionStart, PreCompact and PostCompact never fired (F08). Skill hooks never saw tool calls inside Agent subagents or workflow agents, and the skill's SubagentStop never fired (F09).
3. Settings hooks in .claude/settings.local.json reach workflow agents, survive resume and compaction, and were live on the very next turn when written mid-session (F22). The Stop gate, the SessionStart(compact|resume) re-injection and the guards belong there, gated by a marker file plus the orchestrator's session_id.
4. Stop fires at the end of every model turn, including the turn that launches a background workflow; that workflow appears in background_tasks (F13). The gate must allow the stop while a wave runs or a manual task is awaited.
5. Block with JSON {"decision":"block","reason"}, not exit 2: exit 2 also shows Claude the hook's command line (F11). stop_hook_active and the 8-block cap (CLAUDE_CODE_STOP_HOOK_BLOCK_CAP) apply (F12).
6. SessionStart(compact) additionalContext reached the model after both manual and automatic compaction, capped at 10,000 characters (F16). This is the channel for "re-read your state".
7. A skill whose instructions say to call Workflow is an explicit opt-in (F18). Bypass mode shows no approval prompt. Workflows take no mid-run input, so each wave is one Workflow call (F19). Only the main thread has Workflow, AskUserQuestion and PushNotification (F21).
8. The Skill tool lets one skill invoke another, including context: fork skills. It refuses disable-model-invocation skills, so /execution can call /hackathon and /prose but never /harden (F03, F20). If /execution itself sets that flag, only the first 5,000 tokens of its body survive compaction (F25).
9. ${CLAUDE_SKILL_DIR} works in SKILL.md but is empty in hook commands (F05). allowed-tools and model last a single turn (F04). Deny rules and a PreToolUse deny still bind in bypass mode, which gives the mainnet gate (F23). Pin the version with DISABLE_AUTOUPDATER=1 before the flight (F29).

## Recommendations
1. Install /execution's durable hooks into the project's .claude/settings.local.json at run start and remove them at hand-over: the Stop gate, SessionStart(matcher compact|resume|startup|clear) re-injection and PreToolUse guards. Settings hooks reach workflow agents, survive resume and compaction, and were live on the next turn (F09, F22). Frontmatter hooks alone vanish on /clear or a restart (F07), and their SessionStart and PreCompact never fire (F08).
2. Gate every hook three ways: the marker file .execution/active, the orchestrator session_id recorded in state at start (settings hooks fire in every session in the repository, including a second terminal and dev B's session), and cheap filters (matchers, the `if` field). Exit 0 on any mismatch.
3. Stop gate algorithm, in order: allow if background_tasks contains a running workflow or subagent (F13); allow if state records an awaited manual task or user decision; allow if the completion-check exits 0. Otherwise print {"decision":"block","reason":"<open items, next wave, or record the wait>"}, never exit 2 (F11). Keep a consecutive-block counter; after K blocks set awaiting:stuck, allow the stop and push to the phone instead of letting the 8-block cap override silently (F12). Stay far below the 600 s timeout (F15).
4. SessionStart(compact/resume) hook: print at most about 2,000 characters naming the state file, the current wave, the open items and which SKILL.md or reference sections to Read again (limit 10,000; F16). Treat only SessionStart(compact) or PostCompact as proof that compaction happened, not PreCompact.
5. SKILL.md: say explicitly that the skill's instructions tell Claude to call the Workflow tool, one call per wave (F18, F19). The orchestrator ends its turn after launching; the completion notification starts the verification-and-next-wave turn. Stages that need the developer become separate workflows. Set model and effort per agent() call.
6. Keep /execution `disable-model-invocation: true` (side effects; user-triggered). Put the standing loop rules in the first ~5,000 tokens of the body (F25) and procedures in references the SessionStart hook points back to. After a restart the user retypes '/execution --resume', which works from the phone.
7. In hook commands use $HOME/.claude/skills/execution/... or absolute paths; ${CLAUDE_SKILL_DIR} is empty there (F05). Use ${CLAUDE_SKILL_DIR} only in the SKILL.md body. Do not rely on allowed-tools or model frontmatter for multi-turn runs (F04).
8. Mainnet gate: a settings PreToolUse deny hook and/or permissions.deny rules for mainnet signing and broadcast commands, lifted only when the owner creates a flag file after funding the wallet. These bind in bypass mode and inside wave agents (F09, F23). Also keep mainnet keys out of the environment until then.
9. Manual tasks and decisions: only the orchestrator has AskUserQuestion and PushNotification (F21). Record `awaiting`, push to the phone, end the turn and keep unaffected waves running in the background; the Stop gate allows the stop. Leave askUserQuestionTimeout unset.
10. Verification by a different agent: implement it in the wave's workflow script (a writer agent, then a verifier agent with schema), or capture final reports with a settings SubagentStop hook, which reaches workflow agents; the skill-level one does not (F09).
11. Skill composition: call /hackathon and /prose through the Skill tool for their sprint-time activities (F20). /harden stays user-only. Give a future /frontend no disable-model-invocation flag (and optionally context: fork) if /execution is to call it.
12. Git hygiene before the first commit: git-ignore .claude/settings.local.json and .execution/ runtime files. Standing push authorisation would otherwise publish machine-specific hook paths, and a tracked settings.local.json is held until trust (F24).
13. Rehearsal: set DISABLE_AUTOUPDATER=1, pin the version, and re-run probes R1, R3, R4, R7b and R9 on it, once interactively with Opus 5.5 in bypass mode as well, before the 4 Oct flight (F29).

## Risks
1. Silent loss of a frontmatter-only gate after a crash, restart, --resume or /clear (F07). The orchestrator could then stop 'done' with no enforcement; settings hooks plus a canary check per wave mitigate this.
2. A Stop gate that blocks while a workflow runs or a manual task is awaited forces Claude to poll or improvise, violating 'stop only for manual tasks'. One keyed only on a marker file also blocks unrelated sessions and dev B's session.
3. Cap override: the default 9th consecutive block is overridden. In -p the result text is then empty (F12), which a wrapper could read as success.
4. Exit-2 blocks put the hook command line and paths into the model's context and are flagged as errors (F11).
5. PreCompact fires even for a compaction that then fails (too_few_groups; F16). State logic keyed on PreCompact would be wrong.
6. SessionStart output over 10,000 characters is replaced by a file path and preview that Claude is not told to read (F16).
7. Skill-driven Workflow calls depend on the model honouring the instruction; they were tested only with Sonnet 5.5 in -p (F18).
8. resumeFromRunId works only within the same session; a fresh session restarts a wave from scratch (F19).
9. Claude Code updated itself mid-session (F29). Hook semantics could change between rehearsal and 6 Oct unless pinned.
10. The C: drive had 3.8 GB free at 19:05Z (the brief said 6.9 GB earlier). Workflow transcripts, isolation:'worktree' and parallel installs can fill it mid-hackathon.
11. Settings hooks run for every tool call of every agent; a slow hook script, for example a heavy Python start-up on Windows, taxes every wave.
12. Committing machine-specific hooks under standing push authorisation would break or confuse dev B's identical setup.
13. Doc summaries are unreliable: a WebFetch summary invented a Stop input field (stop_reason). Always check the raw .md or the binary.

## Findings
- F01 [verified-source] The docs list 20 optional SKILL.md frontmatter fields; unknown fields are ignored silently. The fields: name, description, when_to_use, argument-hint, arguments, disable-model-invocation, user-invocable, allowed-tools, disallowed-tools, model, effort, context, agent, background, hooks, paths, shell, metadata, license, compatibility.
  -> The frontmatter for /execution is constrained by F03, F04 and F05. Misspelled keys fail silently, so validate the frontmatter, for example with `claude plugin validate`.
- F02 [verified-source] The binary's frontmatter schema adds keys marked @internal (version, fallback, created_by, improved_by). It types context as the enum inline|fork, and describes hooks as 'registered while this skill is active', which is narrower than the documented lifetime.
  -> Do not use the internal keys. Rely on the measured hook lifetime (F06, F07), not on either description.
- F03 [verified-executed, LB] disable-model-invocation: true blocks four things: Claude's Skill-tool calls (a fixed refusal that also forbids re-doing the steps another way), the description in Claude's context, preloading into subagents, and scheduled-task runs. The user typing /name, including as a claude -p prompt, still works.
  -> /execution can never call /harden, which matches the owner's flow. If /execution sets the flag, Claude cannot re-invoke it after compaction or resume; the user must retype /execution, which works from the phone.
- F04 [verified-source, LB] allowed-tools, disallowed-tools and model apply only to the turn that invoked the skill and clear at the next user message. The skill content stays in context.
  -> Multi-turn unattended runs must take permissions from bypass mode or settings allow rules. Set models per workflow agent with agent() opts.model and opts.effort, not in frontmatter.
- F05 [verified-executed, LB] ${CLAUDE_SKILL_DIR} is substituted in the skill body, and loaded content is prefixed with 'Base directory for this skill:'. In skill hook commands it is neither substituted nor exported. CLAUDE_PROJECT_DIR is exported to both settings and skill hooks.
  -> In hook commands use $HOME/.claude/skills/execution/... or absolute paths. /harden's `${CLAUDE_SKILL_DIR:-$HOME/...}` works only through its fallback.
- F06 [verified-executed, LB] Skill hooks register at invocation; even the invoking prompt's own UserPromptSubmit fired. They keep firing on later turns and after compaction in the same process. Re-invoking the skill does not register them twice.
  -> Skill hooks outlive the /execution run inside the process, so every hook must exit 0 unless the run marker exists (/harden house style).
- F07 [verified-executed, LB] Skill hooks are dropped by /clear and are not restored when the session is resumed in a new process.
  -> A crash, a restart or a phone-driven `claude --resume` silently removes a frontmatter-only Stop gate. Durable enforcement belongs in settings files (F22).
- F08 [verified-executed, LB] SessionStart, PreCompact and PostCompact hooks declared in skill frontmatter never started. The project-settings versions fired, and the same skill's UserPromptSubmit and Stop kept firing.
  -> Post-compaction state re-injection must come from a settings-file SessionStart hook, not from /execution's frontmatter. Measured n=1, in -p only.
- F09 [verified-executed, LB] Skill PreToolUse and PostToolUse hooks did not fire for tool calls inside Agent subagents or workflow agents, and the skill's SubagentStop never fired; its SubagentStart did. Settings hooks fired for all of these, with agent_id and agent_type (general-purpose or workflow-subagent).
  -> Guards that must bind inside wave agents (the mainnet gate, destructive commands, report capture) need settings hooks or permission deny rules.
- F10 [verified-executed] Skill and settings hooks for the same event run in parallel and all their additionalContext is delivered. Identical handlers are de-duplicated only across settings files; a skill's copy stays separate. For PreToolUse the most restrictive decision wins.
  -> If the gate exists in both layers, both run. Make them idempotent and never contradictory.
- F11 [verified-executed, LB] A JSON decision:block and exit 2 both keep the turn going, and the continuation has stop_hook_active true. Claude receives 'Stop hook feedback:\n<reason>' for JSON, but 'Stop hook feedback:\n[<full hook command>]: <stderr>' for exit 2, which is also marked as an error.
  -> The /execution Stop gate should print JSON {decision:block, reason} and never exit 2. Put the open items and the next step in the reason.
- F12 [verified-executed, LB] Consecutive Stop blocks are capped: by default the 9th block is overridden, and CLAUDE_CODE_STOP_HOOK_BLOCK_CAP changes the cap (0 disables it). With cap=2, blocks 1 and 2 were honoured and block 3 was overridden; the -p result text was then empty.
  -> Keep a block counter in state and escalate to 'awaiting: stuck' plus a phone push before the cap overrides silently. Wrappers must not read an empty result as success.
- F13 [verified-executed, LB] Stop fires at the end of every model turn. That includes the turn that launched a background workflow, whose Stop input listed background_tasks [{type:'workflow',status:'running',name}], and the notification-driven turn after the workflow finished, with background_tasks []. /compact and /clear turns fired no Stop hook.
  -> The gate must allow the stop when a workflow or subagent is running, or when the state records an awaited manual task. Block only when the plan is open and nothing is in flight.
- F14 [verified-executed] The observed Stop input keys are session_id, transcript_path, cwd, prompt_id, permission_mode, effort, hook_event_name, stop_hook_active, last_assistant_message, background_tasks and session_crons. SubagentStop adds agent_id, agent_type and agent_transcript_path, and its background_tasks is scoped to the parent. There is no stop_reason key.
  -> Parse exactly these fields. A WebFetch summary invented a stop_reason field, so do not code against summaries.
- F15 [verified-source] Defaults: command, http and mcp_tool hooks time out at 600 s, prompt hooks at 30 s, agent hooks at 60 s, and UserPromptSubmit at 30 s. A timed-out hook gives no decision. Exit 1 is not a block. once:true is honoured only in skill frontmatter. asyncRewake wakes an idle session on exit 2.
  -> Keep the gate script fast and do heavy proofs in agents. Consider asyncRewake later to wake the run when a manual-task report appears (untested).
- F16 [verified-executed, LB] additionalContext from a settings SessionStart hook with matcher compact reached the model after manual and after automatic compaction. PreCompact(auto) can fire for a compaction that then fails (too_few_groups). Output is capped at 10,000 characters, and SessionStart accepts only command and mcp_tool hooks.
  -> Use this hook for the orchestrator's re-read-state pointer. Trust only SessionStart(compact) or PostCompact as proof that compaction happened, not PreCompact.
- F17 [verified-executed] UserPromptSubmit can add context through plain stdout or additionalContext, both delivered as system reminders. It can block, but it cannot rewrite the prompt.
  -> It can inject 'current wave/state' on each user reply, for example when the developer reports back from a manual task.
- F18 [verified-executed, LB] The Workflow tool's own description lists 'The user invoked a skill or slash command whose instructions tell you to call Workflow' as an explicit opt-in. Typing /wfprobe made Sonnet 5.5 call Workflow in -p mode. The ultracode keyword does not count as an opt-in in -p.
  -> /execution's SKILL.md should say explicitly that its instructions tell Claude to call the Workflow tool for each wave. Re-test with Opus 5.5 interactively.
- F19 [verified-source, LB] Workflow facts for waves: no approval prompt in bypass (Workflow allow rule in -p); no mid-run user input, so run each stage as its own workflow; 16 concurrent agents by default. Inputs are script, name, scriptPath and args; resumeFromRunId works in the same session only. agent() options are label, phase, schema, model, effort, isolation:'worktree' and agentType.
  -> Make one wave one Workflow call launched by the orchestrator. Manual steps and approvals sit between workflows.
- F20 [verified-executed, LB] A skill can invoke another model-invocable skill through the Skill tool, including a context:fork skill that runs as a subagent and returns its result. /hackathon and /prose are model-invocable; /harden is not.
  -> /execution can schedule /hackathon sprint activities and /prose passes as Skill calls. A future /frontend must stay model-invocable if /execution is to call it.
- F21 [verified-source, LB] Every subagent loses AskUserQuestion and Workflow. Background subagents, workflow agents included, keep Skill, Bash, Edit, Write and every MCP tool such as Notion, but not PushNotification. Only the main thread can ask, launch waves or push to the phone.
  -> Manual-task stops, user questions, phone pushes and wave launches stay in the orchestrator. Wave agents may write Notion or run skills.
- F22 [verified-executed, LB] Hooks written into .claude/settings.local.json between two turns of one session fired on the next turn without a restart. Settings hooks survive --resume (R2) and compaction (R3, R7b).
  -> /execution can install its durable hooks at run start and remove them at hand-over. The file must be untracked by git, and writing .claude/ needs bypass mode or approval.
- F23 [verified-source, LB] In bypassPermissions only the 'actions no mode auto-approves' still stop an unattended run: ask rules, org 'ask' connectors, AskUserQuestion and requiresUserInteraction MCP tools, critical-path rm/rmdir, cross-session messaging safeguards, and outside reads when blockReadsOutsideWorkingDirectories is on. Deny rules and a PreToolUse deny still bind. Subagents and workflow agents inherit bypass.
  -> Enforce the mainnet gate and destructive-command guards with deny rules or a settings PreToolUse deny hook, opened by an owner-created flag file. Expect AskUserQuestion to wait indefinitely by default.
- F24 [verified-executed, LB] Rules apply in the order deny, ask, allow. Project permissions.allow rules need interactive workspace trust and are ignored in -p for never-trusted folders; hooks and skill hooks run in -p regardless. In the probes, --setting-sources without 'user' also removed ~/.claude/skills from the session.
  -> Dev B needs bypass mode or a trusted repository. Any scripted or headless launch of /execution must include the 'user' setting source.
- F25 [verified-source, LB] A skill's rendered content enters context once and is not re-read from disk. After compaction only the most recent invocation of each skill is re-attached, first 5,000 tokens each, within a 25,000-token total.
  -> Keep /execution's standing loop rules in the first ~5,000 tokens of SKILL.md and procedures in reference files. The SessionStart(compact) hook should point Claude back to them.
- F26 [verified-source] /goal is a built-in session-scoped prompt-based Stop hook, judged by a small model that reads only the transcript. It skips evaluation while background work runs and is restored on resume, but cannot run proof commands.
  -> It is a reference for the gate's 'defer while background work runs' rule. It is not sufficient as the mechanical-proof gate.
- F27 [verified-source, LB] Remote Control is a window onto the same local process, so skill hooks live while that process lives. A stopped process comes back only through claude --continue or --resume, which drops skill hooks. Permission prompts and AskUserQuestion are forwarded and stay open.
  -> A phone relaunch after a crash is a resume, so it needs settings hooks or a retyped '/execution --resume'.
- F28 [verified-executed] TaskCreate, TaskUpdate and the other task tools are absent by default on Opus and Sonnet 5.x; the Sonnet 5.5 session had none and Haiku 4.5 had them. A TaskCompleted proof gate therefore needs CLAUDE_CODE_ENABLE_TODO_TOOLS=1.
  -> This is an optional extra enforcement layer. Do not assume the task tools exist.
- F29 [verified-executed, LB] Claude Code auto-updated from 2.1.285 to 2.1.286 at 2026-09-30T19:09:21Z during this session. Newly launched processes used the new binary. DISABLE_AUTOUPDATER=1 stops background updates.
  -> Pin the version before 4 Oct, re-run the probes (R1, R3, R4, R7b, R9) on it, and keep it frozen through the hackathon.
- F30 [verified-executed] On Windows, shell-form hooks run in Git Bash, and JSON stdout from node hooks parsed correctly on this machine. Exec form needs a real .exe. In PowerShell hooks the bare $CLAUDE_PROJECT_DIR resolves to $null.
  -> Write the hooks as `node <abs path>/x.js`, or `python`, in shell form, and keep them cheap: they run for every tool call of every agent.

Type /execution alone and first in the message. Typing it from the Remote Control mobile client is untested.
- F04: CONFIRMED — Stronger than stated: both the model override and the allowed-tools grant end with the invoking turn, including across autonomous notification-driven turns where no user message is sent. Probe hygiene: echo is auto-approved in every mode, so it cannot test a grant.
- F05: CONFIRMED — The claim holds, but the implication is incomplete. Skill hooks get CLAUDE_PLUGIN_ROOT set to the skill's own directory; it works in shell form ("${CLAUDE_PLUGIN_ROOT}/x.js") and in exec-form args, while settings hooks do not get it. It is undocumented for skills, so use ${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/skills/execution}.
- F06: CONFIRMED — None. Caveat: vendor issue #95280 (open) reports that once: true in skill frontmatter is ignored, so do not rely on it.
- F07: CONFIRMED — None. Addition: /clear can be sent from the phone (Remote Control text-output commands), so a phone-side /clear also silently drops frontmatter hooks.
- F08: CONFIRMED — None, now replicated (n = 2), still -p only.
- F09: CONFIRMED — None. Mechanism sourced: session (skill) hooks are looked up with the agent's own id. The parent's id is added only for the built-in web-fetch subagent's tool and permission events.
- F11: CONFIRMED — The implication should change. JSON decision:block is itself presented as a hook error: R6 raised the 'Stop hook error occurred' notification. The docs' non-error channel, hookSpecificOutput.additionalContext, continues the turn the same way without that notification. The /execution gate should emit additionalContext, not decision:block; either is better than exit 2.
- F12: CONFIRMED — The empty -p result belongs to the decision:block path only. With additionalContext continuations, the cap also applies but the result keeps the last text. Detect the override from the stop-hook-block-cap notification or the informational message, not from an empty result.
- F13: CONFIRMED — The /clear evidence (R8) was confounded, since only skill hooks were present; it is now measured with settings hooks. Two additions. UserPromptSubmit also fires on notification-driven turns, with a prompt starting '<\task-notification>'. A turn that ends on an API error fires StopFailure (no decision control) instead of Stop, so the gate never sees it.
- F16: CONFIRMED — R3 and R7b used an unmatched SessionStart hook that filtered on source in the script; V5 now confirms the explicit matcher 'compact'. Appendix A is inaccurate: R7b's four stream-json messages were merged into a single turn (one result, num_turns 6, one Stop).
- F18: CONFIRMED — None. Also reproduced with Haiku 4.5; Opus 5.5 in an interactive session remains untested.
- F19: PARTLY-TRUE — The default concurrency is not 16 on this machine: it is min(16, max(2, availableParallelism − 2)) = 14 with 16 logical CPUs. Set CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS=16 (range 1-256) to get 16; this was derived from the source, not run. Everything else holds. The schema also has ignored description/title fields and a runId path. agent() model is hidden when CLAUDE_CODE_SUBAGENT_MODEL_FORCE is set.
- F20: CONFIRMED — None. Nuance: interactively, a context: fork skill runs in the background by default with the narrower background tool set; set background: false for an in-turn result.
- F21: PARTLY-TRUE — Right for regular (non-fork) subagents, wrong for workflow agents and forks. Workflow agents are spawned foreground-shaped, so the background filter does not apply. They keep PushNotification, the Cron tools, RemoteTrigger, Monitor and the task tools. They cannot call Agent (no nested subagents), Workflow or SendUserMessage, and they lose AskUserQuestion through the first filter. Forks (on by default interactively) get the main session's exact tool pool. PushNotification has no subagent guard, so 'only the main thread can push' is a design rule to impose, not a platform guarantee; delivery from an agent was not tested. Wave agents can still write Notion and run skills.
- F22: CONFIRMED — Measured in -p only. On Windows, .claude/settings.local.json is read from the session's primary working directory, not the git root, and .claude/settings.json hooks load only from that directory's .claude/. Install hooks at $CLAUDE_PROJECT_DIR/.claude/settings.local.json and start the session at the repository root. The file watcher can miss a change (restart needed), so a canary is warranted. A file created by hand is not auto-added to git excludes.
- F23: PARTLY-TRUE — Correct as the list of permission prompts that bypass does not skip, but not the full list of what stops or breaks an unattended run. (a) Usage limits: a workflow pauses only in an interactive claude.ai session that is not Remote Control, background or teammate, with autoContinueAtUsageLimit on, a reset within 24 h and at most two waits; otherwise the agents fail. (b) API errors end the turn via StopFailure. (c) The Fable usage-credits consent prompt is not forwarded to Remote Control. (d) Other forwarded dialogs expire after 5 minutes with the no-action default. (e) After three unanswered critical-path rm countdowns, further removals are denied immediately.
- F24: CONFIRMED — None.
- F25: CONFIRMED — Addition: the 25,000-token re-attachment budget is filled from the most recently invoked skill first. If the orchestrator loads five or more other skills inline after /execution, /execution itself can be dropped at compaction, so load other skills inside workflow agents. The live skills page changed after the 18:59Z snapshot and now says 'invoke the skill again to restore its full content ... put the most important instructions near the top of SKILL.md'.
- F27: PARTLY-TRUE — /resume is local-only, so a dead `claude --remote-control` process cannot be revived from the phone. Server mode (`claude remote-control`) re-serves a crashed session when the phone sends a message (v2.1.238+), and --continue or --session-id bring sessions back within about 4 h; skill hooks are lost either way (inferred for the re-serve). But server mode reportedly cannot send phone pushes: vendor issue #92661 says PushNotification returns 'Mobile push not sent (Remote Control inactive)'. Trade-off: server mode gives recovery without pushes; --remote-control gives pushes without phone-side recovery. Pushes also need the /config toggles ('Push when actions required' is off here) and are skipped while the terminal is focused.
- F29: CONFIRMED — The swap happened at 19:09:48Z; the new file was written at 19:09:21Z. A second auto-update ran the same day at 09:22:44Z (2.1.282 to 2.1.285). The existing '"autoUpdates": false' in ~/.claude.json did not stop either update, because the binary ignores it for native installs with autoUpdatesProtectedForNative. Only the DISABLE_AUTOUPDATER or DISABLE_UPDATES environment variables work. Set one as a Windows user environment variable, since every claude process updates the shared binary, and pin with `claude install <version>`.

### Missed
1. Skill hooks get CLAUDE_PLUGIN_ROOT set to the skill's own directory, usable in shell and exec form (V1, binary). It is undocumented for skills, so keep an absolute fallback.
2. Default workflow concurrency on this 16-CPU machine is 14 (min(16, max(2, CPUs-2))). Set CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS=16 to get 16.
3. Workflow agents cannot use the Agent tool (disallowedTools: SendUserMessage, Agent, Workflow). A wave agent cannot spawn its own verifier, so the independent proof check must be a separate agent() call in the workflow script. Vendor issue #80544: agent({agentType}) resolves custom agents from the session working directory's registry.
4. Workflow agents are foreground-shaped and keep PushNotification, the Cron tools, RemoteTrigger and Monitor (V2 transcript). Wave prompts must forbid them if pushes and scheduling are to stay with the orchestrator.
5. UserPromptSubmit fires on every task-notification turn, with a prompt starting '<\task-notification>' (V2). It can re-inject the state pointer at each wave completion; logic that detects the developer answering must ignore these prompts.
6. /clear fires SessionEnd, then SessionStart(source clear) with a NEW session_id (V2); resume and compaction keep the id. A gate keyed on the orchestrator's session_id must re-key on SessionStart(clear) while the run marker exists, and /clear can be sent from the phone.
7. API-error turn endings (rate_limit, overloaded, authentication_failed, billing_error, max_output_tokens) fire StopFailure instead of Stop, with no decision control, so the Stop gate is skipped. Add a StopFailure hook that records 'stuck' and alerts. Vendor issues: #91419 (it also fires for helper and subagent failures), #98012 (rate_limit covers both a resumable limit and a non-resumable credits condition), #93728 (Workflow keeps dispatching queued agents after a rate-limit stop, each failing).
8. Workflow runs pause at a usage limit only in interactive claude.ai sessions that are NOT Remote Control, background or teammate sessions, with autoContinueAtUsageLimit on, a reset within 24 h and at most two waits. Otherwise the agents fail (workflows.md:397-409). A phone-monitored Remote Control run needs retry logic, and resumeFromRunId works in the same session only.
9. Phone pushes are best effort. They need the Claude app signed in, OS permission and the /config toggles ('Push when actions required' is not enabled here), and they are skipped while the terminal is focused. Open vendor issues report non-delivery (#96568, #83523, #98500). Server mode cannot push (#92661). The Notion report after each wave is the dependable channel.
10. Remote Control mode is a trade-off. `claude --remote-control` gives pushes but no phone-side revival of a dead process, since /resume is local-only. `claude remote-control` (server mode) re-serves a crashed session when the phone sends a message but reportedly cannot push. Skill hooks are lost in both cases.
11. On Windows, .claude/settings.local.json and .claude/settings.json are read from the session's starting directory, not the git root (settings.md:481, permissions.md:609). Install hooks at $CLAUDE_PROJECT_DIR and start at the repository root. A hand-created settings.local.json is not auto-added to git excludes (settings.md:466).
12. The Stop gate should use hookSpecificOutput.additionalContext. It continues the turn under the same stop_hook_active protection and cap without a 'Stop hook error' notification (V3). decision:block raises that notification and blanks the -p result when the cap overrides (R6).
13. Skill re-attachment after compaction fills the 25,000-token budget from the most recently invoked skill, so skills invoked inline after /execution can push it out entirely. The skills doc changed on 2026-09-30 after the 18:59Z snapshot.
14. `autoUpdates: false` in ~/.claude.json is ignored for native installs (autoUpdatesProtectedForNative); only the DISABLE_AUTOUPDATER or DISABLE_UPDATES environment variables pin the binary. Two auto-updates landed on 2026-09-30 (2.1.282 to 2.1.285 to 2.1.286).
15. Rehearsal probes of permissions must use a command that is not read-only: echo, ls, cat and similar run without a prompt in every mode (permissions.md:255).
16. Workflow agents load the user's global CLAUDE.md (V2 transcript 'instructions' attachment), including 'ask before major decisions', 'remind to commit' and 'offer X post'. Wave prompts must override these explicitly for autonomous work.
