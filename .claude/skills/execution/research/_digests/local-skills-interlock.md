# local-skills-interlock

## Summary
1. /harden starts only when the user types /harden (disable-model-invocation: true), and that invocation is the consent. /execution hands over and never calls it.
2. An autonomous /harden silently falls to report-only if any of these holds: an untracked non-ignored or modified file outside .harden/; a red or flaky build, typecheck or test gate over 3 repeats; no test gate that self-setup can clear; a committed .only; a failed fresh-clone install or gate. /execution's exit gate must reproduce all of these.
3. These can be proven in advance without writing .harden/: prescan, inventory, then infer_profile infer/probe/finalize (never --install), all with --out-dir outside the repo, then gates.py --repeat 3 and a fresh-clone run. gates.py is reusable as the proof engine (exit 0 means every run of every gate passed).
4. Skill-scoped PreToolUse hooks do not fire for subagent tool calls (harden A01-F45). Agent-definition hooks do, and the global settings guard does (it blocked this very workflow subagent). Guards for /execution's workers must live in agent definitions or in post-hoc git checks.
5. The global guard blocks: AI-attribution trailers, which the harness commit template asks for; reads of .env*, keys and .npmrc; and any read verb whose argument names .env, even as an exclusion filter. Agents run with omitClaudeMd must carry these rules in their own prompt.
6. /hackathon Phase B = continuous ledgers (claims, DX journal, known behaviour), time anchors (demo audit at T-6h, recount the morning of, re-verify before citing, record last) and a recon cadence table by event length. "The freeze" is referenced but never timed, so /execution must define it.
7. Event shape switches the visibility calendar, the judge-path table, "README is the pitch", in-room versus clone-and-grep field reading, and Discord-by-hand versus Telegram MCP. Origins is a hybrid: built in person, judged from the repo, a hosted link and .ppt/.keynote slides with an embedded video; no pre-event code; no changes after Wed 7 Oct 23:59 SGT.
8. /harden budgets 60 min + 20 min per KLOC, clamped to 120-600 min; pilots took 80-108 min. On Origins, build-complete must land around T-12h (Wed 11:59 SGT).
9. /harden detects contract sources only by the .sol and .vy suffixes and has no Cardano or Aiken coverage, so a validator change would not be flagged for redeploy.
10. C: had 2.4 GB free at about 21:10, while a /harden run was active on the Hedera repo with its scratch clones on C:. /execution needs a disk-space gate.
11. /prose needs docs that are already true and never invents a fact: the claims ledger must be closed and the evidence must exist in files before it runs.

## Recommendations
1. Treat 'build complete' as a phase-scoped exit: the completion check tags gates as build, harden or deliverable (unlike BNB's flat list). /execution exits when every build gate PASSes and the harden and deliverable gates stay open by design.
2. Add a harden-ready gate (H1-H15 in the dossier), made only of commands. It checks: HEAD exists; no .harden/active; `git status --porcelain=v1 --untracked-files=all` is empty outside .harden/; no .only/fit/fdescribe; a self-setup dry run (prescan, inventory, infer_profile infer/probe/finalize --out-dir outside the repo, no --install) yields a test gate with mode auto and live_side_effects none; gates.py --repeat 3, one run shuffled with a fixed seed, exits 0 with no flaky gate; a fresh `git clone --no-local` plus lockfile install plus gates.py --repo <clone> exits 0; no auto-loaded env files in the tree; harden_agents.py status exits 0; the disk-space floor holds; time left covers harden's budget; on-chain sources are frozen or scoped out; the README, .env.example and TODO checks pass; the latest GitHub Actions run of the offline gates is green.
3. Reuse harden/scripts/gates.py directly as the proof engine for 'a command that exits 0', always with explicit --config and --out-dir outside .harden/, and never with a file named `active` next to the out-dir.
4. Never write under .harden/, never run infer_profile finalize --install, never write or promote a /harden profile, and never invoke /harden. End with a script-printed hand-over naming exactly what the user should type: /harden, /harden <paths>, or /harden --profile <reviewed path>.
5. Set up a GitHub Actions workflow early (wave 0/1) on GitHub-hosted runners. It runs the offline lint, typecheck, test and build literally, with no secrets, vars, environment, continue-on-error or job-level if. It is both a proof source and the evidence that lets /harden's self-setup clear gates. Keep the completion check out of CI.
6. Keep live scripts (deploy, sign, testnet transactions, evidence capture, forked tests) separate from the offline test command and name them clearly, so self-setup bans them and the default test gate stays offline.
7. Do not rely on /execution frontmatter hooks to guard workers: skill PreToolUse hooks do not reach subagent tool calls. Ship dedicated agent definitions (pinned model, omitClaudeMd with their own copy of the no-attribution and no-secrets rules, their own PreToolUse guard, a Stop hook that saves the report byte for byte and returns one line), install them before the session or pass them as --agents JSON, probe them at start, and run `git status` and diff checks after every worker returns.
8. Copy /harden's run-state pattern: a single writer for the .execution/active marker; hooks that do nothing without it and use the fail-open cygpath launcher from harden SKILL.md:11; progress.md with invariants, red flags, checklist, blocked items, log and a resume line, re-read at every wave and after compaction; invariants within the first 5,000 tokens of SKILL.md; the run directory excluded through .git/info/exclude.
9. Copy /harden's budget logic: fix the deadline once, reserve the Phase B anchors and the harden, merge, fix, record and ship slots back from the end, and have a check that only stops launching new work. That check is the trigger for decision 2 (propose and wait).
10. Schedule the /hackathon Phase B activities from the dossier's table as plan tasks, each pointing at its /hackathon file for content, with an owner (A, H or H+A), a trigger by event shape, and a proof. Define the freezes explicitly (validator or contract, code-for-recording, docs) and a tag plus push freeze at the deadline, overriding the standing push authorisation.
11. Encode an event profile with switches: team, presence, judging mode, demo mode and format, channels, time zones, visibility policy, prework rule, event-shipped tools. Use it to turn on or off the visibility calendar, the judge-path verification shape, 'README is the pitch', the field-reading mode, and run-of-show versus video-script rules.
12. For Origins: create the repo at or after T0 and check the first commit's timestamp; aim for build-complete around T-12h (Wed 11:59 SGT); /harden, merge and fix before the T-6h audit (Wed 17:59 SGT); then freeze and recount, human recording (3 min or less), .ppt/.keynote with the embedded video (the /hackathon HTML deck does not qualify), README screenshots last, public or judge access with the judge's fetch run twice, submit, tag.
13. For Cardano or other non-Solidity chains, propose /harden <paths> scoped away from validator sources, or schedule redeploy plus evidence regeneration after /harden: /harden flags only .sol and .vy as contract sources and has no aiken gate.
14. Fix the /hackathon preflight skeleton in each project so it exits non-zero on stale demo state and a dead frontend before counting it as a proof. Treat the deck builder's slide-cap message as a warning, not a proof.
15. Add a disk-space gate (free space on the volume holding TMP and harden's scratch directory) before every wave with installs and before the hand-over, and cap parallel installs. Refuse to start while any .harden/active exists in the target repo.
16. Write every agent commit message to a file and commit with `git commit -F`: conventional format, a cmd: line, no trailers. Strip 'Generated with Claude Code' from PR bodies. Never name .env in shell commands, never read keys, and never retry a command the guard refused in another form.
17. Keep /prose downstream: entry requires the claims ledger to be closed, the facts to be in files and harden's docs lens to have run. Any fact /prose lacks becomes a manual task for the owner. A drift check across the two sentences (README, form, video) and `prose_check.py --shape` before and after are candidate proofs.

## Risks
1. /harden silently runs report-only after a green-looking hand-over. Causes: an untracked .execution/ file, a flaky test, a test loading .env.local, no CI evidence for a test command with URL literals, a committed .only, or a fresh-clone install that relies on local state. The hours reserved for fixes are lost.
2. Forged consent: an agent writes .harden/profile.json or runs finalize --install, and /harden treats it as the owner's profile, which wins whole.
3. Unguarded workers: frontmatter hooks do not fire for subagents, so a worker could edit tests, run a deploy script or broadcast a transaction unchecked. Only the global guard (attribution and secrets) still applies.
4. Attribution loop: workers run without CLAUDE.md follow the harness template's Co-Authored-By line, the guard blocks the commit, and the worker stalls or retries.
5. Guard false positives (`grep -v .env`, reading .npmrc) stall workers, or tempt them to retry in another form.
6. Disk exhaustion on C: (2.4 GB free): /harden's fresh and verify clones plus parallel dependency installs fail mid-wave and look like code failures. A /harden run is active on Hedera right now.
7. Timeline collapse on a 36 h event: /harden alone takes 2-4 h, and the 24 h recon 'halfway' lands at 06:00 SGT. If build-complete slips past about T-12h, harden-before-record and the T-6h audit collide.
8. Cardano validators are unprotected by /harden: a change passes without the contract-source mark and no aiken gate runs, so the script hash changes and recorded evidence goes stale silently.
9. False proofs: /hackathon's preflight.sh and deck builder exit 0 on the defects they print.
10. Wrong deliverable format: the HTML deck instead of .ppt/.keynote with an embedded video for Origins.
11. Disqualification by prework: event-repo code committed before T0, or the rehearsal fixture reused as the event repo.
12. Judge-visible internals: /hackathon places docs/runsheet.md and docs/hard-questions.md inside the product repo, and the DX journal and claims files may also end up in a public repo.
13. An unreachable exit: copying the BNB completion-check without phase tags makes build-complete impossible.
14. Push after the deadline: standing push authorisation versus Origins' 'No changes after the deadline' and the TASKLIST's 'No push after the tag'.
15. A second developer keeps pushing while /harden runs on the other machine, so the harden branch no longer merges cleanly (inferred).
16. Headless relaunch from the phone or scripts without MSYS_NO_PATHCONV, the session-variable unsets or the py.sh launcher: a Python hook exits 2 and blocks every tool.

3. Where do /hackathon sprint files live: the product repo (judge-visible), a private workspace like Hedera's research/findings/, or Notion with a local mirror?
4. Is /hackathon Phase C (upstream filings, memory updates, X post offers) in /execution's scope?
5. Can agents spawned by the Workflow tool use custom agent definitions with their own hooks (the harden-verifier pattern)? The owner's note says hooks cannot be tested inside workflow subagents.
6. What freezes does Origins need, and at what times: validators, code-for-recording, docs, and the push freeze at the tag or deadline?
7. Branch strategy: work on main or feature branches (git-conventions suggests feat/*)? Which branch does /harden start from, and how does dev B pause around a /harden run?
8. Should Notion wave reports be in French (the conversation language) or English (the file language)?
9. How should the recon cadence be mapped onto a 36 h in-person event with a night in the middle?

## Findings
