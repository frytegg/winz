# notion-mcp

## Summary
1. Every tool /execution needs is 'available' on this connection: create-database, create-pages, update-page, update-data-source, create-view, fetch, get/create-comment and get-async-task. Gated: AI search, multi-source SQL and meeting notes; SQL queries have an undisclosed workspace quota. View-mode queries are the only reads documented as quota-free on every plan.
2. The data model fits: SELECT with declared options for states (STATUS options cannot be declared via MCP DDL), a self-RELATION for dependencies (two calls), PEOPLE, URL, NUMBER, CHECKBOX, RICH_TEXT (2,000 chars per object), FORMULA, and board/filter/chart views via create-view. DATE has no time-zone key through the MCP.
3. There is no concurrency control: per-property last-write-wins, no version or CAS, timestamps rounded down to the minute. MCP writes carry the user's own identity (type person), so Notion cannot tell orchestrator writes from phone edits, or orchestrator A from B.
4. create-pages takes 100 rows per call; update-page takes one page per call; writes may return async tasks. The budget is 180 MCP calls/min per user, shared by every subagent on the connection.
5. Main session, foreground/background/workflow subagents and `claude -p` under a claude.ai login can all reach the connector (not with --bare, --strict-mcp-config, an API key or a setup-token). Scripts cannot: OAuth is interactive-only, and a rejected token needs /login at the terminal. Workflow agents run acceptEdits plus the allowlist, so Notion writes there may prompt mid-run.
6. The phone can read, edit, tick and comment. Nothing pushes into Claude Code, so the orchestrator polls one filtered view. Notion won't notify the user of his own orchestrator's writes: use PushNotification over Remote Control, which also takes photos directly.
7. Two devs: a Free workspace with 2+ members has 1,000 lifetime blocks, so dev B must be a guest or the plan upgraded. One workspace per connection, and the tool prefix differs if Notion is added locally rather than via claude.ai.
8. Recommendation: a repo file is the source of truth (git push as CAS, offline completion check, crash recovery from disk, history in git). Notion is a mirror written only by each dev's orchestrator at wave boundaries, plus typed human-owned input fields, ingested into the repo before acting.

## Recommendations
1. Make the repo the source of truth, committed: .execution/plan.json (graph, owners, dependencies, waves, estimates, model, proof command), a generated EXECUTION.md in TASKLIST style, .execution/progress.md (UTC event lines) and .execution/answers/<key>.md. Notion is a mirror plus a typed input channel. This honours 'shared plan in Notion' (shared, read and answered there) while deciding and proving in git.
2. Only the orchestrator (main session) calls Notion. Workers and verifiers write receipts to the repo; the orchestrator mirrors them at wave boundaries. This avoids mid-run permission prompts in workflow agents, rate bursts, schema tokens in workers, and exposing untrusted Notion text to agents that can execute or send transactions.
3. Per-wave mirror: one create-pages (allow_async:false, up to 100 new rows, keyed by a 'Key' property), then update-page update_properties only for rows whose orchestrator-owned fields changed (tracked by hash in an ignored .execution/local/mirror-state.json), then one create-pages report row in a 'Waves' database, then one update_content on the hub 'Now' text using the last-written text as old_str (fall back to insert_content if it fails). Poll get-async-task for any async result. Keep at most 3 calls in flight and honour Retry-After.
4. Field ownership. Orchestrator-owned: State, Proof, Proof link, Verified by, Wave, estimates, Ingested. Human-owned, never written by any orchestrator: Answer, Attachments, Answered, Decision. State each owner in the column COMMENT. A human edit to an orchestrator-owned field is detected as divergence from the last-pushed hash and raised as a proposal, never silently applied or overwritten.
5. Two devs: assign each row statically to orchestrator A or B in the approved plan. Each orchestrator mirrors only its rows and writes its own reports. Cross-dev progress propagates through git pull (verified states live in plan.json), not through Notion. Reassignment and plan amendments go through commit and push, where a rejected push is the compare-and-set. Dev A creates the Notion databases; dev B attaches via the committed .execution/notion.json.
6. Use SELECT, not STATUS, for the state machine (Planned, Ready, Running, Proof pending, Verified, Blocked, Needs you, Answered, Dropped). Use a SELECT Owner (Agent, Dev A, Dev B) plus a SELECT Orchestrator (A, B). Add the dependency self-relation in a second call, or keep a 'Depends on keys' text column when the rate budget is tight. Never name a property ID or URL.
7. Views: 'Board' (GROUP BY State); 'Needs Dev A' / 'Needs Dev B' lists; 'To ingest' (FILTER (Answered = TRUE OR Decision IS NOT EMPTY) AND Ingested = FALSE) as the only polling target, queried in view mode (quota-free); a 'Waves' list sorted by Wave descending for the phone.
8. Polling: one view-mode query on 'To ingest' at every wave boundary, and every 3-5 min while a manual task is on the critical path. For each hit, read faithfully (rows mode or fetch), write .execution/answers/<key>.md, commit, verify mechanically (for example re-read a tx hash on chain), then set Ingested. Read comments only on rows with an open manual task.
9. Alerts and fast answers go through Claude Code, not Notion: PushNotification (under 200 chars, naming the task key) for every 'needs you'. Accept answers and photos by Remote Control reply as the primary path; Notion is the asynchronous fallback and the reading surface.
10. Time: keep UTC instants in the repo. In Notion, write the Due datetime plus a 'Due text' string (for example 'Wed 7 Oct 23:59 SGT'), and use <mention-date ... timeZone="Asia/Singapore"/> in reports. Reports are single-column (mobile collapses columns) and concise.
11. Resilience: when Notion fails (429/529 after retries, timeout, auth), append the operation to an ignored .execution/local/notion-outbox.jsonl, keep building, replay at the next wave, and after repeated auth failures send a PushNotification telling the user to run /login and then /mcp reconnect at the laptop.
12. Portability: discover the Notion MCP server name at runtime and match both mcp__claude_ai_Notion__* and mcp__notion__* in hooks and allowlists. Always pass the shared hub page as parent (never draft mode). Ship references/notion-formats.md compiled from the notion://docs resources, because tool descriptions are truncated at 2 KB.
13. Before the public flip, remove or ignore .execution/notion.json (it holds private workspace IDs, which are not credentials), and add this as a completion-check gate.
14. Rehearse before Sun 4 Oct 12:00 Paris: DDL and self-relation; a +08:00 date on the phone; phone answer, tick and photo, then poll latency; 20 view-mode polls and a few rows-mode reads, watching for quota messages; one update-page from a workflow agent to see whether it prompts; `claude -p "/mcp"` without --bare; the token cost of one wave sync; dev B as a guest authorizing the MCP.

## Risks
1. The connector's session token is rejected while the user is away: /login is terminal-only, so the mirror stalls. It must not stall the build (repo source of truth plus outbox).
2. The undisclosed SQL (and possibly rows-mode) workspace quota runs out mid-hackathon; view mode is the only mode documented as quota-free.
3. Dev B is added as a member of a Free workspace: the 1,000 lifetime-block cap is hit mid-event, deleting blocks does not restore capacity, and block-creating writes fail after the grace period.
4. Silent lost updates: per-property last-write-wins, no CAS, minute-rounded timestamps and identical authorship (the orchestrator acts as the user) make conflicts between orchestrators, or between an orchestrator and the phone, undetectable.
5. Duplicate task rows when a crash falls between an async create-pages and the recording of its page IDs.
6. A Notion write from a workflow agent triggers a permission prompt at night (acceptEdits plus allowlist) and pauses the whole run.
7. Hooks or allowlists miss dev B's Notion tools because his server prefix differs (mcp__notion__* versus mcp__claude_ai_Notion__*).
8. Wrong property value formats cause validation errors, because the exact formats sit in the truncated parts of the tool descriptions.
9. A deadline displays in the wrong time zone on the phone, since the MCP exposes no time-zone key on date properties.
10. Injected or ambiguous instructions in Notion fields or comments, especially from a second human, are treated as commands instead of data.
11. The user never learns a manual task is waiting, because Notion does not notify him of his own orchestrator's writes.
12. A read right after an async write does not see it yet.
13. Oversized query results (over 25k tokens) are truncated by Claude Code, yielding partial state.
14. Report layout breaks on mobile (columns collapse, wide tables).
15. A human edits an orchestrator-owned field in Notion expecting it to change the plan, and the next sync reverts it.
16. .execution/notion.json with private workspace IDs is published when the repo is flipped public.

## Findings
- F01 [verified-executed, LB] Every Notion tool /execution needs (create_database, create_pages, update_page, update_data_source, create_view, update_view, fetch, get_comments, create_comment, get_async_task, create_attachment, create_file_upload) is 'available' on this connection; gated tools are optional ones.
  -> No paid upgrade is needed for the core loop. Avoid AI search, multi-source SQL and meeting notes. Call get-tool-access once at setup and log the result.
- F02 [verified-source, LB] Only view-mode queries are documented as quota-free on every plan. SQL mode has an undisclosed shared workspace quota on non-Business plans and is lossy on rich text; rows mode returns up to 100 faithful rows, and whether it counts toward the quota is unknown.
  -> Poll a pre-built filtered view in view mode. Use rows mode or fetch only to read a single answer. Never depend on SQL mode.
- F03 [verified-executed] The Custom Agent session tools, search_agents and the two upsell tools are not exposed to this connection. The other tools cover moving and duplicating pages, updating views, file uploads, attachments, folders, sidebar listing and Notion Skills.
  -> Don't design around Notion Custom Agents. Never call the upsell tools in autonomous mode.
- F04 [verified-source] Notion's public MCP docs lag the live server: they list query-data-sources as Enterprise-only and name tools the server no longer exposes.
  -> Trust the runtime access map, not the web docs.
- F05 [verified-executed, LB] Claude Code truncates every long Notion tool description at 2 KB, so exact value formats and parts of the grammar are cut off. The six notion://docs resources are complete.
  -> Ship references/notion-formats.md compiled from the notion://docs resources and the visible description text, and validate it in rehearsal.
- F06 [verified-source, LB] The MCP DDL supports TITLE, RICH_TEXT, DATE, PEOPLE, CHECKBOX, URL, STATUS, FILES, SELECT/MULTI_SELECT with options, NUMBER, FORMULA, RELATION (one-way, dual, self), ROLLUP, UNIQUE_ID, CREATED_TIME, LAST_EDITED_TIME and per-column COMMENT. A self-relation needs two steps.
  -> Task dependencies can be native relations: one create-database, then one update-data-source for the self-relation, then one update-page per row with dependencies. Never name a property 'ID' or 'URL'.
- F07 [inferred] STATUS is a 'simple' type in the MCP DDL, so its options cannot be declared there; defaults are Not started, In progress and Done, and groups can only be reconfigured in the UI. SELECT options can be declared.
  -> Model the /execution state machine as a SELECT; boards can group by it.
- F08 [verified-source] Through the MCP a DATE property takes only start, end and is_datetime, with no time-zone key. The REST API has time_zone, and page content date mentions accept an IANA timeZone.
  -> Keep UTC instants in the repo, add a 'Due text' column such as 'Wed 7 Oct 23:59 SGT', and use mention-date with timeZone in reports. Check the phone display in rehearsal.
- F09 [verified-source] Views can be created and updated through the MCP: board (GROUP BY required), list, table, calendar, timeline, chart, form, dashboard, with FILTER, QUICK FILTER, SORT, SHOW and HIDE. Select filters use option names; person filters need a user URI or 'me'.
  -> Create a Board by State, a 'Needs Dev A' list, and a 'To ingest' view as the orchestrator's polling target. Use a SELECT owner rather than PEOPLE for filtering.
- F10 [verified-source] Size limits: 2,000 chars per rich-text object, 100 elements per array, 100 relations per request, 1,000 blocks and 500 KB per payload, and a recommended 500 properties or 50 KB of schema. The MCP adds 200 KiB inline attachments, 20 MiB file uploads and 5 MiB URL imports on Free. Claude Code caps MCP output at 25k tokens.
  -> Keep property texts short and long material in the page body. Keep reports concise and queries narrow.
- F11 [verified-source, LB] create-pages accepts up to 100 pages with one shared parent per call; update-page updates exactly one page per call; writes may return an async_task that must be polled with get-async-task.
  -> Initial load costs one create call; each wave costs k update calls for changed rows only. Use allow_async:false on creates so page IDs come back, and poll get-async-task before any dependent read.
- F12 [reported] Notion MCP allows an average of 180 calls/min per user across all tool calls (search: 30/min), with per-connection and per-workspace API limits, 429/529 responses and Retry-After.
  -> Batch mirror writes at wave boundaries, keep at most 3 calls in flight, and honour Retry-After.
- F13 [verified-executed, LB] The claude.ai Notion connector is reachable from workflow subagents (observed) and, per the docs, from foreground and background subagents, which share the parent session's connection and therefore one rate budget.
  -> Any agent could write to Notion, which is exactly why the design must restrict it: every agent draws on the same budget and could race.
- F14 [verified-source, LB] Workflow agents run in acceptEdits with the session's allowlist, whatever the session's mode, and MCP tools outside the allowlist can prompt mid-run. The user has no mcp__ allow rule. Read-only calls did not prompt here; writes were not tested.
  -> Keep Notion calls in the orchestrator (main session), or add explicit allow rules for the Notion tools; otherwise an unattended wave can stall on a prompt.
- F15 [verified-source, LB] claude.ai connectors load in `claude -p` whenever the active auth is a claude.ai subscription login. They do not load with ANTHROPIC_API_KEY, apiKeyHelper, a third-party provider, a setup-token CLAUDE_CODE_OAUTH_TOKEN, --bare, --strict-mcp-config, or the disableClaudeAiConnectors / ENABLE_CLAUDEAI_MCP_SERVERS opt-outs.
  -> Headless relaunches can use Notion only under the claude.ai login and without --bare. CI or setup-token runs cannot, so never make Notion a hard dependency of a headless path.
- F16 [verified-source, LB] Notion MCP requires interactive OAuth, so no script can read it. A 'session token rejected' connector needs /login, which is terminal-only; the phone can only run /mcp reconnect.
  -> An offline completion check cannot use Notion. A Notion outage while the user is away must not block the build, which requires the repo to be the source of truth plus an outbox.
- F17 [verified-executed, LB] The MCP connection acts as the user himself (type person), not a bot, so orchestrator writes and phone edits have identical authorship. Notion notifies users about other people's actions, so the user is likely not alerted to his own orchestrator's writes.
  -> Assign explicit ownership to every field, since 'Last edited by' is useless. Send alerts through PushNotification over Remote Control, not Notion.
- F18 [verified-source, LB] Notion has no versioning or compare-and-set: each property is last-write-wins, relations are replaced wholesale, 409 is a transient collision, and last_edited_time is rounded down to the minute. The only precondition is update_content's exact-match old_str.
  -> Two orchestrators, or an orchestrator and the phone, can silently lose updates. Partition writes by row and field ownership, route plan changes through git, and use update_content with the last-written text as a guard on the hub.
- F19 [verified-source] Comments can be read (page-level by default, optionally all blocks and resolved threads) and created (page-level, on a block via selection, or as a reply). Each read costs one call per page, and comments are fully usable from the mobile app.
  -> Signal with properties (one view query covers all tasks). Read comments only on rows with an open manual task.
- F20 [inferred, LB] No Notion MCP tool pushes or waits on page or database changes. Webhooks exist only for REST connections with an HTTP endpoint, so the orchestrator must poll.
  -> Poll one view at each wave boundary and every 3-5 min while a manual task blocks the critical path. The instant path is a Remote Control reply.
- F21 [verified-source] Remote Control keeps the local MCP servers, lets the phone send messages, images and files into the running session, and syncs workflow progress. PushNotification reaches the phone when Remote Control is connected.
  -> Use Remote Control as the fast channel for manual answers and screenshots, with Notion as the asynchronous fallback and reading surface.
- F22 [verified-source, LB] A Free workspace with more than one member is limited to 1,000 lifetime blocks; guests do not count and deleting blocks does not help. Free also caps uploads at 5 MB and page history at 7 days, and limits charts.
  -> For two devs, invite dev B as a guest or upgrade to Plus; otherwise task rows and reports exhaust the cap mid-event.
- F23 [verified-source, LB] Each MCP authorization is bound to one selected workspace. Whether a guest can authorize the MCP on a workspace where he is a guest is undocumented.
  -> Test dev B's access in rehearsal (authorize, then list-shared-pages to find the hub) before relying on it.
- F24 [verified-source, LB] Tool names depend on the connection path: claude.ai connectors give mcp__claude_ai_Notion__*, while a locally added server gives mcp__notion__* and takes precedence over the connector for the same URL.
  -> Discover the Notion server name at runtime, and match both prefixes in any skill hooks or allowlists; dev B's 'identical setup' may differ.
- F25 [verified-source] The Notion mobile app collapses column layouts into a single column.
  -> Write reports as one column of headings, a callout and short tables.
- F26 [verified-source] Without an explicit parent, create-pages and create-database produce private workspace-level pages (draft mode).
  -> Always pass the shared hub page as parent so dev B and the phone can see it.
- F27 [verified-source, LB] A workflow run can be resumed only within the same Claude Code session; exiting restarts it fresh, and a run allows up to 16 concurrent agents.
  -> Run state must be persisted outside the workflow runtime, which argues for a repo file as the source of truth for crash recovery.
- F28 [verified-source, LB] git push accepts a branch update only if it fast-forwards, which gives a real compare-and-set between two orchestrators sharing a repo.
  -> Plan amendments, reassignments and claims go through commit and push; a rejected push means pull, revalidate and re-propose.
- F29 [verified-source] The user's rules and prior art already treat a repository file as the plan: completeness is checked mechanically and offline, git history is memory, and run state is kept outside the conversation.
  -> Follow the house style: .execution/plan.json and progress.md, an EXECUTION.md in TASKLIST style, and a completion check that reads the repo.
- F30 [verified-source] Notion warns that content read through the MCP can carry injected instructions, and recommends human confirmation.
  -> Treat Notion reads as data answering typed fields. Anything that widens scope becomes a proposal. Verify answers mechanically, for example a tx hash re-read on chain.
- F31 [verified-source] Calls to claude.ai connectors have a 60 s per-request timer to the first byte and a 5-min idle timeout, and calls made by subagents are never auto-backgrounded.
  -> Keep individual writes small; rely on async task polling for large creates.
- F32 [verified-source] create-database also offers canonical typed databases (tasks, projects, skills); the properties it creates are not documented in what I could read.
  -> Optionally test database_type 'tasks' in rehearsal for Notion-native task features on mobile; the default is the custom DDL.

## Verification

### Missed
1. CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH (Claude Code v2.1.280+) removes the 2,048-character truncation of Notion tool descriptions. Verified by execution on 2.1.286 against a control run. Set it for every session that runs /execution, dev B's included; setting it through settings.json env is untested.
2. Rows mode of notion-query-data-sources draws on the same metered allowance as SQL and has no cursor. query-data-sources (saved view queries included) and notion-search are each limited to 20 calls per 10 s. Rate limits arrive as tool errors with code 'rate_limited' and retry_after_seconds (Notion retries by itself only when the wait is 2 s or less), not as HTTP 429 with Retry-After (mcp-supported-tools .md:566-577).
3. Guests reportedly cannot connect to Notion MCP at all (makenotion/notion-mcp-server#227). User decision 4 therefore requires dev B as a member. On Free, the lifetime block cap then applies, counted since signup, so a two-developer event effectively needs a paid plan. Check the plan and the block count in rehearsal.
4. Headless claude -p starts in 'default' permission mode here, and the user has no mcp__ allow rules, so every Notion write in a headless relaunch is denied unless the run passes an explicit permission mode or --allowedTools. '--bare' is slated to become the -p default and would drop claude.ai connectors, so pin the flags.
5. In the user's bypass sessions, workflow and worker agents inherit bypass: nothing prompts, and nothing stops a worker from writing to Notion or other write-capable connectors (Gmail, Drive, Calendar, Luma).
