# prior-art-planning

## Summary
1. None of the five tools schedules. spec-kit and Kiro run phases or dependency "waves" as barriers, Taskmaster picks "next" by priority, then fewest dependencies, then ID, and CCPM greps frontmatter with buggy readiness scripts. None models durations, resources, humans or deadlines. Take their data models, not their executors.
2. Adopt spec-kit's stable T-IDs, story phases as the cut order, FR/SC coverage and converge's "completion claims are not evidence"; Taskmaster's JSON with dependencies only on lower IDs; CCPM's conflicts_with; Kiro's requirement refs and required/optional; ExecPlan's decision log and restartability; Anthropic's JSON feature list that stays failing until proven.
3. Parallelism is computed, not asserted: no DAG path between the tasks, disjoint write-sets (manifests and lockfiles count as one resource), and no shared unary resource (signing wallet nonce or UTXO, port, DB, a human).
4. Scheduler: CPM plus Monte Carlo plus a parallel SGS with LFT/min-slack priority, tie-broken by longest remaining path, dispatched online. Waves are reporting epochs, never barriers: barriers cost +33 to 63% makespan with 4+ slots in simulation, and the owner's logs show a median 26% of slot time idle under barriers.
5. Plan to P80/P90: with 4+ slots, a deterministic CPM plan was met in only 24 to 44% of simulated runs. Replan every wave from actual/estimate ratios; a 1.5x overrun is flagged in 68 to 93% of runs by 20% completion.
6. Sizing: each task stays within the model's 80% horizon (about 1 human-hour for early-2026 frontier models, METR), runs about 15 to 45 min of agent time (owner's build p50 27, p90 46 min), and has one deliverable and one mechanical proof. Estimate from the owner's 355 logged agents (median list-price cost: build $15, verify $2).
7. Runtime limits: 16 agents per workflow run by default, no user input mid-run, Date.now() and Math.random() throw inside workflow scripts, and 18 concurrent agents coincided with a 29.5-min stall (/harden caps at 4).

## Recommendations
1. D1 TASK SCHEMA (local JSON is the truth, mirrored to Notion). Fields: id T+3 or more digits, topological, deps only on lower IDs, never renumbered | title and description with exact paths | covers [FR-001, SC-002, US1/AC2], at least one | story US# + story_priority P1/P2/P3, or setup/foundational/polish | kind build/test/verify/research/ops/manual/watch/gate/deliverable | required bool | owner agent/devA/devB | executor devA-machine/devB-machine | depends_on [lower ids] + optional lag_min | release_utc | deadline_utc | anchor {relative_to, offset_min, recurrence} for clock tasks (T-6h audit, re-reads) | writes [globs] | resources [manifest, wallet:<name>, port:<n>, db:<name>, browser:<dev>, disk-heavy] | estimate {p10_min, p50_min, p90_min, source} + human_equiv_min | tokens_est {usd_list, basis} | model opus-5.5/sonnet-5.5/haiku-4.5/fable-5.1/inherit | effort low/medium/high/xhigh/max | fast_mode bool | proof {type command/tx/ci/file/url/human-attest, spec, max_runtime_min, negative_control} | proof_hash | verifier {by agent-not-author, context fresh, model, effort} | status planned/ready/claimed/running/built/verifying/done/failed/blocked-manual/blocked-decision/cut-proposed/cut/superseded | attempts, max_attempts (default 2) | claim {by, at_utc, lease_until_utc} | actual {started, finished, wall_min, tokens, usd, verdict, evidence_path} | wave (computed) | decisions (links). The validator refuses cycles, deps on non-lower IDs, tasks without proof/owner/estimate, uncovered requirements, and overlapping writes or resources with no dependency between them. (F01, F05, F06, F08, F10, F11, F15, F31, F33)
2. D2 PARALLELISM RULE: tasks X and Y may overlap only if (1) no path joins them in the transitive closure of depends_on; (2) their expanded write globs are disjoint; (3) they share no resource name, where any dependency, lockfile, workspace config, CI, migration or codegen change declares 'manifest' and any signing task declares 'wallet:<name>'; (4) at most one disk-heavy task per executor runs while free disk is under a threshold; (5) code-writing tasks on the same machine use separate worktrees, with an integration task to merge. [P] is displayed from this rule and never taken from an LLM. (F01, F11, F12, F27, F32)
3. D3 SCHEDULER: (1) validate; (2) per-task lognormal from the owner's reference class, mu = ln p50, sigma = ln(p90/p50)/1.2816, with human estimates recalibrated; (3) CPM forward/backward with release times and deadlines gives slack, and negative slack means cut proposals before plan approval; (4) priority = LST ascending, then longest remaining path, then most total successors, then lowest ID, plus a boost for tasks that unblock a manual task inside its owner's availability window; (5) resources: m_A and m_B agent slots (default 4-8, max 16), human calendars with sleep/talk/travel breaks, unary resources, quota as a soft pause; (6) Monte Carlo K=500-1000 through the same dispatcher gives P50/P80/P90 per deadline and a criticality index, run as a deterministic orchestrator script like /harden's budget.py; (7) online dispatch: whenever a slot frees or a proof verifies, start the top ready tasks allowed by D2, with no barriers; one workflow run = one wave, closed by an exhausted ready set, a manual block or a 60-90 min time box; clock tasks fired by orchestrator timers; (8) after each wave, update the actual/estimate ratio per kind, rerun steps 3-6 and push the Notion report; (9) offer crash options (fast mode on critical tasks, splitting, moving verification off the critical path) as proposals only. (F07, F16, F17, F18, F19, F20, F22, F23, F28)
4. D4 SIZING RULE: S1 human-equivalent size within the model's 80% horizon, cap 60 min, 30 min for integration or ill-specified work; S2 reference-class p90 agent wall time 60 min or less (owner's build p90 46), else split; S3 one deliverable plus one mechanical proof that runs in 5 min or less; S4 no split below about 15 min of agent time unless file ownership or the critical path needs it (each task adds a verifier, median about $2 and 7 min); S5 deploy, transaction, CI and indexer waits are separate ops tasks with re-read proofs; S6 for a 36-h event expect about 25-60 tasks and 5-6 per slot. Model defaults: critical build Opus 5.5 high, other build medium, fresh-context Opus verifier, mechanical checks run without an LLM. (F24, F25, F26, F27, F28, F29, F31)
5. D5 BEHIND-SCHEDULE AND CUT PROTOCOL: compute the build-complete deadline as submission minus (screenshots + video + /prose + /harden P80 + fixes + buffer). After every wave, zone each hard deadline by P(on time): green >= 0.8; yellow 0.5-0.8 (report, prepare options); red < 0.5 (propose a cut, WAIT for the user, keep running unaffected tasks). Cut candidates in order optional, P3, P2, off the must-have critical path. Publish per-story decision deadlines in Notion so the user can decide from the phone. Put short representative build tasks in wave 1 so calibration arrives by 20-30% completion. (F19, F21, F35)
6. D6 PROVEN COMPLETE: a task is done only when a fresh-context agent that is not the author re-ran the proof, saw the expected result and found proof_hash unchanged. Proof artifacts are written by a different agent than the implementer and fail before implementation (recorded negative control). The plan is complete when every requirement ID is covered by a done task, an independent converge-style pass finds no missing or partial gap (appending tasks when it does), and the generated completion-check (one gate per requirement and per irrecoverable deadline, plus a TODO scan) exits 0. (F03, F05, F15, F26, F33, F34)
7. D7 ADOPT/REJECT: from spec-kit adopt IDs, story phases, analyze coverage and converge gap types; reject barriers, self-ticking and asserted [P]. From Taskmaster adopt JSON, lower-ID deps, tags and relevantFiles.action; reject its next-task rule, complexity-as-time and prose testStrategy. From Kiro adopt EARS, requirement refs, required/optional and checkpoints; reject wave barriers and LLM Sync completion. From CCPM adopt depends_on, conflicts_with and file-scoped streams; reject shell-grep state and one shared worktree. From ExecPlans adopt the decision log, timestamped progress and restartability; reject autonomous ambiguity resolution. From Anthropic's harness adopt a failing-until-proven JSON list and one feature per agent. (F01-F15)
8. Recalibration loop: after every wave, rerun the transcript extraction (Appendix B of the dossier) over /execution's own agents to refresh reference-class p10/p50/p90 and $/min by kind and model, without reading message content. (F28, F29)

## Risks
1. Estimates anchored on benchmarks (SWE-bench about $0.55 per task) instead of the owner's build agents (median $15 at list price) will under-budget time and quota badly.
2. Merge bias: a plan built from mean durations was late in 56-76% of simulated runs with 4+ slots; showing the CPM total instead of P80/P90 misleads the user.
3. Reading 'wave after wave' as barriers costs 33-63% of makespan with 4+ slots in simulation; the owner's logs show a 26% median idle share.
4. Hidden shared resources (lockfile or manifest, testnet signer nonce or UTXO, dev-server port, screenshot browser profile, the C: drive at 5.8 GB free) make tasks on different files collide; Graham anomalies mean more slots can slow things down.
5. Over-concurrency against the API: 18 concurrent agents coincided with a 29.5-min stall; an uncalibrated cap can stall the whole sprint.
6. Verification bottleneck: verifiers are 3-4.5x as numerous as build agents; if they share slots with builds, the critical path slips unless verifier capacity is reserved or mechanical proofs skip the LLM.
7. Self-certification leaks: proofs written by the implementer, weakened tests, or LLM 'sync' completion can mark unfinished work done.
8. Tests pass while the work is unmergeable (METR: 38% passed, none mergeable as-is); unit-test-only proofs overstate completion.
9. Manual-task latency (dev asleep, flying, in talks) stalls every successor; manual tasks need front-loading and phone notifications as their latest start approaches.
10. Quota exhaustion mid-sprint pauses workflows until reset; wall-clock forecasts that ignore quota pauses will be optimistic.
11. Date.now() and Math.random() throw inside workflow scripts, so clock-anchored tasks or Monte Carlo placed there fail; they must run in the orchestrator.
12. Replanning churn: reordering priorities every wave can thrash; change dispatch order only when a zone boundary or the critical path changes materially.
13. Two /execution instances (dev A and dev B) can double-claim tasks through Notion without leases and executor partitioning.
14. Time-zone errors between SGT (UTC+8) and Paris (UTC+2); the Origins window is 2026-10-06T04:00Z to 2026-10-07T15:59Z.
15. Convergence-appended tasks that skip re-validation and re-simulation leave the completion check measuring a stale plan.
16. METR horizons come from clean, low-context, algorithmically scored tasks, and Opus 5.5 is unmeasured; applying them directly without the owner's own first-pass success rate may mis-size tasks.

## Open questions
1. What agent concurrency per machine is safe on this account with Opus 5.5 (/harden chose 4 after a stall at 18; the runtime default is 16)? Measure at 4, 8 and 12 in the rehearsal before Sun 4 Oct.
2. What first-pass proof success rate do 15-45 min Opus 5.5 build tasks reach in the owner's stack? It sets max_attempts and buffers.
3. Does fast mode apply to workflow agents and subagents, and are usage credits enabled on the owner's plan?
4. How large is the owner's quota per 5-hour window and per week, in tokens or /usage percent per agent-hour, so token estimates can become pause time?
5. Is the Workflow runtime's queue for agent() calls beyond the concurrency cap FIFO? If not, the script must hold back dispatch to enforce priority.
6. What may be prepared before the TOKEN2049 Origins start (Tue 6 Oct 12:00 SGT)? It sets release_utc for build tasks.
7. How long do /prose, video recording and README screenshots take? They are needed for the backward build-complete deadline.
8. How are Notion edits made from the phone reconciled with the local JSON truth, and which side wins (Notion dimension)?

## Findings
- F01 [verified-source] spec-kit's tasks are one checklist line each, with a sequential ID in execution order, an optional [P] marker and a story label. The generating LLM asserts [P] from two conditions: different files, and no dependency on incomplete tasks.
  -> Keep stable T-IDs and the story labels, but compute [P] from a machine rule (D2) instead of trusting an LLM-declared flag.
- F02 [verified-source] spec-kit orders work as Setup, then Foundational (which blocks every story), then one phase per user story by priority, then Polish, with a checkpoint after each. Dependencies appear only as prose and phase order. A request for explicit per-task dependencies was closed as not planned on 2026-09-25.
  -> Story phases give a natural MVP-first cut order, but /execution needs explicit machine-readable depends_on.
- F03 [verified-source] spec-kit makes tests optional unless the spec requests them. When included, tests must be written first and must fail before implementation. Inside a story the order is Tests, Models, Services, Endpoints, Integration.
  -> Adopt proof-first with a recorded negative control, and make proofs mandatory rather than optional.
- F04 [verified-source] spec-kit's implement step runs phases as barriers, runs same-file tasks sequentially, and has the implementer tick its own [X] boxes.
  -> Reject both phase barriers and implementer self-certification.
- F05 [verified-source, LB] spec-kit's analyze maps FR/SC IDs to tasks and flags requirements with no task. Its converge step inspects the code, ignores ticked boxes, appends remaining work as tasks with gap types (missing, partial, contradicts, unrequested), and never renumbers IDs.
  -> The definition of "proven complete" is requirement coverage by verified tasks plus an independent convergence pass that finds no missing or partial gap (D6).
- F06 [verified-source] Taskmaster's tasks.json has required id, title, description and status fields, plus optional dependencies, priority, details, a prose testStrategy and one level of subtasks. Status and priority have fixed enums. Tagged task lists are isolated and numbered independently.
  -> Use JSON as the machine state. Extend the status set with a built/verifying/done split, and replace the prose testStrategy with an executable proof.
- F07 [verified-source, LB] Taskmaster's next-task rule ranks eligible tasks by priority, then fewest dependencies, then lowest ID, and ignores durations, successors and deadlines. In simulation this order was 4.5 to 13% above the lower bound with 4 slots, against 1 to 4% for critical-path priority.
  -> The dispatcher must rank by slack and remaining critical path (D3), not by dependency count.
- F08 [verified-source] Taskmaster's PRD parser defaults to 10 top-level tasks and allows dependencies only on lower IDs, which makes the graph acyclic by construction. Its prompt contradicts itself on dependencies. Complexity is an LLM score from 1 to 10 with an expansion threshold of 5, not a time estimate.
  -> Copy the lower-IDs-only rule into the validator. Estimate time from reference classes, not from complexity scores.
- F09 [verified-source] Taskmaster's loop runs one task per fresh claude -p session, and the agent declares completion itself with a marker.
  -> Fresh context per task is good. Self-declared completion is what the owner's rule forbids.
- F10 [verified-source, LB] Kiro groups tasks into dependency waves that run one after another as barriers, runs only required tasks, and lets an LLM mark tasks complete by scanning the code. Its generated tasks link to requirements, mark optional tasks, and include checkpoint tasks.
  -> Adopt requirement refs and required/optional. Reject wave barriers and LLM-judged completion.
- F11 [verified-source] CCPM task frontmatter carries depends_on, parallel and conflicts_with, plus an XS-XL size and hours. CCPM caps an epic at about 10 tasks, splits issues into file-scoped streams worked by parallel agents in one worktree, never auto-resolves conflicts, and uses a Definition of Done checklist with no mechanical proof.
  -> Adopt explicit conflict and write-scope metadata. Replace the DoD checklist with a proof.
- F12 [verified-source] CCPM's next.sh treats a task as ready only when depends_on is empty, and blocked.sh reports every task with a non-empty depends_on as blocked even when all its dependencies are closed.
  -> Derive state from one validated JSON file through a tested validator, not from ad-hoc greps.
- F13 [verified-source] CCPM's README claims a 5x wall-time speedup and up to 3x faster delivery without sources, although its own example (DB, service, API, UI) is a dependency chain.
  -> Treat parallel speedup as bounded by the critical path, and simulate it instead of asserting it.
- F14 [verified-source] OpenAI's ExecPlans are self-contained living documents that can be restarted from alone, with mandatory Progress (timestamped), Surprises, a Decision Log and a Retrospective, and independently verifiable milestones. They tell the agent to resolve ambiguities autonomously.
  -> Adopt the decision log, timestamps and restartability. Reject autonomous ambiguity resolution, which conflicts with user decision 2.
- F15 [verified-source, LB] Anthropic's long-running harness: agents declare the whole project done too early. The fix is a JSON feature list that starts all failing, where agents change only a pass flag, work one feature at a time and test end to end. JSON is overwritten less than Markdown.
  -> Keep local machine state in JSON, start every task as not proven, and give each task one feature.
- F16 [verified-source, LB] Graham 1966: any list schedule is within 2 − 1/n of optimal, and the dynamic longest-chain rule has best-possible bound 2 − 2/(n+1). The same paper shows anomalies where more processors or shorter tasks lengthen the makespan.
  -> Use the longest-remaining-path tie-break in dispatch, and re-simulate after changes instead of assuming more slots help.
- F17 [verified-source, LB] In resource-constrained project scheduling, the parallel schedule generation scheme with LFT or WCS priority is the standard single-pass heuristic. The priority rules have closed-form definitions.
  -> The primary priority key is LST/LFT, which is deadline-aware and simple (D3 step 4).
- F18 [reported] Resource-constrained scheduling models absent resources (people) with break calendars, solved by priority-rule methods.
  -> Model dev A and dev B as resources with sleep, talk and travel breaks.
- F19 [verified-executed, LB] Merge bias: expected completion exceeds the critical path computed from expected times. In simulation with 4 or more slots, the realised mean was 1.03-1.18x the deterministic plan, and the plan was met in only 24-44% of runs.
  -> Check deadlines against Monte Carlo P80/P90 and show those to the user, never the CPM total.
- F20 [verified-executed, LB] Wave barriers waste slot time. In simulation, waves ran 1.12-1.63x the lower bound (1.33-1.63x with 4+ slots) against 1.00-1.04x for critical-path list scheduling. In the owner's 37 workflow runs, the slowest agent in a phase took a median 1.34x (p90 2.07x) the phase median, so barriers would have left a median 26% (p90 48%) of slot time idle.
  -> A "wave" is a reporting epoch or workflow-run boundary. Dependents start when their own predecessors are verified.
- F21 [verified-executed, LB] A systematic overrun is detectable early from the actual/estimate ratio: 1.5x is flagged in 68-93% of runs at 20% completion and 81-96% at 30%, depending on threshold. Noise-only lateness is not detectable early, and at a P(on time) < 0.5 threshold its false alarms stay at 2-9%. Earned-schedule SPI(t) and fever-chart zones are the classical monitors.
  -> Replan every wave with observed ratios. Green >= 0.8, yellow 0.5-0.8, red < 0.5 triggers a cut proposal that waits for the user. Keep an explicit buffer for noise.
- F22 [verified-source, LB] The Claude Code workflow runtime runs up to 16 agents at once by default (fewer with fewer CPUs; this machine has 16), takes no user input mid-run, throws on Date.now() and Math.random() inside scripts, and pauses at usage limits then resumes. It warns above 25 agents or 1.5M tokens, defaults to a size guideline under 10 agents, and caps a run at 1,000 agents. The session subagent cap is 20.
  -> A manual task ends a workflow run. Clock-anchored tasks and Monte Carlo live in the orchestrator or its scripts. The script must enforce priority when more than m tasks are ready.
- F23 [verified-executed, LB] Practical concurrency on this account is far below the runtime cap. 18 concurrent subagents coincided with a 29.5-min API stall, and /harden defaults to 4. The owner's hackathon workflow runs peaked at a median of 3 concurrent agents (p90 8, max 14), with a median of 6 agents per run (p90 15, max 55).
  -> Plan with m = 4-8 agents per machine as a profile setting, and calibrate in rehearsal.
- F24 [verified-source, LB] METR TH1.1 (updated 2026-05-08): early-2026 frontier 50% horizons are several hours of human-expert time, but 80% horizons are about 50-90 min (Opus 4.6: 719/70 min; GPT-5.4: 342/54; Gemini 3.1 Pro: 384/90; Opus 4.5: 293/49; Mythos Preview early: 1045/186). Doubling time since 2023 is about 129 days. Tasks are clean and algorithmically scored, and Opus 5.5 is not measured.
  -> Cap task size at the executing model's 80% horizon, about 60 human-minutes (D4 S1).
- F25 [verified-executed, LB] From METR's logistic-in-log-length fits, the implied first-attempt success for early-2026 frontier models is 86-95% at 30 min, 77-91% at 60 min, 67-85% at 120 min and 54-77% at 240 min of human time.
  -> Retries (max_attempts) and schedule buffers are planned in, not treated as exceptions.
- F26 [verified-source, LB] METR's review of agent PRs: 38% passed the maintainers' tests, yet none of the reviewed PRs was mergeable as-is. Test-passing PRs still needed about 26 min of fixes on 1.3 h tasks.
  -> Proofs must exercise observable end-to-end behaviour, and /harden stays mandatory after build complete.
- F27 [verified-source] Vendor guidance: self-contained units with a clear deliverable, 5-6 tasks per teammate and 3-5 teammates (Claude Code agent teams); tasks a human does in 3 hours or less, with sessions kept XS-M (Devin); explicit effort-scaling rules for research (Anthropic).
  -> This corroborates the sizing rule and task counts per slot (D4 S6).
- F28 [verified-executed, LB] The owner's reference class, 355 agent runs from the Hedera, BNB and XRPL builds: wall time p10/p50/p90 is 6.2/26.7/46.0 min for build, 1.6/6.7/31.1 for verify and 13.0/24.9/40.6 for research. Median list-price cost per agent: Opus 5 build $15.18 (p90 $38.65), verify $2.17, research $5.27; Fable 5.1 build $19.49. Total $3,249 over 118 agent-hours. Verify agents outnumber build agents 3 to 4.5 times.
  -> These are the three-point and token priors for the estimator. Verification capacity must be planned explicitly.
- F29 [verified-executed] 97% of agent tokens are cache reads. For Opus 5 agents, cache reads are 66% of list-price cost, cache writes 18% and output 16%. Cost grows slightly faster than linearly with length (log-log slope 1.08 on wall minutes), and $/min rises from about 0.30-0.35 under 20 min to 0.53-0.58 above 40 min.
  -> Cost estimate is about rate(model, length) x minutes. Keep tasks short and agent context lean.
- F30 [verified-source] Cheaper tiers take more steps, so per-task cost gaps are much smaller than price gaps. On SWE-bench Verified: Opus 4.6 $0.55 per instance (28.9 calls), Opus 4.5 high $0.75, Sonnet 4.5 high $0.66 (48 calls), Haiku 4.5 high $0.33 (66 calls). Current prices: Opus 5.5 $4/$20, Sonnet 5.5 $2/$10, Haiku 4.5 $1/$5, Fable 5.1 $10/$50. Fast mode gives up to 2.5x output speed at 2x price, paid from usage credits.
  -> Benchmark task costs are 20-30x below the owner's real build agents, so use the reference class. Fast mode is a paid option to shorten critical tasks.
- F31 [verified-source] Claude Code's effort values are low, medium, high, xhigh and max. Opus 5.5 defaults to medium, high suits work where verification matters, and max is prone to overthinking. Cheap Haiku passes missed findings in /harden pilots.
  -> Schema effort enum. Default critical-path build to Opus 5.5 at high, and use no Haiku for judgement-bearing verification.
- F32 [verified-source, LB] Tasks writing different files can still conflict: signing accounts need serialized nonces, Cardano eUTXO contention limits concurrency, and same-file edits overwrite. Shared manifests and lockfiles and low disk space (5.8 GB free today) are further hidden conflicts.
  -> The parallelism rule includes unary resources (wallet, manifest, port, db, disk-heavy), not only write paths.
- F33 [verified-source, LB] The owner's TASKLIST already defines owner C/A, a proof column and latest dates. The completion-check script turns planned items into gates that exit non-zero until done, stays out of CI, and gained a deadline gate after the artifact-derived list missed an irrecoverable date.
  -> /execution generates the completion-check from the plan, with one gate per requirement and per irrecoverable deadline.
- F34 [verified-source] /harden's research settled the verifier protocol: re-run every cited tool yourself, check that tests were not weakened, use a fresh context without the author's reasoning, and do not count a same-family verifier's approval as independent.
  -> A task is done only when a fresh-context agent that is not the author re-ran the proof and found the proof hash unchanged.
- F35 [verified-source, LB] The work after build complete has a measured length: /harden had a median total of 114.7 min over 9 runs, and one pilot took 157.5 min including a 29.5-min stall. The owner's order is build complete, harden, fix, record, ship, with README screenshots last.
  -> The build-complete deadline is computed backward from submission minus harden P80, fixes, prose, recording, screenshots and a buffer.
