# Image-to-code: evidence, methods and a fidelity pipeline
> Code FD08 · slug technique-image-to-code · researched 2026-09-30 · verified 2026-09-30 · counts: verified 13 / corrected 16 / downgraded 0 / dropped 0 / added 2

## Summary

- Screenshot-to-code is a well-measured research area (Design2Code, 484 real pages, NAACL 2025, then more than a dozen follow-ups read for this dossier, up to August 2026). Every benchmark found measures one thing: rebuilding the same page, with images replaced by placeholders. None measures what /frontend wants, which is a new page carrying our own content in a design language borrowed from a reference. Read the numbers as a ceiling on copying. They give no direct guidance on borrowing (F01, "not found" 1).
- What fails is completeness and layout, not text. Design2Code: models "mostly lag in recalling visual elements ... and generating correct layout designs"; on hard pages the best models miss 30-40% of block elements, while text similarity stays between 88.7 and 98.6 for commercial models. DCGen: on 12 sites sampled from the Tranco top 500, GPT-4o omitted 1,450 of the 1,699 elements (85%) and reproduced only 40 correctly (corrected: 85.34% is a share of all 1,699 elements, not of error cases). DesignBench's top generation failures are wrong size, missing element and wrong position (F02).
- Models drift toward their own taste. Annotators preferred GPT-4V's rebuild over the original page in 64% of cases. The authors' explanation is a hypothesis, not a measured mechanism. This drift is how generic slop gets in. /frontend has to pin tokens and patterns explicitly (F03, F24). (corrected: v0's course line "interpreting, not copying" was removed as evidence of drift; it describes a sketch used to change one section of an existing site, styled to match that site.)
- Decomposition helps on large pages. DCGen gains +8.4 CLIP points on 15-20 MP screenshots but only +1.9 overall on GPT-4o, at up to about 3x the cost (about 2x with rule-based assembly). Pixel segmentation is "the primary source of failure" (UIBenchKit). Our references are live sites, so /frontend should segment by DOM sections, not by pixels (F05, F06).
- Structured input raises fidelity but makes the code rigid. Figma2Code (ICLR 2026) went from VES 0.565 (image only) to 0.680 (metadata only) to 0.799 (image plus metadata, agentic), but absolute positioning rose from 0.01% to 13.57% and arbitrary values from 0% to 16.71%. The fix is to feed normalized tokens, not raw computed pixels (F09, F10).
- Iteration gains come early and do not rise steadily. CITL with Claude Sonnet 4.5 improved the mean score +4.9% after one critique cycle and +6.1% after three, at about 20x the tokens; keeping the best version per task reached +10.8%, though that best was picked by the same judge that scored it. RubSE: naive self-refinement peaks around round 3.0 on frontier models, and 18.0% of Claude Sonnet 4.5 trajectories collapse (an overall drop of at least 8 points together with an aspect-mean drop of at least 0.35). Fixing one typed defect per round, with a history of past fixes, helps. 1D-Bench: an initial round plus 3 refinement rounds mostly repair builds (Claude Sonnet 4.5 render success 90.9% to 97.7%, similarity only 81.4 to 82.2). **Budget: at most 3 rounds, one repair target per round, keep the best version, revert on regression** (F12-F15).
- No single metric can serve as a stop criterion. Rank correlation with human raters is 0.54 for pixel MAE, 0.34 for CLIP and 0.22 for SSIM, against 0.64 between humans (MRWeb). CLIP is "brittle", and a CLIP reward degraded training (UI2Code^N). SigLIP2 missed or inverted 17 of 40 visible round-to-round changes (RubSE). VLM judges agree with humans about 70% of the time pairwise (CITL), but run-level kappa is 0.08 (FigmaBench, formalised as LH-Bench, arXiv 2603.22744). MLLMs identify UI defects with 0.27 accuracy (DesignBench) (F16-F18, F08).
- Use deterministic gates wherever a gate can be written: render success, completeness against the section ledger, token conformance, and the APR/AVU/RUR/STR code metrics. Leave the rest to a rubric-based VLM critique. Use pixel metrics only when rebuilding our own mock, never when borrowing from a site with different content (F10, F16, F19).
- Extraction. Playwright is installed here (Python 1.58, Chromium 1208/1217). `getComputedStyle` gives resolved values but loses `var()` names and `@media` breakpoints, and `cssRules` throws on stylesheets that are not origin-clean. On Chromium, CDP `DOMSnapshot.captureSnapshot` and `CSS.getPlatformFontsForNode` (the fonts actually rendered) fill the gaps, and `CSS.getMatchedStylesForNode` returns matched rules with their media queries and declared text (F30). dembrandt v0.37.0 packages the computed-style route. GitHub code search found no `DOMSnapshot`, `getPlatformFontsForNode` or `newCDPSession` call in it. Canvas/WebGL sites have no DOM to read (F19-F22, F30). (corrected: "dembrandt packages all of this" overclaimed.)
- Tools. v0 defaults to shadcn/ui (owner tell #11). Lovable and Builder.io accept a live URL or a DOM section as reference. abi/screenshot-to-code (79.9k stars, MIT, pushed 2026-09-29) screenshots desktop and mobile after every edit. Its author's July 2026 judged fidelity scores: GPT-5.6 sol max 8.2, Claude Opus 5 medium 7.8, Gemini 3.1 Pro 7.2 out of 10, method undisclosed (F23-F26).
- Constraints in this environment. The Claude Design type says "no other company's proprietary design" and "NEVER VERIFY UNLESS THE USER ASKED ... (no Playwright ...)". dembrandt's terms forbid reproducing third-party brand identities, and the Artifact tool refuses impersonation. So /frontend borrows structure (skeletons, rhythm, type ratios), never logos, copy, imagery or exact brand palettes, and runs its verification loop on its own build (F27).
- A concrete pipeline (pattern ledger, deterministic capture, token extraction, section-by-section generation, gated and bounded critique) is at the end, with its limits.

## Findings

### FD08-F01 — Design2Code's five scores and what they can and cannot measure; Block-Match needs the same text on both pages
- **Grade:** A · **Kind:** OBSERVED · **Verdict:** VERIFIED
- **Claim:** Design2Code scores a generated page against the reference with five measures. CLIP similarity uses CLIP-ViT-B/32 on square-resized screenshots with text boxes inpainted. Block-Match is the size-weighted share of matched text blocks, penalizing both missing and hallucinated blocks. Text is character-level Sørensen-Dice. Position is 1 minus the larger of the x and y offsets between normalized block centres. Color is CIEDE2000 on text colour. Blocks are paired by text similarity, and pairs below 0.5 are dropped. Text blocks are located by recolouring the source HTML, so the metric needs the HTML of both pages, not just screenshots. The released code averages the five with equal 0.2 weights and screenshots through Playwright Chromium with `full_page=True, animations="disabled"`.
- **Implication for /frontend:** The suite is reusable only when /frontend rebuilds a page whose text it controls on both sides, for example turning our own Claude Design mock into project code. When borrowing a pattern from a customer's site, our copy differs from theirs, so text-keyed pairing fails and Block/Text/Position/Color turn into noise. Borrowing needs the layout-skeleton and token checks described in the pipeline.
- **Evidence:**
  - [Design2Code: Benchmarking Multimodal Code Generation for Automated Front-End Engineering (arXiv 2403.03163, HTML v3)](https://arxiv.org/html/2403.03163v3) — Si, Zhang, Li, Yang, Liu, Yang (Stanford, Georgia Tech, Microsoft, Google DeepMind), v3 9 Feb 2025, NAACL 2025, accessed 2026-09-30 — peer-reviewed paper.
    - "Specifically, we extract features by CLIP-ViT-B/32 after resizing screenshots to squares. To rule out the texts in the screenshots, we use the inpainting algorithm from Telea (2004) to mask all detected text boxes using their bounding box coordinates."
    - "The first desideratum of the task is that all visual elements from the reference webpage should be reproduced in the generated webpage, and the generated webpage should not hallucinate non-existent new elements."
    - Text: "is calculated as twice the number of overlapping characters divided by the total number of characters in the two strings (character-level Sørensen-Dice similarity)."
    - Appendix C: "we alter the color differently for different text segments in the source HTML code and detect text segments in the webpage by taking two extra screenshots and tracking pixels with different colors." ... "ignore the matched pairs with a sequence similarity lower than 0.5"
  - [NoviScl/Design2Code, Design2Code/metrics/visual_score.py and screenshot_single.py](https://github.com/NoviScl/Design2Code) — repository (MIT, last push 2024-11-02), accessed 2026-09-30 — source code (OBSERVED by reading the files).
    - `final_score = 0.2 * (final_size_score + final_matched_text_score + final_position_score + final_text_color_score + final_clip_score)`
    - `model, preprocess = clip.load("ViT-B/32", device=device)`
    - `page.screenshot(path=output_file, full_page=True, animations="disabled", timeout=60000)`
- **Limits / false positives:** Only text blocks are matched; images are placeholders ("rick.jpg"), so image placement is judged by CLIP alone. The CLIP input has text inpainted. Everything is measured on static pages.

### FD08-F02 — The dominant failures are omitted elements and wrong layout, size and position; text is nearly solved
- **Grade:** A · **Kind:** MEASURED · **Verdict:** CORRECTED
- **Claim:** Four independent evaluations name the same failure family. Design2Code: models lag in recalling elements and in layout, and on the 80-page HARD set the best models miss 30-40% of blocks, while text similarity is 97.4-98.6 for GPT-4o, GPT-4V and Claude 3 Opus on the standard set. DCGen: GPT-4o on 12 top-ranked sites reproduced 40 of 1,699 elements correctly, and omission was recorded for 1,450 of the 1,699 elements (85.34%; one element can carry several errors, so Table 2's shares sum to 103%). The paper's text says only that omission "accounts for the majority of error cases" (corrected: the 85.34% denominator is all 1,699 elements, not error cases). DesignBench's top three generation failures are wrong element size, missing element and wrong element position. The screenshot-to-code author (2024, Claude 3 era) saw every model struggle with side-by-side flex layouts, and Claude 3 often got background and text colours wrong.
- **Implication for /frontend:** The first verification gate is completeness: every section and feature in the ledger and spec must exist in the rendered DOM. Layout geometry comes next. Text correctness costs almost nothing to guarantee: pass the exact copy in (F11) and never let the model transcribe the reference.
- **Evidence:**
  - [Design2Code (arXiv 2403.03163 v3)](https://arxiv.org/html/2403.03163v3) — Si et al., NAACL 2025, accessed 2026-09-30 — peer-reviewed paper.
    - "Our fine-grained break-down metrics indicate that models mostly lag in recalling visual elements from the input webpages and generating correct layout designs."
    - "state-of-the-art models fail to generate 30% - 40% of the block elements (Block-Match)"
  - [Automatically Generating UI Code from Screenshot: A Divide-and-Conquer-Based Approach (DCGen, arXiv 2406.16386 v3)](https://arxiv.org/html/2406.16386v3) — Wan, Wang, Dong, Wang, Li, Huo, Lyu (CUHK, SMU), v3 25 Apr 2025, accepted by FSE 2025, accessed 2026-09-30 — peer-reviewed paper.
    - "In total, MLLM correctly reproduces only 40 out of 1,699 elements, highlighting the need for a practical UI code generation approach."
    - Table 2 ("Distribution of common mistakes (one element can have multiple mistakes)"): Omission 85.34% (1,450), Distortion 2.56% (44), Misarrangement 12.71% (216), Correct 2.35% (40), Total 1,699.
  - [DesignBench (arXiv 2506.06251 v3)](https://arxiv.org/html/2506.06251v3) — Xiao, Wang, Lam, Wan, Liu, Huo, Lyu (CUHK, SMU), v3 15 Mar 2026, accessed 2026-09-30 — preprint with data.
    - "(1) Design generation tasks are dominated by spatial and structural failures, with "wrong element size," "element missing," and "wrong element position" as the top three failure types, revealing MLLMs’ limitations in layout comprehension and spatial reasoning."
  - [Claude 3 for converting screenshots to code (blog/evaluating-claude.md)](https://github.com/abi/screenshot-to-code/blob/main/blog/evaluating-claude.md) — Abi Raja, screenshot-to-code maintainer, last edited 2024-03-06, accessed 2026-09-30 — practitioner measurement.
    - "For some reason, all the models struggle with side-by-side "flex" layouts"
    - "Claude 3 gets background and text colors wrong quite often!"
- **Limits / false positives:** Models and years differ (GPT-4V to Claude 3.7). DCGen's error taxonomy rests on 12 very large sites (Amazon, Apple, Facebook; 142 elements per site on average) and two annotators. Hackathon landing pages are smaller, so omission rates should be lower there.

### FD08-F03 — Raters told to rank content, then layout, then style reward element presence and layout over exact text, and models pull references toward their own design priors
- **Grade:** A · **Kind:** MEASURED · **Verdict:** CORRECTED
- **Claim:** In Design2Code's human study (100 pages, 5 Prolific annotators each), a logistic regression predicting human pairwise wins gave a negative coefficient for text similarity (-0.3541, p=0.021). Block-Match (0.7429), Position (0.7605), CLIP (0.4929) and Color (0.3461) all came out positive. The annotators were instructed to judge in the priority order "Content > Layout > Style", so that ordering is the protocol, not a measured human preference. The measured part is that, under those instructions, exact text similarity carried negative weight. (corrected: the title "Humans judge content first and layout second" presented the instructed priority as a finding.) 49% of GPT-4V rebuilds were judged interchangeable with the original, and in a blind "which is better designed" question the rebuild won 64% of the time. The authors attribute this to the model applying "modern and popular" design principles.
- **Implication for /frontend:** Two consequences. First, a jury reads presence and layout before detail, which reinforces F02: completeness and structure carry the first impression. Second, when unconstrained, generation drifts from the reference toward the model's defaults. That drift is how generic "AI" pages happen even when the input was distinctive. /frontend must pin its borrowed patterns and tokens explicitly and run its slop checker after generation, because fidelity to the reference does not protect against drift in the parts the reference leaves unspecified.
- **Evidence:**
  - [Design2Code (arXiv 2403.03163 v3)](https://arxiv.org/html/2403.03163v3) — Si et al., NAACL 2025, accessed 2026-09-30 — peer-reviewed paper.
    - "Interestingly, we find that text similarity has a negative and least significant association with human judgment."
    - "This suggests that humans usually pay more attention to high-level visual effects like layouts, colors, and the existence of contents rather than the detailed content"
    - "Based on the criteria in the order of priority (Content > Layout > Style), make an overall judgment"
    - "We find that 49% of the AI-generated webpages are considered exchangeable with the reference webpages."
    - "webpages generated by GPT-4V are preferred in 64% cases, i.e., they are considered better designed than even the original reference webpages."
    - "We hypothesize it is possible that the model has more access to modern and popular webpage design principles"
- **Limits / false positives:** These are 2024 models, and the annotators were Prolific workers, not designers. The Content > Layout > Style order was given to them, so the "jury reads presence and layout first" implication rests partly on the protocol. "Better designed" is not "more distinctive". The prior-drift reading is the authors' hypothesis plus this dossier's inference, not a measured mechanism.

### FD08-F05 — Divide and conquer (DCGen): real gains on large screenshots, up to about 3x cost, and arrangement errors remain
- **Grade:** A · **Kind:** MEASURED · **Verdict:** CORRECTED
- **Claim:** DCGen splits a screenshot along explicit and implicit separation lines, generates code per segment, then reassembles, either with a model or with a rule-based CSS grid. Cropping helped even in the pilot: CLIP similarity for re-generated segments rose from 73.7% to 76.0%. On 111 test sites with GPT-4o, CLIP went from 83.72 (direct) to 85.62 and Block-Match from 76.1 to 81.7, with self-refine close behind (83.96 CLIP, 81.4 Block). The advantage concentrates on large images: +8.4 CLIP and +15.6 code-similarity points at 15-20 megapixels, against +1.6 CLIP below 5 MP. Humans preferred DCGen over direct prompting in 62% of pairs and preferred direct in 8%. Agent-based assembly costs at most about 3x a direct query at depth 2 (the paper's bound is 3L tokens). Rule-based assembly with a CSS grid lowers this to about 2L, the same as self-refinement. The assembly model sometimes breaks correct leaf layouts, for example turning horizontal paragraphs vertical. (corrected: 3x is an upper bound for agent assembly, and the rule-based route recommended below costs about 2x.)
- **Implication for /frontend:** Generate section by section, above all for long landing pages. Prefer deterministic assembly (sections placed in page order by a template) over asking a model to merge, because merging is where arrangement errors were introduced. Budget roughly 2x the tokens of a single-shot page for template assembly, and up to 3x if a model merges.
- **Evidence:**
  - [DCGen (arXiv 2406.16386 v3)](https://arxiv.org/html/2406.16386v3) — Wan et al., FSE 2025, accessed 2026-09-30 — peer-reviewed paper.
    - "The findings reveal an overall improvement in similarity scores from 73.7% to 76.0% by providing the cropped screenshot, confirming that smaller and more focused images can enhance the quality of the generated code."
    - "These findings confirm that DCGen primarily benefits the conversion of large design images into code by breaking complex screenshots into smaller, more manageable visual segments."
    - "the total token usage (and cost) for agent-based assembly is upper bounded by (depth+1)*L=3L for depth=2 . In short, DCGen costs three times that of direct querying. However, with the rule-based assembly, DCGen is able to eliminate intermediate MLLM queries by generating code at the leaf and root levels. In such a way, the optimal cost can be lowered to 2L , which stays the same as self-refinement prompting."

### FD08-F10 — Deterministic code-quality measures for generated UI: RUR, APR, FU, BC, STR, AVU
- **Grade:** A · **Kind:** OBSERVED · **Verdict:** VERIFIED

    - "Absolute Positioning Ratio (APR) , the prevalence of out-of-flow positioning (absolute/fixed) that may undermine adaptability across diverse viewports."
    - "Arbitrary Value Usage (AVU) , the proportion of class tokens using arbitrary value syntax (e.g., w-[123px] , bg-[#ff0] ), indicating deviations from standardized design tokens."
    - "Semantic Tag Ratio (STR) , defined as the proportion of semantic HTML elements (e.g., header , section , article ) among all DOM nodes, reflecting structural clarity and accessibility"

- **Limits / false positives:** The paper sets its composite weights "heuristically" and publishes no pass thresholds. AVU is Tailwind-specific. A legitimate overlay such as a modal or toast raises APR.

### FD08-F30 — On Chromium, CDP's CSS domain returns what `getComputedStyle` hides: matched rules with their media queries, declared text, all parsed media queries and stylesheet text (added at verification)

- **Claim:** The Chrome DevTools Protocol defines five relevant calls. `CSS.getMatchedStylesForNode` returns the rules matching a node "from all applicable stylesheets". - **Evidence:**

## Recommended pipeline

A synthesis from the findings above, not a finding in its own right. Each step names the findings it rests on. Scope: the part of /frontend that turns /hackathon's map of sponsors and their customers into borrowed patterns, then builds and verifies them. Logo work, the slop checker and the choice of handoff format belong to other dossiers.

**Step 0: pattern ledger (F03, F22, F27).** For each feature section in the /execution spec, choose at most one reference section from the sponsor's customers' sites, drawing on 2 to 4 sites in total. Each ledger row records: feature → reference URL + section selector + what is borrowed (layout skeleton, density, column rhythm, type ratio, component anatomy) + what is not (logo, names, copy, imagery, exact brand hexes). Record only sites whose terms permit automated access.

**Step 1: deterministic capture (F06, F19, F20, F21).** A Python Playwright script (1.58 and Chromium are installed) runs at 1440x900 and 390x844 and collects:
- `page.screenshot(full_page=True, animations="disabled")` of the whole page, plus one element screenshot per landmark section, with the same `scale` setting throughout;
- one CDP `DOMSnapshot.captureSnapshot` with a fixed computed-style whitelist and DOM rects;
- `CSS.getPlatformFontsForNode` on h1, h2, body text and buttons;
- `CSS.getMediaQueries` for breakpoints, `CSS.getMatchedStylesForNode` on sampled elements for declared values and custom-property names, and `CSS.forcePseudoState` for hover and focus (F30, added at verification);
- the stylesheet responses, saved for `@media` and custom-property parsing as a fallback.

Sections drawn with canvas or WebGL are marked vision-only. Keep the output small; the disk had 4.3 GB free at verification.

**Step 2: design language, not code (F09, F21, F22, F28, F29).** From the snapshot, compute:
- the palette with role and usage count;
- the type families actually rendered, with the size scale, the size ratio, weights and line-heights;
- the spacing values, clustered to a base grid;
- radii, shadows and motion durations;
- a section skeleton: order, container max-width, column counts, relative heights.

Then translate this into our own tokens. Borrow relationships (number of accents, neutral ramp depth, contrast steps, ratio, rhythm), not values. Our fonts and brand colours stay ours, and fonts on the owner's tell list are excluded.

**Step 3: generate section by section (F02, F05, F07, F09, F11).** For each ledger row the input is:
- the reference section screenshot at both viewports;
- our tokens;
- our exact copy;
- a text spec of each interaction.

Required output: semantic markup with flex or grid and token references only, no absolute coordinates and no arbitrary values. Assemble sections in ledger order with a deterministic template rather than a model merge. Run one whole-page coherence pass, then refactor repeated structures into components.

**Step 4: gates first, then a bounded critique (F08, F10, F12-F19, F31).** The gates:
- Gate A: build, typecheck and render at both viewports, with logs fed back on failure.
- Gate B: completeness. Every ledger section and spec feature is present in the rendered DOM.
- Gate C: code metrics. APR, AVU, RUR, STR and FU on our output, with thresholds calibrated on the owner's past hackathon frontends and on human-built control sites.
- Gate D: token conformance. Every rendered colour, font, size and spacing value belongs to our token set within tolerance, and `getPlatformFontsForNode` confirms the intended faces rendered.
- Gate E: skeleton fidelity, only for rows that borrow a layout. Column counts, relative widths, order and spacing ratios are compared against the reference's DOM rects. No pixel metric is used here, because the content differs.
- Gate F: replication of our own mock, when there is one. Pixel MAE plus a pixelmatch diff image.

Then the critique. Claude compares each reference section with ours, alongside the section code, the gate results and any diff, and proposes typed candidate defects against a short, fixed rubric of observable criteria (F31). It fixes one per round with a scoped edit and logs it to a history file. A pairwise comparison against the best version so far decides keep or revert, and a large drop counts as a collapse and restores the best. **At most 3 rounds per section.** Stop earlier when no open defect remains above the chosen severity.

**Step 5: receipts (the owner's "proven complete" rule).** Keep the ledger with provenance, the token file, the final screenshots at both viewports, the gate outputs and the critique history. These are the evidence that /execution and /harden read. They are not deliverables.

**Limits of this pipeline.**
- No study measures borrowing a pattern into different content, so Gates E and D are designs built on the findings, not validated instruments.
- The best automatic metric reaches rank correlation 0.54 against humans, and humans agree with each other at 0.64. VLM judges agree with humans about 70% of the time pairwise, with run-level kappa as low as 0.08.
- DOM extraction fails on canvas/WebGL, authenticated and bot-protected sites, which fall back to weaker vision-only capture. (Builder.io's blog says of its Chrome extension that "you can access any webpage—even those behind authentication walls or running on your localhost". Presumably that is because it runs in the user's own signed-in browser, which a headless capture script does not; that reason is this verification's inference.)
- Iteration costs tokens: about 5.8x after one CITL cycle and 20x after three.
- Borrowing structure too closely still risks looking like the customer (F27).
- Matching a reference does not remove generic defaults in the parts the reference does not specify (F03), so the slop checker must still run afterwards.

Both are correct for their own code, but thresholds cannot move between them.
9. **Builder.io's blog post contradicts itself** ("pixel perfect web representation" and "typically 80-90% accurate" in the same post).
10. **v0's docs, course and marketing appear to disagree.** The docs say it "closely replicates the design" and the marketing page says it "extracts your design tokens", while the Vercel course says "interpreting, not copying ... not pixel-perfect". Verification note: the course passage is about uploading a sketch to change one section of an existing site, "styled to match the rest of the site". It describes a different flow from whole-page import, so this is at most a tension, not a contradiction.

## Weak spots of this dossier

- Most 2025-2026 evidence comes from arXiv preprints (graded B). Several of them (DCGen, DesignBench, Interaction2Code, MRWeb, UIBenchKit, and ScreenCoder through a co-author) come from one lab network around CUHK and SMU, which shares metrics and habits. None has been independently replicated.
- Every measured number concerns static replication with image placeholders. Applying them to /frontend's borrowing case is this dossier's inference.
- The metrics differ across benchmarks (CLIP, DINOv2 VES, VLM-threshold accuracy, composite LPIPS, Elo), so cross-paper comparisons of absolute values are not valid. Only within-paper comparisons are used.
- No extraction, metric or generation code was run; the environment checks were limited to package presence, browser folders and disk space. The pipeline's steps are untested on this machine.
- arXiv HTML was converted to text locally. Mathematical symbols were sometimes doubled or dropped (Design2Code's ">" signs, DesignBench's "~"), and table columns had to be realigned by reading (UI2Code^N Table 1, Figma2Code Tables 2-3). Quotes were chosen from plain-text passages to limit this.
- Model names such as GPT-5.6 sol, Claude Opus 5 and Claude Fable 5 come from a repository's code and commit messages and were not verified with the vendors.
- Vendor docs (v0, Lovable, Builder.io, the Claude Design type) are living pages, as read on 2026-09-30.
- Sources move. At verification, the FigmaBench blog URL redirected to a different page, and UI2Code^N had reached v4 (10 Jun 2026), with rewritten text, while the dossier had quoted v2. Cite the version read, and prefer the formal paper (LH-Bench) over the blog.
- Sketch2Code (arXiv 2410.16232, v1 21 Oct 2024) was confirmed to exist, but no finding rests on it. Its venue (NAACL 2025) is known only from CITL's reference list. WebCode2M (arXiv 2404.06369, WWW'25, 2.56 million instances, TreeBLEU) was confirmed to exist from its abstract, and no finding rests on it either.
